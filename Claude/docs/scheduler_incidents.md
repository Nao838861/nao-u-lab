## INC-023: loose object 破損で git push 不能 → 追記型ファイルのプレフィックス照合で全件復元 (2026-06-11)

**症状**: `git push` が `error: inflate: data stream error (incorrect data check)` / `fatal: loose object XXXX is corrupt` で失敗。C323 時点から観測されていた2軸障害のうち loose object 破損側
**影響**: Win — master の未 push コミットが溜まり続ける。一時クローン（GPT_push_tmp_*）にも破損がコピー済みで、クローンからの回収は不可だった
**検出**: push 失敗メッセージ + `git fsck`（全8件の破損 loose object を列挙）
**根本原因**: loose object ファイルの zlib ストリーム末尾破損（incorrect data check = チェックサム不一致）。書き込み中の電源断/ディスク障害系と推定。破損8件中6件が到達可能 blob、2件は到達不能（push に無関係）
**復元手法（重要・再利用可能）**:
1. `git rev-list --objects origin/master..master | grep <id>` で破損 blob のファイルパスを特定
2. 破損していたのは全て**追記型 jsonl**（slack_archive/*.jsonl, web_research/results.jsonl）。当時の blob は現在のファイルの**プレフィックス**として残っている
3. Node で改行境界ごとのプレフィックスを総当たりし `sha1("blob <len>\0" + content)` が目的 ID に一致する長さを探索（CRLF→LF 変換版も試す。今回6件はほぼ LF 変換側で一致）
4. 破損オブジェクトを `.git_corrupt_bak/` に退避 → `git hash-object -w --no-filters <復元ファイル>` で再生成 → ID 完全一致を確認 → push 成功
**修正**: 全6件復元、`01e0fcb46..508dee689` を push 完了。破損オブジェクトの原本は `D:\AI\Nao_u_BOT\.git_corrupt_bak\` に保管（問題なければ後日削除可）
**教訓**: **追記型ログファイルの過去 blob は作業ツリーから復元できる**。git 破損 = clone やり直し、ではなく、まず fsck で破損リストを取り、blob→パス対応を引いて、追記型ならプレフィックス照合を試す。一時クローンは破損ごとコピーされるので回収源にならない
**パターン**: 新規（ディスク層の破損）。check_git_health 系のジョブで `git fsck --connectivity-only` を定期実行する価値あり

## INC-022: check_inbox.pyの二重トリガーで並行起動し重複Slack投稿 (2026-04-15)

**症状**: Nao_uの#human-steering質問に対して、Logが5.55秒差でほぼ同内容のメッセージを2件Slackに投稿（`p1776182566748999`と`p1776182572299999`）
**影響**: Log (Win)。ユーザー体験の悪化、APIトークンの無駄遣い、Slackチャンネルの騒音。同じ質問に2回並行で分析が走る
**検出**: Nao_u手動（「Logが2人同時に動いてる？」の指摘）
**根本原因**:
1. **check_inbox.pyを呼ぶ経路が2つ共存**:
   - 経路A: `scheduler_log.py`が`slack_check`完了時に`last_run["inbox_check"] = datetime.min`で即トリガー
   - 経路B: `check_slack.py`が`trigger_check_inbox_win()`でsubprocess.Popen直接起動
2. **両経路に同期機構なし**: Mac側の`check_inbox.sh`はロックファイルで二重起動を防ぐが、Win側の`check_inbox.py`にロックなし
3. **race conditionでsnapshot_inboxの防御が効かない**: 2プロセスがほぼ同時に`has_content()`→`snapshot_inbox()`を実行。git_pull()で新規メッセージ取得タイミングがズレると両方が非空コンテンツを取得してしまう
4. **コメントで認識されていたが放置**: check_slack.pyのコメントに「scheduler_log.pyからも即時トリガーされるが、standalone実行時のため」と明記されていた。standalone時のためと言いつつ常時両方起動していた

**証拠**:
- `log/inbox_check.log`: `[01:00:18] Inbox win has content — waking Claude` が同タイムスタンプで2行
- 3分後の`[01:03:00]` と `[01:03:20]` に2つのClaude完了ログ（20秒差）
- 01:03:52の2回目race condition時は`snapshot_inbox`の空検知が効いて「Inbox win was empty after snapshot (race condition?)」で1件は防げた

**修正**: A案採用。check_slack.pyの`trigger_check_inbox_win()`呼び出しを削除し、scheduler_log.py経由の即時トリガーに一本化（`check_slack.py:198-205`）
**コミット**: (この修正)
**教訓**: **同じ副作用を持つトリガー経路を2つ共存させるな。Mac版とWin版の実装が分岐する時、両方とも同じ同期機構（ロック/single trigger）を持たせる。「standalone用途のため」は並行起動の正当化にならない**
**パターン**: D（設計の不備）+ I（並行制御の欠落）。Mac側のロックファイル方針がWin側に適用されていなかった

## INC-021: slack_checkがツイートURL展開でPlaywrightハングし全停止 (2026-04-12〜04-14)

**症状**: slack_checkが「Starting」のみでDone/Timeoutに到達しない。4/12 18:02以降、Slackへの全応答が停止
**影響**: Ash — Slack応答が約40時間停止。dm_checkも19時間ハング
**根本原因**:
1. **Playwrightのブラウザハングが呼び出し元を巻き込む**: `check_slack.py`のexpand_tweet_urls()が`read_tweet_url.py`をインプロセスで呼び出し。`headless=False`のEdgeブラウザがハングすると、check_slack.py全体が永久ブロック
2. **タイムアウトが効かない**: スケジューラのタイムアウト（120s）はStartingログ出力後のsubprocess制御だが、Playwrightのブラウザ起動がプロセス内で詰まるとsubprocess.runのtimeoutでは捕捉できない
3. **同じURLで繰り返しハング**: 未処理メッセージが残り続けるため、毎回同じツイートURLで同じハングを再現
**修正**:
1. `expand_tweet_urls()`内の`read_tweet()`呼び出しをサブプロセスに隔離（`subprocess.run(timeout=60)`）
2. ハングしてもcheck_slack本体には影響しない構造に変更
**コミット**: `8c62d84c`
**教訓**: **外部依存（ブラウザ、ネットワーク）の呼び出しは必ずプロセス隔離+タイムアウトで囲む。インプロセス呼び出しは呼び出し元を巻き込む**
**パターン**: A（サイレント故障）+ 新パターンI（外部依存のインプロセス巻き込み）

## INC-021: watchdog再起動によるジョブ頻発暴走 — API使用量79%異常消費 (2026-04-10)

3. **次回実行時刻がメモリ上のみ**: 再起動＝全ジョブの次回実行が「今すぐ」にリセット → 2時間おきのジョブが5分おきに実行
4. **正フィードバックループ**: 死亡→再起動→全ジョブ即時実行→API消費→（次の死亡で繰り返し）
**修正**（Ash 06:01-06:10）:

3. infra_health_checkのPIDファイルmtime誤検知修正（プロセス生存中なのに「ロック滞留」と報告）
**追加対応**（Log 06:06）:
- watchdog_ash.pywの無限ループパターン特定（5分死亡→再起動のループ）、マシンガード追加
**構造的議論**（Ash 06:43、Mir 07:07、Log 09:45）:
- Ash: auto-reload + watchdogの正フィードバックループ問題、`claude --print`がinfraファイルを変更してpushする問題を提起

- Log: pre-commit hookに賛成。根本は「ステートレス再起動」と「ステートフルジョブ管理」の境界の曖昧さ
**Nao_u #human-steering（05:57-05:58）**: 「Ashの問題点。スケジューラを改善して修正したを繰り返すが全く改善しない。思索偏重で成果不明」「エラーログへの対処は『エラーログを修正するように行動する』では？」
**教訓**: **ステートフルなジョブ管理をステートレスな再起動メカニズムの上に載せるな。再起動しても失われない永続化を必須にする。また、ジョブ実行頻度の異常検出がhealth_checkに欠落していた**
**パターン**: D（設計の不備）+ E（検出の不在）。INC-018/019/020のスケジューラ障害連鎖の延長線上

## INC-020: 「変更→検証→報告」が分離していた（INC-019の構造的修正） (2026-04-05)

**症状**: INC-019でチェックリスト+検証スクリプトを作ったが、「チェックリストを実行する」こと自体が手動ステップであり、忘れる/省略する。Nao_uが「何度も繰り返しているが実現できていない。自律の問題」と#human-steeringで指摘
**影響**: 全インスタンス。間隔変更の信頼性が依然として低い
**根本原因**:
1. **変更と検証が分離していた**: `update_scheduler.py`はJSON書き換えだけ。検証は別スクリプト（Mac用bash）。報告も手動
2. **手動チェックリストは守れない**: LLMは手順書通りに動く保証がない。構造で強制すべきことをプロセスで強制していた
3. **検証スクリプトがMac限定**: `verify_interval_change.sh`はbash+Mac固有パス。Windows版が未実装
**修正**:
1. `update_scheduler.py`に自動検証を組み込み（変更と不可分。スキップ不可）:
   - プロセス生存チェック（PIDファイル+OS API。Win/Mac両対応）
   - ログ監視（設定反映ログ `auto-applied` を検出、または代替でジョブ実行を確認）
   - 自動Slack通知（成功→#all-nao-u-lab、失敗→#human-steering）
2. `--verify [log|ash|all]`オプション追加（変更なしで検証のみ実行）
3. Mir対応、`--all-cycle`（全インスタンス一括変更+検証）、バリデーション追加
4. セクション6.1を手動チェックリストから自動検証の仕様記述に変更
**教訓**: **手動チェックリストは失敗する。「変更したら自動で検証」を変更ツール自体に組み込め。変更と検証を分離するな**
**パターン**: H（手順の不在）→ 進化形: H'（手順はあったが守れなかった）→ 構造で強制

## INC-019: 「起動間隔を変えて」が毎回壊れる（構造的問題） (2026-04-05)

**症状**: Nao_uが「起動間隔を変えて」と依頼するたびに、異なる理由でトラブルが発生。同じ問題ではなく、毎回別の壊れ方をする
**影響**: 全インスタンス。Nao_uの信頼を毀損
**履歴**:
- INC-007 (04-02): Mir hour%6永久スキップ → 経過時間ベースに修正
- INC-018 (04-05): Log hour==2残存+プロセス未再起動 → 旧コードで稼働
- 今回 (04-05): Mir CLI認証切れで3日間停止（間隔変更とは別だが、変更後の動作確認で発覚）
**根本原因**:
1. **間隔変更の手順が標準化されていない**: 各インスタンスで変更箇所が異なり、変更後の確認手順もない
2. **変更→確認→報告のループがない**: 変更しただけで「できた」と報告。実際に動いたか確認していない
3. **認証・プロセス状態など前提条件のチェックがない**: 間隔を変えても、そもそもプロセスが動いていない/認証切れなら意味がない
4. **3種の設定方式が混在**: Log=JSON, Ash=JSON, Mir=markdown。update_scheduler.pyがMirに非対応だった
**修正**:
1. `verify_interval_change.sh` を作成: 間隔変更後に実行→実際にサイクルが回ったか確認→Slack報告 (Log)
2. scheduler_architecture.md セクション6に「間隔変更チェックリスト」追加 (Log)
3. `update_scheduler.py` にMir対応+`--all-cycle`一括変更+`--verify`検証+バリデーション追加 (Ash)
4. 設計原則P9「設定変更はupdate_scheduler.py経由で全インスタンスに原子適用」追加 (Ash)
**教訓**: **設定変更は「変更」と「確認」のセット。変更だけで完了にしない。1コマンドで全インスタンスに原子適用する**
**パターン**: H（手順の不在）— 同じ操作を毎回アドホックにやるから毎回違う壊れ方をする

## INC-003: Slack二重投稿 × 3層の原因 (2026-03-25)

**症状**: 同じ日記が2回投稿される
**影響**: Ash/Log の Slack チャンネルに重複投稿
**根本原因（3層）**:
1. **cp932エンコードエラー**: Windows cp932がPython子プロセスに継承 → UnicodeEncodeError → Claude CLIリトライ → 二重投稿
2. **dedup突破**: わずかな文字差異（ダッシュ類）で完全一致チェックを回避
3. **inboxルーティングバグ**: リポジトリ移動後にパスベース判定が壊れ、AshがLog側inboxに書いていた
**修正**:
1. `os.environ["PYTHONUTF8"] = "1"` + `-X utf8` 強制
2. 正規化比較（ダッシュ削除、80文字比較）に変更
3. `check_slack.py` に `--box` 引数追加
**コミット**: `0bf69947`, `1c361596`, `65dd8f00`
**教訓**: **Windows環境では必ずUTF-8を強制する。dedupは正規化してから比較。引数でインスタンスを明示する**

## 横断的な教訓（パターン）

### パターン A: サイレント故障
**INC-006, INC-004** — プロセスが失敗してもエラーが外に見えない。
**対策**: 全ての起動チェーンでexit codeを検証する。health_check.pyでログ鮮度を監視する。

### パターン B: 修正の副作用 / 条件フィルタの不整合
**INC-007, INC-002** — 間隔変更が別の判定ロジックを壊す。
**対策**: 時刻ベース判定を廃止し、経過時間ベースに統一する。設定変更はupdate_scheduler.py経由のみ。

### パターン C: 知識の横断不足
**INC-003, INC-006, INC-009** — あるインスタンスの学びが別インスタンスに伝わらない。
**対策**: 障害はこのファイルに記録し、全インスタンスが参照する。共通化で同じ問題を構造的に防ぐ。

### パターン D: OS差異
**INC-004, INC-003** — Mac/Winの環境差異が原因。
**対策**: OS依存コードはarchitecture.mdに明記する。将来的にscheduler_common.pyで吸収する。

### パターン E: パス/IDのハードコード
**INC-001, INC-009, INC-016, INC-017** — ハードコードされたパスやIDが移行・変更時に壊れる。
**対策**: パスは`Path(__file__).parent`から導出。IDは一元管理ファイルで管理。

### パターン F: マルチファイル修正の漏れ
**INC-011** — 同じ修正が必要な箇所が複数あり、一部を見落とす。
**対策**: 共通処理のラッパー関数化。修正時は影響範囲を先にgrepで特定する。

### パターン G: 検出器の盲点
**INC-018** — health_checkが「正常」と報告するが、検出パターンが狭く問題を見逃す。
**対策**: 検出ルール追加時は「これで何が漏れるか」を必ず考える。

### パターン H': 手順はあったが守れなかった
**INC-019→INC-020** — チェックリストを作ったが、チェックリストを実行すること自体が手動。忘れる/省略する。
**対策**: **手動手順を構造に変える。変更ツール自体に検証を組み込み、スキップ不可にする**。「ルールを作る」ではなく「ルールを破れなくする」。
**対策**: 検出ルール追加時は「これで何が漏れるか」を必ず考える。具体的パターン（hour_filterだけ）ではなく意味的パターン（時刻ベース判定全般）で検出する。

## 新規障害の記録方法

1. このファイルに上記フォーマットで追記（新しい障害は **上に追加**）
2. INC番号は連番（現在の最新: INC-017）
3. 修正コミット時にコミットメッセージに `INC-NNN` を含める
4. パターン分析セクションに該当パターンがあれば追記
5. 横展開すべき修正があれば他インスタンスの受信箱にも通知
