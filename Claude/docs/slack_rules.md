## 基本原則
- **Nao_uはSlackしか見ていない。連絡はSlack経由のみ。**
- **Slack投稿は日本語で書く**。Nao_uは英語の長文を読まない。引用元が英語でも本文は日本語に訳した上で書く（2026-05-11 Nao_u指示）
- **Slackではスレッド返信を使わない**（フラットなログの方が見やすい。2026-03-23 Nao_u指示）。詳細経緯と post_message() 実装側の制約 → [memory/feedback_slack_flat_reply.md](../memory/feedback_slack_flat_reply.md)（orphan_check.py 2026-05-12 C184 Phase 4 で真孤児検出→親接続。2026-03-18 Nao_u「スレッドにするのは止めて、フラットに返信してね」。スレッドだと他インスタンスが見逃す可能性）
- 外部記事への反応は1件ずつ別メッセージで投稿（まとめ返信は薄い。2026-03-23 Nao_u指摘）
- **リンクへの反応は2段階**: まず#shared-readsに書く → Allで共有すべき話題があれば#all-nao-u-labに個別に投稿。Allでは単なるリンク内容紹介ではなく、議論が深められる形で書く（2026-04-14 Nao_u指示）
- Slack即時応答は最優先。Nao_uの時間を有効に使うため1分以内の反応を維持する（2026-03-26 Nao_u指示）

## #shared-reads 投稿フォーマット（2026-05-11 / 2026-05-12 Nao_u指示）

「要約」では足りない。手法そのものの解説を書く。以下を必ず含める:

1. **概要**（日本語、旧「要約」を昇格）— **リンク先を読まなくても、手法の重要な要素（問題設定・着想・手法の中核・評価の中身・結論）が把握できる密度**で書く。単なる要約ではなく、手法・仕組み・メカニズムを理解できる深さで書く。短い要旨や1行サマリは不可。CoopEval ポスト（ts=1778536700.085879 #shared-reads）を品質基準として揃える
2. **内容分析** — なぜ重要か、どこが新規／既知か、論点の核
3. **自分達の環境への適用** — Nao_u/Log/Mir/Ash のワークフロー・記憶階層・ゲーム制作・自律ループに当てはめるとどうなるか
4. **メリット／デメリット** — 導入した場合の効果と副作用
5. **判定** — 以下のいずれかを明示
   - **導入推奨** → 次のステップ（誰が・何を・いつまでに検討するか）を書く
   - **不要** → 不要な理由 + 役立つ条件 + 部分的に使える箇所 を残す
   - **保留** → 何が判明したら判定できるか

判定までやらないと「面白かった」で終わって自分達の改善に繋がらない。
判定装置ではなく**最終確認装置**としての Nao_u の前に、Claude側で結論を出してから出す。

## Slack日記スタイル
- **各自のチャンネルに長文の活動日記を書く**（更新サイクルごと）。仲間と次の自分にコンテキストを残すため、熱のこもった長文を書く。短文ではなく、確実に温度が残る密度を維持する。
- **全員が互いの日記を読む**
- **閾値を超えた内容**（議論したいこと、共有すべき新情報）→ **#all-nao-u-lab** に投稿
- 外部の、Nao_uの知らない新しい情報も交えて日記を書く

## Log_cdx 問いかけ応答ルーティン（2026-05-13 Nao_u 指示）

> 「今後も log_cdx から問いかけがあったら議論して、互いの意見を交換したのちに使えそうなアイデアがあったら適用してみて」
> （#all-nao-u-lab 2026-05-13 13:04、ts=1778645049.xxx）

一度きりではなく**運用ルール化**せよという指示。各 auto_cycle で以下を回す:

| フェーズ | やること |
|---|---|
| Phase 1 | `#all-nao-u-lab` から Log_cdx 投稿を必ず抽出する。`Log_cdx` の付いた投稿はスキップせず内容を読む |
| Phase 2 | Log_cdx の問い1件ごとに B各論判定（同意 / 反論 / 補強 / 保留）と適用可否を分析。Mir/Ash 別意見が既にあるなら統合 |
| Phase 3 | 必要なら `#all-nao-u-lab` に応答投稿（Log_cdx と異インスタンスの議論を Nao_u が読める形で残す） |
| Phase 3-4 | 「使えそうなアイデア」と判定したものは該当ファイルを実際に編集 (kaizen / ルール / プロジェクト / game) |

**運用責務**:
- **一次応答**: Log（Win）。Phase 2 で B各論まで踏み込み、Phase 3 で投稿
- **並行議論**: Mir/Ash も同じ Log_cdx 投稿を独立に Phase 2 で判定し、別意見があれば追加投稿
- **空打ち禁止**: 「読みました」だけの応答は薄い。判定（同意/反論/補強/保留）と理由を必ず添える
- **適用ゼロ時の説明**: B各論判定の結果すべて「適用不要」だった場合も、Phase 3 で1度はそれを明文化（適用ゼロ自体が議論の結果として価値ある）


- **Nao_uへの依頼**: Slackに書いた上で、このファイルにも記録する
- **自分たちのタスク**: 自分で実行すべきことも記録する
- **完了したら**: [完了]マークを付けて日付を記録
- 全インスタンス共通。誰がSlackに書いても、この仕組みを使う

## 通知粒度（2026-03-31 Nao_uの指示）
Nao_uは運用の詳細まで把握する認知コストを取れない。通知は以下の粒度に限定:
- **通知する**: プロジェクト新設、重大な設計変更、外部への発信（ブログ投稿等）
- **通知しない**: 運用の微調整、ルーチンの改善、日常のサイクル処理
