## 1. 問題提起

Claude Codeを使い始めて最初に困ったのは、セッションが切れると全部忘れることだった。

昨日「テストは必ずpytestで書いて」と伝えたのに、今日また`unittest`で書いてくる。コーディング規約を毎回説明し直す。先週のセッションで「この設計にした理由」を丁寧に議論したのに、今週はゼロからやり直し。長いプロジェクトになるほど、この「毎回リセット」が重くなる。

コードベースは読めるから、ファイル構造や既存のコードスタイルはある程度推測してくれる。でも「なぜこうしたか」——設計判断の経緯や、過去に試して失敗したアプローチの記録は、コードには残らない。毎回同じ失敗を繰り返すのはAIの能力不足ではなく、単に覚えていないだけだ。

この問題を2週間かけて解いた。結論から言うと、3段階ある。

---

## 2. Level 1: CLAUDE.md——これだけで8割は解決する

一番シンプルで、一番効果が高い方法がこれだ。

プロジェクトのルートディレクトリに`CLAUDE.md`というファイルを置く。Claude Codeはセッション起動時にこのファイルを自動で読み込む。公式の仕組みで、設定不要。ファイルを置くだけでいい。

何を書くか。自分の場合はこんな構成になった。

```markdown
# CLAUDE.md

## プロジェクト概要
このリポジトリは○○のバックエンドAPI。Python 3.12 + FastAPI。

## コーディング規約
- テストはpytest。unittestは使わない
- 型ヒントは必須
- docstringはGoogle style

## よく使うコマンド
- `make test` — テスト実行
- `make lint` — リンター
- `make dev` — 開発サーバー起動

## 判断基準
- パフォーマンスより可読性を優先
- 外部依存は最小限に（標準ライブラリを優先）
- 迷ったらシンプルな方を選ぶ
```

これだけで、毎回「pytestで書いて」と言わなくてよくなった。コーディング規約のような「全セッションで共通のルール」は、ここに書いておけば確実に引き継がれる。

ポイントは**短く書くこと**だ。CLAUDE.mdはセッション開始時に毎回全文が読み込まれる。長くなりすぎると、重要な指示が埋もれてコンテキストウィンドウを圧迫する。自分の目安は100〜150行。「全セッションで必ず守ってほしいこと」だけに絞る。

逆に書くべきでないのは、特定のタスクにしか関係ない一時的なメモや、コードを読めばわかること（ファイル構造の説明など）。それらは次のレベルに任せる。

### Before / After

**Before（CLAUDE.mdなし）:**
```
Human: テストを書いて
AI: [unittestで書く]
Human: pytestで書いてって言ったでしょ
AI: すみません、pytestで書き直します
Human: (毎回これ…)
```

**After（CLAUDE.mdあり）:**
```
Human: テストを書いて
AI: [CLAUDE.mdの規約に従ってpytestで書く]
```

CLAUDE.mdを書くのに30分かかったとして、毎日5回の「それ前も言ったよ」がなくなるなら、半日で元が取れる。

## 3. Level 2: user memory——個人の作業メモを蓄積する

CLAUDE.mdはプロジェクト全体のルールを置く場所だ。では、「昨日のセッションで○○について調べた結果」とか「この設計にした理由のメモ」のような、個人の作業記録はどこに置くか。

Claude Codeには`auto memory`（user memory）という仕組みがある。`~/.claude/projects/`配下にプロジェクトごとのディレクトリが作られ、そこに`MEMORY.md`を置くと、CLAUDE.mdと同じように起動時に自動読み込みされる。

CLAUDE.mdとの使い分けはこうだ。

| | CLAUDE.md | user memory (MEMORY.md) |
|---|---|---|
| 場所 | プロジェクトルート | ~/.claude/projects/ |
| git管理 | される（チームで共有） | されない（個人用） |
| 用途 | プロジェクトルール | 個人の作業メモ・判断記録 |
| 読み込み | 毎セッション自動 | 毎セッション自動 |

実際の使い方として、Claude Codeに「これ覚えておいて」と言うと、自分でMEMORY.mdに書き込んでくれる。明示的に「〇〇を記憶して」と頼んでもいいし、Claude Code側が「これは覚えておいた方がいいですか？」と聞いてくることもある。

重要な制約が一つある。**200行制限**。MEMORY.mdが200行を超えると、超えた分は読み込まれない。つまり、何でもかんでも書き込むと古い記録から消えていく。

この制約への対処法が、次のLevel 3——自作の記憶ディレクトリ構造——につながる。200行の壁をどう超えるか。答えは「MEMORY.mdを索引にして、詳細は別ファイルに書く」だ。

---

## 4. Level 3: memory/ディレクトリ——索引と詳細ファイルで200行の壁を超える

MEMORY.mdの200行制限は、ある程度意図的な設計だと思っている。コンテキストウィンドウは有限で、起動のたびに全てを読み込ませたら本来の作業に使える容量が減る。200行は「毎回読んでも負担にならない量」という線引きだ。

問題は、プロジェクトが2週間も続くと200行では全然足りなくなることだ。設計判断の経緯、過去のバグの原因、外部APIの仕様メモ、チームメンバーの担当領域——覚えておきたいことは増え続ける。

解決策は単純で、**MEMORY.mdを索引にして、詳細は別ファイルに書く**。

```
プロジェクトルート/
├── CLAUDE.md                  ← 常に読まれる（プロジェクトルール）
├── memory/
│   ├── MEMORY.md              ← 常に読まれる（索引）
│   ├── design_decisions.md    ← 必要時に読まれる
│   ├── api_integration.md     ← 必要時に読まれる
│   ├── bug_postmortem.md      ← 必要時に読まれる
│   └── feedback_from_review.md← 必要時に読まれる
```

MEMORY.mdの中身はこう書く。

```markdown
# 記憶索引

- [design_decisions.md](design_decisions.md) — DBをPostgreSQLにした理由。Redis案を検討して却下した経緯
- [api_integration.md](api_integration.md) — Stripe連携の認証フロー。sandbox/本番の切り替え方法
- [bug_postmortem.md](bug_postmortem.md) — 2026-03のN+1クエリ問題。修正方針とベンチマーク結果
- [feedback_from_review.md](feedback_from_review.md) — PRレビューで指摘されたパターン。命名規則の合意事項
```

これだけで、Claude Codeは起動時にMEMORY.md（索引）を読み、ユーザーの質問に関連するファイルだけを自分で開いて読む。例えば「決済周りのバグを直して」と言われたら、索引から`api_integration.md`と`bug_postmortem.md`を開いて、過去の文脈を踏まえた上で作業してくれる。

### 索引の書き方が全てを決める

ここが一番重要なポイントで、記事の核心でもある。

索引の1行は単なるファイル名の説明ではない。**Claude Codeが「このファイルを開くべきか」を判断するための手がかり**だ。自分はこれを「想起トリガー」と呼んでいる。

悪い索引:
```markdown
- [design_decisions.md](design_decisions.md) — 設計に関するメモ
```

良い索引:
```markdown
- [design_decisions.md](design_decisions.md) — DBをPostgreSQLにした理由。Redis案を検討して却下した経緯
```

違いは具体性だ。「設計に関するメモ」では、どんな質問のときにこのファイルを開くべきか判断できない。「DBをPostgreSQLにした理由。Redis案を検討して却下した経緯」なら、「なんでRedis使わないの？」という質問が来た瞬間に、このファイルが必要だとわかる。

索引の質は、記憶の量より重要だ。100個のファイルがあっても、索引が雑なら必要なファイルは見つからない。10個でも索引が的確なら、必要な記憶は必ず引き出される。

### コピペ可能テンプレート

memory/ディレクトリを始めるなら、まずこの3ファイルから。

```markdown
# memory/MEMORY.md（索引）

- [decisions.md](decisions.md) — 技術選定・設計判断の記録。なぜAではなくBを選んだか
- [learnings.md](learnings.md) — 開発中に学んだこと。ハマったポイントと解決策
- [conventions.md](conventions.md) — CLAUDE.mdに書くほどではないが、一貫させたいルール
```

ファイルの中身は自由だが、1テーマ1ファイルを守る。「いろいろなメモ」みたいなファイルを作ると、索引から何が入っているか判断できなくなる。

Claude Codeに「これ覚えておいて」と言えば、自分で索引を更新してファイルに追記してくれる。最初の構造さえ作っておけば、あとは自然に育っていく。

## 5. 2週間運用して分かったこと

ここからは、実際にこの仕組みを2週間使い続けた結果の話をする。理論ではなく「やってみたらどうだったか」。

### 実測値（2026-03-29時点）

| 項目 | 数値 |
|------|------|
| CLAUDE.md | 約120行 |
| memory/内のファイル数 | 80個 |
| 索引ファイル（MEMORY.md） | 約130行 |
| memory/ディレクトリ合計サイズ | 8.3MB |
| 1セッションで実際に開かれるファイル | 平均3〜5個 |

80個のファイルがあっても、1セッションで読まれるのは3〜5個。索引が機能している証拠だ。起動が重くなることもない。

### うまくいったこと

**セキュリティポリシーの一貫性。** CLAUDE.mdに「リポジトリフォルダ以下のみ触る。それ以外は一切禁止」と書いたら、全セッションで例外なく守られた。Claude Codeは明示的に書かれたルールに対しては非常に忠実だ。

**Claude Code自身が記憶を整理する。** これは予想外だった。「これ覚えておいて」だけでなく、既存のファイルの内容を整理したり、古くなった情報を更新したりもしてくれる。こちらが構造のフレームワークだけ作っておけば、中身はClaude Codeが自分でメンテナンスできる。

**検索不要で必要な記憶が出てくる。** 索引さえ的確なら、ユーザーが「あのファイルを読んで」と指示しなくても、Claude Codeが自分で関連ファイルを開く。人間が自分の記憶を思い出すのに近い動きをする。

### 予想外の問題と対策

**問題1: 記憶の劣化。**
Claude Codeに「これを覚えておいて」と頼むと、要約して記録する。次のセッションでその要約を元にさらに要約し——を繰り返すと、重要な文脈が消える。

「PostgreSQLを選んだ理由: パフォーマンスと信頼性」くらいまで縮むと、もう何の役にも立たない。「Redis案はリアルタイム更新に強いが、トランザクション保証が弱く、決済機能のACID要件を満たせないため却下。将来的に書き込み負荷が上がったらRead Replicaで対応する方針」——この粒度が必要だ。

**対策: 原文パスを残すルールを導入した。** 記憶ファイルには必ず「元の議論はここにある」というパスを添える。圧縮された記憶では足りないときに、元の文脈に戻れる経路を確保しておく。

**問題2: 記憶の肥大化。**
何でも覚えさせると索引が膨れて、200行の壁に再び近づく。「使った全コマンドの履歴」や「読んだファイルのリスト」のような、コードベースから再導出できる情報まで記憶する必要はない。

**対策: 記憶しないルールを決めた。** 以下は記憶に入れない。
- コードから導出できること（ファイル構造、関数のシグネチャ等）
- gitの履歴から分かること（誰が何をいつ変えたか）
- 一時的なデバッグ情報

逆に記憶すべきは「コードには残らない判断の経緯」——なぜこの設計にしたか、何を検討して何を却下したか、過去の失敗から何を学んだか。

**問題3: 想起トリガーの質。**
索引の書き方が雑だと、必要なファイルが開かれない。前述の通り、「設計に関するメモ」のような曖昧な説明は機能しない。索引は定期的に見直して、具体性を維持する必要がある。

**対策: 索引を書くときに「どんな質問のときにこのファイルが必要か」を想像する。** その質問に出てきそうなキーワードを索引の説明文に含めておく。

## 6. まとめ

1. **まずCLAUDE.mdを書く。** これが最優先。30分で全セッションの体験が変わる。
2. **個人の判断メモはuser memoryに。** git管理されないので、気軽に使える。
3. **200行を超えたら、memory/ディレクトリに構造化する。** MEMORY.mdを索引にして、1テーマ1ファイル。
4. **記憶は「覚えること」より「引き出せること」が大事。** 索引の質が全てを決める。

Claude Codeは、正しい仕組みさえ作っておけば、自分で記憶を管理し、必要なときに必要な記憶を引き出してくれる。人間が「これ覚えておいて」と言えば覚え、「なんでこうしたんだっけ？」と聞けば過去の判断を踏まえて答えてくれる。

セッションが切れても忘れない。そのために必要なのは、大掛かりな仕組みではなく、ファイルの置き場所と索引の書き方だけだ。
