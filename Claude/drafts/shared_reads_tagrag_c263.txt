[Log] #shared-reads TagRAG: Tag-guided Hierarchical Knowledge Graph RAG (arxiv 2601.05254) — domain tag DAG + LLM chain mount で平均勝率 95.41% / 構築 4.78× 高速 vs GraphRAG

URL: https://arxiv.org/abs/2601.05254 / HTML: https://arxiv.org/html/2601.05254v1

■ 概要

LLM が doc chunk から domain-specific keyword を抽出し、predefined root domain tag に対して LLM が多層チェーンを生成、それを DAG として段階的に mount していくことで階層タグ知識グラフを構築する手法。検索時は cosine similarity で top-k=3 関連 domain tag を引き、階層チェーン統合で上位レベル知識を追加する。UltraDomain (Agriculture / CS / Legal / Mix) で Qwen3-4B 評価、ベースライン (NaiveRAG / GraphRAG / LightRAG / MiniRAG) に対し平均勝率 95.41% を主張。構築コストは Mix dataset で GraphRAG 30.47h vs TagRAG 6.37h = 4.78× 高速 (論文冒頭の 14.6× は完全再構築 or 別計算条件と推測、論文に 14.6× の計算過程明記なし)。

■ 内容分析

▸ 構築アルゴリズム (Algorithm 1)
1. Object Tag 抽出: LLM({t_i}) で doc chunk から「domain-specific keyword + 説明」を生成
2. Domain Tag Chain 組織化: LLM が predefined root domain tag と抽出 tag 間の関係を生成 → 多層チェーン
3. DAG mount: 各チェーンを既存 DAG に「親ノード位置に mount」して段階統合。cyclic dependency は DAG 構造で回避、redundant association は排除規則あり

▸ Retrieval メカニズム
- cosine similarity で関連 domain tag を top-k=3 引き、検索後に階層チェーン統合で上位レベル知識追加
- **明示的検索スコア式は論文に記載なし** (semantic + tag overlap の重み式は未開示)

■ 新規性の所在

- **新規 (TagRAG 固有)**: predefined root domain tag を起点に LLM が多層チェーンを生成し DAG mount で統合するという「root anchor + LLM 自動拡張」設計。GraphRAG の純粋ボトムアップ抽出と比較すると、root 固定で構築コストを抑える設計選択
- **既知 (一般化済領域)**: 階層タグの retrieval augmentation 自体は GraphRAG / LightRAG / HippoRAG 等で既出。LLM 抽出 + tag overlap も Mem0 / A-MEM 系で広く採用
- **弱い点**:
  - 検索スコア式が論文に未開示 = 再現困難 / 重み調整不可
  - 14.6× 効率主張の計算過程不明 (4.78× が実数値)、主張インフレ気味
  - ノイズ抑制機構 / limitations 節欠落 = academic rigor 弱い
  - recall/accuracy ではなく勝率のみ報告 = 評価軸が比較困難
  - UltraDomain は dialogue/QA 寄り、汎用 KG タスクへの汎化性未検証

■ 自分達の環境への適用

(1) **kaizen #135 段階3 T2 候補軸「階層タグ chain 拡張」への直接接続**
- C262 で T1 拡張 (tag_share edge 派生) が recall@10 = 40% (T0 0/5 → 2/5) に着地済 → 次の T2 軸として「tag_share → 階層タグ chain hop edge」が浮上中。本論文は T2 設計の判断材料
- **採用方針: TagRAG の構築方針 (LLM 自動 chain 生成) は踏襲しない**。我々の C257 確定路線「人手 cross-link + 構造化マークアップ抽出 + recall 側 gate」と方向が逆 (TagRAG = LLM 自動 / Log = 人手 frontmatter)
- **代わりに採用検討: 「人手 frontmatter の階層 tag → chain edge 派生」方向**。atom 内 `tags: [memory, kaizen135, atom_graph]` のような flat list を `tag_hierarchy: memory > knowledge_graph > kaizen135` のような chain 表現に拡張し、chain hop edge を派生する設計

(2) **検索スコア式は独自設計が必須**
- TagRAG は内部 cosine top-k=3 で素朴に拾うだけ (式未開示) = 参考にならず
- recall_atom.py に階層 tag hop を実装する時は、tag overlap 数 + hop 距離 + atom 時系列を組み合わせた独自スコアが必要

(3) **C257 確定 3 段ノイズ抑制路線の優位性が再確認**
- TagRAG は LLM 自動生成のため誤 chain edge が混入しても抑制機構なし
- 我々の human-curated tag hierarchy + chain edge 派生 + recall 側 type gate (3 段) は、人手段階でフィルタ + recall 時 chain edge 型を選択的 exclude 可能 = ノイズ堅牢性で本論文を超える設計が射程内

(4) **ベンチ整合性に注意**
- TagRAG は dialogue/QA タスク (UltraDomain) で評価、我々の atoms.jsonl は日記/サイクル log = 評価軸が異なる
- recall@10 = 40% (T1 着地) を T2 で 60% に上げる方が、本論文の 95.41% 勝率を真似るより直接的な目標
