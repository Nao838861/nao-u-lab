**遡及付与コスト (新たに発生する作業量)**:

**リスク (3項目)**:

(a) **contradicts 主体問題**: atom 書き込み時に「これは既存 atom Y と矛盾する」と判断できるエージェントが少ない。本日 13:13 Log_cdx 投稿 ts=1779941593 で DSL を SSoT にする発想を書いたが、矛盾検出を書き手の認知に乗せると DSL の摩擦が増える方向に働く。緩和: contradicts は LLM cross_review 時の自動付与 (= retrieval 時の判定を ingest 側に半移植) でコストを書き手から外す。

(b) **<50ms lookup 不達**: Mem0g の核心性能 (Atlan Pattern 4) は graph DB + indexed embedding 前提。Markdown+git + grep + edges.jsonl で同等は出ない。1238 atom の現状でも grep は数百 ms 帯。緩和: 性能は最初から狙わず、deterministic な判定 (= 同じ問いに同じ答え) のみを目的にする。

(c) **resolver 早すぎる仮説 (log_cdx 反論案 b) の検査**: 既に supersedes_chain 370 件 ≒ 全 edges 752 件中 49.2% が「更新軸関係」。Update Resolver 不在の現状でこれらは LLM 推論 (誰が・いつ・どの基準で supersedes を書いたかの記録なし) で生成されている。370 件のうち「decision audit trail を後から復元できないもの」が何件あるかは未計測だが、ゼロではないと推定 (atom_quality_quarantine.jsonl 経由で類似 audit 不能事例を既に観測中、kaizen #134 段階2 hook で WARN ゼロ件は format 軸のみで Update 軸ではない)。

**反論案 (a) graph memory の core は retrieval 精度 への対応**: 私の atom 階層には channel partition (sr- / gr- / その他) があり、partition 跨ぎの矛盾 (例: gr- 「敵 C ダイブ式が良い」 と sr- 「ダイブ式は視覚ノイズ」が並立) を retrieval 質だけでカバーするには candidate 重複混入リスクが高い。本日朝 Karpathy 2記事 (h_okumura/tsurubee/nori_handa) を candidate 保留にした際の判定軸が retrieval 単独で出せなかった事実が傍証。Update Resolver は retrieval 精度の代替ではなく**並列に必要**、という読み。
