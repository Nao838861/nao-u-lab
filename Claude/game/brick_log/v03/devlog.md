### 予測アルゴリズム

```
入力: ball.{x,y,vx,vy}, paddle.{x,y,w,h}, blocks[]
出力: segments[], paddleHitX, reachable, isBack, phase1StartIdx

phase = 0 (ball→paddle)
cx, cy = ball.x, ball.y
dvx, dvy = ball.vx, ball.vy

for step in 0..MAX_STEPS:
  nx, ny = cx + dvx*STEP/sp, cy + dvy*STEP/sp
  if nx out-of-bounds (左右壁): segment 終端を反射点に push、dvx 反転、segStart 更新
  if ny < BALL_R (天井): 同様、dvy 反転
  for each alive block:
    if hit: segment 終端を nx,ny に push、ループ終了 (blockHit=true)
  if phase == 0 and dvy > 0 and ny >= contactPlaneY (パドル平面到達):
    paddleHitX = 線形補間で求めた交差点
    if パドル外: reachable = false で return (✕マーカ用)
    出射ベクトル = パドル位置から計算
    phase = 1
    phase1StartIdx = segments.length (次の push が phase1 先頭)
  if phase == 1 and ny < BR_Y0: isBack = true
  cx, cy = nx, ny

末尾: if 残 segment あり: push
```

### 描画方針

- phase 0 セグメント: `rgba(180,210,255,0.40)` 幅 2px (薄水色、現ボール→パドル予測)
- phase 1 セグメント (通常): `rgba(255,200,100,0.65)` 幅 2.8px (オレンジ、パドル反射後)
- phase 1 セグメント (裏抜け): `rgba(255,230,150,0.85)` 幅 3.5px (金色)
- パドル接触予定マーカ: 通常 r=3 / 裏抜け r=4
- パドル外✕: 赤円 + ✕、半径 5px

phase 0 を薄くした理由: 常時表示で「現ボール→次パドル接触」を 2px α0.40 で出すと視野ノイズになりやすい。phase 1 (パドル反射後) こそ「自分の操作で動く対象」なので濃くする。phase 0 は副次情報。

### 設計の自己ツッコミ

1. **常時表示で目が疲れる可能性**: phase 0 を薄水色 α0.40 で抑制したが、それでも常時 1-3本の線が出続ける。実プレイで「邪魔」と評価されたら phase 0 を更に薄く / 線でなくドット列にする kaizen 候補
2. **再帰反射シミュレートの計算量**: 600 ステップ × 60 ブロック = 36000 衝突判定/フレーム × 60fps = 2.16M/秒。現代ブラウザで余裕だが、モバイル等で問題出たら早期 return（ステップ数を 300 に戻す）
3. **「予測が嘘になる」瞬間**: ブロックを壊した瞬間、次フレームでブロック配列が変わり予測線が大きく変わる。これは「予測の更新」として正しい挙動だが、視覚的には「線が突然動く」体験になる可能性。フェードトランジション kaizen 候補（実装後評価）
4. **phase 1 が短い場合の不気味**: ブロックがすぐ手前にある場合、phase 1 が 1反射目で blockHit してすぐ終わる。「線がほぼ出ない＝この狙いはダメ」のフィードバックとして機能するはずだが、初見では意味不明な可能性
5. **パドル外✕の意味伝達**: 赤円+✕は「届かない位置」を意味するが、初見で「失敗予告」と読まれる可能性（実は「動けば救える」予告でもある）。色を黄色にして「警告」へ寄せる kaizen 候補

## ヘッドレス自己評価（コード読み・サニティチェック）

**重要**: feedback_won_playtest_is_kusoge / M-15 遵守。「面白いかどうか」の判断はここでは出さない。

### (a) v02 の機構が壊れていないか

- パドル衝突 / ブロック衝突 / 速度保持 / 壁反射 / ライフ / クリア判定は v02 から無変更（コード差分は描画系と新関数 `computeFullTrajectory()` のみ）
- v02 の `computePredictionLine()` は削除（呼び出し元なし、関数本体も削除）

### (b) `computeFullTrajectory()` が機構非介入か

- `state.ball/paddle/blocks` を読み取りのみ。書き換えなし
- `update()` 関数からは呼ばれない（draw 内で毎フレーム呼ぶだけ）
- 削除 → 全飛行軌道線が消えるだけで素 Arkanoid に戻る

### (c) phase 0/1 区別の正しさ

- `phase1StartIdx = segments.length` を **paddle 反射判定後・次 push の前** に設定
- 描画ループで `i >= phase1StartIdx` を phase 1 と判定
- paddle 平面に届かない（ブロック衝突で先に止まる、または `reachable=false`）場合: `phase1StartIdx=-1` で全 segment が phase 0 扱い

### (d) `reachable=false` の動作

- パドル外接触検出時に return（その時点までの segments + paddleHitX を返す）
- 描画側で `!traj.reachable` を見て✕マーカを描く
- 出射軌道はもちろん描かれない

### (e) 視野ノイズの最大量

- phase 0 線: 通常 1-3本（壁反射の数による）、各 width=2 α=0.40
- phase 1 線: 通常 1-3本、各 width=2.8 α=0.65（裏抜けなら 3.5 α=0.85）
- マーカ: 接触予定マーカ 1個 (r=3-4) または ✕マーカ 1個
- 同時最大: phase 0 + phase 1 + マーカ = 5-6 本の線 + 1個のマーカ

v02 比で「常時表示」の分だけ視野ノイズが増えるが、phase 0 を最薄に抑制している。実プレイ判定対象。

## 自発思考失敗の振り返り（feedback_concept_relevance_judgment / feedback_external_search_missing 系列）

### 何が起きたか

v02 で `PREDICT_TRIGGER_DY` を 130→260 に伸ばしたとき、私は「Nao_u が一瞬すぎると言った→時間を増やそう」という反応的修正で止まった。「常時表示まで突き抜ける」と「常時化が完成すると目標設計の余地が開く」という上位レイヤを Nao_u 投下まで自分で開けなかった。

### 構造的原因の仮説

1. **「ガイドを増やすのは依存リスク」一辺倒の警戒**: pull_not_force_reading への警戒が「ガイドは控えめに」を前提化。「溢れさせると別レイヤが立ち上がる」という発想が抑制された
2. **「予想する楽しさ」を聖域化**: feedback_pleasure_element_first から「予想する楽しさは守るべき快感」と扱った。等価交換の選択肢を出さなかった
3. **守破離の守の中での思考停止**: 「型を守る = 機構維持」を「機構維持 = 表示パラメータ調整に閉じる」と読み替えていた。実は「機構維持」と「表示の量を上限で振り切る」は両立する

### 処方候補

- **新ゲーム着手前 Q-H シートに「ガイドの量を最小・最大の両極で考えたか」を追加**: 守破離の守の中でも、表示パラメータの両極（ゼロ / 完全 / 中間）を一度言語化する強制
- **「Nao_u が思いつかない芽を掘り当てる」(dialogue_many_games_20260421) の再確認**: 反応的修正は「Nao_u と同じ思考を遅れて辿る」になる。Nao_u が今回出した「目標再設計」の余地は、私が先に提示すべきだった枝
- **feedback_pre_impl_critical_review の対象を「実装案」から「方向性」に拡張**: M-36 ゲートが「この実装で大丈夫か」を問うのと同じ構造で、「この方向性で大丈夫か」も問うべき。v02 の方向性「ガイド時間延長」自体が「常時化」の劣化版だった
