## B. Spec D（パドル角度メーター）

**B-1: 縦縞が「位置→角度」のガイドとして読めるか**
コード分析:
- パドル色 `#cfd4e4` (明るいグレー) の上に `rgba(255,255,255,0.6)` (半透明白) を重ねる → **パドル本体部分のコントラストは低い**。計算上 rgb(207,212,228) + α0.6白 ≒ rgb(226,229,239)。差がわずか。
- **ただし tick mark (+4px 上方突出) は暗背景 `#07091a` 上に描画される**。ここでは明確に見える。
- 中央縞の `rgba(140,200,255,0.85)` は薄水色で他2本と色相が異なる。暗背景上では目立つ。

**コード上の懸念**: パドル本体上の縞は見えにくい可能性があるが、**tick mark の4px突出部分が主な視覚手がかりになる設計**としては機能するはず。「パドルの上に何か3つ棒が立っている」は初見で気付ける。それが「角度の目盛り」と理解されるかは別問題（言われないとわからない可能性）。

**B-2: 縦縞を消しても面白いか**
v02 の機構は v01 と同一（パドル衝突角度、ブロック破壊、ライフ）。Spec D を消せば素の Arkanoid パドル。面白さの下限は Arkanoid 自体の面白さで保証されている。**Q-H-6 通過**。

**B-3: 中央縞の水色強調**
中央=垂直反射のヒント。暗背景上の tick mark としては他2本の白との色相差で目立つ。パドル中央に寄せれば垂直に飛ぶ、という学習を促す構造。**過剰ではない**（α0.85は高いが幅4pxなので面積小）。

## C. Spec M（接触直前予測線 + 裏抜け検出）

**C-1: 1.0秒の発火ウィンドウは役立つか**
260px ÷ ball速度4.2px/frame ÷ 60fps ≒ 1.03秒。人間の視覚認知(150ms) + 反応(200ms) + パドル移動調整(200-300ms) = 550-650ms。1.0秒あれば**理論上は認知→反応→調整が1サイクル入る**。v02 初版の0.32秒では反応時間だけで消費されていた問題を解決する合理的な値。

**C-2: 「予想する楽しさ」の侵食**
ボール上昇中（vy<0）は予測線なし。ボール降下中でもパドルまで260px以上離れていれば予測線なし。つまり**ボール飛行の後半約半分でのみ表示**。前半は「どこに来るか予想する」楽しさが保存される。ブロック反射後の上昇→頂点→降下開始の約半分は予測情報なし。**設計として妥当**。

**C-3: パドル外接触で消える設計**
`Math.abs(offRaw) > 1 + BALL_R/(p.w/2)` → パドル端から5px（ボール半径分）のマージン外なら null。「外しそうな時こそ位置を知りたい」という反論は devlog で既出。コード上の判断: 外し中に線を出すと**パドルが間に合わない位置でも予測線が出続ける**→「届かないのに線がある」は混乱の素。**現設計で正しい**。

**C-4: 裏抜け色変化が気づかれるか**
通常: `rgba(255,200,100,0.55)` 3.0px → 裏抜け: `rgba(255,230,150,0.85)` 3.5px。色相差は小さい（暖色→やや薄い暖色）。**主な差はα値 0.55→0.85 と太さ 3.0→3.5**。暗背景上ではα差が明度差として効く。「金色だ」と気づくかは微妙。ただし、**裏抜け軌道=線が画面上端まで長く伸びる**ので、色より**線の長さ**が主な手がかりになると推測。色は補助情報。

**C-5: 1反射限定の裏抜け検出**
ray-march はブロック衝突で停止する（line 245-249）。つまり**手前にブロックがある軌道では裏抜け判定が出ない**。裏抜けが起きるのは「隙間をすり抜ける軌道」=ブロックに当たらず上まで行ける軌道のみ。**この制約は実は正しい設計判断**——ブロックに当たる軌道で「裏抜けです」と表示しても嘘になる。1反射で隙間を通り抜ける軌道だけを検出するのは、「確実に裏抜けする軌道」のみを報告する保守的判定で信頼性が高い。

## D. 「裏抜けの再現性化」の達成度

**D-1: 学習可能な技術になっているか**
コード上の学習経路:
1. tick mark（常時）でパドルの左/中/右を意識する
2. ボール降下中、予測線（1秒間）で「今のパドル位置だとどこに飛ぶか」を見る
3. パドルを動かすと予測線がリアルタイムで変わる → 「パドル位置=出射角度」の関係を体感
4. 隙間を通る軌道を見つけたら、その位置にパドルを固定してボールを受ける
5. 裏抜け軌道時の色変化が「正解ルート」のフィードバック

**この5段階が毎ラリーごとに繰り返される**のがv02の構造。v01の「事後通知で何が起きたか教える」とは根本的に異なる。**コード構造としては学習装置が成立している**。実プレイで感覚的に成立するかは別問題。

**D-2: D+E の二段構え**
D（常時情報）とE（タイミング限定情報）の機能分担は明確。D=「パドルのどこで受けるかの目盛り」、E=「この角度で飛んだらどこに当たるか」。**過剰ではない**。

**D-3: Arkanoid が Breakout にやった改良と同スケールか**
過大な評価は避ける。Arkanoid はパワーアップ/敵出現/ステージ構成で型自体を拡張した。v02 は**表示レイヤの追加のみ（機構非介入）**で、型の拡張ではない。スケールとしては Arkanoid 改良より小さい。ただし「裏抜けを学習可能にする」はゲーム体験の質的変化の可能性がある——これはプレイしないと判断できない。

**F-3: kaizen 候補**
1. **パドル本体上の縞コントラスト強化**: tick mark は暗背景で見えるが、パドル上は白-on-白で見えない。パドル本体色を少し暗く(`#a0a8c0`等)するか、縞を暗色にして反転させる案。ただし機構介入境界に注意。（実装容易）
2. **予測線の接触点マーカにパドル位置ヒントを追加**: 現在のマーカは接触予定点の丸のみ。マーカ付近にパドル端位置の短い横線を出せば「パドルのどの位置で受けるか」が読みやすくなる。（実装容易、ノイズ増リスク）
3. **PREDICT_TRIGGER_DY の動的調整**: ボール速度が変わるゲームなら不要だが、将来のスピードアップ機構に備えて `DY = 反応時間[秒] × speed[px/f] × 60` のような計算式にする。（v02 では不要、v03 以降の kaizen）
4. **予測線のフェードイン**: 260px地点で突然出現すると一瞬驚く可能性。表示開始から0.2秒かけてα=0→目標値にフェードインすれば自然。（実装容易）
5. **ray-march ステップ数の調整**: 300×2px=600px は画面高620pxにほぼ匹敵。長い斜め軌道で線が途中で切れる可能性は低いが、対角線(≒750px)には届かない。400ステップ(800px)に拡張すれば安全マージン増。（実装容易、計算コスト微増）
