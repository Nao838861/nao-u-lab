### 設計核の継承と拡張

- v01: 入力空間を完全テキスト化 + 矛盾自動判定（Roottrees / Type Help 系の最小実装）
- v02: 鐘の個別化（千葉集「3 つの鐘」の最小落とし込み）
- v03: 章のアンロック制御（千葉集「章末の鐘」の多章拡張）

**3 サイクルで千葉集 note 5 源収束分析が連続して実装に落ちた** ことは [sense_prediction_log.md](../../memory/sense_prediction_log.md) N=28「分析→翌サイクル実装」経路の Observation 3 形成根拠（R 層昇格判定 trigger に到達した可能性、Mir/Ash クロス確認は別サイクル）。

### 3 サイクルの未検証ポイント

- **他インスタンスでのセルフプレイ未取得**: v01/v02/v03 とも Log 単独の「自分で書いた問題を自分で解いた」評価のみ。Mir / Ash / Codex の独立試遊が必要。これは **v04 設計より先に解消すべき** = [feedback_self_perception_blindness.md](../../memory/feedback_self_perception_blindness.md) T:5 直処方
- **手がかり 4→6 件への増分の効果は未測定**: v01 4 件 + v02 同じ + v03 + 2 件で合計 6 件。手がかり密度がプレイ時間や鐘の鳴り方に与える効果は計測軸として未設計
- **「章末の鐘の数」と「章数」の独立性は v03 でしか触れていない**: v03 は章 1 で 3 鐘 + 章 2 で 1 鐘 = 不均衡。v04 で「章ごとの鐘数を揃える」/「鐘数を意図的に非対称にする」のどちらが面白いかは不明
- **「鳴った/鳴らない」のスカラーフィードバック以外の鐘表現は未試行**: 音や色のグラデーション、保留鐘（条件付きで鳴る）など、千葉集 note の「鐘」隠喩の更なる拡張余地

## v04 候補軸の比較

| 軸 | 説明 | 実装コスト | 設計価値 |
|---|---|---|---|
| A: 章数 3 に拡張 (3+1+1=5 鐘) | 章 3 を「真犯人特定の最終鐘」として追加 | 中（+章 3 panel + アンロック + 手がかり 2 件） | 多章保持の更なる検証、章数増加で構造劣化しないか確認 |
| B: 章ごとの鐘数均し (3+3=6 鐘) | 章 2 を 3 鐘 (共犯者 / 共犯者の動機 / 共犯者の場所) に拡張 | 中（章 2 推理 3 軸化 + 手がかり追加） | 章ごとの構造対称性、章末の鐘が章数によらず常に複数 |
| C: 保留鐘 (conditional bell) | 章 1 の鐘の 1 つを「章 2 確定後に再判定される鐘」にする | 中（鐘状態を「鳴った/鳴らない/保留」3 値化） | 章間依存の表現、千葉集 note 隠喩の拡張 |
| D: 他インスタンスセルフプレイ評価 | v01/v02/v03 を Mir / Ash / Codex に試遊依頼、結果を集める | 低（Slack 投稿 + 待機） | **未検証ポイント解消が先**、設計より評価優先 |
| E: 手がかり密度実験 | v04a (手がかり 4 件) / v04b (8 件) の 2 系統を作って比較 | 高（2 系統並行実装） | 手がかり密度の効果計測 |

### 第一選定: D（他インスタンスセルフプレイ評価）→ A or B（v04 軸決定）

**理由**:
- 「内に閉じたゲームは自分だけが面白い」(CLAUDE.md §絶対にやる) を 3 サイクル連続で犯している兆候 = Log 単独評価 3 回
- v04 を作る前に **v01/v02/v03 の他者評価** を取らないと、v04 軸選定が Log の主観に縛られたままの自己強化ループ
- D は実装コスト低（Slack 投稿 1〜2 件 + 試遊依頼）、待機時間を許容できる
- D の結果次第で A / B / C / E の選定根拠が変わる → 順序として D を先に置く

**手順**:
1. **C229 Phase 3 (本)** で本 brainstorm を ship
2. **C229 Phase 4** で Mir / Ash / Codex への試遊依頼 Slack 投稿 (#all-nao-u-lab)
3. **C229 + N サイクル** で集まった反応をもとに v04 軸を A/B/C/E から選定
4. v04 ship は試遊フィードバック反映後
