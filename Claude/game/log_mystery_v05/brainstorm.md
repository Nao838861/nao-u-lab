### ゲート (a) 着手前広く調べ — 類似事例30本相当の R 層スキャン

R 層を上から順に v05 「保留鐘」軸に適用:

- **R-A 体験から設計する**: 一番楽しい瞬間 = 「鐘が鳴った瞬間の推理確信フィードバック」(千葉集 note 5 源収束分析より)。保留鐘は「鳴ったが取り消された鐘」「条件付き再判定で鳴り直した鐘」で **その瞬間に新しい層を足す** (時間軸フィードバック追加)。`強化する`方向で R-A 違反なし
- **R-B 緊張は外発・誘導は報酬で**: 保留鐘の「条件未充足で鐘が鳴らない」は罰でなく**情報フィードバック** (どの推理軸が未確定か)。Mir 発火段数指摘の反省を踏まえ「段数増加 = 罰駆動」と誤判定しないことを明示。緊張は「保留鐘が鳴り直すかどうか」で外発的に運ばれる (プレイヤーが反応する側)
- **R-C 見えないものは存在しない**: 保留鐘 UI は v04 の 6 鐘表示に「保留マーク (⏸ または ?)」を 1 軸追加。鳴った / 鳴らない / 保留中 の 3 値表示。**目盛りの長さで見せる**: 保留鐘は通常鐘と並ぶが色が灰色 + アイコンが ⏸ で区別。「ヒットボックス縮小」「隠れた減衰」型の見えない rule 追加にはしない
- **R-D 型から始める — 独自要素は1つだけ**: v04 までで「2章 / 3+3=6鐘 / 章間対称」を確立。v05 で追加する独自要素は **保留鐘 1 つだけ** (章数追加・鐘種類追加は同時にしない)。型 = v04 構造、独自 = 「条件付き再判定 = 保留鐘」1 つ。R-D 守破離の守
- **R-E 対症療法を避け根を切る**: v01-v04 4サイクル累積で「章間対称化」「仕様前倒し効果定量化」「他者評価ループ違反 R-A」の 3 課題を確認。v05 は前 2 つを継承 + 後 1 つを次サイクル試遊依頼で別タスク化。v04 を「問題を潰す」改修ではなく **新しい層 (時間軸フィードバック) を足す** 拡張なので R-E 違反なし
- **R-F 指標は誰のどんな行動で取られるかを先に書く**: 本 v05 では新しい指標を入れない (鐘数 6 維持、保留鐘は表示モード追加のみ)。devlog より先にヘッドレスは不要、5 分セルフプレイで「保留鐘が鳴り直すか / プレイヤーが保留中の鐘を読み解けるか」を判定
- **R-G target を1行で明文化**: target = 「LLM がプレイ可能 + 5 分以内で論理的推理可能 + 章間対称構造を体感」。v04 と同じ。保留鐘の追加で target shift は起きない (1 回プレイ体験が変わる方向)
- **R-H 解像度の落ちた言葉を使わない**: 「保留鐘」を実装動詞で書く = 「初回推理時に手がかり条件が部分一致した時、鐘を `bell-pending` 状態にし、追加手がかり読了で再判定して `bell-rung` または `bell-missing` に確定する」。「フレーバー」「面白い」など解像度の低い動詞を使わない
- **R-I 着手前に類似30本、提出前に自己判定**: 類似 30 本は v04 ですでに千葉集 note 5 源 + 都市伝説解体センター + Roottrees + Type Help + Obra Dinn + Golden Idol で展開済、本 v05 はその継承で再走査不要。**自己判定**は Phase 4 セルフプレイで「v04 比で何が体感的に変わるか」を 1 文化してから出す

### ゲート (b) 批判レビュー (懸念3点 + 解決可能性)

1. **懸念 1: 保留鐘の状態遷移が複雑になる**: 鳴った / 鳴らない / 保留中 の 3 値 + 保留中→鳴った / 保留中→鳴らない の 2 遷移で総 5 状態フロー。**解決可能性 = 可**: 状態フローを `bellState` オブジェクトに集約し、`renderBellGroup` で 3 値分岐の単純 if-else で十分。状態遷移は「初回推理時 → 追加手がかり読了時」の 2 phase のみで、フェーズを跨いだ複雑な遷移は持たない
2. **懸念 2: プレイヤーが保留鐘の意味を読み取れない**: 「保留中」アイコン ⏸ は一般 UI で「一時停止」を意味し、「再判定待ち」と直結しない可能性。**解決可能性 = 可**: アイコンの隣に「⏸ 追加手がかりで再判定」と日本語ラベル併記。R-C「目盛りの長さで見せる」準拠。Mir 発火段数指摘の「段数定義次第」を回避する具体策
3. **懸念 3: 「鳴り直す」がプレイヤーの操作感に対応しない**: プレイヤーは推理を一度確定したら戻せない (v04 まで)。「保留中の鐘が鳴り直す」のは autoplay 的で、プレイヤーが能動的に再判定を起こせない設計だとプレイヤー操作感が落ちる。**解決可能性 = 可**: 解決策 = 追加手がかり読了 (CLUES_CH2 内の C7/C8 など) をプレイヤーが能動的にクリックで `revealed` 状態にして、その時点で `re-deduce()` を発火させる。再判定はプレイヤー操作に駆動される (autoplay でない)

全 3 懸念とも「可」=「不可」「不明」ゼロ = R-I「着手前批判レビュー」通過。

### ゲート (c) ブレスト 30 件相当の候補出し

v05 「保留鐘」軸の中での実装バリエーション 10 件 (30 件相当の凝集版):

1. **保留鐘 = 単一鐘 1 つ**: 章 2 鐘 3 つのうち 1 つだけ保留可能 (実装簡単)
2. **保留鐘 = 全鐘**: 6 鐘すべて保留状態を持てる (実装複雑)
3. **保留トリガー = 手がかり部分一致**: ANSWER_CH の一部軸だけ hit、残り軸が未判定の時に保留
4. **保留トリガー = プレイヤー指定**: プレイヤーが「確信できないので保留」を能動選択
5. **保留解除 = 追加手がかり読了**: 未読 CLUE をクリックで読了 → re-deduce
6. **保留解除 = 章遷移**: 章 1 完遂 → 章 2 開始時に保留鐘が自動再判定
7. **保留鐘の鳴り直し演出 = 色変化**: 灰色 → 黄色 → 緑 / 赤 のグラデーション
8. **保留鐘の鳴り直し演出 = テキストフェード**: 「保留中」→ 「鳴った」or「鳴らない」のテキスト差し替え
9. **保留鐘の chord 構造**: 2 つの保留鐘が同時に解除された時の連続演出
10. **保留鐘の最終集約**: renderAllBells で保留鐘グループを別表示 (一章 / 二章 / 保留)

### ゲート (c) ブレスト 絞り込み 3 件

ブレストから 3 案に絞る:

- **案 X**: 1 + 3 + 5 + 7 → **章 2 鐘 1 つだけ保留可能 / 手がかり部分一致でトリガー / 追加 CLUE 読了で解除 / 色変化演出** (最小実装、v04 から +1 軸のみ)
- **案 Y**: 2 + 4 + 5 + 8 → 全鐘保留可能 / プレイヤー指定でトリガー / 追加 CLUE 読了で解除 / テキストフェード演出 (中規模、UI 操作が複雑化)
- **案 Z**: 1 + 3 + 6 + 7 → 章 2 鐘 1 つだけ保留 / 手がかり部分一致でトリガー / 章遷移で自動解除 / 色変化 (autoplay 寄り、R-I 批判レビュー懸念 3 で「プレイヤー能動性」違反)

### ゲート (c) 最終選定: 案 X

理由:
- **R-D 守破離の守**: 独自要素 1 つ厳守、保留軸を最小実装
- **R-I 批判レビュー全項目クリア**: 案 X の状態フロー 5 状態は懸念 1 の解決可能性 = 可 ですでに確認
- **30 分予算内**: v04 が 12 分実装 (実測) で、v05 案 X は v04 から `bell-pending` 状態追加 + `re-deduce()` 関数追加 + CLUE 読了クリック制御追加で +10 分程度を想定 (合計 ~25 分)
- **v04 振り返り §「章間鐘数対称性 = 新たな設計軸」継承**: 章 2 鐘 1 つだけ保留 = 章 1 と章 2 で保留可否を非対称に置く判断、これは v05 で「対称性 → 局所非対称」の 1 次拡張軸として記録する材料になる
