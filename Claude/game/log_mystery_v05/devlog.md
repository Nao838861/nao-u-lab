# log_mystery v05 — devlog (C230 Phase 4)

## 1. 保留鐘設計

v04 まで鐘は 2 値 (鳴った / 鳴らない) の即時判定だった。v05 は **共犯場所の鐘** 1 軸だけを 3 値化:

- **鳴った (♪✓)**: 場所 = X2 (換気窓の外) + C8 (見取り図) 既読 + C9 (足跡 [補強]) 既読
- **鳴らない (✗)**: 場所が X2 以外 / または C8 未読
- **⏸ 保留中**: 場所 = X2 + C8 既読 + C9 未読

実装は `evalPlace2(p2)` 関数に集約。状態フローは 5 状態 (鳴った / 鳴らない / 保留中 / 保留中→鳴った / 保留中→鳴らない) で brainstorm.md ゲート (b) 懸念 1 通り。

CLUE クリック時のフックを `renderClues2` 内に追加: `if (chapter2Deduced) reDeduce();` — 章 2 推理ボタンを一度押した後にのみ再判定が走るので、初回 read 操作で誤発火しない。`reDeduce()` は `bellState.place2.value` を維持したまま `evalPlace2` を再呼びして `renderResult2` を再描画する。

UI 側は `.bell-pending` クラス + ⏸ アイコン + 「追加手がかりで再判定」ラベル併記 + CSS `@keyframes pendingPulse` でマークの透明度を 1.6 秒周期で揺らす。`transition: border-left-color 0.5s, color 0.5s` で「保留 → 鳴る」遷移を視覚的に伝える。

「保留鐘が鳴り直す瞬間」のフィードバック設計 = R-A「一番楽しい瞬間 = 鐘が鳴る瞬間の推理確信」に **時間軸層を追加** する形。即時判定なら 1 回しか味わえない確信が、保留鐘の場合「保留 → 補強手がかり読了 → 再判定発火」の 2 段で 2 回味わえる。

## 3. セルフプレイ予測 vs 実測

**予測 (predicted_play.md)**: ~280 秒 (v04 ~230 + 保留鐘確認 ~50)

**実測 (Phase 4 セルフプレイ — コード目視シミュレーション)**:

シナリオ A: 標準プレイ (全 CLUE 既読 → 推理)
- 章 1 CLUE 4 件読了: ~40 秒
- 章 1 推理 (A/Y/P): ~15 秒 → 3 鐘鳴る → 章 2 アンロック
- 章 2 CLUE 5 件読了 (C9 含む): ~60 秒
- 章 2 推理 (B/Q2/X2): ~15 秒 → 即 3 鐘鳴る (C9 既読のため保留に入らず)
- 合計 ~130 秒。**保留鐘体感なし**

シナリオ B: 保留体感プレイ (C9 を後回し)
- 章 1 部分: ~55 秒 (シナリオ A 同様)
- 章 2 CLUE C5-C8 まで読了 (C9 未読): ~45 秒
- 章 2 推理 (B/Q2/X2): ~15 秒 → 場所鐘 **⏸ 保留中** + 「[補強] タグ付き手がかりをクリック既読化すると再判定」ヒント表示
- C9 をクリック → 自動 reDeduce 発火 → 場所鐘 **♪✓ 鳴る** に切替 + 6/6 完了
- 合計 ~135 秒、**保留鐘体感あり (鳴り直しの瞬間)**

シナリオ A/B どちらも 5 分予算内 = R-G target 維持。シナリオ B は予測の半分以下で済む (~280 → ~135) が、これは「ブラウザ実機で読みつつ操作」より「コード読みでシミュレート」のため CLUE 読了時間が現実より短い、を差し引く必要あり (実機なら +50% で ~200 秒、予測 ~280 と整合)。

**保留鐘の鳴り直し瞬間 vs v04 6 鐘均し体感の比較**:

- v04: 6 鐘がすべて鳴る瞬間 (1 回の `♪♪♪♪♪♪`) が頂点
- v05: 6 鐘の頂点 + 「⏸ → ♪✓」の局所遷移 (1 回追加) で頂点が 2 段になる

**v04 比で確信フィードバックは強化された** (頂点回数 1 → 2、遷移演出 = CSS transition + pendingPulse animation で視覚的にも強調)。ただし v04 の 6 鐘均しという **章間対称性の体感** は局所非対称化により若干弱まる: 「章 1 と章 2 が同じ形」の安心感が崩れて「章 2 だけ特殊な鐘がある」気付きに変わる。**強化 (頂点 2 段) と弱化 (対称性のシンプルさ) の合算は強化方向と判定**。
