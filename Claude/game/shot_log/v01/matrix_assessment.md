## セルごとの根拠

### 視覚軸 (○ ○ △ △)

- **段階1 ○**: 自機 (中央下) / 敵 (small/medium/large の色・サイズ差) / 弾 (自弾は上方向白、敵弾は下方向桃色 + 赤色radial) の見た目で「これは自分／これに当てる／これを避ける」が即読める。アイテム = 青色光球、ゲージ MAX = "BOMB READY!" の大文字テキスト演出 (line 1144-1148)
- **段階2 ○**: ゲージ階段 (35/99) の閾値到達で `playSE('levelUp')` 同期 ring 演出 + 弾数 1→2→3 の視覚反映。「撃つ→当たる→ゲージ増→弾増」の核ループが視覚で読める
- **段階3 △**: BOMB 発動時の派手 ring + particle (line 678-685) で「BOMB 使ったらこうなる」が視覚的に分かる。が、**敵種ごとの危険度を視覚で予告する装置は薄い** (例: large 敵の登場前にレーンに何らかの予兆色が出る、boss 出現前にアラート ring が出る等は未実装)。「次に何が来るか」を視覚で予告する設計余地が残る
- **段階4 △**: ハイスコア表示 (line 964: `'HI '+hiScore`) + ランキング TOP10 表示 (line 1156-1157) で「自分が今どの位置か」は読めるが、**スコア最適化のための視覚情報** (例: コンボ倍率の表示、ゲージ残量の精密表示、wave ごとのスコア記録) は未実装。極めセル (スコアラー層への入口) を視覚軸で支える要素が薄い

### 聴覚軸 (△ △ △ ✗)

- **段階1 △**: shoot / item / damage の基本 SE が事象に同期して鳴る (line 444, 826, 872)。**BGM なし**。SE は「事象に反応する音」のみで、「これからこういう状態になる」を予告する音響装置は無い
- **段階2 △**: killSmall / killMed / killLarge の撃破 SE が敵種ごとに分かれる (line 758-761)。levelUp / gaugeMax は閾値到達音 (line 825, 649)。状態変化が音で伝わる程度は中程度
- **段階3 △**: BOMB 発動の bomb SE (line 673) + gameOver / clear の終端 SE が機能している。応用層の状態変化 (例: 「今は危険、もうすぐBOMB溜まる」を音だけで知る) は **手動 BOMB 発動可能になった瞬間の gaugeMax SE 1 回** のみで、それ以降の継続的音響表現は無い
- **段階4 ✗**: **BGM 不在 = wave 進行 / 盛り上がり / 残り wave 数 / boss 接近** といった時間的構造を音響装置で伝える経路がゼロ。視覚オフでは「自分が今どこにいるか」全く分からない。matrix v0 §「shot_log 系」節「(聴覚, 全段階) = wave 進行を音響装置が伝えるか／単一BGMで音響アフォーダンスゼロは ✗」の典型該当

### 応答軸 (○ ○ ○ ○)

- **段階1 ○**: SPACE / 矢印キーの入力反応は 1 フレーム以内。発射 SE と弾発射の同期が成立 (line 444 `playSE('shoot')` と弾 spawn が同フレーム)
- **段階2 ○**: 撃破時の hitstop (line 777, 785) + shake (line 777) + ring + particle の組合せで「効いた感」が連続して返る。Pichlmair&Johansen 2020 game feel 3軸 (input latency / camera reactivity / sound integration) で言えば全軸成立
- **段階3 ○**: BOMB 発動時の派手 hitstop (`state.hitstop=18`) + 大型 ring (line 678-680) + 大量 particles で「BOMB を使った」応答が桁違いに増幅される。応用層で応答強度が階段する設計
- **段階4 ○**: 高密度時 (revenge bullet + 同時複数撃破) でも hitstop が積み上がらず制御済 (line 777 `Math.max(state.hitstop,6)`) + 死亡 hitstop 35F (line 846) でゲームオーバー演出が「重い終わり」を演出。極めセルでも応答の手応えが崩れない

### 構成軸 (○ ○ △ △)

- **段階1 ○**: wave 制 (buildWaves / line 392-393 `waves:buildWaves(),waveIdx:0`) で敵の出現順序が事前定義 = 「次に何が出るか」が wave 設計で予告される。1 wave 内の敵配置 (small 編隊 → medium key → large debut) で「ここはこういう場所」が読める
- **段階2 ○**: wave 内の敵配置 (line 291 `// W7: medium key wave + large debut`) で対処方法が読める。撃破ループが回せる物理配置になっている
- **段階3 △**: wave 間の階段は存在するが、**次の wave に何が来るかを事前に予告する物理配置の装置は薄い**。boss 出現前のレーンに予兆ブロックが出る、large 出現直前に画面端から色が漏れる等の「来るぞ予告」要素が未実装。devlog M-29 / Q-D 軸の「核ループの読み」は成立しているが、応用層の「予告」は構成軸で担えていない
- **段階4 △**: ノーミス / ノーボム / タイムアタックの極めセルを構成軸が支える要素 (例: ノーボム達成時の隠し敵出現、ノーミス時のレーン報酬) は未実装。Eneba 軸 #4 △ (power-routing) の評価と整合: 「power経路の戦術的奥行き」が構成軸の段階4で薄い

### 時間軸 (✗ ✗ ✗ ✗)

- **段階1 ✗**: HUD 表示は score + bombLabel + HI (line 960-964) のみ。**経過時間表示 / wave 番号表示 / 残り wave 数表示の全てが無い**。state.waveIdx は内部値として存在するが画面に出ない。プレイヤーは「自分が今ゲームのどこにいるか」を時間軸単独で読めない
- **段階2 ✗**: 同上。wave 進行中も「あと何秒で次の wave」「現在何 wave 目」が画面から読めない
- **段階3 ✗**: 同上。「あと何 wave でクリア」「もうすぐ boss」を時間軸単独で予告する装置なし。boss 出現は wave 設計上発生するが、出現タイミングを事前に時間軸で読めない
- **段階4 ✗**: ステージ全体の構造 (例: 「全 9 wave 中 6 wave 目」「boss 1/2/3」) を時間軸で読む経路ゼロ。タイムアタック層が時間軸を競技軸として使うことができない (経過時間が画面に出ないため自己ベスト比較が現場でできない)

**特例: state.t は line 600 で内部加算しているが draw 系には反映されていない**。HUD に出すだけで時間軸 段階1-2 のセルが △ → ○ に上がる可能性が高い (1 mm 改修候補)。

## 弱セル選定 (最も改修価値が高い 1 つ)

**選定: 時間軸 × 段階1-2 (wave 番号と進行が画面から読めない)**

選定基準 3 軸:

1. **改修可能性**: HUD に 1 行追加するだけ (`Wave 3/N` 表示) で △ → ○ に移行可能。実装コスト最小
2. **Nao_u 過去フィードバック整合**: `log/nao_u_live.md` の 18 項目 + dialogue_archive 80本超を走査した限り、wave 番号表示は議論されていない盲点領域。Nao_u が「これが無くて困った」と書いていない = フィードバック干渉ゼロ
3. **1mmで動かせる粒度**: HUD 1 行追加は v01 凍結状態を破らない範囲の **設計修正案** として v02_planning.md に記録可能。v02 着手時に index.html へ 5 行追加で実装完了

**選定理由 (補強)**:
- 時間軸が全段階 ✗ という matrix 評価結果の中で、最も「最小実装で最大の評価変化」を起こせるセルが段階1-2 (wave 番号)

## matrix v0 の限界 4 点との交差検証

matrix v0 §「v0 の限界 / 今後の更新軸」4 点を本適用で検証:
