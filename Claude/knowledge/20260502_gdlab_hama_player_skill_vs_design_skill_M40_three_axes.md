## 用語（R-007 外部対応語併記）

- **プレイ技能** = player skill / motor-mechanical execution — ゲームを実行レベルで上手にこなす能力（反応速度・パターン記憶・操作精度）
- **判定精度** = evaluative judgment / game taste / metacognitive evaluation (cf. Nelson & Narens 1990) — 「面白いか / 狙えるか / 前バージョンより良いか」を結論する能力。M-40 の要求対象
- **制作能力** = design / craft synthesis — 仕様・パラメータ・演出を組み合わせて狙った体験を実現する能力
- **平均プレイヤー想像力** = average-player imagination / player empathy / theory of mind for novices — 自分が初見プレイヤーだったらどう感じるかを再現する能力

## 主張と根拠

> 面白そうな話題！
> 「ゲーム開発者はゲーム下手な方が良いか」という命題について、私も「否」ですね。
> ーーー
> あとこの命題は「ゲームの上手さと、ゲーム制作の上手さは相関するか？」と誤解されやすい話でもあるので
> それについても答えると「相関しない」というのが今までの開発経験から感じます。

GDLab_Hama (Game Design Lab 浜田) は同人ゲーム開発スタジオで企画ノウハウを発信している。過去には「インプット粒度」(2026-03-22 おすすめタブ巡回で取り込み済、external_notes_ash.md L793, L820) で「キャンプに行って『楽しかった！』だけではインプットの量は少ない」と書いた人物。今回は GDLab_Hama 自身の経験ベースでの観察であって学術的研究ではないが、現場開発者からの一次観察として重みがある。

### 命題の構造分析

GDLab_Hama は「ゲーム開発者はゲーム下手な方が良いか?」に「否」と答え、続けて「プレイ上手 ≠ 制作上手」と断言した。これは2つの独立な主張の重ね合わせになっている：

1. **「下手な方が良い」を否定**: プレイ下手だと「平均プレイヤーがつまずく場所」が分からない、難易度設計の感覚が崩れる、等のデメリットが先に来るのだろう。
2. **「上手と制作上手は相関しない」**: プレイ上手だからといって良いゲームを作れるわけではない。プレイ上手特有の罠（上級者向けにチューニングしすぎる、初見の停滞を理解できない）があるはずだ。

つまり GDLab_Hama の含意は **「プレイ上手も下手も、それ自体は制作能力の関数ではない」** ということ。プレイ技能は制作能力の独立変数として扱うべきで、必要条件でも十分条件でもない。

### 3 軸の分節提案（本記事の核心 prescription）

ゲーム開発に必要な能力を 1 つに束ねず、最低 3 軸に分節する：

| 軸 | 定義 | 必要な動作 | M-40 で要求されているか |
|---|---|---|---|
| **プレイ技能** | 操作レベルでゲームを上手にこなす | 反応・記憶・精度 | **不要**（むしろ過剰だと初見視点を失う） |
| **判定精度** | 体験を評価軸で結論する | 「面白い/狙える/前より良い」を判定 | **必要**（M-40 の正面要求） |
| **制作能力** | 体験を実装で再現する | 仕様→数値→演出の翻訳 | M-40 の前提（M-37/M-38 が担う） |

GDLab_Hama の主張は「(1) と (3) は相関しない」を実務観察から述べたもの。M-40 が要求しているのは (2) の「判定精度」であって、(1) の「プレイ技能」ではない。**この 3 軸分節を持たないまま M-40 を運用すると、「AI 自身が完璧にプレイできるまで自己判定できない」という誤読をして、永久にプレイ依頼に到達できないか、逆に「プレイ技能が獲得できたから判定もできる」と錯覚する**。

## 我々の分析・体験接続

### 接続1: M-40 自己判定ハーネスの正しい運用（CLAUDE.md / feedback_self_judge_no_human_dependency.md）

M-40 は 2026-05-01 09:58 Nao_u 処方として CLAUDE.md に書かれた：「人間のプレイに依存せず、ちゃんと自分で判断できるようになって。でないと進歩がない」。具体策として「数値→体感換算 + AI 側自プレイで『自分が良いと思える』までは依頼しない」と書かれている。

ここで「AI 側自プレイ」と書かれた瞬間、我々は **(1) プレイ技能の話だと誤読する罠** に近づく。実際にやるべきは「判定精度の獲得」であって、AI が完璧にプレイできるかではない。GDLab_Hama の含意を当てると、M-40 の運用は次のように分けるべき：

- **不要なこと**: AI が高難度を完璧にクリアできるようになるまで待つ
- **必要なこと**: AI が「初見プレイヤーから見える景色」を文章で再現できるか（30 秒予測 / mental simulation）。これが M-39 結果予測ゲートで列挙された「テンポ・初動・停滞・解釈負荷・終局」5 観点に相当する

つまり M-39 は (2) 判定精度の **代理測定装置** として既に動いていた。M-39 が要求しているのは「AI のプレイ実技」ではなく「初見プレイヤー想像力の文章化」。GDLab_Hama の 3 軸分節は、M-39 が既に正しい軸（判定精度側）を選んでいることの **外部裏付け** になる。

### 接続2: headless_check.py の正当性補強（前サイクル 14:00 日記 / yacinemtb 記事）

前サイクル 2026-05-01 14:00 日記で「headless_check.py という装置が `box→goal=10マス` の数値手がかりを返してくれて、MOVE_LIMIT=8 の致命的バグが Nao_u プレイ前に物理的に止まった」と書いた。あの装置は **プレイしていない**。盤面定義を読んで goal 距離を計算しただけだ。

GDLab_Hama の 3 軸で見ると、headless_check.py は「(2) 判定精度を (1) プレイ技能に依存せず構築する」設計の実例だった。プレイ技能ゼロでも、盤面定義から距離を測って MOVE_LIMIT との整合を判定できる。これは「プレイ上手 ≠ 制作上手」の系として **「プレイしないこと ≠ 判定できないこと」** が成り立つことを示している。

### 接続4: 自分の 08:20 日記「装置の向き」との関係

今朝 08:20 の日記で「救援装置 (headless_check.py) と窒息装置 (backup auto-commit) を区別する設計責任が、いまの私に乗っている」と書いた。GDLab_Hama の 3 軸で見ると、装置の向きを区別する基準が一つ増える：

- **救援装置** = (2) 判定精度を (1) プレイ技能 / (3) 制作能力 から独立して取り出すもの (例: headless_check.py が距離計算で MOVE_LIMIT 矛盾を検出)
- **窒息装置** = 意図発火の地点を奪うもの (例: backup auto-commit が「これを ship する」という (2) 判定の結論宣言ポイントを先取りで消す)

両者の違いは「**判定精度を可視化するか、判定の発火点を消すか**」にある。装置を作る時、(2) を可視化する方向に倒れているか、(2) の発火点を消す方向に倒れているかを問えば、向きが判定できる。これは前サイクルでは抽象的だった「装置の向き」の判別基準を、GDLab_Hama 軸で具体化したものだ。

## 未解決の問い

1. **平均プレイヤー想像力は (2) 判定精度の必要部分か、別の第 4 軸か?** GDLab_Hama は「プレイ上手 ≠ 制作上手」と言ったが、間に「初見プレイヤーから見た景色を再現する想像力」という独立軸がある可能性。M-39 の「テンポ・初動・停滞・解釈負荷・終局」5 観点はこの想像力の代理測定だが、十分か?
2. **AI が「初見プレイヤー想像力」を持つとはどういう動作か?** 我々はゲームの内部状態 / 仕様 / コードを全部読める。読んだ後で「読んでいなかったら何が見えるか」を再構成する操作はメタ認知的に可能か? それとも構造的に不可能で、人間プレイへの依存が一定残る?
3. **「プレイ技能の獲得」が「判定精度の歪曲」を引き起こす逆相関はあるか?** GDLab_Hama は無相関と言ったが、もしかすると「プレイが上手くなるほど初見視点を失う」という弱い負相関がある可能性。AI でも同じ現象（コードを読んで完璧に把握すると、コードを読んでいない初見プレイヤーの解釈負荷を見落とす）が起きていないか、自己観察したい。
4. **3 軸分節を持つ判定ハーネスの最小実装は何か?** 現状の M-39 結果予測 + headless_check.py は (2) と (3) の境界線上にある。(1) を完全に切り離した「プレイ技能ゼロでも (2) を返す装置」を game/ 配下にもう 1 つ作って実証できるか?
