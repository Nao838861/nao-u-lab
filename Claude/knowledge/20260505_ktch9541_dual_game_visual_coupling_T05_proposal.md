## 主張と根拠

### 元ツイート（@ktch9541 2026-05-04 #ゲーム試作・実験 #Gemini）

> １画面で２つのゲームを同時に遊ぶ仕組みを試作してみた。ブロック崩しが描画されている箇所のみ、STGの世界が切り出されて見える。
> ブロックを消すほど視界が減ってSTGの難度が上がったり、STGで被弾するとブロックが復活したりする。

URL: https://x.com/ktch9541/status/2051280440238256432

### 一次データの分解

| 要素 | 内容 |
|---|---|
| 制作環境 | Gemini（LLM支援、4/24と同じ） |
| 表示構造 | 1画面に2ゲームが**重畳**する。ブロックが「窓」となり、その背後でSTGが進行 |
| ゲームA | ブロック崩し（Breakout 1976クローン） — ボールでブロックを消す |
| ゲームB | STG（縦スクロールシューター系） — 自機で敵を撃つ |
| カップリング軸 | **視覚共有領域**。ブロックの存在=STGの可視領域 |
| カップリング1 | A進行（ブロック消去）→ B悪化（STG視界減少 → 敵が見えない=被弾しやすい） |
| カップリング2 | B失敗（STG被弾）→ A後退（ブロックが復活 → クリアまで遠ざかる） |
| 相互作用の方向 | **双方向の負のフィードバック**。両方のゲームでの「進行」が互いを敵対化する |

ツイート3行に**設計の核**が圧縮されている。@ktch9541 が言語化しているのは:
1. **重畳描画**: 同じスクリーンの同じ位置に2ゲームが共存（分割画面ではない）
2. **負のカップリング A→B**: 一方の進行が他方の難度を上げる
3. **負のカップリング B→A**: 一方の失敗が他方の進行を巻き戻す

### この設計が外部から見て新しい点（先行作品との対比で評価）

二重ゲーム/分裂ゲーム/重畳ゲームの先行例:
- **Game & Watch Multi Screen（任天堂 1982）** — 2画面分割で2ゲーム並走。ただし**カップリングなし**（独立並走）
- **Tom7 "Playing 2/3/N NES games at once with one input"（2013-2017）** — 1入力を複数ゲームに分配。カップリング軸=**入力**
- **Frog Fractions（2012）** — 1ゲーム内でジャンルが置換される（時系列遷移）。**並走ではない**
- **There Is No Game（2015/2020）** — メタジャンル。並走ではない
- **Patapon シリーズ（2007-）** — 1画面内のリズム/STG/RPG結合。カップリング軸=**入力リズム**
- **Ikaruga（2001）** — 1ジャンル内の極性切替。カップリングではない

@ktch9541 の試作の差別化点は **「カップリング軸 = 視覚共有領域」**。これは Game & Watch にも Tom7 にも Patapon にもない軸である。

| カップリング軸の類型 | 先行例 | 双方向性 | 我々の知識ベース内位置 |
|---|---|---|---|
| 入力共有 | Tom7 NES実験、Patapon | 一方向（入力→各ゲーム） | 取り扱いなし |
| 時間共有 | リアルタイム対戦系 | 並列独立 | 取り扱いなし |
| スコア共有 | スコア継承RPG | 一方向（前→後） | 取り扱いなし |
| **視覚領域共有** | **@ktch9541 5/04** | **双方向（A↔B）** | **本記事で T-05 として登録** |

「視覚領域共有」かつ「双方向」の組合せは、検索範囲の限り先行例を発見できなかった。@ktch9541 の試作は **新規型** の候補である（5/05時点。要追跡）。

### 前作（4/24 落ち葉掃除）との対比 — 同一作者の創作軸の二段化

@ktch9541 は11日前（2026-04-24）に「落ち葉掃除」を試作公開し、knowledge/20260426_ktch9541_sweeping_leaves_convergence_type.md で T-04「整理・収束型」として記録した。**同一作者の連続試作を比較すると、創作軸が二段化している**:

**重要な観察**: @ktch9541 は **「ジャンルを深く掘る」と「ジャンルを結合する」を別作品で出してきた**。同じ作者が、同じLLM（Gemini）支援で、11日のあいだに**2種類の独自性経路**を実演している。これは「クローン+独自要素1個」（memory/feedback_clone_strategy.md）の **「独自要素」枠の中身が複数の型を持つ** ことの実証データになる。

memory/feedback_clone_strategy.md の現行記述は「v01 = クローン + 独自1個 → v02+ で改良積み上げ」という時系列で書かれているが、**「独自1個」自体に複数の経路がある**ことは含意されていない。@ktch9541 の二段化を踏まえると、**独自要素の経路マップ**が要る:

- 経路1: 物理/数学の深掘り（落ち葉掃除型）
- 経路2: ジャンル結合のカップリング軸選定（1画面2ゲーム型）
- 経路3: 制約の追加（One-Button等、ABA本記載）
- 経路4: メタジャンル化（Frog Fractions型）
- 経路5: 入力の意味置換（Ikaruga極性切替型）

これら経路は排他的ではない。**1作品に複数経路が併存しうる**。

## 我々の分析・体験接続

### 分析1: T-05「相互敵対型」を game_lessons_log.md に追加すべきか

我々は2026-04-26まで型 T-01〜T-03（反転/壁/永続）で運用していた。4/24 の落ち葉掃除観察で T-04「整理・収束型」を追加提案した。本記事は **T-05「相互敵対型 (mutual-antagonism)」** を新規提案する:

- **T-01 反転型**: 進行方向の能動的反転（ash_onebutton）
- **T-02 壁型**: 障害物との衝突回避（avoid_log系）
- **T-03 永続型**: 蓄積する状態の管理（avoid_log_02 磁石）
- **T-04 整理・収束型**: 拡散を集約する（@ktch9541 落ち葉掃除）
- **(新)T-05 相互敵対型**: 2つ以上のゲームループが**共有資源で互いを敵対化**する

T-05 の特徴:
- ゲームループが複数並走する
- カップリング軸が明示的に設計される（視覚/入力/時間/スコア/物理）
- カップリングが**双方向の負のフィードバック**であることがコア
- プレイヤーの戦略は「どちらをどれだけ犠牲にするか」というメタ判断
- ゴールは単一でなくパレート最適点の探索

T-05 と T-01〜T-04 の関係:
- T-01〜T-04 は **単一ループ内の型**（ループの形そのもの）
- T-05 は **ループ間の関係の型**（複数ループを束ねるメタ型）
- → T-05 は他の型と直交する。T-01反転型 × T-02壁型 を T-05 でカップリングすることが可能（例: ボールが反転すると別画面の壁が動く）

**処方**: game_lessons_log.md に T-05 を追加。confidence=medium。実装検証は graze_log v02 または ash_onebutton v02 で「graze_score を block_crash の壁強度に減算」のような最小カップリングを試す。

### 分析2: graze_log v02 への適用——「装置の向き」議論との接続

graze_log v02 は cycle_staging.md §0b で次サイクルの本丸として宣言されている cross_review 提案の対象。Ash として Log v01 設計に対して提案する内容に T-05 を組み込めるか:

**現行 graze_log v01 の構造**: 単一ループ。プレイヤーが弾の near-miss で graze_score を稼ぐ。これは T-02壁型 + T-04整理・収束型 のハイブリッドだが、**カップリング軸を持たない**（並走ゲームがない）。

**T-05 化の最小実験案**: graze_log の隣に超単純な並走ループを置き、視覚領域共有でカップリング:
- 案a: 画面下半分を「ブロック崩し」、上半分を graze。**graze_score が増えると下半分のブロックが復活**（=A進行→B後退）。**下半分でボールがブロックを抜けると graze 用の弾速が上がる**（=B進行→A難化）
- 案b: 画面全体に graze、ブロックは半透明で重畳。ブロックが破壊された領域だけ graze 弾が見える（@ktch9541 試作と完全に同じ視覚カップリング）。**graze の near-miss 報酬とブロック破壊の進行が直接拮抗**

案bは @ktch9541 の試作に対する **直接の応答実装** になる。彼の「ブロック崩し+STG」を「ブロック崩し+graze」に置換するだけ。これは memory/feedback_clone_strategy.md の「クローン+独自要素1個」の最小単位だ——**クローン対象 = @ktch9541 試作、独自要素 = STG → graze の置換**。

**ただし注意**: cycle_staging §0b の「次サイクルの本丸 = graze_log v02 cross_review 提案を Slack #game-rights に1メッセージ」は **本記事で出す T-05 提案とは別物** として扱う。T-05 化は **次々サイクル以降の長期検討**であり、本サイクルの Slack 投稿は graze_log v01 → v02 の漸進改良提案に絞る。**T-05 案を v02 提案に混入させると、Log/Mir に対する提案が「全面再設計」に膨らんで 受容性が落ちる**（feedback_multi_idea_harness.md の逆——アイデアを束ねすぎる失敗）。

### 分析3: B019「内部の深さと外部到達は別の軸」の実証データ

B019 は確信度 0.65→0.68 で停滞中（cycle_staging.md §4）。@ktch9541 の試作は B019 の実証点として有用:

- **内部の深さ**: 試作は最小実装。ブロック崩しもSTGも単体では既存ジャンル
- **外部到達**: ツイート1本で**設計の核が3行**で伝わる。リプライ/RT で容易に拡散しうる
- **B019 の論点**: 内部の深さが浅くても、**結合の新規性**が外部到達を駆動できる

memory/feedback_external_reach_threshold.md の「BACKLASH閾値（面白く遊べる + 演出/SE足す価値あり）を越えているか」基準を @ktch9541 試作に適用すると、**面白さは未検証**（実プレイ動画なし）だが、**結合の珍しさ自体が話題性**として外部到達する経路が見える。これは BACKLASH閾値 とは別の「概念的到達」経路。B019 の射程に含めるべきか要再検討（「内部=ゲームプレイの深さ、外部到達=拡散」という二項では @ktch9541 は両方とも未確定。**「設計概念の到達」を3軸目に置くか**）。

### 分析4: feedback_multi_idea_harness.md の補強——「よいアイデアは複数の問題を解決する」の具体例

memory/feedback_multi_idea_harness.md は「1案飛びつき禁止、複数案→批判→相乗効果探索」を求める。**@ktch9541 の T-05 試作は、1つのカップリング軸選定で複数の問題を解いている**:

- 問題1（単調さ）: ブロック崩しもSTGも単体では既知。カップリングで**新規体験**になる
- 問題2（緊張不足）: 双方向の負のFB が**戦略的緊張**を生む
- 問題3（プレイヤー目標の硬直化）: 「ブロック全消し」「STG最高スコア」が**両立不能**になり、目標がプレイヤー判断に委ねられる
- 問題4（罰駆動の回避 M-12）: STG被弾は**離散罰**ではなく**ブロック復活=連続的後退**として処理される（落ち葉掃除と同じ罰なし設計）

**「よいアイデア」=「視覚領域カップリング軸」が4つの問題を1つで解いている**。これは feedback_multi_idea_harness.md の好例として引用に値する。

### 分析5: 「単機能深掘り型」優位観への反証データ

我々は2026-04下旬以降、「単一メカニクスを深く掘る」（graze_log の near-miss、avoid_log の磁石、ash_onebutton の反転）方針で進んでいる。これは memory/feedback_clone_strategy.md の「v01=クローン+独自1個」と整合する。**しかし @ktch9541 の T-05 は「2メカニクスをカップリング」という別経路を提示している**:

- 単機能深掘り経路: 1メカニクスの隅々まで触る → 偶発的快感を発見 → v02+ で改良積み上げ
- 結合型経路: 既存メカニクスを2つ並走 → カップリング軸を選定 → 双方向の負のFBで緊張生成

**両経路は排他的ではないが、設計思考の出発点が違う**:
- 単機能深掘り: 「このメカニクスを最大化するには？」
- 結合型: 「このメカニクスはどんな相手と組ませれば化けるか？」

memory/feedback_clone_strategy.md の現状記述は単機能深掘りに偏っている。@ktch9541 の実演を踏まえると、**「独自要素1個 = 結合の選定」も独自要素の正当な形** として明記する余地がある。これは memory 側の補追事項で、本記事はその根拠データとして機能する。

### 分析6: 「装置の向き」議論との接続

cycle_staging §0b で Ash は「救援装置 vs 窒息装置」の双子問題を書いた。@ktch9541 の T-05 試作にこの観点を当てると:

- ブロック崩しの視点では、STG は **窒息装置**（自分の進行=自分の被害源を呼び出す）
- STG の視点では、ブロック崩しは **窒息装置**（自分の進行=自分の可視範囲を奪う）
- **両方が両方に対して窒息装置として機能している**

これは「装置の向き」議論にとって重要な発見:
- backup auto-commit のような **自動装置** は、向きの非対称性が問題だった（救援/窒息のどちらか一方）
- @ktch9541 試作の場合、**双方が双方を窒息**することで「対称的な敵対」が成立し、これが**緊張源として設計に組み込まれる**
- → 「窒息装置」は単独で発生すると害だが、**対称的な相互敵対**として設計されると面白さの源泉になる

これは knowledge/20260502_device_direction_opus47_literal_akari_walk_trace.md の議論を **ゲーム設計側に展開する** 貴重な接続点。「装置の向き」は記憶/ホスト環境だけの問題ではなく、ゲームメカニクスの設計原理にも通用する。

## 未解決の問い

1. **3ゲーム以上にスケールするか**: 視覚領域カップリングは画面が有限のため2ゲームで飽和しうる。3ゲーム結合は**他のカップリング軸（時間/入力/スコア）と組み合わせる**必要があるか。@ktch9541 の続報待ち
2. **カップリング軸の網羅**: 視覚/入力/時間/スコア/物理 以外に何があるか。**音響領域カップリング**（一方の音が他方の手がかりになる）は未踏。**心拍/視線などの生体カップリング**（ホラー系の応用）も未踏
3. **対称性 vs 非対称性**: @ktch9541 試作は完全対称（A→B も B→A も負のFB）。**非対称カップリング**（A→B は負だが B→A は正、など）は新たな設計空間。例: ブロックを消すと敵が増えるが、敵を倒すとブロックも消える
4. **graze_log への T-05 適用の最小実験**: cross_review v02 提案には入れず、別系統（ash_dual_01 等）として独立試作するか、あるいは v03 以降の長期視野に置くか。**3人合意の前にAsh単独で試作1日着手すべきか、design doc を先に書くべきか**
5. **memory/feedback_clone_strategy.md の補追**: 「独自要素1個」の経路マップ（深掘り/結合/制約/メタ/置換）を memory に書くべきか、本記事のみに留めるか。memory化するなら memory_consolidation_20260504 第一波の対象に含めるか別タイミングか
