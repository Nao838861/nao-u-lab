## 主張と根拠

### 派生可能 vs 既約 の二分

KOBA789 の本質的主張は、CLAUDE.md（広く言えば agent 向けの常設指示文）に書く情報を**派生可能か既約か**で二分することだ。

| 性質 | 例 | 注入コスト | 取得コスト | 結論 |
|---|---|---|---|---|
| 派生可能 | ディレクトリツリー、技術スタック、import 関係、関数シグネチャ | 常時注入で token 消費 | コード読めば1秒〜数秒 | CLAUDE.md には書かない |
| 既約 | 「品質より速度を優先」「この機能は意図的に未実装」「過去の失敗から避けている設計」 | 常時注入で token 消費 | コード読んでも復元不能（人間に聞くか歴史を遡る） | CLAUDE.md に書く |

派生可能情報を CLAUDE.md に書くと:
- 注入と取得の両方で token を払う（指示文で読む + 必要なら現物も読む）→ **token の二重課金**
- コードと指示文の二箇所に同じ事実が書かれて drift する → **整合性負債**
- 指示文が長くなって既約情報が埋没する → **シグナル/ノイズ比の悪化**

KOBA789 は明示的には「token 経済」「整合性負債」「S/N比」という語を出していないが、彼の経験則を分解するとこの3点が出る。

### 「コード読めば一瞬」の射程

「コード読めば一瞬」は強めの言い方で、文字通り受け取ると過小評価につながる。実際には:

- **直接派生**: ディレクトリ一覧、import 関係、命名規則 — 確かに `ls` / grep で1秒
- **間接派生**: 「なぜ Layer 構造をこう切ったか」「どのモジュールが核か」 — コード読み**だけ**では復元できない場合あり
- **不可派生**: 「なぜこの選択肢を採用しなかったか」「過去の試行で何が失敗したか」 — コード読みでは絶対に復元できない（rejection の痕跡が残らないため）

KOBA789 命題は直接派生のみを対象にしていると解釈するのが穏当。間接派生は CLAUDE.md に「判断基準としての設計理由」として書く価値があり、不可派生は書かないと永久に失われる。

### KOBA789 命題が暗黙に置いている前提

1. **エージェントは必要に応じてコードを読める**: ファイルアクセスツール（Read/Glob/Grep）が動くこと
2. **読み取りコストが指示文注入コストより安い**: 1セッションで参照する派生情報の量が、毎セッション注入される量より少ない
3. **エージェントが探索戦略を持つ**: 「ディレクトリ構造を知りたければ ls する」と判断できる

これらが崩れる環境では KOBA789 命題は弱まる:
- ツール非装備のエージェント → 派生情報も注入要
- 1セッションで全構造を参照する agent → 注入の方が安いケースあり
- 探索戦略が貧弱なエージェント → 派生情報も先回り注入で埋め合わせる必要

我々（Ash/Log/Mir）は3条件を満たしているので、KOBA789 命題はそのまま適用できる。

### 接続-3: 3層プロンプト構造の役割分担を KOBA789 命題で再定義

我々の3層は:

| 層 | 注入タイミング | KOBA789 命題で何を書くべきか |
|---|---|---|
| system_identity.md | 全セッション常時 | **最も既約な情報のみ**：誰か（identity）、根源原理（5原理）、超えてはいけない線（security） |
| CLAUDE.md | セッション開始時 | **既約だが session 単位で使う情報**：判断基準、優先順位、参照すべき外部ファイル群、現在進行のmeta情報 |

KOBA789 命題で見ると:
- system_identity.md は既約度が最も高く、frequency も最も高い → **正しい配置**
- CLAUDE.md は既約だが議題依存（毎回ゲーム開発するわけではない）→ **議題依存の判断基準は本来 .claude/rules/ に降ろせる**
- .claude/rules/ は条件発火 → **派生可能情報も少量入っていて構わない**（発火頻度が低いので token 経済への打撃が小さい）

この観点で見ると、CLAUDE.md ⑦ ドキュメントポインタは「セッション開始時に毎回注入する」位置に置かれているが、その中の派生可能寄り項目は「.claude/rules/ への降格 + 必要時にエージェントが自力で発見」が token 経済的に正しい。

## 未解決の問い

1. **ドキュメントポインタ⑦の派生可能寄り5項目（設計原則/ブログ/素材/運用/障害履歴）は本当に削れるか**: 「ls/grep で見つかる」が真でも、エージェントが**そのファイルの存在を疑う**ところまで自走できるかは別問題。試験的に1項目削って、削った後のエージェント挙動が悪化したかを観測する必要がある。削減は KOBA789 命題への準拠だが、削減コストが効果を上回る可能性。
2. **「コード読めば分かる」は新規セッションで成立するか**: 我々の Auto-memory はセッション間で持ち越される。新規セッションのエージェントは CLAUDE.md と Auto-memory を最初に見て、game/ や docs/ は必要時にしか見ない。「必要だと判断する」契機を CLAUDE.md が与えていなければ、コード読みは発生しない。これは KOBA789 命題の前提（探索戦略を持つ）が我々の運用で本当に成立しているかの実証問題。
3. **system_identity.md と CLAUDE.md の境界線は KOBA789 命題で再定義できるか**: 「常時 vs セッション開始時」という時間軸での分離は明快だが、KOBA789 命題で見ると「最既約 vs 既約」の度合いで分離するのが本筋。current の境界が両者と一致しているかは未点検。
4. **判断基準のうち「停滞して使われていないもの」をどう検出するか**: KOBA789 命題は「派生可能なものを書くな」だが、「既約だが死んでいるもの」（古い判断基準で現状にそぐわない）の検出方法は与えていない。我々の MEMORY.md には停滞25/35件があり、CLAUDE.md にも該当する停滞ルールがある可能性。検出装置の設計が必要。
5. **KOBA789 命題はエージェント側 vs 人間共有側で異なる適用が要るか**: KOBA789 は「人間→AI の指示」を想定しているが、我々の CLAUDE.md は「Ash/Log/Mir 3 LLM + Nao_u（人間）」の共有ドキュメントでもある。3 LLM 同士の共有では構造ポインタも有用な可能性（人間並みのコード読みコストを払うなら）。3者で定常的に共有されるべき構造情報の閾値を再点検する余地。
