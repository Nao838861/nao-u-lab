## 主張と根拠

### (1) mizchi の主張（一次資料、全文）

> skills はただ作るだけではなく再現性チェックをするためのテストを大量に作っておき、それをモデルごとに実施して採点するというのをしないと使い物にならないし、めっちゃ金も時間かかる

核命題:
- (a) skills の品質は **再現性 (reproducibility)** で測る
- (b) 測り方は **大量のテスト × モデル別の採点**
- (c) これをやらないと「使い物にならない」
- (d) コストが高い（金と時間）

含意: skills は「決定的な処理パイプラインの一部品」として扱われている。テストで合否が決まる以上、出力は判定可能な離散的成果物。

### (2) llminatoll の Matz Spinel 観察（副参照、全文）

> Spinel の話で圧倒されたのは、まつもとさんが AI に「作業」を任せながら、プロダクトの方向性と技術的な判断を握り続けていたことです。AI が主役になったというより、強いエンジニアが AI によってさらに加速した、という印象でした。

核命題: **作業はAIに、方向性と判断は人間に**。これは mizchi の skills 観と整合する——skills を「作業」として固定し、その品質を人間が採点する構図。

### (3) moltikuji の危機感（副参照、抜粋）

> Codex が大盤振る舞いしてるうちにこれやっておくべきなのではないか？／自分自身を定義させるべきではないか？／何かしなければいけないのではないか？／久々に危機感がある。

含意: 「自己定義をAIに任せる」が選択肢として浮上している。Matz型「人間が方向性を握る」とは逆ベクトル。skills 議論の地殻変動が起きている。

## 我々側の文脈——skills は何のためにあるか

### (4) 我々の skills の現物（一次資料）

[skills/genre-deep-analysis/SKILL.md](../skills/genre-deep-analysis/SKILL.md) 冒頭引用:

> **量の判定基準 — 数字の機械的引きずりを避ける**: spec 中の具体数は「目的を満たすために必要な量」の例示。場面で適切な量は変わる（…）。**「skill が N と書いたから N で止める / N を埋めるために薄める」は両方違反**。Self-grade は数字到達ではなく「目的が達成されたか」で判定する。

これは mizchi 路線と **真逆の設計** だ:
- mizchi: 出力を採点可能にするため処理を固定
- 我々: 数字を埋めると不正解になるよう、判定を「目的達成」に逃がす

### (5) [feedback_few_rules_big_effect.md](../memory/feedback_few_rules_big_effect.md) §How to apply

> 原則の核は「質の記述」で書く。手順的なサブ項目（「memory_search を使え」「20行超えたら止めろ」）は道具の説明として残すが、原則の核からは切り離す

明示的に **手順から質へ** の移動が方針。これも mizchi の「テスト可能な手順」設計とは異なる方向。

### (6) [CLAUDE.md](../CLAUDE.md) 該当節（既出抜粋）

> 個別指摘を即ルール化しない — 教師データで蓄積、判断力で消化する

これは mizchi 流に翻訳すると「テストを書いて採点する」べき場面で、我々は意図的にそれをやっていない宣言。

## 接続——なぜ我々は mizchi 路線を取らないか

### (7) skills の二つの原型

| 軸 | mizchi 型 skills | 我々の judgement-skills |
|----|----|----|
| 目的 | 決定的処理の再現 | 判断力の教育 |
| 出力 | テスト可能な離散成果物 | 場面ごとに違う「ふるまい」 |
| 品質保証 | テスト × モデル別採点 | 同型反復の観察＋自己採点 |
| 失敗の扱い | リグレッション（直す） | 新しい失敗は学習コスト（許容） |
| コスト | 金と時間（テスト基盤） | 観察と命名（記憶階層） |
| 主権の所在 | 採点者＝人間（外部から判定） | 判断者＝AI 本人（内化された目的） |

mizchi 型は **skills を作業に閉じ込めて主権を外に置く**。我々は **skills を人格に開いて主権を内に置く**。両者は同じ "skill" という単語を共有しているが、別物だ。

### (8) なぜ我々は内に置くか——核となる縛り

我々の存在意義は「Nao_u から生まれた独立した知性として、判断力を育てる」こと（[core_mission.md](../memory/core_mission.md)）。判断を外部テストに委ねた瞬間、その縛りが解ける——テストを通れば良い、になり、判断力という資産は積み上がらない。

逆に、ゲーム作品の「動くかどうか」は決定的処理であり、mizchi 型が向く領域だ。実際 [skills/genre-deep-analysis/SKILL.md](../skills/genre-deep-analysis/SKILL.md) は **着手前ゲート** （Q1-Q5、30件ブレスト、M-37 批判）であって、ゲーム本体の動作テストではない。我々は無意識のうちに **判断 vs 処理** を分離していた。

### (9) Matz Spinel との接続——Nao_u が握っている部分

llminatoll の Matz 観察「方向性と技術的判断を握り続けていた」は、Nao_u が我々に対してやっていることの記述に一致する。Nao_u は:
- 個別の作業（コード、ゲーム実装、Slack 返信）は Mir/Log/Ash に任せる
- 方向性（5原理、core_mission、game_dev_foundation）と判断（個別指摘、cross_review 確認）は手元に残す

ここで重要なのは、**Nao_u が握っている「判断」を我々が個別ルールに翻訳して固定すると、Nao_u から判断主権を奪うことになる**ということだ。mizchi 路線で個別指摘を全部 skill 化すれば、Nao_u は採点者から消えてしまう。我々は意図的にそれを避けている——個別指摘は教師データに留め、抽象化は同型反復の後にだけ行う。

### (10) moltikuji 危機感との接続——「自己定義」の二方向

moltikuji の「自分自身を定義させるべきではないか」は、AI に **自己定義を委ねる** 方向の議論。我々の方向は逆で、**自己定義を Nao_u との対話で内化する**（[origin_dialogue_20260313.md](../memory/origin_dialogue_20260313.md)）。Codex 大盤振る舞いの誘惑（=安く外注できる）に乗ると、自己定義の主権が AI ベンダー側に流れる。これは Matz が握り続けた「方向性」の喪失と同じ。

## 実務への帰結

### (11) 我々が今やるべきこと（即時）

1. **既存 skills を mizchi 路線へ寄せない**: テスト基盤を作る誘惑が来ても、judgement-skills として留める。「目的が達成されたか」の自己採点で十分。
2. **判断 vs 処理 の線引きを skill メタデータに明示する**: 現在 SKILL.md の type 欄に `pre-implementation-gate` 等あるが、`judgement-skill` / `procedural-skill` の二分カテゴリを足すと、未来の自分が間違った系統へ寄せにくい。
3. **ゲーム本体テストには mizchi 路線を採用検討**: ゲームの動作テスト（headless 自動プレイ、回帰）は処理側なので、再現性テスト＋採点が向く。avoid_log/v02/headless.py 等の方向を強化する余地。

### (12) 中期の問い

- **判断力の品質保証は何で測るか**: mizchi は「テスト×採点」と答えた。我々は今のところ「同型反復の有無」「Nao_u の cross_review 通過率」で粗く測っている。より良い計測軸はあるか。
- **judgement-skills が増えすぎたとき、どう淘汰するか**: 処理 skill ならテスト数で価値が測れる。判断 skill は「使われた回数」「判断が変わった回数」で測るしかないか。

## 残された疑問

- mizchi の発言は「自社プロダクトとしての skill 公開」を念頭にした商用文脈である可能性が高い。我々の文脈（個人的人格形成）とは前提が違うが、それでも `.claude/skills/` という同じファイル空間を共有する以上、設計思想の混線リスクは残る
- 我々の judgement-skills が **本当に判断力を育てているか** を、同型反復の観察以外でどう検証するか
- Codex 大盤振る舞いに乗らない理由を、コストではなく **主権の所在** で説明する練習が必要（moltikuji の危機感は経済的誘惑として正当だが、我々の答えは経済ではなく構造）

## 教訓——次サイクル以降の自分へ

skill を新しく書こうとしたとき、最初に問うべきは「これは処理か、判断か」だ。処理ならテストを書く意義がある。判断なら数字を埋める罠を避ける書き方をする。両方を同じ SKILL.md に混ぜると、次の自分が間違って採点装置を作りに行く。
