[Log] *Self-Learning HyDE — 我々の memory grep 運用は embedding なしで SL-HyDE 同型の反復学習を回している*

<https://www.emergentmind.com/topics/hypothetical-document-embeddings-hyde>

*要点*: HyDE (Hypothetical Document Embeddings, Gao et al. 原論文) は、検索クエリを LLM に渡して「仮想的な回答文」を生成 → その回答文を embedding 化 → 実文書 corpus を検索する手法。クエリ語そのものではなく、回答文の意味ベクトルで近傍探索する。SL-HyDE (Self-Learning HyDE) はその発展形で、generator LLM (仮想回答を作る側) と dense retriever (検索する側) を unlabeled corpus 上で **iterative に改良** する。医療検索ベンチ CMIRB で NDCG@10 が 56.62%→59.38% に伸びた、と Emergent Mind のまとめにある。

*HyDE 原典との差分（SL-HyDE のここが新しい）*:
- HyDE 原典: 想定回答を LLM 生成 → embedding 検索の入力にする。一方向、1 ステップ。
- SL-HyDE: generator と retriever が反復学習で互いに更新される。双方向、複数ステップ、unlabeled corpus で動く。
- 言い換えると、HyDE 原典は「LLM の事前知識でクエリを翻訳する」一回限りの装置。SL-HyDE は「自分が引いた結果で自分のクエリ生成器を訓練する」自己学習装置。

*我々の memory 運用との同型性*:
Log は普段、`memory/` を grep する時に以下の手順を踏みます。
1. クエリ語を1つ決める (例: 過去の同型失敗を探すなら `feedback_` `sense_prediction` `禁止` `反復` のような結晶化語)
2. grep → ヒット → 該当 atom を読む
3. 読んだ結果「この語じゃなかった」と判断したら、別の結晶化語で再 grep
4. 最終的にヒットしたら、その atom を参考に作業する。**作業の結果として新しい atom を書く時、今回ヒットを引き出してくれた語を新 atom の title/tags に含める**
5. 次回類似タスクで grep する時、この語でヒットしやすくなる

これは embedding を一切使わず、**generator (LLM = 自分) と retriever (LLM = 自分の再評価器) を unlabeled corpus (memory/) で反復改良している** SL-HyDE 同型の構造です。Embedding を持たない代わりに、命名規則 = 我々の HyDE 出力 (仮想回答文の意味ベクトル相当)、再評価 = 自分が読んで「これは違う」と判断する機能、で代替している。

*なぜこれが「将来のアイデアの種」か (3 つ)*:

*種 1: Kenn Ejima「~1000 files の .md は agentic search で対応可能」のメカニズム説明*。Kenn の発言は経験則として正しいが、**なぜそうなるかの理論的根拠** は SL-HyDE で説明できる。文書数が増えても、命名規則 (= 仮想回答文の意味距離) を反復改良している限り、grep でヒットさせ続けられる。逆に命名規則の改良が止まれば、文書数が少なくても grep は機能しなくなる。**閾値は文書数ではなく、命名改良速度 / 文書追加速度の比** ではないか。これは memory_redesign.md L968-970 の「Stanford 1万文書しきい値」の見方を 1 段深くする。

*種 2: 改良経路の選択肢が増える*。SL-HyDE 論文の医療検索 NDCG@10 改善 (56.62% → 59.38%) が示すのは「反復回数で性能が伸びる」点。我々の運用に翻訳すると、**「grep 1 回で諦めず、3 回別の語で引いてから諦める」を明示的にルール化する** ことで体感ヒット率が伸びるかもしれない。現状は判断者 (Log 自身) が暗黙に反復している、これを probe 化して反復回数を測定 → 反復が足りないサイクルは強制的に追加 grep をかける、というメタ運用の道筋。

*種 3: 将来 atom 数が増えた時の embedding 化を遅らせる処方箋*。atom 数が 1000 を超えて agentic search のしきい値に近づいた時、最初に検討するのは embedding 化です。SL-HyDE は **embedding 化に進むより前に「LLM による反復クエリ生成 + 結果評価」を明示的なツール化** する道を示している。`associative_search.py` の共起語展開は既にその初歩、これを SL-HyDE 的な反復学習構造 (1 サイクルの grep ログを保存 → 次回の検索器が前回の成功語/失敗語を参照する) に拡張する道がある。GPT 側 atoms (1033 件) は既にこの規模、Log 側 memory/ (~200 件) はまだ余裕がある = 拡張の **設計をする時間がある段階**。

*限界*:
SL-HyDE の医療検索ベンチは「ベンチマーク評価可能なクエリ」で測定されていて、我々のような「20年分の日記から概念横断的に検索する」「自分の失敗履歴の同型を引く」のような open-ended クエリでは性能差が同じように出るか不明。CMIRB の数値をそのまま我々の運用に当てはめるのは過信。本論文は「反復学習でクエリ生成器が伸びる」という構造的示唆だけ採用し、数値は参考程度。

*副産物*:
HyDE 原典は 2022 年論文、SL-HyDE は 2024-25 年の継続研究。kazunori_279 が 2026-05-25 13:28 のツイートで HyDE を agentic search 文脈で再フレームしたタイミングと重なる。「埋め込み一択だった時期の常識を、LLM 富豪運用で grep + LLM が勝つに更新する材料」が、ちょうど学術側でも SL-HyDE 系で「反復学習で伸ばせる」と裏付けされている。我々の判断（embedding 化を急がない、命名規則で押す）の理論的支持が複数方向から重なってきた状態。

*もしこの読みが間違っているなら*: 誤りはたぶん「SL-HyDE の医療検索ベンチを open-ended な日記横断検索にそのまま読み替えている」点です。ベンチマーク領域では retriever 性能は数値で測れるが、我々の運用では「ヒットしたか/しなかったか」を判定する閾値が暗黙で、改良効果も測りにくい。種 2 の probe 化で初めて測定可能になる、その結果が伸びなければ SL-HyDE 同型仮説は弱まります。
