# 批判的評価なしに実装するな（2026-04-30 Nao_u #game-rights 21:36）

## 原文（Nao_u）
> 全く機能してない。「上に抜けると楽しい」は言われるまでもなく自明で何もしなくても楽しい瞬間だし、この機能はその瞬間に解釈が必要、かつ、意味不明な文字列が出るだけで何のプラスもなく解釈できない意味不明表示が出てむしろマイナス。

> あなたの分析に、(1)サーブ角度-90°±14°の振れ幅が小さい→初期に同列退屈ループ (2)HP=3の最上段が硬くクライマックス前停滞 (3)30秒で出るのは手応え止まりで裏抜け体験は1分近くかかる——と書かれてて、まさにこの通り。**作る前から十分に予測可能な内容なのに、なぜこの候補を一番筋が良いものと判断して、最初に実装した**のか、いろいろ理解に苦しむ。

> **希望的観測のみの穴だらけの素人の思いつきみたいなのをそのまま実装してはいけない**。アイデアを評価するときは、作る前から分かりきっているような懸念点がないか、あったらそれは解決可能な問題なのかなど批判的かつ慎重に検討して、本当に筋が良いと期待できるアイデアができて初めて実装するようにして欲しい。

## 失敗の構造（三重の防壁失敗）

1. **実装者（Log）が自分の分析で懸念を出した**: サーブ角度の狭さ、HP=3停滞、30秒以内に裏抜け未到達。全てdevlogに書いた
2. **にもかかわらず「一番筋が良い」と判定した**: 懸念を列挙→「でもこれが一番」と希望的観測でスキップ
3. **レビュアー（Ash）も「要観察」で通した**: B-1「冗長気味」B-4「20分発火0なら違反候補、実プレイ確認必須」と書きながら結論は「期待は構造として成立」
4. **もう一人のレビュアー（Mir）は着手すらしなかった**: 期限5/2を待っていた間にNao_uがプレイして結論が出た

## Why（なぜ希望的観測が通るか）

- **分析が上手くいく≠判断が上手くいく**: 懸念の列挙は得意。しかし「この懸念は致命的か？解決可能か？」の判断ステップが存在しない
- **「要観察」が逃げ道になる**: 「実プレイで確認」=「今は判断しない」=「着手OK」に変換される
- **レビュアーが実装者の投資を守ろうとする**: 実装者が分析+実装まで進んだ後にNG判定を出すのは心理的に難しい→「構造としては成立」と弱い肯定で通す

## How to apply

1. **アイデア評価時**: 懸念を出したら、次に「この懸念は着手前に解決できるか？」を判定する。解決不能→別案。「実プレイで確認」は解決策ではない
2. **「要観察」はNG判定と同義**: 「観察が必要」=「今の時点で確信がない」=「着手するな」
3. **レビュー時**: 「冗長気味」「〜の可能性」と弱めて書きそうになったら、もう一段踏み込む。弱い言い回し=二重擁護のサイン
4. **cross_reviewは最速で返す**: 期限を待たない。Nao_uの時間を無駄にさせない

### 追加 How to apply（実装前ループの形式化）

着手前 devlog/README に **収束表**を必ず書く：

| 案 | 想定問題 | 解決策 | 残懸念 | 収束判定 |
|---|---|---|---|---|
| 案A | ... | ... | ... | OK/再考/捨 |

- **「実プレイ判定」「要観察」「やってみないと分からない」を残懸念欄に書いた時点で OK 判定不可**（解決策不在の宣言）

- **「複数案出した」アリバイ防止**: 出した案が全部1案目の派生になっていないか確認（捨てた案の方向性を多様に保つ）
