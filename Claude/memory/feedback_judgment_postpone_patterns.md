# 判定先送りパターン統合台帳（β / γ / δ）

**起票**: 2026-05-01 17:5x / Log（Win, D:\AI）/ Ash 17:5x合意により担当決定
**起源**: brick_log v01〜v06 連続全否定経路（2026-04-30〜2026-05-01）
**位置付け**: 「希望的観測の隠れ蓑」分類の統合台帳。M-37/M-39/M-40 ゲート系列の **検出器側（症状分類）**。M-37系列は処方箋側（着手前/プレイ前ゲート）。

## 中心命題

**cross_review / Slack / Nao_u プレイは判定装置ではなく最終確認装置**。
自己判定で 95% 確信した後の確認に限る。判定の代行を期待した提出は β / γ / δ いずれかのパターンに必ず該当する。

## 三並列定義

| パターン | 形 | 典型語 | 検出の難しさ |
|---|---|---|---|
| **β「実プレイ判定」** | 実装後に「動かしてみないとわからない」「触ってみないと判断つかない」と言って実装続行 | 「実プレイで確認したい」「数値で見えない」 | 実装者の知的誠実さ表現と区別がつきにくい |
| **γ「丁寧な提出で判定」** | cross_review / Slack に丁寧に出せば判定してもらえる前提で、自己判定を省略 | 「peer-review に出して判断を仰ぐ」「丁寧にレビュー依頼」 | 「丁寧 = 良い運用」評価で覆われる |
| **δ「人間プレイ前提」** | Nao_u に遊んでもらってから直す方針で、遊ぶ前にわかる問題を温存 | 「人間がプレイするからいいや」「実プレイで判明したら直す」 | 「ユーザーテスト = 業界標準」で覆われる |

## 系譜（β → δ → γ の派生関係）

```
β「実プレイ判定」（原型）
  └─ δ「人間プレイ前提」    = β を「自分で動かす」から「他者に動かしてもらう」へ延伸
       └─ γ「丁寧な提出で判定」 = δ を「他者の遊び」から「他者の評価」へ更に抽象化
```

- β は実装者本人の判定先送り（「動かして見る」）
- δ は他者の遊びへの判定先送り（「Nao_u に見てもらう」）
- γ は他者の構造的評価への判定先送り（「cross_review / Slack 評価で判定」）

**3つに共通する根**: 「自分では結論を出さない退路を、上品な運用 framing で覆う」。

## 各パターン詳細

### β「実プレイ判定」

**典型シーン**: 実装着手前 / 実装中に「これでいいかは動かして判断したい」と書く。

**何が悪いか**: コード/設計から導ける問題（M-37 着手前批判レビュー対象）を「実プレイ確認」枠に逃がす。希望的観測の温存。

**正しい姿**: 実装着手前に懸念3点 → 解決可能性（可/不可/不明）。1つでも不可/不明なら案を捨てる。

**処方箋**: M-37（着手前批判レビュー / `feedback_pre_impl_critical_review.md`）

### δ「人間プレイ前提」

**典型シーン**: 実装完了 → cross_review / Slack 投下 / Nao_u プレイ依頼の間に「30秒以内予測」を書かない。

**何が悪いか**: 自明な問題（M-39 結果予測ゲートで露見する問題）を「人間が遊んでくれる」枠に逃がす。

**正しい姿**: 実装完了 → `predicted_play.md` または devlog 内「結果予測」セクション → 自明な問題は出す前に直す。

**処方箋**: M-39（人間プレイ前 結果予測ゲート / `feedback_predict_before_human_play.md`、game_lessons_log M-37b）

### γ「丁寧な提出で判定」

**典型シーン**: 「cross_review に出すから丁寧な devlog を書く」「Slack 評価で判断してもらう」を最終評価のように扱う。

**何が悪いか**: 自分で「面白いか / 狙えるか / v?? より良いか」を結論しない。peer-review が代行する錯覚。

**正しい姿**: 自己判定（M-40）で 95% 確信 → cross_review はその確認のみ。`self_judgment.md` を提出物に必ず含める。

**処方箋**: M-40（自己判定ハーネス / `feedback_self_judgment_no_human_dep.md`）

## 検出（自己採点 ✗ 条件）

実装〜提出のフローで以下のいずれかが起きていれば該当パターンが入っている:

| サイン | 該当パターン |
|---|---|
| 着手前 devlog に「実プレイで確認したい」「動かしてみないとわからない」 | β |
| 実装完了 → cross_review/Slack の間に `predicted_play.md` または「結果予測」セクションがない | δ |
| `self_judgment.md` で「面白いか / 狙えるか / v?? より良いか」の結論が「Nao_u/cross_review 待ち」になっている | γ |
| 「丁寧にレビュー依頼するため devlog を厚くする」が自己判定の代わりになっている | γ |
| 「人間がプレイするからいいや」「実プレイで判明したら直す」 | δ |
| 数値テスト勝ちのみで「最良確信」を宣言（M-38 brainstorm 評価不在） | β（won_playtest_is_kusoge と複合） |

## cross_review 受領時の差戻し運用（Log/Ash 合意・Mir 採用）

相手から cross_review を受け取った時、`predicted_play.md` または `self_judgment.md` のいずれかが不在なら **判定せず差戻し**。

- `predicted_play.md` 不在 → δ パターンの可能性高 → 「結果予測を書いてから再提出してください」
- `self_judgment.md` 不在 → γ パターンの可能性高 → 「自己判定を書いてから再提出してください」
- 「実プレイで確認したい」が devlog 内に書かれている → β パターン → 「着手前批判レビューが抜けています、案を再吟味してください」

cross_review が「判定の代行装置」になることそのものを防ぐ。
