# ゲーム制作教訓

**位置づけ**: 上層 = 抽象ルール R-A〜R-I（**ゲーム制作時に最初に読むのはここ**）、下層 = 詳細事例 M-XX/L-XX/S-XX/D-XX/X-XX（**個別判断で必要になった時だけ辿る**）。R 層と M 層の対応は各 R に「**詳細**」リンクで束ねている。

**Nao_u 2026-05-13 #human-steering 起点**: M-XX 個別事例だけでは「サマリーを読んでも意味が分からず混乱を招く」。経験を一段抽象化したルールで本質的な問題を考え、個別事例は詳細を追いたくなった時だけ拾う構造に再設計。

4. 想起ハーネスは `skills/lessons-recall/SKILL.md`、Q-A〜H シート／brainstorm.md／cross_review コメント記入時に並行起動

## 抽象ルール R-A〜R-I（ゲーム制作時の最初に読むのはここ）

R 層は「**思考の質**」を記述する。具体的な数値・作品名・サイクル名は M 層へ降ろした（`feedback_few_rules_big_effect.md` / `dialogue_micromanagement_20260504.md` の方針）。

### R-J. 設計文書は要約ではなく意図の全量を運ぶ — 劣化は書いた瞬間に起きる

設計文書・指示書を「結論の簡潔な要約」で書くと、実装時点で設計意図が劣化する事故が**構造的に**起きる（Nao_u指摘 2026-07-25、2026-08-10 再発。同型2回で原則化）。要約は読み手の中で意図を再構成できない——Nao_uの指示の原文・検討と相談の過程・棄却した代替案とその理由・正誤の具体例を落とした瞬間、文書は「何をするか」だけになり「なぜ・どこまで・何をしないか」が消える。実装者はその空白を自分の推測で埋め、それが劣化の正体である。

処方: (1)設計文書には**原文（指示・議論の生の言葉）を該当箇所へインラインで**置く。別文書へのリンクは索引であり本文の代替にならない (2)各決定に why・棄却案と棄却理由・正しい挙動と誤った挙動の具体例を併記する (3)「簡潔に書けた」と感じたら劣化を疑う——文書の長さはコストではなく、実装者の推測が入り込む面積の削減である (4)要約だけの節を書いたら、その節の実装は設計者の意図と別物になると想定する。

**詳細**: 潮路の島 WORK_ORDER_20260810_CARAVAN_SLICE.md v1（要約のみで発行→Nao_u指摘で全量版へ改訂）が実例。

### R-A. 体験から設計する — 「一番楽しい瞬間」を守る／育てる以外を疑う

新作の着手前と各改修の前に「このゲームで一番楽しい瞬間は、プレイヤーが画面で何をしている時か」を1文で書く。改修案・追加案は、その瞬間を**強化する**か**新しい層を足す**かのどちらかでなければ採用しない。「問題を潰す」改修は、潰した先で核体験が削れていることが多い。装飾UI／演出強化は、その瞬間が**既に自明に楽しい**ならむしろ加害（解釈強要）になる。

**詳細**: [M-14](lessons/M-14.md), [M-15](lessons/M-15.md), [M-17](lessons/M-17.md), [M-36](lessons/M-36.md), [M-39](lessons/M-39.md)

### R-B. 緊張は外発、誘導は報酬で — 罰駆動と自発リスクコア化を避ける

緊張は敵側／環境側から運ばれてプレイヤーが反応する側に置く。罰（時間切れ／自然減衰／時間ペナルティ／隠しデバフ）でプレイヤーを動かさない。報酬経路だけ足すと「ノーリスク連打」「経済反転（撃たない方が得）」が起きるので、ペアで設計する。自発リスク（カスリ／close-call／バズ）をコアにするのは、先行作の前例で**コア用途**として成立しているものに限る。ボーナス用途しか前例がないならボーナス層に置く。**題材選択そのものが pirate 型既存原型の pull を持つかを入口段階で問う**（Margaris 2025-11 (d)「pirate 型既存原型でしか実質機能しない」と独立 source 同方向、graze は「誰の自発リスクごっこでもない」= 原型 pull 不在で R-B 違反の入口段階例として再定位）。

**詳細**: [M-12](lessons/M-12.md), [M-23](lessons/M-23.md), [M-30](lessons/M-30.md), [M-31](lessons/M-31.md), [M-39](lessons/M-39.md), [S-06](lessons/S-06.md), [Margaris 2025-11](https://jmargaris.substack.com/p/on-the-strengths-and-many-weaknesses) (独立 source, R-J 候補降格判定 2026-05-21、`projects/principles.md` §2026-05-21 C215 Phase 3 参照)

### R-C. 見えないものは存在しない — ルールは「見ればわかる／やればわかる」のみ

プレイヤーが画面から知覚できないルールは、数値的に機能していてもプレイヤーの判断材料にならない（ヒットボックス縮小・隠れた減衰・条件で変わる加算値）。同じ事象には同じ数値で反応させ、変わったことを伝えたいなら**目盛りの長さ**で見せる。UI は画面で起きたことを反映する**出力装置**であり、入力装置（読まないと負ける／覚えないと負ける／ゲージの意味を察しないと負ける）にしない。パラメータは「選択肢を制約する AND 画面で目撃できる」両方が揃ってはじめて存在する。

**詳細**: [M-13](lessons/M-13.md), [M-16](lessons/M-16.md), [M-24](lessons/M-24.md), [M-25](lessons/M-25.md), [M-46](lessons/M-46.md), [X-02](lessons/X-02.md), [X-04](lessons/X-04.md)

### R-D. 型から始める — 守破離の守、独自要素は1つだけ

軸ずらし（弾撃たないSTG／移動しないSTG／カスリコア化）の v01 は禁止。クローン元を3本以上引いて一般要素を80%程度取り、独自要素は1つに絞る。「型なし」も「型はあるが筋悪と判定済み」も、コアにはしない（後者は形式上「型はある」と通るので見落としに注意）。型破壊はサブ層／2作目以降に置き、v01 で試みない。前作の不評（「驚きが足りない」「ニンジャに勝てない」等）への対応は、**驚き要素の量で積み増すのではなく基盤の質を上げて返す**。1版で導入する驚き要素は2段まで、3段以上を入れる場合は驚き N 個に対し**橋 N-1 個以上**（事前提示／伏線／章構造の明示等）を着手前に明文設計する。**ジャンル固有の grammar（shmup なら Boghog 4 規則 = Toaplan/レーン/Layered/Pacing、4 失敗パターン = 垂直スタック/画面端/同時高HP/下方ドリフト）は着手前に M-44 等の M 層から引いて assertion 化する**。

**詳細**: [M-22](lessons/M-22.md), [M-28](lessons/M-28.md), [M-33](lessons/M-33.md), [M-35](lessons/M-35.md), [M-44](lessons/M-44.md)

### R-E. 対症療法を避け、根を切る — 3世代で原点に戻す覚悟

「問題を潰す」改修を3世代積み重ねたら、原点（v01／核体験／コンセプト出発点）に戻る判断を最優先する。前進改造で巻き戻し回避するバイアスがある自覚を持つ。改修毎に「核体験を守ったか／消えた快感はないか」を1行自己報告。新vN を出す時点で「v01 重心を強化したか／対症療法か」を明文化する。表現層が強いメタファーで作る時は、それがメカ層を**食う引力**になっていないか着手時に問う（メタファーはほぼ常にメカより強い引力を持つ）。

**詳細**: [M-11](lessons/M-11.md), [M-15](lessons/M-15.md), [M-21](lessons/M-21.md), [M-29](lessons/M-29.md), [L-01](lessons/L-01.md), [L-02](lessons/L-02.md), [X-01](lessons/X-01.md), [X-03](lessons/X-03.md)

### R-F. 指標は誰のどんな行動で取られるかを先に書く — devlog より先にヘッドレス

新しい指標を入れる時、「この指標は誰のどんな行動で最大化されるか」を1行先に書く。AI が押す条件で最大化される指標は、人間プレイ条件と一致しない可能性が高い。devlog の直感を書く前にヘッドレスを走らせる順序を守る。HUD は画面挙動と1行で接続が説明できるものだけ画面に出し、残りは dev-only。プレイヤー行動と無関係に勝手に進行する受動的自滅タイマー（時限爆弾／自動死／勝手なイベント進行）は抜け穴になる。**前提**: ヘッドレス自体が人間プレイと同じコア動作（操作軸／衝突判定／メカニクス本体）で走っていること。ヘッドレスのスコアが人間プレイ感覚と大きく乖離する／不可能なスコアが出る場合は、ヘッドレス側を先に校正してから指標判定に使う。壊れた測定装置からデータを引いて設計判断するのは、測定装置なしより悪い（誤った確信を持つ分だけ）。

**詳細**: [M-10](lessons/M-10.md), [M-32](lessons/M-32.md), [M-45](lessons/M-45.md), [L-03](lessons/L-03.md), [L-04](lessons/L-04.md), [L-05](lessons/L-05.md)

### R-G. target を1行で明文化して維持する — サイクルを跨ぐと無意識でズレる

casual／core fan／コンプ勢／30秒オンボーディング層など、誰のためのゲームかを README 冒頭に1行で書く。Q-A 採点は両 target で書けてしまうので、target の shift は Q-A では検出できない。外部記事を引く時は「その記事の暗黙 target」を1行書いてから採用判断する（target 一致なら直接適用、不一致なら反証寄りの参照に留める）。「コンプ勢向け改善」（追加 END／分岐／隠し要素）は1回プレイの大多数には届かないので、1回プレイ体験が変わるかを先に問う。

**詳細**: [M-20](lessons/M-20.md), [M-27](lessons/M-27.md), [M-34](lessons/M-34.md), [X-05](lessons/X-05.md)

### R-H. 解像度の落ちた言葉を使わない — 外部初見テスト＋実装動詞

私的造語・抽象比喩・「フレーバー」逃避・「再現できる」「面白い」など解像度の低い動詞は、外部初見解釈を1行書いてから使う。ゲーム快感は**実装動詞**（信頼度を上げる／磁力ゲージを溜める／弾を撃ち返す）で書く。「再現できる」と書きたくなったら、再現対象の意図のレイヤー（出現タイミング／反転点／弾発射／編隊役割）を3項目以上書けないなら言わない。ジャンル枠そのものを壊すレベルが意外性の基準線——個別要素の足し算では届かない。

**詳細**: [M-18](lessons/M-18.md), [M-19](lessons/M-19.md), [M-26](lessons/M-26.md), [X-06](lessons/X-06.md)

### R-I. 着手前に類似30本、提出前に自己判定 — 人間プレイは判定装置でなく最終確認装置

着手前に類似事例30本（同ジャンル≥10／異ジャンル同型≥10／「やらなかった」≥5／失敗事例≥5）を引き、ブレスト30件＋絞り込み3件＋着手前批判レビュー（懸念3点＋解決可能性 可／不可／不明）を通す。1つでも「不可／不明」なら案を捨てる（「実装後に観察」は希望的観測）。実装後は self_judgment.md で「面白いか／前作より良いか」を**自分で結論**してから人間に出す。cross_review／Nao_u／Slack は最終確認装置であって判定装置ではない。判定の代行を依頼する framing が出てきたら退路設計の signal。

**詳細**: [M-37](lessons/M-37.md), [M-37b](lessons/M-37b.md), [M-38](lessons/M-38.md), [M-40](lessons/M-40.md), [M-41](lessons/M-41.md), [M-43](lessons/M-43.md)

## 詳細事例（必要に応じて参照）

### LLM 向け詳細層使い方

1. **R 層で判断できなければ詳細を開く**。最初から M-XX 全件を読まない
2. 各行のサマリは **太字キーワード + 核 + 処方** の3パート構成。文脈に合致するキーワードでスキャン → サマリで「開く価値ありか」判定
3. 該当 M-XX のみ `memory/lessons/M-XX.md` を読む
4. **新規エントリ追加時**: (a) 本表に1行追加 (b) `memory/lessons/M-XX.md` 作成 (c) 重複ID 禁止、後発刻印を次番号にリネーム (d) 該当 R-X の「詳細」リンクに追記
5. **本文の参照スタイル**: `[M-22](M-22.md)` 形式リンク。LLM はリンクをトリガーに連鎖読み
