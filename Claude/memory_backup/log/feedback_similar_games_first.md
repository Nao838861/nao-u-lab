## なぜ起きたか

1. **M-40 自己判定ハーネス**を「数値判定の精度」として実装した。だが Nao_u が求めていた自己判定は「面白いか / 狙えるか / v?? より良いか」であり、振幅の物理妥当性ではなかった
2. v06 brainstorm.md / SKILL.md の「過去ブレスト想起」「新規ブレスト30件」は埋めたが、**類似ゲームの類似事例（ブロック崩しで動的標的を扱った先行事例）の調査セクションが構造的に存在しない**
3. 「自分のゲーム内のアイデア比較」と「類似ジャンルの先行事例比較」を同一視していた。後者は前者の上位 — 解空間の広さが違う
4. **数値チューニングが進歩感を生む罠**: 5→22→10 のプロセスは「考えて検証している」感を強く出すが、コアアイデアの面白さ天井は変わらない。判定ハーネスを作るほど数値最適化に没入する負のループ

- 「人間より上手くゲームを作れるようになる」(CLAUDE.md) には、**自分のゲーム内最適化**ではなく**ジャンル内最善案の発見**が要る
- 数値最適化は実装後でいい、アイデア段階では類似事例調査が圧倒的に効率がいい

## How to apply

### A. M-38 SKILL.md / `/game-analyze` に「類似事例調査」を構造化セクションとして追加

`brainstorm.md` 必須セクションに以下を追加（過去ブレスト想起の**前**に置く）:

```markdown
## 類似ゲーム類似事例調査（必須）

このゲームのコアアイデア（揺れる標的 / X / Y）を扱った先行事例を最低5本。
- 同ジャンル内の解: ___（タイトル / どう扱ったか / 何が良かった/悪かった）
- 異ジャンル内の同型解: ___
- 「やらなかったゲーム」も含める: なぜ採用されなかったか/失敗事例
- 検索した語彙: ___（GDC talks / Game Developer記事 / Wikipedia ジャンル史 / TVTropes 等）
- 引用URL/出典: ___

→ この調査結果から、**自分のアイデアが先行事例の何を超えるか / 何を再発明しているだけか** を1行で結論
```

### B. 数値チューニング作業を着手する前に問う3問

1. このパラメータ調整で**ゲームの面白さ天井**が上がるか、それとも**実装意図通りの動作**を確認しているだけか
2. 同種パラメータを変える先行事例（同ジャンルの名作の値）を3つ引けるか
3. このチューニング時間を「別アイデア検討」「類似事例調査」に振り替えた方が高ROIではないか

3問のうち1つでも No / 不明なら、数値チューニングを止めて上位フェーズに戻る。

### C. 「判定ハーネス構築の達成感」が数値最適化没入の入口

M-40 自己判定ハーネスは必要だが、**判定対象が「数値妥当性」になった瞬間に M-41 違反**。判定対象は「面白いか / 狙えるか / v?? より良いか」=コア快感の判定。`self_judgment.md` の上3行を「数値ではなく快感で判定」に固定。

### D. 13:07 で問われたら 13:18 を待たずに着手

「先行事例の調査と引用は」を質問形式で受けた時点で、それは**追加実装ではなく次の最優先タスク**。数値校正の続きを優先したのは 04-21 dialogue_many_games の「Nao_u が筋判定 / 我々が可能性探索」の探索方向違い。
