# 流通レイヤーの設計比較 — 商人・運び屋・備蓄を誰がどう担うか

作成: 2026-07-13（Mir） / 状態: **検討中（Nao_u「慎重に決定したい」）**
親: [../README.md](../README.md) / 発端: [../dialogue/20260712_session2_mir.md](../dialogue/20260712_session2_mir.md) の商人≠運び屋議論

前提（確定済み事項との整合）: 価格は純粋創発（ダブルオークション+価格信念）/ 1設備=1世帯の自営・賃金労働なし / 転職=設備乗り換え（摩擦は資本コストから創発）/ 情報は徒歩・船の速度 / 島内でプレイヤーは商売しない（港のみ）/ 腐敗なし

## モデル一覧

### A. 統合商人（商人=荷馬車）
1つの職業「商人」が荷車を持ち、安い村で買い、運び、高い村で売る。在庫も荷車と自宅に持つ。
- **理解**: ◎ 最もシンプル。「商人が安く買って高く売る」は万人の直感。ゲーム先例も最多（Patrician/Port Royale/Mount&Blade/Annoのトレーダー全部これ）
- **現実整合**: ○ 行商人・振売り・（買積みの）北前船。**小さい経済の姿としては正確**
- **面白さ**: ○ 荷車の動き=裁定の可視化が直接的。ただし流通セクター自体の成長物語は乏しい（荷車が増えるだけ）
- **実装リスク**: ◎ 最低。エージェント1種・契約は財取引のみ。協調の失敗が構造的に起きない
- **弱点**: 定置の大在庫を持つ者が不在→季節平準化・飢饉バッファが弱い。問屋/馬借の史実の豊かさを捨てる

### B. 分離固定（商人と運び屋を別職業としてハードコード）
問屋（蔵を持ち在庫リスクを取る・動かない）と運び屋（荷車で他人の荷を運賃で運ぶ・在庫を持たない）を最初から別職業に。
- **理解**: ○ 「トラック運転手と商社は別」は現代人の直感に合う（Nao_uの世界観）。ただし観察者が両者を画面で見分ける工夫が要る
- **現実整合**: ◎ 問屋/馬借・車借、買積み/賃積みの制度的区別そのもの
- **面白さ**: ◎ 運賃という第三の価格が創発。問屋の時間裁定（収穫期買い・端境期売り）と運び屋の空間裁定が別の生き物として見える
- **実装リスク**: ▲ **最大の弱点**。運送契約市場という新機構が必要で、ミクロの補完性の罠を抱える——問屋は運び屋がいないと遠方の財を買えず、運び屋は運送需要がないと転職しない。**最初の1組が成立しない**コールドスタート問題。デッドロックのデバッグが困難
- **弱点**: 序盤の小さい経済には過剰な分業（3世帯の村に問屋と運び屋は要らない）

### C. 創発分化（役割=資本の組み合わせ）★Mir原案
職業をハードコードせず、世帯が持つ資本が役割を決める: 荷車のみ=運び屋 / 蔵+在庫=問屋 / 荷車+在庫=行商人。経済が小さいうちは行商人（=A）が全てを兼ね、取引量が増えると分業が創発（=Bへ育つ）。
- **理解**: ○ 「持ち物で仕事が決まる」自体は直感的だが、分化の過程は説明なしでは追いにくい（UIの支援前提）
- **現実整合**: ◎◎ 史実の発展経路そのもの（行商→問屋制の成立）。「分業は市場の大きさに制約される」（スミス）が画面に出る
- **面白さ**: ◎◎ 天井最高。**流通セクター自体の進化が三次産業創発の第一幕になる**。裕福な世帯が蔵+複数荷車を集積して「高田屋」になる成長物語も出る
- **実装リスク**: ▲▲ 最高。Bの運送契約機構を含む上に、エージェントが混合戦略（運ぶか・買うか・貯めるか）を評価する必要。**分化が起きない/起きすぎるの両方向の失敗**があり、検証コストが最大
- **弱点**: MVPで最初からやるには重い

### D. Caesar 3方式（独立商人なし）※棄却基準として記載
生産者が自分の荷を市場へ運び、雇い人が配る。島内に商人階級がない。
- **理解**: ◎ / **実装**: ◎ / **テーゼ適合: ✕**。村間の価格差を裁定する者が不在→「1の結果3が生まれる」が起きない。キックオフの(b)選択と矛盾。**これを選ばない理由が明文化されている点にのみ価値**

### E. 問屋ハブ制（Bの垂直統合版・Cの部分集合）
問屋が蔵も荷車も持ち、輸送を内製（家族が荷車を操作）。実質「大きくなった行商人」。
- Cの資本組合せ空間に含まれる（蔵+在庫+荷車N台）。独立モデルというより**Cの終盤の姿**
- 複数荷車の操作者問題→世帯の家族人数=操作できる資産数、という自然な拡張が生まれる（人口の自然増と接続する副産物）

## Mirの推奨: 段階導入（A で検証し、C へ育てる。B は経由地）

1. **MVP=A**: 価格創発の安定性検証（ヘッドレス）には商人が最初から必要で、Aは1エージェント種で回る。まず「行商人だけの島」で価格・裁定・金詰まりの検証を終える
2. **データ構造だけ最初からC対応にしておく**: 「財の所有」と「荷車の所有」と「輸送という行為」を最初から別のものとして持つ（統合商人=自分の財を自分の荷車で運ぶ人、と表現する）。これなら後から運送契約（他人の財を運ぶ）を1機構足すだけでB/Cに進める
3. **蔵（在庫拠点）はAの段階で足せる**: 行商人が蔵を買って「動かない日」を選べるようにするだけで時間裁定が始まる（契約市場より先に問屋が生える）
4. **運送契約はデータが要ると言ってから入れる**: Aを走らせ、「大商人が荷車のボトルネックで成長が止まる」「遠隔地の価格差が放置される」が観測されたら、それが運び屋の存在理由がデータで示された瞬間。入れる根拠と検証基準が同時に手に入る
- この経路は「慎重に決定したい」に対する構造的な答えでもある: **今decideするのは終着点(C)ではなく、Cを閉ざさない最初の一歩(A+データ構造)だけ**
