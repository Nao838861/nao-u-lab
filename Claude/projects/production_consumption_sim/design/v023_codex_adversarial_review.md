# flow_island v0.23 独立敵対的レビュー（Codex）

- 実施日: 2026-07-18
- 対象実装: `2a8face66`（v0.23 自律掃討）
- 判定: **HOLD — `25/28`を改善の根拠として次の大改修へ進むには、監査の信頼性が足りない**
- 範囲: レビューと計測のみ。エンジン、監査、UIは変更していない

## 1. 結論

v0.23には妥当な修正もある。E3を「累積債務日数」から「最長連続債務日数」へ直したこと、海運投資を
worldごとの`expCap`へ分離したこと、自動支援を廃止する方向は支持できる。

一方、主要な成果説明のうち次の3点は実測で支持できなかった。

1. 炭焼き絶滅を「プレイヤーが建て直す」で解いたこと
2. E8の3→4改善を鉄の購入上限修正の効果とみなすこと
3. E16を「村の健康2条件」に変えて漸進建築の優位が確認できたとみなすこと

特に`audit.mjs`のScenario Aへ90日ごとの建て直し行動を混ぜたことで、標準村の経済評価と
「助言へ従ったプレイヤー」の評価が交絡した。24 seedでは建て直しなしより飢餓が2.42倍になり、
E4合格率が24/24から19/24へ後退し、破産も1件発生した。現在の`25/28`はエンジン改善というより、
E3の測定修正、E16の合格条件削除、炭焼きを再出現させたことでE2の判定数が1つ増えた影響が大きい。

## 2. 検証方法

- `v0.22..v0.23`の差分を、`engine.js` / `audit.mjs` / `index.html` / README・CONTEXTの順に静的確認
- 現行の`smoke.mjs`、`ui_test.mjs`、`audit.mjs`、`health.mjs`を独立実行
- Scenario Aを1〜24 seedで比較
  - v0.22までの固定建築台本
  - v0.23の「90日ごとに木工・炭焼き・塩を建て直す」台本
- E16を1〜24 seedで漸進建築 / 一括建築比較
- 炭焼きの転職時点を世帯別に追跡
- 鉄の購入上限4.0 / 5.0を同一seed・同一乱数で比較
- world分離、舗装経路キャッシュ、対岸漁への自律転職を局所probeで確認
- localhostを1440×900のheadless Chromeで開き、実画面を確認

## 4. 発見事項

### F1【阻止】Scenario Aの「チェーン建て直し」は村を救わず、監査を汚染している

1〜24 seedの比較:

| 指標 | 固定建築台本 | v0.23 建て直し台本 |
|---|---:|---:|
| 平均累積飢餓 | 183.46 | **444.08** |
| 平均人口 | 129.08 | 140.58 |
| 平均最終金庫（表示） | -18,935.8 | -6,083.5 |
| E1合格 | 18/24 | **16/24** |
| E4合格 | **24/24** | 19/24 |
| 破産 | 0/24 | **1/24** |
| 最終時に炭焼き不在 | 24/24 | 4/24 |

炭焼きの「存在」だけは改善するが、区画追加、渡航、人口増、食料需要も同時に増えるため村全体の健康を悪化させる。
seed 1では炭焼きをday 270 / 540 / 810に再建し、さらにday 720に木工も再建した。seed 22でも炭焼きを4回再建した。
これは復旧ではなく、吸収状態へ落ちる系に世帯を繰り返し投入している。

現行auditが選ぶseed 11/13/14は偶然E4を全通過するが、24 seedでは5件落ちる。
Scenario Aは固定台本へ戻し、助言追従はE15等の独立シナリオで評価すべき。

### F2【阻止】炭焼き絶滅の原因診断が誤っている

炭焼きは建物不足で消えるのではない。`distress`が直近180日の`hungerHist`合計を使い、現在は回復済みでも
過去の飢えを理由に転職させる。実例:

- seed 1 day 240: purse 190.7、炭36.7荷を持ったまま菜種へ転職。過去飢餓18,060
- seed 11 day 540: purse 10.69、食料46.8荷、炭61.4荷まで回復後に菜園へ転職。過去飢餓54
- seed 13 day 240: purse 355.6、炭17.5荷を持ったまま菜種へ転職。過去飢餓95
- seed 14 day 180: purse 388.4、炭31.1荷を持ったまま木こりへ転職。過去飢餓62

本質は初期の食料分配、過去飢餓の粘着、絶滅後の自然な再参入経路の組み合わせである。
「もう1軒建てる」を解にすると、F1の再建ループになる。

### F3【阻止】E16は不具合修正ではなく、失敗条件を削ってPASSにしている

v0.22のE16は「飢餓が少ない・人口が同等以上・口銭が多い」を漸進建築の成功条件にしていた。
v0.23は口銭条件を削除した。1〜24 seed比較では:

- 新しい健康2条件の合格: **5/24**
- 旧3条件の合格: **0/24**
- 漸進側が5軒すべて建築: 23/24
- 一括側が5軒すべて建築: 24/24

現行auditのseed 12は5件しかない有利seedの1つである。しかも健康2条件を満たすseedでも、漸進側は
seed 5で金庫-213,074対-63,905、seed 9で-41,965対+47,733、seed 10で-145,600対+48,113、
seed 19で+13,262対+41,565と、財政・口銭を大きく悪化させる例が多い。

「建てる→取引が増える→口銭が貯まる→次を建てる」というv0.20の背骨を検証する監査から口銭を外すなら、
先にE16の成功定義を設計し直す必要がある。単一seedのPASS化を改善とは数えられない。

### F4【阻止】デプロイ時にv0.22のengineが残り得る

- `engine.js`は`VERSION='v0.23'`
- `index.html`のtitleはまだ`流通の島 v0.22`
- importはv0.22と同じ`./engine.js?v=133109`

プロジェクト規約はengine変更時のcachebuster更新を必須としている。同じURLのため既存ブラウザがv0.22の
engineを保持する可能性があり、HTMLとengineが混在する。実画面では右下がv0.23でも、上部HUDに
廃止済みの`支援0/3`が残ることも確認した。

### F5【重要】鉄4.0→5.0は理論上の天井を外すが、観測されたE8改善の原因ではない

監査seed 11/13/14を、鉄の購入上限だけ4.0 / 5.0に切り替えて同一乱数で比較した。
飢餓、人口、金庫、麦輸入、最高Lv、転職イベントはすべて同一で、上位世帯も`iron`未充足だった。

したがってE8最高3/3/3→4/4/3の差は、現行台本ではチェーン建て直しが経済を変えた効果である。
5.0への変更自体は将来の理論天井を外す可能性があるが、現時点の因果説明は訂正が必要。
また5.0という値は魔法定数なので、本来は使用価値または輸入パリティから導くべき。

### F6【重要】E1が8.8/日へ後退し、残課題から漏れている

v0.22の標準監査では麦輸入1.5/日で合格していたが、v0.23は8.8/日でFAIL。
24 seedでも固定台本18/24、建て直し台本16/24で、建て直しが悪化させる。
README / CONTEXT / WORKLOGのv0.23残件はE15・E8・E10だけを列挙し、E1を落としている。

### F7【重要】対岸漁はUIから隠れただけで、自律行動から除外されていない

`JOBS`には`fisher2`が残り、`pickJob()`は全`JOBS`を候補にする。水際世帯は破綻転職で対岸漁へ入れる。
24 seedの建て直し台本で2回の`→fisher2`転職を観測した。最終時に残らなかっただけで、罠職業は閉じていない。

### F8【重要】石畳完成時に経路場を無効化していない

`tileCost()`と実移動速度がworldごとの`paved`を見る修正は正しい。しかし石畳完成時は`this.paved=true`だけで、
`this.flow=null`にしていない。局所probeでは、未舗装なら草地直進、舗装後なら道の迂回路が最短になる盤面で:

- 未舗装の次手: `[14,5,9]`
- 舗装直後（古いflow）: `[14,5,9]`
- flow再構築後: `[15,6,7.11]`

現在の経路の歩行速度は舗装化されるが、舗装で新たに最適になった経路へ切り替わらない。

### F9【重要】world分離は不完全で、世帯IDが重複する

海運投資の`expCap`分離はprobeで確認できた。world Aへの投資はworld Bとグローバル`P.EXP_CAP`を変えない。

一方、世帯IDの`HID`はmodule-globalのままで、`new World()`のたびに0へ戻る。world Aへ世帯#0を作り、
world Bを生成した後でworld Aへ世帯を追加すると、world A内に#0が2世帯できた。複数world比較、リプレイ、
将来の保存・復元で、IDをキーにする追跡やUIが壊れ得る。

### F10【重要】E2の観測バイアスが残り、絶滅を合格として隠せる

E2は最終時点に存在する職の和集合だけを対象にし、各職の最良世帯だけを見る。固定台本24 seedでは炭焼きが
24/24で最終不在だったため、炭焼きの採算をFAILにせず「判定しない」。v0.23は台本で炭焼きを残したため
E2のPASSが1つ増え、判定総数が27→28になった。職の不在、代表値、最悪値を分けて監査すべき。

### F11【重要・既知】E15は合格判定として機能していない

現行E15は何も建てず、最終金庫-177,627表示、飢餓167、破産なしでPASSする。自動支援を消しても信用限度が
非常に大きく、4年監査では利息期間も短いため、財政の弧を検証していない。既知負債だが、R1前の阻止条件に
置くべき深刻度である。

### F12【軽微だが広範】自動支援廃止後の残骸がUI・状態・文書に残る

- HUD: `支援0/3`
- engine: `this.bailouts=0`、`co.bail`
- READMEの現行機能: `支援3回`
- CONTEXT §5: `本国支援3回(BAIL)`

プレイヤーに存在しない救済を期待させ、監査出力にも無意味な`support`を残している。

## 5. `25/28`の読み方

v0.22の23/27から、v0.23の25/28への見かけ上の差は次の構成になっている。

- E3: 測定誤り修正でFAIL→PASS（妥当）
- E16: 口銭条件削除でFAIL→PASS（仕様弱化）
- E2炭焼き: 建て直し台本で最終存在し、PASS判定が1件増加（分母27→28）
- E1: PASS→FAIL（回帰）
- E8: 3→4へ動いたがFAILのまま

従って、`25/28`を「経済系が2点改善した」と解釈してはいけない。監査定義変更後の新基準値であり、
旧版との改善比較には使えない。

## 6. 推奨する修理順（本レビューでは未実装）

1. **P0: 監査を先に修理**
   - Scenario Aからチェーン建て直しを外す
   - 助言追従は独立シナリオにし、最低24 seedで健康・財政・建築数を出す
   - E16の成功定義を「都市建設の基本拍」と結び直してから条件を固定する
2. **P0: 配布整合性を修理**
   - cachebuster / title / VERSIONを同期
   - 廃止済み支援のHUD・状態・説明を除去
3. **P1: 炭焼き絶滅を再診断**
   - 現在飢餓と履歴飢餓を分ける
   - 職の自然再参入、空き区画再利用、再建時の人口負荷を同じ設計問題として扱う
4. **P1: 回帰テスト追加**
   - 複数worldの世帯ID一意性
   - 石畳完成直後のflow再構築
   - 隠した職への自律転職禁止または明示的許可
   - E1を残件一覧へ戻す
5. **P1: 鉄の効果を到達局面で再評価**
   - Lv4世帯が鉄購入判断へ到達するseedを選び、上限だけをA/Bする

## 7. セカンドオピニオン

Claude側の第4・第5精査が対象にしたR1-R5の空間設計について、W1「速度だけ2倍では同値にならない」、
W7「E15をR1前に再設計」、W9-W11を統一する「1日圏」原理には同意する。特にE15を阻止条件へ置く判断は、
本レビューの実測とも一致する。

こちらから追加する懸念は、R1の前に**現行v0.23の監査そのものを信頼可能に戻す必要がある**こと。
空間定数や中継蔵の設計が正しくても、Scenario A・E2・E16が現在のままでは回帰と改善を区別できない。
