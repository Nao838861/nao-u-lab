# r004：景物増量と内蔵RAM最適化

2026-10-18。依頼原文：

> 木や家をもっと増やしても３０fpsが維持できるように、徹底的に最適化を繰り返して。木の下のLODはもっと遠くから出したい。不自然なので。最適化を進めて。

## 採用した変更

- 投影・除算・面の裏表判定を512バイトの命令キャッシュに収まる配置へ移動。8ビット商で済む除算は先頭8反復を省略。頂点ポインター、符号、戻り番地をレジスターに保持し、作業RAMへの保存を削減。
- ワールド座標の景物と車の頂点ループを分離。景物で不要な車用判定と入力座標の一時保存を省略。
- 物体全体の球と視錐台による判定を詰め、完全に画面外の物体を頂点変換前に除外。水平z+1.5r、垂直0.75z+1.28125rに固定小数点誤差の余裕を加える。
- 木と家はローカル座標メッシュを各1組だけ持つ。16バイトのインスタンス記述子と6バイトの中心座標で追加でき、8KiB作業領域内で最大20個の景物を置ける。
- 配布版は木8→10本、家2→3軒。既存の景物はそのままに、追加の家はコース内側(420,420)へ分散。木の幹のLOD境界は奥行き24→64ワールド単位。遠方でも樹冠の形は同じ、家のLODはなし。既存の屋根・ひさし・壁色は維持。
- GSUを25MHzのままTURBO経路で駆動。内蔵RAMを立下りで読み、立上りで受け取ることで待ちを削減。命令キャッシュは16バイトを連続転送。GSU genericは既定falseなので既存の診断・立方体回路では従来経路を維持。
- MesenはM7R6だけ新時間モデル。データRAMは3クロック、キャッシュは16バイトの転送16クロック＋制御の余裕10クロック。M7R4/5の時間・色は変更しない。命令単位のモデルでありRTLのサイクル完全再現ではない。

地面テクスチャ、6502、音、物理、r003の空パレット合成はそのまま。共有メッシュ化の座標丸め差は最大1/128ワールド単位なので、旧版との輪郭の1画素差はあり得る。

## 測定と採否

| 試行 | 結果 |
|---|---|
| 8ビット商の除算だけ | 選択8場面で0.076%短縮。画像一致 |
| 投影を命令キャッシュへ | 選択8場面で約7.25%短縮。画像一致 |
| 面判定もキャッシュ内へ | 1,412姿勢すべて画像一致、命令モデルの合計12.816%短縮 |
| ワールド頂点専用経路 | 選択8場面で元の版より約12.54%短縮。画像一致 |
| ゼロ法線成分の乗算省略 | 分岐費用で遅くなり不採用 |
| スパンの遅延初期化 | 全1,412姿勢一致したが全体の短縮率が11.10%に後退し不採用 |
| 左右エッジ直接格納 | 細い面などで2〜7バイトの画像差。条件を変えて3回検証したが不採用 |
| 保守的な物体カリングの引き締め | 増量ROMの1,412姿勢で一致、合計1.224%短縮 |
| PLOTを4画素ずつ展開 | 全1,412姿勢一致したが0.899%遅くなり不採用 |
| 内蔵RAM高速化の第1段階 | 同一絵の重い4場面でRTL 32.75〜36.79ms→21.40〜23.35ms |
| 半周期RAM＋連続キャッシュ転送 | 20景物のストレス版の選択8場面で最大39.115→32.178ms。画像一致。ただし全体30fpsには不足する場面あり |

百分率は同じ命令モデル内の比較。RTL実測時間とは分けて扱う。20景物ストレス版は最終カリング変更前のROMであり、配布する13景物版とは別。

途中の13景物集中配置はキャッシュ32クロックのモデルで最悪27.006ms、RTL代表8場面は13.679〜23.884ms。Mesen全周768姿勢のうち4姿勢で20fpsだった。家の分散と、過大だったキャッシュ待ちモデルの補正を分けて実施した。26クロックに補正後も、集中配置8場面と20景物ストレス8場面の全16場面でモデルはRTLより1.58〜5.25%長い。これは回路の追加高速化ではなくエミュレーターの時間モデル補正。

最終13景物版は高速／従来メモリーモデルの1,600姿勢で全16KiB描画バッファが一致、命令モデルの最悪24.383ms。最終配置の代表8姿勢のRTL実測は10.411〜23.757ms、モデルは1.44〜5.36%長い。記録は配布物 `verification/rtl-gsu.json` と `model-vs-rtl.json` に保存する。選択場面での検証であり、全状態の上限証明ではない。

Mesen 25MHzのCPU・音・Mode7・GSU・PPUを通した全周64地点×4視点×3ドリフト角の768姿勢で、すべて30.0494fps以上。重い代表8姿勢を各120VBlankで測って全て30.0494fps、遠方の木2姿勢は約59.6〜60.1fps。最終PPUの491,520画素が独立参照と一致。旧r003の19場面も画像とGSU時間が一致する。

FPGAは6,118/6,272 LE、メモリー218,240/276,480bit、M9Kは30/30。内部setup最小余裕3.377ns、hold最小余裕0.133ns。クロックは25MHzのまま。外部CPU/PPU/PSRAMのタイミング保証と実機確認は未完了。

配布時のMesen全周768姿勢・重い8姿勢のfps結果、PPU画素照合、RTL起動・合成・描画の記録は配布物の `verification/` に保存する。30fpsは検証した配置・視点の範囲。さらに増やす場合は同じ検査を通す必要があり、無制限に追加できるわけではない。

## 再生成

既存r003 PC ROMを基準に `tools/build_r004.py --project <nes_superfx> --cc65 <cc65/bin> --base <r003.nes> --balanced`。無指定は旧個数の8本2軒、`--dense` は16本4軒のストレス配置。モデルやコードは同じ。基準ROMの6502・地面・音が変わらないことを生成時にassertする。

`tools/scan_r004.py --project <nes_superfx> --variant balanced` で高速／従来モデルを比較し、重い姿勢を `poses.json` に出す。保存先を分ける場合は生成に `--out`、走査に `--folder` を使う。Mesenの準備は `tools/prepare.py`、`tools/build_sky_core.py --generated build/generated/NesFxGsu.hpp --out build/r004-core-calibrated`。RTLは `tools/verify_gsu.py --rom ... --poses ...`、`tools/verify_boot.py --rom ...`、`tools/verify_display.py --exhaustive`、ビットストリームは `tools/build.py quartus`。

`tools/iterate_r004.py` は試行時点のソース・ROMに対する比較用。現在の共有メッシュコードを旧レイアウトのROMに単独で差し替えてはいけない。配布ROMの再生成には必ず `build_r004.py` を使う。
