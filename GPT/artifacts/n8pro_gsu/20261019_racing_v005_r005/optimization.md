# r005：描画最適化と、挙動を保ったFPGA容量削減

2026-10-19。依頼原文：

> 最適化の継続と、あとFPGAの挙動を変えずに容量に余裕を持たせることができるかを徹底的に試してほしい

基準は保存済みr004（回路ソース `c0304dccc3b62114d134662336486944c8df8c8a`）。景物は木10本・家3軒、幹の境界64のまま。地面・色・形状・音・6502・物理・Mesenコア・25MHz設定を保つ。変更はGSUコードと、同じ外部応答を目指したFPGA内部の実装。

## 結果

| 指標 | r004 | r005 |
|---|---:|---:|
| 論理セル LE / 6,272 | 6,118 | 5,957 |
| 空きLE | 154 | 315 |
| M9K RAM / 30ブロック | 30 | 28 |
| 論理RAMビット数 | 218,240 | 218,240 |
| 9bit乗算器 / 30 | 15 | 15 |
| 内部setup最小余裕 | 3.377ns | 3.602ns |
| 内部hold最小余裕 | 0.133ns | 0.107ns |
| 選択した重い8姿勢のGSU単体RTL最大 | 23.7574ms | 22.60292ms |

RAMのデータ量は減らさず、物理ブロックの空きを2個作った。LEの空きは約2倍になったが、全体ではまだ約5%しか空いていない。大きな機能を追加できるほど余裕があるとは言わない。外部バスのタイミング保証と実機動作は未確認。

1,600姿勢で全16KiBの描画バッファが一致。GSU命令モデルの合計クロックは4.4678%短縮（コース768姿勢だけでは4.2387%）。最悪値は24.38292→23.30332ms。軽い5姿勢には最大0.04054%の微増があり、全姿勢が速くなったとは扱わない。Mesen全体の検査では全周768姿勢すべて30.0494fps以上、重い8姿勢も各120VBlankで30.0494fps。時間モデルもコアDLLもr004と同一。

## 採用したFPGA変更と、範囲の根拠

1. 行テーブルを1536×32bitの1配列から512×32bitの3配列へ分割。Quartusが深さを2048へ丸めていた無駄を減らし、8→6 M9Kにした。3配列の読み出し値とバンク選択を同じクロックで登録するため、既存の1クロック読み出しを維持する。有効アドレスは従来通り0..1535。
2. DSPのU/V原点計算は、座標と刻み幅を先に選び、加算器列を共有する。状態13/15で同じクロックに結果を格納する。
3. `PC/PS`は検査後0..256、`y-96`は-96..95。分子・分母の絶対値は57,344以下なのでsigned 17bitで足りる。高さの16bit値×512はsigned 25bitで完全に保持できる。入力検証の32bitノルム計算とエラー判定は保つ。
4. 逐次乗算の加算と除算の減算を、1本の加算器で共有。除算の比較も減算結果のborrowから得る。反復数48と`done`の発生クロックは保つ。DSP内部の除算対象は、正と確認した分母か検証済みノルムだけなので、除数の絶対値回路を省ける。汎用`serial_math`の既定値は従来通り負の除数にも対応する。
5. 描画RAMの`compact()`にある-2048を、同じアドレスとなるビット配線へ置き換える。16,384個の全入力で同値を確認した。
6. 同じRTLを配置seed 1..5で比較し、LEが最小で内部タイミングも成立するseed 3を採用。

基準を再合成したRBFは、保存済みr004のRBFとバイト単位で一致した。最終ソースから通常のビルド手順で生成したRBFも、採用した実験RBFとバイト単位で一致した。

## 試した容量案

設定名の誤記による1件を除き、18案を試した（うち1案はRAM推論に失敗）。下記の複合案は、上の採用変更の部分集合。数値はすべて配置配線後のLEであり、単純な加算的効果としては扱わない。

| 案 | LE | M9K | 採否 |
|---|---:|---:|---|
| 基準＋Area設定 | 6,118 | 30 | 設定だけでは削減なし |
| 初期のRAM分割記法 | — | — | RAMへ推論されず失敗。読み出し記法を修正 |
| 修正RAM分割＋原点共有＋幅縮小＋減算比較 | 5,992 | 28 | 中間案 |
| MUX再構成を明示ON | 5,992 | 28 | Autoと差なし |
| 演算器の入力レジスターを組合せ回路へ | 6,145 | 28 | FFは減ったがLE増、不採用 |
| 加算器共有＋正の除数専用経路 | 5,989 | 28 | 中間案 |
| 右オペランドを18bitへ | 6,116 | 28 | FF/LUTは減ったが最終LE増、不採用 |
| 減算比較版＋右18bit＋アドレス配線化 | 6,126 | 28 | 不採用 |
| 同上＋除算の余り幅も縮小 | 6,084 | 28 | 演算検証は合格、最終LEで不採用 |

## 採用したGSU変更

- 辺の4座標をRAMへ一時保存してから読み直す箇所を、レジスター渡しにした。
- スパン初期化の`$7fff/$8000`を、定数の再読み込みではなくNOTで交互に生成する。
- 負の傾きを辺の開始時にfloor基準へ正規化し、走査線内の方向判定を減らす。
- 画面内に完全に収まる面は、各走査線で繰り返していた左右クリップの一部を省く。
- 分岐の待ち命令へ、必要なレジスター選択を移した。

段階ごとの1,600姿勢合計短縮率は、傾き正規化＋分岐で0.3912%、画面内判定も加えて1.3526%、座標のレジスター渡し＋初期化改善まで加えて4.4678%。すべて基準画像と一致。ROMはGSUコードのある2バンク内だけ2,582バイトが変わり、その他のデータは同一。

## 検証範囲

- 旧回路と候補を並走するmiterを作り、各クロックの全ての定義済み出力を比較。未初期化RAMなど、旧回路で値が未定義な部分は一致の主張に含めない。形式的な全状態証明ではない。
- DSPの34カメラ・26,112ワードを独立整数式と照合し、各クロックの状態・行データも旧回路と比較。
- 汎用演算器2,176件＋DSP用の正の除数経路2,120件を、境界値・乱数・独立整数式・旧回路と比較。48bitの最小値、積の桁あふれ、汎用経路のゼロ除数、busy中のSTARTを含む。
- 33カメラの追加試験で、処理中のレジスター書換え、busy/ready中のSTART、不正カメラ、誤ったcommit、処理中resetを比較。
- 旧r004 ROMと新r005 ROMの両方で、実6502初期化/NMIの282,122バス取引を再生。GSU・DSP・画面DMAを通し、CPUに見える値と完了時刻を比較。
- 新GSUの重い8姿勢で、RTLの全16KiB描画バッファを参照画像と比較。GSUのCPU応答・描画RAM読み出し・完了信号も毎クロック旧回路と比較。
- Mesenの1,600姿勢で描画バッファ一致。全周768姿勢のfps、重い8姿勢のfpsとPPU 393,216画素の独立照合。
- r004と同じMesen DLLを使用。時間モデルは代表8姿勢でRTLより1.61〜5.69%長い見積もりを維持する。

旧ROMを使って比較したのは、FPGA容量削減とGSUソフトの速度改善を分けて確認するため。同じROMへの応答は同じで、新ROMの描画が速くなるのはGSUコードの変更による。描画モジュールとパレット合成そのものは変更していない。

## 再生成

`tools/build_r005.py --base <保存済みr004 PC ROM> --project <nes_superfx> --cc65 <cc65/bin>`で現行ソースからROMを生成。基準ROMのSHA256を確認し、GSUコード以外が変わらないことをassertする。

`tools/build.py quartus --seed 3 --area`でRBFを生成。`tools/area_r005.py`は固定r004ソースから各案を独立生成する実験用。`tools/equivalence_r005.py`と`tools/stress_r005.py`が旧回路との比較を行う。`tools/optimize_r005.py`はGSU試行の再現用で、最終ROMの通常ビルドには`build_r005.py`を使う。

実機用ROMはPC用ROMからPRGと地面データを同じ形式で変換する。配布物にはROM・RBF・r004と同じMesenコア・全検証結果・ソースを別フォルダーとして保存し、旧版を上書きしない。
