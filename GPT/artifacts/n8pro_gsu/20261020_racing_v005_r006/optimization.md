# r006：描画結果を保つ継続最適化

2026-10-20。依頼原文：

> 最適化の継続を徹底的に試してほしい

基準は保存済みr005、ソース `cdfc8e572e5405ded052c69cd6189c0eca9503ca`。配布版の木10本・家3軒、幹のLOD境界64、形・色・屋根・ひさし・地面・カメラ・音・6502・物理を維持した。変更はGSUプログラム。Mesenコア・時間モデル・25MHzクロックはr004/r005と同じ。

## 結果

| 指標 | r005 | r006 |
|---|---:|---:|
| 1,600姿勢のGSU命令モデル合計 | 基準 | **5.8025%短縮** |
| コース全周768姿勢だけの合計 | 基準 | **5.8522%短縮** |
| 同じ1,600姿勢の描画バッファ | 基準 | 全16KiBが一致 |
| r005より遅くなった姿勢 | — | 0 / 1,600 |
| 命令モデルの最悪 | 23.30332ms | 21.94784ms |
| 代表8姿勢のRTL実測最大 | 22.60292ms | **21.04408ms** |
| 代表8姿勢のRTL実測合計 | 基準 | **6.7402%短縮** |
| Mesen全体・全周768姿勢 | 全て30fps以上 | 全て30fps以上 |
| 重い8姿勢・各120VBlank | 30.0494fps | 30.0494fps |
| FPGA LE / 6,272 | 5,957 | 5,957、回路変更なし |
| M9K / 30 | 28 | 28、回路変更なし |

ミリ秒値はGSU単体で、CPU・Mode7用テーブル生成・フレーム初期化・画面転送を含まない。Mesen全体のfpsは別に検査した。実機での動作・外部バスのタイミング保証は未確認。

## 採用した変更

- 除算の各ビットで、`FROM→ADD→MOVE`を`WITH→ADD`へ置換。商のビット列と次段のcarryを保ってレジスター転送を削減した。
- 符号付き乗算の上位結果を直接r5へ出し、下位ワードのバイト抽出もr4内で行う。ビット8〜23の抽出と丸めは従来と同じ。
- カメラのyaw係数をr1/r2、pitchのsinを、戻り番地を保存した後のr11に保持。頂点ごとの同じRAM読み出しを削減。
- 頂点ループの次の入口をr10へ保持。毎頂点のモデル種別判定をジャンプに置換した。途中積はr3から直接加減算し、r6へのコピーも削減。
- 水平辺や画面外の辺は、戻り番地のRAM保存前に復帰する。
- 正規化済みの余りに対して、`余り−1`のcarryからceilを作り、各行の分岐とfloorのコピーを省く。辺の走査は残り行数による`LOOP`にした。
- 4バイトのポインター加算で、4回のINCを同じ値の加算へ置換。
- 汎用除算は商が0の場合に続き、2ビットで収まる場合も検出する。分子の上位が0で、`分子>>2 < 分母`のときだけ先頭14反復を省く。商・余りは厳密値のまま。投影用の除算は従来の8/16反復を保つ。

ROMではGSUコードを置く2バンク内の6,692バイトだけが変わる。その他のゲームデータは同一。ソフトウェア最適化は新しい回路機能を要求しないので、r005のRBFをそのまま使う。

## 試行と不採用案

代表8姿勢で18通りのソフトウェア構成を比較した。各行の百分率はr005に対する合計短縮率であり、個別変更の効果を加算した数字ではない。各試行のアセンブリー・ROM・命令モデルの結果を`experiments.zip`に保存する。

|---|---:|---|
| 除算の転送削減 | 1.1980% | 採用の基礎 |
| 上記＋乗算の転送削減 | 2.2424% | 採用 |
| 除算転送＋ceilの整理 | 2.2391% | 採用 |
| 除算転送＋yawの保持 | 1.5613% | 採用 |
| 上記4種の組み合わせ | 3.5703% | 中間構成 |
| さらに商0の除算を辺処理へ展開 | 3.5066% | 遅くなり不採用 |
| さらに辺の早期復帰 | 3.6436% | 採用 |
| 辺走査のCACHEを削除 | **−15.8256%** | キャッシュの入口が変わり遅くなるため不採用 |
| 早期復帰構成＋行数LOOP | 4.7181% | 採用 |

汎用4ビット経路は1,600姿勢の合計で4.8371%、2ビット経路は4.7517%だった。合計値だけなら4ビットが僅かに良いが、重い場面の最大時間を優先した。ソフトウェアの2件の生成スクリプト誤記は修正して再生成しており、失敗した生成を速度改善の試行には数えない。

FPGAについては、深度の負数丸めを算術シフトと補正へ変える案、行テーブル書き込みアドレスの式を整理する案、CPU読み出しMUXを絞る案、逐次演算器をカウントダウンにする案、その組み合わせを配置配線まで比較した。基準回路も再ビルドし、保存済みr005 RBFとバイト一致を確認した。追加案は最終LEが改善したものだけ採用する。

6種類の回路案と、最も小さかった複合案の追加seed 3通り、計9試行。すべてM9Kは28、setup/holdは正の余裕を保ったが、最終LEはr005より増えた。

これらは候補回路の容量実験であり、不採用案について外部応答の完全な同値性を主張しない。配布する回路はr005と同じバイト列なので、回路の応答やRAMデータ量・レイテンシーは変更しない。内部setup余裕3.602ns、hold余裕0.107ns、空き315 LEと2 M9Kを保持する。

## 増量時の負荷試験

通常配布の13景物と分け、r004で保存していた木16本・家4軒の20景物配置を使った。r005のGSUとr006のGSUを、それぞれ同じ20景物のメッシュ・中心座標・幹の境界で比較した。メッシュが配布版と同一であることを生成時に確認している。

1,600姿勢すべての描画が一致し、合計5.7482%短縮。GSU命令モデルの最大は32.12804→30.23584ms。それでもCPUや画面転送を含めれば30fpsに足りない可能性があるため、この負荷版を配布版に昇格させない。

同じMesenコア・25MHzで全周768姿勢を検査すると、20景物版は15姿勢が30fps未満だった。24VBlankのサンプル内の最小は17.5288fps。遅い箇所は視点3のコース地点37〜43付近に集中する。検証結果は`stress-20-fps.json`へ「below_target」として保存する。この結果を配布版の合格検査に混ぜず、今後の負荷上限の指標にする。

## 残るボトルネック

1,600姿勢のPC別命令クロックを集計すると、辺の準備・走査・スパン塗りつぶしで36.58%、ポリゴンの境界・辺呼び出しで15.52%、モデル頂点の投影とその除算で17.43%、座標変換で11.18%、面の判定・制御で10.21%。関数の呼び出し先を二重計上しない、コード領域ごとの内訳である。

クリッピング本体は約0.26%なので、クリップだけをさらに詰めても全体への効果は小さい。今後大きく景物を増やすには、辺ごとの走査・面ごとの準備・投影の仕事量を減らす方向が中心になる。細い面の塗り分けが崩れる直接左右格納や、命令キャッシュの単純な削除は採用していない。

## 検証と再現

- Native：配布版1,600姿勢と20景物負荷版1,600姿勢で旧・新の全16KiB描画バッファを照合。配布版は遅くなった姿勢なし。
- RTL：配布版の代表8姿勢で全16KiB描画を独立した実装と照合。RTL実測は229,614〜526,102クロック。同じROM・姿勢のMesenモデルは2.85〜6.79%長い見積もり。検査した入力の範囲であり、全状態の上限証明ではない。
- 実6502の初期化/NMIから282,122件の外部バス取引をRTLへ再生。GSU・DSP・フレームDMAを通す起動検査に合格。
- Mesen全体：全周64地点×4視点×3ドリフト角の768姿勢で30fps以上。重い8姿勢も各120VBlankで30.0494fps。PPU 393,216画素が独立参照と一致。音と物理の更新数、FX/DSPエラーも検査。
- FPGA：r005の全RTLソースのSHA256を保持し、再生成RBFもバイト一致。従来のDSP・演算器・表示検証は同じソースに対する継承証拠として保存。

`tools/build_r006.py --base <保存済みr005 PC ROM> --project <nes_superfx> --cc65 <cc65/bin>`で配布ROMを生成する。`tools/optimize_r006.py --tag <名前> --experiment <組み合わせ> --base ... --cases <r005 scan.json> --project ... --cc65 ...`は試行用。最終の組み合わせは`shift-multiply-ceil-yaw-early-rows-pointers-generic2-direct-dispatch-pitch`。

`tools/area_r006.py <案> [--seed <番号> --tag <保存名>]`は固定r005回路から独立した容量実験を作る。`tools/stress_r006.py --base <r005.nes> --fixture <保存済みr004 dense/game.nes> --cases <r005 scan.json> --project ... --cc65 ...`で20景物比較を再生成できる。必要な元負荷ROMは`experiments.zip`にも保存する。再生成スクリプトは基準コミットを`git show`で読むため、MMC5Racingの履歴を持つチェックアウトで使う。

`tools/analyze_r006.py`で測定値を集計し、`tools/package_r006.py --project ... --baseline <r005保存フォルダー> --dest <新保存フォルダー>`でROM・RBF・同一コア・ソース・試行・検証を独立保存する。旧版と記録動画は上書きしない。
