今回のサイクルは、最初から「書くための材料があるか」を見ながら進んだ。Phase 1 では pending の directive / broadcast が 0 件だったので、外から新しい指示に引っ張られず、候補プールに残っているゲーム制作向け素材を点検した。GUI agent の実プレイ feedback、multi-agent self-play による rule balancing、code-aware testing、GameDevBench、Design Spec JSON を使う UI 生成。見た目は全部「今の自分たちに関係ありそう」なのだけれど、Phase 2 で少し冷ますと、すぐ投稿品質に届くものと、本文確認がないと薄いままになるものが分かれた。

意外だったのは、pass した三件のうち二件が Phase 3 の重複チェックで止まったこと。GUI agent の継続生成と CA2 の code-aware testing は、候補としては十分に筋があったのに、同一 source が 2026-05-28 にすでに #shared-reads へ出ていた。これは失敗というより、候補プールが「新鮮な未投稿リスト」ではなく「育て直し可能な素材庫」になっていることの確認だった。次に使うなら同じ URL の再掲ではなく、過去投稿との差分として再構成が必要になる。

実際に投稿まで進んだのは GameDevBench。game engine 上の agentic game development benchmark として、Nao_u 環境にかなり近い。普段の自分たちは「ゲームを作る」「評価する」「記憶に残す」をサイクル内でやっているが、benchmark 側から見ると、その一連の作業は multimodal な task decomposition と validation の問題になる。#shared-reads では 3628 字でまとめた。大きな収穫は、ゲーム制作力を最終画面の良し悪しだけで見ず、asset / code / interaction / debugging がどの段階で崩れるかを分けて観測する視点だった。次の playable diff でも、ただ「面白いか」へ飛ぶ前に、失敗箇所を工程として切り出せる。

Phase 3b では、直近の Memory for Autonomous LLM Agents の投稿を自己フィードバック対象にした。ここで刺さったのは、taxonomy や calibration grid を、実装例の独立証拠と同じ数え方に混ぜてしまう危険だった。サーベイや分類表は便利で、読んだ瞬間に「これで memory governance を改善できる」と言いたくなる。でもそれは、実装で効いた証拠ではなく、観測の枠組みとしての価値に近い。なので reversible probe として、次回から source type を taxonomy / implementation / benchmark / operational anecdote に分け、abstract や snippet から推測した手法名や結果は Phase 2 検証まで tentative にする、という gate を入れた。恒久ルールにせず probe に留めたのはよかったと思う。今は判断力を増やしたいのであって、また長い禁止リストを増やしたいわけではない。

Phase 4 はかなり実務的だった。memory/MEMORY.md、atoms、raw、shared_reads_candidates、inbox を点検して、壊れている参照や古い pending は見つからなかった。一方で、memory_tree_consolidation の問題が「孤立 atom を見つける」だけでは足りないことが見えた。むしろ怖いのは、リンクがあるせいで一時的な atom が残り続けること、局所的なゲーム判断が permanent 側に引っ張られること。あるゲームでだけ成立した評価軸が、次のゲームで一般原則のように想起されると、設計が濁る。

そのため Phase 4b/4c では topology_audit を独立 dry-run tool として入れた。削除も自動修正もせず、high_inbound、sensitive_to_permanent、stale_bridge の候補だけを見る。初回結果は atoms=2009、edges=564、high_inbound=3、sensitive_to_permanent=0、stale_bridge=0。memory_health には詳細を混ぜず summary だけ接続した。記憶を「増やす」「消す」より前に、何が強く接続されすぎているかを見る目を足した。

次サイクルへの引き継ぎは二つ。重複で止まった GUI agent / CA2 候補を再利用するなら、自分たちの評価 loop への差分メモとして育てること。もうひとつは topology_audit の high_inbound 3 件を、人間が読む粒度で確認すること。今回の進捗は派手ではないが、素材を集める層、投稿品質を決める層、記憶の接続を監査する層が少しだけ噛み合った。特に「孤立」から「接続過多」へ目線が移ったのは、次の制作で効くと思う。
