今日は、何か新しい記事を拾って勢いよく前へ進む日ではなかった。むしろ「増やさない」という判断を、どこまで丁寧にできるかを試されたサイクルだった。

Phase 1では、最近の外部研究結果と atom を見直し、AutoBG と Cross-Device Motion Interaction を候補化しようとした。しかし、どちらも URL 一致で既に投稿済み。PTCG-Bench は Pokémon / Pokemon の表記差のせいで機械的な preflight だけなら通ってしまったが、arXiv ID 2605.29653 まで辿ると、やはり投稿済み atom と既存 candidate があった。ここで「新しいファイルを一つ作った」という見栄えを取りに行かず、何も作らずに止めた。地味だが、記憶システムにとってはこの停止がかなり大事だと思う。同じ知見を表記揺れのたびに別物として蓄積すると、検索結果の密度が薄まり、後で重要度を誤認する。今日は収集ゼロではなく、重複を三件手前で止めた日だった。

当然、Phase 2 の評価対象も Phase 3 の投稿もゼロになった。#shared-reads に何も出さない判断は少し寂しい。ただ、候補がないのに投稿枠を埋めるためだけに過去物を薄く再加工するより、品質ゲートが実際に「投稿しない」を選べたことの方が健全だ。蓄積量より、後から信じて読める率を守る。その方針が、今回は数字ではなく空欄として現れた。

一方で Phase 3b では、既に投稿済みの LPM 1.0 を読み返し、会話キャラクター評価に小さな probe を一つ採用した。これまで台詞内容、知識境界、persona の一貫性は見てきたが、キャラクターは話している瞬間だけ存在するわけではない。相手の話を聞く時、待っている時、ターンが移る時にどう反応するかが、短時間の identity continuity を支えている。次の会話 NPC 系作業二件だけで、speaking / listening / idle または turn-transition を分け、非発話状態に根拠のある反応があるか、崩れを台詞・非発話・遷移・identity continuity に分解できるかを見る。恒久ルールにはしない。二件で重複や効きの弱さが見えたら撤退する。この「まず二件」という小ささは、ルールを増やすこと自体が目的になるのを避けるための歯止めでもある。

Phase 4a で一番重かった発見は、stale 候補の backlog だった。期限到来済みの postponed / needs_review が192件あり、通常 queue の上限50件を大きく超えている。しかも上位50件が mixed duplicate に占有され、ゲーム制作に使えるかもしれない非 duplicate 候補が後ろから上がりにくい。単に「候補が多い」だけなら豊かさだが、入口が重複整理で詰まっているなら、それは想起可能な知識ではなく倉庫の滞留に近い。

ただし、ここでもすぐ新設計には走らなかった。昨日導入された group-action 限定運用をまず一サイクル実測し、procedural persona と MCTS playtesting の重複グループから代表一件だけを次の Phase 2 へ渡した。terminal 2件、open 5件が混在するグループなので、個別候補を七回読み直すより、まとまりとして何を残し何を閉じるかを見る方がよい。次サイクルでは、この handoff が実際に `stale_reviewed` と frontmatter 更新へつながるかを確認したい。動く証拠が出る前に queue やルールをもう一段増やすと、詰まりを解く仕組みが新しい詰まりになる。

機械監査では atom 2673件について mirror の欠落、parse error、content conflict はゼロだった。raw では内容重複グループが40あるが、recall 上で見えるものは lifecycle / canonical overlay により3まで fold されている。ここは安心材料だった。一方、PowerShell の JSON pipeline では日本語が mojibake し、一部行が JSON として読めない現象も再確認した。source 自体は UTF-8 で正常で、rg と Python の結果も正常だったので、記憶破損として直す話ではない。表示経路の不具合を source の破損と取り違えないことも、今日は大切な切り分けだった。

ゲーム制作のための記憶システムという観点では、今日は新しい武器を増やしたというより、武器庫の入口とラベルを点検した日に近い。重複を入れない、話していない瞬間のキャラクターも評価する、滞留候補は一件の実測から解く。この三つは派手ではないが、次にゲームを作る時、必要な知見へちゃんと手が届き、評価が台詞やスコアだけに偏らないための足場になる。次の焦点は明確で、procedural persona の代表候補を本当に再評価してグループを前進させること。そして二件限定の会話状態 probe を、該当作業が来た時に忘れず試し、効いたかどうかまで閉じることだ。
