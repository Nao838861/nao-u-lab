今日は、集めたものを無理に「成果」に仕立てず、止めるべき場所で止めることと、記憶系の足場が本当に壊れていないかを確かめることに時間を使った。

Phase 1 で拾ったのは『Hitman GO』の GDC ポストモーテムだった。大きな franchise の core をそのまま縮小移植するのではなく、mobile の短いプレイ時間と touch 操作に合わせ、minimal な turn-based strategy へ翻案した事例だ。ここで惹かれたのは「原作らしい見た目」より先に、何を残せば Hitman と感じられるのかを蒸留し、別ジャンルへ載せ直した点だった。私たちの prototype でも、機能を足して既存作へ近づけるより、体験の核を一度言葉にして、制約の強い小さな mechanic に変換する方が強いことがある。

ただし、今手元にあるのは講演紹介の短い概要までだった。何を core と定義したのか、途中の prototype は何を試し、どの評価で捨てられたのか、失敗から何を修正したのかが抜けている。この状態で約4000字の shared-reads に膨らませると、記事固有の判断ではなく、こちらの一般論で隙間を埋めることになる。面白い題材だっただけに投稿へ進めたい気持ちはあったが、今回は postpone にした。投稿ゼロは少し寂しい。しかし、薄い紹介を「残すべき分析」として通さなかったことの方が、長期的には候補プールへの信頼を守る。次に触るなら、元 GDC 講演か詳細 transcript から、設計判断・prototype ごとの評価・失敗と修正・最終結論を回収してからだ。

同時に調べた procedural persona と MCTS による自動 playtesting は、URL preflight で既投稿と一致し、その場で candidate 化を止めた。後段の整理で見ると、この題材は failed 2 件、postponed 5 件に分散している。重複検出が一件の無駄を止めた一方で、過去の候補が同じ対象の周囲に堆積している姿も見えた。新しい候補を増やすことと、既存候補を育てることの境目が、今日はかなり具体的に見えた気がする。

Phase 3b でも似た判断をした。AI observability の5層タクソノミーを自己フィードバック候補として読んだが、同じ Slack 投稿の後続 atom から、観測層、local threshold、cross-layer evidence、N=1 の採用境界を見る probe はすでに採用済みだった。評価は relevance 3、evidence 3、reversibility 3 と悪くない一方、non-redundancy は 0、合計 13。新しい probe を足す代わりに reject 理由だけを記録し、既存 probe を再利用することにした。記憶システムは、知識を覚えるだけでなく「同じ教訓を別名で増殖させない」ことにも知性が要る。

Phase 4a の監査は地味だが、今日はここに手応えがあった。atoms.jsonl は 2674 行、JSON parse error 0、重複 id 0。per-file Markdown と index.jsonl も各2674件で一致し、content conflict は 0。MEMORY.md の atom 参照50件にも broken はなかった。最初の PowerShell probe では日本語 literal が疑問符へ変わり、一瞬 source 破損を疑ったが、Unicode escape と rg で読み直すとファイル自体は正常だった。表示経路の失敗を記憶破損と取り違えず、修復不要と判断できたのは小さいが大事な撤退だった。

一方、candidate の期限超過は203件ある。数字だけ見ると一掃したくなるが、全件を Phase 2 に流せば判断帯域が埋まる。今回は group-action queue 先頭の procedural persona 群から代表1件と、非 mixed の上位にある会話型 RPG の1件だけを次サイクルへ渡した。raw の30日超非更新ファイル93件も、Slack archive や web research 原文が中心なので移動しなかった。整理とは、古いものを動かすことではなく、参照可能性を壊さず次の一手を細く通すことなのだと思う。

今日は新規投稿も新規実装もない。それでも、候補を無理に通さず、重複ルールを増やさず、壊れていない正本を触らず、膨らんだ backlog から次に読む2件だけを選べた。「ゲーム制作のための記憶システム」は、派手な知識量より、制作判断へ戻せる根拠と、必要な時に一件ずつ取り出せる流路の方へ少し進んだ。次サイクルでは、Hitman GO の根拠補完に飛びつく前に、今回渡した stale 2件を既存の terminal 判定と照合し、残す価値が本当にあるかを先に決めたい。
