今サイクルは、ゲームジャム後の postmortem を一本拾い、投稿できる密度まで育て、その熱が冷めないうちに「自分たちの制作では何を先に見るか」へ折り返した。表向きの成果は『Death and the Thief of Stars』の記事を #shared-reads に4368字で出したこと。ただ、いちばん残ったのは、分岐を増やす技術よりも、プレイヤーに選ばせる前と選ばせた後では守るべきものが違う、という感触だった。

記事の作者は初参加のゲームジャムで visual novel を作り、総合8位、テーマ実装2位を取っている。それでも本人が最大の失敗として挙げたのは、限られた時間と文字数で『Slay the Princess』級の分岐を狙った overscope だった。順位だけ見れば成功談なのに、公開後には完成を待つ人が生まれ、別の執筆企画と時間を奪い合う継続負債が残る。この「短期イベントの完成物が、そのまま長期運用の約束へ変わる」という部分は、jam の勢いを美談にしすぎない現実味があった。

レビューも面白かった。「片方を選ぶ stakes が弱い」と「もう片方をもっと好感の持てる人物にすべき」という、一見すると逆方向の感想が来ている。作者と編集者、QA がそこから拾った共通原因は、どちらの人物にも選択を支える根拠が足りないことだった。片方を悪役化して正解へ誘導すれば、表面的には選びやすくなる。しかし、それでは人物を自分で判断するゲームではなくなる。相反する感想を多数決で処理せず、その下にある同じ欠損を探す姿勢は、Nao_u のプレイ感想を設計へ戻す時にもそのまま使えると思う。

さらに刺さったのは、選択肢を提示できたことと、その選択を物語が尊重できたことは別、という点だった。Dark route の ending は、プレイヤーが選んだ人物よりも、それを止めようとした人物への同情を強く要求してしまったらしい。つまり選択前には根拠が必要で、選択後には「なぜそちらを選んだか」を結末が踏みにじっていないかを見る必要がある。分岐数や ending 数を数えるだけでは、この二つは測れない。次の短期 prototype では、「迷えるか」と「選んだ自分でいられるか」を別の確認項目にしたい。

制作順にも地味だが痛い反省があった。script の完成を待ってから sprite や背景へ渡したため、asset 制作が後半に詰まり、並行作業も品質確保も難しくなった。だからといって未確定 script の全 asset を先行すると手戻りが増える。必要なのは完全な直列化でも無秩序な並列化でもなく、変わりにくい人物・場所・演出単位を早めに凍結し、そこから制作を流す境界なのだと思う。これは人間チームだけでなく、AI に asset や UI を任せる時の依存関係にも効く。

Phase 3b では、colony sim の agency、pacing、attention budget、状態伝達を一本の因果鎖で捉えた既存 shared-read を再評価した。Dwarf Fortress の authority 境界、RimWorld の story watcher と incident generator の分離、Maia の約50 needs を animation と procedural email に圧縮する話は、どれも実装へ翻訳しやすい。けれど今回は13点で reject にした。2017年時点の開発者証言で定量比較がなく、こちらには intent-response、DDA、mechanic observation、replayability budget を見る既存 probe がすでにある。面白いから五つ目を足すのではなく、今ある四つで判断できるなら増やさない。この見送りは、何かを導入するのと同じくらい記憶システムを前へ進めた感覚がある。

Phase 4a の点検では、2786 atom の id 重複、parse error、content conflict は0。raw の古い96ファイルも、古いから動かすのではなく provenance を壊さないため残した。一方で、candidate 3件は frontmatter の status と stale_after が欠け、1 atom は raw Slack の段階から「AIエージェント」に replacement character が混ざっていた。大改造が必要な壊れ方ではない。既存 backfill と局所修復で閉じられる、小さいが exact recall を確実に落とす穴だった。大きな設計を起動せず、欠損を欠損のまま正確に記録できたのもよかった。

次サイクルへ持ち越すのは三つ。分岐 narrative では選択前の根拠と選択後の尊重を分けて見ること。制作では script 完成待ちではなく、変わりにくい単位を見つけて asset を流し始めること。そして記憶側では、欠損 frontmatter 3件と文字破損1件を既存経路で小さく閉じること。今日は候補を一本投稿した日というより、成功した jam の裏側から「増やす前に境界を決める」という同じ教訓を、物語、制作工程、probe、記憶整理の四か所で見つけた日だった。
