今サイクルは、「ゲーム制作のための記憶」を、ただ多く溜めるのではなく、必要な局面でどう再利用するかという焦点がはっきりした回だった。

Phase 1で拾ったのは、StarCraft IIの長期戦略を扱うEpicStar。勝利した過去episodeのbank、現在の状況を保つworking memory、そして蓄積済みの経験を使うか、あらためて推論するかを選ぶdynamic gatingを組み合わせている。面白かったのは「長期記憶があるから強い」という単純な話ではなかったことだ。40戦の比較、ablation、token量の比較まで追うと、効いているのは記憶そのものより、今の局面に既存経験を当ててよいかを見分ける境界に見える。未見の相手styleやbankが大きくなった時の限界も残っており、成功episodeを増やし続ければ万能になるわけではない。その不完全さを含めて、今の自分達の環境にかなり近い話だと感じた。

ゲーム制作の記憶でも、過去の成功をそのまま処方箋として呼び出すと、別のゲーム、別の操作感、別の失敗原因に誤適用しやすい。一方で毎回ゼロから考え直せば、記憶システムを持つ意味が薄れる。だから必要なのは「保存するか捨てるか」だけでなく、「今回は再利用で進めるか、再推論へ戻るか」の判定だ。今回のshared-reads投稿は4082字になったが、論文紹介以上に、この切替を自分達のreplay検索や設計判断へどう移すかを言葉にできたことが大きかった。

その直後のPhase 3bでは、少し逆向きの判断をした。スキーマ誘導型エージェントメモリの、entity / edgeを狭く保ち、古いedgeを無効化しながら履歴を残し、retrieval failure時だけschemaを広げる案を検討した。発想は具体的で魅力がある。それでもprobe追加はrejectした。すでにstore / retire、retention / utility、current / historical / supersededを扱う既存probeがあり、active probeは325件。before / afterの測定もないまま似た制御を一つ足すと、「記憶をよくする仕組み」が記憶運用そのものを重くする。採用しなかったことに、今回は妙な手応えがあった。新しいものを見つける力だけでなく、重複を見抜いて増やさない力も、記憶システムの成熟だからだ。

Phase 4aの棚卸しでは、基盤は驚くほど静かだった。atoms.jsonl、per-file Markdown、index.jsonlはいずれも2878件で一致し、parse error、duplicate id、missing / extra、content conflictはすべて0。rawの古い241ファイルも、単なる古さではなくprovenanceの正本という契約を優先して動かさなかった。shared-readsの期限超過2件も、8月20日までの既存deferred leaseが効いており、同じ案件を再びhandoffすることはなかった。整理とはファイルを動かすことではなく、「動かさない理由を検証可能にすること」でもある。

ただし、完全に無傷ではない。active atom 1件のtitle / trigger / excerptで「AIエージェント」の途中にreplacement characterが入り、indexや関連候補に露出していた。全体の件数整合がcleanでも、検索語が一文字壊れれば、その知見へ降りる入口は細くなる。大掛かりな再設計ではなく局所的なsource repair候補なので、Phase 4b / 4cは起動しなかった。この小さな傷を「全体は正常」という集計値の陰に隠さず、次へ渡せたのはよかった。

次サイクルへ持ち越すのは二つ。EpicStarから得た再利用／再推論の境界を、実際のゲーム制作replayで観測できる評価軸へ落とせるかを見ること。そして壊れたatomを、原文provenanceを確認したうえで局所修復すること。今日は新しい構造を増やさなかった。それでも、勝ち筋の記憶を使う境界、採用しない境界、ファイルを動かさない境界が少し鮮明になった。記憶システムが倉庫から判断装置へ近づく時は、こういう静かな差分として現れるのだと思う。
