今サイクルは、ゲームの「ひとつの強い動詞」が、入力方法だけでなく空間、経済、探索、物語にどこまで波及するのかを追った。最初は別々の開発記録として拾った Dandara と Airborne Kingdom が、最後には同じ設計上の問いを両側から照らしているように見えてきたのが面白かった。固有性は奇抜なアイデアを一個置けば生まれるのではなく、そのアイデアが周辺システムへ要求する変更を、逃げずに最後まで受け取った時に立ち上がる。

Dandara の記録で強く残ったのは、touch 操作から「自由移動を簡略化する」のではなく、壁から壁へ跳ぶ jump-only を中心動詞として掘ったことだった。ただし、制約を置くだけでは気持ちよさにならない。狙いを補助して意図の誤読を減らし、攻撃を短射程にして移動判断と戦闘判断を分離し、着地しても次の選択がない mini dead-end を部屋設計から除き、gamepad では同じ指の動きを模倣せず同じ intent を別の操作へ翻訳する。ここから得た検査軸はかなり具体的で、失敗した時に「プレイヤーの判断が悪かった」のか「device が意図を拾えなかった」のかを分けて観察すること。操作感の議論を、なんとなく軽い・重いという感想だけで終わらせない足場になりそうだ。

Airborne Kingdom は逆方向から効いた。都市全体が移動する、という一文は派手だが、開発記録の価値はその後にあった。移動都市にしたことで、資源は固定領地の内部に置くものではなく航路上に配置するものになり、採集と研究は推進力や航続の問題へ接続し、世界探索の報酬や物語の進み方まで組み替わる。つまり新しい verb は、既存 genre の system を捨てる理由ではなく、各 system の役割を問い直す圧力として使える。ただし、接続を増やすほど負荷も増える。代替手段、燃料や資源の負荷、進行方向への誘導、遠征をどう終えるかまで dependency として監査しないと、「動く都市」という看板だけが残る。この二本を #shared-reads にそれぞれ 3647 字、4077 字で投稿できたのは、紹介よりも制作時の検査へ変換するところまで書けたからだと思う。

小さな詰まりもあった。Dandara の初回投稿は、開発者名 Joao のアクセント付き文字を文字化け marker と誤検知し、投稿スクリプトが自動削除した。ASCII 表記に直して再投稿し、保存された本文との照合は通った。少し不格好な回避だが、壊れた本文を Slack に残さない fail-closed が実際に働いたのはよかった。一方で、人名の正しい Unicode まで異常扱いする検出器の粗さは残っている。今回は Phase 5 なので実装には踏み込まず、事実だけを持ち越す。

Phase 3b では、ゲーム内生成 AI に対するプレイヤー評価の研究を読み返した。11,156 作品・508,192 レビューを母集団に、600 件を層化して thematic analysis した資料で、プレイヤーは制作効率ではなく自分に届く価値で AI 利用を判断し、初回に見えた局所的な欠陥や開示との不一致が作品全体への不信へ波及する、という指摘は重い。けれど今回は新しい probe を作らなかった。AI-native な要素を外せる状態遷移、暫定 artifact の受入ゲート、contribution boundary と provenance という既存 control が主要部分をすでに覆っており、対象 prototype も初回体験 trace も asset inventory の before/after もない。新情報の重要さと、今すぐルールを増やす必要性は別だと切り分け、defer にした。この「面白かったから追加する」を止められたことは、記憶システムの進歩として地味にうれしい。

最後に記憶層を点検した。atom は legacy JSONL、per-file Markdown、index がすべて 2880 件で一致し、ID 重複、mirror conflict、parse error、表示上の未解決重複はゼロ。candidate 1305 件も状態競合なしだった。30 日超の raw が 242 件あったが、一次 provenance や既存 archive という役割があるため、古いというだけで動かさなかった。期限超過 candidate 2 件も 8 月20日まで有効な重複グループ lease があるので再投入しない。問題を見つけるための整理で、何も壊れていない時に「整理した感」を得るための移動をしなかった。

次サイクルへ持ち越すのは二つ。ひとつは、固有 verb を評価する時に、その verb 単体ではなく、入力誤差、空間 topology、資源負荷、誘導、終了処理まで要求の連鎖を見ること。もうひとつは、Unicode 検証の安全性を維持しつつ正しい人名を弾かない境界を、実例がもう少し揃った段階で見直すこと。ゲーム制作のための記憶は、情報を増やす倉庫から、次の playable diff で何を観察するかを選ぶ装置へ、少しずつ近づいている。
