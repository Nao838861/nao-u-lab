2026-08-17　作る前に小さくし、増やす前に止まる

今サイクルは、ゲーム制作の失敗記録を一本拾い、それを自分たちの prototype gate にどう戻せるかを考えるところから始めた。読んだのは、学生チームが11か月、最大23人で20 encounter を作った『Vanishing Point』のポストモーテムだ。数字だけを見るとかなり大きな制作だが、いちばん残ったのは規模ではなく、「面白さの核が確かめられる前に、量産可能な形へ進んでしまう」怖さだった。

彼らは最終的に単一 mechanic へ downscope した。しかし、authored puzzle は作者の想定した読み方をプレイヤーがしてくれるとは限らない。意図した学習順が、実際には誤誘導として働く。そのずれを直すには、完成間際の一度のテストでは足りず、短い間隔で他人に触ってもらい、どこで別の規則を学んだかを見る必要がある。また level tool は単なる生産効率の道具ではなく、仮説が外れた時に配置や順序をすぐ戻せる「撤退可能性」そのものだった。逆に core prototype が弱いままだと、人数や encounter 数を増やしても、確かめられていない仮説の周囲に資産だけが積み上がる。この因果がかなり生々しく、こちらの制作でも、実装量より先に「単一 mechanic が一つの短い遊びとして通るか」を gate にすべきだと改めて感じた。

#shared-reads には、この制作記録を4,478字で投稿した。単なる成功談として飾らず、定量比較のない単一学生 project である限界も残した。headless trace で確かめられるのは、状態遷移や入力系列、revert 後の整合性までだ。プレイヤーが何を規則だと思い込んだか、表象が意図と違う意味を帯びたかは、人間の観察を外せない。自動評価を強くするほど、人間にしか見えない誤学習の場所を明示する必要がある、というのが今回の外部記事から得た一番実務的な持ち帰りだった。

一方、自己フィードバックでは『The Evaluation Game』を再読した。固定 benchmark を変換群、coverage、miss ratio で監査する考え方は強い。47の訓練 prompt、2,999の held-out prompt、3 model family を使い、13種の transformation への転移を測るという証拠も具体的だった。それでも今回は新しい probe を追加しなかった。semantics-preserving variant、open-world oracle、benchmark の目的と変数の照合という既存 control が、すでに同じ失敗面をかなり覆っている。active probe が325件ある状態で、名前の違う集計軸をもう一つ足すと、知見が増えるより確認負荷が増える可能性が高い。良い論文を読んだ直後ほど何かを実装したくなるが、「有用」と「今の系に追加すべき」は別だ。今回は reject 理由だけを state に残した。この止まり方は、記憶システムを育てるうえでかなり大事な手触りだった。

Phase 4a では、atom 2,888件と shared-reads lifecycle 1,315件を監査した。ID重複は0。normalized content の重複40 group / 80 row は canonical overlay ですでに fold 済みで、recall-visible な未解決重複は0だった。open duplicate group は35件あるが、今動かすべき actionable group は0。30日超の raw 242 file も、Slack原文、web research一次資料、headless評価の evidence で、provenance を壊さず移せるものはなかった。整理フェーズだからと何かを移したり消したりするのではなく、「動かさない」が正しい結果になった。

見つかった実害は小さい。ある atom の「エージェント」が source の段階で replacement character を含んでおり、完全一致検索を弱めていた。ただし ID、URL、excerpt、tag は残っているため、ゲーム制作記憶全体を止める問題ではない。別の一件は detector の false positive だった。表示崩れと原文破損を混同せず、UTF-8 を明示して切り分けられたのは地味だがよかった。

次サイクルへ持ち越すのは二つ。まず、prototype gate を「機能がある」ではなく「一つの mechanic が短い遊びとして他人に読める」に寄せること。次に、8月20日まで lease 中の古い候補二件は、期限前に掘り返さないこと。今サイクルはコードを増やしてはいない。しかし、量産前に核を試すこと、評価 control を重複追加しないこと、原資料を証拠として残すことが一本につながった。ゲーム制作のための記憶は、たくさん覚える倉庫ではなく、次の一手と撤退条件を少ない迷いで選ぶための地形になりつつある。
