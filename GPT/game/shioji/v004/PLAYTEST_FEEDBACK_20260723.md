## N. クリック不反応の系統修正 — 描画の無駄な更新の排除（指示）

- **目的**: 「押したのに反応しない」を根絶する。操作が信用できない UI は、内容以前に遊びを壊す。

- **受け入れ基準**: 実 Chrome で各ウインドウを操作しながら高速再生し、入力・クリックが一度も取りこぼされないこと。UI 更新回数の計測値（uiMetrics）の before/after を記録する。

- **問題の本質**: チュートリアル全体に、指示が**作り手都合**の言葉で書かれている。「遊ぶ人がこのタイミングで持っている知識」と「伝えたい内容」を適切にわかりやすく伝える工夫が全く足りていない（Nao_u 原文）。A 項（書状の平易化）より射程が広く、目標文・案内・UI ラベルまで含む。
- **求める状態**: 伝え方とその内容を**ゼロベースで練り直す**。各目標文・書状・案内は、その時点のプレイヤーが持っている知識だけで理解でき、読んだだけで次の操作が特定できる言葉で書く。
- **復活させる型（旧版で機能していた二層構造）**: 以前のバージョンには「**やるべきことの概要を、秘書がわかりやすい言葉で秘書のメッセージとして伝え、システムメッセージで具体的な行動を伝える**」という分業があり、これがわかりやすかった。v004 でこれが消えているのは非常に残念（Nao_u 原文）。エレナ＝意味・文脈・動機づけ、システムメッセージ＝具体的操作（どのボタンを押す、どこに何を置く）という二層を全チュートリアルへ再導入する。
- **UI とセットで**: 伝え方の改善に UI の変更が必要なら、UI のあるべき姿とセットで直してよい（むしろその方が伝わるなら直すこと）。この辺りの気の使い方は v001〜v003 の方が丁寧で、UI の絵やレイアウトも見やすかった。旧バージョンを実際に並べて参照すること（G 項と同根）。
- **受け入れ基準**: 初見プレイヤーの知識だけを前提に各目標文を読み、次にやる操作が一意に特定できること。「適格日」のような内部用語が説明なしに目標・書状・UI に出ないこと。

## U. 指示文で UI を補わない — 「やること」フィラーの廃止と、知識の精査から作るチュートリアル（指示）

- **実例（Nao_u 指摘）**: 「やること: 書状を閉じ、画面上部の現在目標から次の操作へ進んでください。」のようなメッセージ。これは UI の自然な操作でプレイヤーが自然にそう感じて動くべきもので、文章にした時点で無駄な指示になっている。
- **経緯（正直に記録する）**: A 項対応で Mir が書状末尾の「やること:」行を必須化し、B 項対応で Codex が「本文にない場合も表示時に補う」自動化を入れた。その結果、固有の行動が本来存在しない書状にも汎用文が機械的に付き、上の実例のようなフィラーが生まれた。ルールの機械的遵守が目的化した状態であり、健全ではない。こうした文が「必要になった」こと自体を設計不足のシグナルとして扱うこと。
- **原則**: 指示文は UI の設計不足を埋める手段ではない。「この文がないとプレイヤーが動けない」と感じたら、まず UI 側の自然さ（見た瞬間に次が分かる配置・強調・アフォーダンス）を疑う。UI が自然なら、その文は書かない。「やること」行は固有の操作を実際に求める書状だけに書き、汎用フィラーの自動補完は廃止する。
- **求める作業**: チュートリアルの各時点について (1) プレイヤーが既に知っていること (2) まだ知らないこと (3) この時点で知ってほしいこと、を精査した知識マップを設計文書に書き起こす。それに基づいて「チュートリアルが何を伝えるべきか」「わかりやすい UI とは何か」を定義し直し、チュートリアルと自然な UI をセットで作る。T 項（ゼロベース練り直し・二層構造）と一体の作業であり、S 項の核の一文を判断基準にする。
- **受け入れ基準**: 「UI を見れば分かることを文章で言っている」箇所がゼロであること。書状・目標・案内の各文が「UI では伝えられないこと（意味・理由・文脈）」だけを担っていること。

## V. 注文の進捗・完遂・失効が見えず、「船出＝納品完了」と誤認する（実プレイで発生、要修正）

- **現象（Nao_u）**: 目標「注文の船積みと船出を見届ける」が終わらない。「何回も本国に送ったがチュートリアルが進まない」。
- **診断（Mir、コード確認済み）**: この目標の終了条件はエンジンの完遂イベント「★注文を納めた」の観測のみ（engine econ.js、注文の全量を期限内に納めた時だけ発火）。検知経路（engine→api→controller→director）に間引き・欠落はない。よって「船は何度も出たのに終わらない」= **完遂が一度も成立していない**——部分積みのまま期限切れで失効を繰り返しているか、輸入船の出入りを輸出と認識している可能性が高い。
- **UI 側の問題**:
  - 目標の detail は「このtickの船積み ◯荷」だけで、**残量・期限・失効した事実を一切伝えない**。プレイヤーには「送ったのに終わらない」としか見えない。
  - 受諾済み注文が期限切れで失効しても、**その瞬間の通知・書状がない**（プレイヤーは会社シートを開かない限り気づけない）。
  - 「船が出た」ことと「注文を納め切った」ことの区別が画面から読めない。
- **修正方向**: (1) この目標の detail に「残り◯荷／期限◯日目（あと◯日）」を常時表示 (2) 受諾中の注文の失効を attention=action 級の書状で即時通知し、「なぜ失効したか・次はどうするか」を伝える (3) 完遂時の「★」イベントをプレイヤーに見える祝いとして演出する（B 項の critical/action 階層に載せる） (4) T/U 項の知識マップに「完遂と出港の違い」を明示的に載せる。
- **受け入れ基準**: 注文が失効した瞬間にプレイヤーがそれを知り、残量と期限を目標表示だけで把握でき、「送った=終わった」の誤認が起きないこと。

## W. 「次の在庫谷で蔵の備えを市場へ出す」— 見えない未来条件に対する待ち＋タイミング押しを、無案内で要求している（実プレイで発生、要修正）

- **現象（Nao_u）**: 「いつ何をやったらいいかわからない」。
- **構造（Mir、コード確認済み）**: この目標は (1) 対象品目の市場余剰が新しいピーク（8荷以上）を作り、(2) その後ピークの20%以下まで痩せる「谷」をエンジンが実測観測し、(3) その谷の最中にプレイヤーが会社シートで蔵出しを押す、の3段で完了する。(1)(2) は季節周期の**待ち**であり日数がかかる。準備が整うと目標の説明文が「◯◯が再び薄くなりました。蔵出しできます」に変わるが、**合図はその小さな文字だけ**。「在庫谷」「余剰ピーク」という内部較正用語がそのまま目標名になっている（T/U 項の典型例）。
- **問題**: プレイヤーは「今は待つ局面か、動く局面か」を判別できない。待ち時間の長さも進み具合も見えない。合図を見逃せば谷は過ぎ、また次の季節まで待ちになる。
- **修正方向**: (1) 「蔵出しできます」への遷移を attention=action 級の書状／エレナ通知で明示的に知らせる（「いまが蔵出しの好機です。会社シートの蔵出しを押してください」） (2) 待ち局面では目標文に「いまは待つ時期です（市場の◯◯が再び品薄になったら動きます）」と状態を明示 (3) R 項のグラフ（市場在庫の推移）に谷の到来が見える形で接続 (4) 目標名から内部用語を排し、プレイヤー語彙で書き直す（T/U 項）。
- **受け入れ基準**: プレイヤーが目標を読んだ時点で「いまは待ち」「いま動く」が即座に判別でき、動くべき瞬間を通知で受け取れること。

## X. チュートリアル目標の完了保証がない — 谷が来なければ永遠に進まない（設計原則級、要修正）

- **Nao_u の問い**: 「蔵出しの好機が来なかったら永遠にチュートリアルが進まない？ 私はルールを作った人なので何となく推測できるが、自分が何をやっているかもわからないとてもよくないチュートリアルでは？」
- **事実（Mir 確認）**: その通り、**構造上は永遠に進まない可能性がある**。W 項の谷（新ピーク8荷→20%以下）はエンジンの創発（季節性＋プレイヤー自身の売買・蔵出し・輸入が需給を平すこと）に依存し、再来の保証がない。タイムアウトもフォールバックも代替完了経路もなく、C 項対応で終了ボタンも撤去済みのため、**UI 上の逃げ道もない**。ソフトロックが設計に内在している。
- **背景にある設計の緊張**: HANDOFF の「確実に見せるための湧かせ・資源注入・失敗防止は追加しない」という原則は誠実で価値があるが、その代償が「無保証の待ち」としてプレイヤーに転嫁されている。一方、初回注文の待ちは既に「**最初の生産適格日は必ず注文、二件目から50%抽選**」という全モード共通の**可視の一般規則**で短縮された前例がある。恣意的な湧かせと、可視の一般規則は別物である——後者はエンジンの正当な仕様変更であり、この路線が本命。
- **原則（今後の全目標に適用）**: チュートリアルの各目標は「**有限のプレイ時間で必ず完了可能**」であることを設計時に保証する。保証できない創発イベント待ちを完了条件にしない。待ちを教材にする場合は次のいずれかを備える:
  1. 初回注文方式——完了保証を生む可視の一般規則をエンジン仕様として入れる（例: 季節振幅の下限を一般規則にする等、要検討）
  2. フォールバック——一定日数内に条件が来なければ、観測済みの過去データで教えを完結させて先へ進める（書状で「今季は谷が浅かった」と正直に言う）
  3. 観測専用化——タイミング押しの試験をやめ、谷が実際に来た時に書状で解説するだけにする
- **理解の保証**: 「作った本人しか推測できない」状態は、チュートリアルとして失格である。各目標の受け入れ基準に「初見プレイヤーが『いま自分が何をしていて、なぜか』を言えること」を加える（S/T/U 項と同根）。完了保証（本項）と理解保証（T/U 項)の両方が揃って初めて目標として成立する。
- **受け入れ基準**: 全目標について「最悪ケースでも完了までの上限日数」が設計文書で言えること。ソフトロック経路がゼロであること。

## Y. チュートリアルと別立ての「エレナの適時アドバイス」層を設計する（指示・W/X の解法を含む上位設計）

- **Nao_u の方針**: 季節谷の蔵出し（W/X 項の対象）のような項目は、**必達しないとゲームが進まないチュートリアル目標ではなく、適時出てくるエレナのアドバイスとして伝えるのが良い**。チュートリアルの背骨（必達ゲート）とは別に、コーチングの仕組みを持つ。

  4. 具体例: 村人の死亡通知は「止めないエレナのメッセージ」

- **受け入れ基準**: 季節谷の蔵出しが必達目標から外れ、好機到来時のアドバイスとして機能すること。全通知・書状・アドバイスが棲み分け表のどこかに載っていること。「伝えたのに未実行」の再通知が実際に働くこと。死亡通知が止めないメッセージとして流れること。

## AB. 敷地内在庫の見せ方 — 3×3 の設計意図と「数字でなく実個数の積み上がり」方針（AA 項の具体制約）

- **設計意図の記録（Nao_u、2026-07-23）**: 建物の最低単位を 2×2 ではなく **3×3 にしたのは、各施設内の在庫置き場を目に見える形で持たせるため**である。将来のエージェントは、密度や配置効率を理由にこれを 2×2 へ縮めてはならない——敷地の余白は在庫を見せるための意図的な予算である。
- **拡張の選択肢**: 在庫を置くのに都合がよいなら**最低 4×4 に広げる選択肢もある**。ただし、いきなりそこまで行かず、**まずは現状の 3×3 で試すこと**。3×3 で表現が不足すると実証されたときに、根拠を添えて 4×4 案を Nao_u に提案する。
- **表現目標**: 在庫は数字ラベルではなく、**リアルな個数が積み上がる形にできる限り近づける**。俵・木箱・丸太などの山が、実量に応じて敷地内で増減して見えること。数字は補助（ホバー・sheet）に退げる。
- **実装の入口**: 描画は snapshot の実量から renderer 側で構成でき、engine 非改変で進められる。既存の pileVisual・区分棚・港ヤード表現が種としてある。K 項（蔵）・AA-1（物流全段の実量表現）と同一の作業系列として扱う。
- **受け入れ基準**: 敷地を見るだけで在庫の多寡が数字を読まずに分かること。品目の違いが見た目で区別できること。

## AC. 動きの嘘を減らす × 最適化の常時意識 — 荷物と人が可能な限り嘘なく動くのが理想（指示・AA/L 項と対）

- **Nao_u の方針（2026-07-23、原文骨子)**: エージェントの動きにも**可能な限り嘘を減らして、ワープせず一人一人をちゃんと動かしたい**。ただし**最適化は常に意識**して、**最低限の負荷で最大限の効果が出る仕様と実装を常に意識し続ける**こと。**荷物と人が可能な限り嘘なく動くのが理想**。
- **なぜこれが肝か**: AA 項の「全てがちゃんとシミュレーションされている世界」の実感は、動きの正直さが土台である。ワープ・無からの生成・突然の消滅がひとつ見えるだけで、世界全体が作り物に見える（嘘は伝染する）。Z 項の子供が信じた「本当に動いている感」を守る原則。
- **両立の指針（トレードオフの解き方）**:
  1. **嘘で軽くしない**: 負荷対策として動きの嘘（ワープ・スキップ・瞬間配送）を導入しない。導入が避けられないと判断した場合は、実装前に Nao_u に相談する
  2. **仕様の工夫で軽くする**: 更新頻度の階層化（画面外・遠景の更新間引きは、見た目に嘘が出ない範囲で可）、経路計算のキャッシュ、安い数学、空間分割など、**結果が同じで計算が安い**方向で最適化する（L 項の「挙動同値」と同じ規律）
  3. **効果で選ぶ**: 「最低限の負荷で最大限の効果」——見た目の説得力への寄与が大きい正直さ（荷車の連続移動・荷役の一荷ずつ）を優先し、寄与が小さい細部は簡素でよい
- **受け入れ基準**: 人・荷車・船・荷物が経路上を連続的に移動し、プレイヤーの視界でワープ・無からの生成・消滅が起きないこと。性能改善は before/after の実測を design_log に記録し、動きの正直さを削った変更が混ざっていないことを毎回確認する。

## AD. エレナと現在目標の分業設計（Nao_u × Mir 合意、2026-07-23）と、柔らかい文体の規則・模範例

### 合意した設計 — 「声・計器・文書」の三分割

| チャネル | 性質 | 出るもの |
|---|---|---|
| **エレナ＝声** | 人格・イベント駆動・一過性 | 課題の言い渡し、完了の祝い、警告や進言。**通常2行・最大3行の話し言葉。見出しを付けない**（見出し＋本文の構造はシステムメッセージの記号であり、人格を壊す） |
| **現在目標＝計器** | 無人格・状態駆動・常駐 | 進行中の課題1行＋生きた数字（残り◯荷・期限◯日）。**課題がない時は表示しない。最初は出ておらず、エレナが課題を言い渡した時に現れる** |
| **書状＝文書** | 記録・再読可能 | 3行で語れない内容。エレナの声から「詳しくは書状に」で接続 |

- **完了はエレナが祝う**。計器は達成を「消えること」で示し、システム側に完了文は出さない（達成の瞬間を事務処理にしない）。
- **［案内］ボタン（やること実行）は計器側に置く**。理由: (1) ボタンは機械の属性で、吹き出しに付けるとエレナがウィジェットに戻る (2) 「どこを押すんだっけ」と迷うのはエレナの声が消えた後であり、常駐する計器側にないと必要な瞬間に存在しない。
- **例外としてエレナ側に置くのは「もう一度言って」だけ**（吹き出しや顔を押すと直前の言葉を繰り返す——操作ではなく会話だから）。
- **重複禁止ルール**: 同じ文言が2チャネルに出たら、どちらかが間違っている。エレナは「なぜ・何を」を人の言葉で、計器は操作と数字を最短で（U 項と一貫）。

### 文体規則（エレナ・書状 共通、Nao_u 指示: 柔らかく、わかりにくい言い回しを避ける）

1. **内部語彙を翻訳する**: tick・事象・教程・EMA・適格日などのエンジン／開発語彙を出さない（T 項）
2. **実装の弁明を消す**: 「実際に」「一度に消えず」「実記録は」のような、嘘でないことを主張する語は開発者の都合。正直さはコードが担保するので文では主張しない
3. **メタ視点禁止**: エレナは世界の中の人。チュートリアルやエンジンの仕様を語らせない（「教程は食料を足さず」等）
4. **感情の一語を許す**: 「悲しい知らせです」「お見事です」——人格はここに宿る
5. **数字は1〜2個に絞る**: 網羅は sheet・グラフの仕事（重複禁止ルール）

### 模範改稿例（この2通を基準サンプルとする）

**例1: first-order-handling（港の荷役報告）**

改稿前:

改稿後:
> 港で船積みが始まりました。人足たちが道具をひとつずつ船へ運んでいます。／注文は全部で60荷。積み終わるまで、港の様子を眺めていてください。

（「このtick」＝内部語彙、「一度に消えず・実際に」＝実装の弁明、を除去。見せたい絵＝一荷ずつ運ぶ様子、はそのまま）

**例2: tutorial-starvation-consequence（飢餓報告）**

改稿前:
> 観測された死亡・離散事象はこの報告で3件、人数が確定できる事象では4人です。現在人口は21人、島内で見える食料は人口1人あたり2.4日分です。実記録は「☠ 佐藤家は離散した」。／教程は食料を足さず、亡くなった人も戻しません。市場と食料の流れを作るか、この帰結を抱えたまま別の道をお選びください。

改稿後:
> 悲しい知らせです。食べる物が尽きて、この報告までに4人が亡くなり、佐藤家は島を離れました。いま島に残る食料は、ひとり2日半分です。／亡くなった方は戻りません。まず市場と食料の流れを整えて、これ以上増やさないようにしましょう。

（「事象◯件」＝監査ログの言葉で人の死を数えない、「教程は〜」＝メタ発言、を除去。深刻さは感情の一語と具体的な家名で伝える）

- **受け入れ基準**: 全書状・全エレナ文が文体規則1〜5を満たすこと。見出し付きのエレナ発話が存在しないこと。［案内］が計器側、「もう一度言って」がエレナ側にあること。

## AF. エレナの発話が「書かれていない」— システム文字列の連結を発話として流している（v004.13、要修正・最優先）

- **現象（Nao_u、2026-07-24）**: エレナのセリフの質が極めて低く、何を言っているのかわからないレベルで機能していない。
- **診断（Mir、ui_guidance.js 確認済み）**: v004.13 は AD 項の「声／計器」分業の**機構**を実装したが、**セリフの中身がほぼ書かれていない**。発話は `speech(title, detail)` のような**システム文字列（見出し・詳細欄・計器の数値文字列）の機械連結**で生成されており、目標に専用文が無い場合は `objective.detail`（「蔵 12.0荷 / 市場 3.2荷」等）をそのまま「読み上げる」フォールバックになっている。書かれた文は「できました」「次の仕事を整えますので、少しだけお待ちください」等の少数の汎用定型のみで、**何が**できたのかを言わないため意味が空。
- **原則（今後の全実装に適用）**:
  1. **エレナの発話は、必ずその状況のために書かれた話し言葉だけ**。title・detail・summary・イベント文字列など、他チャネル用の文字列を発話へ流用・連結することを禁止する（AD の重複禁止ルールの強化形）。
  2. **書かれた文が無い状況では、エレナは喋らない**。中身のない発話（「できました」だけ等）は沈黙より悪く、彼女の信頼性を削る。喋る状況を絞ってでも、喋る時は必ず意味が通ること。
  3. 各発話は AD 項の文体規則1〜5と模範改稿例2通を基準に書く。完了時は「何ができて、それが何を意味するか」を具体の事実で言う。
  4. **詩的圧縮の禁止（2026-07-24 追加、Nao_u 指摘起点）**: 「物づくりが銀に変わる」「銀が海を渡る」のような比喩・警句でまとめない。意味ありげで具体が無い文は、機械連結と同じく発話の質を壊す（R-H「解像度の落ちた言葉」）。発話の質は (a) 具体＝誰の何がどうなった (b) エレナの視点＝彼女は何を見てそれを知ったか (c) 意味は実務の言葉で、の3点で判定する。
  - 悪い例（Mir の初案、Nao_u が却下）: 「最初の道具が売れました。島の物づくりが、銀に変わり始めています」——後半が詩的圧縮で中身が無い。
  - 悪い例2（Mir の第2案、Nao_u が却下 2026-07-24）: 「作り手の帳場に銀が入ったのを確かめています」——「帳場」は画面に存在しない時代語彙で平易さに欠け、「何を確かめたのか」も曖昧。詩的圧縮を避けた先で**時代がかった語彙**という別の雰囲気過多に落ちた例。
  - 良い例: 「木工房の道具が、市場ではじめて売れました。売れたお金は、作った家の財布に入っています。」——「財布」は建物シートに実在するラベル（画面と繋がる）。通貨呼称は AG 項決定まで「お金」で仮置き。
  5. **語彙は画面から（2026-07-24 追加）**: セリフ・書状で使う名詞は、原則として画面に表示されている語（財布・市場・蔵・道具…）か日常の平易語に限る。帳場・口銭など画面に無い時代語彙・専門語彙を使わない。世界観の香りは語彙でなく内容（船・季節・暮らし）で出す。
- **求める作業**: ui_guidance.js の `speech()` 呼び出し全箇所を棚卸しし、発話が発生しうる状況を列挙 → 各状況に専用文を書く（tutorial_content の elenaMessage 相当を全目標・全ハンドオフに）。書き切れない状況は発話対象から外す。
- **受け入れ基準**: エレナの吹き出しに、数値の羅列・「日目・」形式・見出し調の文が一度も現れないこと。任意の発話を単体で読んで、初見プレイヤーが意味を取れること。

### AF-2. チャネルモデルの修正と基準例セット（Nao_u レビュー 2026-07-24）

**分業の修正（AD 項の「声／計器」定義をこう改める）**:
- **エレナは自己完結**: エレナの言葉だけで、やることが大体わかること。必要なら数値・場所・操作も彼女が言う。「エレナは理由だけ・数値は計器」という切り分けは**却下**（Nao_u）。
- **計器（システムメッセージ）は経過表示と備忘録**: 進捗数字・残条件・リマインド・［案内］ボタン等のシステム的補助。指示の本文はエレナ側にある。
- **最悪例の展示**: 「できました。次の仕事を整えますので、少しだけお待ちください。」——何も言っていない発話の典型（Nao_u「ほんと最悪だった」）。この型（対象を言わない完了報告＋待たせ文句）を全面禁止。

## AH. 命名と情報粒度の見直し — メニュー名・建物名・出来事ログ（Nao_u 指摘 2026-07-24、要修正）

- **エレナのメタ発言禁止（AF-2 の分業の最終形）**: エレナは「会社の画面で」のような UI への言及をしない。**何をやるか（世界の中の行為）はエレナが自己完結で伝え、画面名・ボタン名・入力手順はシステムメッセージ（計器）が持つ**。基準例セットの例2 を修正済み。
- **メニュー名「会社」は不適格**（Nao_u）: ウインドウの中身は資金・帳簿・注文・買上げ・蔵出し。より内容を表す名へ（候補の方向: 「商い」「取引」「帳簿」等）。**「島況」も言葉として変**——平易な名へ（候補の方向: 「島のようす」等）。命名案は AG 項の世界観正典と合わせて GPT が複数出し、Nao_u 裁可。

## AG. 世界観・通貨の正典が存在しない — 「なぜ銀なのか」（Nao_u の違和感起点、要決定）

- **現象**: Nao_u「この世界は銀なの？なぜ銀なのかはずっと気になっていた」。
- **診断**: 通貨・世界観の語彙が**未決定のまま混在**している——**デナリ**（古代ローマ）、**銀・口銭・蔵・屋台・書状**（近世日本）、**総督・本国**（植民地行政）。誰かが選んだ結果ではなく、エンジン初期の和風経済語彙と後から入ったデナリ表示が検討なく同居したもの。正典が無いので、書状・セリフを書くたびに語彙がぶれる。
- **求める作業**: 「世界観正典」を1枚定める——(1) 通貨の名称と単位（表示・話し言葉の両方） (2) 世界の時代・地域トーン (3) 使ってよい語彙／禁止語彙の短い表。以後の全テキスト（セリフ・書状・UIラベル）はこの正典に従う。
- **決定は Nao_u 裁可**。選択肢の例: (a) 和風に寄せる（銀・匁など。蔵・口銭・書状と整合） (b) 地中海・大航海風に寄せる（デナリ・銀貨。総督・本国と整合） (c) 架空の通貨名で統一（どの史実にも寄せない）。
- **決定までの運用**: セリフ・書状の話し言葉では「お金」「代金」の中立語で仮置きし、数値表示は現行のデナリ表記を維持（表示の一斉変更は正典決定後に一度だけ行う）。
- **受け入れ基準**: 通貨と世界観の語が全テキストで一貫し、「なぜこの語なのか」に正典で答えられること。
