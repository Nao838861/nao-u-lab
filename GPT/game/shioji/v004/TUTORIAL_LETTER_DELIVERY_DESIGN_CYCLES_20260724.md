# チュートリアル書状導線・章ゲート設計 3 サイクル

## 体験の核

プレイヤーは、エレナの短い言葉で「いま何が起き、次に何をするか」を迷わず理解し、詳しい記録が本当に必要な場面だけ書状を読む。

### サイクル1の最有力案

必須／任意の区別とは独立した `startAfter` 表を導入し、目標評価と書状発行の両方を同じ章ゲートに通す。保存データには章番号を増やさず、完了済み goal id から現在の有効範囲を決める。

### 懸念

- 古い保存では将来目標がすでに誤完了している可能性がある。完了を巻き戻すと保存破壊になるため、既完了は尊重し、新規発火だけを止める。
- 任意目標を必須化すると待ち時間を増やすため、今回は行わない。

### サイクル2の最有力案

すべての通知定義に保存形式とは独立した配信種別を与える。強制書状は重要な五件、任意書状は契約結果・章末・比較資料・原価資料に限定し、その他は一覧に残らない一言通知にする。任意書状の告知中だけ、エレナ欄に対象を直接開くボタンを出す。

### 懸念

- 書状を減らしても内部の発火済み状態は必要であるため、director 内部では通知レコードを保持し、公開 API だけを分ける。
- 任意書状のボタンが消えた後も、書状一覧と未読バッジからは開けるようにする。

### サイクル3の最有力案

director は決定的な配信状態だけを持ち、時間差・DOM・モーダル操作は main 側の一対象一タイマーで扱う。狭幅時は現在目標の可視状態を body class へ反映して会社シートを下げる。検証は章ゲートの Node テストと、実ブラウザの「予告→強制開封」「エレナから任意開封」「スマホ非重複」に限定する。

### 懸念

- タイマーはタブ停止などで遅れるが、順番は崩れない。時間の正確さではなく予告が読めることを優先する。
- 表示中に次の通知が発火しても、対象 id を固定して一件ずつ処理する。

## 採用する統合案

1. 必須性とは別に、任意目標と対応通知へ章ゲートを導入する。
2. 通知を `forced`（予告後に自動開封）、`letter`（エレナから任意開封）、`message`（一言だけ）へ分離する。
3. 書状一覧は `forced` と `letter` のみを公開し、軽い警告・回復・祝福は履歴へ残さない。
4. 任意書状は告知後にエレナの主発話を解放するが、未読書状として一覧には残す。
5. engine は変更せず、チュートリアル進行・UI・限定ブラウザ検証だけを行う。
