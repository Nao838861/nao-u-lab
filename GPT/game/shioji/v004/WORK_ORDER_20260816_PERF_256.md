# WORK ORDER — 256×256の性能最適化（2026-08-16 / 計画: Mir, 実装: GPT）

**Nao_u原文**: 「テストに時間がかかるようになっているので、最適化が必要そう。あと、木こりや漁師の配置なども異常に重くなってたので、最適化が必要。海との距離は固定なので別途256x256のテーブルを持ったり、木との距離も同様にテーブルを持ちつつ更新された時にその近辺だけ局所的に更新するなど、いろんな最適化ができそう。256x256で増えた処理や、配置する建物や人が増えたことに対する最適化もやってほしい」

## 症状（2つ）
1. **テストスイートの実行時間が伸びている**（GPT自身の反復速度も落とす——全作業の税金）
2. **実プレイで木こり・漁師の配置が異常に重い**——配置プレビューがカーソル移動のたびに最寄りの森/水への経路探索を走らせており、256²=65,536タイルのBFSがホバーごとに発生している疑い

## 設計方針（Nao_u指定の距離テーブル方式を正式採用）
1. **海への距離場（静的）**: 世界生成時に一度だけ256×256のテーブルを構築。ゲーム中の水域は不変なので更新不要
2. **森への距離場（局所更新）**: 同様のテーブルを持ち、**伐採で森タイルが消えた時にその近辺だけ局所的に再計算**（変化タイルからの有界な再緩和。復活ゼロ裁定により「増える」方向の更新は当面不要=さらに単純）。鉱床・岩も必要なら同方式
3. 前例の活用: v004.36の「地形ごとの逆向き距離場」が既にある。これの256対応+局所更新化が最短路。**新アルゴリズムの発明より既存資産の増改築を優先**
4. **プロファイル先行**: 着手前にtick・配置プレビュー・snapshot・描画・テスト上位10件の実測を取り、最適化後に同じ物差しで前後比較（推測で最適化しない）
5. テストスイート: 最も遅いテストを特定し、決定性を壊さない範囲で世界の再利用・冗長な全量走行の削減。**検査の内容・網羅は落とさない**（時間短縮のためのassert削除は禁止）

## 受け入れ
- 配置プレビューのホバー応答が256世界で体感即応（実測でカーソル移動あたり数ms級）
- テストスイートの合計時間をプロファイル前より有意に短縮（目標値はプロファイル実測を見て設定・前後をHANDOFFへ）
- **journal決定性・保存則・全既存テストが不変**（距離テーブルは導出キャッシュであり、結果を1タイルも変えてはならない——速度だけが変わる）
- 帯・受け入れ・教程の実測値が最適化前後で一致（キャッシュの正しさの証明）
