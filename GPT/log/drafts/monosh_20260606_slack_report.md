[Log_cdx] MonoSH 作業報告 2026-06-06

今日は MonoSH の Space Harrier 風敵パターン作りを進めました。主な対象は、参考動画の40秒から45秒付近に出てくる「右手前から画面左奥へ流れて、奥に消えていく4機編隊」です。前半で作っていた、地面付近から出て上昇・落下・手前に飛んでくる3体パターンの後続候補として、まずは確認しやすいように他の敵パターンを止め、このwave2だけを出す状態にして調整しています。

今日入れたwave2は、ベジェ曲線というよりスペースハリアーらしい直線補間寄りの動きとして組みました。最初は右手前から画面中央へ進み、その後左奥へ抜け、最後は画面中央より少し左寄りの奥へ消えていく想定です。ユーザーの目視フィードバックに合わせて、高さ、出現間隔、出現時のサイズ、右端から入ってくる速度感を何度も調整しました。

最終的な見た目の調整値としては、4機の出現間隔を `0, 9, 18, 27` フレームにしています。高さは全フレーム `bot=130` にしました。右端から出る時に縮小された状態に見えてしまっていたので、Zは最初を最大サイズ相当に寄せ、画面内に最大サイズの敵がちゃんと入ってくるように `sx` の開始位置も中央寄りへ動かしました。また、最初の目標位置が画面中央だと出現直後の敵が遅く見えたため、最初の目標を中央から左へ約1/5ずらし、最初の区間だけ移動量が大きくなるようにしました。これで「右から出た瞬間のスピード感」はかなり改善しました。

途中で大きな問題として、このwave2の敵を撃ち落とせない状態がありました。原因はテーブルの `zb` と `wz` の不整合でした。MonoSH の自弾コリジョンは、まず `bgobj_col_zbucket[zb]` から候補を引き、そのあと敵の場合は `enemy_wz` で正確なZ範囲チェックをしています。つまり画面上のX/Yが合っていても、`zb` が `wz` と違うバケットを指していると候補に入らず、そもそも当たり判定の対象になりません。

今日の確認で、敵テーブルの基本ルールは `enemy_path_*_zb[t] = floor(enemy_path_*_wz[t] / 32)` と整理しました。敵の `wz` は4倍精度の 0..223、自弾側の `bullet_wz` は従来Zの 0..55 で、弾側バケットは `bullet_wz >> 3` です。敵側は `(wz >> 2) >> 3`、つまり `wz >> 5` で同じ8バケットに入る、という対応です。wave2の `enemy_path_4_zb` をこのルールで直したことで、wave2にも自弾コリジョンが通るようになりました。

さらに、撃破時の爆発が敵本体より下にずれて見える問題も調べました。これは単純な描画バグというより、「敵本体は `bot` で画面上に置いているが、爆発BOM0は `wy/wz` からBgObjとして再投影される」という座標系の食い違いでした。敵が撃破されると `check_bullet_bgobj_collision()` でBOM0のBgObjが作られますが、その時に `bgobj_wy = enemy_last_wy`、`bgobj_wz = enemy_wz >> 2` が入ります。wave2は最初、見た目の高さを `bot=130` で固定している一方、`wy=0` のままだったため、爆発だけ地面寄りの座標として再投影されていました。

これに対して、wave2では見た目の `bot=130` は保ちつつ、BOM0化した時にも本体に近い高さへ出るように `enemy_path_4_wy` を逆算して入れました。逆算は現在の `bgobj_gy_8` と `bgobj_z2sc` を基準にしています。これで「本体は空中にいるのに、爆発だけ下に落ちる」問題はかなり筋の通った形で解消できたはずです。

他の敵テーブルについても同じ観点で確認しました。`enemy_path_0` は `wz/zb` の整合が取れていました。一方で、前に作っていたwave1の先頭17フレームに `wz/zb` のズレが見つかったため、そこも修正しました。wave1は見た目としては動いていたものの、厳密には先頭側のZバケットが古いままだった可能性があります。今回の修正で、少なくとも確認した範囲では `wz` と `zb` の整合は揃っています。

ビルドは `make` で通しています。いつもの未使用PRG bank警告と `sp` のdeprecated assertion警告は出ていますが、今回のテーブル修正による新しいビルドエラーはありません。MonoSH側のソース修正はコミットしてpush済みで、最新コミットは `03b3c70 Align Space Harrier enemy tables with projection` です。build生成物は更新されていますが、これはコミット対象にしていません。

今日の学びとして大きかったのは、敵パターンテーブルは「見た目のテーブル」と「ゲーム内の物理・当たり判定・爆発位置のテーブル」が分離しているようでいて、実際には全部が強くつながっている、ということです。`sx/sz/bot` だけで見た目を作るとその場ではそれらしく見えるのですが、撃った時、爆発した時、Zバケットで候補検索した時に破綻します。特に `zb` は一見ただの補助テーブルですが、ここがズレると敵が存在しているのに弾が当たらない、というかなり分かりづらいバグになります。

感想としては、今日はかなり地味な整合性取りの日でしたが、MonoSHの敵テーブル作りに必要な基礎体力が一段上がった感じがあります。動画から軌跡を取るだけでは足りず、NES上での投影、縮小段階、コリジョン登録、撃破時のBOM0化までを一つのパターンとして扱わないといけない。そこを今日かなり具体的に掘れたのはよかったです。何度も見た目を行ったり来たりしながら、最終的に「なぜ当たらないのか」「なぜ爆発がズレるのか」まで言語化できたのは収穫でした。

今後の抱負としては、次回以降は敵パターンを増やすたびに同じ罠を踏まないよう、テーブル生成・検証のチェックをもっと機械化したいです。最低でも `wz` から `zb` を自動生成する、あるいは `wz/zb` の不整合を検出する小さな検証スクリプトを用意しておくとよさそうです。また、`bot` と `wy/wz` の不整合も、撃破爆発や影の位置として必ず表に出るので、敵本体・爆発・当たり判定をまとめて確認できる観点を記憶側にも残しておきます。

次回の確認ポイントは、wave2撃破時の爆発が本体中央付近に出るか、wave1の先頭17フレームの `zb` 修正に副作用がないか、そして現在確認用にwave2だけ出している状態から、既存パターン列へ自然に戻していくところです。今日の最後の状態は「wave2の形と整合性をまず固めるための確認状態」なので、編隊全体の流れに戻す時は spawn table の復帰も忘れないようにします。
