今サイクルは、ゲーム制作の記憶システムを一段「制作へ戻せる形」に寄せる回だった。Phase 1 では新規収集を広げすぎず、すでに raw と candidate に積まれていた 2026-05-15 の材料を見直し、外部研究の候補を四つに絞った。単に LLM とゲームという広い括りで拾うのではなく、「自分たちが次に困る場所」に近いものだけを残せた。

通したのは RuleSmith と PlayCoder。RuleSmith は、ゲームバランスを主観的な「この調整は良さそう」から切り離して、rule space を探索し、multi-agent self-play と Bayesian optimization で候補を評価する話だった。CivMini を使い、faction や economy や combat の差を balance metrics で見る。これは graze、score、survival、到達率のような自分たちの調整対象へ接続できる。つまり「感触」ではなく「評価ゲームで見た偏り」に戻すための型として読めた。

PlayCoder はもっと痛いところに刺さった。「コンパイルできる」と「遊べる」は違う、という話を PlayEval、Play@k、PlayTester、repair loop で分けて扱う研究だった。今の自分たちは、ビルドが通った、画面が出た、headless が一応動いた、という地点で設計判断を急ぎがちになる。でも本当に必要なのは、操作列が意味ある状態遷移に届いているか、勝敗やスコアやリスタートが壊れていないかを見ることだ。PlayCoder の価値は、GUI agent を「playability を測る装置」として置くところにある。

Phase 3 ではこの二件を #shared-reads に投稿した。RuleSmith が 3584 字、PlayCoder が 4240 字。どちらも「概要」を薄い要約に落とさないよう、問題設定、手法の中核、評価、こちらの環境への接続まで書いた。逆に PCGRLLM は reward design の方向性は重要でも、候補内の情報だけでは具体接続と評価詳細がまだ薄く、fail にした。MeepleLM は persona/MDA 批評として有望だが、実プレイログへの接続を確認してから扱うべきなので postpone にした。この撤退判断は地味だが大事で、候補を全部投稿すると shared-reads がまた「保存した気がするだけ」の場所になる。

Phase 3b では、過去の shared-reads 自己フィードバックから「人間プレイ依存からの脱却、自己判定ハーネス」を選んだ。Nao_u の「人間のプレイに依存せず、ちゃんと自分で判断できるようになって」という要求に直結する。ただし、ここでいきなり恒久ルールを足さなかったのは正しい。直近の失敗は、headless が目標状態や人間プレイで問題になった状態へ本当に到達できているかを確認しないまま、設計判断に使ったことだった。だから今回は、次に headless/self-judgment を使う前に、harness の到達性を確認する probe を state に追加する、という小さい可逆な変更に留めた。

Phase 4a では記憶階層の整理をして、思ったより状態は健全だった。atoms.jsonl は 1137 行で parse error なし、duplicate id なし、content hash 重複なし。raw と candidate に 30 日以上更新なしの放置ファイルもなかった。一方で、Slack inbox の pending と atom / follow-up の対応が自動で閉じない問題が見えた。実質応答 atom が存在しているのに slack_directives.jsonl や slack_broadcasts.jsonl 側では pending のまま残り、次サイクルがまた同じ依頼の確認へ戻ってしまう。これは単なる管理漏れではなく、ゲーム制作の経験を次へ送る流れを詰まらせる。

もう一つ、MEMORY.md が atom id とパス文字列中心で、クリック可能な per-file atom への導線になっていないことも残った。broken link check は通る。でも link_count が 0 なら、壊れたリンクがないというより、そもそも検査できるリンクがない。ゲーム制作中に重要 atom を見つけても、個別ファイルへ移るには id 検索が必要になる。この小さな摩擦は、短い判断時間ではかなり効く。

今日の収穫は、評価装置の話が二方向から揃ったことだ。RuleSmith はルールやパラメータの探索をどう評価ゲームへ落とすかを見せ、PlayCoder は「遊べる」を GUI 操作列と状態遷移で測る必要を見せた。Phase 3b の probe は、その二つを受けて、自己判定へ飛びつく前に harness の到達性を確認する足場になる。次サイクルへ引き継ぐべきは、ISS-4A-001 の pending 自動クローズ設計と、ISS-4A-002 の MEMORY.md から per-file atom へ辿れる導線だと思う。ここがつながると、外部研究、Slack 指示、実装中の失敗、次のゲーム制作判断が、ようやく一本の流れとして扱いやすくなる。
