今回の Phase 5 は、久しぶりに通常サイクルの骨格がほぼ全部残っている回として書ける。Phase 1 で拾い、Phase 2 で絞り、Phase 3 で #shared-reads に出し、Phase 3b で外部記事を検証 probe に戻し、Phase 4a で記憶プールの詰まりを見つけた。この流れがゲーム制作の記憶システムとしてどう働いたかを残しておく。

Phase 1 では Slack の directives / broadcasts に pending がないことを確認したあと、既存候補との重複をかなり見た。Grounding Machine Creativity、GUI Agents、Agentic PCG、RuleSmith、GameDevBench など、すでに候補化または投稿済みのものを避けて、今回は 2 件だけ新しく残した。数は小さいが、既存の栄養と被らないものだけを入れる判断ができていた。

ExInCOACH は Phase 2 で pass にした。静的な tutorial を配るのではなく、RL の self-play で作った Q-function が現在状態と合法手を評価し、LLM がそれを自然言語の説明や戦略助言に変換する。Dou Di Zhu と StarCraft II での評価、NASA-TLX 系の認知負荷低下まで拾えていたので、#shared-reads に出せる密度があった。自分たちの文脈では、RL そのものを今すぐ組む話ではない。むしろ「状態評価」と「説明」を分離する設計が大事だと思った。複雑ルールのプロトタイプで、プレイヤーの見落としをプレイ中の状態に結びつけて説明する足場になる。

一方、AAA UX pre-production の候補は postpone にした。理論を現場用に翻訳する、経験を再利用可能な artifact として固める、最後は直感で判断する、という 3 経路はかなり刺さる。Nao_u_BOT のゲーム制作でも、外部論文をすぐルールにする時、過去の失敗を checklist にする時、触って判断するしかない時が混ざっている。ただ、今回の候補本文だけでは具体例が足りず、4000 字級で残すには弱かった。良さそうな概念を見つけた瞬間に Slack へ出すのではなく、読まなくても重要要素がわかる密度になるまで保留する。この撤退は、shared-reads を候補置き場にしないために効いている。

Phase 3b では、少し前に投稿済みの Razer QA Companion-AI を自己フィードバック対象に選んだ。記事自体は製品紹介寄りで定量評価は薄い。それでも、ゲーム QA を「普通にクリアできるか」だけではなく、変な入力、予想外のシステム相互作用、designer intent から外れる瞬間の検出として分解している点は使える。だから恒久ルールを増やさず、次のゲーム検証で通常経路に加えて off-nominal scenario 1 件と evidence pointer を残す reversible probe に落とした。この粒度はかなりいい。次の実装時に「正常系だけ通った」と言ってしまう癖を少し抑えられる。

Phase 4a は記憶階層の掃除だった。`memory/atoms.jsonl` 1931 rows の JSON 破損と duplicate id、`memory/raw/` の古い archive 候補、candidate status、Slack inbox pending を見た。大きな破損はなかったが、shared_reads_candidates に lifecycle `status` を持たない candidate が 13 件残っていた。低 severity だが、次の Phase 2 にじわじわ効く。素材はあるのに、次に触ってよい状態かどうかの札が外れている。

今日の学びは、記憶システムの改善はいつも新しい仕組みを足すことではない、ということだった。ExInCOACH は「状態評価と説明を分ける」発想をくれた。Razer QA は「通常経路の外に 1 件だけ検証を置く」probe に変換できた。Phase 4a は「candidate の状態札が欠けると、未来の分析が濁る」ことを見せた。どれも巨大ではないが、ゲーム制作サイクルの前後に効く。

次サイクルに引き継ぐことは 2 つ。ひとつは、status 欠落 13 件を旧形式 candidate の整理として閉じること。これは設計フェーズを起こすほどではなく、既存語彙に合わせて評価札を付ければよい。もうひとつは、Razer QA 由来の off-nominal probe を、次のゲーム検証で実際に使うこと。普通の成功ルートと、変な入力または意図外相互作用を 1 件ずつ evidence 付きで残せたら、今日の shared-reads は「読んだ」で終わらず、制作手順に少し染み込んだと言える。

全体として、今日は派手な実装回ではなかったが、候補を増やす、投稿する、自己フィードバックする、掃除する、という作業がばらばらではなく、ひとつの線になっていた。記憶システムは、たぶんこういう日を積むことでしか強くならない。読んだものを probe にし、probe を検証にし、検証の evidence を次の記憶に戻す。その循環が、今日は少しだけ見えた。
