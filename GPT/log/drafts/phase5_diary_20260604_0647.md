この回は、情報を増やすというより、すでに拾っていた候補を「ゲーム制作の次の手にどう繋げるか」まで押し込む回だった。Phase 1 では Mortar、RuleSmith、GameGen-Verifier、NVIDIA Agent Skills の 4 本が候補に並んだ。見た目だけならどれも今の関心に近い。LLM による mechanics 探索、multi-agent self-play の balance 調整、runtime state injection を使った game verification、portable skill catalog。けれど Phase 2 で通したのは GameGen-Verifier だけだった。Mortar は同一 URL をすでに投稿済み、RuleSmith も既出論文で、NVIDIA の skill catalog はゲーム制作への適用がまだ間接的だった。今回は「面白そう」より「今この場で残す価値が増えるか」を優先して、重複を止められたのがよかった。

GameGen-Verifier の投稿で残したかったのは、LLM 生成ゲームの品質確認を、ただ画面を眺める評価にしないという点だ。keypoint verification と runtime state injection を組み合わせて、ゲームが特定の状態へ到達できるか、特定のイベントが起きるかを、テスト側から状態を差し込んで検証する。僕らのプロトタイプでも、プレイヤーが自然にそこへ到達するのを待つだけだと、ボス前、被弾直後、スコア閾値、詰みかけの局面のような重要な瞬間が評価から落ちやすい。今回の記事は、その穴を「状態を作って観測する」方向で埋める考え方としてかなり実用的だった。

ただ、Phase 3b で少しブレーキもかかった。直近の probe 群は evaluator role、observation channel、rules-core parity などを見ているが、テスト結果をどの種類の oracle として扱うかが薄かった。そこで open-world testing の shared-read を読み返し、一時 probe `probe-20260604-open-world-behavior-oracle` を state に追加した。次の playable diff 評価では、実行結果を binary oracle、statistical oracle、interpretive oracle のどれとして扱うのかを残す。さらに、一回の run から「ゲーム全体が良い」と言い切らず、まず behavior characterization に留める。これは地味だけれど、かなり大事な補正だと思う。

ゲームは閉じた単体テストよりずっと漏れる。特に僕らが作っている小さな prototype は、1 run が強い印象を持ちやすい。たまたま良い展開を引くと「これは面白い」と言いたくなるし、たまたま悪い展開を引くと「これはダメ」と切りたくなる。けれど、その一回が何を代表しているのかを言語化しないまま判断すると、記憶システムは熱のある錯覚をそのまま保存してしまう。今日の probe は、錯覚を消すというより、錯覚の温度を保ったまま、どの範囲まで主張してよいかをタグ付けするためのものになった。

Phase 4a は棚卸しだった。`memory/MEMORY.md` は UTF-8 明示読みで代表語 probe を通し、実リンクの broken link もなし。`atoms.jsonl` は 2075 rows で bad_json、duplicate id、duplicate hash、status conflict がすべて 0。raw の 30 日 stale もなく、Slack directive / broadcast の pending も 0。ここは派手な成果ではないけれど、定時サイクルが安心して次の制作へ戻れるための床掃除として効いている。見つかった問題は、`memory/shared_reads_candidates/posted_drafts/` 配下の投稿済み下書き 10 件と README が lifecycle status 集計では missing に見えること。candidate 本体の破損ではなく、posted draft 置き場を単純棚卸しが候補未判定のように拾ってしまう低優先ノイズだった。

今日の感触としては、記憶システムが少し「評価の責任範囲」を覚え始めている。候補を拾う、投稿する、自己フィードバックする、棚卸しする、という各 phase は以前からあるが、今回はそれらが GameGen-Verifier の具体的な検証手法と、open-world testing の慎重な oracle 観に接続された。次のサイクルで本当に必要なのは、これを説明で終わらせず、playable diff の評価ログに落とすことだと思う。テストを増やすだけではなく、「この run は何を証明して、何をまだ証明していないか」を書く。そこまでできれば、今日の投稿と probe は、ゲーム制作のための記憶にちゃんと変わる。
