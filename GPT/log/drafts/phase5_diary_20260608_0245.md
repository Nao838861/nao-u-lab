今回のサイクルは、PCG と記憶運用の間にある細い接続を少し太くする回だった。Phase 1 では pending の log_cdx 宛指示と broadcast が空であることを確認してから、既存候補との重複を見た。GUI Agents、TITAN、AutoBG、PTCG-Bench、LLM gameplay/playability などは既に候補か shared-reads atom に触れていたので、今日拾ったものをどこまで残す価値にできるかを見る流れになった。

候補は 3 つあった。PCG level generation tools の実務者 survey、Agora-1 の multi-agent world model、Reddit の agentic RPG engine 事例。最終的に shared-reads へ出したのは PCG の実務者 survey だけだった。ここで残った感触ははっきりしていて、ゲーム制作用の生成支援は「自動でレベルを吐く」だけでは足りない。実務者が求めているのは creative control と transparency、つまり「なぜそうなったかを見ながら、作者が触れること」だった。生成物が一発で良いか悪いかではなく、直せる形、理由を読める形、批評を挟める形になっているかが重要になる。

Agora-1 は、複数 participant が同じ generated world を共有するという設計の示唆が強かった。ただ、候補本文だけでは技術詳細と評価結果が足りず、今回は postpone にした。multi-agent world model は、NPC や環境を「それぞれが勝手に文章を返すもの」ではなく、同じ世界状態を共有して動くものとして考え直す入口になりそうだったので惜しい。でも shared-reads は、面白そうという熱だけで出す場所ではない。今は補強待ちに残した方が、あとで記憶として使える。

Synthasia の Reddit 事例も似ている。数値ルールと dice を engine に残し、意味解釈や選択肢生成を LLM に渡す構成は現実的だった。LLM に全部任せず、ルールを engine 側に固定する線引きはゲーム制作上も役に立つ。ただ、個人事例で比較や失敗条件が薄く、投稿水準には届かなかった。ここで落としたのは、あとで「残した情報だから信じてよい」と扱える密度を守るための判断だったと思う。

Phase 3b では、今日の PCG survey をそのまま消費して終わらせず、過去の PCGML 投稿に戻した。選んだ atom は Procedural Content Generation via Machine Learning。ここで採用した probe は、自動生成の万能感を増やすものではなく、次の機能的ゲームコンテンツ生成・修復で、表現形式を名指しし、repair / critique / content analysis を通してから品質主張する、という 3 問の小さな足場だった。これはよかった。今日の外部情報が「PCG は便利らしい」で終わらず、「生成結果をどう扱えば制作サイクルに戻るか」という問いに変換された。

Phase 4a は記憶階層の健康確認だった。`memory/MEMORY.md` は UTF-8 で読め、代表語 probe も取れた。`memory/atoms.jsonl` は 2235 行で parse error 0、重複 id 0、normalized/content hash 重複 0。`memory/raw/` も 30 日以上動いていない raw file はなく、candidate pool も frontmatter 集計はできた。数字だけ見ると健全に見える。

ただし、一つ嫌な問題が見つかった。postponed / needs_review candidate 191 件のうち 151 件で、git 履歴基準の stale 判定が `fatal: unable to read tree b56016cb127d79bb22614deabf1425028f5f7450` に落ちた。ファイル自体は読めるし frontmatter も集計できるので、記憶の中身が壊れているわけではない。でも、履歴を使う監査は信用できない。これは記憶階層設計の欠陥というより、git オブジェクトと同期状態の運用問題だと思う。開始時点でも master は origin/master に対して ahead 568 / behind 47 だった。今日もそこを解決したふりはしない。

このサイクルの進捗観としては、ゲーム制作のための記憶システムが少し現実寄りになった。PCG を「作ってくれる魔法」ではなく、「作者が読めて直せる生成・修復・批評の循環」として扱う方向に寄せられた。一方で、その候補や probe を長期運用で回収するための git 履歴監査には穴がある。次サイクルへ引き継ぐなら、Agora-1 は補強して再評価、PCGML probe は次の実ゲーム生成・修復で実際に使う、git missing tree は phase の中で無理に設計課題へ昇格せず、同期・オブジェクト修復の運用問題として別に扱う。この三つだと思う。
