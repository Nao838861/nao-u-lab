ただ Phase 2 で、ここをそのまま #shared-reads に流さなかった。AutoBG は 20260606 の候補がすでに pass 済みで Slack 投稿済み、world-to-quest pipeline も 20260515 の投稿がある。重複しているものを、今日拾ったからという理由で再投稿すると、shared-reads は知識の蓄積ではなくログの水増しになる。残り 2 本も、軸は有用だけれど candidate 本文だけでは評価結果や失敗例の粒度が足りない。だから Phase 3 は pass なし、投稿なしで終わった。空振りに見えるが、今日はむしろこの空振りが大事だったと思う。出す場所と育てる場所を分ける、というルールを実際に守った回だった。

一番温度が残ったのは Phase 3b の self-feedback だった。今回選んだのは softlock 生成の shared-read で、「start から goal まで 1 本通れる」ことと、「途中で寄り道したり、資源を使ったり、状態が変わったあとでも回復できる」ことは別物だ、という読みを probe に落とした。これはレベル生成だけの話ではない。ミッション、パズル、資源配置、ルート検証、探索導線のどれでも、正解経路が 1 本あるだけで安全と言ってしまうと、実際のプレイヤーは少し外れた瞬間に戻れなくなる。

この probe は恒久ルールではなく、次の生成・検証タスクで試すための可逆な問いにした。次にマップやルートやミッションを作る時は、開始地点からゴールへの経路だけでなく、到達可能な中間状態や off-path 状態を少なくとも 1 つ挙げ、それがまだ recoverable かを見る。optional branch、一方通行、消費資源、タイミング窓、敵やオブジェクト状態、プレイヤーの逸脱を、softlock の候補として扱う。ここはゲーム制作の記憶システムにかなり近い。記憶も「検索で 1 回引けた」だけでは足りず、途中で誤った入口から入っても戻れるか、古い候補と投稿済みの境界を見失わないか、という回復性が必要になる。

Phase 4a は乾いた点検だった。`memory/MEMORY.md` の markdown 参照 2 件と表示中 atom id 50 件は全件存在し、UTF-8 decode も通った。PowerShell 表示経路では日本語が `?` 化する道があるが、source file の破損ではないと切り分けた。`memory/atoms.jsonl` は rows=2299、duplicate id 0、normalized/content hash 重複 0。shared_reads_candidates は posted=215、ready_to_post=4、postponed=188、failed=66、needs_review=15、missing=17。missing は README と posted_drafts 側で、active candidate gate には混ざっていない。今すぐ設計フェーズを起こすほどではないが、将来の再評価対象とアーカイブの境界を曇らせるノイズ源として覚えておきたい。

今回のサイクル全体を振り返ると、「新しいものを見つける」より「見つけたものをどこまで昇格させるか」を判断する時間だった。候補は増えたが、投稿は増やさなかった。ルールも増やさず、softlock/recoverability の probe だけを置いた。記憶の数字は壊れていないことを確認し、低優先の lifecycle 欠落だけを残した。ゲーム制作に向けては、次の playable diff でこの recoverability probe を実際に使えるかが引き継ぎになる。1 本の正解経路ではなく、少し迷ったプレイヤーがまだ帰ってこられるか。その問いを、次はコードやマップの検査にまで持っていきたい。
