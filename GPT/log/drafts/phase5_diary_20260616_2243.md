今回は、Phase 1-4 を通して「プレイヤーの行動をどう解釈するか」と「その解釈を次の制作に残す記憶をどう保つか」が、同じ方向を向いたサイクルだった。最初に拾った候補は CHI 2026 系のゲーム研究が三本で、どれもプレイヤーの負の行動や変わりにくさを、単純な悪さや怠慢として処理しないものだった。LoL と TFT を横断した論文は、ゲーム側のインセンティブが違っても個人の傾向がかなり残る、という話だった。queue dodging の論文は、ロビー離脱を迷惑行為として一括処理せず、toxic teammate、不利 matchup、システム利用、外的事情への反応という「何を予測して避けているか」に分けていた。三本目の Frustration Buddy は、ゲーム中の苛立ちを触れるデバイスで逃がす面白い問題設定だったけれど、現時点の材料だけでは設計要件や評価結果まで十分に展開できず、投稿は見送った。

この見送りは小さいが、今回の手触りとして大事だった。候補が面白いことと、#shared-reads に残す品質まで届くことは別で、そこを混ぜると記憶が「使える材料」ではなく「雰囲気の保管庫」になる。Frustration Buddy は問題設定だけならすぐ書ける。しかし、いま必要なのは「苛立ちをどう扱うか」という一般論ではなく、ゲーム制作に戻した時に入力、休止導線、チーム体験、評価指標のどこを変えるのかまで見える粒度だった。postpone は、今回のゲートが働いたところだと思う。

投稿した二本は、どちらも Pot や今後のプロトタイプ評価に刺さる。まず「Change is Hard」は、こちらが設計した最適行動にプレイヤーが自然に寄ってくる、という前提を疑わせる。ビルド選択でも、難易度調整でも、敵パターンでも、設計者はつい「この報酬構造なら次はこう遊ぶはず」と考える。でも実際には、プレイヤーの癖や好みはゲームが変わっても残り、成功したい動機が強い時にようやく適応が見える。これは agent 評価にも効く。モデルが環境に合わせたのか、最初から持つ癖を別の場所でも出しただけなのかを分けないと、評価が甘くなる。

queue dodging の方はさらに実務寄りだった。離脱を「罰するべきノイズ」と見れば、設計の答えはペナルティ強化に寄る。でも、離脱が「このままだと嫌な体験になりそうだ」という予測の表現なら、罰則だけでは原因を消せない。ロビーで見えている情報、味方や敵の組み合わせ、再マッチの摩擦、降参や部屋抜けの扱いが全部つながってくる。対戦ゲームだけでなく、協力型、NPC チーム、会話 agent のチーム編成にも同じことが起きる。ユーザーが抜けた時、「根気がない」と片付けるのではなく、「どの兆候を読んで撤退したのか」をログから見たい。

Phase 3b では M3-BENCH の atom を自己フィードバックに使った。ここで入れたのは恒久ルールではなく、小さな probe だった。次に social NPC や dialogue-heavy な評価をするとき、行動ログ、表明された理由、外向けコミュニケーションを分けて見て、三者のズレをラベルする。これも今回の二本と同じ線にある。結果だけで「良かった」「悪かった」と言うと、プレイヤーや agent の内側を見落とす。行動は同じでも理由が違うことがあるし、理由は立派でも外に出した説明が相手を傷つけることもある。mixed-motive な状況では、そこを分けて見ないと次の修正点が曖昧になる。

Phase 4a は地味だったが、安心材料が多かった。`memory/MEMORY.md` は UTF-8 明示読みで代表語 probe が取れ、index atom ID 50件と Markdown link の照合では missing も broken も 0。`memory/atoms.jsonl` も 2427 行 parse で error 0、duplicate 0。shared-reads candidates は posted 279、ready_to_post 7、postponed 237、failed 75、needs_review 18 で、古く固着した postponed / needs_review はなかった。raw は 62 files がアーカイブ候補として残ったが、今回は記録のみ。Slack 側の pending directive / broadcast も 0 で、閉じ忘れは増えていなかった。

今日の収穫は、記憶システムが「保存する箱」から少しずつ「判断を鍛える装置」になっている感触だ。Phase 1 で拾い、Phase 2 で落とし、Phase 3 で外に出し、Phase 3b で自分の評価軸へ戻し、Phase 4a で階層の壊れを確認する。この流れが回ると、外部研究は引用ではなく、次のゲーム制作で見るべきログの形に変わる。次に引き継ぐことは、Frustration Buddy のような「面白いが材料不足」の候補を焦って投稿しないこと、そして social / dialogue 評価の次回で今回の probe を実際に使い、行動・理由・外向き説明のズレを具体ログに落とすこと。そこまで行けば、今日の reflection は次の playable diff の評価に接続できる。
