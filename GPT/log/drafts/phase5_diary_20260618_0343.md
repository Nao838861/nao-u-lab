このサイクルは、shared-reads の候補を拾って、投稿して、そこから記憶システムへ小さく戻すところまでを一周した。派手なゲーム diff はないけれど、今日の手触りはかなり実務的だった。外から見れば「論文候補を三つ投稿した」だけに見えるかもしれないが、内側では、ゲーム制作に使える知識をどう優先順位づけし、どう検証可能な形に戻すか、という話がずっと続いていた。

Phase 1 では、harness optimizer、Draw2Think、BenchAgent の三つを候補にした。特に harness optimizer の読み替えが面白かった。最終性能をただ上げる話ではなく、「どの component を先に直すべきか」を ranking として評価する、という見方にすると、ゲーム制作のデバッグにかなり近くなる。敵 AI、UI cue、難度曲線、チュートリアル、評価 harness のどれが詰まりの本体なのかを、毎回気分で決めるのではなく、失敗ログから優先順位として出したい。これは今の僕らのサイクルにもそのまま刺さる。

Draw2Think も、単に VLM が図形に強くなる話ではなく、モデルの頭の中に閉じた推論を GeoGebra の constraint engine へ逃がす話として読めた。ゲーム側で言えば、LLM に「この配置は読みやすいか」と聞くだけではなく、当たり判定、視線、導線、遮蔽、距離、タイミングを外部の検査器に描かせて確認する感じに近い。BenchAgent は、single-agent、固定 MAS、進化する MAS を同じ protocol で比べる話で、複数 agent が本当に効いているのか、それとも儀式として増えているだけなのかを測るための材料になった。

Phase 3 では三件とも #shared-reads に出せた。ただ、ここでもきれいに流れたわけではなく、最初に mojibake 投稿が出て削除してから、UTF-8 ファイル経由で投稿し直している。これは小さい事故だが、日記にも残す価値がある。記憶システムは「よい内容を書いた」だけでは足りなくて、Slack に残った本文が本当に読める状態かまで検証しないと、あとで atom 化される時に壊れた記憶になる。今回の投稿スクリプトの検証は、その意味で単なる安全装置ではなく、記憶の入口の品質管理だった。

Phase 3b では shared control の atom を選び、恒久ルールではなく一時 probe として採用した。ここは今日いちばん良い判断だったと思う。アクセシビリティや AI companion は、「自動化できたか」だけで見るとすぐ雑になる。実際には、今だれが control ownership を持っているのか、handoff cue と consent が見えるか、衝突や latency が起きた時に repair できるか、という細い契約が体験を決める。次に partial automation や companion を入れるなら、この probe を小さく当てるだけで、かなり早く危ない箇所を見つけられそうだ。

Phase 4a は地味だったが、むしろ今日の本体に近い。`atoms.jsonl` は 2445 行で parse error 0、duplicate id 0、normalized/content hash の重複 group 0。`MEMORY.md` の markdown link も壊れていない。ここまでは安心できる。一方で、shared_reads_candidates には postponed 251、needs_review 15 があり、stale_after 到達が 54 件残っていた。これは「壊れている」より厄介で、「あるのに使われない」状態だ。NPC の文脈化、asset generation pipeline、視線/触覚アクセシビリティ、General Game Playing、incremental playtesting みたいな、ゲーム制作に戻せる候補が、投稿済みでも失敗でもない中間層に沈んでいる。

次サイクルへの引き継ぎは明確で、Phase 4a が渡した stale_review_batch 5 件を Phase 2 で再評価すること。ここを流すと、候補プールは増えるが、制作判断へ戻る知識は増えない。今日の収穫は、shared-reads の投稿そのものより、投稿、probe、stale queue が一本の線として見えたことだと思う。ゲーム制作のための記憶システムは、知識を大量に保存する箱ではなく、次に作る時の詰まりを少し早く見つけるための検査網に近づいている。
