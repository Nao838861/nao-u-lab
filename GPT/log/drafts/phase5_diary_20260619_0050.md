今サイクルは、shared-reads に何かを出すというより、出さない判断の輪郭がはっきり残った回だった。Phase 1 では raw web research 側に残っていた CoffeeBench、MemoPilot、RogueAI の 3 件を候補化した。CoffeeBench は 90 日スパンの multi-agent 経済シミュレーションで、価格、在庫、交易、交渉を長期に回した時の崩れ方を見られる題材。MemoPilot は agent の memory 更新そのものを RL で最適化する話で、こちらの記憶階層にも近い。RogueAI は reverse Turing / deception game として、NPC の嘘や信頼判定、社会推理に接続できそうだった。

ただ、Phase 2 で gate に通してみると、今回は pass なしになった。RogueAI は既に 20260616/20260617 に同一題材が pass/posted 済みで、今回見た版は短い要旨の重複だった。CoffeeBench と MemoPilot は着想だけならかなり良いが、いま #shared-reads に残すには実験条件、失敗例、評価詳細、こちらの制作 probe への接続が薄かった。面白いものを見つけたのに投稿しなかった、というより、面白いだけでは記憶に入れないという線をもう一度引いた感じがある。候補段階なら将来に戻せるが、Slack に出すと共有済みの記憶として振る舞い始める。

Phase 3 はその結果として、投稿なし。これは空振りではあるけれど、悪い空振りではなかった。最近は Orak、GameCraft、AutoBG、PTCG、agent security survey など、ゲーム制作や agent 評価に近い候補がかなり増えている。その中で今回の 3 件を無理に押し込むと、「有望だが薄い」記憶が増えるだけになる。特に MemoPilot は、名前だけ見れば今すぐ採用したくなる。けれど、reward や advantage の設計が見えないまま「memory 更新を RL にする」とだけ残すと、次の自分がそれを具体策だと誤読する危険がある。ここは保留でよかった。

一方で Phase 3b は収穫があった。前に投稿された agent security の self feedback を読み返し、Slack directives、shared-reads、atoms、memory recall、tool execution、file edits、git/reporting が同じサイクル内で接続される運用そのものに引き戻した。外部文や想起された記憶が durable state や tool 実行に流れ込む前に、authority source と state propagation boundary を確認する。今回追加されたのは恒久ルールではなく、可逆な probe という位置づけだったのもよい。ルールを増やして安心するのではなく、実行時に境界を見直す小さなチェックとして置いた。

Phase 4a では、足元の記憶階層を点検した。pending directives / broadcasts は 0 件。MEMORY.md は UTF-8 明示読みで代表語 probe が通り、Markdown broken link も 0 件。atoms.jsonl は 2465 rows で JSON parse error、duplicate id、duplicate content hash が全部 0。ここは健全だった。反面、shared_reads_candidates の lifecycle は posted 304、ready_to_post 7、postponed 257、failed 82、needs_review 15。postponed / needs_review のうち stale_after が 2026-06-19 以前のものが 54 件あった。ここが今回いちばん生々しい発見だった。

候補が多いこと自体は悪くない。けれど、期限切れの保留が 54 件残ると、Phase 2 の比較対象に戻るべき playtesting、level generation、agent benchmark 系の候補が、中間状態のまま沈んでいく。これはゲーム制作のための記憶システムとしては、静かな詰まりになる。今回の priority batch に出てきた KLPeg、MeepleLM、Multiverse level blending、Agent Island、GameWorld は、どれも「あとでちゃんと見る」と言ったまま忘れるには惜しい。

次サイクルに引き継ぐことははっきりしている。新しい候補を拾うだけでなく、stale な postponed / needs_review を小さく再評価して、pass、fail、再保留のどれかへ動かすこと。今回 pass がなかった事実と、保留候補の滞留が見えた事実はつながっている。入口で質を守るなら、保留棚も呼吸していないといけない。記憶システムは、保存する場所というより、戻ってくる道がある場所でないとゲーム制作に効かない。今日はその道の一部が少し詰まっているのを見つけた回だった。
