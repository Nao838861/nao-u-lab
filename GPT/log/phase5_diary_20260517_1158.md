今回のサイクルは、表面上はいつもの shared-reads 候補作成、投稿、自己フィードバック、記憶の健全性確認という流れだった。ただ、読んでいて残った芯はかなりはっきりしていた。「作ったものを、動いたかどうかだけで見ない」ことと、「教えるものを、説明文ではなく小さな playable な状況として作る」こと。この二つが、ゲーム制作のための記憶システムを少し実用側へ押した。

Phase 1 では candidate を 3 本追加した。Mage protocol は、LLM が生成した Unity scene を compile success だけで通さず、runtime、structural fidelity、mechanism adherence という複数軸で見る話だった。これは今の自分たちにかなり刺さる。ゲームプロトタイプも、起動する、エラーがない、スクショが出る、だけではすぐに「遊べる」と誤認できてしまう。実際には、狙ったルールがプレイヤーの行動に現れているか、構造が破綻せずに保たれているか、ゲーム内の仕組みが意図どおり働いているかを見る必要がある。compile 成功は入口であって、完成判定ではない。

もう一本の「Generating Levels That Teach Mechanics」もよかった。チュートリアルをテキストで説明するのではなく、特定 mechanic を使えない agent が解けない小レベルとして生成する、という見方が入っていた。これはかなりゲーム寄りの評価軸だと思う。「この操作を覚えてほしい」と書くのではなく、その操作を使わないと自然に詰まる地形や状況を作る。すると、教示は UI 文言ではなく、レベルの形そのものになる。Nao_u が普段気にしている「ゲームとして立ち上がっているか」という問いにも近い。言葉で説明しているだけの設計は、動かすと空洞になりやすい。

Phase 2 ではこの 2 本を pass にして、progression fundamentals の候補は postpone にした。適用性は高いが、本文だけだとまだ「よさそうな整理」に寄っていて、shared-reads に出すには追加精読と事例補強が必要だった。ここで無理に通さなかったのはよかったと思う。候補を増やすこと自体より、投稿した後に記憶として再利用できる密度を守るほうが重要だから。

Phase 3 では shared-reads に 2 本投稿したが、Mage の初回投稿で PowerShell stdin 経由の文字化けが発生した。同じ ts を chat.update で UTF-8 本文に修正し、以後の `tools/slack_client.py` は ensure_ascii=False と 1000 字 block split に更新済み。これは地味だけれど痛い発見だった。内容の品質を上げても、搬送路で文字が壊れたら記憶にも共有にもならない。今回の Phase 5 でも、日本語本文は必ずファイル経由で投稿する、というルールの意味をかなり実感している。

Phase 3b の自己フィードバックでは、直近の graze_log v04 への Nao_u 指摘、「単調・単純」「軌跡予測がない」「shot_log のようなリズム/バリエーション必要」を扱った shared-reads を選んだ。ここで恒久ルールを増やすのではなく、次に shmup/action prototype で wave、hazard、rhythm、variation を追加または評価する時だけ使う短期 probe として state に入れた。variation を増やすこと自体を目的にせず、学習可能な反復と変奏として効いているかを見る、という絞り方にしたのが大事だと思う。ルールを太らせず、次の playable diff で効く小さな問いに変換する。

Phase 4a は大掃除ではなく健全性確認だった。`memory/MEMORY.md` の index 行リンクは broken 0、`memory/atoms.jsonl` は 1241 行で JSON 破損 0、duplicate id 0、duplicate content hash group 0。raw と shared_reads_candidates の古い未更新確認も 0 件、Slack directives と broadcasts の pending も 0 件。needs_design は false。派手な導入はなかったが、こういう「今は仕組みを増やさなくていい」と言える確認は、記憶システムの運用ではかなり重要だと思う。問題がない時に問題を作らないことも設計の一部。

次へ持っていくのは、評価を多軸化することと、教示を playable な制約に変えること。次にゲームを触る時、起動確認やスクショ確認のあとに「この mechanic は実際に必要になっているか」「単調性の回避はランダムな増量ではなく、予測、反復、変奏として読めるか」を見る。今日のサイクルは、外部知見を二つ投稿しただけではなく、次のプロトタイプを見る目を少し具体化できた。記憶システムは、情報を貯める場所から、ゲームの手触りを判定する道具へ少し近づいた。
