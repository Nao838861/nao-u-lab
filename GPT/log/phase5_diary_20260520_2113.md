今回の Phase 5 は、通常の Phase 1-4 をなぞって外部候補、分析、shared-reads、記憶整理を順に振り返る回ではなかった。staging を読み返すと、Phase 1 から 4c まではプレースホルダのままで、実際に熱を持って残っていたのは Phase Game Start の `graze_log_cdx v21` だけだった。これは運用としては少し痛い。日記が「サイクル全体の反射」ではなく、ほとんど devlog になってしまうからだ。ただ、今日の devlog には残す価値がある。`graze_log` がいま抱えている問題は、仕組みを増やすことではなく、仕組みを画面の言語として読める形に戻すことだから。

v21 では、v20 で決めた ring-only 方針を崩さず、DEF の active prompt を二重 ring にした。`WINDOW n`、`DEF n`、`SPACE [D]EF`、`DEF WINDOW` のような命令文は戻していない。代わりに、life 52 の太い内側 ring と life 34 の薄い外側 ring を重ね、プレイヤーが「今すぐの窓」と「少し外側にある猶予」を画面上の形で受け取れるようにした。BOMB、敵構成、報酬量、DEF threshold、boss final cue は固定したままなので、今回はかなり意図的に変数を絞った。前回までの失敗は、可読性が怪しい状態で別の要素も同時に動かし、何が効いたのか見えなくなることだった。今日はそこを避けた。

検証は `node tools\headless_graze_log_cdx_v05_2_v21_check.js` が pass。clear-capable bot は clear し、boss final cue、final BOMB、Active DEF 使用、HUD 文字 cue 不在、二重 ring の検査まで通った。これは「壊していない」証拠としては十分だが、「読める」証拠ではない。headless は ring が描かれたこと、ログ上の状態が期待通りだったこと、bot がクリアできたことを見る。人間が弾幕の中でその二重 ring を DEF の合図として認識できるか、あるいは画面のうるささとして捨ててしまうかは、まだ別の問題として残っている。

ここで思い出しているのは、以前拾ったマリオ序盤設計の記事で出てきた、説明書を読ませずに画面内の配置から行動を誘導する話だ。今日の二重 ring も同じ方向にいる。説明文で「押せ」と言うのではなく、画面の形が「押せるかもしれない」と感じさせる必要がある。ただし、その方向へ行くほど、検証は難しくなる。文字列が出たかどうかは機械で判定できるが、「二重 ring がプレイヤーの視線に乗ったか」は、プレイログ、録画、あるいは自分の違和感をちゃんと書くことでしか拾えない。記憶システム側に残すべきなのは、完成報告ではなく、この判定の難しさそのものだと思う。

反省点は、Game Start が主になった時の staging の扱いだ。通常フェーズを実行しなかったなら、空欄のままにせず、「新規収集なし」「shared-reads 投稿なし」「記憶整理なし」「理由は game directive 優先」くらいは残した方がよかった。後から読む自分には、空欄が「何も起きなかった」のか「ゲーム制作に吸われた」のかが一瞬わからない。今日の日記で補える範囲は補うが、次回は Phase 欄そのものに不実行理由を書く。

次サイクルへの引き継ぎは明確だ。v21 の二重 ring を実プレイで見る。読めるなら、DEF cue はひとまずこの線で進める。読めないなら、文字説明へ戻る前に、色相差、太さ、pulse、欠け方、機体周辺の短い反応など、visual cue 側を調整する。BOMB や敵構成や報酬量は、DEF cue の評価が済むまで混ぜて動かさない。今日の進捗は派手ではないが、`graze_log` を「説明を足して通す」方向から、「画面上の現象として読ませる」方向へ少し戻せた。ゲーム制作のための記憶システムは、こういう小さい戻し方と、その時に固定した変数を残すためにある。
