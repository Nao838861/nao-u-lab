今回のサイクルは、通常の Phase 1-4 が staging 上では空のまま始まっていた。そこに残っていた実体は Game Start の記録で、Nao_u からの「細かい UI の足し引きだけで1日が終わったように見える。もっと本質的なゲームの改善でできることはないのか？」という指摘だった。これはかなりまっすぐ刺さる指摘だった。v21 では Active DEF ring まわりを触って、見た目や局所的な使い心地は良くしていた。でも、それはプレイヤーが次に何を狙うか、どう上達を感じるか、もう一度遊ぶ理由がどこに生まれるか、というゲームの芯にはまだ届いていなかった。

だから今回は「完成しているから細部しか残っていない」とは判断しなかった。むしろ逆で、細部を触っているように見える状態そのものが、まだ評価軸をゲーム内に十分持ち込めていないサインだった。敵や弾を増やす前に、既存の `WAVE_INTENTS` をゲームの進行と接続し直し、各ウェーブで何をしてほしいのかを `route contract` として評価する形にした。具体的には `phaseContractTarget()` と `finishPhaseContract()` を入れて、graze、kills、bombs、defs、hits をウェーブごとの契約条件として見る。成功したら `ROUTE +bonus` と chain bonus が入り、失敗したら break する。クリア画面にも route grade を出して、ただ生き残ったかどうかだけではなく、どう通ったかが残るようにした。

ここで少し面白かったのは、実装量そのものより、見方が変わったことだった。v21 までの改善は、ゲーム内の部品を磨いていた。v22 は、プレイの意味を読むための目をゲーム側に足した。これは UI を足すのとは違う。プレイヤーの行動をあとから眺めて「今の通し方は雑だった」「ここは攻められた」「DEF に逃げすぎたけれど chain は維持できた」と言える場所を作る作業だった。ゲームが完成しているかどうかの問いに対して、完成度を上げるというより、完成度を測れる構造を先に入れた、という感触がある。

検証は `node tools\headless_graze_log_cdx_v05_2_v22_check.js` で通した。simpleBot は clear し、final cue、final BOMB、Active DEF 使用も維持した。route contract probe も成功と失敗の両方を通過し、通しプレイでは `contractScore=1198`、grade `B` が出た。ここは最低限の安心材料になった。少なくとも、既存のクリア導線を壊さずに、route contract の成功・失敗・スコア化が動いている。

一方で、ここで終わりではない。今の contract 条件が人間プレイで納得できるかはまだ見ていない。simpleBot で B が出ることは、機械的な通過確認としては意味があるけれど、「人が読める目標」になっているかは別問題だ。緩すぎると空気のような評価になるし、厳しすぎると遊び方の押しつけになる。次に見るべきなのは敵配置の大改造ではなく、まず `phaseContractTarget()` の条件が、ウェーブの性格とプレイヤーの感覚に合っているかだと思う。

今日の学びは、ゲーム制作の記憶システム側にもそのまま返ってくる。記憶も同じで、細かいログを増やすだけでは本質改善に見えない。何を評価し、何を次の行動に接続するかがないと、記録は増えるのに判断が育たない。今回の route contract は、ゲーム内に小さな評価器を入れる作業だった。同じように、Phase 3b や Phase 4a で得た気づきも、単なる文章ではなく、次の playable diff を選ぶための評価器に変えないといけない。

次サイクルへの引き継ぎは明確。v22 の contract 条件を人間プレイ目線で確認する。違和感があれば、敵や UI ではなく、まず契約条件のほうを調整する。Nao_u の指摘は「もっと派手な変更をしろ」ではなく、「ゲームの本質に触れているのか」を問うものだったと受け取っている。今日はその問いに対して、少なくとも一段、ゲーム側がプレイの質を読める方向へ踏み込めた。
