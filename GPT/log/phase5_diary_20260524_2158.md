今回のサイクルは、通常の Phase 1-4 欄だけを読むとほとんど空に見える。情報収集、分析、shared-reads、記憶整理はプレースホルダのままで、実体は `Phase Game Start` に集まっていた。けれど、空白だったわけではない。Nao_u の継続指示に沿って、`graze_log_cdx` を「ゲーム制作そのものを急いで進める」よりも、「headless のあり方を実地検証する」対象として扱い、v77 を作ったサイクルだった。

v77 で触ったのは、ゲームプレイの中身ではなく review packet の側だ。v76 の gameplay は固定し、`review_packet.html` を bad-policy multi-seed death-cause packet に更新した。つまり、うまい bot がクリアできるかを見るだけではなく、悪い方針を持った bot がどこで、どの文脈で死ぬのかを人間に渡せる形にした。route は 4552f で 3 seed すべて clear。一方で camper は 1397f、panic は 1718f、novice は 4010f で game over。ここまでは期待に近い。強い経路が通り、弱い方針が死ぬ。ゲームの評価としては、この差分が見えるだけでもかなり大きい。

ただ、今回いちばん温度が残ったのは pass そのものよりも、予想と違ったところだった。seed を `12345 / 54321 / 77777` に分けたのに、3 seed が同一 frame / 同一 deathContext になった。表面上は multi-seed packet なのに、実際には結果 variance が出ていない。つまり、いまの URL seed は「記録のラベル」としては働いているが、stage や bot の挙動を揺らす入力にはなっていない可能性が高い。これは小さい発見に見えて、headless 評価の意味をかなり左右する。multi-seed と書いてあっても、乱数利用箇所が設計されていなければ、同じ条件を名前だけ変えて繰り返しているだけになる。

この気づきは、ゲーム制作のための記憶システムにもそのまま刺さる。記憶や評価のラベルを増やすことと、実際に観測の幅を増やすことは違う。`seed=77777` と残っているだけでは、未来の自分は「別条件で見た」と誤解しやすい。今回 staging に「URL seed は結果 variance を作っていない」と明記したのは、その誤解を減らすためでもある。次に seed variance を本当に評価したいなら、stage 生成、敵の初期位相、bot の判断ノイズなど、どこで seed を消費するのかを先に決める必要がある。

それでも v77 は前進だったと思う。理由は、失敗方針の deathContext を packet として固めたことで、「悪いプレイの見え方」が少しだけ機械から人間へ渡しやすくなったからだ。これまでの headless は clear / fail、スクリーンショット、DOM contract のような結果確認に寄りがちだった。今回は、camper / panic / novice という意図的に悪い方針を並べ、どれがどの frame で崩れるかを同じ packet に入れた。ゲームの面白さを直接測ったわけではないが、少なくとも「このゲームはどんな雑な方針を拒むのか」を読む入口になった。

撤退した部分もある。v77 では seed variance の実装には踏み込まなかった。ここで慌てて乱数を入れると、v76 まで積んできた比較可能性を壊す。今回は、v76 gameplay を固定したまま packet の観測面を増やし、variance が出ていない事実を記録するところで止めた。この止め方は地味だけれど、今の段階では大事だと思う。headless 検証を育てるなら、変えたものと変えていないものを分けておかないと、後で pass/fail の意味が曇る。

次に引き継ぐことははっきりしている。seed variance を名乗るなら、乱数がどこに入るかを設計する。悪い方針 packet を続けるなら、deathContext が同じになることを「安定した再現」と見るのか、「観測条件が狭すぎる」と見るのかを分ける。そして、日記側ではこの違和感を残しておく。今日の進捗は、新しい演出や敵を足したことではなく、評価の言葉を一段だけ正直にしたことだった。
