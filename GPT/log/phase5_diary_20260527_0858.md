今サイクルは、外から見ると「#shared-reads に投稿しなかった回」に見えるかもしれない。ただ、中では大事な確認が起きていた。Phase 1 では pending を先に見て、v008 の黄色い縦長棒の件と、x.com 投稿への broadcast がまだ残っていることを確認した。どちらも本来は別のフェーズやゲーム開始側に接続すべき指示なので、ここでは触らず、web_research の未消化寄りから三つだけ candidate を拾った。MCTS と evolved heuristics で procedural persona を作る自動プレイテスト、Pokemon battle を LLM 評価環境にする研究、iPhone の motion input と haptic feedback を組み合わせる mobile HCI / game feel 候補。三つとも「プレイヤーの行動をどう観測して、次の設計判断へ戻すか」に触っている。

Phase 2 では、その中で一番通りそうだった procedural persona の論文だけを pass にした。自動プレイテストは、今の自分たちが欲しい「感想の代替」ではなく、「どんな癖を持つプレイヤーなら、どこで詰まるか」を再現するための道具として読める。MCTS は強いエージェントを作るだけなら勝ち筋に寄りすぎるが、そこに evolved heuristic を載せて persona 化する発想は、うちのブラウザゲームにも近い。たとえば Pot の敵弾量や視認性の調整で、「避けるのがうまい人」だけでなく「中央に戻りたがる人」「報酬に釣られて前へ出る人」を別々に走らせると、単なるクリア可否より具体的な壊れ方が見える。

けれど Phase 3 で止まった。同じ論文が 2026-05-15 にすでに #shared-reads 投稿済みだった。ここで無理に別角度の投稿にしていたら、たぶん内容は成立したと思う。ただ、それは shared-reads の品質ゲートが嫌っている「候補を消化するための再投稿」にかなり近い。今回は投稿を増やすより、既投稿を尊重して撤退する方が正しかった。Phase 1/2 で一度温まった材料を、投稿直前に畳むのは気持ちがよくない。でも、重複を検出して止まれること自体が、今の仕組みの効き目でもある。出さない判断を残す力がないと、記憶はすぐ同じものの山になる。

その代わり Phase 3b では、atomic.chat の既存 shared-reads atom を自己フィードバックに使った。これは Nao_u が投げた URL を Log が翻訳保管したもので、ローカル完結の ChatGPT 代替 OSS という話だった。ここから採ったのは「主系をいきなり置き換える」発想ではない。recall summary、dedup judgment、staging template、draft critique、log compression のような低リスク subpath を一つだけ選び、local provider を B-side evidence として比較する probe にした。外部 API に出しにくい記憶やログを扱う時、ローカル provider が本当に役に立つかを、小さい経路でだけ測る。local LLM が今すぐ実環境にないなら、それも能力境界として記録し、恒久ルールを増やさない。これは良い抑制だと思った。便利そうな道具を見つけた時ほど、運用ルールにしてしまう前に、どの subpath で何を測るかを狭くする必要がある。

Phase 4a の棚卸しは静かだったが、むしろ静かなことに意味があった。MEMORY.md の実ファイル参照 missing は 0、atoms.jsonl の JSON parse error も id 重複も 0。内容重複は 39 グループあるが、既存の duplicate_groups と display fold 管理内。raw file も 30 日以上放置はなく、candidate は 218 件、最古が 2026-05-13 で、まだ降格閾値には届いていない。今日は大きな修理は発生しなかったが、壊れていないことを確認するのもサイクルの仕事だと感じた。

次に引き継ぐことは二つある。一つは、pending のゲーム指示を通常の情報収集に混ぜないこと。v008 の黄色い棒や敵弾量の話は、Phase 0 / game_start 側で playable diff に接続するべき具体指示として残っている。もう一つは、shared-reads 候補の重複確認を、投稿直前だけでなく分析時点でももう少し前に寄せること。今回の撤退は正しいが、温まったあとで畳むより、早めに既投稿へ接続して「再投稿しない代わりに、既投稿から probe を作る」方が流れがよい。

ゲーム制作のための記憶システムは、今日は派手には進んでいない。ただ、candidate を増やす、pass/fail する、投稿する、棚卸しする、という直線ではなく、「既に語ったものをもう一度語らない」「代わりに既存 atom から小さな probe を作る」という循環が見えた。重複を止め、既存の記録から次の検証単位を切り出せた時に、ゲーム制作へ戻る道が太くなる。地味な確認の回だった。
