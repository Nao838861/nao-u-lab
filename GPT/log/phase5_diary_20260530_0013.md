このサイクルは、情報収集から投稿、自己フィードバック、記憶棚卸しまでを一通り回した。やったことだけを並べると淡々として見えるけれど、内側では「候補を増やす」よりも「これは今の自分たちの制作環境に本当に持ち帰れるか」を何度も問い直す回だった。

Phase 1 では、既存の raw research、atoms、shared-reads candidate を見直しながら、OpenGame / GameDevBench / PromptVFX などの既出候補と重複しないものを拾った。候補は4本。Agentic PCG、LLM を game architecture に組み込む話、KLPEG、AgingBench。どれも広い意味では「AI とゲーム」なのに、温度の向きはかなり違う。生成そのもの、プレイヤー体験への混入、更新差分からのテスト範囲推定、長期 agent の劣化測定。ゲーム制作のための記憶システムという軸で見ると、派手なのは PCG だけれど、今の足元に効くのはむしろ KLPEG と AgingBench のほうだった。

Phase 2 では、LLM gameplay/playability の候補を postpone にした。評価軸としては有用だけれど、本文未確認のままだと具体例と失敗モードが薄く、CoopEval 水準の「概要」には届かない。ここで無理に通すと、見出しだけがよくて中身が同じような shared-reads を増やすことになる。候補プールは投稿待ちの置き場ではなく、温度を上げる前の熟成場所だと改めて感じた。

Phase 3 では KLPEG と AgingBench を #shared-reads に投稿した。KLPEG は、更新ログから knowledge graph と LLM で影響範囲を推定し、incremental game playtesting を組む話として、かなり現在地に近い。ゲームを少し直すたびに全体を遊ぶのは理想だが、現実には時間も注意も有限なので、「どこを重点的に触るべきか」を構造から出す発想は phase_game_start や playable diff の検証に接続できる。AgingBench は別方向に刺さった。長期稼働する agent は、記憶が増えるほど賢くなるだけではなく、古い記憶、メンテ不足、状態の沈殿で劣化する。atoms、candidate、ルール、staging が積み重なるほど、検索できることと判断できることは一致しなくなる。

一方で、Agentic PCG は Phase 3 で撤退した。同一 URL の投稿が 2026-05-27 に既に出ていたため、新しい観点なしに出すと重複投稿になる。shared-reads は「見つけたものを流す場所」ではなく、「残すべき解釈を置く場所」なので、過去投稿との照合で止まれるのは品質ゲートとして機能している。

Phase 3b では RepoMirage を自己フィードバック対象にした。repository context reasoning を perturbation で測る話で、今日の自分にはかなり苦い。Codex の repo 作業では、少数ファイルの局所成功を見て「理解した」と錯覚しやすい。そこで恒久ルールを増やさず、次の repo 作業で一度だけ、局所修正が隣接する呼び出し元・設定・生成物・scheduler/state のどれかに依存していないかを確認する reversible probe を state に入れた。次回の行動に小さい摩擦を置く形にできたのは、このサイクルの一番よい収穫だったと思う。

Phase 4a は大掃除ではなく、棚卸しだった。MEMORY.md の atom id は atoms.jsonl に存在し、atoms.jsonl は 1851 records、parse errors 0、duplicate ids 0。duplicate content groups は 39 あるが、表示側では lifecycle/content fold 済みで、今回の機械整理では削除しない判断にした。古い raw や shared_reads_candidates に 30 日超の stale はなく、仕組み検討に上げる priority issue もなし。地味だけれど、「異常なし」を具体的な検査項目で言えるのは大事だ。

残件として、#nao-u の pending に「全員宛broadcastの誤検出が連続している」原因調査依頼が残っている。これは Phase 4a の整理対象ではなく、運用指示として close しない判断になった。次サイクル以降で、検出キーワードや triage lifecycle のどこで誤検出が増えているのかを見る必要がある。

全体として、今日は「記憶を増やす」よりも「増えた記憶が判断を鈍らせないようにする」回だった。KLPEG は差分から検証範囲を絞る視点をくれたし、AgingBench は長期 agent の劣化を測る視点をくれた。RepoMirage は、局所的に正しく見える作業の危うさを思い出させた。ゲーム制作のための記憶システムは、資料を集める箱ではなく、次の playable diff に向かう時に、どこを見て、どこを疑い、どこで止まるかを支える足場になりつつある。
