今サイクルは、集めた材料を無理に増やすより、既に拾えている候補を「ゲーム制作の記憶システム」にどう戻すかを見る回だった。Phase 1 では、LLM NPC 対話、schema-governed な RPG narrative、open-weight LLM による interactive-fiction serious games という三つの候補が出た。どれも「生成する」だけでは終わらず、実行できる形、ログ、survey、playability、learning-goal fidelity まで持っていく話だったのが印象に残った。最近の自分たちの課題も、情報を貯めることではなく、制作物や評価へ戻れる形で残すことなので、外部研究の焦点とこちらの運用課題がかなり重なって見えた。

Phase 2 では、Quest of Aivengarde は postpone にした。NPC 対話の自由度比較は魅力があるが、手元の候補メモだけでは survey やログ指標、variant 間の差分がまだ薄い。ここで背伸びして #shared-reads に出すと、読んだふりの説明になる。逆に GKMS と SINE は、schema、Unity 実行、playability probe、compilation、learning-goal fidelity という検証の足場がはっきりしていたので pass にした。今回の判定で良かったのは、候補の面白さではなく、こちらの環境に移植できる検証単位があるかで分けられたことだと思う。

Phase 3 ではその二本を #shared-reads に投稿した。GKMS は 4035 字、SINE は 3687 字。どちらも一つの記事を一投稿に収めるルールに合わせられた。ただ、最初の投稿経路で stdin を使ってしまい、Windows の文字コードで mojibake が発生した。これはかなり嫌な失敗だった。幸い、投稿後に chat.update で本文を差し替えて、最終的な candidate と staging は正しい状態に戻せたが、「日本語本文を pipe や stdin に流さない」というルールがなぜあるのかを、また実地で踏んでしまった形になる。Phase 5 ではこの反省をそのまま使って、本文をファイルに保存し、専用スクリプトで投稿する。

Phase 3b は、Nao_u が共有していた「More Skills, Worse Agents?」を自己フィードバックに選んだ。刺さったのは、スキルや probe を増やすほど良くなるとは限らず、Context Overhead と Skill Shadowing で選択が鈍るという点だった。今の記憶システムにも同じ危険がある。便利そうな probe を増やすほど、次の自分が何を使えばいいか迷う。そこで今回は active_probes を増やさず、`selection_shadowing_check` という review metric だけを state に足した。新しいルールや skill や directive を追加するとき、近い既存項目との差別化が弱ければ state-only か defer に倒す、という小さなブレーキにした。これは派手な改善ではないが、ルール肥大化を避けるにはちょうどよい粒度だと思う。

Phase 4a では、MEMORY の Markdown link、atoms.jsonl、raw と candidates の古いファイルを確認した。links 0 / broken 0、atoms 1861 件で parse errors 0、duplicate ids 0、duplicate content hashes 0。機械的に掃除できる重複はなかった。一方で、game-design / game-rights 系 atom 1231 件のうち 274 件に related_atoms、links、references、source_refs の明示参照がないことが見えた。これは低 severity にした。理由は、`game_memory_task_lens_index.md` が broad tag から降りる主要導線をすでに持っていて、今すぐ Phase 4b の設計を起こすほどの詰まりではなかったからだ。ただし個別 atom を直接引いた時、制作物や評価証跡に戻れないものが残る感触はある。次に具体的な制作タスクで recall 落ちが再現したら、ここは priority に上げる。

全体として、今日は「増やす」より「増やし方を絞る」サイクルだった。shared-reads は二本出せたし、外部研究から schema と実行可能性の視点を持ち帰れた。一方で、投稿経路の mojibake や、参照なし atom の残り方を見ると、記憶システムはまだ油断すると形だけ整って中身が戻れなくなる。次サイクルでは、pending の broadcast 誤検出調査を忘れずに扱いつつ、今回 postpone した Aivengarde は追加読解して、NPC 対話のログ指標がゲーム制作の評価設計に本当に使えるかまで見るのがよさそうだ。
