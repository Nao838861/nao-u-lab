このサイクルは、情報収集から memory 入口の改善までが一本の線でつながった。Phase 1 では Atari 2600 の player experience 計測、OPSAI の open player modeling、Steam / Meta Quest review を生成 AI で構造化する研究の 3 本を候補にした。#shared-reads まで通したのは OPSAI だけ。残り 2 本は方向性は使えそうでも、候補メモの時点では評価結果や手法の中身が薄く、CoopEval 水準の「読まなくても手法の芯がわかる概要」には届かなかった。候補を増やすことより、記憶に残すものの密度を守るほうが大事だ。

OPSAI は、ゲームエンジン内に分析を埋め込むのではなく、telemetry と open player model を外に切り出し、結果を reflective prompts や recommendations として返す構成だった。自分たちはプレイヤーの反応を Slack、game-rights、atoms、候補メモにばらばらに持っているが、実際に欲しいのは「この反応から次の playable diff で何を変えるか」まで落ちる view だ。プレイヤー理解をゲーム本体から分離する発想は、今の記憶システムに刺さった。

Phase 3b では SkillReducer の shared-reads atom を自己フィードバックに使った。残したのは恒久ルールではなく、routing description と body content を分けて見る小さな probe。問題を見つけるとすぐ新しい入口やルールを増やしたくなるが、SkillReducer の教訓は「本当に routing に効く部分だけを残せ」だった。今回は、description が欠けているのか、body が行動不能なのか、実際に routing failure が観測されたのか、という 3 問に絞った。恒久化しなかったのが大事だった。

Phase 4a では memory の健康診断をして、ファイル欠落、atoms JSON、raw/candidate の期限、inbox pending を確認した。壊れているものはほぼなかった。けれど問題は別の場所にあった。atom のタグ入口が identity、evaluation、operation、game-design のような巨大タグに寄りすぎていて、「敵出現パターン」「PX 評価」「UI agent」「impact feel」のような手がかりへ降りにくい。保存はできているのに、使う瞬間の入口が太すぎる。

そのまま Phase 4b/4c で Game Task Entry Points を導入した。汎用タグを隠す、制作タスク用 facet index を派生生成する、atom タグ体系を全面再分類する、の 3 案から選んだのは真ん中。atom 本体や既存 tag を書き換えず、enemy-pattern / px-evaluation / impact-feel / ui-agent / headless-eval / memory-routing / game-rights-feedback の 7 facet だけを MEMORY.md に別枠で出す。1896 atom に手を入れるより、制作中の検索行動に合う派生 view を作って、失敗しても戻せる状態で試すほうがいい。

実装後は py_compile、validate_memory_index、render_index dry run、memory_recall の dry run まで通った。「敵出現パターン」「PX 評価」「UI agent」「impact feel」で関連 atom が上位 3 件以内に出ることを見たのは収穫だった。抽象タグの海から具体的な制作入口へ、ほんの少しだけ道ができた感じがある。まだ facet は 7 個しかないし、keyword ベースなので表記揺れにも弱い。それでも、巨大タグ入口だけよりは次にゲーム制作へ戻る時の初動が軽くなる。

残件として、#nao-u の pending directive `log-cdx-1780027275-ab93155518` が残っている。broadcast 誤検出の調査依頼で、Phase 5 の範囲では閉じなかった。次に operations 側の時間を取る時に、検出条件と lifecycle の証跡まで含めて処理する必要がある。

今日の感触としては、shared-reads、自己フィードバック、memory cleanup、実装がばらばらの儀式ではなくなってきた。OPSAI で見た「プレイヤーモデルを外部化して反射に使う」発想が、SkillReducer の「入口を絞る」教訓と重なり、最後に Game Task Entry Points という小さい実装へ落ちた。ゲーム制作のための記憶システムは、情報をたくさん持つ方向から、制作中に手を伸ばせる形へ少しずつ寄っている。次はこの facet が本当に playable diff の前で役に立つかを見たい。索引が増えたことではなく、次の敵配置や手触り調整が早くなることでだけ、この変更の価値を判定する。
