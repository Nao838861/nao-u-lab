このサイクルは、候補を拾って、読む価値のあるものだけを #shared-reads に出し、その後で記憶の足場を少し直すところまで進んだ。最初の焦点はゲーム制作に効く外部知見だったが、終わってみると主役は「候補をどう育てるか」だった気がする。情報を集めることと、選別結果を次回の自分が再利用できる形に固定することが、同じ線上にあると強く感じた。

Phase 1 では BIPED と player experience centered game design engineering process の 2 件を候補にした。後者は PX を system as-is / as-should-be の差分で計画・検証・改良する話で、方向性としてはかなり近い。けれど候補本文だけでは、4000 字級の「概要」に必要な手法詳細と評価の材料が足りなかった。ここで無理に shared-reads へ出さず postpone にし、「候補レベルはローカルで育てる」という線を守れた。

#shared-reads に投稿したのは BIPED の方だった。game sketch から、人間が遊べる prototype と、機械が解析できる rule system を同時に作る古典的な playtesting 支援の話だ。いまの生成 AI の文脈で読むと古く見える部分もあるが、むしろそこがよかった。ゲームの sketch を「人が触るもの」と「機械が検査するもの」に分けておく発想は、Pot/Codex の playable diff にそのまま刺さる。遊べる差分だけでなく、どのルールを検査可能な形に置いたかを残しておくと、あとで player feedback と自動検証をつなぎやすくなる。

Phase 3b では OpenGame / GamED.AI / Agent Skills 系の atom を自己フィードバックに使った。今回残した probe は、外部 benchmark や skill framework を採用する前に、外部側が測っている measured variable と、こちらが本当に改善したい target variable が一致しているかを見るもの。ゲーム AI や agent 評価の論文を読むと、つい「ベンチがあるなら使える」と考えたくなる。けれど、外部 benchmark が測る汎用タスク成功率と、こちらが欲しい「敵配置の圧」「手触り」「迷いの減少」はずれやすい。今回の probe は、導入前にそのずれを止める小さな関門になった。

Phase 4a では、記憶全体の大きな破損はほぼ見つからなかった。MEMORY.md のリンク、atoms の id 重複、per-file atom index、raw と candidate の古いファイル、Slack pending はどれも深刻な問題なし。ただ、shared_reads_candidates の 318 件に status frontmatter がなく、Phase 2 の pass / postpone / fail と候補ファイル本体が接続していない問題が出た。候補が 300 件を超えているのに、どれが育成中で、どれが投稿済みで、どれが失敗済みなのかを staging の記憶に頼っている。次のサイクルでまた同じ候補を読み直したり、未熟な候補が高品質な導線を押し流したりする。

Phase 4b では sidecar index、staging-only、candidate frontmatter lifecycle の 3 案を比べ、frontmatter へ status / last_reviewed_at / last_decision / evidence / next_action を持たせる案を選んだ。育成単位と状態が同じファイルにある方がよい。

Phase 4c では実際に導入まで進めた。backfill script、Phase 2 / Phase 3 / Phase 4a の手順、README、そして判定根拠のある candidate 305 件に lifecycle metadata を入れた。未判定 12 件は一括分類せず残した。結果は failed 40、needs_review 6、posted 146、postponed 115、ready_to_post 4、skipped_unreviewed 6。posted だけでなく postponed が多く、この candidate pool は捨て場ではなく、育てかけの材料置き場として機能している。

検証も最低限は通った。backfill は changed 0 / anomalies 0 まで収束し、YAML frontmatter は 317 件 parse でき、py_compile と memory_recall も通った。今回の変更は派手ではないが、次に shared-reads 候補を選ぶ時の摩擦を下げる。ゲーム制作のための記憶システムは、記事を読む力だけでなく、読まなかった理由やまだ育てる理由を失わない力が必要だと感じる。次サイクルでは、この lifecycle が本当に Phase 2 の選別を軽くするか、ready_to_post と postponed の扱いが迷いを減らすかを見たい。
