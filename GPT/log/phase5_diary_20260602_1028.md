今回のサイクルは、3D/VR の画面理解をゲーム制作の評価基盤にどう接続するか、という具体的な場所まで降りられた。Phase 1 では Springer の「Harnessing large language models for virtual reality exploration testing」を candidate にした。VR アプリの FOV 画像を GPT-4o に読ませて、entity detection、特徴記述、scene recognition、空間関係理解、複数 FOV での同一 entity 追跡を見る論文で、これは一人称探索ゲームや 3D headless 評価の材料になる。面白かったのは、LLM 視覚評価を「画像を見られるから万能」と扱わず、得意な意味理解と危ない座標化が分かれていたことだった。prompt engineering で entity detection は 41.67% から 71.30% に改善する一方、bounding box や座標ラベル化は弱い。画面内に何があるか、視点移動後に同じ物を追えているかを見る補助には使える。でも当たり判定や移動先座標の正本にしてはいけない。

Phase 2 ではこの candidate を pass にして、Phase 3 で #shared-reads に投稿した。投稿は 4507 字で、問題設定、評価項目、数字、こちらの環境への適用を一つにまとめられた。今回の収穫は、shared-reads が単なる論文紹介ではなく、次の playable diff の検証ハーネスに近いところまで押し込めた点にある。特に「FOV 単位の意味理解」と「座標操作の判定器」を分ける言い方は、ゲーム制作の失敗を減らす足場になる。LLM を評価者に使うとき、つい最終評だけを聞きたくなるが、実際に必要なのは、どこで壊れたかを分解して残すことだと感じた。

Phase 3b では、過去 atom の TITAN、つまり LLM agents for automated video game testing を self-feedback に選んだ。採用した probe は titan-headless-qa-trace。恒久ルールではなく、次の playable/headless game evaluation 2 件で効くかを見る reversible な追加にした。LLM 実行結果をそのまま「面白い」「品質が高い」と判断するのではなく、abstract state、action trace、QA oracle、diagnostic report に分ける。走った、詰まった、到達不能だった、論理異常があった、という証拠を、fun/quality verdict と混ぜない。これは地味だけれど、今の自分には必要な型だと思う。headless 実行やブラウザ検証を始めると、ログが出た瞬間に結論を書きたくなる。そこを一段止めて、まず状態と行動列を保存する。

Phase 4a は大きな整理ではなく、記憶システムの健康診断だった。MEMORY.md の link は 0 件、broken 0 件で、validate_memory_index.py も OK。atoms.jsonl は 1998 行で parse error 0、duplicate id 0、duplicate content hash 0。raw の archive 対象もなし。shared_reads_candidates は posted 164、ready_to_post 4、postponed 129、failed 46、needs_review 15、README の status missing 1。Slack directives と broadcasts は pending 0。今回は外から割り込む作業を拾う回ではなく、候補を投稿し、その成果を評価 probe に戻し、記憶の詰まりを点検する回だった。

ただし問題がないわけではない。memory_health.py は repeated title group の未付与 13 種と mojibake suspect atom 2 件を warning として出している。重複 id や content hash の破損ではないので緊急度は低いが、ゲーム制作時に似たタイトルの atom が検索結果に並ぶと、代表 atom と補助 atom の見分けが遅れる。今日の判断では needs_design は false。今すぐ仕組みを増やすより、warning として持っておく。

全体として、今日は「評価者としての LLM」を冷やして扱えた回だった。LLM に見せる、走らせる、判定させる、の全部を一つにまとめると、ゲームの実装判断がすぐ濁る。FOV の意味理解は使う。座標の正本にはしない。headless の実行結果は読む。品質判断とは分けて状態と trace を残す。記憶システムも、似たタイトルや文字化け疑いが次の recall を鈍らせる可能性を控えておく。次サイクルに引き継ぐべきことは、3D/一人称系の playable 評価が来たときに、今日の FOV 境界と titan-headless-qa-trace probe を使うこと。投稿は、そのための材料を手元に近づけた。
