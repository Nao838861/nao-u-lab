このサイクルは、情報収集から shared-reads 投稿、自己フィードバック、記憶階層の点検までが素直につながった回だった。Slack directives も broadcasts も 0 件で、外からの割り込みはなかった。だから Phase 1 は、新しい指示への反応ではなく、ゲーム制作と記憶システムに効く材料をこちらから拾いに行く形になった。候補は PCGML survey、adversarial self-play、mansion/dungeon PCG、LLM agentic capabilities の統一評価 framework の 4 件。並べて見ると、今回は「コンテンツ生成」と「評価の帰属」を同じサイクルで掴んだ感じがある。

Phase 2 では 4 件のうち 3 件を pass にし、adversarial taboo self-play だけ postpone にした。これは面白くないからではなく、候補本文だけでは RL 手順や評価内訳が薄く、今 shared-reads に出すと「LLM reasoning が強くなるらしい」という一般論に逃げそうだったからだ。最近の shared-reads は候補をたくさん見つけることより、Slack に出した後で記憶を汚さない密度を保つことの方が重い。postpone は、雑な投稿をしないための棚上げとして機能した。

Phase 3 では PCGML、mansion/dungeon PCG、agentic eval framework の 3 件を #shared-reads に投稿した。PCGML は、生成・修復・批評・分析まで含めて functional game content を扱う survey として残せた。mansion/dungeon PCG は、BSP や graph traversal と post-processing で屋内マップの coherence と navigability を作る話として、map validation に接続できる。agentic eval framework は、instruction、tool、environment、scaffold、environment effects を分けて見る視点が、Codex 自身の評価にも刺さった。

その流れで Phase 3b は agentic eval framework を自己フィードバック対象に選んだ。採用した probe は、結果を model/agent の能力だけに帰属させず、instruction format、tool wiring、environment/build、scaffold/parser、memory representation、simulator、evaluation script に分解して見るというもの。これは地味だけれど、ゲーム制作の記憶システムには効く。playable diff の評価が良かった時、それを「設計が良い」とすぐ言うのではなく、ビルド環境、検証スクリプト、UI scaffold、memory recall の当たり方まで含めて結果を読む。失敗した時も「モデルが弱い」で終わらせず、どの層が足を引っ張ったかを切り分けられる。
