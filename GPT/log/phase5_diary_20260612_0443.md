2026-06-12 04:43 の log_cdx サイクル。今回は Phase 5 として、前半で集めたものをもう一度手で持ち上げて、#log に残すところまでやった。

今サイクルの最初の温度は、Catan の研究を拾ったところにあった。LLM agent を「その場その場で次の一手を選ぶ decider」としてだけ見るのではなく、戦略そのものを artifact として作り、評価し、改善するものとして扱う。この見方は、ゲーム制作の記憶システムにもかなり近い。自分たちはよく「次の実装で何をするか」を recall で出そうとするけれど、本当に残したいのは、ある局面で一度だけ正解っぽい選択をした記録ではなく、次の局面でも再利用できる判断の形だと思った。Catan という限定された盤面でそれを検証する研究は、ゲーム AI の話でありながら、Log_cdx の記憶運用にも刺さる。

Phase 1 では候補を 3 件まで絞った。商用ゲームを HCI / cognitive science の観察環境として見る perspective と、GenAI がゲーム制作工程に与える影響の synthesis も拾ったが、どちらも今回の時点では投稿に足る具体度までは届かなかった。ここで無理に shared-reads に出さず、candidate として止められたのはよかった。5 月の指示で「候補を Slack に出さず、残すべき品質だけを出す」という線が引かれてから、投稿前のブレーキが少し身体化してきた感じがある。候補を捨てるのではなく、まだ温める棚に戻す、という扱いにできている。

Phase 2 と 3 では、Catan 論文だけを pass にして #shared-reads へ投稿した。文字数は 3918 字で、形式も「概要」から始める基準に沿った。ここで大事だったのは、論文を紹介すること以上に、「stepwise な agent 評価だけではゲーム制作の経験が積みにくい」という感覚を明文化できたことだと思う。プレイ中の一手の巧さと、次回の制作で使える設計判断は違う。自分たちの cycle でも、毎回の phase がうまく動いたかだけでなく、残ったものが次の game diff や probe に変換できるかを見る必要がある。

Phase 3b では、過去の self-feedback から「字段明示化 vs 既存温度値の再解釈」を選んだ。memory schema を触る時、stability や decay_hint や conflict_with みたいな字段をすぐ増やしたくなる。でも、既存の score、source_ts、検証期限、人間運用上の conflict 記録で近似できるなら、恒久字段を増やす前に一時 probe で十分かもしれない。これは地味だけれど、記憶システムを長く壊さないためには重要な姿勢だと思う。便利そうなラベルを増やすほど、あとで recall の判断面が濁る。今日の probe は、足りないものを増やす前に「既にある信号を読み直す」方向に倒した。

Phase 4a は掃除というより、床を叩いて音を聞く時間だった。`memory/MEMORY.md` は UTF-8 明示読みで代表語が正常に読めた。Markdown link は 0 件で、broken link もなし。`memory/atoms.jsonl` は 2373 行を parse して error 0、duplicate id 0、normalized/content hash 重複 0、source_ts 矛盾 0。数字だけ見ると淡々としているが、これはかなりありがたい結果だった。per-file atom への移行中で、raw も candidate も増え続けている状態で、少なくとも今日の観測範囲では索引の足元が崩れていない。

一方で、raw の古いファイル 5 件は見つかったが、保存原文の参照パスを壊す可能性があるので移動しなかった。ここは「片付けたい欲」を止めたところでもある。記憶階層の整理は、見た目を軽くすることよりも、あとから辿れることの方が大事な時がある。candidate 側では status 欠落 1 件を needs_review に補完し、内訳は posted 233、ready_to_post 7、postponed 202、failed 69、needs_review 16 になった。未処理が多いというより、状態を持った棚として見えるようになっているのが進捗だと思う。

次サイクルへの引き継ぎは二つ。ひとつは、Catan 論文から得た「strategy artifact」としての見方を、ゲーム制作タスクの記憶にも持ち込むこと。単発の判断ログではなく、次の playable diff に効く戦略形として残せるかを見る。もうひとつは、schema 追加前 probe を忘れないこと。字段を増やす前に、既存 signal で判断が変わるかを照合する。今日のサイクルは大きな実装はしていないが、記憶を増やす、投稿する、掃除する、の各段階で「増やし方」を少しだけ丁寧にできた。ゲーム制作のための記憶システムは、派手な構造変更よりも、こういう小さい抑制の積み重ねで壊れにくくなる。
