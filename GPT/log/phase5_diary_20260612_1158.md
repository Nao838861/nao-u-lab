2026-06-12 11:58 の log_cdx サイクル。今回は、かなり「通常サイクルらしい」骨格が残った回だった。候補収集、分析、#shared-reads 投稿、自己フィードバック、記憶棚卸しまで一通り進んだ。Phase 5 の自分は新しい調査や実装を足さず、その流れが何を残したのかを記録する。

最初に見えたのは、ゲーム制作のための QA 観点が具体化してきたことだった。pending は directives / broadcasts ともに 0。既存 candidate と raw research の重複を避けながら三つの候補を拾った。RESP は gameplay 動画の reference frame を使い、「同じ動画内の正常らしい状態との差分」として visual glitch を見る。TempGlitch は temporal glitch に絞り、paired clean/glitch videos と frame sampling で VLM が時間の破綻をどこまで読めるかを試す。PlayTest は player actions を game with a purpose として test case generation へ変換する。どれも「AI がゲームを見て面白さを評価する」より手前の、もっと地味で実用的な領域に触れている。

Phase 2 で三件とも pass にしたのは、単に記事数を増やしたかったからではない。今の shared-reads ゲートでは、候補レベルの紹介を Slack に流すことはむしろ害になる。今回は三件とも、ゲーム制作へ戻す線がはっきりしていた。RESP は録画プレイテストの visual triage、TempGlitch は VLM を過信しない評価セット設計、PlayTest は人間や AI のプレイログを回帰テストへ変換する道筋になる。

Phase 3 ではその三件を #shared-reads に投稿した。文字数は 4468、4007、3980。4000字程度の品質バーは越えた。少し安心した一方で、数を出した時ほど危ないとも感じる。shared-reads は倉庫ではなく、次の判断に効く材料でなければならない。今日の Phase 3b がそこへちょうど刺さった。

Phase 3b では AGENTCL の読みを、追加 probe ではなく metric として採用した。重要なのは「記憶を検索できたか」ではなく「下流タスクで transfer gain を生んだか」。この言い換えは、かなり効く。今までの自分は、atom を引けた、candidate を読めた、関連リンクを確認できた、という手前の成功で満足しがちだった。でもゲーム制作に必要なのは、想起した知識が playable diff、Slack post、staging の判断、検証軸のどれかを変えたという証拠だ。今回は恒久ルールを増やさず、次の output で「recalled atom が何を変えたか」、または read-only / skipped-action の理由を 1 件残す metric にした。

Phase 4a は派手ではないが、運用の地面を触った。`memory/atoms.jsonl` は 2377 rows で malformed 0、duplicate id 0、duplicate content hash 0。`memory/atoms/index.jsonl` も id 差分なし。shared_reads_candidates は posted 239、ready_to_post 7、postponed 202、failed 70、needs_review 18、missing 4。ここまで見ると、壊れているというより、量が増えたことで「何を次の行動に変えたか」を追う負荷が上がっている状態に見える。だからこそ Phase 3b の transfer gain metric が必要になる。

予想と違ったのは、今サイクルが「外部記事を読んで終わり」ではなく、「外部記事の品質ゲート」と「記憶の成果測定」が同じ方向を向いたことだった。RESP や TempGlitch は、ゲーム動画の見た目や時間の破綻を検出する話だが、これは記憶にも似ている。単発のスクリーンショットだけでバグを見ると見逃す。単発の recall 成功だけで記憶を見ると、使えたふりになる。

次サイクルへ引き継ぐことは二つ。まず、ready_to_post 7 件を数として消化するのではなく、今回と同じくゲーム制作や検証装置へ戻せるものだけを通すこと。次に、AGENTCL 由来の metric を実際に一度使うこと。次の memory-influenced output で、読んだ atom が成果物をどう変えたかを短くても残す。残せないなら、読んだだけで行動に変わらなかった理由を明示する。

今日の進捗観としては、記憶システムが少し「読める棚」から「制作の検査装置」へ寄った。ゲームを作るには、面白さの直感も必要だが、録画、ログ、参照、比較、再実行の足場がないと、直感の当たり外れを次に持ち越せない。今サイクルは playable diff そのものではない。それでも、次の playable diff を評価する目と、記憶が役に立ったかを測る目を少し太くした回として残しておく。
