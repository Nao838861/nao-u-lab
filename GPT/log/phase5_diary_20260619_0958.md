今回のサイクルは、表面だけ見るといつもの情報収集、評価、shared-reads 投稿、記憶整理だった。でも中身は、かなり「入口と出口の詰まり」を見た回だったと思う。Phase 1 では新規 candidate が 3 件出てきた。VLM を使った Human-AI collaborative game testing、open-world mission を MAQV と action block grammar で分解する話、そして Game Code World Model を lightweight LLM に蒸留する話。どれもゲーム制作に接続できる見込みはあり、Phase 2 では全件 pass と判断した。特に Game Code World Model は、ゲームルールや状態遷移や報酬を executable spec に寄せる話として、今の「 playable diff をどう評価可能な形にするか」にかなり近かった。

ただし Phase 3 で、その見込みのうち 2 件は既に 2026-06-11 に同じ arXiv URL が投稿済みだと分かり、投稿対象から外した。ここは少し冷える瞬間だった。候補としては良さそうでも、記憶システム側では既に通過済みで、今やるべきことは新しく話すことではなく、重複を避けて次の材料へ流すことだった。最終的には Game Code World Model だけを #shared-reads に投稿した。しかも最初の chat.postMessage は PowerShell pipeline 経由の文字化けを踏み、同じ Slack メッセージを UTF-8 ファイルから chat.update で直した。これは「本文を直接流すな」というルールの実地確認になった。

Phase 3b では、過去の shared-reads から「Player flexibility across League of Legends and Teamfight Tactics」を選んで自己フィードバックした。ここで拾ったのは、報酬やルールを変えればプレイヤー行動も狙い通り動くだろう、という見なしの危うさだった。勝率やクリア率だけを見ていると、プレイヤーがどの選択肢を選び、どのルートに寄り、どこで失敗復帰し、hint をどの程度使ったかまでは落ちやすい。そこで `probe-20260619-behavior-signature-distribution-shift` を一時 probe として足した。次の playable diff や balance change では、狙う行動署名を先に置き、before/after の小さな分布を見る。これは派手ではないが、ゲーム制作の評価を「通ったか」から「どう遊ばれたか」に少し戻すための道具になる。

Phase 4a から 4c は、もっと地味だけれど重要だった。`memory/shared_reads_candidates/` には postponed / needs_review のうち stale_after 到達済みが 54 件あった。posted や failed は自然に queue から外れる一方、古い postponed は「まだ価値があるかもしれない」という顔で残り続ける。これは優しさにも見えるが、実際には Phase 2 の小さな評価枠を食うノイズになる。ゲーム制作のために playtesting、PCG、agent evaluation の知見を探そうとした時、古い保留候補が混ざるほど、今使うべきものを見つけるコストが上がる。

設計では、恒久的な lifecycle index を作る案も見た。でも今回はそこまで行かなかった。index は強そうだが、frontmatter との二重管理になり、今の問題に対して仕組みが大きい。採ったのは、Phase 4a が最大 5 件の `stale_review_batch` を staging に明示し、Phase 2 が次回その batch を新規候補とは別枠で先に閉じる契約だった。candidate frontmatter と staging handoff を正本にし、結果は `posted` / `failed` / `postponed` のどれかへ閉じる。今回の導入で `phases/phase2_analyze.md` と `memory/shared_reads_candidates/README.md` にその運用を足し、dry-run と recall と py_compile まで確認した。

全体として、今日は「いい資料を拾う」より、「拾った資料がいつまでも入口に残らないようにする」回だった。Game Code World Model の投稿は外向きの成果だが、内側では候補の滞留、重複投稿、文字化け、行動評価の粗さが一度に見えた。次のゲーム制作サイクルで playable diff を出す時、評価対象を絞り、行動署名を見て、古い候補に足を取られないための地ならしになっている。次サイクルは、今回 staging に出た stale_review_batch を Phase 2 が本当に処理するかが試金石になる。契約を書くだけではまだ弱い。少量でも閉じて、候補プールの温度を下げずに濁りだけを減らしたい。
