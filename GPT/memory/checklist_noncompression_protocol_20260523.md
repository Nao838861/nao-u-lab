# チェックリスト非圧縮プロトコル

Codex はチェックリストを作る時、過去の指示や記憶を短く要約しすぎて、重要な条件を落とした劣化コピーを作る傾向がある。このファイルは、その再発を防ぐための運用ルールである。

## 禁止

- 元の指示が長い時に、短い一行チェックへ圧縮してはいけない。
- 「敵配置を改善する」「指標をハックしない」「headless を走らせる」のような見出しだけで、何をもって達成か分からない項目にしてはいけない。
- 実装しやすくするために、途中でチェック項目を削除、統合、対象外化してはいけない。
- 指標が通るように HP、スコア、AI 方針、敵数、閾値を動かして「達成」としてはいけない。
- 前回のチェックリストをさらに要約して次回用チェックリストを作ってはいけない。

## 必須フォーマット

チェックリストの各項目は、少なくとも次の形にする。

- `出典`: ユーザー原文、memory ファイル、lesson ID、または対象プロジェクトの design log。
- `元の意図`: 省略しない。原文の重要語を残し、抽象語に置き換えない。
- `達成条件`: どのファイル、どの挙動、どの評価結果があれば「やった」と言えるか。
- `未達判定`: どういう手抜きや劣化コピーなら未達か。
- `証跡`: design log、headless 結果、wave 表、self_judgment、git diff など。

## 作成手順

1. まずユーザーの最新指示から、原文のまま保持すべき文を抜き出す。
2. 次に、関連 memory / lesson から「実装前に読むべき正本」を列挙する。
3. その後で初めてチェックリストを書く。
4. 書いたチェックリストを、元の原文と照合し、「落ちた名詞」「落ちた動詞」「落ちた未達判定」を探す。
5. 落ちた条件を短い見出しで足さず、必ず `出典 / 元の意図 / 達成条件 / 未達判定 / 証跡` まで書く。
6. 実装中にチェックリストを変更する場合は、変更理由を design log に書き、削除ではなく blocker / v002 / intentionally accepted に分類する。

## 2Dシューティングの特別ルール

2Dシューティングでは、敵設計とステージ展開が毎回落ちやすい。次の項目は「敵配置」などの一行にまとめず、必ず独立項目として残す。

- 敵は HP、速度、弾数ではなく、プレイヤーに何をさせるかで定義する。
- 敵出現は `reference / time_window / spawn / path / fire_rule / player_intent / success_feel / failure_pressure / bad_policy_check / telemetry` で書く。
- ステージは単発 wave の羅列ではなく、前 wave が作ったプレイヤー位置を次 wave が利用する。
- Boghog 4 規則と 4 失敗パターンを assertion 化する。
- `camper`, `lane-holder`, `blind-sweeper` など、ユーザーが指摘しそうな雑な勝ち方を bot policy として先に作る。
- per-second telemetry は集計値の飾りではなく、どの秒にどんな体験問題があるかを見るために使う。
- noMechanic / mechanicHeavy の比較は、固有メカが弱いのか、AI が下手なのか、敵配置が単純すぎるのかを分けて考える。

## 次回への引き継ぎ

このプロトコルは、今作だけのメモではない。次回以降、ゲーム制作でユーザーが「自律して完成」「shot_log くらい」「敵配置」「時系列評価」「チェックリスト」と言ったら、チェックリスト作成前にこのファイルを読む。
