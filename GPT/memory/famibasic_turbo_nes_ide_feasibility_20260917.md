# FamiBASIC TurboのNES ROM開発環境化：初回相談

> 訂正：続くGitHub調査で対象ソースを特定した。以下はソース確認前の一般論であり、現行実装の不足機能・着手順・見積もりの根拠には使用しない。非公開リポジトリの具体的な調査結果はこの公開リポジトリへ転記しない。

## ユーザーの相談原文

> FamiBASIC Turboの開発について相談したい。この環境を、nesのROMが作れる統合開発環境にできないか？そうするためのハードルは何？ROM作成からエミュレータ実行まで内包したい。

## 確認範囲

現ワークスペースの実装・記憶検索ではFamiBASIC Turboのソースを特定できなかった。ソースの場所を問い合わせ済み。以下は実装監査の結果ではなく、NES向け開発環境の一般的な実現性と提案。実装着手や既存言語の仕様変更は未決定。

## 提案と主要な判断点

ROM生成から内蔵エミュレータ実行までの統合は可能。8bitworkshopにブラウザ内コンパイルと生成ROMの即時実行の先行例がある。難所は、既存BASICの意味・速度・描画・音をNES実機相当の制約に落とす部分。

- 既存環境が6502コードを生成していれば、ROM構成・ビルド・エミュレータの統合が中心。JavaScriptなどの独自インタプリタなら、新たなNES向けコンパイラまたはNES上の実行系が必要。既存ファミリーベーシックROMを動かす方式なら、独立ROMとしての起動経路と元ROM・素材への依存確認が必要。
- 推奨案は、対応範囲を明示したNESターゲット。BASIC解析→Cまたは6502アセンブリ→既存ツールチェーン→独自ランタイム・画像・音声とリンク→`.nes`生成→内蔵エミュレータへ渡す。C経由でも型・整数演算・文字列・命令の意味は別途定義する必要がある。
- 既存インタプリタをNESへ移植してプログラムと同梱する方式も可能だが、CPU時間とRAMの負担を小さなゲームで測る必要がある。完全互換を先に約束しない。
- 本体CPU RAMは2 KiB。描画はタイル・パレット・スプライト構成で、描画更新タイミングにも制約がある。PC側で自由に描画できる機能が存在するなら、変換可能性を命令ごとに評価する。
- 最初は単純なカートリッジ構成と整数中心の小さな言語範囲に絞る。画面表示、パッド入力、キャラクター移動、効果音、フレーム待機が動く最小ゲームを往復させる。
- IDEのNES実行は書き出すものと同じROMバイト列で行う。別エミュレータでも同じROMを検証する。これは実機確認の代替保証ではない。
- ブラウザだけで完結するならコンパイラのWebAssembly化等を検討。デスクトップ同梱ならネイティブツールを呼べる。エミュレータ自作は必要ない。ソース行単位のデバッグは追加でソースと機械語の対応情報が必要。

最初に確認したい資料は、構文解析・実行ループ・描画・音源・サンプルプログラム。これらを見て「そのまま対応／制約付き／非対応」を作成すれば、具体的な規模見積もりができる。

## 一次資料

- [8bitworkshop IDE](https://8bitworkshop.com/docs/docs/ide.html)：内蔵コンパイラ・エミュレータ、コンパイル成功時のROM再実行。
- [cc65 NES target](https://cc65.github.io/doc/nes.html)：既存NES向けCツールチェーンの入口。FamiBASIC互換コンパイラではない。
- [JSNES](https://github.com/bfirsh/jsnes)：ブラウザ／Node.js組み込み、ROMバイト列ロード、描画・音声・入力API。
- [NESdev CPU memory map](https://www.nesdev.org/wiki/CPU_memory_map)：本体RAMとアドレス配置。
- [NESdev PPU programmer reference](https://www.nesdev.org/wiki/PPU_programmer_reference)：描画制約とPPU操作。
- [NESdev PPU palettes](https://www.nesdev.org/wiki/PPU_palettes)：背景・スプライトの色構成。
