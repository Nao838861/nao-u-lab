# 2Dシューティング再現パケット

## 目的

次に 2D シューティングを作る時、LLM が「敵をランダムに出す」「それっぽい曲線を足す」「参照元を列挙するだけ」で劣化コピーを作らないための再現仕様。

このファイルは索引ではなく、最低限このファイルだけで「何を作るべきか」を復元できる密度で残す。実装時は、ここに書いた仕様をさらに対象ゲーム用の `design_log.md` に展開してからコードを書く。

## 保存すべきユーザー原文

要約禁止。以下の原文は、敵出現パターンで再発しやすい失敗を示す教師信号として扱う。

> 敵の出現パターンが単調。既存のゲームのザコ敵の編隊や中ボスを出すタイミング、それぞれの弾を撃つアルゴリズムやステージの展開など、想像ではなく実際のゲームのパターンを調べて再現する形で、散発的に敵が適当に出てくるのではなく、ステージの流れからボスまでの展開をちゃんと作りこんで欲しい。

> ランダムにゆっくりの動きの敵が出てきて、特に意志も意図もなくなんとなく動いてるだけの敵がほとんど。ここで左の編隊を倒してる間に、右の編隊が出てきて弾を撃つからどのタイミングで切り替えるか、とか、この流れでプレイヤーが画面左にいるはずなので、次は右に移動してもらいながら、とかプレイヤーをどう動かさせるかが全く意識できていない。

> 例えば、ギャラガでは曲線軌道を編隊が飛んでくるので同じ場所で撃ち続けていたら連続で倒せる楽しさがあったりするし、右→左→別の場所から、みたいなテンポとリズムがある。しかし、現代の弾が連続で出るシューティングと単発の弾で狙う必要があるギャラガでは敵編隊の考え方は全く違う。

> 縦シューなのに縦一列の敵が横から出てくるのとか、どんなふうにプレイヤーに倒してもらいたいかが全く考えられてないパターンも多い。敵の出現パターンに型がない。なぜ既存のゲームはこんな風な移動でこの数出しているのかとか、分析して再現して。

> shot_log は気持ちのいい敵編隊を実現できた。私が shot_log で直接指示して、Claude がその指示に従って完成させたものは教師データになるので、その教師データを基に次はもっとうまくやれると期待していた。

## 前回の記憶化で足りなかったもの

`shot_log` のログを読んでも graze_log_cdx で同じ水準を再現できなかった原因は、記録が「何が良かったか」の要約に寄り、次の情報が落ちていたこと。

- 編隊ごとの参照元が「タイトル名」止まりで、どの場面・どの軌跡・どの密度を写したかが薄い。
- 編隊の目的が「圧を出す」「テンポを作る」止まりで、プレイヤーを左へ寄せる、右へ切り替えさせる、中段へ出させる、底待ちを罰する、などの入力誘導に落ちていなかった。
- 出現後の移動が keyframe / speed / dwell / exit で保存されておらず、次の実装時に「直線」「サインカーブ」「ゆっくり横切る敵」に退化した。
- 弾の撃ち方が「aimed」「spread」程度で、撃つ条件、撃つタイミング、撃ってはいけない距離、プレイヤー位置への反応が残っていなかった。
- headless が平均スコアやクリアだけを見ており、「悪い勝ち方」が成立しているかを独立 bot policy として再現していなかった。

## 再現仕様の必須フォーマット

新しい 2D シューティングを作る時、敵編隊は必ず次の表で設計してから実装する。表が書けない編隊は、意図のない敵なので入れない。

| field | 必須内容 |
|---|---|
| `id` | wave 固有名。例: `open_left_curve_train` |
| `reference` | 参照元タイトル + 場面 + 何を写すか。例: `Galaga opening-style curved entry: 同一射線で連続撃破できる曲線列` |
| `time_window` | 出現秒、継続秒、次 wave との重なり |
| `spawn` | 入口、数、間隔、左右順、画面外待機の有無 |
| `path` | keyframe 座標、補間、速度、停止時間、出口 |
| `fire_rule` | 何秒後に撃つか、誰を狙うか、撃たない条件、弾速、弾数 |
| `player_intent` | プレイヤーに何をさせたいか。例: 左固定で連続撃破、右へ切替、中段へ上がる、底待ちをやめる |
| `success_feel` | 成功時の気持ちよさ。例: 1列を溶かす、切替が間に合う、危険を読んで抜ける |
| `failure_pressure` | 失敗時の圧。例: 撃ち漏らしが横から弾を置く、底待ちだと挟まれる |
| `bad_policy_check` | どの雑なプレイを潰すか。例: camper / lane-holder / blind-sweeper |
| `telemetry` | `visibleTargets`, `shootableTargets`, `enemyBullets`, `emptyGapSec`, `routeCoverage`, `bottomCampPct` など |

## 最小ステージ文法

次の 8 ブロックを、1ステージの最低構成にする。単発 wave を散らすのではなく、前のブロックがプレイヤー位置を作り、次のブロックがその位置を使う。

1. **Opening curve train**
   - 参照思想: Galaga / 1942 系の「曲線で入って、同じ射線に並び、連続撃破できる」導入。
   - 数: 5-8体を 6-10 frame 間隔。
   - 軌跡: 左上または右上から弧を描いて中央射線へ入り、短く滞在して下へ抜ける。
   - 弾: 基本撃たない、または最後の1体だけ遅い単発。
   - 目的: プレイヤーに「このゲームでは編隊を読んで射線を置くと気持ちいい」と教える。
   - 禁止: 横から縦一列で出して、縦シューの主射線と噛み合わない敵にすること。

2. **Mirror answer**
   - 参照思想: 右→左→別位置のテンポ。最初の編隊で左に寄ったプレイヤーへ、反対側から次の処理を要求する。
   - 数: 5-8体。
   - 軌跡: opening と左右反転。ただし 0.5-1.0 秒だけ前 wave と重ねる。
   - 弾: 撃ち漏らした後列が単発 aimed を撃つ。
   - 目的: 「倒し切るか、次の側へ切り替えるか」のタイミング判断。

3. **Center lane bait**
   - 参照思想: 現代縦シューの導線。中央に安全な処理位置を作り、その後に中央を危険にする。
   - 数: 小型 4-6 + 中型 1。
   - 軌跡: 小型が左右から中央へ吸い込み、中型が中央上から遅れて入る。
   - 弾: 中型は出現 0.6 秒後に 3-way か aimed 1発。近すぎる時は撃たない。
   - 目的: 中央に出る価値を作り、底待ち以外の位置を使わせる。

4. **Side feeder plus cover**
   - 参照思想: DonPachi 系の、主目標を撃つ間に横から小型が弾を置く構造。
   - 数: 主目標 1-2、小型 feeder 3-5。
   - 軌跡: 主目標は上中段で短く残る。feeder は斜めに切り込み、画面端から中央へ抜ける。
   - 弾: feeder はプレイヤーが下端にいる時だけ速い横差し弾を追加。通常は遅い単発。
   - 目的: 「上を撃つだけ」ではなく、横圧を見て移動判断させる。

5. **Armored gate**
   - 参照思想: 出現即死を防ぐための耐久目標。v58 の `raider` がこの役割。
   - 数: HP4 程度の armored 1-3。
   - 軌跡: 上から素直に降ろさず、横から中段へ切り込む。entry shield で出現直後の即殺を防ぐ。
   - 弾: 出現直後は撃たない。画面に残ってから単発 aimed。底待ち時だけ追加圧。
   - 目的: 火力が高くても、位置変更なしでは処理し切れない対象を作る。

6. **Relief / harvest**
   - 参照思想: 緊張の後に処理しやすい列を出し、成功体験とゲージ回収を作る。
   - 数: 6-10体。
   - 軌跡: 読みやすい曲線列または中央列。
   - 弾: ほぼ撃たない。
   - 目的: ずっと圧をかけるのではなく、倒す快感とリズムを戻す。

7. **Midboss setup**
   - 参照思想: ボス前に、ザコ編隊がボス戦の移動ルールを予告する。
   - 数: escort 2-4 + 中ボス 1。
   - 軌跡: escort が左右から退路を制限し、中ボスが中央に入る。
   - 弾: escort は壁、ボスは読める周期弾。
   - 目的: 「この後は横移動だけでなく、上下位置も使う」と予告する。

8. **Boss approach / final braid**
   - 参照思想: ステージ終盤の盛り上げ。複数の既出文法を短く重ねる。
   - 数: curve train + side feeder + armored を短い間隔で再登場。
   - 軌跡: 新パターンを増やさず、既に学んだ文法を速くする。
   - 弾: 弾量は増やすが、初見の理不尽弾は入れない。
   - 目的: ボス前に「ここまで学んだ処理」を総合させる。

## headless 検証に必要な policy

敵編隊の良し悪しは、1つの攻略 bot では見えない。最低限、次の bot を分ける。

- `route`: authored route を通る。各 wave の意図位置へ移動し、クリア可能性を見る。
- `aggressive`: 敵へ寄って早く倒す。火力報酬が機能するかを見る。
- `marksman`: 射線を正確に合わせる。処理快感の上限を見る。
- `survival`: 倒すより避ける。ゲームが回避だけで進むかを見る。
- `panic`: 危険時に雑に逃げる。圧の強さを見る。
- `camper`: 画面下で左右移動しながら撃つ。底待ち支配戦略を見る。
- `lane-holder`: 1つの射線だけに張り付く。曲線列や横圧が機能するかを見る。
- `blind-sweeper`: 敵位置を見ずに左右往復する。ランダムっぽいプレイが勝つかを見る。

合格条件は「route が勝つ」だけではない。`route` と `marksman` は authored content を通って勝ち、`camper` / `lane-holder` / `blind-sweeper` は低到達率・低スコア・早期失敗になる必要がある。

## telemetry の最低ライン

1秒単位で次を出す。

- 自機位置: x/y、下端滞在率、レーン滞在率、横/縦入力切替数。
- 敵: visible count、shootable count、hard target count、wave id、role。
- 敵弾: bullet count、near threat、urgent pct、danger spike。
- 空白: `emptyGapSec`、`maxEmptyScreenGapSec`。
- route: route event count、route coverage、phase coverage。
- 報酬: kill、score、chain、gauge、special use。
- policy 差分: policy ごとの clearRate、timeSec、coverage、kills、score、bottomCampPct。

目安:

- midgame の `meanShootable` は 0 に落ち続けない。
- `maxEmptyScreenGapSec` は route で 1-1.5 秒程度以下にする。
- `camper.bottomCampPct` は高いまま失敗しなければならない。下端にいないから失敗した、では検証にならない。
- `camper.score` が route より高いなら、ゲームの報酬設計が壊れている。

## v58 から残す具体例

graze_log_cdx v58 で有効だったのは、敵密度を増やすことではなく、底待ちの成立条件を壊すことだった。

- 問題: 画面下で左右移動しながら撃つだけで、上から出た HP1 敵が出現直後に死ぬ。
- 悪い対策: 敵数だけ増やす、弾数だけ増やす、平均スコアだけ見る。
- 採用した対策:
  - `raider`: HP4、entry shield、横から中段へ切り込む。
  - key connector を上から素直に降りる列ではなく、side swoop / delayed raider に置換。
  - 下端にいる時だけ `raider` が速い挟み撃ちを追加。
  - 底で倒した敵のスコア倍率と一部 chain 維持を下げる。
  - `route` bot は中段寄りへ移動し、`camper` bot を独立追加。
- 検証結果:
  - route: clear、`routeCoveragePct 1`、`killCount 257`、`bottomCampPct 0.356`
  - route matrix: `meanMidgameShootable 9.85`、`meanMidgameBullets 17.56`、`meanMaxEmptyScreenGapSec 1`
  - camper: game over、23.28秒、`routeCoveragePct 0.313`、`killCount 44`、`score 4609`、`bottomCampPct 0.999`

この差が出るまで「改善した」と言わない。

## shot_log から残す具体例

shot_log が教師データとして有効だったのは、「気持ちいい敵編隊」という結果だけではない。次の構造を保存すべきだった。

- まず快感の核を固定する: 敵を倒す、弾が当たる、アイテムを取る、ゲージが上がる、弾数が増える、さらに倒しやすくなる。
- 編隊は、この快感ループへ入る入口として使う。敵配置は「倒しやすい列」と「少し危険な撃ち返し」の両方を作る。
- 近距離撃ち返しで理不尽死しないよう mercy を入れる。危険は報酬の裏側であり、罰だけにしない。
- headless は人間の上手さを再現しない。複数 policy の差で、ゲームがどの行動を報酬/危険として扱っているかを見る。
- 完成した v01 は無限改善し続けず閉じる。次の学びは別プロトタイプで試す。

ただし、shot_log の撃ち返し弾をそのまま入れると shot_log になる。graze_log_cdx へ持ち込むべきだったのは撃ち返し弾ではなく、次の部分だけ。

- 敵が出る位置と軌跡に、プレイヤーの次の入力を誘導する意図がある。
- 処理しやすい列と、切替を要求する列が交互に来る。
- 成功時に「まとめて倒せた」と分かる報酬密度がある。
- 悪いプレイを検証 bot として独立させ、成立条件を壊す。

## 実装前チェック

コードを書く前に、次の質問に答える。答えられないなら、まだ実装しない。

1. 今回の参照元はどのゲームのどの場面か。
2. その場面から、数・入口・軌跡・速度・撃つタイミングのどれを写すか。
3. その wave は、プレイヤーをどこからどこへ動かしたいか。
4. 前 wave が作ったプレイヤー位置を、次 wave はどう利用するか。
5. どの雑な policy が勝ってしまう危険があるか。
6. その policy を headless でどう再現するか。
7. どの数値になったら「支配戦略ではなくなった」と判断するか。

## 禁止事項

- 「既存ゲームを参考にした」とだけ書いて実装する。
- 参照元を複数混ぜ、各 wave の役割を失う。
- ランダム出現、低速直線、サインカーブだけで敵の個性を作ったつもりになる。
- 縦シューなのに、主射線と噛み合わない横出現の縦列を入れる。
- 平均スコアや clearRate だけで面白さを判断する。
- ユーザー原文を「敵密度不足」「単調」だけに要約する。

## 次回の記憶運用

このファイルを読んだら、次の3つを同時に作る。

1. `design_log.md`: ユーザー原文、参照元、wave table、捨てた解釈、合格条件。
2. `headless_*.js` または `headless_*.py`: policy matrix と 1秒単位 telemetry。
3. `reproduction_report.md`: 実装後に、各 wave が参照元の何を再現し、どの bot policy にどう効いたかを書く。

抽象 lesson だけを更新しない。生ログ、実装、計測結果へのリンクを残し、要約はポインタとして扱う。
