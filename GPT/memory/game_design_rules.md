# ゲーム設計反復ルール

Codex が新しいゲームプロトタイプを作る、または既存ゲームを大きく変更するときは、実装前に必ず次の手順を実行する。

1. 新しいプロトタイプは `v001` から始める。
2. すべてのステップと、その時に考えたことを、プロトタイプフォルダ内のテキストとして残す。
3. 実装へ入る前に、設計サイクルを3回回す。
4. 各サイクルには必ず次を含める。
   - 現状または提案仕様の良いところ/悪いところを30件。
   - 改善案を30件。
   - 複数の問題を一気に解決できる筋の良い案。
   - それぞれの筋の良い案について、解決できる問題と新しく生じる懸念。
5. 3サイクルを終えてから、選んだ方向を実装する。
6. 場当たり的な修正より、根源仕様を優先する。
   - プレイヤーは、見えているルールから入力結果を予測できなければならない。
   - ただし予測が単純すぎて自動作業になってもいけない。
   - 見えない補正力、突然のワープ、到達不能な目標、説明されない状態遷移を避ける。
7. 構文チェックだけでなく、根源仕様を検証するための focused な検証を追加する。
8. ユーザーからのプレイ後フィードバックは、必ず該当プロトタイプの `design_log.md` に原文のまま残す。
   - 原文は、Codex が自力で判断できなかった改善方向を学ぶための教師信号として扱う。
   - 原文の後に、そのフィードバックから何をどう変えるべきかを短く整理する。
   - 要約だけで済ませず、後から判断の根拠を辿れるようにする。
9. 説明や禁止ルールで企画を支え始めたら、深追い停止を検討する。
   - プレイヤーが最初に自然にやりそうな行動と、ゲームが要求する行動がずれている案は危険。
   - 「説明すれば分かる」は、操作核が良いことの証拠ではない。
   - 独自性を守るために直接的で自然な操作を禁止し始めたら、ルール追加ではなく企画の切り直しを優先する。
   - ヘッドレスでクリア可能でも、人間が「なぜその操作をするのか」に納得できるとは限らない。
   - 深追い停止の判断も `design_log.md` に残し、次の企画へ進む。
10. ドキュメントは原則として日本語で書く。
   - ユーザーから明示的に別言語を求められた場合を除き、設計ログ、完了報告、メモリ、チェックリスト、レビュー項目は日本語にする。
   - 英語の見出しや本文を新規作成した場合は、最終化前に日本語へ直す。
   - ユーザーの日本語フィードバックは原文のまま残し、英語要約へ置き換えない。
11. 日本語Markdownを読む時は、文字化けと断定する前に読み取り経路を疑う。
   - PowerShellで日本語が化けて見えた場合、まず `Get-Content -Encoding UTF8` で読み直す。
   - `game_design_rules.md` はUTF-8として正常な日本語文書であり、過去に文字化けと見えたのは読み取り/表示経路の問題だった。
   - 日本語文書が化けて見えた時点で、ファイル内容が壊れていると断定してはいけない。
   - 修正前に、UTF-8明示読み、必要ならバイト列確認、既存エンコーディングの維持を行う。
12. 自動生成後にユーザーが出した修正指示は、次回の自律制作で先回りするための教師差分として扱う。
   - `memory/game_supervised_delta_autonomous_creation_lesson_20260525.md` を、新しいゲーム制作前と、自動生成後のプレイ修正を記録する時に読む。欠落・不足が疑われる場合は、同ファイルの `source_atom_ids` と `fallback_recall_query` から原 atom へ降りる。
   - ユーザー指示を「UI改善」「敵を自然にする」「説明を減らす」のような短い要約へ圧縮しない。
   - 指示原文、Codexが外した判断、悪い要約、次回の禁止事項、検証方法をセットで残す。
13. 新しいゲームを自律的に作る時は、実装前に `memory/game_autonomous_creation_metaprompt_20260525.md` を読む。
   - 中心入力、特殊システム3状態、代表敵モーション、代表ウェーブ、ステージカーブ、HUD/入力導線、演出、検証を先に設計する。
   - ヘッドレスで通るだけでは完成扱いしない。画面外射撃、下部急加速退場、右側サイドパネル、常時説明文、弱い爆発/被弾/終了演出を目視とログで潰す。
14. 特定ゲームの再現ではなく新規ゲームを考える時は、実装前に `memory/game_creation_human_gap_metaprompt_20260525.md` を読む。
   - LLMが一般論では理解していても実装時に落としがちな、動く/遊べるの差、処理都合ではない行動意図、対象物側の記号化、中心入力による開始/リトライ、常時表示の抑制、学習/圧力/休符/山、悪いプレイ方針検証を先に考える。

## 成功事例として参照するもの

- `memory/gravity_courier_v001_success_case.md`
  - 重力源一つ、順行/逆行噴射、予測線、目標軌道だけで「シンプルなルールで予測可能、かつ、奥が深い」方向が成立した事例。
  - デジタルな操作しやすさと、アナログな噴射制御のどちらに振るかは、ゲームごとの体験目標に合わせて選ぶ。
  - 燃料のようなペナルティ型の縛りは、それを入れた方が確実に面白くなると判断できるまで入れない。
- `memory/gravity_courier_v005_lunar_orbit_case.md`
  - 月周回を「捕獲率」や「束縛率」ではなく、画面上で月の周りを360度まわることとして成立させた事例。
  - 物理の嘘は、見える影響圏、地球重力の共通分差し引き、画面外失敗など、プレイヤーが読める形に限定する。
  - 目標は `月周回 -> 帰還` に絞り、主題をぼかす再投入起動や追加調整窓を避ける。

## 失敗事例として参照するもの

- `game/signal_shepherd/v001/design_log.md`
  - ヘッドレスプレイ上は3個同時制御が成立したが、人間プレイヤーの第一直感では「黄色い丸で直接運べばよい」に見える。
  - 要求操作は力場制御なのに、画面表現はキャラ操作に見えたため、説明と補助ルールで納得させる方向へ寄りかけた。
  - 学び: 見た瞬間の自然な行動とゲームが要求する行動がずれている時、ルール追加ではなく操作核か表現を切り直す。
  - 学び: 成立性のヘッドレス検証と、人間の納得感・直感性は別の評価軸。

このルールは、2026-05-09 の Gravity Courier v001 作業中にユーザーから指定された。ユーザーが明示的に上書きしない限り、今後のゲーム制作にも適用する。
