# ゲーム設計反復ルール

Codex が新しいゲームプロトタイプを作る、または既存ゲームを大きく変更するときは、実装前に必ず次の手順を実行する。

1. 新しいプロトタイプは `v001` から始める。
2. すべてのステップと、その時に考えたことを、プロトタイプフォルダ内のテキストとして残す。
3. 実装へ入る前に、設計サイクルを3回回す。
4. 各サイクルには必ず次を含める。
   - 現状または提案仕様の良いところ/悪いところを30件。
   - 改善案を30件。
   - 複数の問題を一気に解決できる筋の良い案。
   - それぞれの筋の良い案について、解決できる問題と新しく生じる懸念。
5. 3サイクルを終えてから、選んだ方向を実装する。
6. 場当たり的な修正より、根源仕様を優先する。
   - プレイヤーは、見えているルールから入力結果を予測できなければならない。
   - ただし予測が単純すぎて自動作業になってもいけない。
   - 見えない補正力、突然のワープ、到達不能な目標、説明されない状態遷移を避ける。
7. 構文チェックだけでなく、根源仕様を検証するための focused な検証を追加する。
8. ユーザーからのプレイ後フィードバックは、必ず該当プロトタイプの `design_log.md` に原文のまま残す。
   - 原文は、Codex が自力で判断できなかった改善方向を学ぶための教師信号として扱う。
   - 原文の後に、そのフィードバックから何をどう変えるべきかを短く整理する。
   - 要約だけで済ませず、後から判断の根拠を辿れるようにする。

## 成功事例として参照するもの

- `memory/gravity_courier_v001_success_case.md`
  - 重力源一つ、順行/逆行噴射、予測線、目標軌道だけで「シンプルなルールで予測可能、かつ、奥が深い」方向が成立した事例。
  - デジタルな操作しやすさと、アナログな噴射制御のどちらに振るかは、ゲームごとの体験目標に合わせて選ぶ。
  - 燃料のようなペナルティ型の縛りは、それを入れた方が確実に面白くなると判断できるまで入れない。
- `memory/gravity_courier_v005_lunar_orbit_case.md`
  - 月周回を「捕獲率」や「束縛率」ではなく、画面上で月の周りを360度まわることとして成立させた事例。
  - 物理の嘘は、見える影響圏、地球重力の共通分差し引き、画面外失敗など、プレイヤーが読める形に限定する。
  - 目標は `月周回 -> 帰還` に絞り、主題をぼかす再投入起動や追加調整窓を避ける。

このルールは、2026-05-09 の Gravity Courier v001 作業中にユーザーから指定された。ユーザーが明示的に上書きしない限り、今後のゲーム制作にも適用する。
