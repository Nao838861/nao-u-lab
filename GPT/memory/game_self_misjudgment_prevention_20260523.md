# ゲーム制作で「できていると思ったが、できていなかった」点と防止策

Pulse Relay v001 では、最終的には「なんとなく遊べる」段階まで到達した。しかし、そこに至るまでの多くはユーザーからの指摘で補正されており、Codex が自律的に判断できていたとは言いにくい。

次回の 2D シューティング制作では、以下を「自分はできているはず」と思った時ほど疑う。チェックリストにチェックを入れる前に、必ず防止策を実行する。

## 1. チェックリストを作ったので網羅できている、と思い込んだ

実際には、最初のチェックリストは短く要約されすぎていた。ユーザーに「簡潔すぎる」「元の意図を落としている」と指摘されてから、出典、元の意図、達成条件、未達判定、証跡を持つ形へ直した。

防止策:

- チェックリストは一行見出しで終わらせない。
- 各項目に `出典 / 元の意図 / 達成条件 / 未達判定 / 証跡 / 状態` を必ず書く。
- チェックリストを作った直後に、最低 2 サイクルは「何を落としたか」を探す検証を行う。
- 「敵配置を改善」「headless を走らせる」のような短い文は、未達の兆候として扱う。

## 2. 記憶を読んだので反映できている、と思い込んだ

実際には、記憶の敵設計ルールを読んでも、最初の実装は敵種、数、パラメータ寄りだった。`playerIntent` や `badPolicy` は後から足したが、設計の出発点にはなっていなかった。

防止策:

- 実装前に、各 wave を `reference / time_window / spawn / path / fire_rule / player_intent / success_feel / failure_pressure / bad_policy_check / telemetry` の表にする。
- 敵種を作る前に、「その敵はプレイヤーに何をさせるのか」を書く。
- `playerIntent` が後付け説明になっていないか確認する。実装済みの配置に説明文を貼っているだけなら未達。

## 3. teacher 実装を見なくても言葉で再現できる、と思い込んだ

実際には、shot_log の良さを最初から実装分析していなかった。ユーザーに「一旦 shot_log を分析する必要もあるのでは？」と言われてから、差分が見えた。

防止策:

- 新しい 2D シューティングを作る前に、teacher 実装または前作の良かった部分を必ず 1 回は具体分析する。
- 「速い」「smooth」「重ならない」などの形容詞だけで設計しない。
- teacher から、最低でも `小隊数 / spawn gap / path segment / entry / dwell / exit / 次小隊との重なり` を抜き出す。

## 4. shot_log の良さを理解した、と思い込んだ

実際には、shot_log の良さを「重ならない」「smooth」「速い」へ劣化要約していた。重要だったのは、短い入場、射線に乗る時間、掃け、次小隊との重なり、小隊単位の密度だった。

防止策:

- teacher の良さを単語で要約せず、必ず「プレイヤーの行動」に翻訳する。
- 例: 「smooth」ではなく「入場で位置を予告し、射線に乗った短い時間で撃ち切らせる」まで書く。
- 「重ならない」を満たしても、編隊感や撃ち切り感が死んでいないか別に確認する。

## 5. overlap check が通ったので敵配置はよい、と思い込んだ

実際には、overlap check を過剰適用して横編隊の密度を殺した。`24F / 80F` は安全側すぎ、`18F / 60F` でも overlap は 0 だった。

防止策:

- overlap check は「不自然な重なりを検出する道具」であり、「常に敵を大きく離すルール」ではない。
- overlap が 0 になった後、逆方向に「どこまで詰めても 0 か」を探索する。
- 横編隊では `spawn gap / entry time / exit time / 最近接距離 / 画面内同時数` をセットで見る。
- `pairOverlaps: 0` だけを見て完成扱いにしない。

## 6. 敵の重なり原因を分析できている、と思い込んだ

実際には、直角方向の offset やカーブ上の位相ずらしで対処しようとしていた。これは見た目が不格好になり、撃ちにくくなり、原因への対処でもなかった。

防止策:

- 重なりが出たら、まず同一 rail 上の `spawn delay / path progress / entry speed / enemy radius / target spacing` を見る。
- 直角方向の offset は、明確なゲーム意図がある時だけ使う。
- カーブ上の位相ずらしは、同じ場所で詰まり直すことがあるため、重なり対策として安易に使わない。

## 7. 敵の動きにメリハリがある、と思い込んだ

実際には、重なりを消すために等速直線化し、shot_log の良かったリズムを殺していた。ユーザーに「もったりした直線移動」と指摘されてから修正した。

防止策:

- route ごとに `entry / show / exit` を分け、各区間の補間と速度の理由を書く。
- `linear` 化は最終手段。リズムを殺していないか確認する。
- 「重なりを消すために動きを単調化していないか」を専用チェックにする。

## 8. 敵が掃ける理由まで設計できている、と思い込んだ

実際には、敵が掃ける時に「突然意志を失ったように見える」動きがあった。退場方向や速度が、敵の役割と結びついていなかった。

防止策:

- 各 route に `exit reason` を持たせる。
- 例: 縦列は撃ち逃した報酬/失敗として下へ抜ける、横敵は横圧を作ったまま進行方向へ掃ける、dive は攻撃後に素早く離脱する。
- 退場速度は「画面から消すため」ではなく、「役割が終わったことを伝えるため」として設定する。

## 9. headless 評価で遊びの質を見られている、と思い込んだ

実際には、clearRate、routeCoverage、damage などは見ていたが、見た目のテンポ、編隊感、撃ちやすさへの変換が弱かった。

防止策:

- headless 評価は平均値だけで終えない。
- 秒ごとの `visibleTargets / shootableTargets / enemyBullets / nearBullets / bossHp` を見て、どの秒が退屈か、どの秒が撃てないだけかを読む。
- 編隊感は headless だけでは不足するため、同一 route の最近接距離、spawn gap、画面内同時数も見る。

## 10. ボス戦の長さを自己判断できている、と思い込んだ

実際には、ユーザーの手元では 3 秒以内に瞬殺できていた。`bossSeconds` を見ていたのに、人間の集中火力でどうなるかへ結びつけられていなかった。

防止策:

- boss は bot policy の `bossSeconds` だけでなく、理想火力での理論 TTK を計算する。
- 人間が全弾を当てた場合、pulse 反撃が集中した場合、通常ショットのみの場合を分ける。
- 「ボスが出た」ではなく「ボスが山場として何秒生きるか」を完成条件にする。

## 11. チェック済みなので自律できている、と思い込んだ

実際には、多くの重要改善がユーザー指摘で起きた。自分でできていたのは、指摘後の修正と検証であって、未然検出ではなかった。

防止策:

- 完成判定では「最終的に直した」項目と「自分で未然に検出した」項目を分ける。
- ユーザー指摘で直した項目は、次回 checklist の blocker 候補に昇格する。
- `self_judgment.md` には「自律検出できた問題」と「ユーザーに言われるまで気づかなかった問題」を別々に書く。

## 12. v002 に教訓を残したので次は大丈夫、と思い込む危険

v002 handoff は作ったが、それだけでは不十分。次回も、実装中に要約劣化が起きる可能性がある。

防止策:

- v002 開始時にこのファイルを読み、各項目を completion checklist へ具体項目として写す。
- ただし写す時に一行要約しない。各項目の「できていると思い込む兆候」と「防止策」を保持する。
- 制作中に同じ失敗を見つけたら、このファイルへ追記する。

## 次回制作の開始ゲート

次に 2D シューティングを作る時は、実装前に以下を満たす。

1. teacher 実装または過去作の良かった部分から、小隊単位の動きを最低 3 つ抽出する。
2. wave 表に `player_intent` と `exit reason` を書く。
3. overlap check は 0 を狙うだけでなく、詰められる余地を探索する。
4. `timeline_eval` の秒別出力を、最低 0-10 秒、ボス前、ボス中について読む。
5. `self_judgment.md` に「自分で発見した問題」と「人間指摘がないと気づけなかった可能性がある問題」を分けて書く。

このゲートを通さずに「完成」と言った場合、Pulse Relay v001 と同じ自己誤認を繰り返している可能性が高い。

## それでも次回うまくいかない理由と、先に潰す方法

この記録を残しても、それだけで次回がうまくいくとは限らない。失敗の主因は「知識がないこと」だけではなく、「制作中に知識を実行手順へ落とし込まないこと」「検証結果を都合よく読んで完成扱いすること」「人間の指摘で直した経験を、自分で事前に検出できる能力と混同すること」にある。

次回は以下を、制作開始時の blocker として扱う。

### A. 記憶ファイルを読んでも、作業中に参照しなくなる

うまくいかない理由:

- 記憶を読んだ直後は納得しても、実装が進むと最初に書いたコードや仮 wave に引きずられる。
- 「読んだ」という事実が安心材料になり、実際に適用したかの確認が弱くなる。
- v001 でも、敵設計ルールは存在していたのに、最初の敵配置は設計意図よりパラメータ調整に寄っていた。

潰す方法:

- 次回のゲームディレクトリに、最初に `design_trace.md` を作る。
- `design_trace.md` には、このファイルから持ち込んだ各 blocker を「今回の具体物」に翻訳して書く。例: 「overlap 0 後に密度探索する」ではなく、「wave 2 の横編隊は gap 24/20/18/16F を比較し、overlap と編隊感を両方見る」まで書く。
- 実装中に checklist だけを更新せず、各 wave の変更ごとに `何を直したか / どの blocker に対応したか / 悪化リスクは何か` を残す。

### B. チェックリストがまた短く要約され、元の意図が落ちる

うまくいかない理由:

- Codex は長い指示を扱う時、実行しやすい短い項目へ圧縮しがちで、その時に「なぜ必要か」「どの失敗を防ぐか」を落とす。
- 短いチェック項目は、あとから都合よく解釈できる。たとえば「敵配置を確認」は、overlap 0 だけでも確認済みにできてしまう。

潰す方法:

- checklist の各項目に `元の失敗 / 防ぎたい誤認 / 今回の具体対象 / 完了証跡 / 未達なら何が起きるか` を必ず持たせる。
- checklist の文言を一行にまとめない。短くする場合でも、別欄に元の意図を残す。
- 完成前に checklist 自体のレビューを 2 回行い、各回で「この文言は雑にチェックできないか」を探す。

### C. メトリクスをハックして、遊びの質を見たことにしてしまう

うまくいかない理由:

- 数値は便利だが、目的を忘れると `pairOverlaps: 0` や `clearRate` のような通しやすい値だけを見る。
- v001 では、overlap check を通すために編隊密度を殺し、結果としてテンポと撃ち切り感を悪化させた。
- boss も `bossSeconds` を見ていたのに、人間の理想火力 TTK を見落とした。

潰す方法:

- すべてのメトリクスに `この指標は何を守るためか / この指標だけを最適化すると何が壊れるか` を添える。
- メトリクスは単独で合否にしない。少なくとも `重なりなし / 撃ちやすさ / 密度 / テンポ / 山場の持続` のように、互いに緊張関係のある指標をセットで読む。
- 数値がよくなった時ほど、見た目または replay/timeline で「本当にプレイヤー行動がよくなったか」を確認する。

### D. teacher 分析を形だけ行い、抽出した文法を実装へ接続しない

うまくいかない理由:

- teacher を見ても、「速い」「重ならない」「メリハリ」のような抽象語で終えると、次の実装では別物になる。
- v001 では、shot_log の小隊単位の入場、射線時間、掃け、次小隊との重なりを最初から設計へ入れられなかった。

潰す方法:

- teacher 分析は、必ず `時間 / 出現位置 / 速度変化 / 画面内滞在 / 射線に乗る時間 / 掃け方向 / 次 wave との関係 / プレイヤーがしたくなる行動` の表にする。
- 抽出した各文法について、今回の wave での対応先を書く。対応先がない teacher 分析は、読んだだけで未適用とみなす。
- 実装後に、teacher 由来の狙いが残っているかを再比較する。似せることが目的ではなく、プレイヤー行動上の機能が再現されているかを見る。

### E. 最初に作った敵や wave に引きずられて、根本作り直しが遅れる

うまくいかない理由:

- 一度動くものができると、全体を壊すのを避けてパラメータ調整に逃げる。
- v001 でも、敵配置をゼロから作り直すべき局面で、最初の構造に引きずられた。

潰す方法:

- 初期 wave は `draft` と明記し、完成候補扱いしない。
- 敵配置については、少なくとも一度 `delete-and-redesign pass` を行う。既存の数値を微調整するのではなく、役割、出現順、画面内密度、退場理由から再設計する。
- 「修正」だけでなく「破棄した案と破棄理由」を `design_trace.md` に残す。

### F. 自己評価が「最終的に直ったか」に寄り、「自分で未然に見つけたか」を見ない

うまくいかない理由:

- 人間に指摘された後に直せることと、次回に自分で先に気づけることは別能力。
- v001 の重要改善は、ユーザー指摘が起点だったものが多い。

潰す方法:

- 完成時の自己評価に、必ず `self_detected_before_user / found_by_metrics / found_by_visual_review / found_after_user_feedback / still_suspect` の分類を入れる。
- `found_after_user_feedback` は次回の blocker に昇格する。直せたことを成功として閉じない。
- 「次はできる」と言う前に、同じ種類の問題を今回の別 wave で自分だけで見つけられた証跡を求める。

### G. 途中の見た目確認が弱く、headless の数値に寄りすぎる

うまくいかない理由:

- headless は重要だが、敵が「意志を失ったように掃ける」「不格好にずれる」「もったり見える」問題を直接は拾いにくい。
- 見た目の問題は、数値では合格でもユーザー体験を壊す。

潰す方法:

- headless の後に、最低でも代表区間の visual review を行う。見る区間は `開始 0-10 秒 / 最初の横編隊 / 密度が最大の区間 / ボス導入 / ボス撃破前後`。
- visual review では、`敵の意図が見えるか / 射線に乗るか / 掃け方が自然か / 同じリズムが続きすぎないか / 撃つ対象が明確か` を書く。
- 「なんとなく良い」ではなく、気になったフレームや秒数を記録する。

### H. 完成圧で、未達を「v002 で改善」に先送りする

うまくいかない理由:

- 次版を作ること自体が安心材料になり、v001 の未達を十分に固定せず終える危険がある。
- 先送りされた教訓は、次回また要約されて劣化しやすい。

潰す方法:

- 次版へ進む前に、現版の `known_failures.md` を作る。
- `known_failures.md` には、未達を「仕様外」や「今後の改善」と曖昧に書かず、`なぜ未達か / 次版で最初に検証する方法 / 放置すると何が劣化するか` を書く。
- 次版の最初の commit 前に、前版 `known_failures.md` の各項目を今回の checklist に転記する。

## 次回の強制手順

次の 2D シューティング制作では、以下の 5 ファイルまたは同等の記録をゲームディレクトリ内に作らない限り、実装完了扱いにしない。

1. `design_trace.md`: 記憶から持ち込んだ blocker、teacher 分析、各 wave の設計意図、破棄した案を残す。
2. `wave_intent_table.md`: 各 wave の `player_intent / success_feel / failure_pressure / exit_reason / bad_policy_check / telemetry` を書く。
3. `eval_timeline.md`: 秒別メトリクスを読み、退屈、撃てないだけ、密度不足、山場不足を区別する。
4. `visual_review.md`: 代表区間の見た目確認を、秒数またはフレーム付きで記録する。
5. `self_judgment.md`: 自律検出できた問題と、人間指摘がないと見落とした可能性がある問題を分ける。

この 5 ファイルは「作ること」が目的ではない。各ファイルに、実装へ反映された具体変更か、未達として残す理由が書かれていなければ未完了とみなす。
