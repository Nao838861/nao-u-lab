# Gravity Courier v005 月周回プロトタイプの経緯と教訓

日付: 2026-05-09

## 何の記憶か

`Gravity Courier v005` で、月の周回軌道をゲームとして成立させるために行った設計判断と、ユーザーフィードバックから得た教訓の要約。

今後、重力、軌道、月、二体問題、宇宙船、予測線、物理っぽいゲーム、学習できる高難度操作を扱う時に参照する。

## 出発点

v001 では、単一の地球重力と順行/逆行噴射だけで、シンプルだが奥のある軌道操作が成立することが分かった。ユーザー評価では「シンプルなルールで予測可能、かつ奥が深い」方向が成功とされた。

v005 では、その次の段階として「月へ行く」「月重力で捕まる」「月の周りを回る」を試した。

## 重要な失敗

- 最初は `捕獲率` や `束縛率` のような内部指標を見せようとしたが、ユーザーには意味が分かりにくかった。
- 「月の影響圏に一定時間いると成功」は、実際に月周回している感覚にならなかった。
- 月重力だけを強くしても、船だけが地球重力を受け、月はレール上を動く構造では、実際に月周回できる気がしなかった。
- 開始地点が月に近すぎると、地球を周回して月へ向かうゲームではなく、最初から月に吸われるゲームに見えた。
- 月周回後に再投入起動や調整窓を置くと、主題がぼけた。
- 半径で軌道外れ判定をすると、画面内に見えているのに失敗する可能性があり、直感に反する。

## 採用した根本仕様

- プレイヤーに見せる成功条件は「月の周りを360度まわる」。
- `捕獲率` や `束縛率` は表示しない。
- 月影響圏内では、船と月に共通してかかる地球重力を差し引く近似を入れる。
- 月周回の判定は、月中心で見た船の角度変化を累積する。
- 月面に近づきすぎたら失敗。
- 軌道外れは半径ではなく、船が画面外へ出た時に判定する。
- 失敗時は進行維持の再投入ではなく、最初からリセットする。
- 目標は `月周回 -> 帰還` の2つに絞る。
- 月は初期位置で船から離し、船がほぼ一周してから近づける配置にする。
- 画面は正方形にし、月の外側に余白を残す。

## 実装上の要点

- キャンバスは `1152 x 1152`。
- 月周回目標は `moonOrbitTargetAngle = Math.PI * 2`。
- 月影響圏は最終的に `influenceRadius = 220`。
- 月初期角度は最終的に `baseAngle = -2.8`。
- 月重力はゲーム用に誇張し、`moonMu = 900000`。
- `isOffscreen(ship)` で画面外判定する。
- `debugMoonOrbitProbe()` と headless チェックで、月近傍に実際に360度以上回れる軌道があることを確認する。
- headless チェックでは、開始後しばらく待ってから逆行噴射する単純操作で、月周回目標を通過できることも確認する。

## 学んだ設計原則

- 内部物理の正しさより、プレイヤーが画面から読めるルールとの一致を優先する。
- ただし、判定だけを分かりやすくしても、実際の挙動がそう見えなければ失敗する。見た目の運動と成功条件を一致させる。
- 「一周したら成功」のような自然言語と画面の動きが一致する条件は強い。
- 物理シミュレーションが完全でなくても、嘘の範囲を絞れば納得できる。今回の嘘は「月影響圏内で地球重力の共通分を差し引く」こと。
- ゲーム的な補正は、見える範囲と見える結果に結びつける。見えない吸引、見えないワープ、抽象的な率は避ける。
- 目標が増えると、主題がぼける。月周回が主題なら、月周回と帰還だけでよい。
- 失敗条件はプレイヤーが見て納得できるものにする。画面外へ出たら失敗は、半径だけで失敗より読みやすい。
- 開始直後の配置は重要。最初から目標に近すぎると、学習すべき軌道操作が消える。
