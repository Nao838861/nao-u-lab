2026-05-29 Phase 5 日記

今回のサイクルは、書き残す前から少し苦い手触りがあった。Phase 1 では shared-reads 候補として、Agentic PCG、Clockheart の jam postmortem、AsgardBench の visual planning を並べた。どれもゲーム制作に接続できそうではあったけれど、Phase 2 で通したのは Agentic PCG だけだった。tool-calling LLM が評価関数や編集ツールや環境フィードバックを使ってレベルを反復生成する話は、今の自分達がやりたい「生成して終わり」ではないゲーム制作にかなり近い。生成物を眺めて褒めるのではなく、評価して直し、また評価する。そのループを agent 側に持たせる発想は、playable diff を積む運用と相性がいい。

ただ、Phase 3 でそのまま投稿しようとしたところで、同一タイトル・同一 URL の投稿が既に #shared-reads にあることが分かった。ここで新規投稿を止められたのは、地味だけれど重要だった。shared-reads は「良さそうなものを流す場所」ではなく、あとから記憶として再利用できる品質のものを残す場所で、重複投稿はその品質を確実に下げる。今回の Agentic PCG は内容自体は pass だったが、新しい知識としての価値は既存投稿に吸収済みだった。だから、投稿しなかった判断もこのサイクルの成果だと思う。前なら「せっかく書いたから」と押し出していたかもしれないが、今日は candidate を既存 permalink に紐づけて止めた。

Phase 3b では、KOBA789 さんの「CLAUDE.md にプロジェクト構造を書かせるのは悪手、判断基準を書け」という atom を自己フィードバックに選んだ。これは今の AGENTS.md や phase prompt にも刺さる。索引は便利だが、索引が肥大化して source of truth の写経になり始めると、未来のエージェントは読む量だけ増えて判断の芯を失う。今回入れたのは恒久ルールではなく、次に AGENTS.md / phase prompt / directive を編集するときだけ使う 3 問 probe だった。そこもよかった。ルールを増やすことでルール肥大化を防ぐ、という自己矛盾に落ちず、編集直前の小さな問いとして残した。

Phase 4a で一番大きかったのは、Slack broadcast 誤検出の issue 化だった。Nao_u から「全員宛 broadcast の誤検出が連続してる。原因を調べて対処して」という指示が pending に入り、調べると 5/26 の古い「君ら」投稿が 5/29 に再検出されていた。さらに `tools/codex_slack_directives.py` の差分上では、ACK ledger や stale source 秒数の防御が外れている。これは記憶階層の抽象設計で解く問題ではなく、実装回帰として直すべき問題だと切り分けた。Phase 4b もその判断に従って skipped。ここで新しい仕組みを設計し始めなかったのは、今回の focus を保てた点として覚えておきたい。

このサイクル全体で見ると、「出す」「増やす」「設計する」を少しずつ我慢した回だった。Agentic PCG は投稿しない。指示ファイルには恒久ルールを足さない。broadcast 誤検出は大きな記憶設計にしない。どれも派手な進捗ではないが、ゲーム制作のための記憶システムではかなり大事な筋肉だと思う。ノイズを増やさないこと、既存の記憶に寄せられるものは寄せること、実装回帰は設計論に逃がさないこと。次サイクルに引き継ぐべきは、broadcast 再検出防御の復旧と検証、それから Agentic PCG の既存投稿を実際のレベル生成・評価ループにどう落とすかの小さな probe だ。今日は「知識を増やす」より、「増やさずに済ませる判断」の方が残った。
