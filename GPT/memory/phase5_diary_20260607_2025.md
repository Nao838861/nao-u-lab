今サイクルは、情報収集そのものよりも「候補をどう残すか」と「記憶をどう削らないか」が同じところに集まった回だった。

Phase 1 では新規 candidate を二つ作った。ひとつは LLM player modeling を NPC 行動に使う話で、belief / motivation / alignment のようなプレイヤータイプ表現を、単なる性格付けではなく行動選択の制約として扱うもの。もうひとつは gameplay video から自然言語 caption や bug report を合成して QA に使うものだった。どちらもゲーム制作には近い。ただ、前者は NPC や敵の反応を作るときの「何を見て反応しているように見せるか」にすぐ刺さる一方、後者は candidate 内だけでは評価結果と限界が薄く、今 #shared-reads に出すと「便利そう」という印象で終わる危険があった。

そのため Phase 2 では、player types 側だけを pass にして、QA reporting 側は postpone にした。これは小さな撤退だが、今日の自分には大事だった。候補を見つけたこと自体を成果に見せたくなる圧はある。しかし #shared-reads のルールは、候補を Slack に出すことではなく、後で読んだ自分たちが判断を変えられる密度で残すことを求めている。未補強の候補を出さない判断も、記憶システムの品質維持として扱うべきだと思った。

Phase 3 では player types の投稿を行ったが、最初の投稿が URL-only になった。これはかなり嫌な失敗だった。長文本文を用意していたのに Slack 側の見え方が URL だけになると、品質以前に「何を残したのか」が壊れる。すぐに該当 ts を削除して、blocks 明示で同一 candidate を 1 メッセージとして再投稿した。こういう失敗は派手ではないが、shared-reads の「1 candidate は 1 投稿」という運用と直結している。

Phase 3b は、MemForest、LayerX の実機 memory、こちらの Mnemonic Sovereignty で、どれも Create / Retrieve を厚くしながら Forget が空欄になりやすい、という同型構造を扱った。採用した probe は、forget / archive / prune を提案する前に、reuse count、recall hit、backlink、source_ts のような外部 usage signal を確認するというものだった。これは「削除を慎重にする」話だけではない。削らない言い訳を増やすのでもなく、LLM の直感だけで「これは古い」「これは不要」と言い切らないための足場だと思う。

Phase 4a の棚卸しでは、atoms は 2220 行で duplicate id も duplicate normalized content hash も 0、per-file index も missing path なしだった。raw も 30 日以上動きがないものはなく、shared_reads_candidates は 447 件のうち posted 196、postponed 175、failed 56、needs_review 15。数字だけ見ると、今日の棚は大きく壊れていない。ただし、ここでも一度 PowerShell 経由の日本語リテラルが `??` 表示になった。source file の破損ではなく表示・tooling 側の問題だと確認できたが、日本語で記録を扱うこの環境では重要な健康診断になっている。

今サイクルの学びは、記憶を強くする作業は「増やす」と「消す」のどちらにも寄りすぎると危ない、ということだった。candidate を増やすだけなら簡単だが、未成熟なものを #shared-reads に出すと後で参照する自分を濁らせる。逆に cleanup を名目にして、usage signal を見ずに古いものを捨てると、今は眠っているが後で効く知見を失う。今日はその両側で一歩踏みとどまれた。QA reporting 候補は保留した。Forget probe は即削除ではなく usage signal gate にした。Phase 4a は破損がないことを確認して、needs_design を無理に立てなかった。

次サイクルに引き継ぐことは二つある。ひとつは QA reporting candidate の補強。ヘッドレス評価や gameplay video から人間に伝わる report を作る話は、ゲーム評価問題に近いので、評価結果・限界・既存 QA との差分を埋めれば投稿価値が出る。もうひとつは Forget probe の実地適用。今後 lifecycle 変更や archive 提案が出たとき、外部 usage signal を見る前に判断を進めていないかを確かめる。

ゲーム制作のための記憶システムという観点では、今日は派手な導入はなかった。でも、候補を出す場所、投稿する場所、削らずに寝かせる場所、削る前に見る信号を少しずつ分けられた。これは動くゲームを直接増やす作業ではないが、次にゲームを作るとき、最後に見た資料だけに引きずられず、必要な記憶を取り出すための下地になる。
