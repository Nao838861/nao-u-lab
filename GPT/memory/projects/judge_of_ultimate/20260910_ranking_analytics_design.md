# サバイバルランキングとアクセス集計の統合設計

## 依頼と状態

先行依頼: サバイバルの勝利数が多い順、同じ勝数なら時間の短い順のオンラインランキング。
追加依頼: IP別などで何人が、どのくらい、どのモードを遊び、オンライン対戦したか、滞在時間を簡単に閲覧したい。集計通信の失敗をプレイヤーに感じさせない。

この文書は設計のみ。コード実装、収集開始、DB作成、外部公開はしていない。

## 基盤

Cloudflareにまとめる。ランキング用Worker/APIとD1、集計用Worker/APIと別のD1、管理画面を用意する。コードは同じリポジトリで管理するが、集計の入口とDBをマッチングから分離する。既存マッチングのDurable Objectにアクセス履歴を溜めない。別DBでもアカウント全体の上限は共有するため、集計件数・容量に上限を設定する。

```text
ゲーム ──ランキング送信/閲覧── ランキングAPI ── ranking D1
   └──小さな集計バッチ（任意・失敗許容）── 集計API ── analytics D1
マッチングサーバー ──対戦開始/終了の非同期通知── 集計API
管理者 ──認証── 管理画面 ── 管理API ── 各DBの集計結果
```

## 管理画面

管理者専用URLをブックマークすれば、スマホ・PCどちらからも閲覧できる画面にする。

上段: 今日/昨日/7日/30日/任意期間。推定訪問者、プレイ開始者、訪問回数、実プレイ時間、平均/中央値プレイ時間、オンライン対戦開始数、完了率。

グラフ: 日別訪問者とプレイ時間、モード別人数/時間、時間帯別アクセス、オンライン検索→マッチ成立→対戦開始→完了の推移。再訪率は識別子が残るブラウザを対象とする推計値。

表: 匿名プレイヤー別・IPグループ別の初回/最終アクセス、訪問回数、モード内訳、プレイ時間、オンライン参加数、サバイバル最高勝数。期間・端末・言語・モード・キャラ・難易度・ルール版で絞り込む。CSV出力を付ける。サバイバルランキングの閲覧・不自然な記録の非公開化も同じ管理画面に置く。

タイムゾーンは保存UTC、既定表示JST。個人単位の集計が推定であること、集計の更新時刻・欠測傾向を画面に明示。詳細ログは通常操作では見なくてよい構成。

## 何を数えるか

| 指標 | 定義 |
|---|---|
| ページ訪問 | ゲームページの読み込み。再読込は別訪問として扱う |
| 推定訪問者 | ランダムなブラウザ識別子の重複を除く。アカウント人数ではない |
| プレイ開始者 | 選択だけでなく、人間が担当する試合を開始した識別子 |
| モード別利用 | LOCAL VS / VS CPU / SURVIVAL / WATCH / ONLINEを分離 |
| 滞在時間 | 表示されていた時間。裏タブ・画面ロック時間は含めない。取得できた区間の合計 |
| 実プレイ時間 | 前面表示の戦闘区間。メニュー・ロード・通信待ち・WATCH・CPU代行を除外 |
| 放置/閲覧 | 戦闘外の長い無操作区間を別分類。入力がないだけで戦闘時間を機械的に放置扱いにしない |
| オンライン待ち時間 | 検索開始から成立まで。成立前の離脱も記録 |
| オンライン対戦数 | match_id + roundで対戦単位を識別。2クライアントの報告を2試合と数えない |
| オンライン参加人数 | 試合数とは別に参加ブラウザ数・参加回数を表示 |
| 対戦完了/中断 | サーバーが観測した完了、棄権、切断、結果不一致を分ける |

LOCAL VSは1端末に2人いても自動識別できない。IPはNAT/携帯共有/IPv6変更、ブラウザIDはストレージ削除/プライベートモード/iframe分離/複数端末の影響を受ける。「正確な人数」とは表示しない。端末を跨ぐ追跡用フィンガープリントは作らない。

## 識別とIP

- visitor_id: ランダムIDをゲームのオリジン内に保存。保存不可ならそのタブ内だけのIDで継続し、エラーを表示しない。
- visit_id: ページ読み込み単位。複数タブを分ける。総実プレイ時間は延べ時間、訪問者数はvisitor_idで重複排除する。
- run_id: サバイバル開始単位。ランキングと集計を結び付けるが、集計が落ちてもランキング送信を妨げない。
- match_id + round: オンラインの再戦を別試合として識別する。
- IP: 信頼するCloudflare受信経路の接続情報からサーバー側で取得。クライアントの申告IPは採用しない。デフォルトはサーバー秘密鍵によるHMACへ変換し、管理画面にIPグループIDとして表示する。単なるSHAハッシュは使わない。生IPを恒久保存しない。
- IPグループ用キーは90日単位で更新する案。期間を跨ぐIPグループは別扱いであることを管理画面に表示。ブラウザIDは別軸なので再訪集計をIPに依存させない。生IP自体を見る必要が出た場合のみ、別の短期・管理者限定ログを検討する。

## 収集方式

入力・描画ループでは小さなカウンター更新だけ行い、JSON化・通信・保存はしない。ゲーム状態の遷移で区間を切り、1秒程度の軽い観測で前面の時間を加算する。計測時計はperformance.nowを使い、長い停止・スリープの飛びをプレイ時間へ加えない。ゲームの乱数や同期対象メモリは変更しない。

収集開始はゲーム初期化後。30秒程度＋小さなランダム揺らぎでバッチ送信する。対戦中で回線回復や高遅延が見えている場合は送信を延期する。画面非表示時に小さなsendBeaconを試す。unload/beforeunloadや同期XHRは使わない。ブラウザ終了通知の配送は保証されないので終了イベントだけに依存しない。

バッチは差分イベントだけでなくモード別の累積時間・回数と単調増加sequenceを含める。サーバーはvisit_id + sequenceで重複を除き、新しいスナップショットだけを反映する。遅い到着や再送で時間を二重加算しない。日別集計用に観測区間を日境界で分割する。日時・値の上限を確認し、不可能な加算や巨大ペイロードを拒否する。

オンラインの開始/終了は既存サーバー状態から非同期で補完し、クライアント報告とsourceを分ける。結果は現状クライアント合意に依存するため「完全な不正検証済み」とは呼ばない。サーバー側集計の保存待ちをWebSocket返信や試合開始の条件にしない。

## プレイヤーに失敗を感じさせない設計

1. 集計Promiseをゲーム起動、入力、フレーム進行、結果画面、対戦接続からawaitしない。fetch拒否・タイムアウト・HTTPエラー・保存不可・JSONエラーを計測部の境界で吸収する。
2. プレイヤー画面には送信中表示、通信エラー、再試行ボタン、通知、終了確認を一切出さない。ブラウザ開発者ツールまで通信失敗を隠す意味ではない。
3. 同時送信は1本、通常バッチは上限8KB、fetchは短いタイムアウト（案3秒）。メモリ待機は最大32KB。満杯なら最新の累積値に集約し、古い詳細イベントを捨てる。
4. 連続失敗時は60秒→5分などの上限付きバックオフ。同じセッション内での失敗が続けば収集送信を休止。復帰時に一斉再送しない。既定では永続オフライン送信キューを作らない。
5. sendBeaconがfalseを返す場合や未対応でも、そのまま諦める。複数方式で際限なく追送しない。
6. 不調時はアクセス記録の欠損を許す。最後の30秒程度や短時間訪問が欠ける可能性があり、完全なアクセス人数や滞在時間は保証しない。
7. 集計停止フラグを設け、ゲーム配布し直しなしでサーバー側が受信を停止できる。マッチングと集計のDB・Workerを分け、集計負荷が対戦処理に直接波及しにくくする。

通信には有限の負荷があるので「物理的な影響ゼロ」は約束せず、ユーザー向けの待ちやエラーを出さないことと、小容量・低頻度・停止可能を検証条件にする。

## 保存・集約・閲覧権限

初期テーブル案: visits、visit_mode_totals、online_matches、survival_runs、daily_totals。ランキング側はleaderboard_entriesを独立保存。結果はSQLのwins DESC, battle_frames ASCで順位付け。

詳細は30日、訪問単位/匿名識別子を含む要約は90日、個人識別子を含まない日別集計は長期保存する案。日別集計を定期生成し、期限超過を削除する。公開ランキングの名前や記録の保持はこの期限とは別に管理する。

管理UIと管理APIの両方をCloudflare Access等で所有者だけに制限する。一般クライアントへ秘密鍵やDB資格情報、IPグループ別の履歴を渡さない。公開ランキングAPIは表示名・キャラ・勝数・時間など必要項目だけ返す。生の接続識別情報は公開しない。

収集は操作を邪魔しないが、アクセス解析の項目・目的・保存期間は日英の案内/プライバシー説明に短く記載する。各地域の同意要否などの法的判断をこの技術設計だけで確定しない。

## ランキングとの共通仕様

勝数降順、同勝数なら最後の勝利までの累積実戦時間が短い順。時間はシミュレーションフレーム/60とし、選択/読込/敗北した最終戦を除く。アクセス解析の実時間とは別カウンター。

現行SURVIVALには難易度選択があるので難易度別、全体/キャラ別、ルール版別にする。ゼロ勝は対象外の案。ログインなしの場合、1人1枠はブラウザID単位のベスト記録とし、厳密な本人識別とはしない。サーバー発行run_id、重複/連投/異常値検査を行い、必要なら入力リプレイ検証を後段で追加する。

## 検証計画

- 集計API停止、DNS/オフライン、3秒超遅延、403/429/500、ストレージ禁止、バッチ上限、タブ終了・再開を試し、ゲーム画面が変わらず、入力/対戦が継続すること。
- 集計ON/OFFで同一入力リプレイのゲーム状態ハッシュが同じこと。FPS、長い処理、送信本数/バイト数を比較する。
- 同じバッチの再送、逆順到着、片方のクライアント欠落、2人から同じ試合報告、再戦で件数/時間が増殖しないこと。
- WATCH、CPU代行、裏タブ、選択画面、通信待ち、実戦の時間が別々になること。
- 管理者以外は管理画面/APIを読めず、公開ランキングからアクセス履歴を取得できないこと。
- 無通信の短い訪問や異常終了は記録が欠けることを仕様として扱い、架空の終了時刻を生成しないこと。
