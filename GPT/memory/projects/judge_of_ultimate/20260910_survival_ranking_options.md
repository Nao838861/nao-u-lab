# サバイバルのオンラインランキング方式検討

ユーザー依頼: 勝利数が多い順、同勝利数なら時間が短い順のランキング。Googleスプレッドシート、契約中のさくらインターネット、その他方式を比較。今回は検討のみで実装・外部設定変更なし。

既存オンラインはCloudflare Workers + SQLite-backed Durable Objects。ランキングの第一候補は既存WorkerにランキングAPIと独立したD1 DBを追加する方式。マッチング用DOの状態へランキングを混ぜず、読み取り・保存を分離する。既存インフラと運用を共用でき、SQLによる勝数降順／時間昇順の検索、集計、管理が容易。さらに構成要素を減らすなら独立したランキング用SQLite Durable Objectも候補。

Google Sheets + Apps Scriptは小規模な試作と目視管理に便利だが、公開ゲームの保存先としては実行上限、同時更新、公開APIと権限の扱いを自前で整える必要があり優先度は低い。DBからCSV出力してスプレッドシートで見る用途なら適する。

さくらは既存契約の種類が不明。レンタルサーバでPHP + MySQLが使えるプランなら十分実現可能で追加費用を抑えられる可能性がある。VPSなら実装自由度は高いがOS等の保守負担が異なる。契約内容を確認する前に無料・機能利用可とは断定しない。

ランキング仕様案:

- 勝数降順、同勝数は時間昇順。勝数・時間とも同じなら同順位。
- 時間は最後の勝利時点までの累積実戦シミュレーションフレーム/60。キャラ選択・読み込み・通信待ち・最後に負けた戦闘を除外し、同勝数で早く負けるほど有利になる問題を避ける。0勝はランキング対象外の案。
- 現行runtimeのjou_cpu_level_pendingはSURVIVALも含むため難易度を混在させない。難易度別、またはランキング用難易度固定。全キャラ総合とキャラ別、バランス変更ごとのシーズン／ルール版も検討。
- 名前・キャラ・勝数・戦闘フレーム・難易度・ルール版・run_idを保存。日英表示は同じデータから行う。ランキング送信失敗でゲーム自体を止めない。
- ブラウザ自己申告はDB方式を変えても改ざんできる。初期はサーバー発行run_id、重複・連投・不可能値の排除、CPU代行/デバッグ排除。強い検証が必要なら乱数seedと入力リプレイのサーバー再生を別途設計する。トークンだけでスコア真正性は保証しない。

2026-09-10確認の一次資料:

- https://developers.cloudflare.com/d1/platform/pricing/ : Free枠は読取500万行/日、書込10万行/日、保存5GB。インデックスにも書込が発生。Workerリクエストや実行料金は別枠。実契約と利用量未確認なので追加費用ゼロは保証しない。
- https://developers.cloudflare.com/durable-objects/platform/pricing/ : SQLite版DOはWorkers Freeでも利用可能。
- https://developers.google.com/apps-script/guides/services/quotas : 上限超過で実行停止。
- https://rs.sakura.ad.jp/function/mysql/ : レンタルサーバのMySQL提供はプラン確認が必要。
