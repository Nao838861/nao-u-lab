# サンプルシューティングを変更せずスクロール機能を拡張できるか

本調査に基づく採用仕様は [共通BGスクロール仕様](D:/HomeBrew/FamiBASIC_Turbo_main/docs/common_scroll_spec.md)。本書は調査方法と実測結果を保持する。

## 結論

**既存サンプルを移行せず、共通スクロールを別のビルド経路として拡張する方式なら実現可能。** 現在すでにビルド時の分離があり、実行時の判定追加は不要である。サンプルの仕様・BASIC・専用描画・RAM配置・フレーム待機を変更する必要はない。

共通機能を改変した隔離SDKで、保存済み最新版と新規生成最新版の両方を再ビルドした。どちらも変更前後で**ROM全体1,572,880バイトと全ラベル番地が一致**した。変更したコードを使う通常スクロールのROMは変化し、対照も成立した。

今回確認したのは追加機能の分離可能性であり、長いマップ・二軸スクロールの新しい共通実装そのものはまだ作っていない。

## ユーザー指示原文

> 他は多少許容するが、サンプルシューティングはギリギリ処理落ちしないように作ってるので仕様も実装も変えたくない。それが実現可能かどうか調査して。

前の「サンプルを共通APIへ接続して同速を確認する」提案は、この指示によって置き換わった。今後はサンプルを移植しない。通常制作でのAPIの簡潔さと、既存サンプルの専用実装の維持を両立する。

## 現行コードの分離点

対象SDK：`D:\HomeBrew\FamiBASIC_Turbo_main`、HEAD `f2ab22dcfbb515ec58736bb72ba716584b46b490` と調査時点の既存未コミット変更を含む。各実験では `famibasic/` と `runtime/` を `.tmp/` へ複製し、そちらを変更した。製品側・保存済みプロジェクトのファイルは変更していない。

| 接続点 | 確認内容 |
|---|---|
| `famibasic/project_background.py` の `prepare()` | `side_art_b` の専用変換を先に選び、共通素材経路へ流さず戻る |
| `famibasic/initial_graphics.py` の `enabled()` | 調査した両サンプルは準備前・準備後ともFalse |
| `famibasic/bg_scroll.py` の `selected()` | 調査した両サンプルは準備前・準備後とも対象マップなし |
| `famibasic/compiler.py:535` 付近 | 対象マップと初期素材生成の両方が有効な構成だけ `COMMON_BG_SCROLL=1` を定義し、橋渡しコードを組み込む |
| `runtime/kernel.s` / `runtime/fullscreen.s` | 共通機能の入口・NMI・IRQ・初期化への追加が `.ifdef COMMON_BG_SCROLL` 内。定義のないROMには命令自体が入らない |
| `famibasic/bg_render.py` の `common_settings()` | 既存BASICが描画を管理するゲームマップを共通設定から除外する意図が明示されている |

したがって、マップ寸法だけを見て自動移行する必要はない。通常制作向けの明示された方式で新ドライバを選び、サンプルは既存方式に留められる。

## 実行した分離試験

再現スクリプト：[probe_scroll_build_isolation.py](../../../tools/probe_scroll_build_isolation.py)。以下の実験を、保存済み版と `fresh_project()` が生成する最新版のそれぞれに実行した。

1. 入力をメモリ上に固定して、変更前のシューティングと通常横スクロールをビルド。
2. 隔離SDKの `runtime/bg_scroll.s` のIR領域末尾へ64バイト追加。
3. 隔離SDKの共有 `runtime/kernel.s` でも、`COMMON_BG_SCROLL` 条件内へNOPを1命令追加。共有ファイルを変更しても、非採用側の番地を動かさないことを確認。
4. 同じ入力から両ROMを再ビルドし、全バイトとラベル番地を比較。
5. 初期素材生成と共通スクロール生成を、呼ばれたら例外を出す関数へ一時置換。シューティングは同じROMを生成でき、通常横スクロールは意図した例外で停止することを確認。
6. メモリ上の入力と、元の保存済みプロジェクト全ファイルのハッシュが変わらないことを確認。

| 入力 | 共通機能組込み | 改変前後のROM | 全ラベル番地 | 共通生成禁止時 |
|---|---|---|---|---|
| 保存済みSIDE ART B | なし | 全バイト一致 | 一致 | 成功・ROM一致 |
| 新規生成の最新版SIDE ART B | なし | 全バイト一致 | 一致 | 成功・ROM一致 |
| 通常横スクロール（対照） | あり | 変化あり | 比較対象外 | 意図した例外 |

保存済み版の前後SHA-256：`b4d9fd00e547115390b7157e755e3f7f3a6f564b55a806369694451027cf9b50`。

新規生成版の前後SHA-256：`bb608b291930a12d054cc9d29e77b4ad8be6ea3a1fd94d9f9171acc9db04e7f5`。

結果の生データ：[保存済み版](scroll_isolation_saved_20261117.json)、[新規生成版](scroll_isolation_fresh_20261117.json)。両者は入力・SDK取得時点が異なるため、両者同士のROM一致は要求していない。それぞれ同じ入力・隔離SDKでの改変前後を比較した。JSONの `elapsed_seconds` はPCビルド時間であり、ゲーム実行速度の計測ではない。初期SAVはどちらにも生成されず、SAVの比較項目は両方未生成という意味である。

再現例（出力先は未作成のディレクトリを指定）：

```powershell
python tools/probe_scroll_build_isolation.py --sdk D:/HomeBrew/FamiBASIC_Turbo_main --project D:/HomeBrew/FamiBASIC_Turbo_main/build/basic_only/game --output .tmp/scroll_isolation_saved
python tools/probe_scroll_build_isolation.py --sdk D:/HomeBrew/FamiBASIC_Turbo_main --project D:/HomeBrew/FamiBASIC_Turbo_main/build/basic_only/game --output .tmp/scroll_isolation_fresh --fresh
```

## 拡張時に維持する境界

- サンプルのBASIC・専用描画・資源変換・テーブル順序・BANK配置・待機処理を変更しない。共通APIへの移植やラッパー呼出しの追加も行わない。
- 幅と高さだけでドライバを推測せず、既存の専用方式と通常制作向けの方式をビルド時に分ける。専用マップへ新方式の初期設定を自動追加しない。
- 新ドライバのコード、RAM予約、バンク構成、NMI/IRQの追加は、その機能を使用するビルドだけへ組み込む。全ROM共通の起動処理や予約領域を無条件に増やさない。
- 既存のBGSCROLLの構文を使えば、新命令追加による予約語・本体コンパイラの表変更を必須にしないで済む。サンプルが使う通常ランタイムの意味・出力は維持する。
- 将来の実装を採用するときも、同じ入力とSDK基準でサンプルのROM全体・番地の一致を確認する。変化があれば、FPSが同程度という理由では受け入れず、まず混入経路を修正する。

## この調査から言える範囲

ROM全体が同一なら、同じ初期RAM・入力・エミュレータ／実機条件におけるCPU命令、バンク配置、描画タイミングも同じになる。今回の変更はサンプルの実行経路へ追加コストを持ち込んでいない。

一方、新しい共通スクロール自体の処理時間・最大マップ寸法・二軸同時転送の上限は、実装後に別途測定する。今回の調査で全編プレイや物理実機試験、サンプルのFPS再計測は行っていない。実装も含めてサンプルを共通ドライバへ統一する要求なら、今回確認した無変更の条件とは両立しない。
