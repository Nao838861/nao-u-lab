# GOSUB／GOTO後の3バイトの余白（2026-10-04）

ユーザーが提示したBASIC 2880・2900・2910の逆アセンブルについて、生成元を確認した。
アプリ・コンパイラの実装は変更していない。

## 原因

本体コンパイラはバンク切替が不要な転送と、切替が必要な転送の命令領域をともに6バイトに揃える。
現行wide経路の根拠は `D:/HomeBrew/FamiBASIC_Turbo_main/runtime/wide_metadata.s:825` の
「Six bytes for both near and far transfers」と、同ファイル860～903行の出力処理。
従来のC経路も `runtime/frontend.c:587` の `bank_transfer()` で同じ方式を採用する。

切替不要の場合は3バイトの直接JSR／JMPと3バイトのEA、切替が必要な場合は
3バイトの `JSR bank_call`／`JSR bank_jump` と2バイトの行先アドレス・1バイトのバンク情報。
GOSUBではその前に共通の `JSR bank_enter` があり、戻るためのバンク等の状態を保存する。
後から未解決の行先を確定しても6バイトの領域が変わらないため、後続の配置を保持できる。

## 提示コードの読み方

- `$A424～A426` はGOSUBから戻った後に実際に実行される3個のNOP。3バイト・6 CPUサイクルのコストがある。
- `$A434～A436`、`$A463～A465`、`$A47B～A47D` も同じ余白。直前のJMPで別の場所へ移るため、この経路では実行されず、容量だけを使う。
- `.byte ... data / reserved` は `famibasic/native_export.py:234` の一覧生成の汎用表示。到達可能な命令として復号しなかったバイトをまとめて出す。関数末尾の規約を意味しない。
- `basic_2880_body` 等はBASIC行のラベルで、各行が独立した関数という意味ではない。
- この箇所のNOPはタイミング調整が目的ではなく、転送領域を固定長にするための埋め合わせ。

削減余地はある。ただし単にバイナリから消すと後続アドレスがずれるため、生成・参照解決・行位置情報の整合が必要。
NOPの2サイクルは利用中のpy65の `MPU.cycletime[0xea]` でも確認した。最適化や再ビルドはこの調査では行っていない。
