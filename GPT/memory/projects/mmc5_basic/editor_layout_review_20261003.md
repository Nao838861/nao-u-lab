## 仕様決定（実装状況は末尾を参照）

- 右端のIDE内実行画面は仕様から廃止する。実行表示は独立したエミュレータウインドウに統一する。
- エミュレータの初期倍率は3倍。NES映像部分は768×720で、タイトルバー・メニュー・窓枠が加わる。
- 倍率変更の入口はエミュレータウインドウのメニューへ移す。IDEの右端パネルは設定入口としても廃止する。
- エミュレータに一般的なメニューを設け、今後キーコンフィグ等を追加する方針。メニュー全体の詳細設計・実装は後回し。
- 編集ウインドウはフルHDモニタでの使いやすさを基準に仕様を検討する。
- 標準の編集配置はタブで1画面ずつ編集する方式。左右分割は必要なときに利用者が選ぶ。
- BASICの長い行は既定では折り返さず横スクロールする。必要時に表示の折り返しをONにできる。ソースの改行やBASIC行番号は変更しない。
- BASICの入力補完は入力中に候補を自動表示する。明示的な選択・確定で挿入し、Escで閉じられる。入力を勝手に書き換えない。
- BASIC行番号はソースの一部として直接編集し、必要なときに自動採番・RENUMの補助を使う。通常の編集で行番号・参照先を自動変更する方式は採用しない。
- F5実行時はIDEが管理するプロジェクト全体を保存してからビルド・実行する。
- 保存先が未指定の新規プロジェクトでは、初回F5で保存先を選んでから実行する。仮保存先への自動保存は採用しない。
- F5のビルド・起動成功後は、キー入力先をゲーム窓へ自動で切り替える。

## 編集ウインドウの設計前提

- 起動時の自動最大化は採用しない。4KでもフルHD程度の通常ウインドウで起動する。モニタ面積に比例して初期サイズを増やさない。
- 標準サイズで全編集タブの主要操作が十分使いやすいことを優先する。大きなモニタや縦方向の拡張を、操作の成立条件にしない。
- 通常のリサイズを許可し、余裕のある利用者は主に縦へ伸ばして見渡せる範囲を増やす。横方向や手動最大化を禁止する意味ではない。

## 当初の提案（検討時点では寸法・復元方式が未確定）

初期サイズは窓枠込み1800×960程度を仮基準とする。これは100%表示での候補値であり、現在のTkの `geometry()` にそのまま与える値ではない。1920×1080の画面上で窓枠・タスクバー・余白を確保できるか、実際の作業領域から確認して決める。収まらない環境では作業領域内に調整し、4Kという理由で基準より大きくしない。

Windowsの物理ピクセルとUIの論理サイズは区別する。高DPIで数値をそのまま論理サイズとして拡大すると4Kでも大きすぎる窓になる場合がある。一方、物理寸法を厳密に固定しながら文字倍率を尊重すると、表示できる情報量が減る。4Kの150%／200%表示では文字を小さくして帳尻を合わせず、利用者の表示倍率を尊重した標準配置が成立するかを確認する。物理寸法をどこまで固定するかは実画面評価で決める。

| 領域 | 標準サイズでの使い方 | 縦に伸ばしたときの効果 |
|---|---|---|
| BASIC | 1面編集を既定にし、左右分割は任意。長い行は横スクロール | 同じ文字サイズで表示行数を増やす |
| BG | 道具・素材とマップの編集範囲を標準サイズ内に配置 | 同じズームでマップと素材一覧を広く見渡せる |
| スプライト | 素材一覧・パレット・描画領域を集約。必須操作を画面全体のスクロール先へ追いやらない | 一覧の表示量を増やす。描画倍率は自動変更しない |
| 音楽・素材・テーブル | 操作ボタンと一覧・詳細を標準サイズ内に配置 | 一覧の表示件数を増やす |
| 出力ログ | 折りたたみと高さ調整を用意し、編集領域を確保 | 利用者が必要に応じて高さを増やす |

縦に伸ばした余白は編集領域へ配分し、ツールバー・ボタン・フッターの高さは維持する。文字サイズやドット絵のズームは窓の寸法と独立させる。リサイズだけでタブの構造や道具の位置を大きく切り替えない。

次回起動は前回の通常ウインドウのサイズ・位置を復元する案。モニタ構成変更で画面外になる場合は位置とサイズを作業領域内に補正する。「標準レイアウトに戻す」は通常の標準サイズへ戻す。最大化状態の次回復元は既定にせず、必要性を後で検討する。

エミュレータは別窓3倍を維持する。編集窓と独立して配置し、フルHDで双方を常時左右に並べることを標準サイズの条件にはしない。4Kでは空いた領域へ移動できる。エミュレータの映像倍率も編集窓のリサイズに連動させない。

確認項目は、フルHD100%／125%、4K100%／150%／200%での標準サイズ、同じ幅で縦だけ拡張した状態、モニタ構成変更後の復元。標準サイズで主要操作が隠れず、不要な余白や全体スクロールを避け、縦の拡張で表示範囲だけが増えることを確認する。

検討時のコードではBASIC・音楽・テーブルに伸縮する領域があるが、スプライトの描画Canvasは固定サイズ、BGの単独窓は1640×900であり、全タブ共通の標準サイズでの使いやすさは未検証。初期サイズの数値変更だけで完成とは判定しない。

今回は全体仕様の検討として決定事項と提案を記録した。アプリのコード・利用者設定は変更していない。確認はコード・git履歴・保存設定の読み取りであり、新規GUI起動や実画面のレイアウト測定は実施していない。
