# V3ベースのゲーム制作拡張・エディタ設計

2026-09-16 / 設計案、未実装・未実測。命令名は提案。

## 1. 製品の中心

**V3風BASIC＋6502コンパイラ＋キャラエディタ＋BGエディタで、実用的なファミコンゲームを作る。** 完全互換や元ROMの不具合再現は目標にしない。V3の行番号、整数、配列、文字列、基本制御を土台に、描画を短く予測可能に書けることを優先する。

最初の制作目標は、自作キャラが動く横スクロール画面、固定スコア欄、数段の遠景スクロール、破壊できるBG、BGMと効果音を持つ1ステージ。そのための道具を先に揃え、旧命令の網羅を先行させない。

## 2. フレーム単位の描画モデル

```text
BASICでゲームを更新
  ├ OAM配列へスプライトを書込む
  ├ 配列からBG更新をキューへコピー
  ├ 次のスクロール位置を指定
  └ ラスターテーブルを作成
              ↓ FRAME
VBlankでBG転送 → OAM DMA → スクロール復元 → ラスター設定を有効化
              ↓
画面表示中は固定機械語のIRQ処理がラスターテーブルを実行
```

主処理が作る「次フレーム」と、割込みが読む「表示中フレーム」を分離する。OAM・スクロール・ラスター表は二重化し、BG転送キューも所有者を切り替える。1byteの公開フラグを最後に書き、NMIは書きかけを一切参照しない。

### 命令契約

| 命令 | 動作 |
|---|---|
| `FRAME` | 保留中のBG転送とOAM・スクロール・ラスターを次のVBlankへ一括公開し、反映完了まで待つ |
| `VBFLUSH` | 保留BG転送だけをFIFO順に複数VBlankへ分けて消化し、完了を待つ。現在のOAM・スクロール・ラスターは維持 |
| `DISPLAY OFF` / `DISPLAY ON` | フレーム境界で描画の停止・再開。ロード画面や大規模初期転送用 |
| `FRAMECOUNT()` | フレームカウンタ。BASICの反復数とは独立 |
| `VBFREE()` | 作成中キューの空きバイト数 |
| `VBCOST()` | 作成中キューの見積り転送サイクル数 |

`FRAME`は同一VBlankに収まる転送だけを受け付ける。予算超過は公開前に`FRAME TOO LARGE`、キュー容量超過は予約時に`VB QUEUE FULL`。どちらも古い表示を維持する。自動で一部だけ反映してスクロールを先行させない。大量転送は`VBFLUSH`か描画停止で明示的に処理する。

転送の順序はFIFO。同じアドレスへの複数書込みも初期版では省略しない。`FRAME`の復帰後、作成側へ直前の表示状態を引き継ぐため、変更のないOAM・スクロール・ラスターは維持される。キューは空に戻す。

処理落ちで次フレームが間に合わなければ、前の表示状態とラスター表を再利用する。NMIはFRAME呼出しの有無にかかわらず動き、音・入力・フレームカウントを進める。未公開の描画状態は勝手に反映しない。

## 3. OAMを配列として扱う

### 基本API

| 記法 | 内容 |
|---|---|
| `OAM(index)=value` | 次フレームのOAM影配列へ1byte書込み。index=0..255 |
| `OAMSET slot,x,y,tile,attr` | 1スプライト分をまとめて設定。slot=0..63 |
| `OAMHIDE slot` | 指定スロットを非表示 |
| `OAMCLEAR` | 全スロットを非表示 |
| `OAMSIZE 8` / `OAMSIZE 16` | 全体の8×8 / 8×16モードを次FRAMEで切替 |
| `METASPR first,x,y,asset,pose,flags` | エディタで組んだ複合スプライトをfirst以降へ展開（第二段階） |

`OAM()`は通常DIMの対象ではない組込みBYTE配列。定数添字は直接storeへ落とし、動的添字も名前検索なしで処理する。16bit値からの代入は範囲検査し、意図的な縮小はU8で表す。8bit式そのものは案1の規則でwrapするため、代入時の範囲検査で落ちた桁を検出・復元しない。詳細は[8bit整数設計](integer_types_20260916.md)を参照する。

生配列の並びは **Y、タイル番号、属性、X**。例:

```basic
100 OAM(0)=79
110 OAM(1)=16
120 OAM(2)=0
130 OAM(3)=120
140 FRAME
```

これは画面座標(120,80)のスプライトを設定する例。OAMのYは実表示より1小さい。`OAMSET 0,120,80,16,0`ではこの変換を内部で行う。画面外の座標は隠す方針とし、上端の部分クリップなど実機で表せない状態を無理に再現しない。[OAM仕様](https://www.nesdev.org/wiki/PPU_OAM)

属性はパレット0..3、背景との前後、左右・上下反転を含むハードウェア形式を使い、名前付き定数も提供する。8×16時のタイル番号の下位bitはパターンテーブル選択であり、エディタの書出しと一致させる。

OAMのスロットは利用者が割り当てる。METASPRも自動的に既存スロットを奪わず、必要数を資源情報として公開する。旧V3のSPRITE/MOVEを追加する場合は、明示予約したスロット範囲だけを管理させる。同じフレームの同じスロットを両方式で更新する指定は診断する。

64個・同一走査線8個の制限を前提に、エディタに重なりヒートマップを表示する。自動ちらつき制御は選択機能で、OAM順を既定で入れ替えない。

## 4. BG更新を配列から予約する

### 転送とタイル操作

| 記法 | 内容 |
|---|---|
| `DIM BYTE tiles(31)` | 0..31の32要素。BASIC整数配列とは別の8bit配列 |
| `VBWRITE address,tiles(),offset,count,step` | 配列の連続countバイトを予約。VRAM側のstepは1または32 |
| `VBFILL address,value,count,step` | 同じ値を予約。VRAM側のstepは1または32 |
| `BGPUT page,tx,ty,tile` | 物理ネームテーブルのタイル1個を予約 |
| `BGROW page,tx,ty,tiles(),offset,count` | タイルの横一列を予約 |
| `BGCOL page,tx,ty,tiles(),offset,count` | タイルの縦一列を予約 |
| `BGPAL page,bx,by,palette` | 16×16単位のBGパレット領域を変更 |
| `PALSET index,color` | パレットの次フレーム値を設定し、転送費用に計上 |

```basic
10 DIM BYTE ROW(31)
20 FOR I=0 TO 31
30 ROW(I)=16
40 NEXT I
50 BGROW 0,0,12,ROW(),0,32
60 BGPUT 0,10,11,17
70 FRAME
```

**配列データは命令呼出し時にキューへコピーする。** 予約後に元配列を書き換えても予約内容は変化しない。これにより配列が別PRG-RAMバンクにあってもNMIがそのバンクを切り替える必要がない。元配列ポインタだけを渡すゼロコピー方式は初期版では採らない。

内部転送レコードはopcode、16bit転送先、count、step、payloadを持つ。countは内部では最大255、長い要求は安全に分割する。全レコード分の領域を確保してから予約を確定し、途中だけ追加しない。原配列と宛先範囲を事前検査する。

`VBWRITE`の初期対象はネームテーブル／属性の$2000..$2FFF。CHR-ROMへの書込みは拒否し、パレットはPALSETへ分離する。各レコードでPPUアドレスとincrementを設定し、終了後はスクロール用レジスタ状態を復元する。

BGROW/BGCOLは32×30タイルの範囲を越えたらエラー。次ページへの分割は上位のマップ機能で行う。汎用VBWRITEは明示アドレスのため属性領域にも書けるが、ページのミラーを解決して影データを更新し、BGPALとの併用で古い属性に戻らないようにする。

通常BGのパレットは16×16単位。BGPALは属性byteの該当2bitだけを変更し、他の3領域を保持する。BGエディタの8×8配置と色選択を混同させない。

## 5. BGスクロールと大きいマップ

| 命令 | 内容 |
|---|---|
| `BGLAYOUT HORIZONTAL` | 横に並べた2画面。物理的には2枚のCIRAMページを使う |
| `BGLAYOUT VERTICAL` | 縦に並べた2画面 |
| `BGSCROLL x,y` | 次フレーム先頭の表示開始位置を指定。更新はFRAMEで公開 |
| `MAPDRAW asset,mx,my,page,tx,ty,w,h` | エディタのマップ領域を展開・予約（第二段階） |
| `MAPGET(asset,mx,my)` | 論理マップのタイル／メタタイルIDを取得 |
| `MAPATTR(asset,mx,my)` | 論理マップの衝突・地形属性を取得 |

低水準BGSCROLLはピクセル単位の座標。HORIZONTALでは512×240、VERTICALでは256×480のリングとして正規化する。ハードウェアのY境界を256でwrapしない。負座標の剰余は非負になる規則を明示する。

**スクロール値の変更だけでは、画面外の新しい地形は転送されない。** 最初はBGCOL/BGROWを使って露出する列・行を更新し、同じFRAMEでスクロールを公開する。横スクロールのマップストリーマを次に実装し、縦と自由方向はその後。

HORIZONTAL / VERTICALはゲーム制作者向けの配置名であり、一般に呼ばれるhorizontal / vertical mirroringとは名称が逆になりうる。内部では$5105への実際の配線選択を保持し、ビルドレポートに対応を出す。

上位マップはワールド座標、物理VRAMリング、カメラ座標を分ける。初期の軸ごとのワールド座標は符号付き16bitの範囲で運用し、巨大マップは後段でチャンク番号＋局所座標へ拡張する。マップのタイルや当たり属性は描画用の影データとは別に持ち、見えていない地形も照会できる。

スクロール速度が転送能力を上回る場合は必要転送量を診断する。カメラのテレポートは描画停止して再構築する。HUDの固定は画面内の走査線分割で実現し、独立した第2BGレイヤーがあるかのようには扱わない。

## 6. ラスタースクロール

### BASIC側のAPI

```basic
100 RASTERCLEAR
110 BGSCROLL 0,0
120 RASTERX 0,48,32
130 RASTERX 1,112,64
140 RASTERX 2,176,96
150 FRAME
```

上部48行を固定し、以後の帯で横スクロール位置を変える例。`RASTERX slot,line,x`は「表示行lineから横位置xに切り替える」という画面側の意味にする。内部IRQカウンタ値をBASICへ露出しない。

| 命令 | 段階 | 内容 |
|---|---|---|
| `RASTERCLEAR` | 初期 | 次フレームのイベント表を空にする |
| `RASTERX slot,line,x` | 初期 | 指定行から横スクロールを変更 |
| `RASTERVIEW slot,line,x,y` | 次段階 | 指定行の先頭で表示するBG位置をx,yに変更 |
| `RASTERBANK slot,line,bank` | 発展 | BGのCHRバンク変更。対象描画モードを限定 |

初期の仮上限は16イベント、行1..239、イベント間隔8行以上。line=0はBGSCROLLで指定する。表をFRAME前に行順にソートし、同じ行の競合や間隔不足をエラーにする。8行間隔は性能保証値ではなく、実機計測後に調整する初期制約。

RASTERXは横位置のみを変え、Yは通常のPPU描画進行を維持する。RASTERVIEWのyは画面全体のオフセットではなく、分割行で見せるマップ上のY位置。フレーム先頭のYと混同しないようエディタにも分割位置を表示する。

### IRQ実装と制約

MMC5の$5203/$5204による走査線IRQを使い、読出しによるackと次イベントの設定を行う。走査線検出はPPUのアクセスに依存するため、描画OFFでは表を停止し、ONで初期化する。[MMC5の一次調査](https://forums.nesdev.org/viewtopic.php?t=658)

IRQは固定ROMの短い6502処理で、事前に変換したレジスタ値を読む。BASICのGOSUB、文字列処理、バンク切替、乗算器利用をIRQから呼ばない。NMIが新しい表を公開し、IRQは表示中の表のみ読む。

IRQが指定行で来るだけで、任意の時点にPPUレジスタを書いてよいわけではない。水平・垂直スクロールにはPPU内部のアドレスラッチと転送時点が関係する。とくに垂直分割は$2005/$2006の書込み列とタイミングを固定機械語で作る。[PPUレジスタ仕様](https://www.nesdev.org/wiki/PPU_programmer_reference)、[分割スクロールの実装報告](https://forums.nesdev.org/viewtopic.php?t=7784)

初期は横方向の帯スクロールから検証する。IRQ入口の遅延、実行中命令による揺れ、DMC DMAなどが境界位置に影響するため、DPCM再生との併用は別試験を通すまで保証対象にしない。1走査線ごとの波形スクロールは後段の専用高速モードとし、初期APIの16イベントから可能と推測しない。

MMC5のvertical split機能は左右に分割する別機能であり、今回の上下の帯スクロールの代用にはしない。

## 7. キャラエディタ

ユーザー回答「両方ほしい（まずPC版から）」により、PC版を先行し、ファミコン本体版も制作する方針で確定。UI基盤はまだ決めず、今回は画面やツールを実装しない。

### 必須機能

- 8×8タイルのドット編集、拡大、ペン、消しゴム、塗潰し、選択、コピー、左右上下反転、Undo/Redo。
- パレット4色表示。背景色とスプライト透明色を用途別に表示する。
- 16×16、16×32などのメタスプライト組立て、原点、パーツの相対座標、優先順位、アニメーションプレビュー。
- 8×8 / 8×16モードの見え方、消費OAM数、同一走査線の重なりを表示。
- タイルIDの固定と名前付き参照、使用箇所表示。削除・並替えでマップを壊さず参照更新。
- PNG入出力とNES 2bpp CHR書出し。PNGは取込み時に4色への対応を確認し、無言の色変換をしない。

32 KiB CHR-ROM案では総計2048個の8×8タイルを格納できるが、全部を一度に指定できるわけではない。編集上の資源IDと、表示中のCHRページ内番号を分離する。初期の通常描画はBGとスプライト各4 KiBセット（各256タイル）を基本とし、OAMSETのtileは表示中セット内の番号とする。

## 8. BGエディタ

- キャラエディタの同じタイル集を使い、ブラシ、矩形、塗潰し、コピー、Undo/Redoで配置。
- 標準は8×8タイル配置＋16×16パレット領域。メタタイルは16×16を基本に四つのタイルとパレットをまとめる。
- 画面サイズを超えるマップ、カメラ枠、画面端で更新する列／行、ネームテーブル境界を表示。
- 別レイヤーに当たり属性（壁、水、ダメージ、梯子など）と敵・アイテム配置点を保存。
- 当たり属性の見た目や配置点は制作補助で、実機に追加の表示レイヤーを作らない。
- 固定HUD領域、ラスターバンドの設定とプレビュー。1フレームあたりの転送概算を表示。
- エディタプレビューに加えて、同じ資源を組み込んだ確認ROMを生成してPPUでの結果を確認する。

MMC5の拡張属性による8×8単位のパレットは魅力的だが、初期の2画面スクロールとは別モードにする。ExRAMの属性は全ネームテーブルに同じ位置で適用され、CPUアクセスにもモード制約がある。単純に4画面分の自由な属性メモリとして使えない。導入時はVBlank中のExRAMモード切替・更新・復帰まで専用ドライバで管理する。[MMC5仕様](https://www.nesdev.org/wiki/MMC5)

## 9. 編集データとビルド

```text
game.project.json     バージョン、ターゲット、資源一覧、パレット、BASIC入口
art/tiles.json        タイルの安定ID、名称、4色インデックスの画素
art/sprites.json      ポーズ、原点、パーツ、アニメーション
maps/stage01.json     サイズ、メタタイル、属性、配置点、カメラ／バンド設定
src/game.bas          BASIC本体
build/                CHR、マップ、資源定数、ROM、検証レポート
```

各編集ファイルにschema_versionを付ける。元データはPC編集用の可読形式、ROM側はタイル・マップ・メタスプライト・属性のバイナリに変換する。タイルの物理配置最適化で安定IDを変えず、生成された資源定数へマッピングする。

リソース名はコンパイラがプロジェクトから取り込み、例としてHERO_IDLE等を定数として解決する。DIM BYTEのデータやROW/COL転送も同じ形式につなぐ。圧縮マップの展開・ROMバンク読出しは主処理で行い、NMIに復号させない。

本体エディタを作る場合は、編集中のCHRを表示できるCHR-RAMターゲットが必要。RAMバッファ上のタイルをVBlankで転送する専用経路を追加する。元のCHR-ROMターゲットへゲームを出力する際は、編集済みタイルをROM資源として焼き込める。PRG-RAMとCHR-RAMの容量は別々に指定する。

## 10. フレーム処理の資源予算

固定PRG-RAM 8 KiBの再配分案:

| 領域 | 予算 |
|---|---:|
| ネームテーブル＋属性の影2画面 | 2048 B |
| 作成／消化する転送キュー2本 | 2048 B |
| 次フレームOAMと表示状態の控え | 512 B |
| 16件×16byteのラスター表2本 | 512 B |
| 制御スタック | 1024 B |
| 音楽・入力・フレーム状態 | 1024 B |
| 一時領域・余裕 | 1024 B |
| 合計 | 8192 B |

CPU内部RAMの$0200にOAM DMA元の表示用256byteを置き、PRG-RAMの作成済みスナップショットからNMIでコピーする初期案。コピーとDMA両方の費用を見積りに含める。将来は内部RAMの二重OAMページへの配置でコピーを省く選択肢もある。

NMIの予算は、固定費（割込み出入り、音、OAMコピー＋DMA、スクロール復元）と転送レコードごとの最悪費用で計算する。キュー1 KiB全部を毎フレーム転送できるとは考えない。NTSCを初期対象とし、PAGE跨ぎ等も含むサイクル表からFRAMEの受付上限を決める。

IRQコードは固定ROM、表は固定RAM、専用ゼロページを使用する。NMIの遅延が表示期間へ漏れないこと、IRQ中のレジスタ保存、表示OFF中のIRQ停止を検査する。

## 11. 実装順序と合格条件

1. **最小コンパイラ**: BASICがROMになり、算術・分岐と画面出力を確認。本体での小規模コンパイルと再RUNの開始時間も初期から測定する。
2. **最初の制作一式**: キャラ／BGエディタの最小版、資源ビルド、BYTE配列、OAM、VBWRITE、FRAME。自作画像で操作デモを作る。
3. **横スクロール**: 2画面配置、BGCOL、属性更新、BGSCROLL。継ぎ目が壊れず、転送不足を検出できる。
4. **帯スクロール**: RASTERX、固定HUD、数段の遠景。行境界のずれを実機と独立したエミュレータで観測。
5. **ゲームの完成に必要な機能**: メタスプライト、地形照会、配置点、音楽・効果音。1ステージを作って命令の不足を修正。
6. **発展**: 垂直ラスター、密な波形、拡張属性、CHR-RAM、本体エディタ・本体コンパイラ。

最低限の検証ケース:

- 予約後の配列変更が転送へ混ざらない。キュー満杯でも半分だけ予約されない。
- FRAMEの予算超過では新OAMやスクロールだけが反映されない。
- 描画中にBASICが止まっても、最後のOAM・ラスター・音の状態が破損しない。
- BGの属性更新で隣接16×16領域の色を壊さない。ミラー先の書込みも影へ反映される。
