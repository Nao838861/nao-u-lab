# 8bit整数拡張の設計案

2026-09-16 / 提案、未実装。依頼: 「8bit整数を扱える拡張も欲しいね。どういう形式が適切だろうか？」

## 1. 推奨する宣言形式

**DIMに型名を追加し、単独変数と配列に同じ記法を使う。** 既存のDIM BYTE配列案を拡張する。

| 記法 | 範囲 | 1要素の保存量 | 主な用途 |
|---|---|---:|---|
| `DIM BYTE X` | 0..255 | 1byte | タイル番号、画面内座標、属性、入力ビット |
| `DIM SBYTE VX` | -128..127 | 1byte | 小さい速度、相対位置、移動方向 |
| `DIM INTEGER WX` | -32768..32767 | 2byte | ワールド座標、スクロール位置、添字、計算 |
| `DIM BYTE TILE(255)` | 各要素0..255 | 計256byte＋配列管理情報 | BG転送、地形、描画データ |

未宣言の数値変数は従来どおりINTEGER。括弧内はV3風の「最大添字」とし、0から含める。`DIM BYTE X,Y,TILE(255)`も受理する。文字列の`$`記法は維持する。

型はコンパイル時に固定する。スカラーの型宣言は初期化命令ではなく、実行開始時に0初期化する変数の宣言。使用前の宣言を必須とし、途中の再宣言や型変更をエラーにする。配列DIMの実行状態・境界検査は基本設計に従う。

名前への新しい記号接尾辞は追加しない。X@等の記号は短いが、初見で符号や幅が分かりにくい。AS BYTE形式も可能だが、既存案のDIM BYTEへ統一し、同じことを書く複数の文法を増やさない。

## 2. 計算と代入を分ける

**保存は8bit、式の通常の整数計算は符号付き16bitとして定義する。** BYTEはゼロ拡張、SBYTEは符号拡張して値を保つ。

```basic
10 DIM BYTE X
20 DIM SBYTE VX
30 DIM INTEGER NX
40 X=250:VX=10
50 NX=X+VX
```

NXは260。X+VXが途中で4に巻き戻ることはない。SBYTEの-1とBYTEの255を加えれば254、比較すれば-1の方が小さい。Cの暗黙の符号なし変換規則を持ち込まない。

8bit代入時は範囲を検査する。`X=260`や`VX=128`はエラー。定数ならビルド時、動的値なら行番号付き実行時エラーにする。失敗時に元の変数を変更しない。READ/INPUTやOAMへの代入にも同じ規則を使う。

式の途中でINTEGER範囲を超えた場合も通常のオーバーフロー。例えばBYTE同士でも200*200は40000となり、標準INTEGER式の範囲を超える。型の保存幅だけを見て「8×8の積なら必ず受理する」とはしない。符号なし16bitや32bit式は別の将来拡張とする。

FORの制御変数は初期版ではINTEGERに限定する。BYTEで0..255を回したときにNEXTで0へ戻り無限ループになる問題や、終了後の変数値の曖昧さを避ける。配列の添字もINTEGER式で計算し、ループ内のデータをBYTEで持つ。

## 3. 意図的に巻き戻す記法

| 関数 | 意味 |
|---|---|
| `U8(expr)` | INTEGERの下位8bitを取り、0..255として返す |
| `S8(expr)` | 下位8bitを2の補数の符号付きとして解釈し、-128..127で返す |

これらは通常の範囲検査付き代入と違い、**明示的な切捨て**。返値はそれぞれの範囲を持つINTEGER値として後続式へ参加する。

```basic
100 DIM BYTE PHASE
110 PHASE=255
120 PHASE=U8(PHASE+1)
```

PHASEは0になる。`U8(-1)=255`、`S8(255)=-1`。`U8(X)`は16bitのビット演算`X AND 255`と同じ結果で、意図を読み取りやすくする記法である。

U8/S8は引数の計算を無制限幅に変更するものではない。`U8(200*200)`は引数計算でエラーになる。コンパイラが下位8bitしか使わないと気付いても、必要な中間オーバーフローを勝手に消してはならない。

## 4. ゲームでの使い分け

```basic
10 DIM INTEGER PX,CAMERA,NX
20 DIM SBYTE VX
30 DIM BYTE ANIM,TILE(255)
40 PX=120:VX=1
50 NX=PX+VX
60 IF NX<0 THEN NX=0
70 IF NX>511 THEN NX=511
80 PX=NX
90 ANIM=U8(ANIM+1)
```

位置の制御と画面外判定はINTEGER、小さい速度はSBYTE、アニメーション位相やタイル番号はBYTEにする。ワールド座標をBYTEに押し込める必要はない。画面内と確認した後でOAMへ渡せばよい。

VBWRITE/BGROW/BGCOLの生データ引数はBYTE配列とし、SBYTE/INTEGER配列を同じものとしてreinterpretしない。必要ならBYTE配列へ明示変換する。OAM()も同じBYTE代入規則を持つ。

## 5. 速度への接続

言語仕様で16bit式と定義しても、常に2byte演算を生成する必要はない。

- BYTE代入・コピー、BYTE配列のロード／保存は1byteでよい。
- BYTE同士の大小比較は符号なし8bit比較へ落とせる。
- `PHASE=U8(PHASE+1)`は意味が一致するので8bitのINC等へ落とせる。
- 通常の`X=X+1`には255でのエラーを保つ処理を入れる。巻き戻ってから検査する形で変数を破壊しない。
- 範囲が証明できる場合だけ検査を省略する。SBYTEとBYTEの混在では符号を保つ。
- 配列の要素サイズが半分になり、固定領域に収めやすい。配列管理情報やバンク境界処理は別途必要。

最適化の成果は生成コードとサイクル数で確認する。BYTE宣言だけで、すべての式が必ず2倍速くなるとは保証しない。

## 6. 最低限の検証

- BYTEの0/255、SBYTEの-128/127、範囲外定数、動的範囲外と代入先の不変性。
- 250+10=260、BYTE255とSBYTE-1の加算・比較、200*200のエラー。
- U8の-1/0/255/256、S8の127/128/255、引数側オーバーフロー。
- BYTE配列の最大添字、配列サイズ、OAMへの変換、転送元の型不一致。
- BYTEのFOR制御変数が明確な診断になること。
- 最適化ON/OFFで結果とエラー位置が一致すること。

導入順はBYTEスカラー・配列・U8、続いてSBYTE・S8。どちらも標準のv3-game拡張として扱う設計案とする。
