# 横スクロールサンプル向け・既存マリオアルゴリズムの所在

2026-11-17。依頼は「以前自分がテストで作ったスーパーマリオのクローンのアルゴリズム」を探し、横スクロールサンプルで床・ブロックに衝突するマリオとして動かせるか調べること。今回は原典の特定と移植条件の調査まで。製品コード・サンプルは未変更で、BASIC上の速度は未測定。

## 原典と既存の移植版

- 利用者のGBA版：[MarioGBASample/test7/mario.c](D:/AI/Nao_u_BOT/Claude/game/MarioGBASample/test7/mario.c:51)。移動・ジャンプ・衝突・アニメーション・カメラがまとまっている。座標単位は `global.h` の `ONE=256`。地形取得は同フォルダーの `bgsys.c` の `getTile`、ブロックへの作用は `BlockHit` 呼び出しと `MoveBlock.c` を参照。
- 後のPython版：[study_platformer_01/core.py](D:/AI/Nao_u_BOT/Claude/game/study_platformer_01/core.py:789)。冒頭でGBA版からの移植と明記。描画なしで物理だけ動かせる。衝突対象の定義は [tilemap.py](D:/AI/Nao_u_BOT/Claude/game/study_platformer_01/tilemap.py:17)。
- 元画像はGBA版 `data/mario.bmp`、Python版 `assets/player.bmp`。128×64のパレット画像で、先頭6コマは16×16・4色。既存素材の変換元として使える。
- 既存の分析記録：[teacher_study_platformer_01_analysis.md](../../teacher_study_platformer_01_analysis.md)。

原典の動きを基準にする。Python版には後から大きいマリオ・アイテム・敵・カメラ変更などが加わっているため、現行Python版の全挙動を原典と同一とは扱わない。特に原典のカメラは画面左80pxを基準に前進追従、Python版は56〜104pxの範囲と左右追従。壁への座標補正にも差がある。

## 移すべき動き

| 要素 | 原典の値・処理 |
| --- | --- |
| 座標精度 | 1px = 256の固定小数点 |
| 歩き／Bダッシュ | 加速度12／17、最高速度384／640（1.5／2.5px毎フレーム） |
| ジャンプ | 初速−1024、横速度の絶対値が490以上なら追加−112 |
| 可変ジャンプ | 上昇中かつA保持中は速度へ−48、その後に重力78を加える |
| 落下 | 重力78、落下速度上限1280（5px毎フレーム） |
| 地上操作 | 逆方向への制動、入力を離した時の `vx*250/256` の摩擦、低速時の停止 |
| 衝突 | 頭・両足・進行側の胴体を地形に照会し、床・壁・天井で座標と速度を補正 |
| 表示 | 停止・歩き・ブレーキ・ジャンプ、左右反転 |

原典の `mario.c:150` 以降が衝突の中心。頭の衝突時に `BlockHit` を呼ぶため、天井に止まる処理とブロックを叩く演出・破壊は分けて移植できる。

## FamiBASIC側で必要な接続

現行 `famibasic/data/basic_templates/scroll-horizontal.bas` は固定したスプライトと自動横スクロール、上下キーによるカメラ移動だけで、主人公の物理や地形衝突はない。`jump.bas` の簡易着地処理を流用するより、見つかった原典の物理を移す方が依頼に合う。

1. ワールド座標に物理を適用し、描画時だけカメラ座標を引く。自動スクロールを主人公への追従に変える。画面の高さ・表示領域・端での停止はFamiBASIC側に合わせる。
2. BGの16×16ブロックの属性から、床・土・レンガ・アイテムブロックなどを固体として参照する表を生成する。雲・茂み・背景の丘などは通過させる。エディターのブロック属性 `tag` は存在するが、現行の共通BGスクロールに汎用の地形照会APIはないため、書き出しとBASICからの参照を接続する必要がある。
3. 表はワールド座標から引く。原典の `getTile` はGBAの描画用512×256領域を照会しているため、そのままでは長いマップに対応できない。CHR番号が非ゼロなら固体という判定も使わない。現行64×16ブロックなら1セル1バイトで1024バイト。
4. BASICの `INTEGER` は符号付き16ビット。ワールド座標を単純に256倍すると画面内のY座標でも桁あふれするため、整数ピクセル座標と8ビットの小数部に分け、速度は符号付き16ビットで保持する。精度を落とす必要はない。
5. 摩擦の中間値 `640*250` も16ビットを超える。`a=ABS(vx), q=a/128, r=a MOD 128` とし、絶対値を `q*125+(r*250)/256` で計算して符号を戻せば、途中の積を32767以下にして元の切り捨て結果を保持できる。負の座標加算での繰り上がり・繰り下がりは、BASICのゼロ方向への除算と区別する。

最高移動速度は共通BGスクロールの各軸8px毎フレーム以内に収まる。ただし、これはBG転送量についての見通しであり、物理・衝突を含むBASIC全体が60fpsで動くことを証明するものではない。移植後に実機相当のフレーム計測が必要。

## 今回の確認

既存Python版を描画なしで動かし、床・壁・天井だけの小さいマップで確認した。結果は [mario_algorithm_probe_20261117.json](mario_algorithm_probe_20261117.json)。製品BASICでの試験ではない。

- 歩き1.5px、Bダッシュ2.5px毎フレームに到達し、床に着地したまま走行。
- Aを1フレーム押すジャンプは28.2734375px、40フレーム保持は69.6875px上昇し、両方とも着地。
- 左端160pxの壁に対し主人公の左端144pxで停止。天井への接触で上昇速度が0になることも確認。
- 摩擦の16ビット向け分解は速度−640〜640の1281ケースで元の式と一致。途中の積の最大は31750。
- 整数座標と小数部の分離は速度−1280〜1280・小数部0〜255の655616ケースで値を保持。

結論：元のアルゴリズムと素材があり、床・ブロックに衝突する横スクロールサンプルへの移植は可能と判断する。未実施なのは製品への実装、BG属性との接続、原典とのフレームごとの挙動比較、BASIC上の速度測定。
