# 入門スクロールサンプルの2画面制限

依頼原文：

> FamiBasicTurboの縦スクロールと横スクロールのサンプルは、2画面より多いスクロールに設定できないのだがなぜ？

調査対象は `D:\HomeBrew\FamiBASIC_Turbo_main`、HEAD `f2ab22d` と開始時から存在した作業差分を含む現行ファイル。今回は原因調査のみで、本体のコードや既存差分は変更していない。

## 確認した原因

- `famibasic/bg_studio.py:1098`：長さの選択肢が `('1','2')`。現在値も最大2へ丸めて表示する。
- `famibasic/bg_render.py:26`：共通の背景書き換え方式は、縦256×240/480、横256/512×240だけを許可する。
- `famibasic/bg_scroll.py:29`：生成時に8×8チップ総数2048以下を要求する。1画面は32×30＝960チップ、2画面は1920、3画面は2880なので、3画面はこの上限も超える。
- `famibasic/data/basic_templates/scroll-vertical.bas:8` と `scroll-horizontal.bas:8`：BASIC自身も480px／512pxで座標Cを0へ戻す。

`docs/common_scroll_samples_20260926.md` と `docs/bg_render_modes_20260928.md` にも入門用共通処理の制約として記載されている。実行処理 `runtime/bg_scroll.s` は表示外の行・列を順次入れ替える方式であり、マップ長を2画面へ固定する必然性を表示方式そのものから説明するのは不適切。現在のサンプル向け実装・設定・生成契約の上限である。

## 拡張時の接続先

画面数の選択肢だけ、あるいはBASICの周回値だけを変更しても動かない。設定検証と生成容量を合わせて拡張し、マップ格納領域・バンク切替を確認する必要がある。実行側も行／列番号を1バイト状態と即値 `BG_LENGTH` で処理しているため、長距離化では座標の正規化・逆方向・周回・大移動を含めて見直す。既存Flight Labの長いステージはBASIC側が描画を管理する別経路で、共通サンプルへの自動切替対象ではない。

## 実行確認

現行の `validate_settings` に縦／横それぞれ1・2・3画面の設定を渡した。両方向とも1・2画面は成功、3画面は上記寸法制約の `ValueError` となった。長いマップを動かす改修やROM実行検証は行っていない。

## BASIC仕様の再確認と整理提案（未採用）

追加の依頼原文：

> BASICのこの辺りの仕様ってどうなってた？2画面を特別扱いすべきなのか、そうでないのか。シンプルな仕様にしたいが、どうするのが適切？

当初案 `game_extensions_20260916.md` 第5節では、低水準の2画面リングと上位の論理マップを明確に分けていた。現行 `docs/language.md:184` と `famibasic/manual_text/scroll.py` も、BGLAYOUTを横512×240／縦256×480の配置、BGSCROLLを次FRAMEの表示位置指定として説明している。通常ランタイム `runtime/kernel.s:1225` はこの範囲を処理するが、COMMON_BG_SCROLL構成では同じ命令から別の自動行列転送処理へ分岐する。入門サンプルは後者である。

別系統の `docs/map_runtime_api.md` はMAPOPEN／MAPCAMによる長い縦マップを提供する。MAPCAMは絶対Yを設定してフレームも進めるため、BGSCROLL＋FRAMEとは待機契約が違う。現行汎用MAPは横方向未対応であり、既存の全機能が一つの命令体系で統一済みとは説明しない。

提案は、通常制作での「マップの長さ」に2画面という区切りを設けず、マップ上のカメラ位置と表示更新だけを共通化すること。2026-11-17の追加指示により、既存サンプルシューティングはこのAPIへ移行せず、仕様・実装・出力ROMを維持する。共通機能は通常制作向けに独立して追加する。分離の実測は [変更しない条件での調査](20261117_scroll_isolation_report.md) を参照する。

- 通常の編集項目は幅・高さ・各軸の端の動作（停止／循環）。1・2・3画面以上に同じ契約を使う。カメラはX/Yの二軸を持ち、縦進行に小幅な横移動を加える既存サンプルも表現する。静止背景もカメラを動かさず使える。方向は制作用プリセットや内部の最適化に使い、BASICの座標指定を一軸へ制限しない。初版で保証するマップ寸法・移動量は実測に基づいて別に定める。
- 標準のBASICは既存サンプルに合わせ、BGSCROLLでドット単位の絶対カメラ位置を設定、FRAMEで表示を反映して待つ。フレーム待機は位置指定と分離する。新しいページ切替命令は不要。
- 停止はカメラの表示範囲をマップ内に収め、循環はマップ全長を周期にする。既存サンプルの循環を自動的に停止へ変更しない。周回値はマップ寸法から参照できるようにし、BASICへの480／512の重複記載を解消する。
- BGLAYOUTと物理ページ指定の描画命令は上級・互換用に残す。自動マップ使用時には内部配置をドライバが管理し、利用者による競合する設定は診断する。旧ソースの数値の意味を無条件に変更しない。
- 容量・座標幅・通常移動量・大移動の再構築は制約として明示する。2画面上限の代わりに無制限を約束しない。格納・転送の最適化はコンパイル時に選び、同じマップに対する命令の意味は画面数で変えない。現行の共通書き換え処理は2画面でも行列を転送している。

これは仕様整理の推奨案であり、採用決定や実装変更ではない。MAPCAM等の既存経路を廃止・変更する場合は互換方針を別途決める。

外部の技術確認：NESdevの [PPU scrolling](https://www.nesdev.org/wiki/PPU_scrolling) は、VRAMにある2画面を超える範囲を表示する際、表示外の列・行へ新しいデータを書いてからスクロールする方式を説明する。検索結果本文で確認（ページ直接取得は403）。表示用メモリの大きさとステージの長さを分ける根拠として使用した。

## 縦進行＋小幅の横移動を含める補正（未採用）

追加の依頼原文：

> サンプルシューティングで入れている縦スクロールしつつちょっと横にもスクロールできる仕様はどう扱う？

前回答の「初版は縦か横の一方向に絞る」提案は既存サンプルを表現できず、上記の現行提案を二軸カメラへ修正した。採用や実装変更はまだ行っていない。

既存の根拠：`experiments/horizontal_scroll_v001/README.md` は幅320px、横カメラ0〜64px、中央32px、最大1px/更新を記載する。後続 `docs/horizontal_screen_coordinates_20260928.md` は、自機と空中物を画面座標、地形攻撃をマップ座標へ変換する仕様を記録する。`docs/latest_game.md` は最新版の横カメラ0〜64を確認している。古い見積書だけを現在の実装と解釈しない。

論理画面幅256pxを基準に、横幅320px・停止のマップならカメラ範囲は0〜64pxとなる。既存表示の左8pxマスク等は別の表示制約であり、横可動幅を72pxへ読み替えない。通常の縦スクロールは横幅を画面幅にしてXを固定する同じモデルで表現できる。方向プリセットはこの幅・高さの初期値を用意する操作とする。

カメラの追従先・速度・停止はBASICのゲーム処理で決め、共通機能は指定されたX/Yに必要な背景更新を担当する。HUD、スプライト、敵弾の座標をBGSCROLLが自動変更する契約にはしない。画面座標かマップ座標かはゲーム側で選び、同じ座標の地形表示・当たり判定・破壊状態が整合するようにする。

二軸同時移動では行と列の転送が同じフレームに必要になりうる。現在の一軸用共通処理へX指定だけを足す改修ではなく、転送予算と隠す端、破壊済み地形を画面外へ出して戻す試験を含めて対応する。APIを二軸にすることと、任意の広さ・速度での自由スクロールを初版で保証することは区別する。

## 現行サンプルの仕様・速度維持の実現性（2026-11-17、実装前評価）

追加の依頼原文：

> これは、いまのサンプルシューティングの仕様と速度を変えずに高速に実現できるものか？

設計上は実現可能性があるが、新APIへ移行した生成コード・実ROMの速度比較は未実施であり、同速を確認済みとは回答しない。仕様の統一と、毎フレームの描画実装を一種類へ統一することを分ける。

`experiments/horizontal_side_art_b/make.py` は既定でBASIC描画を選び、`basic_renderer.py`・`row_cache.py` 等で固定幅・BYTE演算・固定アドレスの転送を生成し、BANK配置まで調整している。古い横スクロール試作のASMだけを現行実装として扱わない。新しいBASIC APIも、幅・高さ・資源配置・端の動作など事前確定した条件から必要な処理だけを生成する方針が適する。ゲーム名や特定の行番号を認識するコンパイラ最適化にはしない。横64pxの範囲、最大1px/更新、破壊属性の合成、キャッシュの更新方法、画面座標の敵・弾やHUDを一括で汎用16bit処理へ変換しない。

現行の転送順も仕様維持の対象である。`scroll_restore.py` と `docs/flight_lab_scroll_restore_20261003.md` は、PPU転送→スクロール復帰・OAM転送→ExRAM列補充の順へ直した履歴を持つ。単に最終的なカメラ座標が一致するだけでは足りない。共通FRAMEへ接続するときも待機の追加・入力更新のずれ・スクロール復帰期限の後退を起こさない。PPUレジスタ復帰の期限は [NESdev](https://www.nesdev.org/wiki/PPU_scrolling) でも確認した。

採用判定は、移行直前の編集済み最新版と同じ素材・入力・難易度・武器条件で、カメラ・地形破壊・当たり判定・HUD・ボス遷移を照合し、描画画素・PPU書込み時刻も検証する。速度は平均／ピークCPU時間、更新遅れ、描画締切を比較し、ROM/RAM量とBANK配置も確認する。機械語の命令が同じでも配置や呼出しが変われば速度は変わり得る。過去の固定測定を現在の性能保証へ流用せず、現行サンプルの安定60fpsを前提にしない。

この回答時点では既存経路を共通APIへ接続する案を提案していたが、後続の「仕様も実装も変えたくない」という指示で置き換わった。現行方針はサンプルを移行せず、通常制作向けの共通機能をビルド時に分離すること。より広い自由スクロールは別条件として性能を測定する。この節の時点ではソース・仕様・既存検証記録の調査のみで、分離の実測は次の調査記録に保存した。
