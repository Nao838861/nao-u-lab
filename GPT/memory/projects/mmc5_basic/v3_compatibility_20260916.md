# V3互換範囲の追加要求と検討

## ユーザー指示

> V3のBASICにある命令はほとんどすべてを網羅して。例外は、V3依存でどう考えても今回の実装には不要な物くらいにしておいてほしい。

> 一旦そこを検討してみて。

今回は互換範囲の調査・設計。実行コードの実装再開ではない。

## 成果物

[プロジェクト側の検討書](D:/HomeBrew/FamiBASIC_Turbo/docs/v3_compatibility_plan.md) に命令・関数・複合構文の候補台帳、コンパイラ設計への影響、除外候補を記録。READMEの完成方針も更新。

- 通常の言語機能、開発操作をほぼすべて対象にする。文字列、実行時DIM、DATA、STOP/CONT、エラートラップ、自動移動、PLAYを難易度を理由に除外しない。
- ファイル保存や保存枠はSAVE/LOAD/BACKUP等の目的を維持して接続。旧テープの物理信号や原版ROM内部の番地一致は別の非互換候補。
- GAMEや既定キャラは自作サンプル／素材へ置換する提案。原版内容の同梱は必要としない。
- **BGPUTが衝突**。現行拡張の1タイル書込に対して、V3ではBG復元用。V3側の意味を優先し、拡張は仮名BGTILEへ改名する案。コードはまだ改名していない。
- 行確定時のトークン化・解析結果保存、RUNの単純なコード生成、未編集コードの再利用を提案。100msはV3級ソースの通常編集後RUNについての性能試作目標で、合意済みの待ち時間でも実測でもない。
- STOP/CONTとエラー復帰には行・文位置、BASIC制御スタック等の管理が必要。現行CPUスタック中心の実装は見直し対象。

## 調査の限界

fbastool作者のトークン表、Micah CowanのV3解析、田中アイロンの解析、パレイドのV3印付き実行観察を参照。公式V3マニュアル全ページの照合と原版V3での独立検証は未完了。トークン一覧は完全な文法の証明にはならない。

SYSTEMのV3での有効性、複合ON分岐、保存の派生書式、関数の別名等は保留。V2の観察結果をV3へ無条件適用しない。台帳は候補として扱い、全命令確定や互換率をまだ主張しない。

変更は文書のみ。実装済み機能も意味が一致するまで互換対応済みと数えない。プロジェクトにはremoteがないため、コード側のpushは設定なしで失敗する。GPT側の記録は既存remoteへpushする。
