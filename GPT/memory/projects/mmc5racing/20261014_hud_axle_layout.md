# 摩擦円を前輪2つ・後輪2つへ整列

## フィードバック原文

> 4輪の荷重、ゲーム中は見えないからスプライト欠けてもいいので、横に並べてほしい。欠ける時には荷重の方が欠けて。あと、摩擦円の限界を超えたら円を赤くして。

続く訂正:

> ごめん、全部一列に並べるんじゃなくて、以前みたいに前輪2つ、後輪２つを並べてほしい。プレイヤーには被らない高さで合った方が良い。

最初の「横に」を全4輪一列と解釈して作業中だったが、訂正に合わせて前後2×2へ変更。一列版は未コミット・未公開で、最終成果物に含めない。今回は荷重のスプライト欠けを明示的に許容する指示であり、以前の全走査線8枚以内という配置制約より、この表示意図を優先した。

## 実装と起動

ユーザーが見た統合ROM `0b4c7d6` を基点に作業。チェックアウト `D:\HomeBrew\MMC5Racing_hud_horizontal`、ブランチ `codex/hud-axle-load`。名前にhorizontalが残るが、表示は前後2×2。commit `0f44fff20b04988e7edb6ad4d80cbd9e759669b2` を `Nao838861/MMC5Racing` の同ブランチへpush済み、終了時clean・ahead/behindなし。mainや別スレッドの新しい統合ブランチへは混ぜていない。

起動は `D:\HomeBrew\MMC5Racing_hud_horizontal\play_hud.cmd`。ROMは `build\MMC5Racing_HUD_Axles.nes`、Mesenで表示済み。SHA256 `43fb9feae43adfa7f1269af5b3be9a2ca168568bf72fb784551a13e9e84a4fab`。

上段は前左・前右、下段は後左・後右。円の左端X180/212、OAM Y119/151、可視下端167で、自車の表示開始168より上。円の大きさは従来の摩擦容量、白い点は制限前の要求力。飽和フラグ `$B4..B7` で円の両半分を白から赤へ変更する。CHRのplane0と既存palette3白/2赤を使い、車のパレットは変更しない。

## CPU車側へ渡すOAM契約

荷重の円56〜63を最も低い優先順へ移動するため、統合基点で58〜63だったCPU車3台を**40〜45**へ移動。自車48〜53・ゴースト4/11は維持。力の点15/19/23/27、状態表示55/16/17/31/33/39/46。境界マスク42を54へコピーし、ピクセルと位置は維持。CPU車が自車より先のOAMとなり、重なるとCPU車が手前になる。荷重は全ての車・点・マスクより後なので先に欠ける。各車軸の左右の円の優先順を2 NMIごとに交換し、ゴースト点滅と同じ輪の欠けを固定しない。

初期分担の「CPU60〜63予約」とは異なるため、この変更を合流時に共有する。`direct-runtime/build_hud.py` とHUD本体に加え、CPU描画の `FAKE_OAM=$02A0`・停止時非表示・契約出力も変更済み。bank120の予約域へHUDコードは追加していない。物理bank126・割り込み制御バイナリは不変。

## 検証と残る性能制約

実6502 HUD1792条件で座標・色・容量・OAM優先順・バンク復元を確認。実PPU画像8枚で前後の高さ、全4輪の白い点、右輪だけ赤い円を確認。画像検査のみ環境変数で入力注入し、通常動作検査と分離した。検証中のpy65内部型エラーは独立再実行で通ったが、原因は未確定で修正済みとはしない。

Mesen通常1900フレーム、密集・FULL・旋回各1500フレームを測定。転送拒否0、通常・密集・FULLはフレーム保持0。旋回は1091レースフレーム中6回で、同じWindows Mesenによる変更前の5回から1回増加。HUD追加コストは通常・密集・FULLの最大main時間で119 cycles。完全60fpsは未達で、CPU車側の最適化と合流後に再検証が必要。結果・再現手順・代表画像は開発側 `verification/hud-horizontal/README.md` に保存済み。
