# MMC5Racing 最新CPU車・HUD・モードの統合

## フィードバック原文

IDEのActive fileは `D:\HomeBrew\MMC5Racing\play.cmd`。

> これバージョン滅茶苦茶古くない？最新とマージした奴でお願い。

原因は、モードを追加したmainの `735ce36` が、CPU車とHUDの作業ブランチを取り込んでいなかったこと。既存ROMがあれば再ビルドしないplay.cmdも、古い版を起動し続ける原因だった。

## 対応

`origin/integration/persistent-rivals-60fps-20261013` の `8593c50` と、`origin/codex/hud-axle-load` の `33c259d` をmainへマージ。関係のない `feature/nes-gsu-lab-20261013` は合流しない。別作業ツリーの未コミット `race-src/direct-abi.inc` にも触らない。

CPU3台・千鳥配置24/48/72px・前後2×2 HUD・フォント・モード・別タイムを通常起動へまとめた。`build_release.py` は最新の検証済み高速化フラグ一式を選ぶ。`build.cmd` / `play.cmd` / `play_hud.cmd` は同一の統合ROMを使い、起動時は毎回再ビルドする。

新しいHUDの時計・円・CPU車CHRを旧フォント合成で上書きしないよう、時計用の中間CHRを先に新フォントへ変換した。最新ゴーストと荷重円はpalette2の赤を共有しているため、GRIPは白い車体インク `$3F1B` のみ青へ変更し、赤 `$3F19=$16` を保持する。前回の「濃い青のトリム」は現行では赤いトリム。

最新のブレーキ高速化とモード処理の合流でPRG補助が40バイト溢れた。ガード付き空き `$B500..$B7FF` に収め、隣の生きたB800テーブルを避けた。モード別保存の `$6780..$67BF` はCPUのRAMと非重複。

単純合流では負荷試験turnsに5回の更新落ちがあった。円テーブルをビルド時に変換して既存RAMへ置き、バンク切替を省略。優先順ごとにOAMを直接書く。通常角度で重複する車輪上書き、常時非表示の6枚目のデータ転送、ブレーキの未使用符号拡張、不要なBITも削除した。4輪の円・力点は毎フレーム更新し、画面やIRQ締切を縮めない。

## 自己評価

古いmainだけを見て最新と判断したのが誤り。次の可逆な確認手順として、着手時にmain以外のCPU/HUDブランチとworktree、通常起動ROMのmanifestを照合する。初回モード実装の設計サイクル自体は保持し、その性能証拠を最新統合版へ流用しない。

Python 3.10のpy65では過去と同様、HUD比較の初回に一度だけ不一致が出て、独立再実行では全1792ケースが通過した。原因未確定。実Mesenの全6試験と別の16384ケース、保存・UI検証も独立して実施した。人間によるGRIPの最適進入速度・制動量の体感調整は未実施。
