# MMC5Racing 3D版の仕様案

2026年10月16日。対象は、現行MMC5Racingのブレーキ・荷重移動・グリップ／ドリフトを楽しみながら、立体的なコース表示と視点切り替えで走りたいプレイヤー。

**現行の4輪物理を60Hzで保ち、GSUで30fpsの3D画面を描く。走行中に車載・近い追従・高い追従・俯瞰の4視点を切り替える。** 最初は現行コースを平面の3Dメッシュにし、同じ操作で同じラインを走れる版を作る。その後に自車＋CPU3台の5周レース、ゴースト、緩い起伏へ進む。

一番楽しい瞬間は、コーナー手前で減速して前輪へ荷重を乗せ、車の向きと進行方向を見ながら旋回し、出口へ加速して抜けるとき。3D化では、この判断と手応えを強める。

ここにある描画面数・時間配分はゲーム向けの初期予算案。実測済みなのは別のポリゴンベンチマークで、路面・4台・4視点・ゲーム処理を組み合わせた30fpsは次の測定対象である。今回は仕様検討であり、ゲームや回路の実装変更は行っていない。

## ゲームの基本仕様

| 項目 | 第一候補 |
|---|---|
| レース | 自車1台＋現行ロジックのCPU3台、5周。タイムアタックも用意 |
| 操作 | 左右で操舵、Aアクセル、Bブレーキ。GRIP／DRIFTは現行の意味を維持 |
| 視点 | SELECTの押した瞬間で4視点を順送り。初期は高い追従、次走でも直前の選択を保持 |
| START | 初期版は現行どおりタイトル復帰。ポーズを追加する場合は操作変更として別途扱う |
| 物理・入力・音 | 約60Hz。描画回数から独立した固定ステップ |
| 3D描画 | 約30fps、2回のNTSC fieldごとに完成画像を提示 |
| 画面 | 256×192の3D領域＋下48行のHUDを第一候補。解像度を毎フレーム変更しない |
| HUD | 速度、周回、ラップ／合計時間、順位。4輪の荷重・摩擦円は下段へ収める。実装用のMHz・面数は開発表示のみ |
| コース | まず既存コース1本の平面版。コーナー、道路幅、ゲート、木8本・建物2棟の位置を基準にする |
| 車 | 向きと横滑りが読めるフラットポリゴン。近距離で16〜24投入三角形／台を初期候補とする |
| 保存 | モード別タイムとゴーストを継承する方向。3D版の保存先・形式版は分け、2D版の保存を上書きしない |

SELECTの割り当ては、移植時に実際の入力処理と照合する。ゴーストの選択など既存操作が同じボタンを使っていれば、同じ入力で同時に発火させない。

初期版では、ブースト・タイヤ摩耗・燃料・時間切れを新しいルールとして足さない。既存の運転操作を比較できるよう、路面の摩擦係数やBの効きを3D化と同時に変更しない。路外・木／建物への接触・再挑戦も、最初は現行仕様を基準にする。

## 4つの視点

[バーチャレーシングの公式紹介](https://archives.sega.jp/segaages/vr/)は、ドライバーズアイから鳥瞰まで4視点を走行中に切り替える構成を説明している。本作も、同じ車・同じコースを選んだ視点から描く。4画面を同時に描かないため、視点の数だけ描画時間が増える構成にはしない。

車体長をLとした初期調整値。距離や高さは既存ワールド座標へ換算し、走行して調整する。

| 視点 | カメラ位置の候補 | 狙いと注意点 |
|---|---|---|
| 1 車載 | 車体前寄り、高さ約0.3L | 路面の近さと速度感。自車の外装を省き、最小限のボンネットを必要に応じて描く。近面クリップが重要 |
| 2 近い追従 | 後方約2L、高さ約0.7L | 車体の向きと横滑りを読む。近い路面の塗り量と、車によるコーナーの隠れを測る |
| 3 高い追従 | 後方約4L、高さ約2L | ブレーキ位置と出口を見渡す。初期選択とし、最初の操作感比較にも使う |
| 4 俯瞰 | 後方約6L、高さ約6L | コース形状と複数車の位置関係。見える範囲が広いため遠方の形状を簡略化する |

追従視点では、カメラ方向を進行方向寄りに滑らかに変え、車体の向きは別に描く。低速・停止・後退では速度ベクトルから方位を決めず、車体方向や直前のカメラ方向を使って安定させる。カメラの補間で車を曲げたり、進路へ戻す力を足したりしない。俯瞰も車を基準とした方位にし、切り替えによって左右操舵の意味を変えない。

初期版の視点変更は、次に着手する画像から反映し、完成画像の交換時に切り替える。通常は1〜2描画期間、約33〜67msの反応を想定する。車の状態、入力、タイマー、ゴーストをリセットしない。切り替えのために新旧2視点を同時描画したり、長い暗転を挟んだりしない。補間付きのカメラ移動を追加する場合も1画像につき1視点で描き、中間姿勢の負荷を測る。

## 物理とコース

最初は世界の横方向2軸で現行物理を使い、高さを0に固定する。現在の位置・速度・車体方位・角速度・4輪荷重・摩擦円・GRIP／DRIFTの状態を描画側へ渡す。車軸内で接地点計算を共有し、4輪個別の荷重と力を残す現行の近似も継承する。

3D描画用の座標へ渡す際は、物理状態の元の固定小数点精度を保つ。既存の128方向の背景画像から方位を逆算する方式にはしない。車体のピッチ・ロールを荷重から少量動かす演出は候補になるが、初期版では物理への反作用を加えない。

道路は世界座標のメッシュとして作り、車載でも俯瞰でも同じ道路を描く。路面から離れても車の座標で自由に走れる。コース中心線は描画の分割や進捗判定に使えても、自車を線へ吸い寄せる用途には使わない。

現在のチェックアウトには道路マスクと8個の周回ゲートがあるが、中心線・幅・曲率の編集可能な元データが揃っているとは確認できていない。移植時には現行道路の輪郭を復元し、3Dメッシュと現行の道路判定を照合する。輪郭の近似誤差は最大値と位置を測り、路面が見えるのに路外扱いになる箇所を残さない。以降のコースは共通の幾何データから描画メッシュ・道路判定・周回ゲートを生成する。

坂道は平面版の操作が成立してから追加する。緩い起伏から始め、路面高・法線・車体の傾き・勾配の加減速・荷重を同じ地形から計算する。ジャンプ、立体交差、トンネルは後段とする。上下の道路が同じ平面座標を共有する場合、道路判定の層と隠面処理も必要になる。

## 車と景物の描画予算

開発上の比較基準は、GSU 50MHz相当・通常RAMの待ち据え置き・クリア25MHzのv003モデル。25MHzも同じ操作・4視点で軽量描画を検証する。実機の採用周波数は、統合回路と外部メモリーの確認結果で決める。

[50MHzベンチマーク](../../../../../projects/nes_superfx/demos/polygon/v003/README.md)では、小型立方体38個が204〜228描画三角形／画像で、画素書き込みは約5,400〜6,000だった。一方、大きい立方体17個は81〜102描画三角形、約23,400〜26,400画素書き込みで、どちらも最長約32msだった。**道路のように画面を広く塗る条件へ、小型立方体の200面以上という値をそのまま使わない。**

50MHzでゲーム処理を組み合わせる際の初期目標は、次の60〜90描画三角形／画像。近面クリップで増えた三角形もこの枠へ数える。面数だけで採否を決めず、投影頂点数、スパン数、画素書き込み量、並べ替え、フレーム提示時刻を併せて測る。

| 対象 | 初期の描画三角形目安 | 費用を抑える方法 |
|---|---:|---|
| 道路本体 | 14〜20 | 見える区間だけを出し、近くのカーブを細かく、遠くの直線を長く分割。隣接面で頂点共有 |
| 縁石・白線 | 8〜12 | コーナーの入口・頂点・出口が読める区間を優先。細い線のために全区間を二重に塗らない |
| 自車＋CPU3台 | 合計24〜32 | 同じメッシュを共有し、物体ごとに変換。投影サイズによって遠い車を簡略化 |
| 木・建物 | 4〜8 | 近いランドマークを優先し、遠い景物を少面数の板や箱へ置換 |
| ゴースト等の余裕 | 0〜8 | 完成版の同時表示負荷として追加計測。透明描画を前提にしない |

表の通常想定は50〜80面程度で、60〜90面の全体枠にはクリップによる増分と状態差の余裕を含める。25MHzの軽量設定は40〜60面程度を候補とし、同じコース・同じ車台数・同じ視点を保ちながら遠方形状と景物の詳細を減らして測る。これらの面数で30fpsが達成済みという意味ではない。

車の簡略化は画面上の大きさで選ぶ。近い車は16〜24投入三角形、中距離は12面程度、数画素の車は4面程度や向きの分かる小さな表現へ変える。切り替えのしきい値には幅を持たせ、境界で形が毎画像往復しないようにする。物理、衝突、CPU車の進行は描画の詳細度から独立させる。

道路の外の空と地面は、まず2色の範囲フィルで用意する。平面コースと固定したカメラ傾きなら、各視点の地平線に対応するRAM範囲を事前に求められる。現行のタイル配置に合わせた範囲列を使い、汎用の矩形フィル回路を必須にしない。単色16KiBは0.65536msで、2色版はコマンド数と二重書き込みの有無を含めて測る。

道路の塗りが支配的なら、次の回路追加は水平スパンフィルを優先する。まず実際の道路のスパン長分布を取り、短いスパンの発行費用も含めて判断する。スパン回路の未測定の効果を、初期版の30fps成立の根拠にはしない。

## 色とHUD

現在のABI2ベンチマークは画面全体で共通の4色を使う。2bppだからといって、各ポリゴンを任意の16色へそのまま塗れる構成ではない。最初は空・草地・路面・車／白線を分ける4色で、輪郭・向き・コーナーが読めるかを確認する。車体の上面と側面には既存色を使い、影も同じ配色内に収める。

完成版で現行GRIPの青い車やDRIFTの赤系を出すには、車の一部や識別マーカーをPPUスプライトで補うか、タイルごとのパレット選択と配色変換を追加する。MMC5の拡張attributeだけを有効にしても、車と路面が同じタイルで必要とする色の問題は自動では解決しない。GSUを4bppで描いてから変換する方式は描画RAM・帯域・変換時間も増えるため、別の評価対象とする。

HUDは下48行にまとめる。初期の走行確認は速度・時間・視点の最小表示から始め、完成版では通常CHRの文字と小さな4輪HUDを使う。PPUスプライトの8枚／走査線制限を含め、文字と円が同じ行へ集中して消えない配置を検査する。ゲームの主画面へベンチマークの面数やクロック表示を常設しない。

## CPUとGSUの分担

| 担当 | 処理 |
|---|---|
| 6502／MMC5側 | 60Hz入力、自車の既存4輪物理、既存CPU車ロジック、計時・周回・ゴースト、APU／拡張音源、HUD準備 |
| GSU側 | 選択中のカメラ、共有頂点の変換、透視投影、クリップ、裏面除去、深度順、フラット塗り、描画完了通知 |
| 専用回路 | RAM範囲フィル、2bppアドレス変換、表示バンクの保護、完成画像の公開 |

描画要求には、世界状態の番号、物理時刻、カメラ番号とパラメーター、自車・CPU・ゴーストの姿勢、表示対象の区間をまとめる。GSUが読む要求は処理中に変更せず、CPUは次の要求を別の領域で準備する。完成した画像・カメラ・位置に依存するOAMを同じ世代としてVBlankで公開する。前の背景へ新しい車マーカーだけを載せない。

物理の60HzをGSU完了待ちのループに従属させない。長い旧NT／ExRAM転送IRQと回転背景の準備は3D側の表示入口で置き換え、物理・計時・音・保存は残す。表示が間に合わない時は前画面を保持して遅延を記録し、レース時計や物理の時間を遅くしない。

既存物理の検証例には約8,600〜9,100 CPU cyclesの処理があるため、自車物理だけでも約5msの規模になる。CPU側は1回の物理期間あたり8ms以内を初期予算とし、CPU3台・音・記録・通信・共有バスの待ちを含めて測る。CPU車すべてに自車と同じ4輪計算を無条件で4台分実行する設計にはしない。

描画の33.3ms予算は、初期目標として次のように分ける。

| 内容 | 初期予算 |
|---|---:|
| 背景の範囲フィル、GSUの変換・クリップ・並べ替え・描画・flush | 合計22ms以内 |
| ホスト同期、表示経路、必要になったメモリー調停／コピーの評価枠 | 合計3ms |
| 視点・可視状態の変化に対する余裕 | 約8ms |

CPUとGSUが並行して動けても、物理バスが共有なら待ちは発生する。CPUをほぼポーリングだけにしたベンチマークの時間を、物理・音・ゴーストが動くゲームへ足し算なしで適用しない。特にPRGとSRAMの線を共有する実機案では、NESの応答期限を優先する調停を含めて評価する。

## 描画エンジンで先に直す点

車載と低い追従では、道路の三角形が近面をまたぐ。現在のベンチマークはその面を丸ごと拒否するため、ゲームでは路面に穴が開く。**近面で面を切って描く処理は4視点の最小要件**とする。投影前の座標範囲、画面端、大きな三角形、クリップで増える頂点と面の作業領域も検査する。

平面版では、空／地面を用意し、路面と縁石、車と景物を適切な順で描く。物体中心だけの深度順は、長い道路、交差する形状、丘の裏の車には不十分。道路を短い区間へ分けて扱い、立体交差を導入する前に道路面と車の前後関係を保証する方式を追加する。最初から全画素のZ-bufferを必須にはしない。

既存の単一メッシュのベンチマーク入力を、道路・車・景物の複数メッシュへ拡張する。同じ車メッシュのデータは共有しても、各車の位置と角度から頂点を毎画像変換する。コース全体を毎フレーム6502からコピーせず、起動時の常駐データまたは区間ごとの先読みを使う。

## マッパーとメモリーの整合

ゲーム側の表示契約は、ユーザー指定の**GSU描画RAMをPPUから直接読む方式**を基準にする。一方、別スレッドの[PLATFORM.md](C:/Users/owner/Downloads/MMC5Racing/development/superfx-lab/PLATFORM.md)には完成画像をCHR PSRAMへコピーする構成案がある。この違いはゲームのPresent処理で分離し、回路案との整合を取る。コピー経路を採用する場合は、その時間とRAM競合を含めたゲーム計測が必要になる。直読のベンチマーク結果をそのままコピー経路の結果とは扱わない。

現エミュレーターのGSU窓`$5000..$52FF`はMMC5の制御と衝突し、表示・フィルの`$5Fxx`もExRAM領域と重なる。**現行MMC5Racingを今のABI2へそのまま載せることはできない。** 同居版では資料の`$4800..$48FF`、キャッシュ`$4A00..$4BFF`、管理`$4Fxx`という移動案を起点に、正式な配置と所有権を回路側・エミュレーター側で合わせる。ABI1／ABI2は診断・比較用として保持する。

ゲームのメモリーは、物理・入力・記録を置くCPU用領域と、GSUのコード・作業・メッシュ・描画領域を分ける。回路案のGSU RAM 128KiB、外付けSRAM 256KiB、PRG PSRAM、CHR PSRAMを対象に割り当てを作るが、既存エミュレーターの40KiBだけで全ゲームが収まるとは前提にしない。CPUとGSUで領域を分けても、物理ポートの独立性が保証されるわけではない。ゴースト2候補・セーブ・音源用の現行実サイズも監査する。

MMC5の全機能を保持するプラットフォーム方針は継続する。旧資料の「既存MMC5Racingへの統合は要求しない」は今回のゲーム設計依頼より前の範囲であり、ゲーム側は本依頼で3D版を検討する。ここで同居回路の完成、50MHz実機動作、画像経路の成立まで認定するものではない。

## 実装する順番と確認条件

| 段階 | 成果 | 次へ進む確認 |
|---|---|---|
| 接続確認 | MMC5＋GSUの同居モデル、衝突しない窓、物理60Hzと描画30fpsの要求／完了／公開 | 無変更の物理状態列・時計・音の速度、CPU／GSU所有権、表示世代が一致 |
| 走行版 v001 | 現行平面コース、自車1台、GRIP／DRIFT、4視点、256×192 | ブレーキ・旋回・加速・路外・スピン・停止・後退で操作と道路が読める。近面の穴なし |
| 4台レース | CPU3台、周回・順位・5周ゴール、木と建物 | 千鳥スタート・密集・俯瞰・コーナーで30fps。見える障害物と衝突が一致 |
| 記録と表示 | ゴースト、モード別記録、通常CHRのHUD、必要な配色改善 | カメラに依存しない記録、表示・深度・保存の整合、HUDの走査線制限 |
| 起伏 | 緩い坂、車体姿勢、勾配と荷重 | 見た目と走行への影響が一致。立体交差とジャンプは別段階 |

性能試験では、停止・最高速・最大旋回・車載の近面・俯瞰の広範囲・4台密集・景物が集中する向き・ゴースト同時表示・連続視点切り替えを固定シナリオとして残す。最大面数だけでなくGSU時間、バス待ち、提示間隔、CPU物理更新漏れ、公開画像の世代番号を測る。

操作の比較では同じ入力列を2D版と平面3D版へ与え、車体位置・速度・方位・荷重・周回時刻の一致を確認する。視点を切り替えた版と切り替えない版も物理状態が一致することを確認する。そのうえで、実際のプレイでブレーキ開始・横滑り・出口が読めるかを判定する。

最初に作る代表シーンは、直線からカーブ入口へ入り、Bで荷重を乗せ、旋回してAで出口へ加速する一区間。この場面を4視点で走れることを、台数やコース数の拡大より先に確かめる。

## 比較対象と根拠

- 現行MMC5Racing：操作、4輪モデル、5周、CPU3台、記録の基準。[開発側README](D:/HomeBrew/MMC5Racing/README.md)、[配布manifest](D:/HomeBrew/MMC5Racing/releases/main-release.json)。参照時のmainは`d9e887eee1682bb278a3e0e6e737f4bb647fd93a`、clean。現行の表示寸法は136×184で、古いFRAME_CONTRACTの176行の説明と区別する。
- バーチャレーシング：視点切り替えとフラットポリゴンの読みやすさの参照。[セガ公式](https://archives.sega.jp/segaages/vr/)。操作・コース・車モデルをそのまま複製する意味ではない。
- F-ZERO：遠くのコースを読んで速度とラインを選ぶ構成の比較対象。[任天堂公式紹介](https://www.nintendo.co.jp/clvs/soft/f_zero.html)。地形トラップやダメージを本作へ採用する指定ではない。
- 頂点数と形の選択：少ない面で向きを読ませ、事前に頂点予算を測るという[任天堂の開発者インタビュー](https://www.nintendo.com/jp/topics/article/9214cd6a-758b-11e7-8cda-063b7ac45a6d)。本作の性能値の根拠は、下記の実測と今後の道路シーン試験。
- [GSU 25MHz専用クリア版](../../../../../projects/nes_superfx/demos/polygon/v002/README.md)、[50MHz・RAM待ち据え置き版](../../../../../projects/nes_superfx/demos/polygon/v003/README.md)。いずれもゲーム処理・正式MMC5同居・実機の性能保証ではない。

設計上は、R-Aの運転の核、R-Cの見える荷重と挙動、R-Eの物理変更の分離、R-Fの描画単体とゲームの測定区別を使った。[3回の検討ログ](design_log.md)に依頼原文、評価、改善案、採用理由を残している。
