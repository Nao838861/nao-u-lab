# MonoSH 解説動画 構成案

## 企画の核

前回動画のビットマップ描画方式は説明し直さない。冒頭で実機映像を短く見せ、「画面全体のビットマップ描画方式はこちらの動画で扱っています」とだけ案内する。

今回の中心命題は次の一文に置く。

> ファミコンが画像を拡大しているのではなく、あらかじめ作った複数サイズの絵から、奥行きに合うものを高速に選んで描いている。

そこから、単なる描画技法では終わらず、Space Harrier 固有の物量配置・敵軌道・ボス挙動をどう移植したか、AIを解析・生成・最適化・検証にどう使ったかへ進む。

物語の因果は以下とする。

1. ファミコンには一般的な画像拡大機能がない。
2. 16段階のサイズを事前生成し、奥行きから選ぶ。
3. 各サイズを高速に描くため、位置ずれ別の6502コードまで事前生成する。
4. それでも大きな物体を同時に出せば、フィルレートの限界に当たる。
5. 原作 Space Harrier の構成を解析すると、敵弾の濃い区間と大木の濃い区間が時間で分離されていた。
6. その「見えない負荷設計」まで移植し、AIで大量解析・コード生成・差分検証を回した。

### 0:55–2:25 拡大縮小の実装

#### 1. オフラインで16段階を生成

- `png/Tree0/` や `png/BossFace/` の base 画像を見せる。
- `tools/gen_sprite_sizes.py` が固定比率で16サイズを生成する様子を、ファイルが順に現れるアニメーションで表す。
- 最大サイズ `_00` から最小サイズ `_15` までを横一列または奥へ並べる。
- 実行時補間ではないため、各サイズの二値化結果を人間が確認・調整できることも触れる。

#### 2. 奥行きから位置とサイズを引く

`src/game.c` の `bgobj_z2sc[56]` と `bgobj_z2size[56]` をそのまま長く見せず、図に翻訳する。

- `Z` が小さいほど手前。
- `bgobj_z2sc` は世界座標から画面上の横方向オフセットを作る倍率。
- `bgobj_z2size` は16段階のどの絵を使うかを決める。
- 地面上のY位置は別の射影テーブルから得る。

図は「世界座標 `(wx, z)` → 射影テーブル → 画面座標 `(sx, sy)` と size index」の一方向フローにする。

#### 3. 絵ではなく描画コードを選ぶ

ここが技術的な驚きとして一番強い。

- `tools/gen_multisprite.py` は各サイズについて、Xの4通りのビット位置とYの偶奇2通り、合計8通りの描画コードを生成する。
- 実行時は `size * 8 + y parity * 4 + x shift` で描画ルーチンを選ぶ。
- 透明部分を飛ばし、不透明な連続部分は単純な `sta` にし、端だけ read-modify-write する。
- 生成したコードは8KBのPRG bankへ詰め、MMC5のbank切替で呼ぶ。

Remotionでは、4ピクセルが1バイトへ詰まる小図の上をスプライトが1ドットずつ横移動し、選ばれる4種類のX shiftが切り替わるアニメーションにする。Y偶奇も上下2段で示す。コード全文ではなく、最後に `size × 8 + parity × 4 + shift` だけを残す。

### 2:25–4:25 Space Harrier 固有の移植

章見出しは「画面を似せるだけでは、移植にならない」。原作と MonoSH の比較を主役にする。

#### 1. 敵軌道を動画から表へ戻す

- 原作動画をフレームへ分解。
- 敵の中心位置・画面上の大きさ・接近タイミングを測る。
- MonoSH側の `wx / wz / bot / size` テーブルへ変換。
- 原作とNES版を左右に置き、軌道点とZのグラフを同期表示する。

素材候補:

- `docs/space_harrier_stage1_reference.md`
- `docs/space_harrier_stage1_spawn_analysis.md`
- `tools/houdini/export/enemy_path_spaceharrier_*`
- `tmp/nes_vs_recording_preview.png`
- `tmp/boss_motion_final/contact_sheet.png`

#### 2. 原作の「負荷設計」も移植する

67秒のタイムラインを一本表示し、前半を敵アイコン、後半を木アイコンで塗る。

- `t≈10–38`: 敵と敵弾が濃く、大木はほぼ出ない。
- `t≈40–66`: 大木が濃く、敵は薄い。

ナレーション案:

> 原作を数え直して分かったのは、見た目ではなく順番でした。敵弾が多い時間と、大きな木が画面を埋める時間が、ほとんど重ならないように作られています。

ここで「高速化はアセンブラだけではない。ステージ構成も処理落ち対策」という動画の第二の結論を出す。

#### 3. 自動解析をそのまま正解にしない

AI・画像処理は木、bush、flystone、敵、爆発、タイトル文字を取り違えた。投影テーブルも原作と MonoSH で一致しないため、トラッキング座標の直輸入では距離感が崩れた。

自動抽出結果をたたき台にし、最終的なタイミングと見た目は人間が比較動画を見て校正した。この失敗を短く見せると、後半のAI活用が宣伝調ではなくなる。

### 4:25–6:15 6502最適化

#### 1. 1回の更新を2フレームに分ける

画面を縦ではなく時間方向の2枚に割る。

- Frame 1: 大きなソフトスプライトをVBUFへ描く。
- Frame 2: VBUF消去、地面、遠景、敵・弾・衝突などのロジック。
- 2 NMIで1ゲーム更新、実質30fps。

静的計測の代表値を表示する。

- Frame 1: 約20,000 cycles。
- Frame 2: 約8,000–11,000 cycles。
- 大きい木1本のblit: 約4,200 cycles。

数値を大量に並べず、「大きな絵の面積が支配項」と分かる棒グラフにする。

#### 2. AIの最適化案も計測で落とす

一度、種類から関数を引くデータ駆動ディスパッチを試したが、cc65がソフトスタック経由の重いコードを生成し、かえって遅くなった。ここはAI活用の重要な失敗例として使う。

ナレーション案:

> コードだけ見れば、きれいで速そうでした。ところが生成された6502コードを測ると遅くなっていました。そこで完全に戻しました。

「AI案 → build → generated asm → cycle measurement → reject」のループを画面で一周させる。

#### 3. 効いた最適化は検証可能にする

- C版をアルゴリズムの正本として残す。
- 6502 asmへ逐語的に移す。
- sim65で複数seed・2000 scenarioの結果を突き合わせる。
- 生成asmとサイクルを測る。
- makefileのフラグ1行でC版へ戻せる。

代表例:

- `update_enemy`: 8体時に約49%削減。
- `draw_bgobj_all`: 弾が多い場面で約1,842 cycles/frame削減。
- フィルレート限界に達した箇所は、コードでなくOAM退避・物量配置・適応的デグレードで解く。

### 6:15–7:55 AIをどう使ったか

独立した「AIが作りました」章にはせず、それまでの工程を一枚の循環図へ回収する。

1. 観察: 原作動画をフレーム分解し、AIが全数カウントと候補抽出。
2. 変換: Pythonでサイズ画像、軌道テーブル、6502描画コードを生成。
3. 実装: Cとasmを往復し、bank配置やfarcallを修正。
4. 検証: 比較映像、sim65、checksum、静的cycle解析、実機・エミュレータ確認。
5. 判断: 見た目、遊び、原作らしさ、どこまで似せるかは人間が決める。

この章の主張:

> AIで一番変わったのは、コードを書く速度より、一人では省略しがちな大量の比較と検証を回せるようになったこと。

AIの得意領域:

- 何十枚・何百枚のフレームを同じ観点で数える。
- 変換スクリプトや生成コードを作る。
- generated asmを追い、bankや範囲外アクセスを調べる。
- 変更前後を機械的に突き合わせる。

人間が握る領域:

- 軌道が気持ちよいか。
- 原作に忠実であるべき所と、ファミコン向けに変える所。
- 自動抽出が見た目として間違っている時に止める判断。
- 限られた物量を、どの場面に使うか。

ボス、敵編隊、黒丸敵、反射弾、ロックオン、大木の接近を短くモンタージュする。図やコードは消し、最後はゲームそのものを見せる。

## AIを主役にしすぎない見せ方

AIの画面や会話ログを長く見せると、技術解説が「プロンプト紹介」へ寄ってしまう。AIは成果物と検証ループで見せる。

- 会話画面: 最大でも合計10〜15秒。判断が変わった箇所だけ。
- コード生成: 入力と出力を同時に見せる。
- 解析: フレーム数、検出数、比較結果を可視化する。
- 失敗: 遅くなったディスパッチ、自動抽出の誤認、bank違いハングを一つずつ短く出す。
- 成功: 「AIが正解した」ではなく「検証可能な形へ変換した」と説明する。

## Remotion と DaVinci Resolve の分担

### Remotionで完成させる範囲

- 全章の尺とカット順。
- ゲーム映像、前回動画、原作比較素材の配置。
- 16段階スプライト、Zスライダー、射影図、8 shift図、bank図。
- コードの行ハイライト、diff、タイムライン、cycle棒グラフ。
- 章タイトル、テロップ、字幕の初稿。
- 仮ナレーションまたは確定ナレーションに合わせたフレーム単位のタイミング。

構成変更はRemotionへ戻す。DaVinci側で章順や図解の長さを再設計しない。

### DaVinci Resolveで行う範囲

- ナレーションのノイズ除去、EQ、コンプレッサー、音量統一。
- BGMと効果音の最終ミックス。
- CRT実写、エミュレータ映像、原作映像の色・黒レベル・サイズ感の統一。
- 数フレーム単位の最終トリム。
- 必要なら字幕の誤字修正と焼き込み。
- 最終エンコードと公開用ラウドネス確認。

Remotionからは、映像マスターに加えてナレーション、BGM、効果音を別stemで出せる構成にしておくとDaVinciでの仕上げが軽い。

## 最初に作るRemotionプロトタイプ

いきなり全編を作らず、まず45秒だけ作る。

1. 現在のMonoSH映像 8秒。
2. 前回動画へのリンク 7秒。
3. Tree0 baseから16サイズが展開する 10秒。
4. Zスライダーで選択サイズが切り替わる 12秒。
5. 実ゲームの木が接近する映像へ一致させる 8秒。

この45秒で、フォント、色、ゲーム映像の拡大率、コード表示量、ナレーション速度を確定する。その後、同じ部品で残りの章を組む。
