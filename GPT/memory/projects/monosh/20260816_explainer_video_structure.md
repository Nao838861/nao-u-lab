# ファミコン向け擬似3Dデモ 解説動画 構成案

## 呼称と企画の核

動画内ではプロジェクト名を出さない。最初だけ「今回制作したファミコン向け擬似3Dデモ」と呼び、以後は「今回のデモ」で統一する。「今回の手法」はCompiled Spriteなど個別の技術を指す時だけ使う。

前回動画で説明したビットマップ描画方式は説明し直さない。冒頭で前回動画の見栄えのする箇所を5〜8秒だけ見せ、「画面そのものの描き方は前回の動画で紹介しています」と案内する。

今回の技術的な主役は、拡大縮小そのものではなく**Compiled Sprite**。拡大縮小は、Compiled Spriteを16サイズ分あらかじめ用意し、奥行きに応じて選んだ結果として説明する。

中心命題は次の三つ。

1. 絵をデータとして読みながら描くのではなく、その絵を描く6502の命令列をあらかじめ生成する。
2. 拡大縮小、地面、座標変換、敵の軌道を、実行時の重い計算ではなく大量のコードとテーブルへ置き換える。
3. AIによって、コード生成・変換・検証・実装の反復が現実的になり、人間の役割が実装者から判断と指示を担うプランナーへ変化していった。

動画全体を貫く一文は次にする。

> ファミコンでも、メモリさえあればいろいろなことができます。ただし今回は、当時の市販ソフトでは現実的でなかった量のROMと生成作業を使っています。

「当時は不可能だった」と断定するより、ROM容量・制作工数・コストの面で現実的ではなかった、と表現する。ハードの限界を破った話ではなく、計算を事前生成と大容量ROMへ移した話として見せる。

開発過程の映像は補足ではなく、動画の第二の主役にする。技術図解の直後に必ず当時の実映像へ戻り、「この仕組みが一日目、二日目、三日目にどう育ったか」を見せる。

## 0:32–2:35　Compiled Sprite――絵をプログラムに変える

### 1. 普通の描画とCompiled Spriteの概念図

ここはコードを知らない視聴者にも分かる図をRemotionで作る。8×8程度の小さな絵を左右に二つ並べ、同じ絵が別の方法で描かれる様子を同時再生する。

左側「普通の描画」:

```text
画像データ
   ↓
1バイト読む → 透明か判定 → 描画先を計算 → 書く
   ↑_______________________________________↓ 繰り返す
```

右側「Compiled Sprite」:

```text
元画像 ──開発時に変換──> その絵専用の6502命令
                              ↓
                    LDA #値 → STA 描画先
                    LDA #値 → STA 描画先
                    必要な場所だけ書く
```

図の動き:

- 左は透明部分を含む全マスをカーソルが巡回する。
- 「読む」「判定」「座標計算」のランプが毎回点灯する。
- 右は塗る場所だけへ線が飛び、透明部分を飛ばす。
- 右側の命令列を実行するたび、対応する画素が同じ色で点灯する。
- 下に概念的な処理量メーターを置き、右が先に描き終わる。
- 正確なcycle比較ではないため、メーターには「概念図」と明記する。

ナレーション案:

> 普通は、プログラムが画像データを一つずつ読み、透明かどうかを調べ、書く場所を計算します。でも、この絵なら、どこへ何を書けばよいかは最初から決まっています。そこで、その答えを6502の命令として先に作っておきます。絵を描くプログラムそのものが、絵のデータを兼ねている。これがCompiled Spriteです。

### 2. 位置ずれに対応する8通り

VBUFでは1バイトに横4ピクセル、縦2ライン分の情報が詰まっている。任意の1ドット位置へ高速に描くため、各画像について次の8通りのコードを生成する。

- 横位置の余り4通り。
- 描画開始Yの偶数・奇数2通り。
- 合計`4 × 2 = 8`通り。

画面では4ピクセル×2ラインの一ブロックを拡大し、同じ絵を1ドットずつ動かすたびに、選ばれる命令列が切り替わる様子を見せる。式は小さく`size × 8 + y parity × 4 + x shift`とだけ表示する。

### 3. 16サイズを先に作って拡大縮小にする

- 元画像から16段階のサイズをオフラインで生成する。
- 16サイズそれぞれに8位置分のCompiled Spriteを生成する。
- 一種類の物体につき、基本は`16 × 8 = 128`通りの専用描画コードを持つ。
- 実行時は奥行きからサイズ番号を引き、該当するコードを呼ぶだけ。

ナレーション案:

> 実行中に画像を拡大しているわけではありません。大きさの違う絵を16段階、さらに位置ずれごとに8通り、先に全部プログラムへ変換してあります。奥行きに合わせて、その中から一つを選んでいるだけです。

速度とROM容量の交換を、16サイズ×8位置のカードが8KBのPRG bankへ大量に詰まる図で見せる。

> 計算を減らした代わりに、同じ絵の専用コードを大量に持ちます。速さをROM容量で買っているわけです。

ここで中心命題を一度回収する。

> ファミコンでも、メモリを大量に使えばできることは増えます。ただし、これだけのコードを人手で作るのは現実的ではありません。そこで最初から、画像変換とコード生成をAIに作ってもらいました。

## 2:35–5:00　Space Harrierらしい3Dをテーブルへ分解する

章見出しは「画面に出ているものは、ほとんどテーブルで動かせる」。

### 1. 3Dゲームを機能ごとに分ける

Space Harrierは3Dゲームだが、この場面で必要な機能を分解すると、実行時に万能な3Dエンジンを回す必要はない。

- カメラは自由に回転しない。
- 敵は、あらかじめ決めたレールやパターンに沿って動く。
- 遠い物ほど固定された消失点へ寄せればよい。
- 奥行きごとの見た目は、事前にテーブルへできる。

入力と出力の一方向図を出す。

```text
奥行きZ ─┬─> 横方向の寄り方 ─> screen X
         ├─> 地面上の高さ   ─> screen Y
         └─> 16段階の番号   ─> sprite size

経過frame ──> 敵の軌道テーブル ─> world X / Y / Z
プレイヤーY ─> 地面テーブル選択 ─> 地平線の高さ
```

ナレーション案:

> 3Dゲームを丸ごと再現しようとすると大変です。でも、敵は決められたコースを飛び、カメラは回転せず、遠い物は一つの消失点へ集まっていく。この条件なら、奥行きごとの横位置、高さ、大きさを全部表にしておけます。画面に出ているものは、ほとんどテーブルで動かせます。

### 2. 実際のCテーブルを見せる

図から実コードへ寄る時は、`src/game.c`の次の三配列を一画面へ抜き出す。

- `bgobj_z2sc[56]`: 奥行きから横方向の倍率。
- `bgobj_z2gy[56]`系: 奥行きから地面上のY座標。
- `bgobj_z2size[56]`: 奥行きから16段階のサイズ番号。

三列すべてを読ませるのではなく、一つのZを選び、該当する三要素だけを同じ色で光らせる。その値が画面上の木のX・Y・サイズへつながる線を出す。

補足として、背景物は56段階、敵は滑らかに動かすため4倍精度の224段階テーブルを使う、と小さく表示する。長い配列をスクロールして「大量の表でできている」量感も2秒だけ見せる。

## 5:00–6:15　二フレーム描画と初期の人間・AI分業

### 1. 説明上は「生成フレーム」と「転送フレーム」にする

ソース内のFrame1/Frame2という名称は、説明順と逆で混乱しやすい。動画では内部名を出さず、次の二段で説明する。

```text
A: 次の画面を作るフレーム
   VBUF消去 → 地面・遠景 → 敵・弾・衝突などのロジック

B: 大きな物体を描き、表示へ渡すフレーム
   Compiled SpriteをVBUFへ描画
   → 上下の非表示期間を使い、通常VRAM側とExRAM側へ分けて転送
   → 表示ページを切り替える
```

実装では2 NMIで1ゲーム更新し、ゲーム側は実質30fpsで進む。転送は一回の「VRAM更新」ではなく、MMC5の通常VRAM側とExRAM側へ役割を分けている。詳細なphase 0/1の順序は図の脚注へ留め、ナレーションでは「二系統へ分割転送」と表現する。

画面は横長タイムラインにし、CPU処理・通常VRAM側転送・ExRAM側転送を三色に分ける。ページを二枚重ね、片方を表示中にもう片方を作ることが分かれば十分。

代表値は棒グラフへする。

- Compiled Sprite側: 約20,000 cycles。
- ロジック・地面側: 約8,000〜11,000 cycles。
- 大きい木一本のblit: 約4,200 cycles。

### 2. 初期は人間が骨格、AIが機械作業

この時期の分業を明確にする。

人間:

- フレームワーク。
- 敵・弾の基本アルゴリズム。
- 最初から負荷を意識したデータ構造と更新順。
- どの見た目を残し、何を削るかの判断。

AI:

- 画像サイズ変換。
- Compiled Sprite生成。
- PRG bankの割り当てと管理。
- 検証用の再生プログラム。
- 機械的なCから6502 asmへの移植。

実装方針は、まず読みやすいCでロジックを固め、計測して本当に重い箇所だけをAIにasm化してもらう。C版とasm版は複数条件で出力を突き合わせ、フラグ一つでC版へ戻せるようにする。

代表例として、次だけを短く出す。

- `update_enemy`: 8体時に約49%削減。
- `draw_bgobj_all`: 弾が多い場面で約1,842 cycles/frame削減。

旧案にあった「きれいなディスパッチへ変更したが遅くなってrevert」の話は削る。今回の主題である開発過程の変化を優先する。

## 6:15–7:35　中期――映像から敵軌道を半自動生成する

### 1. Houdiniでの手作業から始めた

敵の動きはHoudini上で軌道を作り、ランタイム用テーブルへ書き出していた。

```text
Houdini viewport → exporter → C table → ファミコンで再生
```

AIがエクスポータと変換スクリプトを作り、人間が原作映像と見比べて速度感・距離感を直した。しかし敵が増えるほど、Houdini上で一本ずつ軌道を作る作業自体が重くなった。

### 2. 人間がキーフレームを印し、AIが表へ変える

原作動画をコマ画像へ分解し、人間が敵の重要な位置へマーカーを置く。AIがマーカーを抽出し、中間フレームを補間して、敵軌道テーブルを生成する流れへ変えた。

```text
原作動画
  ↓ コマ画像化
人間が数枚へマーク
  ↓
AIが座標抽出・補間・テーブル生成
  ↓
比較映像で確認
```

これにより手間が減り、目測だけでHoudiniへ置くより精度も上がった。

### 3. 全自動検出も試したが、人間の印が速かった

画像を理解できるモデルが使えるようになり、最初は敵検出器まで作って完全自動化を試した。しかし、小さい敵、重なり、点滅、背景との混同で十分な精度が出なかった。

いくつかの敵はAIと対話しながら誤検出を修正し、ほぼ自動で表を作れた。一方で全体としては、人間が要所だけマークする方が速いと判断した。

ここは「AIなら全部見つけられる」という成功談にしない。

> 自動化を増やせば、必ず速くなるわけではありませんでした。人間が数か所だけ教え、残りをAIに埋めてもらう方法が、この映像には一番合っていました。

## 7:35–9:20　終盤――完全なバイブコーディングへ

終盤は、ソースコードを一行ずつ人間が作る比率が急激に下がったことを、黒丸敵、プレイヤー、ボスの三例で見せる。

### 1. 黒丸敵――仕様と絵を渡して一式を作る

黒丸の敵が三体出る場面を流しながら、実際に履歴へ残っていた指示を短く再構成して表示する。

> 奥から現れ、遠・中・近の三回、蓋を開いて弾を撃つ。閉じている間はプレイヤー弾を反射する。開閉は大中小の三サイズを用意する。

### 2. プレイヤー――絵と動作条件から状態遷移を作る

プレイヤーが左右へ寄った時の向き、地面を走る時、被弾して転ぶ時、落下する時の映像を連続で見せる。

この頃には、人間は絵と「どの状態でどのアニメを出すか」を伝え、AIが状態判定、OAM更新、フレーム進行を実装する形になっていた。人間はソースの細部より、実機上の動きと差分を見て指示する。

当時のプレイヤーアニメの原文プロンプトは現存ログから特定できていない。動画制作時に推測文を「当時のプロンプト」として出さない。コミット`2bfd8cd`の差分と、実際のアニメ映像を根拠に説明する。

### 3. ボス――基本アルゴリズムは人間、調整は自然言語

ボスの実装も大部分はバイブコーディングだったが、完全自動では安定しなかった。最初の運動モデルや制約は人間が指定し、動くようになった後は、次のような見た目の指示でパラメータを調整した。

- プレイヤーへ近づきすぎるので、距離を大きくする。
- 上方向の動きが足りないので、振幅を増やす。
- 画面端で不自然に止まるので、折り返しを滑らかにする。

当時のボス調整の原文プロンプトも現存ログから特定できていないため、上記は「指示の形式を再現した要約」と明記する。コミット`54a332b`、`704ab76`、`2bfd8cd`の変化を、ボス初期→移動調整→完成の三段で見せる。

ナレーション案:

> 終盤には、私は一行ずつコードを書く人ではなくなっていました。絵と仕様を渡し、動いた画面を見て、もっと離す、上へ大きく動かす、と指示する。プログラマーへ指示を出すプランナーに近い立ち位置です。ただし、何を作るか、どの動きならよいか、基本の仕組みをどうするかは、人間が決めないとうまくまとまりませんでした。

### 4. AI活用の変化を一枚で回収する

```text
人間が実装の骨格      人間がキーフレーム指示    人間が仕様・絵・評価
AIが変換とasm化       AIが抽出・補間・表生成    AIが実装一式

     実装者 ───────────────> プランナー／ディレクター
```

モデル名は補助的に出すなら一度だけにし、主題にはしない。「高性能なモデルが登場した」ことより、「成果物と画面差分を介して指示できる範囲が広がった」ことを中心にする。

## 9:20–10:00　結果と締め

ボス、敵編隊、黒丸敵、反射弾、ロックオン、大木の接近を短くモンタージュする。図やコードは消し、最後はゲームそのものを見せる。

ナレーション案:

> ファミコンに、新しい拡大機能を足したわけではありません。実行中の計算を、描画コードとテーブルと大容量のROMへ移しました。そしてAIが、その膨大な事前作業と試行錯誤を現実的なものにしました。ハードの限界が消えたわけではありません。でも、同じハードで作れるものの範囲は、大きく変わったと思います。

最後は数秒間ナレーションを止め、ゲーム音だけを流す。

短く閉じる場合の最終文:

> 描画コードとテーブル、そして何度でも試せる開発環境。その積み重ねで、ファミコンの上にこの奥行きを作っています。

## AIの見せ方

AIの会話画面を長く見せると、技術解説がプロンプト紹介へ寄りすぎる。会話ではなく、入力・生成物・画面上の結果を見せる。

- 会話画面は合計15秒以内。
- 実在する原文は黒丸敵の指示だけを候補にする。
- 見つからなかったプロンプトを推測で再現しない。
- 初期は「変換ツール」、中期は「半自動化」、終盤は「実装一式」と、AIの担当範囲が広がる様子を見せる。
- 成功だけでなく、全自動検出より人間のマーキングが速かった例も入れる。
- 「AIが正解した」ではなく、「人間が画面を見て直せる回数と範囲が増えた」と表現する。

- 最終エンコードと公開用ラウドネス確認。

各章の終わりにはゲーム映像へ戻り、説明対象が実際にどう見えるかを確認させる。
