# 奥行きに沿った滑らかな拡縮

依頼原文：「拡大縮小の段階が荒く感じる。奥行きに対する一対一のスケールマッピングテーブルってある？」「修正して滑らかにして。」

111項目あっても元画像の段階に由来する同サイズ区間が長かった。縮小済み画像を増やすのではなく、CPUが渡す寸法を直す。固定upstreamは変更せず、ビルド時に単調3次Hermite曲線で14表を再生成する。最長同サイズ区間は木9→6、通常敵12→5、ボス胴15→4、顔7→2。整数画素・小さい絵の最小寸法による同値は残る。

開いたEM1は別経路で、5pose×3サイズしかなかった。5pose×111項目・1,110bytesをCODEと一緒にWRAM7Fへコピーし、GSU稼働中もROMを使わず読む。描画・当たり判定・C参照経路を同じ表へ揃えた。Z1段階で最大20画素の切替を最大1画素へ抑える。中間距離の命中矩形は新寸法へ変わる。

木の高さと接地を別々に丸める最初の試作では樹冠の後退が増えた。接地Yは維持し、最大地面伸長のカメラで樹冠を補間して高さへ戻す。65カメラ×全Zの逆戻りは38→20箇所、最大1画素のまま。幅・高さの単調性だけでは接地した絵の動きの品質を判定できない。

拡縮単体887ac0a0で全Z1,221場面・7,404画像の全FBが独立計算と一致。C/nativeは道中5,587・ボス2,749論理更新で全状態と有効描画矩形が一致。通常18,000field・射撃なし9,000fieldで全区分60.099fps、表示遅延0。

検証中に遠景修正版ca4198f219と音の検討a99214da6cが親ブランチへ入ったため、両方の変更を保持して統合。統合ROM0b5e3c57と887ac0a0の全byteを照合し、CPU命令は背景位置の即値2箇所だけが異なることを確認した。その他は遠景の色・画像3,119bytesとchecksum。全450個の既存label、GSU、GSU用画像・UV・寸法表は同一。全Z/C-nativeの根拠は887ac0a0に紐付けて保ち、統合後の速度・表示・操作は別の実測へ分ける。

正本：[結果・比較GIF・再現手順](../../../projects/monosh_fx2/game/v001/RESULTS_20261008_SMOOTH_DEPTH.md)、[統合byte照合](../../../projects/monosh_fx2/game/v001/results/smooth_depth_20261008/integrated/integration.json)。通常は[play.cmd](../../../projects/monosh_fx2/play.cmd)で公開ROMを開く。更新時はROMを開き直してリセットし、旧WRAMコードを含む旧ステートを使わない。

統合版0b5e3c57でも通常18,000field・射撃なし9,000fieldは全区分60.099fps、表示遅延0。通常のGSU最大は道中11.591ms・ボス12.707ms。9種類の回帰試験8,080field、自機17pose・全四反転・16弾サイズ、三カメラ最終RGB、押しっぱなし・転倒・ボス撃破・全12KiB転送が通過した。全Z/C-nativeは887ac0a0、公開版の速度・RGB・回帰は0b5e3c57、と根拠を区別する。
