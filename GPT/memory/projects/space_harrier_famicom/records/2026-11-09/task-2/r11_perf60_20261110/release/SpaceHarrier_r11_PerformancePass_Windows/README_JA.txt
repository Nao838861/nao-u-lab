Space Harrier r11 PerformancePass / Windows

ZIP全体を展開してPLAY_R11.batまたはPlay_R11.exeを起動してください。
今回のROMと専用Mesenを同梱しています。以前のセーブ状態は読み込まないでください。

操作: 矢印=移動、Z=ショット、X=NES B、Enter=通常/ボス切替、右Shift=無敵切替。

今回の変更
・木と草の旧拡縮準備を省き、同じ最終投影とUVだけを計算します。
・投影乗算の不要な積と死んだ補間履歴、カメラの二重コピーを省きました。
・木、草、飛んでくる石、EM0、ボス、地面の直前の見た目修正を維持します。
・GSUクロック、転送速度、ゲームAI、衝突判定、音楽更新頻度は変えていません。

測定: 同じ6000 NTSCフィールド・同じ固定位置オート射撃
平均表示速度 57.945 → 58.727 fps
更新遅延 205 → 131回（36%減）、表示キュー破棄 9 → 5回
敵と木草が密集する固定5秒区間 51.08 → 54.49 fps
まだ常時60fpsではありません。ボスと近い大きな敵弾も残る負荷です。

原因
通常の密集場面はCPU側のゲーム更新と描画コマンド作成が主因です。
測定した重い区間ではCPU更新と描画準備の平均合計が約17.45msで16.64ms予算を超えます。
同じ通常密集区間のGSU自体は最大約7.53ms、アップロード開始から転送完了までは最大約11.32msでした。
ボスではGSU最大約11.63ms、アップロードと転送を含め最大約15.43msまで達し、余裕が約1.2msしかありません。
上記CPU内訳は最適化前の代表重負荷窓の値です。

検証
通常2000更新、ボス1000更新で867bytesのゲーム用RAMとOAMが基準と一致。
通常2000パケット、ボスで両方が発行した989パケットの描画コマンドとカメラが一致。
ボス11更新は処理速度差でキュー抑制が変わるためパケット比較から除外しました。
実経過フレームと音楽カウンタは速度改善に伴って異なります。
木草10989例、石3663例、乗算77761例の命令差分試験を通過。
上下左右の繰り返し移動と射撃900フィールドもエラー・EM1競合なし。
実機、FPGA、全ステージの長時間検証は未実施です。
