敵の赤い目・8×1属性 試作結果

v021表示版から独立した試作ROMと専用Mesenを作り、拡大したEM1/EM0の目を赤く表示できました。空や中間緑が透明部分から見える8×1行では赤を取りやめ、背景を元の色で残します。通常色の実PPU録画は約19.97秒、黒版は約9.98秒です。これは採用前の研究版です。FPGAへの配置が1 LAB不足で失敗し、実機用RBFは未生成です。実機操作・SD書き込み・ROM/RBFの既存ファイル上書きは行っていません。

実装は次の条件で背景を守ります。

通常パレットは地面[$09,$10,$29,$19]、空[$09,$10,$29,$14]を維持し、パレット2だけ[$09,$10,$29,$16]にします。$19が敵本体に使っていない中間緑、$16が試作の赤です。空の通常パレットには中間緑自体がないため、空でも同じ赤パレット2を使えるのは、透明部に紫$14が露出しない8×1だけです。紫を赤へ一律置換する方式ではありません。

目のマーカーはGSU色4＝2bpp値0＋既存の不透明ビットで渡します。通常の透明値0とは区別します。GSUは色4のサンプルだけCMODE$11、ほかは$10にして、透明部分のPLOTは引き続き省略します。各オブジェクト開始時にも$10へ戻します。別の赤マスク用フレームバッファ、転送、描画コマンドは追加していません。

合成時には、非透明な敵画素で覆われていない背景に色コード3（地面の$19／空の$14）が1画素でもあるか判定します。あればその8×1全体を元のパレットで表示し、目は元の暗色へ戻します。なければ赤パレット2を選び、目だけコード3へします。共通の暗緑・灰・明緑の3色はそのままです。山・森の見える画素も背景として判定します。赤が見える行と見えない行が動きに応じて変わることは、この背景優先条件の結果です。

EM1は旧v002_Bマニフェストの4つの瞳座標、EM0はSFC素材3の実パレットを復元して縮小した赤画素14個を使っています。輪郭や透明画素を赤く塗り足していません。閉じたEM1は参照素材に赤がなく、そのままです。ボスの目の赤化は未実装です。

現在の制約は大きく3点あります。

1. 色4入りの敵画像は既存の拡大用byte描画経路だけで使います。du<256の拡大時だけ目が赤くなり、縮小・等倍側は元のpacked画像と暗い目のままです。大きさの境界で見え方が切り替わります。
2. 8KiB作業領域を増やさず試すため、ボスのbyte画像・span最適化用キャッシュを敵2体に転用しました。ボスは元のpacked経路へ戻るため、拡大ボスの描画は遅くなります。本試作をそのまま通常採用することは勧めません。
3. 色4の既存不透明ビットを目に割り当てています。v021ゲーム用GSUは通常0..3しか出しませんが、将来の白フラッシュ等で色4を使う場合は別の識別方式が必要です。

クロック比較は同じ合成矩形を同じ専用Mesen・仮定50MHzで描く合成試験です。実機性能を測った値ではありません。通常色の約20秒の録画ではlate_fields、queue_drops、queue_starvations、deadline_missesの最大値はいずれも0でした。ただしボス戦は入っていません。全ステージの安定性、60fps達成、入力を含むゲーム進行の完全一致を証明する試験ではありません。ゲーム本体、render_adapter.s、interpolation.s、生成済み描画テーブルはv021と同一ハッシュです。

FPGAは実機動作したv019 signed-pitch回路を基準にracing_display.vhdの合成式だけを変更し、3回のcompileを行いました。最初は394/392 LAB、式を等価変形しても配置不可、seed2で393/392 LABとなり、まだ1 LAB超過です。最後の失敗レポートの推定値は6,187/6,272 LE、222,464/276,480メモリビット、29/30 DSP9bit要素です。LE数だけでは収まるように見えても、LAB単位の配置が成立していません。新しいfit成功・RBF・STAタイミング値はありません。旧signed-pitch回路のsetup余裕0.987nsなどを本候補の余裕として扱ってはいけません。クロック状態、外部バスの待ちサイクル、PSRAM転送面を増やす変更はしていませんが、タイミング成立を保証するものではありません。

実機と表示版は分けて扱う必要があります。v021は山・森とその状態レジスタを専用Mesenに追加した表示版です。実機で約23秒動いたv019 signed-pitch RBFにはその山機能がありません。本試作のFPGA差分もv019回路基準なので、山を含むv021の実機版にはなっていません。また旧回路は通常の敵画素にもパレット2/3を選ぶため、赤パレット入りの試作ROMを旧RBFで起動すると背景の中間緑が赤くなるおそれがあります。このROMを既存RBFに組み合わせてSDへ配置しないでください。

検証の証拠は以下です。

- results/red_eye_tests/RESULT.json：全背景bitplane組合せ×空/地面の131,072例、計1,048,576画素を独立した色オラクルで比較。非目画素と透明部の色一致、衝突時の目の暗色フォールバックを検証。同じベクトルを実際のracing_display state10から抽出したVHDL式へ与えGHDLでも一致。
- red_eye_tests/gsu_unit/ORACLE.json：実際にGSU機械語を動かした24例、計1,179,648画素を比較。敵・ボス・閉じた目・弾の4サイズ、透明余白も含む。赤の不透明ビットによる表示は別途実PPU録画で確認。
- red_pixel_evidence.json：通常色の実PPU録画1,200フレーム中364フレームで赤を検出。ピーク571フレーム目で262画素。判定はプレイ領域内の赤RGBで、目だけのオブジェクトID識別ではない。
- BLACK_COMPARISON.json：別ROMの実PPU録画の同じ571フレーム目を比較し、$09のRGB(11,72,0)を$0FのRGB(0,0,0)へ置換した期待画像と全61,440画素が一致。黒案は敵本体に加え山の陰影、森、地面の暗色部にも効く。
- hardware_experiment/compile.log、output_files/probe.fit.summary、attempt1/、attempt2/：配置失敗のログ。実機試験は行っていない。
- MANIFEST.json：元v021 ROM、元専用DLL、実機成功signed-pitch RBFが既存の記録済みSHA256から変わっていないことを照合済み。SDへの操作は一切していない。

再ビルドはこの独立フォルダで python -X utf8 build.py、専用DLLは python -X utf8 tools/build_palette_core.py です。現在のsrc/が正本です。tools/implement_red_eye.pyは初回のコピーを加工した履歴用スクリプトで、現ソースへ再実行するものではありません。RTLはhardware_experiment/の最終ソースが正本で、seed2でも配置失敗しています。results/red_eye_capture、v2、v3は初期失敗や古いROMを撮った履歴で、成果物には使っていません。deliverables/の動画と比較だけをレビューしてください。

次に必要なのは、全サイズで目マーカーを出す方法、ボス拡大キャッシュを失わない画像配置、FPGAのLAB削減です。これらを解決し、山の実機化とは別に回帰試験・タイミング検証を通してから、許可と安全条件を確認した実機試験へ進めます。
