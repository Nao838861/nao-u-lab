# 赤目＋暗緑と、赤目＋黒の見た目比較

最新の高精細画像・6音声を保つ赤目r6から、暗緑 `$09` を黒 `$0F` にした独立比較版を作成した。**見た目確認用で、正式採用していない。** 元ROM・RBF・SDを変更せず、実機操作もしていない。

## 共有色への影響

| 部分 | 黒版で見える変化 |
|---|---|
| 地面 | 最も暗い帯や模様が黒になる。中間緑 `$19` と明緑 `$29` はそのまま。黒い帯の面積が広く見える。 |
| 森・山 | 暗緑で表していた陰影が黒になる。明るい葉や山の灰色は同じ。暗部どうしが接する箇所は一体に見えやすい。 |
| 敵・木・ボス | 暗緑の陰影が黒になる。形・解像度、灰色・明緑、赤目は維持。近い敵では黒い部位が強く見える。ボスの瞳を追加で赤くした変更はない。 |
| 自機本体 | ネイティブスプライトの青・黄・紫・茶色など、不透明な色番号は変更していない。抜き部分はその場所の背景を表示する。 |
| 自機の影 | もともとの黒 `$0F` を維持。背景の地面も黒くなった部分に重なると影の境界が見えにくくなる。地面比較の画像で確認できる。 |
| HUD | 共有する暗緑の地色が黒になる。文字の灰色はそのまま。 |
| 空・赤目 | 空の紫 `$14`、目の赤 `$16` は変更なし。赤目9,924画素の出現数も同じ。 |

この案は、敵だけに黒を足す処理ではなく、**共有暗色を黒へ置き換える案**。背景の色番号0は共通なので、暗緑を保った背景と黒い敵の陰影をこの1か所の変更だけで分離できない。自機や影ですでに黒を使っていたため、画面全体の同時色数を増やす変更でもない。

見た目の比較では、黒版は敵の陰影と灰色の差が強く、赤も強く見える。一方、地面・森・HUDの暗部が広く黒くなるため、元の緑のまとまりを維持するなら左の暗緑版が穏やか。追加色の導入を検討する場合も、この共有色への影響を分けて判断する必要がある。

## 変更の範囲と検証

ROM全体の差はパレットの **8バイトだけ**（オフセット3363,3367,3371,3375,3379,3383,3387,3391）。4つの背景パレットと4つのスプライトパレットの透明／共有色エントリを `$09` → `$0F` にそろえた。画像、音声、GSUプログラム、CPUの処理、入力、難易度など、それ以外のROMバイトはr6と同じ。`palette_change.patch` はr6のソースへ反映する場合の差分。

元のr6と同じSelect無敵・移動・連射・Start操作で、通常敵→ボス→通常敵を1800フィールド通した。元r6の実PPU動画と新しい黒版の実PPU動画、**110,592,000画素**を比較した。

- 変化18,577,132画素は、すべて暗緑RGB `(11,72,0)` →黒 `(0,0,0)`。
- その置き換え以外の画素差は **0**。
- 赤RGB `(181,49,32)` の画素は双方9,924で一致。赤が新たに背景へ広がる変化はない。
- 全1800サンプルのテレメトリはr6と一致。締切超過は双方20回で、追加負荷はない。これは元から残る超過が0になったという意味ではない。
- 音声のソース・ドライバ・データはROMの8バイト差以外が一致することで保持を確認。動画音声は双方ピーク6,792、クリップ0で無音ではない。採取したPCMは終了部分のサンプル数も異なり、バイト一致はしないため、同一波形の証明とはしない。左右比較動画では左の音声トラックを1本使う。

詳細値は `COMPARISON.json`、変更位置とハッシュは `VARIANT_MANIFEST.json`。

## ROMと動作条件

黒版ROM: `MonoSH_RedEye_Audio_v034_r6_BLACK_RESEARCH_UNTESTED.nes`

SHA256: `474e9ce9fd505b7300493744c0c6933e937463321663b178bdb7833ee0806f16`

元の暗緑r6 ROM SHA256: `879ace700f04a95dc0ec0b373bb3e92635f2b226a057e4ca8fa2ac74fca2b39f`（未変更）。

専用Mesen DLLは `red_eye_latest_audio_v034_r6/runtime/MesenCore.dll` を共用。SHA256 `ba6118ababf6d59e55ab9654ddff5a354ae8dd0b934aad520f38b80e2803ab92`。新しいDLLや回路は必要ない。目の色4を扱う回路はr6のものが必要で、r6以前のRBFへ戻すとこのROMの赤目は成立しない。

対応RBFは既存の `MonoSH_RedEye_Audio_v034_r6_HW_UNTESTED_fd7c70d6.rbf`、SHA256 `fd7c70d67c6587d538c68908003f54d65c980d5e7837c41c5e54849bed5e1e4f`。これも変更していない。r6時のfitは392/392 LAB・6242/6272 LE、内部setup最小0.501ns、hold最小0.144ns。今回はパレットだけなので再fitしていない。

**実機では未確認。** r6と同じく、`ppu_oe` のクロックと69入力・97出力の外部タイミングが未制約。最新の山・森処理の実回路への完全移植、最新音源の実機出力、ボス目の素材領域の確定も未解決。この比較で実機対応済みとは扱わない。

再現は親フォルダの `prepare_red_black_comparison.py` にある8バイトのROM変換、`tools/capture_red_latest.py` による専用Mesen採取、`tools/compare_black_latest.py` による左右比較。操作コマンド・元ROM・DLL・ラベルのパスは `VARIANT_MANIFEST.json` と各スクリプトに保存している。
