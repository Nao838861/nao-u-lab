# r7：背景の暗緑を保ち、物体に黒を追加する独立試作

**可能。共通色0は暗緑 `$09` のまま固定し、8×1内の必要色が黒用パレットに収まる場合だけ、最終的に見える物体の暗部を黒へ変える。収まらない場合は物体の黒を暗緑へ戻す。** 赤目と露出した背景を優先する。前回の全体暗緑→黒版とは別の方式・別フォルダで、正式採用はしていない。

地面の暗緑と中間緑、空の紫、遠景の森・山の色、HUD、自機の不透明な色を維持した。前景の敵・木・岩・弾など、GSUで描く物体の暗部だけが黒の候補となる。背景として合成する遠景の森と、前景物体として描く木は区別する。自機の影は従来から黒で、地面を全体黒化していないため、前回の全体置換のように暗い地面へ一斉に埋もれる変化はない。

赤目のある8×1や、露出した紫／中間緑を守る8×1では物体の暗部が暗緑へ戻る。物体内に黒と暗緑の境界、目の周囲の暗緑の区間が残る。移動・縮小で8×1との対応が変わると切り替わりも起きうる。すべての距離の敵を常に黒くする方式ではない。

## 実際のPPUパレットと4組の制約

現行の固定構成では、背景用4組は空／地面で共用する。空に4組・地面に別の4組を同時に持つ構成ではない。8×1属性が供給するのは2bitのパレット番号で、区間ごとの自由なRGB表ではない。

| 背景パレット番号 | 色0 | 色1 | 色2 | 色3 | 役割 |
|---|---|---|---|---|---|
| 0 | `$09` 暗緑 | `$10` 灰 | `$29` 明緑 | `$19` 中間緑 | 地面の通常色 |
| 1 | `$09` 暗緑 | `$10` 灰 | `$29` 明緑 | `$14` 紫 | 空の通常色 |
| 2 | `$09` 暗緑 | `$10` 灰 | `$29` 明緑 | `$16` 赤 | 赤目 |
| 3 | `$09` 暗緑 | `$10` 灰 | `$29` 明緑 | `$0F` 黒 | 物体の黒 |

PPUの背景色番号0は共通の背景色 `$3F00` を使う。パレット3の色0だけを黒へ変えて、背景の暗緑と使い分けることはできない。今回は全ての色0エントリを元の `$09` に保つ。ネイティブスプライトの色0は透明で、そのミラーエントリも `$09` のまま。不透明な自機の各色は変えない。

**暗緑＋黒は同じ8×1で両立できる。** 共通色0に暗緑を残し、パレット3の色3を物体の黒に使うため。露出した背景の暗緑は色0、物体の黒は色3という別の番号になる。

一方、暗緑を保つ以上、各組の自由な非共通色は3枠。灰・明緑・赤・黒の4種類を同一区間に要求すると収まらない。区間に暗緑の画素が実際になくても、共通色0をその区間だけ別色へ転用できるわけではない。背景の紫／中間緑も含めて4種類の非共通色が必要な場合も同様。

また、灰・赤・黒だけなら共通暗緑と合わせて4色で収まるが、現在のパレット3には赤がない。このような**1区間の色数上は可能でも、利用可能な4組の編成にはない**場合もある。これを「画素当たりの上限で絶対不可能」とは扱わない。別の5組目を追加することは2bit属性だけではできず、既存組の変更やパレットRAM更新と整合する新しい制御が必要となる。

今回の4組が固定された条件では、黒を含む必要色集合が利用可能な組に収まる全ブロックで黒を使い、収まらない時だけ黒を暗緑へ戻す。赤目を消して黒を優先することはしない。

## 色・透明・重なりの判定

GSUはr6と同じソース／実行エンジン／460Bプログラム。画像の0は透明、1は灰、2は明緑、3は物体の暗部、4は不透明な目。フレームバッファでは色4が低2bit=0と既存alpha bitで表される。

```text
mask = fxLow | fxHigh | alpha
eyes = alpha & ~(fxLow | fxHigh)
dark = fxLow & fxHigh
exposedBackground3 = bgLow & bgHigh & ~mask

露出背景3あり → 通常の地面／空パレット。物体の黒と目は暗緑へ戻す
露出背景3なし・目あり → 赤目パレット2。物体の黒は暗緑へ戻す
露出背景3なし・目なし → 黒パレット3。物体darkだけ色3へ写す
```

地面の背景bitplaneは既存の表示色へ変換してから判定する。背景の色0・1・2は4組で同一なので、黒用に替えても露出した背景は変わらない。背景3は、地面なら中間緑、空なら紫なので、その画素が**露出している場合だけ**競合になる。物体に完全に隠れた背景色は数えない。

物体同士の重なりは、GSUのPLOTが完了した最終bitplaneとalphaを使う。透明0は下の物体を保持し、後から通常色で描いた部分は既存alpha処理で古い目マスクを消す。したがって隠れた敵の元画像を色集合へ足したり、透明0を黒とみなしたりしない。全GSU物体の色3を対象とするため、敵・木などの個別IDを保存する追加メモリも使わない。

ネイティブOAMの自機・影はこの背景合成より後にPPUで重なる。そこに隠れる背景も保守的に維持する。OAMで隠れることを根拠に背景色を捨てる最適化は行っていない。後段の透明・優先順位まで含めて背景を壊さないための制約である。

## 実データでの4組目の選択と限界

既存の地面・空・赤目の3組を維持し、黒＋残る5色から2色を選ぶ全10案を比較した。最終GSU合成入力の各色の有無を、8×1ごとに数えた。隠れた物体は除外、露出背景は保持、赤目はr6で赤くなる条件を維持する。

30秒中の合成呼び出し15,265,536ブロックで、物体の黒候補は延べ4,170,377画素。これはバッファに合成した候補の数であり、実際に表示された画素だけの集計ではない。

| 4組目の色集合 | 黒にできる候補画素 |
|---|---:|
| 暗緑・灰・明緑・黒（採用案） | **3,641,512** |
| 暗緑・明緑・紫・黒 | 3,321,806 |
| 暗緑・明緑・中間緑・黒 | 3,026,286 |
| 暗緑・明緑・赤・黒 | 2,972,663 |
| 暗緑・灰・赤・黒 | 1,750,898 |

全10案と必要色集合別の集計は `palette_budget.json`。代替案は色集合としての上限評価であり、今回その回路や動画まで実装したという意味ではない。今回の場面と既存3組を保つ条件下では、灰＋明緑を残す案が最大だった。別のステージや素材で同じ順位とは限らない。

採用案は黒候補の **87.3185%** を黒にでき、528,865画素分が暗緑へ戻る。内訳は露出した空の紫458,588、中間緑60,906、赤目との同居9,371。これらのうち、どの4色組でも非共通色3枠を超えるものは8,931。残る519,934は区間単独なら表現可能な組もあるが、今回の4組にその組がないというパレット編成上の制約である。

## 画質・背景保護の検証

- 独立した画素oracleとC++、実際の `racing_display.vhd` の抽出式を比較。空／地面の全背景bitplaneパターン、hide、透明0／灰／明緑／暗部／目の全5^8前景列など **1,824,644条件、14,597,152画素**が一致した。露出した背景の画素は元のNES色と一致し、目の赤もr6条件を保持する。色0はパレットごとの別色として扱わず、共通背景色で検証した。`compositor_tests.json`。
- 実PPU出力1800枚、110,592,000画素をr6と比較。差は暗緑→黒の **2,494,124画素だけ**。赤の出現9,924画素は同数で、それ以外のRGB変化は0。黒の変化があるフレームは1761、最大5892画素／フレーム。`native_comparison.json`。
- RGB差分だけでは、元の暗緑が背景か物体かを区別できない。背景保護の証拠は、別途の入力maskに基づく上記画素oracle／RTL試験と組み合わせる。画像だけから所有者を推測して保証しているわけではない。
- 110nsメモリモデルのHUD所有権65,536条件、native CHR40位相329,240確認、連続フレーム0/19/39nsと途中stopの計7項目を新しい表示RTLで再試験し合格。`strict_ppu_tests.json`。機能シミュレーションで、配置配線後SDFや実基板の測定ではない。

## 処理時間・メモリ・回路

ROMはr6から背景パレット3の色3 `$14` → `$0F` の **1バイトだけ**変更。共通色0、他のパレット、画像、音声、CPU命令、GSUバイナリは同じ。r6の色4透明判定回路も変更していない。追加は表示合成で黒を選ぶ条件とマスクで、サイクル数・転送形式は増やさない。

| 項目 | r6 | r7 |
|---|---:|---:|
| GSUコード | 460B | **同一460B、追加命令0** |
| アトラス全体 | 7168B | 同一7168B |
| 追加の物体／alphaマスクRAM | 0 | **0** |
| FPGAメモリ | 222464bit | 同じ222464bit |
| DSP9 | 29/30 | 29/30 |
| fit後LE | 6242/6272 | **6246/6272** |
| LAB | 392/392 | **392/392** |
| 1800フィールド締切超過 | 20 | **20** |
| queue_drops | 22 | **22** |
| present_count最終値 | 1786 | **1786** |

GSU画像プログラムと実行エンジンをバイト一致で確認し、追加描画命令はない。r6で測定したEm1 112×120の5.4063ms、ボス胴80×54の2.5718msなど、GSU部分を増やす変更ではない。今回の実測でも全1800サンプルの描画・世代・位相・入力等のテレメトリが一致した。既存の20回の超過が残るため、「毎フィールド新しい描画が完成する60fpsを達成」とは扱わない。

専用Mesen内の集計用カウンタはホスト側2KiBで、カートリッジのRAMではない。画像自体やGSUの不透明マスクは増やしていない。音声PRG89～99と音声ルーティングのソースもr6と一致する。

Quartusで新しくフルコンパイルした。seed2は393/392 LABでfit失敗したが、同一論理をseed1で配置すると392/392 LABで成功した。失敗時のレポートも `../results/hw_seed2_no_fit` に保存した。最終は0エラー・54警告、制約済み内部パスの最小setup **0.364ns**、hold **0.143ns**、recovery6.181ns、removal0.951ns。資源もタイミングも余裕は小さく、別の変更を追加してもfitする保証はない。

**外部タイミングは未完了。** 新しいSTAにも`ppu_oe`未制約クロック、69入力・97出力bitのI/O遅延未制約が残る。PSRAM・CPU/PPUストローブ・基板／レベル変換・SPIのmin/max条件が必要。仮のfalse pathで消していない。内部STAに正の余裕があることを実機動作の証明とはしない。
