# r9：局所黒・赤目を残し、爆発とボス弾へ既存の赤を共有

**別案のr9を作成した。背景4パレットと共通の暗緑を一切変更せず、SFCで暖色だった爆発4素材とボス弾に、既存の赤 `$16` を使う。** 明部は既存の灰 `$10` のまま。白・オレンジの完全再現ではないが、黒＋灰より元の暖色へ近づける控えめな案で、前案のように局所黒を全体から失わない。

fitは392/392 LAB、6236/6272 LE。最終的に**新しいタイミング除外を残さず、元r7と同じSDCで、同じ配置配線の全制約済みチェックを再解析して合格**した。setup最小0.840ns、hold最小0.145ns。実機・外部電気条件の確認は別で、今回の作業では実機操作やSD書き込みをしていない。

## 元画像で確認した色と形

同梱のSFC変換元はインデックスPNGなので、その灰色のPNG表示色を原色とはみなさない。BGR555の `palette.bin`、セルごとの `cells.bin`、`offsets.bin` を使って復元した。証拠とSHAは `SFC_COLOR_EVIDENCE.json`。

| 対象 | 復元された使用色 |
|---|---|
| 爆発source5/39/40/41 | 暗赤 `(123,8,0)`、クリーム `(255,246,213)` |
| ボス弾source31 | 上記2色＋橙 `(255,123,24)` |
| 通常敵弾source6/7/8/37 | 青系。詳細RGBと使用量は上記JSON |

r9の赤 `$16` の実出力は `(181,49,32)`。色だけの単純なRGB距離では、元の暗赤から黒は123.26、r9赤は77.90。元の橙から黒は284.13、r9赤は104.96となり、暖色の方向へ近づく。これは知覚尺度や全画面再現率ではなく、単一材質色の目安。クリームに対する明部の灰は未改善で、元のボス弾の暗赤と橙も別々には復元していない。

爆発56×42、ボス弾32×32など、r7の高精細な形・透明・UV・座標は維持。元画像比較のr7/r9列は色番号の理想的な近似を示し、8×1の競合を反映した実画面は動画の方で確認する。

## 4パレットを維持する方法

r7のパレット32バイトはROM内で完全一致のまま。PPU色0も暗緑 `$09` のままで、地面・空・遠景の森・山・自機のパレットを変更していない。

| 背景組 | 共通色0 | 色1 | 色2 | 色3 |
|---|---|---|---|---|
| 0 地面 | 暗緑09 | 灰10 | 明緑29 | 中間緑19 |
| 1 空 | 暗緑09 | 灰10 | 明緑29 | 紫14 |
| 2 赤 | 暗緑09 | 灰10 | 明緑29 | 赤16 |
| 3 局所黒 | 暗緑09 | 灰10 | 明緑29 | 黒0F |

組2を目だけでなく効果の赤い部分にも使う。新たなRGB色番号や5組目を足さず、既存色の使い先を増やす方式。白・橙用に組3を奪った前案とは異なり、組3の局所黒はそのまま残す。

8×1内で露出した背景の色3（中間緑／紫）が必要なら、その通常パレットを優先し、効果の赤も暗緑へ戻す。露出背景3がなく、目または効果の赤があれば組2を使い、同じ区間の通常物体の黒は暗緑へ戻す。赤がなければ従来どおり組3の局所黒を使う。灰・明緑・共通暗緑は全組で同じなので、露出背景は変色しない。

**黒が暗緑へ戻るのは、赤と同じ8×1で黒用パレットと両立しない箇所など、従来と同じ背景優先ルールの範囲。** 色の追加のために、無関係な全画面の黒を外す処理はしない。

## タグ・圧縮・共有資源の見直し

前案は効果タグのためにPixel Cacheの別ビットを保持し、レジスタが17増えた。r9では、描画時にタグを既存のbit2へ畳み込み、すでにある1bitマスクを使う。低2bit＋マスクの計3bitで区別する。

| 合成クラス | 意味 |
|---|---|
| 0 | 透明。下の画素を維持 |
| 1 / 2 / 3 | 通常の灰／明緑／暗部（局所黒候補） |
| 4 | 不透明な目。赤候補 |
| 5 / 6 | タグ付き効果の灰／明緑。共通色のまま |
| 7 | タグ付き効果の暗部。赤候補 |

GSUの既存COLOR高位ニブル固定機能を使い、オブジェクト開始時にタグを一度設定する。RACING 2bppのPLOTで、色のbit2とタグのbit4をORして既存キャッシュbit2へ格納する。**透明判定の後に畳む**ため、透明0にタグがあるだけでは画素を書かず、背景や下の物体を赤くしない。

タグは各画素を描いた時点で保存する。後のオブジェクトのタグを見て一括判定しないので、同じ8画素キャッシュに複数物体が混在しても所有者を維持できる。通常物体で上書きした画素はタグを消し、透明な穴は下の画素とタグを残す。

赤の選択式は `alpha & ~(fxLow ^ fxHigh)`。これによりクラス4の目と7の効果を同じ赤として扱う。クラス5/6は赤とみなさない。GSUの通常の非RACINGモードは元の色格納のまま。

画像の圧縮ペイロード・行ポインタ・各素材の格納アドレスは維持した。ヘッダbit6を種類フラグにするため、RLE幅を「low6＋1」へ変更し、packedはlow5をstrideとして使う。幅64の通常素材を誤って効果と判定しないよう、**全RLEヘッダとGSUデコーダを同じ版で更新**した。単にフラグだけを旧アトラスへ足す組み合わせは使わない。

| 項目 | r7 | r9 |
|---|---:|---:|
| GSUプログラム | 460B | 478B / 512B |
| アトラス全体 | 7168B | 同じ7168B |
| キャッシュ前の使用量 | 6930B | 同じ6930B |
| 64B行キャッシュ前の空き | 174B | 同じ174B |
| 追加の画素マスクRAM | 0 | 0 |
| FPGAメモリ | 222464bit | 同じ222464bit |
| レジスタ | 2450 | 2451 |

画素ごとのGSUタグ命令を追加せず、開始時の設定と行ヘッダの処理に限定した。21,135,360画素のGSU面データ検証で、元の形を維持することも確認した。

## 画質・背景保護・重なり・互換性

- 独立した画素oracleとC++／抽出RTLで、背景の全bitplaneパターン、hide、8クラスなど294,912条件・2,359,296画素が一致。共通色0は実PPUの共通背景色として検証し、露出背景1,213,293画素を保持。
- 実際のGSUの18素材・215条件・21,135,360画素の面データ比較に合格。
- 実際の新GSU RTLで、目、爆発4素材、ボス弾、通常木の上書きの7コマンドを実行。面とタグの読み出し全32,768バイトが独立期待値と一致。混在キャッシュと上書き後のタグも確認した。
- さらにタグ付き効果を全て64×80へ拡大して高速サンプラを通し、通常木を8画素境界からずらしたx43へ重ねる7コマンドも実行。追加の32,768バイト比較が一致し、繰り返し画素と部分上書きでもタグが残留しないことを確認した。`GSU_FAST_RTL_METADATA_TESTS.json`。
- HUD、native CHR、110nsメモリモデルの連続フレーム0/19/39ns、途中stopの計7項目を新RTLで実施し合格。これは機能シミュレーションであり、SDFや実基板の検証ではない。
- 旧r7 ROMを新しいr9専用Mesenコアで1800フィールド動かし、RGB画像ハッシュと全テレメトリが元のr7実行と完全一致。`R7_COMPATIBILITY.json`。

r7とr9の実PPU1800枚を比較すると、元の目の赤9,924画素はすべて保持され、**効果の赤563,979画素**が追加された。変化は黒／暗緑→赤と、同じ区間の黒→暗緑だけ。

通常物体の黒が暗緑へ戻った量は **12,151画素**。前案r8の1,930,154画素から大幅に減った。これは効果の赤と同じ8×1で黒を同時に出せないための局所的な退避であり、効果自体の黒が意図して赤へ変わった画素とは分けて集計している。実画像だけでは前景／背景の所有者を区別できないため、背景保護は上記mask付きoracleと組み合わせて評価した。

合成候補の効果暗部804,779画素中、赤にできたものは698,240（約86.8%）、露出背景3との競合で暗緑へ戻ったものは106,539。これは未表示バッファやOAMに隠れる候補を含む延べ集計で、画面に表示した画素だけの割合ではない。`COLOUR_COVERAGE.json`。

## fitとタイミング：最終成果物に新しい除外はない

seed1は393/392 LABでfit失敗。seed2はfitしたが、最初はM2入力→トップの最初のFF `m2_age[0]` にhold−0.029nsがあった。hold最適化を有効にしただけでは同じ違反が残った。失敗レポートは `../results/hw_seed1_failed`、`hw_seed2_hold_failed`、`hw_seed2_all_hold_failed` などに保存した。

トップのソースでは、独立したM2を50MHzの8段シフトへ入れ、判定で使うのは第2段と第8段。そこで配置を助ける試みとして、先頭FFへのM2データ1経路だけに一時的なCDC除外を与えた。後続段や他のM2経路をまとめて除外してはいない。

**配置後、その一時除外を完全に外し、同一の配置配線を元r7の全制約で再解析した。最終 `clocks.sdc` は元r7とバイト一致。M2→先頭FFと先頭→第2段も解析対象へ戻したことを別スクリプトで確認した。** 同じRBFのまま、次の全制約済みチェックが正の余裕になった。

| 最終値 | 結果 |
|---|---:|
| LAB | 392 / 392 |
| LE | 6236 / 6272 |
| メモリ | 222464bit |
| DSP9 | 29 / 30 |
| setup最小余裕 | 0.840ns |
| hold最小余裕 | 0.145ns |
| recovery最小余裕 | 5.861ns |

`FULL_CONSTRAINT_RECHECK.json`、`FULL_CONSTRAINT_AUDIT.log`、`FINAL_EXCEPTIONS.rpt`、`probe.sta.rpt` に最終結果を保存した。`M2_CDC_REVIEW.txt` は配置過程の記録で、最終除外を残したという意味ではない。元の負余裕を消したレポートだけで合格とはしていない。

再ビルドは `tools/build_shared_hardware.py` に、補助制約で配置→補助制約を外す→元のSDCでSTA→負余裕なら停止、という手順を記録した。任意のseedで単純にfull compileすれば同じ配置になるとは言わない。

**外部・実機の成立は別。** `ppu_oe` の未制約クロック、69入力・97出力のI/O条件、MTBF、CPU/PPU/PSRAM/SPIのmin/max、基板・レベル変換遅延は未解決。今回の内部STAの数値を外部電気条件の保証へ拡張しない。

## 通常の青い敵弾を変更しなかった理由

SFCの通常敵弾は青系で、暖色ではない。例えば暗青 `(49,65,148)` から黒への単純RGB距離は168.91、既存赤へは176.45。通常弾まで赤くするのは原色へ近づく対処ではないので、タグの対象から外した。16相アニメ・形・通常の灰／黒を維持する。

青を新たな背景色として持たせる案も検討した。4組目を「暗緑・灰・青・黒」にすると明緑を失い、r7の集計に対する黒候補の表現可能上限は3,641,512→1,741,527（47.8%）へ落ちる。「暗緑・青・明緑・黒」なら81.6%だが、同じ8×1に弾の灰ハイライトを保持できない。どちらも露出した空の紫／地面中間緑とは別の競合がある。

これは以前のr7候補ヒストグラムを使う色集合の上限評価で、青い弾の完成ROM／回路を実装・fitした値ではない。黒を維持する優先度に照らし、今回は採用しない。`BLUE_PALETTE_BUDGET.json`。通常弾の青、真の白／橙、ボス弾の元の3色分離は残件である。

## 受け渡しと残件

既存ROM・RBF・SDは上書きせず、元r7のROM・DLL・RBFのSHAが不変であることを確認した。r9は独立した一致する組として保存し、正式採用や実機確認はしていない。

このRBFはr7実験回路を基にした候補で、最新の山・森の専用Mesen処理が実回路へ完全に移植済みとは確認していない。別担当の最新実機枝へ取り込む場合は、差分を統合した後でその枝について再fit／STAが必要。今回のfit数値を別の回路へそのまま流用しない。

実機での起動・継続、音源の実機出力、外部タイミング、ボスの目の素材領域は未確認。今回進められたのは、4パレットと局所黒を残した効果の赤共有、タグの資源圧縮、背景と重なりの保護、機能試験・最終全制約STA・同一操作の速度と互換性の確認である。

ROM再生成は `tools/build_shared_red_rom.py`。r8へ依存せず、保存したr7と現在のソースから同じSHAのr9を生成できる。検証は `run_shared_red_tests.py`、`test_red_detail.py`、`test_rtl_latest.py`、`run_shared_strict_ppu.py`、`verify_shared_compatibility.py`。いずれもこの研究コピー内に出力し、SDや実機を操作しない。
