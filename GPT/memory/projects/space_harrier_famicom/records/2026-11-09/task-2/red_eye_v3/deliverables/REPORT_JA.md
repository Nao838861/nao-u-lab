赤い目 v3：切り替え負荷の削減と未対応部分の限界

キャッシュ切り替えの更新区間を約27.5msから約3.44msへ短縮しました。GSUプログラム、背景優先の合成式、FPGA回路はv2と同じです。小さい敵とボスの赤化は今回の実行ROMには追加していません。その条件と容量をモデルで調べ、未制約の外部タイミングもポート単位で整理しました。

元v021、実機成功済みsigned-pitch RBF、赤い目v1/v2のROM、v2の候補RBFは記録済みSHA256から変わっていません。既存ファイルを上書きせず、全て新規 red_eye_v3/ 以下に作成しました。実機操作・SD書き込みは行っていません。

切り替えを短くした方法

v2は画像10ページ2,560バイトとGSUコード512バイトの計3,072バイトを転送しました。比較すると実際に違うのは画像1,036バイト、コード446バイトの計1,482バイトでした。v3は違うアドレスだけを更新します。同じ書き込み値をまとめ、LDA即値1回に複数のSTA絶対アドレスを続けたコードを生成しました。

| 更新方向 | 変更バイト | 値の種類 | 書込コード容量 | 実測CPUクロック | 更新区間 |
|---|---:|---:|---:|---:|---:|
| ステージ→ボス | 1,482 | 110 | 4,667B | 6,160 | 3.44178ms |
| ボス→ステージ | 1,482 | 109 | 4,665B | 6,158 | 3.44066ms |

値は専用Mesen上のNTSC CPU 1,789,773Hzで、eye_cache_begin～eye_cache_endの区間を測りました。v2の同じ区間は49,134～49,356クロック、27.45～27.58msでした。約87.5%の削減です。今回の4回の計測ではPPUフレーム境界をまたぎませんでしたが、開始位相によらず絶対にまたがないことを保証する試験ではありません。実機測定でもありません。

1,482個のSTA絶対アドレスだけでも5,928 CPUクロック、命令モデルで約3.312msかかります。現データの書き換え数を維持する限り、今回の実測との差は約0.13msです。これ以上の大幅な削減には、書き換え自体を減らすか、全画像を常駐させる方式が必要です。これは6502命令モデルでの下限で、実機外部メモリの保証値ではありません。

転送はv2と同じくGSUとFILLの停止中、preloaded=0で行います。GSUは全更新が完了する前に次の描画を開始できません。画像・span・不透明ビットの解釈は変えていません。GSU命令キャッシュは起動時に全て初期化済みで、今回の部分更新は未変更部分も有効なままの状態を前提にします。4回の切り替え後に、作業画像7,168バイトとプログラム512バイトをそれぞれ期待値と全比較し、一致しました。これはMesenの実行結果で、GSU回路の部分キャッシュ書込を実機で測った結果ではありません。

差分コードはPRGバンク83と89へ置きます。v2の追加バンク1個に対してv3は2個です。ROM全体は元から予約した1MiB PRG内に収まり、ファイルサイズ1,179,664バイトは変わりません。実行時RAM、GSUコード510/512バイト、FPGAの使用量は増えていません。

小さい敵の赤化：できる部分と原理的に残る部分

現ROMは引き続きdu<256の拡大経路だけが赤マーカーを扱います。縮小経路へ同じ瞳マーカーを追加した場合を、既存の座標・Nearest Neighbor・透明部・背景優先を変えずに計算しました。EM0／EM1の全サイズと空／地面88条件、横8通りを検査し、モデル内の1,598,272画素について、指定瞳以外を変えないことを確認しています。縮小経路の実GSUコードは未実装で、以下はモデル値です。

| 実サイズ例 | 今のROM | 全サイズ経路を実装した場合の空での赤画素数（横8通り） |
|---|---|---:|
| EM0 32×18 | 赤なし | 9～12 |
| EM0 28×16 | 赤なし | 8～12 |
| EM0 20×12 | 赤なし | 0～3 |
| EM0 16×10 | 赤なし | 0～3 |
| EM0 12×8 | 赤なし | 0～2 |
| EM0 8×4／4×4 | 赤なし | 0。元の縮小で瞳サンプル自体が0 |
| 開いたEM1 12×14 | 赤なし | 0。元の縮小で瞳サンプル自体が0 |

瞳を1画素もサンプルしないサイズでは、同じ縮小規則を守ったまま赤を表示することはできません。強制的に1画素を足したり、別の元画素を選ぶ縮小へ変えたりすると、「既存画素を守る」条件を変更することになります。瞳を拾うサイズでも、8×1の透明部から空や中間緑が露出する横位置では、背景優先で赤を取りやめる場合があります。

全サイズ化に向けた容量の検討

単純に4つの32×32素材へ1bitマスクを付けると512バイト追加です。現在の7,168バイトの画像領域へそのまま足すと7,680バイトになり、512バイト超過します。一方、不要な上下の透明行だけを除いて全画像を再配置する案は、実際にデータを生成して7,136バイトに収まりました。

| 再配置案の内訳 | 容量 |
|---|---:|
| 元のpacked7素材＋回転弾4姿勢 | 2,816B |
| EM1 byte画像 | 1,024B |
| EM0 byte画像（実内容17行） | 544B |
| ボス本体byte画像（実内容22行） | 704B |
| ボス顔byte画像 | 1,024B |
| ボスのspan lookup＋span | 1,024B |
| 合計 | 7,136B、残り32B |

4つのbyte画像の全4,096元画素（既存の指定瞳だけ色4化を許す）と、11個のpacked素材ブロック、ボスspanの参照内容を比較しました。透明部の削除ではなく、描画されない上下のゼロ行を格納から省き、V原点を補正した案です。

この案を動かすにはCPUの素材ID再割り当て、GSUの4素材ディスパッチ、縮小も扱うbyteサンプラ、移動したlookup参照が必要です。現GSUは510/512バイトで残り2バイトしかなく、既存経路の組み直しが前提です。再配置データはNOT_RUNNABLEと明記しており、現ROMには組み込んでいません。新サンプラの実行時間や全512バイト内への実装可否は未検証です。画像容量だけを理由に不可能とは言えませんが、現時点で動作・速度を保証できる案でもありません。

ボスの赤い目

現在のボス顔は参照パレットbank7の黒、暗緑(8,57,16)、緑(57,189,49)、明色(205,205,164)を使い、赤系色から瞳を自動抽出できません。本体bank2は縮小後に赤茶色と分類される103画素を含みますが、材質の色と瞳を区別できません。これを全て赤へ替えると目以外を変えるおそれがあります。

瞳として変更してよい元座標をまだ検証できていないため、ボスの画素は現状を維持しました。再配置案でもボスは元色のままです。ボスの瞳座標または確認可能な参照画像を特定し、その部分だけをマーカーにする工程が残っています。

外部タイミングの未制約

回路・制約・DLLはv2から変更していません。コピーしたRBFもSHA256 0740d5ff1f7856665484637206e829eca16cf9ef6a57053f67a375e8eec03e9aでバイト一致です。今回新しいfitやSTAを実行したという意味ではありません。

v2の結果は392/392 LAB、6,222/6,272 LE、setup最小0.736ns、hold最小0.123nsです。制約が設定されているクロックはclk=20ns、spi_clk=20ns、m2=500ns、gsu25=40nsです。これらは内部の制約付き経路の結果です。

別に未定義クロックppu_oeがあります。base_sv/map_255.sv:290のnegedge ppu_oeでメニューの属性アドレスを取り込みます。単に周期を仮定してcreate_clockを足すだけでは、アドレスのsetup/holdや50MHzメニューRAM側との関係は確定しません。

以前のRTL回帰はメモリ読み出し110ns、解除15ns、PPUのlow/high各186ns、位相0/19/39nsというデジタルモデルです。これらは基板の実測値でも、PSRAM部品の保証値でもありません。実部品の型番・速度等級、データシートのmin/max、レベル変換と配線遅延、対応する実機のCPU/PPUストローブ条件、MCU SPI設定を確認してから、input/output delay、CDC、根拠のある例外を定義する必要があります。未制約を消すためだけの一括false-pathや仮のゼロdelayは追加していません。

残った作業は、未制約の根拠となる実部品・実機条件の特定、部分命令キャッシュ更新の実機確認、全サイズbyteサンプラの再設計、ボス瞳座標の検証です。山・森は引き続きMesen側だけで、候補RBFへ移植していません。今回の成果は切り替え負荷を削った別ROMと、画像を守る比較結果・未対応部分の定量資料です。実機起動は行っていません。
