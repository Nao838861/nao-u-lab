対象: https://www.gamedeveloper.com/design/postmortem-a-rationally-designed-funny-game---the-making-of-biped-in-hindsight

■ 概要
Game Developer の「Postmortem: A Rationally Designed Funny Game」は、biped を「変な2脚ロボットの協力ゲーム」として完成させるまでに、何を試し、何を捨て、どこへ戻ったかを振り返る制作記録である。biped は ragdoll physics を使った coop action-adventure で、プレイヤーはキャラクター全体ではなく、左右の脚を2本のスティックで直接動かす。歩く、滑る、つかむ、仕掛けに触るといった行為が、身体操作のぎこちなさと物理の予期しない揺れから生まれる。さらに couch coop では、2人が会話し、歩幅やタイミングをそろえ、互いの失敗を補いながら進むことが体験の中心になる。

出発点は狙い澄ました企画ではなく、別プロジェクト内の山登りロボット実験だった。4肢を ragdoll で自然に見せ、さらにプレイヤーに4肢を別々に操作させるのは重すぎる。そこで腕を捨て、2本の脚だけで垂直面を歩く案が出る。結果として、腕のないロボットは登りやすいだけでなく、床を不器用に歩く姿そのものが見ていて楽しい存在になった。記事はこの偶然を bottom-up game dev として扱う。情熱、反復、偶然で見つかった小さな手触りが、当初の大きな冒険企画を押しのけ、2脚ロボット中心の制作へ焦点を変えた。

その後、チームはすぐに core fun を言語化できたわけではない。巨大な長脚版、頭の大きい版、サイズや重さの違うロボット、壁越え、シーソー、レース、音楽に合わせたフィギュアスケートなど、多くの実験を行った。社内発表では「何でもできそう」という期待が集まり、そこから暗いダンジョン、足のライト、死体を使うパズル、PvP、戦闘まで試す。特に PvP は、年齢層を上げ、ゲームを小さく子供っぽく見せないための「強い」案だった。だが playtest では、参加者は楽しみつつも、それは自分たちの知る biped ではないと返した。この失敗が転換点になる。

チームは設計基盤を、脚を自分のペースで動かす快感と、個人の欠点を補い合って共通目標を達成する coop に戻した。そこから生まれた重要な mechanic が、2人が相談し、計画し、文字通り一歩ずつ実行する number mechanic である。これは「歩くことを考える」体験と、2人の tight coordination を同時に要求するため、以後の level design の核になった。記事内の rational design process は、抽象的な好みではなく、入力、学習、失敗頻度、難度曲線、見た目、レベル構成を、core action へ照合していく方法として使われている。

中盤以降の判断も同じ軸で説明される。顔はかわいく表情豊かにしたいが、プレイヤーの注意は脚へ残すべきなので、表情は制限する。6km の ice cave ski level は、slow-paced なレベル群に dynamic range を入れるための魅力的な案だったが、1.5か月かけても狙った wow には届かず、制作量も重すぎたため切られた。Alpha 近辺では、validated mechanics を playground pool として整理し、Color、Cliffhanger、Balance のように名前を付け、そこから biped らしい要素だけでレベルを作る。最後の polish でも、number platform 付近で小さな入力が誤作動を生む問題に対して、足を見えない comfortable location に寄せる補助を入れ、挑戦の前に基本アクセシビリティを守っている。結論は、core fun に忠実でいること、合理的な設計階層を持つこと、チームと時間が許す以上に作りすぎないことが、作りたい版のゲームを成立させたというもの。

■ 内容分析
この記事の強さは、「偶然見つけた面白さ」と「rational design」が対立していない点にある。biped の核は最初から理論で設計されたものではなく、腕を捨てたら妙に楽しい、2体並ぶと寂しさが消える、物理の失敗が笑いになる、という観察から出ている。一方で、そこから先は何でも足すのではなく、各 mechanic が「脚を動かす快感」と「補完型 coop」を濃くするかで選別される。発見は bottom-up、収束は rational という二段構えになっている。

特に PvP の扱いが重要である。PvP と戦闘は、プロダクト不安への答えとしては強い。テンポを上げられるし、対象年齢も広げられそうに見える。しかし playtest が示したのは、楽しさの有無ではなく identity のずれだった。「面白いが biped ではない」という否定は、通常の面白さ評価だけでは拾いにくい。これは制作中の危険な追加要素を測る良い例で、強い刺激、広い訴求、作った mechanic の総動員が、作品の中心を薄める場合がある。

もう一つの軸は、削除と保存の分離である。ski level は大量に作った上で切られたが、全実験を無駄にしたわけではない。validated mechanics は playground pool に残し、atomic parameters を理解したうえで、レベル、難度、見た目のペース配分へ使う。つまり、試した要素をそのまま製品へ入れるのではなく、「使えることが分かった mechanic」と「今回の core に入れる mechanic」を分けている。この分離があるから、実験を恐れず、同時に製品を太らせすぎない。

ただし記事は、biped の成功を綺麗に整理した hindsight でもある。PvP や ski level の具体的な playtest 指標、どの mechanic が pool から落ちたか、solo mission が coop core とどの程度 tension を持ったかまでは深くない。読むべき教訓は「rational design を導入すれば迷わない」ではなく、迷った後に戻れる言語を作ること、そして playtest の否定を identity 判定として扱えることにある。

■ 自分達の環境への適用
Nao_u_BOT の短期プロトタイプでは、新要素を足す時に「面白いか」だけでなく「この作品として濃くなるか」を別軸で見る必要がある。BOMB や shot_log 系のように、操作、ログ、演出、敵、リスクを追加できる余地が多い作品ほど、PvP 的な強い案に引っ張られやすい。Phase 0/Phase 2 の staging に、core action、補完または対立の関係、プレイヤーが読むべき失敗、identity を薄める追加要素、の4項目を置くと、biped の PvP 失敗を小さな検査にできる。

また、playground pool の考え方は memory に向く。試作で「動いた」「面白かった」要素を即採用扱いにせず、validated mechanics pool と product mechanics を分けて記録する。各 mechanic には入力、学習、失敗頻度、難度曲線、見た目依存の有無を短く付ける。こうしておくと、今作では切った ski level 的な案も、次作の材料として残せる。重要なのは、削除を敗北ではなく、core に対する照合結果として残すこと。

■ メリット・デメリット
メリットは、プロトタイプの偶然を殺さずに、制作後半の選別基準へ変換できること。面白いが別ゲームになる案、テーマには合うが制作量が重すぎる案、快感より誤操作を増やす案を切る根拠が作れる。validated mechanics pool と組み合わせれば、削除した知見も次回へ再利用できる。

デメリットは、coop と物理の失敗が笑いになる biped 固有の性質が強く、単独プレイやシステム主導のゲームへそのまま移せないこと。また rational design を後から言語化しすぎると、偶然の発見や遊びの違和感を早く切りすぎる危険がある。初期は広く試し、収束時に使う方が合う。

■ 判定
部分採用。制作ルールとして固定するのではなく、新要素評価と postmortem 記録の probe にする。次の playable diff では、追加要素ごとに「面白いか」と「この作品らしさを濃くするか」を分け、切った mechanic も validated pool として残す。
