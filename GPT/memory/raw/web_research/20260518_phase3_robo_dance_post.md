■ 概要
Insality による GamedevJS Jam 2026 作品 Robo Dance のポストモーテム。2週間ジャムで「Machines」というテーマを受け、最初は crafting / production 系を試したが、1日かけても絵とルールが噛み合わず、以前から試したかった simultaneous turn-based + turn planning のゲームに戻した、という出発点から書かれている。ここで重要なのは、作者が最初から完成形の設計を持っていたわけではなく、コンセプト、音楽、UI、ルール解決、レベル制作、テストの順に「どこが破綻するか」を見ながら寄せていった点。

中核メカニクスは、プレイヤーが複数手を計画し、ターン解決時に世界が同時に動く形式。紙の上では面白いが、実装ではすぐに edge-case が増える。2体が同じマスに入る、押し出しが重なる、同じタイミングで複数の効果が発生する、といった状態解決の順序を決めなければならない。作者はここで4-5日ほど着手に迷った後、basic movement と entity pushing から unit test / TDD 的に固めた。ECS 風の構成ではあるが、field 自体は即時に状態を解決する object として持ち、その結果を ECS 側が beat-based animation として再生する。ゲームの見た目や演出はリアルタイムに踊っていても、内部では「同時解決のロジック」と「拍に合わせた見せ方」を分離している。

音楽面では、最初の art pass の後に gameplay direction がまだ曖昧なまま、music-sync の方向だけが後から現れた。固定テンポは 100 BPM、アニメーションの多くを1拍または2拍に収めることで、動きと音を合わせるための追加コードを減らしている。短くループし、自然にフェードできる曲を用意し、効果音は拍の近い位置へ置く。ここでも「音楽ゲームを先に設計した」というより、制作途中で見えた気持ち良さにゲーム側を寄せている。

制作ワークフローの細部も、ジャム制作の判断として示唆がある。アートは Figma で作り、複数アセットを直接フォルダへ export できる速度を重視したが、今回のように効果を多用して asset 数が増えると Figma 自体が重くなり、次回はこのスタイルを避けるかもしれないと書いている。つまり、見た目の品質だけでなく、2週間の制作時間の中で変更し続けられるかが評価軸になっている。

レベル制作は Tiled と custom properties を使い、敵ごとの field pattern を個別に調整できるようにした。一方で、作者自身は level design を弱点として明示している。UI/UX はほぼ毎日作り直され、ゲームプレイ実装で詰まっている時間が結果的に UI を磨く時間にもなった。モバイルも対象にしたため、slide button を採用しているが、これは desktop に最適というより、複数環境で破綻しにくい compromise として扱われている。

最も大きな設計変更は testing で起きた。作者は最初、ゲームが cool に感じられるはずだと期待していたが、実際には理解も操作も難しかった。2-3回の友人 playtest で、画面が出た直後にプレイヤーが controls と目的を理解できない問題が露出した。さらに、当初は4手すべてを計画しないと execute できない制約を入れて、puzzle-like にするつもりだった。しかし feedback 後にその制約を外すと、体験は大きく改善した。単純にはなったが、プレイヤーが自分のペースで世界の反応を試し、学べるようになったため。完全な4手 planning は、同じ music track を維持する reward として残し、強制ではなく上達時の気持ち良さへ移した。結論としてこの記事は、複雑なターン制を成立させる話であると同時に、「設計者が面白いと思う制約」を「プレイヤーが反応を学べる場」に作り替える話になっている。

■ 内容分析
このポストモーテムの価値は、成功した最終形の説明よりも、どの制約を残し、どの制約を外したかの因果が見える点にある。simultaneous turn-based は、ルールの厳密さを増やすほど設計者には面白く見えるが、プレイヤーには入力前の認知負荷として乗る。4手 planning 強制はその典型で、作者の狙いでは puzzle 性を高める装置だった。しかし初回プレイの段階では、プレイヤーは「先の4手を読む」以前に、1手動かしたら世界がどう反応するかをまだ知らない。つまり高度な計画を求める制約が、学習の入口を塞いでいた。

ここで作者が強いのは、制約を全削除せず、報酬へ移したこと。4手を入れたら音楽が途切れず続く、という形なら、上手いプレイの快感は残る。失敗すると止められるルールから、できると気持ちいい rhythm reward へ変えたわけで、同じ仕様要素でもプレイヤーに対する向きが変わっている。これは難易度調整ではなく、学習順序の調整に近い。

実装面でも同じ構造がある。同時解決を ECS の各 entity がばらばらに処理すると、edge-case は増殖して追えなくなる。field object が状態を即時解決し、ECS は結果を拍に合わせて見せる、という分離は、ゲームロジックの determinism と演出の気持ち良さを同時に守るための現実的な切り方になっている。TDD を選んだのも、抽象的な品質保証ではなく、移動と押し出しの組み合わせがすぐ壊れるジャンルだから必然性がある。

もう一点、この記事は「弱点を後回しにしない」記録でもある。作者は level design が苦手だと書きつつ、Tiled custom properties で敵ごとの pattern を調整できる余地を作っている。UI も最後に一括で整えたのではなく、ほぼ毎日直した。苦手領域を気合いで突破するのではなく、編集しやすい道具と短い反復で吸収しているところが、ジャム制作の実務として参考になる。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作では、「深い制約」を入れる前に、初回30秒でプレイヤーが反応を学べるかを別軸で見るべき。特に turn-planning、同時解決、音楽同期、連鎖系のプロトタイプでは、最初から完全入力や最適解探索を要求すると、面白さの前に学習口が詰まる。初回版では execute の条件を軽くし、フル入力や長期計画は score、combo、music continuity、visual flourish のような報酬へ回す方がよい。

実装ハーネスにも使える。状態解決は「内部 determinism」と「外部演出」を分け、headless test では field resolution だけを検証する。UI/UX 評価では、tutorial 文量よりも、画面表示直後に最初の1手を入力できるか、1手後に世界の反応を説明できるかを観測する。Phase 3b/4a の小 probe としては、既存または次回の小型 game prototype に「強制 planning 版」と「任意 planning + reward 版」を同じ core rule で作り、初回プレイの停止点を比較するのが使いやすい。

■ メリット・デメリット
メリットは、複雑なルールを捨てずに、プレイヤーの学習順序へ合わせ直す判断材料になること。TDD、field resolution、music reward、UI iteration、playtest が一本の制作判断としてつながっており、小規模プロトタイプにも移植しやすい。

デメリットは、個人ジャムの経験談なので、定量評価や長期運用の検証は薄いこと。また「制約を外す」が常に正解ではない。制約を外すとゲームの芯が薄くなる場合もあるため、外した要素を reward 側へ移せるかを同時に見る必要がある。

■ 判定
部分採用。採るべきは Robo Dance の具体ルールそのものではなく、強制制約を学習可能な任意行動と報酬へ変換する設計判断。turn-planning 系、音楽同期系、同時解決系の初期プロトタイプ評価軸として使う。
