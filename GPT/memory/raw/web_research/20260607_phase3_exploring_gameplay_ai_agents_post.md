■ 概要
Fernando de Mesentier Silva らの "Exploring Gameplay With AI Agents" は、ゲーム開発中の playtesting を「人間プレイヤーの代替として UI を操作する AI」ではなく、「設計者の問いに答えるための headless mechanics simulation」として組み直した事例である。対象は公開前の The Sims Mobile。論文の出発点は、通常の playtest が主観的で高コストで、広い行動空間を十分に覆いにくいという問題である。とくにサービス型・サンドボックス型のゲームでは、報酬、待ち時間、クールダウン、資源回復、イベント進行、キャリアや関係性の分岐が絡み、少数の人間テスターだけでは「どの選択肢が極端に不利か」「報酬が意味を持っているか」「ビルド間で遊びのリズムがどう変わったか」を定量的に見落としやすい。

著者らは最初、実ゲームクライアントを agent に操作させようとした。しかしクライアントは人間のタップ速度に合わせて作られており、描画やアニメーションや UI メニューを飛ばせず、待ち時間も早送りできない。さらにビルド更新のたびに agent 側の操作ロジックを書き直す必要があった。そこで The Sims Mobile の調整値が JSON ファイルに格納されていることを利用し、ゲーム全体ではなく、検証に必要な bare bone mechanics だけを別アプリケーションとして再実装した。この simulation は状態を完全に制御でき、グラフィックと UI を無視し、ゲーム内時計を進められる。論文ではゲーム内 action の実行速度がおよそ千倍になり、1 秒に約 1000 action を扱えるため、A* のような探索アルゴリズムが使えると説明されている。

実験の作り方も重要で、agent は汎用的に「楽しく遊ぶ」のではなく、ゲームデザイナーと相談して決めた明確な質問に答えるように構成される。各 use case では、まず「関係性カテゴリに不均衡があるか」「キャリア進行に何 action 必要か」「career object は進行短縮に効いているか」「ビルド変更で off-time と session 構造はどう変わったか」という問いを立て、その問いに対応する heuristic を作る。A* は各 action 選択で探索ノード数を 2000 に制限し、最適性よりも十分速く目的の差分を出すことを優先する。関係性のように初期選択や遅延効果で局所解に入りやすいケースでは、1000 回の simulation 平均を取ってカテゴリごとの差を見る。

結果は実際の設計変更につながっている。関係性カテゴリでは Friendship と Rivalry の進行が 3-4 appointments 程度で進む一方、Romantic の第 2 event だけが 13 appointments を要求する外れ値として出た。調整データを確認すると、この event だけ必要経験値が他カテゴリの同段階の約 2 倍になっており、後続 iteration で修正された。キャリア進行では Barista、Culinary、Fashion、Medical を比較し、Barista はレベル上限が低いため action 数が小さい一方、他キャリア間にも早期進行差があることを示した。この差は設計意図に沿うと判断され、変更は不要とされた。

さらに Barista の特定 event では、agent が event を最後まで進めず、最小報酬だけ取って timeout まで待つ奇妙な戦略を選んだ。調べると、第 2 段階に進むには第 1 段階の 2 倍以上の effort が必要なのに、報酬が同じという tuning error があった。career object の検証では、Fashion と Culinary では object が進行短縮に効くが、Barista では効果が小さく、Medical では level 10 以前に object が出ないため影響がないと分かった。これを受けて team は object の影響と入手性を調整した。ビルド比較では、Build B は Build A より目標到達に 4 倍以上の action を必要としたが、session 間の待ち時間は平均 6 時間から約 45 分へ短くなった。つまり Build A は早く進むが、Build B は短い間隔で再訪させる体験に寄っている、という設計上の選択肢を定量化した。

論文の結論は、agent playtesting の価値は「完成クライアントを AI に遊ばせること」だけではなく、設計上の問いに合わせて mechanics の小さな再現系を作り、大量 simulation で比較可能な指標を出すことにある、という点である。クライアント操作型の Softmax agent と simulation 上の A* agent を比べると、simulation は多くの career でより optimal に近い行動列を見つけ、variance も低い。A* は heuristic 設計の手間を要求するが、MCTS のように実験ごとの win condition を置くだけで探索できる方法も今後の候補として挙げられている。

■ 内容分析
この論文の強さは、AI agent を「プレイヤーらしさの再現」ではなく「設計質問に対する測定器」として割り切っているところにある。人間らしさを求めると、agent の行動品質、UI 認識、操作ミス、学習データ、プレイヤーセグメントの妥当性がすべて問題になる。しかしここでは、あえて sub-optimal な人間行動を捨て、短経路探索や報酬最大化で極端な差分を探す。これにより「普通のプレイヤーが必ずこう遊ぶ」とは言えないが、「この tuning では合理的探索がこの抜け道を選ぶ」「このカテゴリだけ必要 action が突出している」といった設計の歪みを早く見つけられる。

もう一つの軸は、実装対象を game client ではなく data-driven mechanics に寄せている点である。The Sims Mobile のように調整値が JSON で分離されている場合、headless simulation は本体実装から完全には独立しないが、少なくとも UI と演出と待ち時間から自由になる。これはゲーム制作の早期段階では特に有効で、まだ playable client が揃っていなくても、報酬曲線、進行条件、選択肢の相対価値を先に検査できる。逆に、この方法で分からないものも明確である。触感、演出の納得感、操作の迷い、テキスト理解、社会的・感情的な意味づけは測れない。論文が扱うのは「体験の全評価」ではなく「mechanics と tuning の検算」であり、この範囲設定が実用性を上げている。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作では、Phase 0 や playable diff の直後に、完成クライアントを無理に自動操作する前段として、最小 mechanics harness を置くのが合っている。たとえば資源、報酬、移動、リスク、敵出現、カード効果、待ち時間、スコア倍率だけを TypeScript や Python の純粋関数で再現し、agent sweep で 1000-10000 run を回す。検査対象は「最短で勝てる行動列」「使われない選択肢」「報酬が同じなのにコストが違う action」「局所最適に吸われる build」「1 つの戦略だけが支配する状態」に絞る。

記憶システム側では、shared-reads 候補から直接恒久ルールを増やすより、Phase 3b/4a の probe として `headless_mechanics_probe` のような評価単位を作るのがよい。各ゲーム案ごとに、問い、簡略 model、agent 種別、run 数、見つかった imbalance、実装へ戻した diff を atom 化すれば、後で「どの作品で simulation が本当に効いたか」を取り出せる。重要なのは、simulation の成功を gameplay の成功と混同せず、あくまで設計レビュー前の検算レイヤーとして扱うこと。

■ メリット・デメリット
メリットは、短時間で広い状態空間を探索でき、設計者が気づきにくい tuning error や報酬の無意味化を早期に発見できること。UI 自動操作より軽く、playable が未完成でも使える可能性がある。デメリットは、簡略 model の妥当性に強く依存し、体験の感情面や操作感は別評価が必要なこと。また heuristic を作り込むほど、agent が「問いに答える測定器」から「作り手の仮説をなぞる装置」になりうる。

■ 判定
部分採用。完成クライアント操作 agent ではなく、設計レビュー前の headless mechanics simulation と agent sweep として採用する。目的はプレイヤー代替ではなく、報酬、進行、選択肢、ビルド差分の検算に限定する。
