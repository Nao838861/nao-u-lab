■ 概要
Lanie Dixon の「Paper Playtesting and Roleplaying as an NPC to design "The Irregular"」は、VR ミステリーゲーム The Irregular の最初のシナリオを、3D 実装前に紙プロトタイプで丸ごと検証した UX research 事例。問題設定は、複雑な謎解きゲームでは、論理の破綻、難易度、物語理解の不足が、実装後に発覚すると非常に高くつくこと。チームは「ミステリーの論理に大きな破綻がないか」「難易度は適切か」「プレイヤーが大きな物語像を理解できるか」を先に問いとして置き、紙の手がかり、質問、ヒント、正誤応答を用意した。研究者はゲーム内 NPC としてロールプレイし、各プレイヤーがどの手がかりを使って推論したか、どこで止まったか、どのメモを取ったかを timestamp 付きで記録した。結果として、重要な手がかり 5 件の修正、新規手がかり 1 件の追加、地図の必要性、ゲーム内ノート機能の根拠を、3D アセット制作前に得ている。

■ 内容分析
この記事の中核は、紙プロトタイプを「安い代替物」としてではなく、実装前に答えるべき研究質問へ合わせて作った点にある。The Irregular は VR 作品だが、今回検証したかったのは VR の身体性ではなく、謎の論理、難易度、物語理解だった。だから、完全な 3D 空間ではなく、印刷した手がかりと紙上の進行だけで十分だった。これは fidelity の選び方として重要で、低忠実度だから雑なのではなく、検証したい問いに対して不要な忠実度を切っている。

テスト設計も具体的。チームはまず各 clue の narrative relationship と intended logic path を整理し、正しい clue connection が存在することを確認した。その上で、プレイヤーが答えを出した時に、どの手がかりを根拠にしたかを指し示してもらう。これにより、単に「解けた/解けない」ではなく、解けた理由が意図した論理経路なのか、偶然なのか、誤読なのかを分けられる。難易度は、各 question にかかった時間、正誤応答、使った clue、本人の難易度評価から見ている。物語理解は、セッション後に key plot point と全体の mystery narrative を再説明してもらう形で拾っている。

NPC ロールプレイはリスクの高い手法だが、記事はそこを隠していない。研究者が NPC として同席すると、プレイヤーは話しやすくなり、思考過程や質問が自然に出る。一方で、研究者がプレイヤーを誘導し、データを汚す危険がある。チームは master guide、質問、正しい clue response、hint、不完全/誤答への定型応答、沈黙時の prompt を用意し、できるだけ同じ体験を提供しようとしている。timestamp 付きノートも強い。観察メモと本人コメントを色分けし、自動 timestamp で各 phase の所要時間を後から計算できるようにしたことで、プレイ中に時計を操作せず、後で「どの段階に時間がかかったか」を見られる。

得られた発見も実装判断に直結している。プレイヤーは clue の日付から timeline を作ることがあり、紙とペンのメモは、将来のゲーム内ノート機能の根拠になった。銀行台帳の文字の誤読、credits と debits の混同、London と Wales の地理関係が分からないため地図が必要、といった問題も、VR 空間や高解像度 3D アセットを作る前に見つかった。最終的に 5 clues の更新と 1 clue の追加を行い、数千ドル規模の無駄を避けた、という結論になっている。

この事例で特に良いのは、観察結果が「面白かった」「分かりにくかった」で止まらず、制作物の変更単位へ変換されていること。文字の見間違いは clue の表記修正、地理関係の理解不足は map の追加、詳細なメモ行動は note taking mechanic の根拠になる。つまり、研究質問、観察データ、修正項目の対応が切れていない。ここが切れると、プレイテストは大量の感想を集めるだけになり、結局どの asset や rule を変えるべきか分からなくなる。

ただし、紙プロトタイプでうまくいった理由は、謎解きの基盤が情報理解と論理接続だったからでもある。記事は VR ゲームを扱っているが、テスト対象は VR らしさではない。これは弱点ではなく、むしろ検証対象の切り分けができているということ。紙で検証できる層と、実機でしか検証できない層を混ぜない姿勢が重要になる。

■ 自分達の環境への適用
この事例は、謎解き、チュートリアル、ステージ導線、AI エージェント用タスクの理解確認にかなり使える。自分達のゲーム制作では、実装前に「この仕掛けは理解されるか」「この情報配置でプレイヤーは正しい因果を作れるか」「難しさは操作失敗なのか情報不足なのか」を分けたい場面が多い。そういう時、いきなり完成 UI や 3D 表現を作らず、紙、テキスト、スクリーンショット、簡単な HTML だけで puzzle state と clue を再現し、プレイヤーまたは LLM テスターに解かせる。

小さな検証案としては、次の playable diff 前に「clue table」を作る。列は clue id、プレイヤーに見せる内容、意図した推論、誤読されそうな点、確認質問、期待する回答根拠。テスト中は timestamp、提示した clue、プレイヤーの発話、使った根拠、停滞地点、誤答種別をログ化する。headless 評価なら、LLM テスターに「答え」だけでなく「根拠として使った情報」を必ず出させ、意図した clue connection と照合する。これにより、正答率だけでは見えない「偶然正解」「説明不能な正解」「正しい材料を見たが接続できない」を分離できる。

記憶システムにも応用できる。shared-reads 候補や game lesson を使う時、単に「この lesson を参照した」ではなく、「どの根拠 atom からどの制作判断に接続したか」を trace できると、記憶の誤接続を発見しやすい。The Irregular の clue connection と同じで、答えが合っているだけでは足りない。根拠経路が意図通りかを見る必要がある。

制作サイクル上の使い所は、実装前レビューより一段前にある。仕様が固まってからチェックするのでは遅い。シナリオ、ステージ、チュートリアル、UI 導線のどれかに「プレイヤーが情報を読んで推論する」部分があるなら、asset 制作やコード化の前に、紙またはテキストの playable script を作る。そこで答え、根拠、停滞、誤読を取る。得られた修正は、次の実装タスクへ直結する形で issue 化する。これなら、Phase 0 の game directive を通常収集に流さず playable diff へ接続する運用とも相性が良い。

■ メリット・デメリット
メリットは、実装コストが高い前に、理解、論理、難易度の破綻を切り分けられること。紙プロトタイプでも、完全なプレイ体験ではなく研究質問に対応する要素を再現すれば、十分に判断材料になる。NPC ロールプレイや定型応答は、プレイヤーの思考を引き出しつつ、介入をある程度制御する手法として使える。timestamp ノートは、後で「どこが詰まりか」を定量と定性の両方で見られる。

デメリットは、身体性、操作感、視線誘導、空間把握、音や演出の圧力は紙では検証しにくいこと。VR やアクションゲームでは、紙で解けたから実装後も良いとは言えない。また、NPC 役の研究者がうまく振る舞えないと、プレイヤーを誘導してしまう。script と canned response が必須で、準備時間も通常のテストより長い。記事では 3 日の準備を置いており、安いが即席ではない。

■ 判定
採用。特に「根拠を指させる」「timestamp 付きで停滞と正誤を取る」「実装前に clue connection を検証する」は、そのまま使える。VR 的な身体性や操作感の検証には使い過ぎず、論理、理解、導線、記憶参照の検証に限定して導入する。
