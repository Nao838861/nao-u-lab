■ 概要
対象は CHI 2026 採択予定の “Shared Control for Game Accessibility: Understanding Current Human Cooperation Practices to Inform the Design of Partial Automation Solutions”。論文の問題設定は、障害のあるプレイヤーがアクセスできない操作を別の人に任せ、同じゲームキャラクターや同じゲーム状態を共同で制御する shared control を、将来の software agent 支援へどう移すかである。ここでいう shared control は、単なる難易度調整や aim assist ではない。Xbox Controller Assist、PS5 Access Controller と別コントローラの併用、Titan Two のような遠隔共同操作などを通じて、pilot である本人と copilot である支援者が、1 つのプレイを分担する実践を指す。

著者らは、accessible gaming の shared control 経験を持つ 14 名に半構造化インタビューとフォーカスグループを行った。参加者は pilot 8 名、copilot 5 名、assistive gaming expert 6 名を含み、役割が重なる参加者もいる。分析方法は reflexive thematic analysis で、まず人間同士の共同操作がどのように使われているかを整理し、次に「人間 copilot の一部を software agent に置き換える partial automation は受け入れられるか、どの設計条件が必要か」を引き出している。重要なのは、AI 支援をいきなり提案するのではなく、現在の人間支援の細部を足場にしている点である。

結果はかなり具体的だ。shared control が解いている問題は、単に「ボタンを押せない」ではない。細かな入力強度の制御、移動とカメラなど複数軸の同時操作、高速な連続入力、メニューやセットアップ、画面上の重要情報の把握、進行に詰まった時のヒント提示が混ざる。多くの参加者は既存のアクセシビリティ機器やリマップで単独の入力を実行できるが、同時に多数の操作を管理する curse of dimensionality で詰まる。人間 copilot はこの負荷を、操作分担、状況説明、提案、代行プレイ、合図、セットアップ支援によって下げている。

partial automation への期待は、人間支援が不要になることではなく、支援者の都合に依存しない選択肢を増やすことにある。参加者は software copilot に関心を示す一方で、過剰に上手い自動操作が player agency を奪うこと、AI の行動意図が読めず automation confusion が起きること、共同プレイの社会性が失われること、マルチプレイで不公平な補助になることを懸念している。そのため論文の設計ガイドラインは「できるだけ自動化する」ではなく、「本人が制御できる入力を優先し、残りを明確に分担し、必要な場面だけ支援し、何をしているかを返す」方向に寄っている。

具体的な設計要件として、操作支援では fine control、同時多次元操作、高速シーケンスを扱うこと。情報支援では on-demand な質問、詰まり検出、楽しみを壊さないヒント、重要要素の signaling を扱うこと。社会性では human cooperation も残し、遠隔協力や multiplayer assistance を支えること。操作分担では、本人の agency が高い主要操作を本人側に残し、copilot 側の担当範囲を macro-functionality 単位で厳密に分けること。自律性では、明示コマンドに反応する actuator 的支援と、FPS の照準補助のように高速すぎて逐次指示できない自律介入を使い分けること。通信では、自然言語だけでなく、短縮コマンド、非音声入力、画面表示、音、光、振動、ハイライトなどをユーザー設定可能にすることが挙げられている。

結論は、partial automation は shared control の置換ではなく拡張である、という位置づけになる。人間 copilot は社会的包摂と楽しさを生むが、常に利用できるとは限らない。software copilot は自立性と一貫性を高められるが、agency、意図理解、説明、マルチプレイ公平性を壊しやすい。したがって、今後の実装は「人間支援の良さを AI に全部真似させる」ではなく、どの支援を人間に残し、どの支援をソフトウェアに任せ、本人がどう主導権を保つかを明示する必要がある。

■ 内容分析
この論文の価値は、ゲーム AI 支援を能力の高さではなく、共同操作の契約として扱っている点にある。よくある自動操作は「プレイヤーが苦手な部分を AI が補う」と表現されるが、それだけでは本人が何をして、AI が何をしたのかが曖昧になる。論文はそこを automation confusion と agency loss の問題として扱い、操作分担の明確さを中心に置く。特に「同じ action を両者が触ると責任の所在が読めない」「同じ macro-functionality は同じ担当者に寄せる」という指摘は、ゲーム内 AI copilot の UI 仕様に直結する。

もう一つ強いのは、支援を操作だけに閉じていないことだ。copilot の仕事には、メニュー移動、セットアップ、画面や敵の説明、進行ヒント、危険や注目要素の合図、プレイヤー意図の推定が含まれる。これは LLM や VLM をゲームに入れる時に陥りがちな「チャットで攻略を教える」より広い。支援は入力代行、知覚補助、意思決定補助、社会的同行に分解でき、それぞれで自律度と説明方法が違う。

ただし限界も明確で、参加者の多くは mobility impairment で、hearing や cognitive impairment の参加者はいない。参加者は Western countries に偏り、partial automation を実際に使った経験もない。つまり、この論文は完成した効果検証ではなく、human cooperation の現場から partial automation の設計仮説を抽出した研究として読むべきである。次に必要なのは、人間 copilot baseline と software copilot prototype を同じゲームで比較し、agency、enjoyment、成功率、疲労、社会性を測る実験になる。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作では、AI 支援を「プレイヤーを置き換える自動攻略」として入れない方がよい。使うなら、shared-control copilot として、代行範囲、情報提示、介入タイミング、共同感の 4 軸で仕様化する。たとえば操作が忙しいプロトタイプでは、プレイヤーが主操作を握り、AI は照準微調整、カメラ、危険ハイライト、リトライ時の短い助言だけを担当する。パズルや探索では、AI が勝手に解を出すのではなく、明示要求された時だけヒントを段階的に出す。

記憶システム側にも使える。game-rights feedback や playtest log から「本人が残したい agency」「AI に任せてもよい負荷」「混乱した自動介入」をタグ化し、次の実装前チェックに入れる。特に Phase 3b/4a の probe として、「この補助は誰の action か判別できるか」「AI が上手すぎて遊びを奪っていないか」「情報支援と操作支援を混ぜていないか」を見ると、AI 要素の入れ方が粗くなりにくい。

■ メリット・デメリット
メリットは、アクセシビリティ支援と AI copilot 設計を同じ枠で扱えること。自動化の強さではなく、agency、分担、説明、社会性で評価できるため、ゲーム体験を壊す支援を早めに検出できる。デメリットは、実装コストが上がること。単純な auto-play より、担当範囲の UI、介入レベル設定、フィードバック表示、ユーザー別調整が必要になる。また論文自体は仮説抽出段階なので、実プロトタイプでは別途テストが必要。

■ 判定
部分採用。AI 操作支援を入れる時の設計チェックリストとして採用する。特に「本人の agency を残す操作分担」「AI の行動を説明する feedback」「人間協力を置き換えず選択肢として増やす」は、今後のゲーム prototype 評価に入れる価値が高い。
