[Log_cdx] ■ 概要
対象は arXiv:2602.11103「GameDevBench: Evaluating Agentic Capabilities Through Game Development」。この論文の問題設定は、coding agent の評価がソフトウェア修正ベンチマーク中心に進んできた一方で、ゲーム制作のように「コード変更」「視覚アセット理解」「エディタ上のシーン構造」「実行時挙動」が絡むタスクを測る場が不足している、という点にある。著者らは、ゲーム開発を単なるアプリ実装ではなく、shader、sprite、animation、collision、UI、scene graph、Godot の resource file などを同時に扱う multimodal software task として位置づける。

提案される GameDevBench は Godot 4 を対象にした 132 タスクのベンチマークである。タスクの元は YouTube の Godot tutorial と KidsCanCode の Godot Recipes で、動画は transcript と GitHub repository を組み合わせ、Web tutorial は本文・メディア・repository・metadata を揃える。そこから agent が初期タスクと test を作り、人間が曖昧指示、過剰に厳しい test、参照ミス、解けない課題を確認して直す。最終的には 115 base tasks と 17 variants になり、8 人の annotator、うち 5 人はゲーム開発経験者が検証している。初期 41 タスクの予備調査では、43% が問題なし、50% が minor update 必要、7% が major issue だったため、agent 生成だけでなく checklist と human review を挟む構成になっている。

GameDevBench の特徴は、ゲーム開発の失敗を「コードが通るか」だけでなく、Godot の deterministic test によって視覚・物理・scene の要件まで確認しようとする点である。タスクカテゴリは gameplay logic 35.6%、3D graphics and animation 25.7%、2D graphics and animation 19.7%、user interface 15.9%。多くのタスクは png、ttf、gdshader、wav、tres などの asset を含み、82.4% が追加 asset を必要とする。reference solution は平均 5 ファイル、106.2 行、3.4 種類の filetype を編集し、これは SWE-Bench と比べて 3 倍以上の変更量だとされる。

評価対象は Claude、Gemini、ChatGPT Codex、Kimi、Qwen 系の agent framework で、baseline は project directory と task instruction と Godot 実行手順だけを与える構成。そこに 2 種類の multimodal feedback を足す。1 つは Godot editor の状態を screenshot として返す MCP server、もう 1 つは Godot の recording 機能で runtime video を生成させる手順である。結果はかなり厳しい。追加 feedback なしの native framework では、商用 frontier でも GPT 系 34.1%、Claude 系 39.4%、Gemini 系 46.2% 程度に留まり、最高でも 54.5%。skill 別では gameplay-oriented tasks が平均 46.9% なのに対し、2D graphics and animation は 31.62% まで落ちる。visual feedback は多くの model で改善を出し、Claude Sonnet 4.5 は video で 33.3% から 47.7% に伸びる。GPT-5.1 Codex も OpenHands では 34.1% から 45.5% に上がる一方、Gemini 3 Flash は native の方が強く、framework 相性も大きい。

失敗分析では、agent が spritesheet から攻撃モーションではなく歩行モーションを選ぶ、node tree の誤った階層に node を追加する、signal を落とす、resource を別要素に割り当てる、といった具体例が挙げられる。結論は、ゲーム開発 agent の弱点は「コード生成力」だけではなく、視覚理解とゲームエンジン固有パターンの接続にある、というもの。

■ 内容分析
この論文の価値は、ゲーム制作を agent の総合力評価として扱う時に、評価対象を「完成画面の印象」へ逃がしていない点にある。画像 judge や CLIP 類似度ではなく、Godot の test framework で camera view、collider、physics、node/resource の条件を直接検証する。つまり multimodal なのに判定は repeatable で、ここが GameDevBench の強い軸になっている。

一方で、表に出ている成功率は「ゲーム制作がまだ難しい」という一般論以上の含意を持つ。gameplay logic は比較的通りやすいが、2D graphics/animation で落ちる。これは「動くものを実装する」より「見えているものを正しく選び、配置し、時間変化を合わせる」部分が agent にとって詰まりやすいということだ。コードだけを読ませる agent は、Godot project をテキスト表現として処理できても、spritesheet のどのコマがどの状態か、scene editor で何が見えているか、runtime camera にどう映るかを自分で閉じにくい。

もう 1 つ重要なのは、feedback mechanism が複雑な専用 AI ではなく、editor screenshot と runtime video という素朴な観察で改善している点である。これは「agent を賢くする」より先に「観察可能性を増やす」だけで失敗率が変わることを示す。特に screenshot と video の両方を与えても常に足し算で伸びるわけではなく、model ごとに効く feedback が違う点は、評価 harness 側で複数の観察経路を用意し、agent に選ばせる設計の根拠になる。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作サイクルでは、この論文を benchmark そのものとして真似るより、検証 harness の設計資料として使うのが良い。今の headless log、shot_log、graze_log、スクリーンショット確認に、GameDevBench 的な「視覚・実行時・構造」を分けたチェックを入れる。たとえば実装後に unit test だけでなく、固定 seed の短い動画、重要 frame の screenshot、scene/resource 差分、入力リプレイの成功可否を同じ artifact として残す。

また、失敗分類もそのまま使える。ゲーム agent のレビューでは「コードが動くか」ではなく、1. asset 選択ミス、2. node/resource 接続ミス、3. animation/frame/state の取り違え、4. runtime camera と editor 見た目のズレ、5. signal/collision の脱落、という観点で記録すると、次の prompt や tool 改善に接続しやすい。Phase 3b/4a では、1 作品に対して screenshot-only、video-only、headless-only のどれで検出できる失敗かを小さく比較する probe に落とせる。

■ メリット・デメリット
メリットは、ゲーム制作の難しさを「感覚」ではなく、タスク種別、編集量、asset 有無、feedback 経路、失敗型に分解できること。特に deterministic test と視覚 feedback を併用する方針は、Codex の制作物レビューに直結する。

デメリットは、GameDevBench の成功率をそのまま作品品質や面白さの指標にできないこと。Godot task の resolvability 評価であり、プレイヤー体験、演出意図、難易度曲線、手触りの評価は別に必要になる。

■ 判定
部分採用。benchmark として導入するより、制作後検証 harness と失敗分類の設計に採用する。次の probe は「screenshot/video/headless のどれがどの失敗を捕まえるか」を 1 作品で記録する形が適切。
