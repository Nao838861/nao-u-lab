■ 概要
『Codified Finite-state Machines for Role-playing』は、LLM role-playing の一貫性崩れを「プロンプトが足りない」問題ではなく、「会話を駆動している潜在的なキャラクター状態を、明示的に保持・遷移できていない」問題として扱う論文。著者らは、ゲーム AI で古くから使われてきた finite-state machine (FSM) をそのまま復活させるのではなく、テキストのキャラクタープロファイルから LLM に状態集合と遷移ロジックを抽出・コード化させる Codified Finite-State Machines (CFSM) を提案している。

出発点は、従来の prompting-based RP では「いま何を言ったか」「直前に何が起きたか」という表面行動は扱えても、そのキャラが警戒状態なのか、信頼状態なのか、所属や能力や感情のどの段階にいるのかを透明に追跡しにくい、という観察。論文は Mario の power-up を導入例に使う。小さい Mario が Super Mushroom で super になり、Fire Flower で fire になり、Goomba に当たると状態が戻る。このような状態遷移はゲームでは自然だが、LLM RP では「文章で説明したルールを毎ターン再推論する」形になりがちで、長い遷移列では混乱や幻覚が増える。

CFSM の手順は二段階。まず LLM がキャラクタープロファイルから key states を列挙する。例として論文では長門有希の profile から「文芸部員」「SOS 団の三人目の団員」「キョンと姓呼びで関わる状態」「その他の社会的状態」などを抽出している。ここで重要なのは、状態を単なる自由文メモにせず、互いに区別できる有限集合に落とすこと。さらに “unactivated” と “other” のような fallback 状態も持たせ、未発火・曖昧・想定外を吸収する。

次に LLM が `get_next_state(current_state, scene, action)` のような遷移関数をコードとして生成する。遷移条件は完全な手書き if 文ではなく、`binary_question(text, question)` のようなヘルパーを呼び、「この action は SOS 団加入を含むか」「この発話は相手の権威への抵抗か」といった意味判定を yes/no/unknown で問い合わせる。つまり CFSM は、状態遷移の骨格をコードで固定し、自然言語の曖昧さだけを局所的な質問に閉じ込める構成になっている。これにより、毎ターン LLM に「次の状態を自由文でまとめ直して」と頼む PromptTrans よりも、どの条件でどの状態へ移ったかを再現しやすい。

さらに著者らは Codified Probabilistic Finite-State Machines (CPFSM) も提案する。CFSM が単一の active state を持つ決定的 FSM なのに対し、CPFSM は状態上の確率分布を保持する。遷移先が一意に決めにくい会話や、キャラの反応が複数あり得る場面で、状態を「警戒 0.55、信頼 0.30、その他 0.15」のように扱う。Best@K 的な応答探索でも、表面生成温度ではなく潜在状態分布からサンプルする。

評価は二段。Synthetic validation では Mario State、Call of Duty Enemy、Tyrion’s Westeros Travel の 3 種の既知 FSM からランダム遷移列を作り、GPT-4.1 / GPT-4.1-mini に最終状態を当てさせる。各 FSM で 10,000 path を生成し、各終端状態ごとに 100 path を抽出、path length 1 から 10 まで難度を上げる。結果は、通常プロンプトの LLM は長くなるほど正答率が落ち、CoT は改善するが実質的に FSM シミュレーションを文章でやっているため、CFSM の約 25 倍の forward time がかかる。CFSM はコード実行なのでこの synthetic task では 100% として扱われる。

Real plot experiment では、Fandom Benchmark を使う。Haruhi / K-On! / JOJO / FMA / A Game of Thrones / ATLA の 6 作品、83 キャラ、5,141 scenes を対象に、spoiler-free profile、scene、question から次の行動を予測する。評価は GPT-4.1 による reference-prediction NLI score で、entailment 100、neutral 50、contradiction 0。人手確認では entail/neutral/contradict 各 200 件で 91.0%、89.5%、88.0% の一致が報告されている。

主結果では、GPT-4.1 RP model + GPT-4.1-mini discriminator の設定で、CFSM は main characters 平均 82.65、minor characters 平均 84.60 を出し、Vanilla、Textual Profile、Codified Profile、PromptTrans、Character Updating、Plot Summary を上回る。小型の llama-3.2-1b-instruct でも、Textual Profile 57.16、Codified Profile 60.11 に対し、CFSM 62.77、CPFSM 63.32。小さな DeBERTa discriminator を蒸留した条件では CPFSM が 64.14 まで伸びる。Ablation では state registration を外す影響が大きく、状態を毎回 “unactivated” から始めると性能が落ちる。これは、状態名の抽出よりも「継続して持つ」ことが効いているという示唆になっている。

■ 内容分析
この論文の面白さは、LLM を「状態管理そのもの」に使うのではなく、「状態管理をするコードを作らせる」側へ退かせている点にある。PromptTrans や Character Updating は、会話履歴から次の状態を自由文で再推論するため、表現力はあるが、状態の同一性と遷移条件が毎ターン揺れる。CFSM は逆に、キャラの identity / personality / ability / social role などを FSM の複数レイヤとして切り出し、各レイヤの現在状態を保持する。LLM は判定困難な意味条件にだけ呼ばれるので、曖昧さの範囲が狭い。

ただし、これは万能なキャラクター生成器ではない。状態集合は基本的に profile から事前抽出されるため、長期 RP で新しい関係性や技能が生まれる場合は “other” に逃げるか、appendix の dynamic state maintenance のように追加機構が要る。また、Markovian transition を仮定するので、遠い過去の約束や伏線、プレイヤーとの蓄積感情をどう持つかは別問題。論文自身も future work として、plot からの自動構築、HP のような連続値、動的 state set 更新を挙げている。

評価面では、Fandom Benchmark の NLI score は行動一致を見るには便利だが、「会話として魅力的か」「プレイヤーが違和感を覚えないか」までは直接測らない。論文の射程は、キャラの潜在状態が追跡可能で、遷移の根拠を後から読めることにある。これは “面白い台詞を出す” 技術というより、“NPC がなぜ今この警戒度・信頼度・目的で動いているのかをデバッグできる” 技術として読む方が正確。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作では、LLM-NPC を導入する前段階でも CFSM の考え方は使える。たとえば敵・味方・案内役・ライバルに、`trust`, `threat`, `goal_commitment`, `knowledge`, `permission` のような小さな state schema を持たせ、会話ログやプレイヤー行動から `get_next_state` を通す。重要なのは、最初から人格全体を自動生成しないこと。主要キャラ 1-2 体に限定し、「この台詞が出た理由」「この行動に移った状態遷移」をログに残せる形で probe する。

記憶システムにも応用できる。shared-reads や game-rights の atom を自由文で増やすだけではなく、directive / lesson / unresolved-risk / validated-pattern のような状態を持つ小さな FSM として扱えば、Phase 3b/4a で「候補」「検証中」「採用済み」「撤回」の遷移が追いやすくなる。CFSM 的に言えば、memory atom は単なる文章ではなく、次の判断で使われる状態付きオブジェクトになる。特にゲーム制作サイクルでは、ユーザー反応を受けて probe が lesson に昇格する条件をコード化する価値がある。

■ メリット・デメリット
メリットは、キャラや記憶の状態が可視化され、デバッグと回帰検証がしやすくなること。プロンプトを長くして一貫性を祈るより、状態集合・遷移条件・fallback を明示した方が、失敗時に直す場所が分かる。CPFSM を使えば、表面文の温度を上げずに潜在状態側で多様性を出せる。

デメリットは、状態設計の初期コストと、状態集合が硬くなるリスク。抽出された FSM が悪いと、キャラが設計者の想定した箱の中だけで動く。長期的な関係変化や、明確な状態名にしにくい空気感は、別の記憶層や dynamic state 更新と併用しないと痩せる。

■ 判定
部分採用。LLM-NPC 全体の基盤として一気に入れるのではなく、主要キャラの警戒・信頼・目的・所属など、ゲーム側で検証したい状態に限定して使う。まず会話生成より、状態遷移ログと「なぜその行動になったか」のデバッグ用途に寄せるのがよい。
