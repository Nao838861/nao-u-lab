■ 概要
Mortar は、automatic game design の中でも「メカニクスをどう作るか」と「作ったメカニクスをどう評価するか」を同じ系に入れようとする研究である。ここでいう game mechanics は、ジャンプ、回避、衝突、資源消費、敵との相互作用、勝敗条件のように、プレイヤーの行動とゲーム状態を結びつけるルール群を指す。ゲームの見た目やレベルだけを生成しても、メカニクスが弱いと、プレイヤーが上達する余地や選択の意味は生まれにくい。Mortar の問題設定は、メカニクス設計が専門性と反復時間を要する作業であり、単に「それらしいルール」を出すだけでは不十分だという点にある。

手法の中核は、quality-diversity algorithm と Large Language Model を組み合わせ、多様な候補メカニクスを探索することにある。quality-diversity は、単一の最高点だけを探すのではなく、違う性質を持つ複数の良い候補を archive として残す探索枠組みである。Mortar では、LLM がメカニクスの生成や変形に関わり、探索側が候補の幅を広げる。重要なのは、候補メカニクスを単体の説明文として評価しない点である。候補は、進化で得られたメカニクスと archive 由来の既存メカニクスを組み合わせ、complete game として合成された上で評価される。つまり「このルールは面白そうか」ではなく、「他のルールと一緒にゲームになった時、何を生むか」を見る。

評価には tree search が使われる。Mortar が重視する軸は skill-based ordering score で、強いプレイヤーが弱いプレイヤーを一貫して上回れるかを見る。これはゲームの面白さ全体を測る指標ではないが、メカニクス評価としてはかなり実務的な芯を持つ。もし新しいメカニクスがランダム性だけを増やし、うまいプレイヤーと下手なプレイヤーの差を潰すなら、そのメカニクスは上達余地を壊している可能性がある。逆に、強い探索方針や操作方針を持つプレイヤーが安定して良い結果を出せるなら、そのメカニクスは学習、計画、判断、熟練の余地を支えている可能性がある。Mortar はこの ordering を保つ方向に候補を評価する。

公開要旨では、Mortar は多様で playable に見えるゲームを生成し、skill-based ordering score により貢献するメカニクスを作れると説明されている。さらに、システム構成要素の役割を確認する ablation studies と、人間フィードバックに基づく user study も行っている。ここから読める結論は、automatic game design を「LLM にゲーム案を書かせる」段階で止めず、探索、合成、プレイヤーモデル評価、人間評価までつなげる必要があるということだ。Mortar の価値は、生成の派手さより、メカニクス候補を「上達可能なゲームを作る部品」としてふるいにかける評価設計にある。

この構成は、ゲーム生成研究でよくある「playable で多様なら成功」という基準から一歩進んでいる。playable は最低条件であって、プレイヤーがなぜ勝てたのか、次に何を改善できるのか、ミスと学習がどの程度つながるのかまでは保証しない。Mortar は、候補メカニクスが complete game の中で skill ordering に寄与するかを見ることで、少なくとも「上達の余地を生むルールか」という問いを評価に入れている。これは、ゲームを生成物ではなく、プレイヤー行動を分化させるシステムとして見る立場である。

■ 内容分析
Mortar の記事固有の強さは、メカニクスを自然言語の創作物として扱い切らない点にある。LLM はルールをいくらでも書けるが、ルール文だけでは、そのゲームが上達可能か、偶然に支配されるか、最適行動が単調になるかは分からない。Mortar は候補を complete game に組み込み、tree search で player strength の差が結果に出るかを見る。これは、「生成したメカニクスがゲーム内で機能しているか」を、かなり限定された形ながら実行ベースで問う設計である。

skill-based ordering score は、面白さの代理指標としては狭い。雰囲気、驚き、気持ちよさ、物語的な納得、初心者の入りやすさは直接測れない。また、強いプレイヤーが勝つゲームが常に良いわけでもない。パーティゲーム、物語体験、探索重視の作品では、skill ordering を強めすぎると作品の温度を誤る。ただし、アクション、パズル、戦術、ミニゲームの初期設計では、この狭さがむしろ利点になる。少なくとも「ランダムに見えるが、習熟で改善できない」候補を落とすフィルタとして使えるからだ。

もう一つ重要なのは、quality-diversity と archive の使い方である。自動設計でありがちな失敗は、ひとつの評価関数に過適合して、似た候補ばかりが残ることだ。Mortar は多様性を明示的に持つ探索を使い、既存 archive のメカニクスと組み合わせて complete game を作る。これは、単発の新ルールではなく、ルール同士の相性を見る方向に寄っている。メカニクスは単独で面白いのではなく、移動、障害、報酬、失敗条件、情報提示との関係で効く。Mortar の設計はその事実に合っている。

一方で、公開情報だけでは、tree search の player model がどの程度ゲームジャンルに依存するか、生成されたゲームの長期的な遊び応えをどこまで測れるかは慎重に見る必要がある。探索プレイヤーが得意なゲームだけが高く評価されるなら、評価軸が設計空間を狭める。したがって Mortar は「人間の面白さ判定を置き換える手法」ではなく、メカニクス候補を大量に出した時に、まず上達余地のあるものを拾い上げる一次評価として読むのがよい。

この点で、ablation と user study が入っていることも重要である。自動評価だけなら、システムが自分の評価器に合わせて都合の良いゲームを作っただけかもしれない。構成要素を外した時の性能差を見る ablation は、LLM、quality-diversity、archive、tree search のどれが効いているかを切り分ける助けになる。user study は、skill ordering では拾えない人間側の印象を補う。Mortar は、単一の数値でゲームを断定するより、自動評価と人間評価を分けて持つ設計として見る方が筋がよい。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作では、Mortar をそのまま automatic game designer として導入するより、メカニクス候補の初期フィルタに落とすのが現実的である。たとえば短いアクション試作で、dash cooldown、弾速、反射、近接リスク、リロード、graze 報酬のような追加ルール候補が複数ある時、それぞれを headless simulation にかけ、強い policy と弱い policy の差が安定して出るかを見る。

最小 probe は、候補ルールごとに 3 種の bot を走らせる形でよい。random bot、単純 heuristic bot、少し先読みする bot を用意し、score、clear rate、damage taken、time to objective を比較する。良い候補は、単に平均 score が高いものではなく、heuristic や先読みが random より一貫して良くなるものとする。これなら「遊べるが上達しない」ルールを早めに落とせる。Phase 3b/4a の自己フィードバックにも、candidate の面白さを語る前に skill ordering の差があるかを見る小さな検査として接続できる。

■ メリット・デメリット
メリットは、メカニクスの良し悪しを「上手い行動が報われるか」という実行可能な軸に落とせること。大量候補を人間が全部遊ぶ前の粗いふるいとして効く。デメリットは、評価が skill に寄るため、探索、雰囲気、驚き、初心者体験を過小評価しやすいこと。tree search や bot が弱いと、メカニクスではなく evaluator の癖を測る危険もある。

■ 判定
部分採用。自動でメカニクスを完成させる仕組みとしてではなく、ミニゲームやアクション試作の候補を headless に絞る skill-ordering probe として使う。最終判定は人間レビューと短い手触り確認を残す。
