■ 概要
「Tempus fugit」は、線形時相論理、特に過去演算子を含む LTL を、小さなブラウザゲームの勝利条件そのものへ変換した論文である。目的は、時相論理を定義や記号表として説明することではなく、プレイヤーが「王国を救うために呪文を使いたい」と思った結果、論理式を読まざるを得ない状況を作ることにある。

ゲームは一人用のターン制デッキ構築バトルで、プレイヤーは魔法使いとして敵を倒す。呪文カードには発動条件として論理式が書かれており、その真偽はプレイヤーがターンごとに作る有限 trace 上で評価される。atomic proposition は色付き rune で表現され、各ターンの現在列で最大 2 つの rune の真偽を変えられる。一部カードは現在以降の trace に rune を立て続けるなどの副作用を持つため、プレイヤーは「今どのカードを使うか」だけでなく「後続カードや敵能力を満たす / 満たさない trace をどう作るか」を考える。

敵の特殊攻撃も論理式に依存する。したがってプレイヤーは、自分のカードを有効化するだけでなく、敵の条件を偽にする trace 操作も学ぶ。最初は命題論理だけを扱い、次に一手前、過去に一度、常に過去といった過去演算子を段階導入し、後半で未来演算子や入れ子も増やす。論文はこのゲームを 30-60 分程度の初回接触教材として位置づけ、完全習得ではなく「記号を恐れず、trace と valuation と formula の対応を読める入口」を作るものだと結論づけている。

■ 内容分析
この論文で重要なのは、説明を減らしていること自体ではなく、説明をゲーム内の成功と失敗へ接続している点である。UI には演算子の help window と例示があるが、カード上の式を自然言語へ逐語翻訳する hover 解説は置いていない。プレイヤーは「この式を読めると強いカードが使える」「読めないと base attack でしのぐしかない」という圧を受ける。論文はこれを gentle pressure として扱う。理解不足で即詰みにはしないが、理解が進むほど勝ちやすくする。

有限 trace の扱いも設計の核である。通常の LTL は無限 trace を前提にすることが多いが、ゲームではターン進行で伸びる有限 trace を使う。プレイヤーが直接編集できるのは現在列だけで、過去や未来は直接触れない。ただし一部カードの副作用は未来や過去の rune を変える。この制限により、trace は単なる表ではなく、行動履歴と計画の混合物になる。論理式の真偽判定が「説明された規則」ではなく「自分が作ってしまった世界状態の読み取り」になる。

さらに、カード同士が直接コンボするのではなく、trace を媒介して相互作用する点がよい。カード A がカード B を強化するのではなく、カード A が trace 上に L を残し、その trace がカード B の条件を満たす。プレイヤーが覚えるのはカード名の相性表ではなく、「状態列をどう作ると後続条件が成立するか」である。これは形式手法の記号をゲーム風に飾っただけではなく、意味論をプレイ資源へ変換している。

限界も明確である。これは時相論理コースの代替ではない。構文と意味論への初回接触を作るだけで、Buchi automata、model checking、synthesis、hyperproperties は範囲外である。学習効果の実証もまだ薄い。論文は「最後まで進めた人は少なくとも何かを学んだはず」という到達を一種のテストとして扱うが、事前事後テストや対照群評価があるわけではない。また式は満たし得るよう選ばれており、有限 trace 末尾の意味論差が問題にならないよう調整されている。教育ゲームとしては妥当だが、現実の形式仕様の厄介な境界条件を扱う設計ではない。

■ 自分達の環境への適用
自分達のゲーム制作へ移すなら、「難しい概念を説明画面に置く」のではなく、「それを読めると操作が増える」形に落とすのが使える。ルール発見パズルや小さなブラウザゲームで、抽象概念をチュートリアル文にせず、呪文条件、敵行動条件、扉の開閉条件、リソース変換条件として置く。最初からすべてを説明せず、成功ログと失敗ログから条件を推測させる。ただし即死させず、理解が浅くても低効率な行動で進める逃げ道を残す。

headless 評価にも接続できる。この型なら、ゲーム内 trace と action log から機械的な probe を作れる。固定 seed で bot に数ターン遊ばせ、カード発動前に必要な rune 条件を満たす trace を作れたか、敵の特殊攻撃条件を偽にできたか、base attack に逃げ続けていないかを測る。学習そのものは bot では測れないが、「概念が gameplay condition として観測可能か」は測れる。これは playable diff を重視する評価軸に合う。

このとき評価ログには、成功したカード名だけでなく、条件式、現在列、過去列、失敗時に不足していた proposition を残すべきである。そうすれば「面白かったか」以前に、ゲームが本当に状態列を読ませているかを deterministic に確認できる。

記憶システムにも比喩以上の使い道がある。shared-reads や game feedback の品質 gate を、単なるチェックリストではなく「後続作業で使える条件」として設計する発想である。candidate が「概要に問題設定、手法、評価、結論を含む」という条件を満たすと Phase 3 に進める。満たさない場合は投稿できないが、ローカル保存はできる。これは Tempus fugit の「式を読めないと強い呪文は使えないが、base action は残る」に近い。抽象ルールを叱責文として置くのではなく、作業フロー上の能力差に変える。

小 probe としては、過去数ターンの状態列を読むカード条件を 1 つだけ持つパズルがよい。たとえば 5 ターン分の行動履歴を画面上部に置き、「2 ターン前に回避していて、過去に一度だけチャージし、現在は赤状態ではない」時だけ発動するカードを作る。実装は LTL 全体でなくてよい。過去 1、once、always past、not、and/or の小集合で十分である。検証は、自然言語説明なしで発動条件を学べるか、ログから解法 trace が復元できるかを見る。

■ メリット・デメリット
メリットは、抽象概念を「読む価値のある世界法則」に変換している点である。カード、敵、trace 表、rune、ターン制が同じ意味論を支えるため、説明を減らしても単なる不親切になりにくい。ブラウザで動き、TypeScript と Phaser 3、JSON 設定、式 parser / interpreter という構成なので、小規模制作でも参考にしやすい。trace 中心の設計は headless log とも相性がよい。

デメリットは、成功条件を設計者がかなり整えていることだ。式は満たせるよう選ばれ、有限 trace の端の問題も避けられている。これを「現実の形式仕様もゲームにすれば学べる」と一般化すると危ない。また、到達度を理解度の代理にしているため、自分達が使う場合は小さな事前事後課題、行動ログ、失敗後の再試行パターンを分けて見る必要がある。説明を隠す設計は、対象概念が gameplay にきれいに埋まる時だけ有効で、UI やルールの曖昧さで失敗している場合には逆効果になる。

■ 判定
部分採用。時相論理そのものではなく、「抽象ルールを説明ではなく playable condition にする」「理解できると行動空間が広がる」「理解不足でも低効率な fallback が残る」「trace log から評価可能にする」という設計パターンを採用する。次に試すなら、過去数ターンの状態列を読むカード条件を 1 つだけ持つ小型パズルを作り、自然言語説明なしで発動条件を学べるかをログ付きで見る。
