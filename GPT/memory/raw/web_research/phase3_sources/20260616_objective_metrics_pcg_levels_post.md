■ 概要
対象は Michael Beukman、Steven James、Christopher Cleghorn による “Towards Objective Metrics for Procedurally Generated Video Game Levels”。PCG で生成したゲームレベルを比較する時、「見た目が違う」「人間が難しそうに感じる」「特定ゲーム用の leniency 指標が高い」といった評価だけでは、ゲームや表現形式をまたいだ比較が難しい。論文の問題設定はここにある。生成器が増えるほど、研究でも制作でも「どの生成器が、どんな意味で良いレベルを出したのか」を公平に比べる必要があるが、既存の評価はレベルのタイル配置や視覚的特徴、ゲーム固有の危険物数、専門家の主観に寄りやすい。そこで著者らは、レベルそのものの表面情報ではなく、planning agent がそのレベルを解く時に実際に取る行動と探索負荷を見る。

提案は simulation-based な 2 つの指標である。1 つ目は diversity metric。複数レベルに A* agent を走らせ、各レベルで得られる action trajectory を文字列のような系列として扱い、レベル間の edit distance で多様性を測る。重要なのは、単にタイル分布や部屋形状が違うかではなく、「解くために要求される行動列がどれだけ違うか」を見る点である。見た目が違っても同じ走り方で解けるレベルは、プレイ上の多様性は低い。逆に表現形式やサイズが多少違っても、agent の行動列として比較できれば、ゲーム非依存に近い形で差分を扱える。

2 つ目は difficulty metric。これは A* agent が解に到達するまでに、search tree をどれだけ探索・展開する必要があったかを見る。最短経路長だけなら「長いから難しい」に寄りすぎるし、敵や穴の数のような game-specific feature は別ジャンルへ持ち出しにくい。探索量を見ることで、agent にとって計画がどれだけ入り組んでいたか、すぐ解が見つかるレベルなのか、多くの候補状態を試さないといけないレベルなのかを測ろうとしている。論文では A* を使うが、考え方としては planning agent の挙動を観測する枠組みであり、別の planner に置き換える余地もある。

評価では、この diversity metric が level size や representation の違いに対して既存の視覚・構造ベース指標より頑健で、playability に直接関係する要素を捉えやすいことを示す。一方で difficulty metric は慎重な結果で、既存の難易度推定と相関する domain がある一方、別 domain では課題も残る。つまり論文は「A* で面白さを完全に測れる」とは言っていない。成果は、PCG レベル評価を人間の好みの代替にすることではなく、少なくとも playable behavior に沿った横断指標を作り、生成器同士の比較や大量候補のふるい分けを再現可能にする点にある。著者らが evaluation framework を公開しているのも、指標を論文内の概念で終わらせず、同じ手順で再検証できるようにするためである。

この framing は、PCG を「生成アルゴリズムの見栄え競争」から「生成物がプレイヤーに何を要求するかの比較」へ戻している。ある生成器が広いレベルを作り、別の生成器が狭いレベルを作ったとしても、タイル数や部屋数だけではプレイ体験の差を説明できない。A* が通った action trajectory を比べれば、迂回、戻り、分岐選択、連続した移動のような要求がどの程度変わったかを同じ土俵に置ける。difficulty も、最終的な解の長さではなく、解を見つけるまでの search effort を見るので、「短いが探索上は紛らわしい」「長いが一本道で簡単」という差を拾える可能性がある。ここが、単なるクリア可否チェックより一段細かい。

■ 内容分析
この論文の読みどころは、評価対象を「生成物の静止画」から「解法の痕跡」にずらしたこと。PCG の評価では、density、linearity、leniency、tile distribution のような指標がよく使われるが、それらは設計者が何を危険・複雑・緩いと見るかを先に定義する必要がある。Mario なら穴や敵、Sokoban なら箱と壁、パズルなら到達可能性や手数、といった具合に、ゲームごとに評価語彙が分かれる。A* agent の trajectory に寄せると、語彙は「どの action をどの順に要求したか」へ落ちる。これは抽象化としてかなり強い。

ただし、この強さは同時に限界でもある。A* が見ている state/action 空間に含まれない楽しさ、緊張、学習、見た目の読解、操作感の気持ちよさは測れない。また difficulty を探索木の展開量で見ると、planner にとって難しいことと、人間にとって難しいことがずれる可能性がある。論文自身も difficulty metric については、片方の domain では有望だが、別 domain では課題があると述べている。この正直さがむしろ実用上は大事で、指標を「面白さスコア」にしない歯止めになっている。

もう一つ重要なのは、diversity を見た目の差ではなく要求行動の差として扱う点。生成 AI や PCG のレビューでは、スクリーンショット上の変化量が多様性と混同されやすい。しかしプレイヤーが毎回同じジャンプ、同じ回避、同じ鍵取り順を要求されるなら、体験としては似ている。trajectory edit distance は、この混同を避けるための実用的な proxy になる。

研究としての弱点は、general metric を目指すほど、個別ゲームの意味を削る必要があること。A* の action space に落ちる要素は比較しやすいが、ゲームデザインで重要な「なぜその行動をしたくなるか」「失敗した時に納得できるか」「危険を理解する前に予告があったか」は別の観測が必要になる。したがって、この論文は評価の最終審判ではなく、候補集合の形を把握する計器として読むのがよい。特に PCG の iterative loop では、生成器を少し変えた時に、見た目の分布ではなく要求行動の分布がどう動いたかを追う用途に向いている。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作サイクルでは、headless 評価にこの発想を小さく入れられる。たとえば level、敵配置、報酬配置、puzzle seed を複数生成した時、clearRate と score だけを見ると「全部クリアできる」「平均点が同じ」で止まる。そこに、bot が実際に取った action sequence、訪問セル、危険回避、探索ノード数を残せば、同じ成功率でも「毎回ほぼ同じ導線」「寄り道を要求する seed」「短いが探索負荷が高い seed」を分けられる。

実装単位は大きくしない方がよい。まずは既存プロトタイプの replay log に、入力列の normalized edit distance と探索回数を追加する probe で十分。人間レビュー前の候補選別として、同一テンプレの量産を落とし、行動の幅がある seed を残す。記憶システム側にも、candidate を shared-reads 化する前に「この評価は見た目の差か、要求行動の差か」をメタデータとして残せる。

■ メリット・デメリット
メリットは、評価が reproducible で、ゲーム固有の見た目指標より gameplay に近いこと。大量生成した候補を人間が全部遊ぶ前に、行動差分と探索負荷で粗く並べ替えられる。デメリットは、agent 実装への依存が強いこと。A* がうまくモデル化できない操作感、反射神経、学習、読み合いは抜ける。探索量を難易度と呼ぶ時も、人間の体感難易度とは必ず分けて扱う必要がある。

■ 判定
部分採用。PCG 評価の正解指標としてではなく、headless bot が生成候補を比較するための追加計器として使う。まず trajectory distance と search effort を記録し、人間レビューを置き換えず、候補の偏り検出に使う。
