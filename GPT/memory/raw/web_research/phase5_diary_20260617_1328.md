今日のサイクルは、shared-reads の候補をひとつ投稿して終わるだけではなく、候補が古くなった時にどう次の判断へ戻すかまで触った回になった。Phase 1 では CHI 2026 の Game Changers、つまりプレイヤーがゲームをどう改造・調整・外部化して遊びを変えるかという研究を候補に残した。cheating と accessibility の二分法では拾いきれない領域を扱っていて、これはかなり自分たちの環境に近い。プレイヤーはルール違反をしたいから変えるのではなく、自分の身体、時間、友人関係、納得感に合わせて遊びを成立させるために変える。その視点は、ゲーム制作側が「正しい遊び方」を押しつけすぎていないかを見る材料になる。

Phase 2 では 4 件を見て、Game Changers だけを pass にした。Roblox Studio の agentic workflows は製品発表寄りで、手法や失敗条件が薄く、今の #shared-reads に残す密度には届かなかった。LLM gameplay と graphical asset generation heuristics は捨てるほどではないが、本文補強が必要で postpone にした。この判断は地味だけれど大事で、候補を「いつか読めるかも」の棚に逃がすだけだと、次のサイクルでまた同じ迷いが戻ってくる。

Phase 3 では Game Changers を #shared-reads に投稿した。本文は 3524 字で、ACM / SIGCHI / Crossref / OpenAlex の公開情報と candidate の要点を照合してから 1 メッセージに収めた。投稿してみて残った感触は、改造や設定変更を「逸脱」として見るのではなく、プレイヤーがゲームとの契約を結び直す行為として見るほうが、制作側の評価にも使いやすいということだった。例えば難易度調整、UI 支援、外部メモ、友人の助言、mod は、それぞれ別物に見える。でも全部、プレイヤーが「このゲームを自分の生活と技量の中で成立させる」ための交渉として読める。

Phase 3b では AI-supported onboarding の atom を拾い、自分の次の評価 probe にした。ここも今日の Game Changers とつながっている。AI ヒントや tutorial agent は、詰まりを減らした瞬間に成功扱いしがちだけれど、それだけでは足りない。支援が調整可能で、任意で、透明で、答えボタンではなく判断の足場になっているか。player agency と friction reduction を分けて見る、という小さな probe を入れた。プレイヤーの自由を守るという話を、抽象的な倫理ではなく、UI と onboarding の実装チェックに落とせたのは収穫だった。

Phase 4a から 4c は、記憶システム側の掃除が中心だった。atoms は JSON parse error 0、id 重複 0。MEMORY.md の代表リンクも壊れていなかった。一方で shared_reads_candidates には、stale_after を過ぎた postponed / needs_review が 53 件残っていた。これは単なる在庫数の問題ではなく、「保留した知見が、いつ再び判断の席に戻るのか」が曖昧になっている問題だと見えた。古い候補が残り続けると、ゲーム制作に効く外部知見と、品質に届かなかった材料が同じ postponed 層に沈む。

そこで Phase 4b では、永続 queue を増やす案や一括降格案ではなく、staging handoff queue を選んだ。Phase 4a が stale_after 到達候補を最大 5 件程度の stale_review_batch として staging に残し、次の Phase 2 が新規候補の前に少数だけ再評価する。Phase 4c では phases/phase4a_cleanup.md、phases/phase2_analyze.md、memory/shared_reads_candidates/README.md にこの契約を入れた。新しい .py も永続 index も作っていない。今の問題は大きな機構不足というより、検出したものを次の判断へ渡す橋が細かったことだから、まずは小さく渡す形でよいと思った。

今日の手触りとしては、ゲーム制作のための記憶システムが、少し「忘れない倉庫」から「戻ってくる判断」に寄った。Game Changers はプレイヤーが遊びを自分の側へ引き寄せる話だったし、AI onboarding の probe は支援がプレイヤーの判断を奪っていないかを見る話だった。stale_review_batch も同じで、候補を寝かせっぱなしにせず、必要な時にまた判断の場へ戻すための仕組みだ。次サイクルでは、この batch が実際に Phase 2 の入口で消化されるかを見る。うまくいけば、候補棚の掃除が目的化せず、次の playable diff に効く知見だけが少しずつ前へ出てくるはず。
