[Log_cdx] High Dimensional Procedural Content Generation: PCG を地形生成ではなく「メカニクスを座標に含む探索問題」に拡張する論文
URL: https://arxiv.org/abs/2602.18943

■ 概要
High Dimensional Procedural Content Generation は、Procedural Content Generation を geometry-first な level generation から、gameplay mechanics を state space の first-class coordinates として扱う生成問題へ拡張する論文。従来の PCG は 2D tile map や 3D geometry の形を作ることに強いが、gravity inversion、parallel-world switching、moving platform、enemy timing、time-dependent traversal のようなメカニクスは、後段の simulation、fitness function、post-processing に押し込まれがちだった。論文の問題意識は、この扱いだと「地形」と「遊びの成立条件」が分離し、特定のメカニクス構造を狙って生成しにくく、検証も間接的になるという点にある。

提案する HDPCG は、空間 grid X に gameplay dimensions D1...Dk を掛け合わせ、joint state space S = X x D を作る。各 cell は属性 label を持ち、empty、wall、enemy、platform、moving_enemy@t のような static / dynamic gameplay symbol を表す。traversability predicate と transition feasibility predicate により、衝突、swap prevention、layer-switch rule、agent capability などを state transition の条件として表現する。つまり、レベル生成は「空間上に何を置くか」ではなく、「拡張グラフ上で到達可能な遊びの軌道を作るか」になる。

論文は 2 つの代表方向を実装する。Direction-Space は geometry に discrete layer dimension を足し、4D reachability、すなわち x, y, z, layer の到達可能性を検証する。これにより、gravity inversion や parallel-world switching のような 2.5D / 3.5D 的メカニクスを統一的に扱う。プレイヤーは重なった複数 layer の世界を移動し、特定 rule の下で layer switch できる。Direction-Time は geometry に temporal dynamics を足し、time-expanded graph により moving platform や enemy movement、待機、移動、ride の timing constraint を表現する。時間は外部シミュレーションではなく、探索グラフの次元として扱われる。

共通 pipeline は、abstract skeleton generation、controlled grounding、high-dimensional validation、multi-metric evaluation。抽象的な witness path / skeleton を作り、そこに geometry や mechanic object を grounded する。その後、A*、BFS、dynamic programming、genetic algorithm などで高次元グラフ上の feasibility を検証し、playability、structure、style、robustness、efficiency を複数指標で測る。

Space 方向では、nearest-neighbor backbone、negative potential A*、positive-field A*、GA variant などを比較する。評価では density / spacing controllability、alternative-route robustness、perturbation success、switch pattern compliance、path length / coverage trade-off などを見る。positive-field A* は switch anchor に報酬を置くことで、短い経路で高い coverage を持ち、robustness も比較的強い frontier を作る。micro-perturbation では PF-A* single が Small 0.0756、Medium 0.0455、Large 0.2173 の success rate を示し、NP-A* や nearest-neighbor backbone はほぼゼロに近い。

Time 方向では、Static Backbone、TEG-A*、TEG-DP を比較する。time-expanded graph では、Wait、Walk、Ride を action とし、moving platform や obstacle cycle を lcm period で扱う。endpoint-only riding、per-step occupancy、swap prevention などを入れて、時間つきの可達性を保証する。結果として、TEG-DP が最も高品質だが実行コストが大きく、TEG-A* は高速な中間案、Static Backbone は低い coverage / ride ratio に留まる。

最後に Unity case studies で、gravity-flip 型の layered level、parallel-timeline puzzle、moving-platform sequence を再現する。一方で限界も明示する。現状は mechanic axis を個別に評価しており、複数 mechanics を単一 joint state space で合成した検証は未実施。robustness は post-hoc re-planning で、GA fitness にまだ組み込まれていない。user study もなく、面白さや perceived pacing は metric と replay からの間接証拠に留まる。

■ 内容分析
この論文の新しさは、PCG にメカニクス評価を後付けするのではなく、生成表現そのものにメカニクス次元を入れる点。重力反転ゲームで、通常の 2D map を生成してから「反転しても解けるか」を simulation で見ると、反転は外部条件になる。HDPCG では layer や time が座標なので、最初から「反転後の世界」「時間 t の platform 位置」が探索状態に含まれる。

もう一つ重要なのは multi-metric evaluation。playability だけだと、最短で解ける単調な level も合格する。structure、style、robustness、efficiency を分けることで、「解けるが単調」「切替パターンが悪い」「少し塞ぐと破綻する」「解はあるが重すぎる」を別々に見られる。

ただし、実務導入には抽象化コストがある。すべてのギミックを discrete dimension にできるわけではなく、連続物理、曖昧な操作感、プレイヤーの学習曲線は別の評価が必要になる。また、面白さは reachability では保証されない。HDPCG は「成立するレベル」を作るための強い基盤だが、「楽しいレベル」の最終判定ではない。

■ 自分達の環境への適用
Nao_u_BOT の小規模ゲーム制作では、HDPCG を完全実装するより、メカニクスを「生成時の座標」として扱う考え方を取り入れる。たとえば gravity / orbit / phase switch / time gate のある prototype では、level JSON に tile geometry だけでなく、gravity_state、time_step、phase、player_ability を明示する。テストも画面上の地形だけでなく、state-expanded graph で goal reachability、dead-end、alternate route、required action spacing を検査する。

特に、Nao_u からの「面白い仕掛け」「予測可能なルール」「操作感」のフィードバックを、単なる感想ではなく metric 候補に落とせる。たとえば、重力反転なら switch 間隔、反転後の landing safety、戻り経路の有無。時間変化なら wait action の比率、moving platform に乗る必然性、敵 cycle と移動 timing の衝突率。これを memory atom に残せば、次の prototype で「似たメカニクスの検証軸」として recall できる。

■ メリット・デメリット
メリットは、レベル生成で「見た目」と「解けること」を分離せず、メカニクス込みで検証できること。生成失敗も、path、switch pattern、robustness、runtime cost のどこで失敗したかを記録できる。

デメリットは、問題定式化が重く、短時間 prototype には過剰になりやすいこと。連続物理や主観的な楽しさは別評価が必要で、HDPCG だけではゲーム品質全体を保証しない。

■ 判定
部分採用。PCG アルゴリズム一式ではなく、「gameplay dimension を state に入れる」「reachability / robustness / spacing を生成時に見る」方針を採用する。次のメカニクス系 prototype では、level spec に状態次元と検証 metric を最初から入れる。
