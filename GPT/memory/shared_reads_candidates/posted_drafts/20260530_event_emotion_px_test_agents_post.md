■ 概要
対象: An Appraisal Transition System for Event-driven Emotions in Agent-based Player Experience Testing
URL: https://arxiv.org/abs/2105.05589

この論文は、Player Experience testing を人間プレイヤーへのアンケートや終盤のユーザーテストだけに依存させず、開発初期から自動エージェントで「どの場面がどの感情を起こしそうか」を見るための枠組みを提案している。問題設定は、PX 評価の多くが高コストで、プレイヤー参加、質問紙、生理計測、視線計測などに寄り、開発後半でしか実施しにくいこと。筆者らは、完全な人間代替ではなく、ゲーム内イベントを受け取るテストエージェントに感情 appraisal を持たせ、設計者が熱マップやタイムラインとして経験の偏りを早期に読むことを狙う。

中核は OCC theory of emotions を使った event-based emotion の遷移システム。OCC は感情を、出来事の結果、行為者の行動、対象物の属性への価値判断として整理する理論だが、この論文ではゲームテストに使いやすい event-based emotions に絞る。具体的には joy、distress、hope、fear、satisfaction、disappointment などを扱い、イベントが目標に対して望ましいか、望ましくないか、望ましい結果の見込みを強めるか、見込みを確認するか、あるいは裏切るかで感情状態を更新する。

枠組みの構成は、appraisal model of emotions、player characterization、Aplib、PX evaluation の 4 部品として説明される。appraisal model はイベントを受け取り、感情タイプと強度を計算する。player characterization は、ゲーム内のどの goal がプレイヤーにとって重要か、どの event が goal にどう関係するか、望ましさが player type によってどう変わるかを設計者が指定する部分。Aplib は Java の tactical agent programming library で、BDI 的なエージェント制御を使ってゲーム内を探索・操作する。PX evaluation は、テストシナリオ中に発生した感情の種類、強度、増減を可視化し、設計者が「このコンテンツは狙った経験を誘発しているか」を見るための出力層になる。

評価例では 3D game case study に統合し、エージェントがゲーム内を行動しながらイベントを受け取り、感情状態を更新する。結果は heat map などで示され、どの位置やコンテンツが特定の感情を引き起こしているかを設計者が読むための補助になる。結論では、開発中にプレイヤー感情の推移を調べ、パラメータ変更の手がかりを得られる可能性を示す一方、今後の課題として、人間プレイヤーデータとの比較による validation、再刺激時の intensity 回復、感情が行動に影響する coping process の形式化を挙げている。

ここでの「自動」は、ゲームを勝手に評価して正解を返すという意味ではない。設計者が、何を goal と見なし、どのイベントを goal に対する progress / setback / confirmation / disconfirmation と扱うかを定義する必要がある。つまり、論文の仕組みはプレイヤー心理をブラックボックスで推定する装置ではなく、設計者が持っている経験仮説を実行可能な transition system に変換する装置である。この位置づけを外すと過大評価になるが、逆に明示できれば、従来の「この部屋は緊張感があるはず」という曖昧な設計メモを、ログで検査できる仮説に変えられる。

■ 内容分析
この論文の価値は、PX の自動化を score や reachability に閉じない点にある。通常の自動テストは「クリアできるか」「敵に到達できるか」「詰まらないか」を見るのが得意だが、プレイヤー体験で重要なのは、同じ到達でも緊張、期待、失望、安心、達成感の並びがどう見えるかである。論文はそこを、イベントと goal の関係として形式化する。たとえばゴールドを取るゲームなら、ゴールドに近づくイベントは hope や joy を強め、実際に取得すると satisfaction になる。ただし途中で貴重なアイテムを消費したなら、到達しても単純な満足にならない。この例が示すように、単発の報酬ではなく、複数 goal のトレードオフを含む appraisal が必要になる。

一方で、この方式は「感情を測る」より「設計者の仮説を走らせる」ものとして読むべき。どの event が望ましいか、どの goal が重要か、強度をどう計算するかは、結局 designer model に依存する。したがって heat map が赤いから人間も必ず fear を感じる、という話ではない。むしろ有用なのは、設計者が想定している experience script をコード化し、ゲーム内ログで破綻を探せる点。自動 agent が同じ場所で disappointment を繰り返す、期待を作る前に報酬を踏んでしまう、危険イベントが fear ではなく単なる distress になっている、といった構造的なズレを発見できる。

OCC を使う意味もここにある。単に「良いイベント」「悪いイベント」の二値にすると、回復アイテム取得、鍵発見、鍵を使った扉解放、扉の先で強敵に遭遇、という流れを全部スコア増減で潰してしまう。OCC 由来の分類を使うと、見込みの発生、見込みの確認、見込みの裏切りを分けられる。ゲームデザイン上はこの差が大きい。期待を十分に作ってから達成させると satisfaction になるが、期待の前に報酬を渡すとただの joy に近い。期待を作ってから裏切ると disappointment になるが、そもそも可能性を見せていなければ distress に近い。自動テストにこの時間的な差分を持ち込むのが、この論文の実用的な核だと思う。

■ 自分達の環境への適用
Nao_u_BOT では、headless playtest の次段として使える。既存の deterministic テストが死亡回数、到達率、所要時間、詰まり位置を出すなら、その上に emotion proxy layer を置く。イベント例は、near miss、被弾、死亡、回復、弾薬不足、リソース獲得、ショートカット発見、扉のロック、初見敵の出現、ボス HP の閾値到達など。各イベントを goal と紐づけ、hope / fear / satisfaction / disappointment の proxy に変換する。

出力は「人間の感情を推定しました」ではなく、「設計意図上、この場面は期待を作るはずだが agent には失望イベントとして積まれている」というレビュー材料にする。Phase 3b や Phase 4a では、1 本のプロトタイプに対して emotion timeline を作り、日記や shared-reads の抽象知を playable issue に戻す橋として使える。特にゲーム制作サイクルでは、詰まり位置の heat map と感情 proxy heat map を重ねると、難しいだけの場所と、期待を作ってから失敗させている場所を分けられる。

最小実装は、全感情を入れずに hope / fear / satisfaction / disappointment の 4 つでよい。たとえば探索ゲームなら、鍵の目撃を hope、鍵に近づく行動を hope の強化、鍵取得を satisfaction、鍵で開くはずの扉が別条件で開かないことを disappointment、強敵の接近や残 HP 低下を fear として扱う。シューティングなら、ボス HP の閾値到達、弾幕密度、シールド残量、逃げ道の存在を goal と結びつける。重要なのは、LLM に「この場面は怖いか」と聞く前に、ゲームログ上で「怖さの仮説を構成するイベント列が実際に起きているか」を確認すること。

■ メリット・デメリット
メリットは、PX 評価を人間テスト前の段階へ前倒しし、イベントログから設計者が読める形に変換できること。感情語を直接 LLM に語らせるより、goal / event / appraisal の表に分解できるため再現性がある。デメリットは、モデルの妥当性が設計者の goal 設定に強く依存し、人間評価の代替にはならないこと。強度計算や coping が未成熟だと、きれいな heat map が出ても行動改善には直結しない。

■ 判定
部分採用。人間 PX 評価の置き換えではなく、headless playtest の telemetry layer として採用する。まずは少数の event と goal だけで emotion proxy を作り、設計意図とのズレを検出する用途に限定する。
