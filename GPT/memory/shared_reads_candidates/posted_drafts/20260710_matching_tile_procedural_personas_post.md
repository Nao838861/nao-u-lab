■ 概要
「Automated Playtesting of Matching Tile Games」は、Match-3 系ゲームの自動プレイテストを、単一の最適 solver ではなく複数の procedural persona で行う論文である。対象は Bejeweled / Candy Crush に近い簡略化 Match-3 フレームワークで、7x7 盤面、隣接タイル交換、3 個以上の一致、落下、連鎖、スコア倍率を持つ。ただし特殊ピースは実験から外している。著者らは MCTS agent の UCB1 をそのまま使わず、遺伝的プログラミングで node selection 用の数式を進化させる。作る persona は 4 種類で、スコア最大化 MaxS、スコア最小化 MinS、次に可能な手数の平均を最大化する MaxM、同じく最小化する MinM。各個体は 50 seed で 20 move ずつプレイし、100 個体の population を 100 世代進化させ、vanilla MCTS と random agent と比較する。最後に 41 人の user study で 6 round の人間 play trace を取り、preset board で agent の結果と比較する。結論は、MaxS / MinS は人間の高低パフォーマンス範囲を推定でき、盤面ごとの差は難易度推定に使える、というもの。

■ 内容分析
この論文は「プレイヤーらしさ」を心理記述で終わらせず、評価関数として MCTS に埋め込む点が強い。MaxS は長期的に点を伸ばすプレイヤー、MinS は短期的・非効率なプレイヤーの近似として置かれる。MaxM は盤面上の選択肢を増やすため、即時スコアより将来の自由度を好む persona になる。MinM は逆に選択肢を狭める。ここで面白いのは、4 persona が「うまい/下手」の一本線ではなく、スコアと可動性という別軸で設計されていること。ゲーム制作で欲しいのは最強 AI ではなく、設計がどの遊び方にどう反応するかなので、この分割は実用的である。

実験設定も比較的読みやすい。MCTS は root node を 250 回訪問し、rollout は初期 20 move から実 move が進むほど短くなる。進化では加算、乗算、除算、平方根、定数、子ノード勝利回数、訪問回数、現在ノード訪問回数、利用可能 move 数などを使い、100 個体から上位 10% を残し、残りを mutation / crossover で作る。各世代は前世代の最高 fitness を超えるよう進む。結果では、スコア最大化 agent は徐々に改善して plateau に達する一方、手数最大化 agent は早く peak に達する。これは「次の合法手を増やす」方が「連鎖や高得点を狙う」より一手先の局所戦略で実行しやすいからだと説明される。MinS では理論最低 1200 点に届かず 1600-1700 点付近で落ち着き、強制 combo により完全な低スコア維持が不可能な盤面構造が示される。

user study との接続も重要である。41 人の人間は preset board 3 枚と random board 3 枚を 20 move ずつ遊ぶ。preset board の人間平均は Board 1 が 4530.24、Board 2 が 3042.93、Board 3 が 2911.71。agent 比較では MaxS が Board 1/2/3 で 7080/6460/7040、MinS が 1740/1380/1500、vanilla MCTS が 5240/4500/5840、random が 2720/3840/2340。人間平均は MaxS 以外の persona より高く、MinS は人間最低値より低い。Board 1 は人間でも agent でも高得点になり、盤面自体が易しいと判断できる。つまり persona は人間の完全再現ではなく、レベルの上下限と盤面差を測る物差しとして使われている。

限界も本文中に見える。特殊ピースを外した簡略版なので、商用 Match-3 の爆発的な連鎖設計や booster 経済は見ていない。さらに MaxM / MinM は「利用可能 move 数」を代理指標にしているため、選択肢が多いことが楽しいのか、迷いを増やすのかまでは判断できない。ここを誤ると、headless 評価で「選択肢が多いほど良い」という雑な結論になる。論文の価値は、persona が正しい心理モデルであることではなく、同じ board を複数の行動傾向で測ると設計差が見える、という実験の型にある。

■ 自分達の環境への適用
Nao_u_BOT のプロトタイプ評価では、bot を 1 体にしない。たとえばパズルやレーン制アクションなら、`goal_rusher`、`risk_avoider`、`score_greedy`、`space_keeper` のように、評価関数だけ違う簡易 persona を用意する。実装は MCTS まで行かなくてもよい。既存の deterministic bot に重みを渡し、同じ seed で 20-50 run 走らせ、勝敗、スコア、選択肢数、危険滞在率、戻り操作回数、報酬取り逃しを persona 別に出す。単一 bot がクリアできるかではなく、同じステージがどの persona にだけ厳しいかを見る。

この設計は headless 評価だけでなく、制作サイクルにも合う。Phase 0/ゲーム制作では、1 playable diff ごとに「リスク回避型は詰まるが突撃型は抜ける」「高得点型だけが退屈な待ちを選ぶ」「選択肢維持型が常に安全すぎる」などの差分を staging に残せる。人間フィードバックが来た後は、どの persona の失敗ログが Nao_u の指摘に近かったかを見る。近ければその persona の重みを次回評価に残し、遠ければ捨てる。procedural persona を恒久ルール化するのではなく、プロトタイプのジャンルごとに小さく入れ替えるのが現実的である。

最初の probe はかなり小さくできる。既存の headless runner に `persona_name` と `weights` を渡し、同じ seed list を 3 persona で回すだけでよい。出力は `persona_name`、`seed`、`result`、`score`、`available_actions_mean`、`risk_time`、`objective_progress` 程度に絞る。LLM に評価させる時は、全体平均ではなく「persona 間で一番割れた指標」を優先して読ませる。これなら MCTS の実装に入る前に、複数視点評価が制作判断を良くするかだけ検証できる。

■ メリット・デメリット
メリットは、難易度を単一スカラーにしないこと。MaxS / MinS が performance range を作り、MaxM / MinM が選択肢の広がりを測るので、同じ「簡単」でも高得点が出る簡単さと、選択肢が多くて迷う簡単さを分けられる。41 人の人間 trace と比較しているため、完全再現ではないが、agent の結果を人間範囲の外枠として使う位置づけも明確である。

デメリットは、Match-3 に強く依存していること。スコア、合法手数、20 move、combo という指標は、STG や探索ゲームにそのまま移せない。特殊ピースも除外されているため、現代的な Match-3 のスキル差や爆発的連鎖は薄い。また 41 人の user study は参考にはなるが、参加者属性が偏りやすく、persona が人間心理を十分表すとは言えない。遺伝的プログラミングで数式を進化させる部分も、短期プロトタイプでは重い。最初は進化なしの手書き重み persona で十分で、効果が見えた場合だけ探索や進化へ広げるべきである。

■ 判定
部分採用。MCTS 数式進化までは採らず、persona 別 headless run という評価設計を採る。次のパズル/レーン型 prototype では、少なくとも 3 種の評価関数で同一 seed を走らせ、平均結果ではなく persona 間の差分を調整材料にする。
