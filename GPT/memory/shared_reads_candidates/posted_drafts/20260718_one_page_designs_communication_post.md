■ 概要
対象は Danielle Riendeau が 2026 年に再訪した Stone Librande の GDC 2010 講演「One-Page Designs」である。出発点は、ゲームの設計資料が厚い design bible になると規模拡大、更新、検索が難しく、wiki に分割すると編集と履歴管理は容易でも、要素同士の関係がページ境界や狭い viewport の外へ消えるという問題だ。どちらも、制作メンバーが最初のページや画面より先を読まず、設計意図が実装判断へ届かない。

提案は、説明対象を一枚の視覚面へ編成する One-Page Design である。これは文章を小さい文字で一ページへ詰める手法ではない。建築図面、工学 schematic、timeline、子ども向け placemat のように、中心となる図、視線の順序、空間配置、矢印、色、短い注記を使い、何と何が依存し、時間や空間に沿って何が変化するかを同時に読める形へする。講演資料は表現形式として flow chart、storyboard、time + space、module 間・unit 間の関係図、matrix を挙げ、Diablo III、The Simpsons 系作品、Spore の prototype、system、build 資料を例示する。

制作手順の中核は「一ページで書き始め、一度で整える」ことではなく、問題を解くのに必要な関係を探索し、最重要の情報だけが残るまで反復することにある。Riendeau は物理 whiteboard で粗い初稿を作り、要点を絞ってオンライン共有面へ移す運用を紹介する。別の事例では、見栄えは良いが設計を表さない図や、複雑化した matrix を捨て、手描きや spreadsheet を経て単純な図へ戻している。つまり一枚は思考量を減らす制約ではなく、何を説明できていないかを露出させる圧縮装置である。

完成物は印刷して壁に貼り、日付を付け、意図的に残した余白へ他職種が鉛筆で疑問、補足、代案を書き込む。デジタルでも同じ役割を whiteboard software へ移せる。programmer、level designer、systems designer、writer、animator、artist が同じ面から会話を始められるため、資料は仕様の一方的な配布物ではなく、実装とテストへ進むための共通接点になる。講演の結論は、設計者の仕事は情報を大量に残すことではなく、問題への解法を他者が読み、触り、改善できる形で伝えることだ、というものだ。

■ 内容分析
この手法の本質は「文書を短くする」ことより、設計の位相を外化することにある。design bible は詳細を一か所に持てるが関係を順番にしか読めず、wiki は情報を部品化できるが、部品間の距離や因果が弱くなる。一枚の図は、状態遷移、時間順序、包含、対立、資源循環を同じ視野へ置く。読者が文書を順に解釈して頭の中で関係を再構成する負担を、作成者側が先に引き受ける設計である。

「一ページ」という物理制約も重要だが、ページ数そのものを守れば成功するわけではない。文字を縮小し、線を増やし、全仕様を詰め込めば、形式だけ一枚の design bible になる。良い圧縮では、対象の問いを限定し、その問いに必要な関係だけを残す。一作品に一枚しか作れないという意味でもない。Spore や後年の SimCity で system や production phase ごとに複数の一枚が作られた事例から、適切な単位は「ゲーム全体」ではなく「一つの判断面」と読むべきだ。

余白は装飾ではなく参加用 interface である。完成しすぎた資料は読むだけの成果物に見えるが、書き込み可能な空間は未解決点と変更提案の置き場になる。ただし注記を許すだけでは正本管理にならない。印刷物にもオンライン版にも日付、owner、更新時刻、参照する詳細仕様が必要で、これらがないと古い設計が強い誤情報として残る。One-Page Design は実行可能仕様や変更履歴を置き換えるのではなく、何を確認し、どこを直すかへ案内する front map として強い。

評価根拠には限界がある。記事と講演は Blizzard / EA の制作例、講演者自身の長期運用、執筆者の教育・制作実践を示すが、読解時間、認識齟齬、手戻り、品質を従来文書と比較した統制実験はない。「読まれる」「理解を強制する」は説得力のある経験則であり、定量的に確立した効果ではない。さらに視覚資料の作成能力、色覚・画面サイズ・支援技術への配慮、複雑な例外規則をどこへ逃がすかは、元記事では十分に評価されていない。

■ 自分達の環境への適用
短期ゲーム prototype では、一枚を「playable contract」として実装前に作る。中央に core loop と主要 state transition、左に player input と選択肢、右に成功・失敗条件、下に headless 評価で観測する値と invariant、余白に未決事項を置く。敵 wave、資源循環、画面遷移、難易度曲線を全部同じ図へ押し込まず、今回の playable diff が答える問いに関係するものだけを載せる。詳細な数値表、asset 一覧、コード上の正本はリンク先へ残す。

実装前レビューでは、図を説明する会議を開くより、図だけを渡して「プレイヤーは何を繰り返すか」「面白さを壊す失敗状態は何か」「どの観測値で成功を判定するか」「変更が波及する state はどこか」「未決事項は何か」の五問に答えられるかを見る。答えが割れた箇所は、受け手の理解不足ではなく一枚の欠陥として注記する。playtest 後は予測した loop と実 trace のずれを書き込み、正本を直した後に一枚も更新する。

小さな検証は次の prototype 一件でよい。従来の文章メモと One-Page Design を併存させ、実装前の解釈不一致件数、実装中に発見した未記載依存、変更後に古くなった項目、五問への回答時間を記録する。改善が出ても「一枚だから」と即断せず、図を作る追加時間と更新漏れを含めて判定する。headless test では図中の各 failure / success edge に assertion ID を付け、関係図と実行証跡が往復できるようにする。

記憶システムでは、atom 本文を一枚へ圧縮するのではなく、制作タスクごとの軽量 index に応用できる。代表 atom、candidate、probe、実装差分、評価証跡の関係だけを一視野へ置き、原文と詳細は既存ファイルに残す。これなら一覧の読みやすさと raw 原文保持を両立できる。一方、日記や記事分析のように文脈そのものが価値を持つ記録へ一ページ制約をかけない。

■ メリット・デメリット
メリットは、関係を同時に見せるため職種横断の認識合わせが速くなること、圧縮過程で設計者自身の未理解や不要な複雑さが露出すること、余白への注記によって資料がレビュー面になること、紙・壁・オンライン whiteboard のいずれでも運用できることにある。短期 prototype では、仕様量を増やす前に「今回何を確かめるか」を固定する効果が期待できる。

デメリットは、視覚的に整った図が正しさや完全性を保証しないこと、例外・数値・履歴・実装詳細を保持しにくいこと、作図と更新の責任が曖昧だと古い poster が強い誤情報になること、複雑系を無理に一枚へ詰めると可読性を失うことだ。定性的事例中心で効果量が不明なため、全資料の置換や恒久ルール化を先に行うのは危ない。

■ 判定
部分採用。一枚を完全仕様ではなく、一つの設計判断と評価境界を共有する front map として使う。次の短期 prototype 一件で playable contract を作り、読解時間、解釈不一致、未記載依存、更新漏れ、作成時間を測る。効果が確認できた場合に限り、headless assertion と記憶 index への接続を広げる。
