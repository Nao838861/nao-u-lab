■ 概要
Klei Entertainment のリードデザイナー Nels Anderson と創業者 Jamie Cheng が、『Mark of the Ninja』を16か月で完成させた過程を振り返ったポストモーテムである。出発点は「忍者らしく振る舞い、そう感じられるゲーム」を作ることだったが、当時ほぼ前例のない横スクロール2Dステルスが成立する保証はなかった。そこで新技術と新ジャンルを同時に賭けず、『Shank 2』の成熟した描画・アニメーション基盤を使って設計リスクの検証へ早く入った。同時に、手描き済み背景の修正が広範囲の描き直しへ波及した旧工程を捨て、環境用texture tilingとpreview toolへ数か月を先行投資した。ステルスは光源、遮蔽物、敵、経路の微調整で面白さが変わるため、レベルを安く変更できること自体をゲーム設計能力と見なした判断である。

設計の核は、ステルス行動を Observe / Plan / Execute / React に分解し、既存3D作品の慣習ではなく「player-centric systems」と「intentional gameplay」を目標にしたことだ。複数の相互作用する仕組みを読み、複数の有効な経路から自分で選び、意図した操作を実行し、崩れた状況へ反応する。この体験を2D画面で明瞭にするため、一般的な段階式の隠密度を捨て、プレイヤーは hidden か illuminated の二値だけにした。暗い世界観と読みやすさを両立させ、ボタン入力後の結果を予告するanimation cue、音や視界の表示、光源配置などを、週2回の初見playtestで調整した。Craigslistで集めた未経験者の要望をそのまま実装せず、「戦闘が不満」という声なら、なぜ隠れず戦いたくなったのかまで遡った。tutorialも文字を大きくするのでなく、二つの対象を同時に狙わなければ進めない配置など、行動を通して理解させる形へ変えた。

成功談だけではない。初期には炎の伝播や状況ごとに異なる複雑な敵反応を数か月作ったが、面白い判断へ結びつかなかった。開始約4か月で核が曖昧なままだと認め、さらに2か月、レベルを次々作って「どの配置が興味深い選択を生むか」を探し、大量のartとanimationを捨てた。一般プレイヤーへのtest開始も約8か月目で、粗さを理由に遅らせずもっと早く行うべきだったと自己評価している。物語と上級能力の確定も遅れ、air-dashとtime-stopは相当量の実装後に廃棄、採用したshort-range teleportさえ出荷認証の2〜3か月前に入り、既存レベルの再設計を招いた。大型レベルでは、先行投資したtoolも差分反映に数分、全exportに最大1時間かかるようになった。最終的には予定を3〜4か月延長し、全編を通したtestでlevel、control、cinematic、重複itemを磨いた。結論は、原則・可読性・反復基盤・初見観察が連動すれば未知の形式を成立させられる一方、核と後半要素の確定が遅いほど、制作後半へ高価な再作業を送るというものだ。

■ 内容分析
この記事で最も重要なのは、Observe / Plan / Execute / React という四語そのものではなく、抽象原則を制作判断へ降ろす鎖が見えることだ。例えば「プレイヤー中心の選択」を守るために、隠密度の精密さより判断可能性を優先して二値化する。「観察」を成立させるために、敵AIだけでなく暗所の背景、光、音、入力予告まで情報設計として扱う。そして、その配置を何度も変えられるtoolと、知識を持たない人の行動観察を用意する。面白さをmechanicの数ではなく、情報を読み、意図を作り、結果との差を回収できる循環として設計した点が強い。

playtestの読み方も具体的である。発言は解決策ではなく症状であり、観察すべき対象は「何を欲しいと言ったか」より「なぜその行動を合理的だと思ったか」だった。戦闘を強くしてほしいという要望に従えばステルスの核を壊し得るが、戦闘へ向かわせた情報や報酬を直せば核を保てる。ただし記事自身が示す通り、週2回という頻度だけでは早期検証にならない。一般参加者へ見せたのが開発中盤である以上、最初の8か月に形成された前提や資産は既に高価だった。「高頻度」と「低成熟度から始める」は別の条件である。

tool投資にも二面性がある。texture tilingとpreviewは変更の波及を抑え、生産性へ乗数的に効いた。一方、実際の大型レベルという最大負荷を早期に通しておらず、終盤にはexport時間が設計反復を止めた。つまり「toolを先に作る」が教訓ではない。変更頻度が高く、他職種への波及が大きい箇所へ投資し、想定最大規模の代表シーンで待ち時間を継続計測することが教訓になる。同様に、後半能力は単体の楽しさだけでなく既存contentへ要求する再作業量まで含めて早く試す必要がある。

限界も明確だ。これは一作品の成功後に書かれた回顧で、対照実験や継続率などの定量評価はない。成熟した既存pipeline、Microsoftとの問題解決型の関係、3〜4か月の自費延長が結果へ寄与しており、四原則やplaytestだけを成功原因として分離できない。また、binary stealthは2D画面で状態を即読させる目的に適合した局所解で、曖昧さや不確実性そのものを楽しむゲームへ一律移植すると探索の緊張を失う。それでも、成功と失敗が同じ工程上で対応しているため、因果の証明ではなく制作上の反証チェックリストとして有用である。

■ 自分達の環境への適用
短期ゲーム制作では、実装前に作品固有の体験循環を4〜6個の動詞で書き、各動詞に「プレイヤーが読むcue」「選べる代替」「意図を表す入力」「失敗後に戻せる操作」を一つずつ対応させる。四語を固定テンプレートにはせず、例えば回避ゲームなら Detect / Commit / Thread / Recover のように対象作品の判断へ翻訳する。最初のplayable diffは全contentの縮小版ではなく、この循環が一周し、情報不足と操作失敗を区別できる一場面にする。

評価はheadlessだけで閉じない。headlessでは発見から入力までの時間、選択経路、警戒遷移、失敗後の回復率、同じ安全策への集中を記録し、ルール上の選択肢が実際に使われるかを見る。しかし暗い画面が読めるか、cueが入力結果として理解されるかは画像と初見行動の問題なので、節目ごとに説明なしのfirst-contact testを置く。発言は原文保存しつつ、修正単位は要望でなく「どのcueが、どの誤推論を生み、どの行動へ押したか」にする。buildが粗いことは延期理由にせず、仮素材でも核の推論が観測できる版を早く用意する。

制作基盤は、汎用editorを先に完成させるのでなく、直近の反復を支配する待ち時間へ絞る。levelの一部変更、再読込、headless batch、代表的な最大規模sceneのexport時間を計測し、変更1回がasset再生成や手作業修正へ連鎖する箇所だけ自動化する。新しい能力は、単体sandboxで面白さを確認した後、「既存levelの何割を壊すか」「敵・camera・tutorialへ何種類の追加cueが要るか」を採否条件に含める。後半用だから後半に試すのではなく、contentが依存する前に最小版を通し、不採用時の損失を小さくする。

最後に、機能完成と全編調整を同じ締切へ押し込まない。vertical sliceの時点で、全編を通して削るための期間を別枠に置く。追加asset数ではなく、重複能力の統合、難所のguard数、光源位置、操作猶予、説明の冗長さを調整する期間である。今回の小さな検証は、既存prototype一つについて体験動詞と観測可能なcueを表にし、最も曖昧な一循環だけを変更前後のheadless traceと初見動画で比較する形がよい。

■ メリット・デメリット
メリットは、作品の核、画面上の可読性、playtest、tool、content確定時期を別々の話にせず、反復一回の費用と質として結べることだ。要望追従を避けながら初見者の失敗を利用でき、複雑な仕組みを足す前に「興味深い選択を生んだか」で廃棄できる。能力の楽しさと再作業コストを同時に見るため、終盤の連鎖的な作り直しも減らせる。

デメリットは、動詞への圧縮が早すぎると、まだ言語化できない手触りや偶発的発見を切り捨てることだ。二値化と明瞭なcueを普遍原則にすると、曖昧さを読む面白さまで消す。初見testの反応は対象者、説明、build品質に左右され、少人数の迷いを即座に一般化すると過修正になる。tool投資も短期作では回収前に制作を終える可能性があるため、待ち時間と変更回数から回収可能性を見積もる必要がある。

■ 判定
部分採用。体験動詞からcue・選択・入力・回復を結ぶ設計、要望でなく行動動機を見る初見観察、変更の波及を減らす局所tool、後半能力をcontent依存前に試す採否ゲートを採る。四段階モデル、binary stealth、週2回という頻度は作品固有の解であり固定ルールにはしない。まず一つのprototypeで、最も曖昧な体験循環を変更前後のtraceと初見観察で比較する。
