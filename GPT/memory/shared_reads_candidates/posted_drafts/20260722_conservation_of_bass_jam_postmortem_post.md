■ 概要
『Conservation of Bass』は、テーマ「Equivalent Exchange」の第48回 GM48 game jam に48時間で制作された puzzle game である。結果は総合1位だけでなく全評価カテゴリで1位となり、記事執筆時点では同 jam 史上最高評価だった。作者が強調するのは受賞結果そのものより、過去の jam では scope を広げすぎ、重要 system や致命的 bug が締切直前まで残っていたのに、今回は最も穏やかに開発できたという制作過程の差である。その差を生んだ中心策が、coding 前に mechanic の展開可能性を調べる「同じ mechanic で異なる level を少なくとも5つ考えられるか」という採用試験だった。

チーム内では複数の puzzle 案が出たが、この試験を通ったのは「player の位置を1×1 tile と交換する」案だけだった。単純な規則を早期に固定できたため、最終日まで gameplay を変える事態を避け、level design を coding、art、sound と並行して進められた。作者は game design には実際に遊ばないと分からない edge case もあると認めつつ、本作では基礎が単純だったため、mechanic を決めた時点で最終像がほぼ見えたと振り返る。つまり5案の列挙は完成を保証する仕様書ではなく、実装へ進む前に一つの規則が複数の問題を生めるかを安く調べる gate として働いた。

テーマへの接続でも、規則を足すより一貫させる変更を選んでいる。初期案には交換できる1×1 block と交換できない1×1 block が混在したが、「同じ mass のものとは交換できる」という conservation of mass の見立てに合わせ、すべての1×1 block を交換可能に統一した。一方、player が tile と結合して ladder のような大きい物体と交換する案や、goal の water glass 自体を交換する案は、本則を複雑にするため採用しなかった。visual は最小限で平面的な pixel art に smoothing shader を掛け、効果音と音楽には vocal sample を使った。結論は、単一 mechanic の展開可能性を早期に確かめ、例外と追加規則を抑えたことで、48時間を機能追加ではなく並行制作と polish に使えた、という postmortem である。

■ 内容分析
「5 level を考えられるか」が測っているのは、面白さそのものではなく mechanic の生成力である。一つの操作が、配置や順序や到達可能性を変えるだけで異なる問題状態を作れるなら、level ごとに新しい verb を実装せず内容を増やせる。逆に二つ目、三つ目の案を作るたび例外 tile や新能力が必要になるなら、中心 mechanic ではなく追加要素が level 数を支えている。coding 前の列挙によって、この違いを実装費が発生する前に露出させられる点が重要である。単なる brainstorming の「案が5個ある」ではなく、同じ入力と同じ遷移規則から5個が出ることが gate の芯になる。

本作では、この gate が scope 制御だけでなく職種間の契約を安定させた。level designer は交換規則を前提に配置を作り、programmer はその規則を実装し、art と sound は読みやすさと手触りを補える。途中で core verb が変われば、level、code、tutorial、asset の全てに手戻りが波及するが、早期に固定できれば各工程が並走できる。polish の時間は偶然余ったのではなく、仕様変更による直列待ちと再作業を減らして先に確保された、と読むべきである。

テーマ適合の修正も示唆的だ。「交換可能な1×1」と「交換不能な1×1」を見た目などで教える代わりに、同じ mass なら交換可能という一文へ world の規則を揃えた。これは機能追加ではなく例外削除であり、player が覚える条件を減らしながら題名、theme、mechanic を同じ説明へ圧縮している。ladder や goal 交換を見送った判断も同じで、個々には面白そうでも、結合状態や特殊な勝利条件を入れると「何と何が等価か」の境界が増える。短期制作では新規性の量より、少数の規則から予測できる範囲を広げる方が、理解可能性と level 展開を同時に守りやすい。

ただし、記事の評価根拠には明確な限界がある。5 level rule を使わなかった対照制作はなく、成功は経験あるチーム、theme 適合、visual、vocal sound、jam の参加者層などが合成された結果である。全カテゴリ1位や最高評価は成果の強い外部指標だが、どの要因が何点を生んだかは分離できない。また「5」は経験則であり、5案の質、難度曲線、重複度、長編へ拡張した時の深さを保証しない。成功作の回顧なので、同じ gate を通過して失敗した案が観測されない survivor bias もある。従って、5という数を普遍的な閾値にするのではなく、実装前に展開不足を発見する検査として使うのが妥当である。

■ 自分達の環境への適用
短期 game prototype の着手前に、core mechanic を「入力・状態遷移・結果」の一文で書き、その規則だけを使う5つの level sketch を作る。5つは見た目だけ変えず、導入、空間制約、複数対象の順序、既知規則の反転的利用、複合 mastery のように要求する判断を分ける。各 sketch に新規 actor、例外条件、新しい操作が必要なら印を付け、二つ以上が追加規則に依存する場合は実装へ進まず、mechanic の再選定か scope の明示的な拡張へ戻す。数を満たすための水増しを防ぐには、「同じ解法を配置だけずらしたものは1案」と数える。

最初の playable diff では、5 level 全部を完成させず、最も単純な案と最も境界条件の厳しい案を一つずつ実装する。前者で規則が初見で読めるか、後者で mechanic が本当に異なる判断を生むかを見る。human playtest では、説明後の完走率だけでなく、操作後に何が交換され、次に何が可能になると思うかを尋ね、player が規則を再構成できるかを確認する。5案を列挙できても、この二端の probe が同じ思考しか要求しないなら、展開可能性は見かけだけである。

headless 評価には level の面白さを直接代行させず、固定した規則の invariant を守る役を持たせる。交換前後で対象の占有数や保存すべき量が変わらないこと、swap が定義された対象だけに作用すること、操作後に goal が到達不能になる state が意図せず生成されないことを検査する。小さな map なら state space を探索して各 sketch の solvability、最短手数、行き止まり率を比較できる。ただし最短手数の差を「異なる面白さ」と同一視せず、human test に渡す候補の重複や破綻を早期除去する補助指標に留める。

制作サイクルでは、gate 通過時の mechanic 文と棄却案を staging に残し、以後の変更が本則の明確化か新規則の追加かを区別する。本則が安定したら level、code、asset、sound を並行化し、新規則の追加には既存5 sketch の再検証を要求する。polish は末尾の余り時間ではなく、gate 通過後に予約する工程とする。これにより、「作り始めたから捨てにくい」を避け、単純さが生んだ時間を feedback、animation、audio、難度調整へ確実に振り向けられる。

■ メリット・デメリット
メリットは、展開しない mechanic を coding 前に安価に落とせること、level design を早く開始して他工程と並走できること、追加機能ではなく配置と組合せで content を増やしやすいことにある。また、theme を規則の例外削除に使うと、世界観、操作、説明が一つの mental model に揃う。棄却案も「悪い案」ではなく、短期版の本則を守るために将来の拡張へ隔離できる。

デメリットは、個数目標が容易に Goodhart 化することだ。似た配置を5個並べても学習、驚き、難度曲線は生まれず、紙上で成立しても操作感や可読性は分からない。単純な mechanic を早く固定することが、playtest で必要と判明した変更まで拒む口実になる危険もある。さらに jam の48時間と長期製品では必要な持続性が違い、完成品なら5案ではなく、複数 chapter にわたる組合せ、失敗からの回復、accessibility、content production cost まで別途検証する必要がある。

■ 判定
部分採用。固定値としての「5」や受賞との因果は採用せず、実装前に同一規則だけで異なる判断を要求する複数 level を列挙し、展開不足と例外依存を発見する着手 gate を採用する。次の短期 puzzle prototype では5 sketch と両端2案の playable probe を作り、invariant は headless、規則理解と手触りは human playtest で判定する。gate 通過後は core rule を職種間の契約として固定し、追加 mechanic より polish を優先する。
