■ 概要
『Dungeon Puzzle Sweeper』は、『Dragonsweeper』に着想を得た、Minesweeper 型の盤面へ RPG 的な敵・規則を載せたブラウザゲームである。作者 Brianna Townsend は、元作品の盤面には「ドラゴンは中央」「リッチは四隅」「スライムメイジは辺上で周囲を8に囲まれる」「ガーゴイルは向かい合う一対」といった、互いに依存する配置条件が多数あることに注目した。単純に各ユニットについて空きマスを走査し、既配置ユニットとの関係を確認してランダム配置すると、関係検査が連鎖して生成に最大約1秒かかり、さらに途中まで埋めた後で残りを置けない盤面に到達する。捨てて再生成すれば遅くなり、失敗を許せば必要ユニットや100%到達可能スコアが保証できない。

作者が採った解法は、各配置対象に「現在置けるマス集合」を持たせ、候補数が最少の対象から決める方法である。初期候補は種類ごとの関数で作り、配置のたびに、置いた種類と位置を未配置の全対象へ通知して候補を削る。中央しか候補がないドラゴンが先、次に候補4箇所のリッチ、辺が減りやすいスライムメイジ、と制約の強い対象から確定する。ガーゴイルの片方を置けば相方の候補が1〜2箇所へ狭まり、次の処理対象へ浮上する。候補が0になった場合は、各手で保存しておいた盤面へ一手戻り、直前に選んだ位置を候補から除外して別案を試す。そこも尽きればさらに再帰的に戻る。これは記事では “Waveform Collapse” と呼ばれているが、実体は最少残余値ヒューリスティック、制約伝播、深さ優先の backtracking を組み合わせた制約充足探索に近い。

制作面では、自作 C++ エンジンを Emscripten、SDL2、Makefile で WebAssembly 化した。Zig の cross compile は資料不足で断念し、32bit 化や sRGB 二重適用による暗転を解決した後、縦長画面、touch marking menu、Flask と Redis の leaderboard を加えた。新規アートと UI を3〜4日で仕上げた公開版は、24時間で1000 browser plays、3週間で5000超、その時点でも1日100超の play が続いた。「スマートフォンで遊べる」配布形態まで設計したことが成果につながっている。

■ 内容分析
価値が高いのは、生成を「乱数でそれらしい盤面を作る処理」ではなく、「全制約を満たす解を探索し、失敗を局所的に巻き戻す処理」と定義し直した点である。最少候補から置くと、後から置き場所を奪われやすい対象を早期に処理できる。失敗時も盤面全体を捨てず、どの決定が候補消失を起こしたかに近い位置まで戻れる。配置規則を種類ごとの初期化関数と更新関数へ分けたため、「配置順を手書きする」のではなく、新しい制約を同じ探索器へ追加できる。

ただし、一般的な Wave Function Collapse と同一視すると設計を誤る。隣接パターンから局所許容集合を収縮する WFC より、この記事の対象は中央・角・一対関係など大域制約を持つ CSP である。使える核は名称ではなく、MRV、制約伝播、backtracking である。記事には旧方式の「最大約1秒」はあるが、新方式の生成時間、backtrack 回数、最悪探索量、snapshot のメモリ量はない。盤面全 copy は小盤面では明快でも、規模が増せば差分 undo が適する。

「全ユニットを置ける」は「良い puzzle」の十分条件でもない。初手から推論可能か、運任せの分岐がないか、難度分布が狙い通りかは未評価である。1000/5000 plays も配布成功の指標であり、生成品質、完走率、retention を直接示さない。確認できるのは制約違反を避ける実装と公開導線の有効性で、面白さの保証ではない。

実装上は、制約更新の正しさも注意点になる。ある配置によって候補から除く処理は書きやすいが、巻き戻し時に候補集合まで完全に復元しなければ、存在する解を消したまま探索を続ける。盤面だけの snapshot で十分か、各 tile の候補集合も含むのかは記事から明確でない。また「最後に置いた tile から更新する」方式では、複数段の依存が一回の通知で収束するか、候補減少を queue へ積んで fixed point まで伝播する必要があるかを規則ごとに確認すべきである。ここを曖昧にすると、速いが不完全な generator になる。

■ 自分達の環境への適用
我々の配置型 prototype では、generator を「盤面画像を返す関数」ではなく、決定履歴を返す deterministic evaluator として作る。各 seed の配置順、各手の候補数、除外候補、backtrack 回数、最大巻き戻し深度、探索 node 数、生成時間、制約違反数を JSON に残す。p50/p95 時間と最悪 seed を固定回帰にし、候補0の seed も失敗直前盤面と decision stack を artifact に残す。

最初の probe は8〜12種類、1000 seed 程度でよい。必須個体数、角・辺・中心、距離、対、非隣接を個別 invariant にする。別系統の solver で解の有無、推論手数、仮定が必要な分岐数、序盤の選択肢数を測る。generator と検査器がロジックを共有すると同じ誤りを正解扱いするため独立実装にし、難度は生成時の backtrack ではなく player 側 solver の情報量で見る。

小盤面ではまず snapshot 方式を採り、p95 時間やメモリが閾値を越えた時だけ差分 undo へ移す。最適化前に failure seed と決定列を保存すれば、変更前後を同じ探索問題で比べられる。配布面は別 probe とし、portrait viewport、片手 touch、誤 marking の取り消し、初回 load、resume、leaderboard 送信失敗を早期 web build で通す。生成 invariant、playability、公開後 funnel は混ぜない。

性能 probe には通常 seed だけでなく、角・辺の候補を競合させる盤面、対になる個体が候補を奪い合う盤面、解が一つだけの盤面、意図的に解なしにした盤面を入れる。解なしケースが有限時間で停止し、診断可能な理由を返すことも生成器の仕様である。多様性は完成盤面の hash、種類ごとの位置分布、同型盤面を正規化した重複率で測り、「1000 seed が全部成功したが実質10形しかない」という退化を検出する。

Web 移植で起きた32bit 化と sRGB 二重適用は、game logic が同じでも platform contract が変わる例でもある。native と wasm で同じ seed から同じ盤面 hash が出るか、色変換、入力座標、save format、leaderboard payload が一致するかを golden test にする。これにより mobile 対応を UI の見た目だけでなく、決定性を保った配布経路として検証できる。

■ メリット・デメリット
メリットは、相互依存する規則を候補集合で表せること、壊れやすい決定を先に解くこと、失敗を全再生成でなく局所巻き戻しで診断できることにある。seed と trace を残せば回帰試験が容易で、WebAssembly と touch UI の早期導入もテスターまでの距離を短くする。

デメリットは、最悪時には探索が指数的になり、盤面全 copy も重くなること、制約充足だけでは解き味や多様性を保証しないこと、generator と評価器が同じ誤りを持ち得ることにある。元作品に近い企画では、出典、固有表現、遊び方の差、公開時期も別 gate で見る必要がある。

■ 判定
部分採用。MRV、制約伝播、backtracking、失敗 seed の trace 保存は配置型 generator の標準 probe として採用する。一方、「WFCを使えば良い盤面になる」という一般化、全 snapshot の恒久採用、play 数を生成品質の証拠とする解釈は採用しない。制約充足、解き味、配布導線を分離して評価する。
