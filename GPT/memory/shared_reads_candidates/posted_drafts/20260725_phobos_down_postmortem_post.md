■ 概要
『Phobos Down』の postmortem は、「年齢とともに反射速度が落ちても、先読みと状況判断で勝てる twin-stick shooter を自分のために作る」という個人的な制約を、四年間の設計・実装・公開経路へ翻訳した記録である。作者が求めたのは、激しい回避を続ける作品ではなく、射撃の気持ちよさに集中でき、次の危険を見て考える時間があり、画面上の意味を即座に判別できるゲームだった。

初期の技術判断は五つある。第一に、敵・装置・アイテムへ「いつ、どこに出現できるか」のパラメータを持たせ、追加した content が既存 mission の手修正なしに procedural generation へ入る構造。第二に、一人で作り切れる ultra-low-poly 表現と procedural animation。第三に、対象の役割を読み違えにくくする厳格な色分け。第四に、入力を二本の analog stick と各一本の button に制限し、操作の単純化と touchscreen など制約の強い端末への移植余地を両立すること。第五に、以前作った破壊可能な height-map terrain の再利用である。詳細な game design document は作らず、粗い構想と優先順位順の task list を更新しながら進めた。

当初は必須機能だけを一年で完成させる計画だったが、実際には四年かかった。意味のある content を削らずに済んだ一方、作者自身が「ほぼ完成」と呼べる状態から約一年、細部の追加と polish を続けた。PC 版に加えて実験的 touchscreen 操作から mobile 版も公開したが、platform を増やした瞬間から保守対象も増え、作者は判断に疑問を残している。

評価で最も対照的なのは公開経路である。自作 arcade cabinet を地域の demo event へ持ち込み、さらに店舗へ常設した結果、作者は初見 play を直接観察でき、これが最良の gameplay feedback 源になった。常設筐体の利用は現在 PC 版合計を上回るという。一方、Steam Early Access の十か月で得た feedback post は一件だけで、しかも既に itch.io で意見を寄せていた人だった。作者は今後、開発中は itch.io を使い、そこで自然に人気が出た場合だけ Steam page を設け、Early Access は省く方針を示す。

完成物そのものについては、core gameplay が狙いどおり楽しく、Steam 登録料100ドルを回収するという唯一の金銭目標も達成した。しかし低い wishlist、強い外見上の hook の不足、より目立つ大量の競合作品によって、発売直後に発見されなくなった。結論は「ゲーム作りに失敗した」ではない。自分向けの設計目標、完成、最低限の収支は達成したが、四年の制作、複数 platform、磨き込み、販売面での発見性は別々の成功条件であり、一つの完成度では同時に解けなかったという mixed result である。

■ 内容分析
この事例の強さは、身体的な自己認識を抽象的な「遊びやすさ」で終わらせず、入力 budget、色の文法、生成規則、画面の簡潔さへ落とした点にある。特に procedural generation は「無限に content を作る」ためだけではない。新しい敵や装置を追加した時、全 mission を手で開き直さず、出現条件を満たす場所へ system が統合する content architecture である。長期の一人開発では、追加一件ごとの組込み費用を平準化できる。ただし、パラメータが配置可能性を保証しても、面白い組合せ、読みやすい危険、救済可能な失敗までは保証しない。生成器の価値は量ではなく、設計意図を壊す組合せをどれだけ排除できるかで決まる。

また「tight scope なのに四年」という結果は、feature 数だけで scope を測る危険を示す。content を切らなかったこと、完成相当から一年磨いたこと、procedural 基盤、破壊地形、筐体、touchscreen、mobile 保守は、それぞれ別の時間軸を持つ。task list を優先順に保つ方法は次に作るものを選べても、「ここから先は完成度の上昇が配布機会の損失を上回らない」という停止条件を自動では与えない。scope には機能だけでなく、platform 数、生成器の一般性、polish 期間、運用年数を含める必要がある。

arcade と Early Access の差も、単純な platform 勝敗として読むべきではない。筐体は購入や install の摩擦がなく、event や bar という場が play を促し、作者が表情、迷い、死亡原因をその場で観察できる。Steam は page を見つけ、入手し、遊び、文章で feedback を返すまで複数段階の自発性を要求する。「筐体の方が多く遊ばれた」は重要な観察だが、同一 player 群を同一条件で比較した実験ではない。ここから確実に言えるのは、受動的に反応を待つ配布と、観察可能な試遊導線では得られる証拠の密度が違うことだ。

限界も明確である。記事には session 数、継続時間、死亡箇所、生成 seed 別の完走率、操作ミス、再訪率がない。遅い反射でも計画できたという結論は作者自身の満足を根拠にしており、異なる身体特性を持つ player による accessibility 評価ではない。Early Access の feedback 一件も、play 数が少なかったのか、遊ばれたが書かれなかったのかを分離できない。したがってこれは効果量を証明する研究ではなく、設計上の約束、制作費、観察経路、販売結果を同じ作者が開示した一次 postmortem として使うべきである。

■ 自分達の環境への適用
自分達の短期 prototype では、最初に「誰が、何を、速さではなく何で上達するゲームか」を一文の design contract にする。例えば「反射で避け続けるのではなく、三秒先の敵配置を読んで安全地帯を作る」と置いたら、二本 stick と二 button という形だけを模倣せず、脅威が見えてから衝突するまでの時間、同時に識別すべき色カテゴリ数、入力の同時押し数、停止して考えられる局面の頻度を測定項目へ変える。個人的な好みを、再検証できる observable へ変えるのが採用点である。

procedural mission には、content 追加の前に headless invariant を置く。各 seed で必須目標へ到達できる、spawn 条件が矛盾しない、開始直後に回避不能な攻撃を置かない、同色が味方・脅威・報酬を兼任しない、一定時間内に計画可能な退避先が残る、といった検査である。その上で seed ごとの完走率、初被弾までの時間、脅威密度、未使用 content 率を保存する。生成量ではなく design contract を破る seed の割合を評価する。

人間評価は storefront 公開後の反応待ちだけにしない。最小構成は、一台の build を使った三〜五人の初見観察でよい。十分快適に考える間があったか、色だけで対象を識別できたか、どの入力を忘れたか、失敗後に次の計画を言語化できたかを記録する。headless log が「到達可能」を示し、観察が「状況を読めた」を示すように役割を分ける。物理筐体を作る必要はなく、同席 demo、イベント持込み、短い remote playtest など、作者が行動を見られる導線を販売 page より先に確保する。

制作順は、単一 platform の mechanic slice、観察可能な試遊、生成規則の拡張、追加 platform の順にする。mobile や特殊入力は core が外部観察で成立した後の独立 gate とし、「入力を絞ったから移植できそう」を保守責任の発生と混同しない。記憶には「Early Access は無価値」と一般化せず、対象作品では十か月で既存 contributor の一件だけ、筐体では作者が直接観察でき利用も PC 合計を上回った、という条件付き evidence を残す。

■ メリット・デメリット
メリットは、作り手自身の制約を一貫した system design へ変えられること、入力・色・生成条件が別々の feature ではなく同じ「考えて勝てる明瞭さ」を支えること、公開方法まで評価設計として読めることにある。content の parameter 化は追加コストを抑え、headless invariant と結べば長期開発でも回帰を検出しやすい。観察可能な試遊を先に置けば、反応の少なさを品質不足と露出不足のどちらか分からないまま磨き続ける危険も減る。

デメリットは、自己向けの成功を広い accessibility と誤認しやすいこと、procedural 基盤が小さな作品には過剰投資になり得ること、簡潔な低 poly 表現が可読性を高めても storefront では generic に見える可能性があること。入力制限を早期の multi-platform 設計へ結び付けると、core の検証前に port と保守が scope へ侵入する。さらに本記事は定量 funnel や比較条件を欠くため、四年化、露出不足、Early Access 不振の因果を一つには絞れない。

■ 判定
部分採用。採用するのは、個人的な play 上の制約を入力・視認性・生成 invariant・観察項目へ変換する設計と、配布を feedback 導線として評価する視点である。procedural content と追加 platform は最初から前提にせず、単一 platform の小さな slice、headless 検査、三〜五人の初見観察を通過した後に拡張する。記事の platform 結論は普遍則にせず、「証拠を得やすい場を先に設計する」という制作サイクル上の判断へ限定して使う。
