■ 概要
MedGame は、静的な臨床症例を「読んで理解する資料」から、状態・選択・結果を順に経験する実行可能なストーリーテリングゲームへ変換する研究である。既存の医療教育LLMが質問応答や一回のフィードバックに留まりやすいのに対し、症例全体を診療開始から診断・治療までの意思決定列として再構成することを問題にしている。中心の着想は、LLMへ一度に「ゲームを作れ」と頼まず、脚本と制作進行を二つのエンジンに分けることにある。

第1段の Medical Narrative Designer は、患者要約を根拠に Clinical Storyline を生成する。構造は Act（診断、治療などの大段階）、Scene（問診、検査、方針決定などの局所段階）、Decision Node（プレイヤーが解く選択・情報収集）という階層で、各選択には正誤、説明、teaching point、次に開示される情報を持たせる。症例の事実を保つこと、教育上意味のある判断点を置くこと、Pydantic schema に適合して機械実行できることを別の制約として与える。第2段の Story Director は、この物語を画像・音声・動画の生成タスクへ分解し、各タスクを有向非巡回グラフ（DAG）にする。後の場面が同じ患者画像や直前の場面レイアウトを必要とする場合、`[task_001_output]` のような symbolic placeholder で依存を記述し、実行前に参照先、循環、graph depth を検査して topological sort する。初期フレームを視覚的な基準にし、上流アセットを後続生成へ渡すことで人物同一性と場面連続性を保つ。

評価用の MedGame Bench は PMC-Patients 由来の5,000症例を八診療科に均等化し、4,000件を学習、1,000件をテストに分ける。物語生成は JSON parse、schema、business logic の三層構造検証に加え、症例情報の統合、人物・場面利用、物語品質、臨床判断、選択肢、医学説明、質問、feedback を個別評価する。演出計画は sample/task 単位の構造妥当性と、resource assignment、API type selection、parameter content を測る。構造は規則で、内容は GPT-5.2 judge で採点し、50例ずつの人間評価との相関は医療物語で平均 r=0.81、演出計画で r=0.61 だった。

task-specific fine-tuning は、特に形式遵守と演出計画を大きく改善した。たとえば Qwen3-32B の物語 Strict validation は79.4%から99.1%へ上がり、fine-tuned Qwen3.5-27B の演出計画は sample-wise 99.8%に達した。一方、最良モデルでも医学的正確さは10点中おおむね7点で頭打ちだった。低得点草稿を医療専門家が修正すると、1症例あたり平均8箇所以上の修正が入り、医療正確性と教育品質は約6点台から約8点へ改善した。8人の上級医学生が同じ5症例を原文、text-only、multimodal で比較した pilot では総合知覚得点が3.19、3.79、4.19となり、multimodal は engagement、presence、usefulness を上げたが、軽い認知負荷も増えた。これは学習成果の証明ではなく、著者自身も work in progress としている。

■ 内容分析
この研究でゲーム制作に効くのは、生成モデルの銘柄より「意図を表す物語」と「制作物を作る依存グラフ」を分離したことだ。Clinical Storyline はプレイヤーが何を知り、どこで判断し、何を返されるかを表す意味層であり、Story Director の DAG はどの素材をどの順で作り、何を再利用するかを表す実行層である。前者を変えずに画像APIを差し替えられ、後者の失敗を物語破綻と混同せず検査できる。これは生成物を直接 runtime に流す方式より、失敗箇所の特定、再生成範囲の限定、キャッシュ、制作再現性に強い。

一方、論文中の「分岐ゲーム」と実証範囲は分けて読む必要がある。主系は既に起きた症例を忠実に再現する線形 trajectory で、Decision Node は学習者の入力を受けても基本的に既定の次状態へ進む。異なる選択から異なる臨床状態へ進む branching は付録の推論時拡張であり、branch state を人手または半自動で与え、医学レビューする案に留まる。したがって、選択が世界を大きく変えるナラティブゲームの生成能力まで示した研究ではない。また、DAG が保証するのは参照整合性と実行順であって、生成画像の顔や空間が実際に一貫することそのものではない。論文自身も長い modification chain は品質劣化を招くため避けるとしている。

評価設計にも二重の注意が要る。5,000件は強い規模だが、fine-tuning の参照軌跡は Gemini-3-Pro が生成し、内容評価は GPT-5.2 が担うため、人間制作の正解を学んだというより、強いモデルが作った規約と別の強いモデルのrubricへ適応した面がある。人間相関 r=0.61 の演出評価は順位付けの補助信号には使えても、単独の合否判定には弱い。さらに学生実験は8人・5症例の知覚評価で、保持率、推論改善、技能転移を測っていない。p=0.0039でも母数と課題範囲は小さく、「映像化が面白く見えた」と「教育効果が上がった」は同一ではない。

■ 自分達の環境への適用
生成型ナラティブ prototype では、MedGame の二段構成を小さく移植できる。まず `story_graph.json` に scene、入場時の既知情報、player action、state transition、feedback、終了条件だけを書く。次に別の `asset_tasks.json` に sprite、背景、台詞、効果音、演出の生成・変換タスクと input/output dependency を置く。ゲーム本体は生成モデルを直接呼ばず、検証済み artifact と事前生成assetだけを読む。これなら headless 実行で「全sceneに出口がある」「到達不能nodeがない」「選択前に答えを開示していない」「参照assetが存在する」「依存graphにcycleがない」を決定的に検査できる。

最小probeは、一つの短い分岐を3 scene、2 decision、2 endingで作ることから始める。物語層では状態遷移、情報開示順、選択肢の識別力を検査し、実行層では invalid reference、cycle、最大依存深度、再生成対象数を記録する。人間playtestでは「選択理由を説明できるか」「結果が選択の帰結として納得できるか」「映像追加で判断情報が見やすくなったか」「演出が操作テンポを遅らせたか」を別々に採る。LLM judge は草稿の異常候補を絞る用途に限定し、playable の面白さや選択の納得感は実プレイで確定する。

記憶システムにも同じ分離が使える。candidate 本文を意味層、URL・取得時刻・生成手順・検証結果を provenance DAG と見なし、内容更新と証拠更新を別 artifact にする。下流の atom や投稿がどの原文と評価から作られたかを参照で結べば、原文変更時に影響範囲だけ再評価できる。ただし制作サイクルへ入れる際は、巨大な汎用基盤にせず、まず story/asset の二ファイルと数個のvalidatorで効果を測る。

■ メリット・デメリット
メリットは、物語意図と生成ツール都合の分離、機械検証可能な中間表現、依存関係に基づく部分再生成、事前生成によるruntime安定性である。構造・内容・体験を別指標にした評価も、headlessが通っただけのゲームを完成扱いしないために使える。専門家修正がどの指標を改善したかまで測った点は、人間レビューを最後の飾りではなく工程として置く根拠になる。

デメリットは、schema適合が高品質を保証しないこと、線形症例向け設計を自由分岐へ広げると状態数とasset数が急増すること、マルチモーダル化が認知負荷と制作費を増やすことだ。参照軌跡とjudgeが共にLLM依存なので、評価系の盲点をモデル群で共有する危険もある。医療のような正解制約が弱い創作ゲームでは「正確さ」の代わりに何をrubricにするかを自分達で定義しなければならない。

■ 判定
部分採用。二段階artifact、依存DAG、決定的validator、事前生成assetという制作構造は採用価値が高い。一方、MedGame固有の五層schema、映像中心の演出、LLM judgeによる最終合否はそのまま移植しない。まず小規模な分岐prototypeで、デバッグ時間、部分再生成量、選択の納得感が改善するかを測ってから拡張する。
