■ 概要
対象は、3人チームが制作中のブラウザ向け roguelite『Loop Explorers』で行った強化方式の変更を振り返る devlog である。ゲームは『Loop Hero』に着想を得ており、戦闘後に得た tile を限られた町の区画へ置くと、外周を巡回して戦う hero が強くなる。区画を埋めた後も成長を続けられるよう、当初は gold を支払って既設 tile を upgrade する仕組みだった。プレイヤーは gold が入る loop 終了時など、手持ちの tile と資金を見比べ、いつ、どの tile に投資するかを任意に決められた。

問題は gold の価値が強すぎたことだ。作者のプレイでは、序盤の戦力を直接上げる tile より gold 生産 tile を優先し、終盤に町の大半を最大強化する方策へ寄りやすかった。そこで同じ tile を重ねて upgrade する duplicate merge 方式へ変更し、gold は三択候補の reroll と、将来実装する merchant に使う設計へ分離した。狙いは、gold を成長の必須資源から便利な補助資源へ下げ、経済優先の退化戦略を弱めることだった。

理屈の上では新方式の方が健全に見えたが、3人の実プレイではゲームが明確に楽しくなくなった。第一に、好きな時点で gold を支出する判断が消え、loop 終了時に資金と tile をまとめて配分する山場が薄れた。第二に、duplicate を素材として消費するため町に並ぶ tile が以前より約50%減り、村を作り上げる視覚的・空間的な充実感が落ちた。戦闘数を増やして tile 供給を補っても、この損失は解消しなかった。第三に、重要 tile の duplicate はほぼ常に merge、重要でない tile は merge せず別の強い tile を置くため、upgrade 判断が乱数で配られた選択肢に従うだけになりやすかった。

記事時点の結論は確定解ではない。チームは、いま楽しい旧方式へ戻し、経済 snowball は後続 build で調整する案へ傾いている。ただし戻せば gold が upgrade、reroll、merchant の三用途を背負うため、単一資源への機能集中という問題は残る。この devlog の価値は、長期 balance の完成解ではなく、「支配戦略を消した」という数値上の改善が、支出タイミング、盤面の密度、建設の手触り、選択の非自明さを同時に壊した因果を、失敗した実装差分として記録している点にある。

■ 内容分析
これは単純な「fun と balance のどちらを選ぶか」ではない。二案は、同じ upgrade cost を別通貨へ付け替えただけでなく、意思決定の主体と時刻を変えている。gold 方式では、資源を貯めるか使うか、複数の既設 tile のどこへ投資するかを、プレイヤーが任意の時点で決める。duplicate 方式では、upgrade の機会そのものが抽選結果に依存し、候補が現れた時だけ判断する。前者は「何を、いつ強化するか」、後者は「配られた duplicate を使うか」であり、判断空間が縮んでいる。

gold 方式の欠点は戦略の収束で、duplicate 方式の欠点は局所判断の自明化である。ここを一つの balance 指標で比べると見誤る。序盤の gold tile 優先率や終盤の最大強化率が下がっても、一周あたりの意味ある支出回数、選択肢間の価値差、決定を保留できる時間、町に残る tile 数が下がれば、体験全体は痩せる。特に「重要なら常に merge、不要なら常に置き換え」は、選択 UI が存在しても実質的には一択である。選択肢の個数ではなく、異なる状況で選好が反転するかを見る必要がある。

さらに duplicate は二重の費用を持つ。upgrade のために素材を一枚失う数値的な機会費用と、町の見た目から建物一つを失う表現上の費用である。後者は damage や win rate には出ないが、このゲームでは「町を作る」こと自体が進行の可視化なので重大だ。約50%という盤面密度の低下は、報酬量の減少ではなく、成長の痕跡を消す変更になっている。戦闘数を増やす対処が効かなかったのも、供給速度ではなく、merge が配置済み資産を継続的に吸い込む構造が原因だからだ。

一方、この記事の証拠は限定的である。制作チーム3人の自己 playtest で、外部参加者、run 数、勝率、到達 loop、選択ログ、両方式の反復比較は示されていない。旧方式への慣れ、新方式の UI や演出の未成熟、同時に変えた戦闘数などが感想へ混ざった可能性もある。したがって「gold 方式が普遍的に優れる」とは言えない。信頼できるのは、実装した新方式で三種類の具体的な損失を観測し、理論上の健全さだけでは採用できないと判断したところまでである。

■ 自分達の環境への適用
ゲーム prototype の経済や upgrade を差し替える時は、勝率や資源量だけでなく、最低でも四系統の回帰を分けて取る。第一は経済で、資源別の獲得量、支出先比率、未使用残高、特定生産物の初手選択率を見る。第二は判断で、一分または一 loop あたりの意味ある選択回数、候補間の価値差、同じ選択が連続する割合、状況により選好が反転する割合を見る。第三は盤面で、配置物数、占有率、種類数、消費された配置物数を追う。第四は表現で、成長前後の screenshot や replay を並べ、強くなったことが説明なしで見えるかを人間が判定する。

headless 評価で自動化しやすいのは最初の三系統である。gold 方式と duplicate 方式を同じ seed 群で走らせ、勝率だけでなく decision event、resource sink、board occupancy を event log に出す。強い bot が毎回同じ gold tile を取るなら退化戦略の警報、duplicate 出現時の選択がほぼ固定なら自明化の警報、強化速度が同じでも盤面数が半減するなら表現回帰の警報とする。ただし bot は「村を作った感じ」を測れないため、最後は短い実プレイと画像比較を残す。自動評価は fun の代理ではなく、どの軸が変わったかを早く発見する装置に限定する。

小さな検証なら、旧方式、新方式、第三案の3 build を固定 seed で比較する。第三案は gold を残しつつ退化戦略だけを弱める案で、例えば upgrade cost の逓増、gold 生産 tile の上限、戦闘力条件を満たさないと高 tier upgrade を解放しない、用途別 token への分割が考えられる。各 build で同じ10 runを取り、序盤の経済偏重、意味ある判断回数、最終盤面数、最大強化率を表にする。その後に人間が各 build を短時間遊び、「loop 終了時の配分が山場になったか」「町の成長が見えたか」を記録する。これなら fun を単一スコアへ潰さず、設計変更が何を直し、何を壊したかを追える。

制作記憶にも、変更理由だけでなく回帰軸をセットで残すべきである。「gold が強すぎたので duplicate にした」だけでは、次回も同じ副作用を見落とす。変更前の守りたい体験、修正対象の退化戦略、予想した改善、実測した副作用、戻す条件を一つの atom や devlog に揃える。成功した数値調整より、棄却した build がどの体験軸を落としたかの方が、次のゲームで再利用しやすい。

■ メリット・デメリット
メリットは、制作途中の一次記録なので、抽象的な design principle ではなく、変更前の問題、実装した対策、実プレイでの三つの回帰、撤回候補まで因果で追えることにある。また、資源 balance と判断密度、盤面密度、テーマ表現を分離する評価観点は、小規模 prototype へ低コストで移せる。特に「選択肢がある」と「非自明な選択がある」を分ける視点は有効である。

デメリットは、記事が結論前の短い devlog で、定量比較や外部 playtest がないことだ。旧方式へ戻す判断もまだ仮説で、gold の用途集中を解決していない。第三案の優劣も検証されていないため、具体的な処方箋として模倣すると危ない。また、約50%の盤面減少はこのゲーム固有の報酬頻度と merge 規則に依存し、別ゲームへ数値を一般化できない。

■ 判定
部分採用。gold 方式への回帰そのものは採用せず、「退化戦略を消したか」と「面白さを構成する判断頻度・盤面密度・成長表現を守ったか」を別々に回帰確認する評価法を採用する。次の経済・upgrade 改修では、固定 seed の event log と短い実プレイを組み合わせ、勝率改善だけで build を確定しない。
