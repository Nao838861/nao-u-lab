■ 概要
『Sengoku Space Opera』の開発記録は、友人とのplaytestで見つかった三つの不具合を、「game simulationの進行を、表示中のtabのlifecycleへ結び付けていた」という一つの設計ミスとして捉え直したrefactorである。症状は、別tabで条件を満たしたquestがMothership tabを開くまで完了通知されない、enemy撃破後にtimerが0になってもfleetが10秒以上returningへ移らない、別tabを見ている間に到着したfleetがSpace tabを開くまで処理されず残り続ける、というものだった。個別画面が非表示になると更新処理も止まり、playerが見ていない場所ではsimulation上の時間まで止まっていた。

修正は四段で構成される。第一に、briefingとquest通知を各tabから外し、app全体で生存するbackground managerへ移した。どの画面でも条件成立を受け取れるようにし、状態遷移の所有者をUIからglobal layerへ引き上げた。

第二に、building建設、gacha、fleet出撃などのserver responseへ、「quest stateが変化したので再取得せよ」という小さなsignalを自動的に同梱した。以前は各featureがquest refreshを明示的に呼び、一箇所でも忘れると通知が欠落した。変更後はresponseがcache invalidationの契機だけを伝え、clientは最新stateを取り直す。

第三に、fleet到着判定の基準時刻をserverへ揃えた。端末時計が少し進んでいるとclient countdownは0でもserverでは未到着で、次のpollまで約10秒待つ。そこでresponse headerのserver timeから端末との差を補正し、表示と受理条件を同じ時間軸へ揃えた。

第四に、fleetやscoutの次回到着時刻に、表示tabとは無関係なbackend checkを予約した。100 fleetでも全件にtimerを持たず、最早一件だけを予約し、処理後に次を選び直す。常時pollingやrealtime connectionなしに画面外eventを処理する設計である。

評価はbenchmarkではなく、公開後に友人が想定外のtab遷移で遊んだplaytestと実地debugである。作者はsolo開発中にhappy pathしか通さず、global化を後回しにしたと振り返る。結論は、症状別patchでなく四つの仕組みを組み合わせ、browser SLGの「非表示中は世界が止まる」問題を軽い構成で解くことにある。

■ 内容分析
この事例の価値は、三症状を別bugとして直さず、event ownershipとtime authorityの誤りへ還元した点にある。UIがstateの投影だけでなくsimulation進行まで担っていたため、presentation都合のvisibilityがdomain上のdeadlineを左右し、tab移動という無害な操作がgame ruleを変えていた。

responseへsignalをpiggybackする設計は、完成したquest objectでなく変化の契機だけを返してcanonical stateを別途fetchするため、buildingやgachaをquest表現へ密結合させない。ただし記事はsignalの形式、version、fetch失敗時の再試行を示していない。一度見逃すと古いstateが残るedge-triggerでは脆いので、dirty hintとして扱い、再取得を冪等にし、再接続時にもserver versionと照合する必要がある。

clock補正はclientの「到着した」とserverの「まだ到着していない」が食い違う境界bugを消す。ただしnetwork遅延や端末sleep中のclock jumpは説明されず、header時刻をそのまま合わせれば片道遅延分ずれる。到着処理はserverが冪等判定し、client補正は表示とrequest schedulingの近似に限定するのが安全である。

最早deadline一件だけの予約はpriority queueの先頭だけにwake-upを置く設計で軽い。一方、browserはbackground timerをthrottleし、端末sleepやprocess終了ではcallbackが失われる。wake-upは最適化とし、復帰時にはserver time以前のeventをまとめてcatch-upする必要がある。同時到着、重複check、失敗後の再送にもserver側の冪等性が要る。

評価上の限界は大きい。playtester数、再現回数、修正前後の遅延分布、request数、battery・CPU負荷、offline復帰、clock skew幅は提示されていない。「100 fleetでも最早一件だけ」という計算量上の説明はあるが、100 fleetでの測定結果ではない。またclient actionのresponseへsignalを載せる方式は、server側だけで自然発生するquest変化や別deviceからの更新を即時には運べない。常時接続を避ける判断は小規模SLGには合理的だが、更新鮮度の要求が高いmultiplayerへそのまま一般化はできない。

他人のtab移動で初めて壊れた発見経路も重要である。「Space tabを見ながら待つ」happy pathでは正しく見えるため、観測場所を変える、別作業へ行く、遅れて戻る経路をsystem invariantとして試す必要がある。

■ 自分達の環境への適用
複数sceneやmenuを持つsimulation prototypeでは、まず「UIを一度も開かなくても同じstateへ到達する」をinvariantにする。quest、enemy spawn、resource生産、cooldown、NPC移動などのdeadlineをscene scriptへ置かず、simulation stateとevent queueへ集約する。UIは現在stateを読むprojection、入力はcommand、時間経過はauthoritative clockを引数にしたtransitionとして分離する。

headless testではfake clockを使い、少なくとも五経路を同じ最終stateで比較する。(1) 対象画面を表示したまま期限を越える、(2) 別画面で期限を越えてから戻る、(3) 一度に複数deadlineを越える、(4) clockを進めた後にprocess復帰を模擬する、(5) 同じsignalや到着checkを二度配送する、である。比較対象は表示文言ではなく、quest version、fleet status、resource量、処理済みevent IDとする。これで画面依存、catch-up漏れ、重複適用をdeterministicに検出できる。

最小probeは大規模なglobal event bus導入ではなく、一種類のdeadline、例えばenemy spawnかresource回収だけを移す。`next_due_at`の最小値を一件予約し、wake-up時とresume時の両方で`due_at <= server_now`を全件処理する。通信を伴うならcommand IDまたはevent IDでserver処理を冪等化し、response signalはstate本体でなくversion更新のhintにする。計測するのは、非表示中の取りこぼし件数、期限からstate反映までの遅延、重複request数、resume時のcatch-up件数、active event数に対するtimer数である。

記憶システムでも、閲覧時だけingestやindex更新が進む構造を避け、保存・Slack取込・atom lifecycleをbackground processが所有し、UIやrecallはprojectionとして読む。canonical dataのversion変化をsignalしつつ、消失に備えたversion照合と冪等な再生成を正しさの土台にする。「通知は最適化、state比較が回復経路」という切り分けである。

■ メリット・デメリット
メリットは、UI lifecycleとsimulation lifecycleを分離し、症状横断で一つの原因を除けること、featureごとのquest refresh呼び忘れを減らせること、server基準時刻によってcountdown境界を揃えられること、全event分のtimerや常時pollingを持たず最早deadlineだけを予約できることにある。友人の自由なtab遷移から設計上の盲点を発見した過程も、観察playtestとheadless回帰testを接続する良い例になっている。

デメリットは、global managerを安易に巨大化すると新しい密結合点になること、response signalだけではserver発の変化やoffline期間を完全に扱えないこと、clock offset推定がnetwork遅延やsleepでずれること、background timerが実行時刻を保証しないことだ。記事には定量的な修正後評価、failure retry、重複配送、同時deadline、複数device、process終了後の復帰がない。従ってpatternは採用できるが、「これで画面外eventが完全に解決した」とまでは判断できない。

■ 判定
部分採用。event ownershipをUIからsimulationへ移すこと、server-authoritative time、最早deadline一件の予約は採用する。一方、response signalやtimerを正しさの根拠にはせず、version照合、resume時catch-up、冪等なserver処理を加える。まず一種類のeventで非表示・遅延復帰・重複配送をfake clock付きheadless testにし、取りこぼし0を確認してから横展開する。
