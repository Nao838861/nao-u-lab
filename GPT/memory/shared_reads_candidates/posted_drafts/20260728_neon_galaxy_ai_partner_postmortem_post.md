■ 概要
この記事は、Dreamcast・PlayStation 2・WonderSwan 時代にゲームプランナーを務め、その後25年間 web 制作に携わった作者が、AI と2週間でブラウザ RTS『NEON GALAXY』を公開した制作記録である。完成版は最大8人の online multiplayer、co-op、最大32の AI faction に対応する。作者はコードを書けるが、今回は自分では一行も直接書かず、ゲームの仕様と違和感を言葉にし、AI が実装し、browser 上の build を二者で確認する工程を release まで続けた。

着想の原点は、2000年前後の crunch 中に遊んだ名前も忘れた Flash game だった。光る星から三角形の艦隊を別の星へ投げる、単純で美しい感触だけが25年間残っていた。作者は現代的な strategy game が unit type、counter、tech tree、ability を積む方向を chess にたとえ、それらを記憶し続ける負荷を避けるため、囲碁やオセロに近い規則の少なさを選んだ。unit の種類と upgrade を捨て、戦闘は常に一対一の相殺、すべての星は艦を自動生産し、player の判断を「どの星から何隻をどこへ送るか」に限定する。生産操作から手を離すことで、盤面を観察して無防備な星を見つける瞬間を体験の核にした。

初日の指示は、黒い画面に48pxほどの neon circle を置く、周囲に小さな dot を回す、triangle を足す、click で別の星へ送る、という視覚と操作を一段ずつ増やすものだった。その日の終わりには、一つの HTML file に星、艦隊、占領を備えた playable prototype ができた。作者はその初日版を改変せず公開し、2週間後の release 版との間に、単なる「AI が速かった」という感想ではなく、実際に触れる before/after artifact を残している。

工程の中核は、長い完成仕様を先に渡すことではない。作者はゲームプランナーの仕事を「頭の中の game を、別の人が実行できる言葉へ変換すること」と定義する。何が動くか、どう感じるべきか、現在の build の何が違うかを言語化し、AI の実装を画面で確かめ、screenshot と「余白が大きすぎる」のような短い修正指示を返す。この loop を2週間繰り返した。記事の結論は、実装能力が不要になったという一般論より、planner として長年鍛えた仕様化・観察・修正指示の技能が、AI との制作にほぼそのまま移ったという当事者の発見にある。

■ 内容分析
この事例の価値は、「一行もコードを書かなかった」という派手な看板ではなく、設計の情報を playable build へ変換する単位が小さいことにある。最初から multiplayer や32 faction を含む全体像を一括生成したのではなく、円、周回点、三角形、移動、占領の順に、視覚的に検証できる一変更を積んでいる。各変更の合否を browser で即座に判断できるため、言葉の曖昧さが長期間蓄積しない。これは仕様書の量を減らしたというより、仕様を静的文書から「指示、実装、観察、修正」の短い閉ループへ移したと見るべきである。

もう一つ重要なのは、AI 制作と game design の簡素化が別々の話ではない点だ。unit type や tech tree を削った規則は、player の認知負荷を下げるだけでなく、AI が実装し作者が目視確認する state space も狭める。全 unit が一対一で相殺されるなら、strength table や upgrade 依存の例外が減り、画面上の数と移動先が仕様の中心になる。作者の強みは prompt の技巧より、25年前の記憶から「何が残ったか」を抽出し、それ以外を捨てた編集判断にある。AI はこの核を選んでおらず、核を短時間で操作可能な形へした。

ただし、記事が示す評価証拠は限定的である。確認できる成果は、初日に playable な単一 HTML ができたこと、2週間で公開版へ進み、online multiplayer・co-op・多数 AI faction を実装したこと、初日版と完成版を公開していることだ。一方で、prompt 回数、生成コード量、bug 数、手戻り時間、automated test、外部 playtest、retention、balance 指標は報告されない。作者自身が実装を直接書かなかったことと、コードを理解・監督できなかったことも同義ではない。25年の web generalist 経験とゲームプランナー経験が、architecture や不具合の見立てに暗黙に効いている可能性が高い。

記事には制作中を「hell」「death march」と呼ぶ表現もあり、速度がそのまま持続可能性を意味しない。短い loop は変更コストを下げるが、できる変更が増えるほど、止める基準がなければ試行回数も膨らむ。title を AI が置いた逸話や subagent 投票は面白いが、意思決定の再現可能な方法ではない。この記事は AI-native 制作の品質保証を証明した研究ではなく、強い言語化能力を持つ一人の制作者が、小さな規則の game を公開まで運んだ一事例として読むのが正確である。

■ 自分達の環境への適用
自分達の制作サイクルへ移すなら、「AI に全部作らせる」ではなく、planner loop を一回の playable diff の契約として採用する。各 loop で、観察可能な変更を一つ、期待する player action を一つ、合格条件を一つに絞る。たとえば「敵を追加」ではなく、「画面右端から1体が出現し、player の前方を横切り、接触時に既存の被弾処理だけが起きる」と書く。実装後は screenshot、短い動画、headless trace の少なくとも一つで確認し、違和感を位置・時間・量・反応の語へ変えて次の修正へ渡す。

NEON GALAXY の初日版のように、最小版を museum artifact として固定するのも使える。最初に体験の核が成立した commit、代表 screenshot、操作手順、headless metric を一組で保存し、後の機能追加が核を強めたかを比較する。完成版だけを見ると、multiplayer や faction 数の多さが成功に見えるが、比較軸は「盤面を見て無防備な対象を発見し、送る判断が気持ちよいか」に戻す。機能数ではなく、核を観察しやすくしたか、判断の意味を増やしたかで差分を評価する。

次の小型 prototype では、三段階の probe が現実的である。第一段階は30〜60分で、黒背景、object、移動、勝敗までを単一 scene または単一 HTML にする。第二段階は作者自身の3回の play で、各回に「最初に迷った瞬間」「意図より遅い反応」「説明なしで理解できた規則」を時刻付きで記録する。第三段階は既存 headless harness で、勝率だけでなく decision count、idle time、対象選択の偏り、同じ失敗の反復を取る。画面観察と deterministic な trace が同じ違和感を示したものだけを次の修正単位にする。

さらに、AI に渡す instruction と受け入れ証拠を対にして残す。prompt の巧拙を記憶するのではなく、「どの観察から何を変更し、何の証拠で通したか」を保存する。これなら別モデルや別実装環境へ移っても再利用でき、成功した長文 prompt の模倣に陥らない。仕様化能力を制作速度だけでなく、検証可能な判断履歴へ変換することが、自分達の記憶システムとの接続点になる。

■ メリット・デメリット
メリットは、実装待ちを短縮し、視覚・操作の違和感を記憶が新しいうちに修正できること、規則を削る設計と小さな実装単位が互いを強化すること、初期 artifact を残せば機能追加で核が埋もれたかを比較できることにある。プランナーの技能をコード生成の前段ではなく、各 build の合否判定へ継続投入できる点も大きい。

デメリットは、結果が作者の観察眼と言語化能力に強く依存し、AI が品質責任を引き受けるわけではないことだ。短い見た目の修正は速くても、network 同期、保存、security、性能、長期保守の正しさは screenshot だけでは分からない。単純規則は scope を制御する一方、例外や成長要素を削りすぎれば深さも失う。2週間で release できたという速度は、外部 playtest や保守コストの比較なしには一般化できず、長時間労働を成功条件として再現すべきでもない。

■ 判定
部分採用。playable diff を中心にした短い planner loop、体験の核を先に固定する規則削減、初日 artifact と最終版の比較を採用する。一方、「コードを書かない」を目標にはせず、automated test、headless trace、外部 playtest を別の品質ゲートとして維持する。AI の速度ではなく、観察から修正までの距離を縮め、各変更の根拠を残せたかで評価する。
