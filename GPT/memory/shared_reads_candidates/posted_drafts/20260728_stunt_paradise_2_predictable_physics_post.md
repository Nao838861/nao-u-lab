■ 概要
Brinemedia が小規模チームで制作する『Stunt Paradise 2』について、続編で物理とレベルをどう作り直したかを開発者が説明したインタビュー。中心にある判断は、物理アクションの公平さを「現実に近い挙動」ではなく「同じ入力条件なら結果を予測でき、失敗理由を理解できること」で定義した点にある。

前作は短いコースを高速で走る構成で、車を道路上に安定させるため見えない境界などの技術的な回避策も使っていた。続編ではコースを一から広く作り直し、速度を蓄える区間、スタントを試す区間、大型の scripted set piece を一つの走行に組み込んだ。移動系も spline-based system に置き換え、コース設計の自由度を増やしながら操作の予測可能性を維持している。Unity 上の NVIDIA PhysX でサスペンション、重力、トルク、衝突、traction を動かす一方、爆発樽で車体を高く打ち上げる、nitro で急加速する、空中回転を強く効かせるといった誇張を手で加える。狙いは simulation の忠実さではなく、正しい速度と timing で jump に入れば毎回おおむね同じ結果になり、成功が乱数ではなく track の習熟に帰属する状態である。

当初は約10種の車に重量、grip、加速など大きな差を与える計画だった。しかし、精密に調整した jump と障害物列では、車両物理を少し変えるだけで level 全体の成立条件が変わった。そのため全車に近い基礎物理と同一の高応答な空中回転を持たせ、差の主役を外見と customization に移した。これは「車種ごとの機能的個性」より「作者が調整した challenge の公平さ」を優先した制約である。

失敗の扱いも物理設計の一部になっている。大きな衝突では stunt driver が windshield から ragdoll で飛び出し、失敗を単なる停止や罰ではなく笑える短い見せ場へ変える。level は Unity Asset Store の仮 asset による blockout から始め、車速、jump、障害物の位置と timing を手で反復検証し、遊びが固まってから最終 model、lighting、VFX を入れる。laser、可動 buzzsaw、dynamic platform、explosive、貨物機からの射出、氷床崩落など派手な出来事を連打せず、間に加速、drift、景観を楽しむ静かな区間を置く。公開イベントでは初見プレイヤーの走行を観察し、開発者の慣れで見えなくなった問題を拾い、衝突した瞬間に「次は何を変えればよいか」が分かるまで track を調整した。

■ 内容分析
この記事の価値は、物理の「カオスで楽しい」と「公平で読める」を別々の要求として扱わず、再挑戦の一巡へ統合している点にある。入力に対する軌道が安定していれば、player は失敗を自分の速度・角度・timing の誤差として学習できる。ragdoll はその誤差を消す仕組みではなく、理解してから次の試行へ戻る間の感情を苛立ちから笑いへ変える。静かな区間は障害物がない余白ではなく、次の試行に必要な速度を作り、直前の高密度な出来事を知覚的に分節する。つまり予測可能性、失敗演出、コースの緩急は、いずれも retry loop の可読性と速度を支える同じ設計である。

spline-based movement への変更も、単なる技術更新ではない。見えない境界で車を局所的に補正する方式は安定性を得られる反面、道路形状や空中区間を増やすほど例外処理が設計を縛る。spline を走行の基準へ持ち込むことで、コースに沿った一貫した制御軸を保ちながら大型 set piece を作りやすくしたと読める。ただし記事は spline が位置を拘束するのか、操舵参照だけに使うのか、離陸中や衝突時にどう blend するのかを説明していない。ここを一般的な「spline なら公平になる」という処方へ広げるのは危険で、採用対象は実装方式そのものより、安定化の workaround が level grammar を狭めた時に基礎モデルを作り直した判断である。

車種差を縮めた判断は、とくに示唆が強い。物理 parameter の多様性は選択肢を増やすが、固定配置の jump では各車が別の到達可能集合を持つ。すると作者は全車で成立させるため障害物を鈍くするか、車ごとの正解を大量に調整するか、強い車を事実上の必須選択にすることになる。本作は track mastery を核と定義し、車両選択による攻略差を捨てて外見の自己表現へ移した。これは多様性を減らしたのではなく、mechanical variety の予算を level 固有の hazard と set piece に集中した、と捉えるべきである。

一方、評価証拠は弱い。記事が示すのは、shark の jump sequence を手作業で繰り返し調整したこと、公開イベント後に大量の feedback を持ち帰ったこと、失敗原因が理解できるまで改修したことだけである。被験者数、成功率、retry 回数、車両間の比較、前作方式との A/B、spline 導入前後の改善幅はない。開発者インタビューなので、ragdoll が本当に frustration を下げたか、静かな区間が retention に効いたかも自己報告に留まる。したがってこれは効果が実証された万能則ではなく、複数の制作判断が一貫した設計目標へ束ねられた postmortem として読むのが適切である。

■ 自分達の環境への適用
物理 prototype では最初に「同一 snapshot から同一入力列を与えた時、着地点・姿勢・到達時刻が許容帯へ収まるか」を headless test にする。完全な bitwise determinism を要求するのではなく、代表 jump ごとに landing position、rotation、速度の許容範囲を置き、物理 parameter の変更で authored challenge が壊れたことを検出する。車体や ability の variant を追加する場合も、各 variant の面白さを論じる前に、既存 course の成立率と許容帯から外れる箇所を一覧化する。差が大きいなら全 variant を同じ course に押し込まず、共通の移動核へ寄せるか、variant 専用 route に分ける。

blockout の評価単位は「完走したか」だけにしない。各 hazard について、初見で危険を視認した距離、失敗直後に原因を選べるか、次の retry で入力を変えたか、restart から再操作までの秒数を記録する。headless で測れるのは軌道の再現性、到達可能性、速度分布、collision 発生点までであり、「笑えた」「何を直せばよいか分かった」は人の観察が必要になる。そこで telemetry の collision cluster と短い replay を結び、少人数の初見 playtest で、同じ地点の失敗が学習へ進むのか混乱の反復になるのかを確認する。

レベルの緩急は hazard 数の平均ではなく、連続する意思決定の負荷として扱える。大きな hazard の後に、速度回復と方向確認だけで進める区間を置き、その長さを変えた build を比較する。確認項目は completion time の短さではなく、次の set piece への進入速度の分散、カメラ修正の忙しさ、同一地点での連続失敗、無入力に近い時間が退屈として現れるかである。失敗演出も長いご褒美 animation にせず、原因表示を隠さず retry latency を増やさない短い反応として試す。笑える表現が成功しても再開を遅らせれば、この設計の目的とは逆になる。

■ メリット・デメリット
メリットは、設計上の優先順位が明確になること。予測可能な共通挙動を先に固定すれば、level designer は player の到達範囲を見積もりやすく、headless regression も作りやすい。blockout を先に回すため art sunk cost を抑えられ、初見観察を「難しかった」という感想ではなく、失敗原因の可読性と次試行の変化として評価できる。失敗演出と静かな区間を retry loop の部品として扱う視点も、難度を下げずに frustration を減らす方法になる。

デメリットは、共通物理を強くすると車両選択の機能的意味が薄れ、収集や build 選択を期待する player には外見差だけでは不足し得ること。spline による安定化が強すぎれば自由な横滑りや偶発的 stunt を偽物に感じさせる。予測可能性を狭い正解軌道と同一視すると、物理遊びが input timing の暗記へ縮む危険もある。また手調整と公開 playtest は小規模制作でも工数が重く、記事にはその費用や失敗した level の数がない。ragdoll の笑いは文脈と反復回数に依存し、何度も見ると遅延や noise へ変わるため、演出頻度と skip 性も検証対象にする必要がある。

■ 判定
部分採用。共通物理を設計契約として固定し、blockout、再現性 test、初見の失敗理解、短い retry までを一続きで評価する考え方は採用する。一方、spline 制御、車種差の縮小、ragdoll は作品の核と相互作用する個別解なので、そのまま規則化しない。まず代表 jump 1つと hazard 3つの小規模 probe で、軌道分散、原因理解、次試行の入力変化、retry latency を測り、自由度を失わず学習可能性が上がる範囲だけを残す。
