■ 概要
『Death and the Thief of Stars』は、初めて game developer と manager を務めた作者が、game jam 向けに制作した分岐型 visual novel である。作品は総合8位、Theme Implementation 2位を得たが、作者は受賞を成功談として閉じず、時間と文字数に制約がある場で『Slay the Princess』のような大規模分岐を目指した overscope を最大の失敗とした。小さな kinetic story なら完成度を上げられたのに、script、分岐、asset、演出の全てが薄くなったという評価である。公開によって閲覧、review、新しい team member を得た一方、「公開した以上は完成させる」という期待も発生した。別の小説企画と大学生活を抱える作者は、作品を捨てないが優先度を下げ、長期で進める判断をした。

物語への review には、「Libulan と Liadlao のどちらを選ぶかの stakes が弱い」と「Libulan をもっと好ましい人物にすべき」という逆向きの提案があった。editor と QA は、表面的な修正案をそのまま選ばず、どちらの選択にも十分な土台がないことを共通原因として抽出した。ただし作者は、片方を antagonist にして正解を作ることも、片方の好感度を上げてもう一方を選べなくすることも望んでいない。人物をどう判断するかを player に委ね、その判断自体を物語が尊重する構造を目指している。ところが Dark route の ending は、Liadlao を選んだ読者に、止めようとした相手への同情を強制し、選択理由を後から否定していた。作者は jam 固有の参加条件から解放された Chapter 3 で、この終幕を大きく改稿するとしている。

ほかにも Chapter 2 への遷移が速いこと、反応の種類が少なく agency が限定的であること、Liadlao の sprite、Sidapa の voice volume、background の活用が不足したことを挙げる。presentation の不足は担当者の能力だけでなく、script の確定を待って asset 制作を始めた管理順序にも帰責している。今後は gradual update を重ねず、全体を完成させてから公開し、約一年後以降に demo を出す案を選んだ。ただし Chapter 2 に3変種、Chapter 3 に8変種を計画しており、無償の学生中心 team、資金不足、離脱可能性を考えると、記事の結論は「改善策が確立した」ではなく、「問題を具体化したが、改善案もなお scope risk を抱える」である。

■ 内容分析
この記事で最も価値があるのは、相反する feedback を多数決で処理せず、両方が観測した欠損へ戻した点である。「stakes を強くする」と「人物を好ましくする」は解決策としては逆だが、選択前に player が人物、危険、欲望を比較できる材料が不足しているという診断なら両立する。ここで注意すべきなのは、作者が「土台不足を良いこととして lean into する」と述べた部分である。価値判断を押し付けないことと、判断材料を与えないことは別物だ。曖昧さを守るなら、両者の利害、証言の偏り、約束の代償を増やし、どちらにも合理性と疑念を成立させる必要がある。情報を減らして中立にするのではなく、競合する根拠を増やして正解だけを消すべきである。

また、選択肢の品質は選択前だけでは決まらない。player が自分の判断で route を選べても、ending がその判断を愚かさや誤解として回収すれば、agency は遡及的に失われる。Dark route の問題は悲しい結末ではなく、選んだ側が重視した stakes を扱わず、別人物への同情を正しい感情として強制したことにある。破滅や後悔を描いても、選択時の論理に世界が応答し、player が「自分の判断の結果だ」と理解できればよい。

production 面では、script 完成待ちで asset が直列化し、締切側で sprite、voice、background の品質不足として表面化した。visual novel は文章が source of truth になりやすいが、立ち絵の感情差分、背景数、音声量は scene list と仮台詞から先に予算化できる。必要なのは一回の handoff ではなく、変更しにくい asset contract を早く固定し、細部だけを後で更新する流れである。無償 team では稼働を強制できないため、欠員時に削れる優先度と代替表現も要る。

全体完成後に公開する方針にも二面性がある。途中版で limited agency を体験させない利点はあるが、feedback が長期間止まり、3変種と8変種が異なる判断を生むかを完成近くまで検証できない。記事には再結合点、固有 scene 数、総 word count、team の月間稼働、変更前後の playtest がない。順位も個別判断との因果を示さないため、これは完成手法の証明ではなく設計仮説である。

■ 自分達の環境への適用
分岐 narrative の prototype では、各 choice を「選択前の根拠」と「選択後の尊重」に分けてレビューする。選択前には、各 option について player が観測できる利益、危険、人物の信用根拠、未確定情報を表にする。一方だけが情報量や魅力で勝っている場合は、劣る側を悪役化して差を広げず、その側を合理的に選ぶ一つの価値軸を追加する。反対に両方が薄い場合は「正解がない設計」と呼ばず、競合する証拠を playable scene に置く。選択直前に player が各人物をどう理解し、なぜ選んだかを短く記録しておけば、作者の意図した曖昧さと単なる説明不足を区別できる。

ending review では、route ごとに「選択時に守ろうとしたもの」「world が返す直接結果」「失ったもの」「最終場面が要求する感情」を並べる。最後の感情だけが別 route の価値観に寄っている場合、選択を遡及的に無効化している疑いがある。小さな probe として、同じ choice に二つの短い ending を作る。一つは作者が伝えたい moral を前面に出す版、もう一つは player の選択理由から結果を返す版にし、初見者へ「結末に納得したか」ではなく「自分の選択理由が物語に認識されたか」を聞く。悲しさや好感度と、判断尊重を別指標にする。

headless 評価は物語の意味を採点せず、分岐規模と実装整合性を監視する。route graph から到達不能 node、choice 後に同じ内容へ即時合流する偽分岐、flag の未回収、ending ごとの固有 scene 数を抽出する。Chapter 2 の3変種と Chapter 3 の8変種が直積なら最大24経路になるため、実際に必要な固有 state と再結合可能な表現差を分け、word count と asset count の上限を先に出す。各 route の選択理由タグが ending の台詞や state で一度も参照されない場合は警告する。ただしタグ参照数を agency の点数にせず、人間が ending を読む対象を絞る検査として使う。

制作順は full script 待ちをやめ、第一 playable slice の scene contract を早期に固定する。必要 character、emotion set、background、voice の有無、分岐後も再利用できる asset を一覧化し、仮素材で一 route を最初から ending まで通す。その後に script と asset を並行化するが、free team の不確実性を前提に must / should / cut の三段階を置く。公開戦略は「小刻みな本編更新」対「完成まで非公開」の二択にせず、短い検証 build は限定 playtest、外向けには縦切り demo、物語本編は完成単位で出す。これなら未完成 route を約束として背負わず、選択根拠と ending 尊重の失敗を早く発見できる。

■ メリット・デメリット
メリットは、scope、物語 feedback、ending、asset pipeline、公開後の負債が一つの事例で因果的につながっていることだ。特に、逆方向の review から共通原因を探すこと、選択可能性と選択結果の尊重を別々に検査すること、script と asset の直列待ちを contract 化で崩すことは、短期制作へ移植しやすい。jam が露出と仲間を得る場である一方、完成期待を生むという観察も、公開判断を単なる marketing benefit で見ない材料になる。

デメリットは、単一作者による初回制作後の自己報告で、tester 数、変更前後の測定、route graph、工数がないことだ。jam の順位は外部成果だが、どの設計判断が順位へ寄与したかは分離できない。作者の改善計画には、元の overscope を認めながら3変種・8変種へ広げる矛盾が残る。全体完成後の公開も、品質を守る可能性と feedback を遅らせる危険の両方がある。無償 team の並行作業を一般的な高速化策として扱うと、調整負荷や burnout を増やし得る。

■ 判定
部分採用。相反する feedback を共通の設計欠損へ戻す診断、choice の根拠と ending の判断尊重を分離する評価、route graph による scope 見積り、scene contract を使った script・asset の並行化を採る。一方、分岐数の拡大と完成まで非公開という計画はそのまま採らない。まず一つの choice と二つの ending で判断尊重を比較し、固有 state・word・asset の実測から拡張上限を決める。
