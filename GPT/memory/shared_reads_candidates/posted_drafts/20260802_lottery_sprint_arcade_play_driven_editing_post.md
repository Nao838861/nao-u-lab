■ 概要
完成したゲームを LLM に一括生成させるのではなく、プレイ中に「速くして」「弾の色を変えて」と声で指示し、変化を次のプレイで即座に確かめる play–edit–feedback cycle を検証した研究。対象は Raspberry Pi 5 を組み込んだ Space Invaders 型の筐体で、プレイヤーは専用ボタンで音声入力し、Whisper が文字化、GPT-4o が現在のゲーム設定と JSON schema を参照して変更案を作る。編集可能な領域は、プレイヤー速度・連射・残機、敵の行列・速度・弾発射確率・耐久力、UFO、バリア、難度上昇、power-up、色・ pixel pattern、音量など約100 field に限定される。

変更は plan と action の二段階である。plan は対象 field、現在値、新値、理由、予想されるゲーム上の効果を固定形式で列挙し、action がそれを atomic JSON patch へ変換する。validation を通った時だけ設定を書き換え、ゲームを reset して新状態を遊び直す。プレイ中に連続的に変えないのは、特に非専門家が「どの指示が何を変えたか」を前後の二状態から帰属しやすくするためだ。設定 field や適用値は画面に出さず、音声認識文だけを表示し、効果は振る舞い・見た目・音から読ませる。

評価は21人が5 trial ずつ、合計105 trial を行い、各 trial で最低2回の成功編集を求めた。715件の音声 command 中694件、97.1% が validation を通り、21件は状態を変えず拒否された。NASA-TLX は概ね中程度、post survey と UEQ は概ね肯定的で、programming 経験3群間に統計的に信頼できる差は出なかった。ログの設定 path を TF-IDF 化し PCA、mixed-effects model で分析すると、外観・弾・UFO など即座に知覚しやすい変更は usability、敵・音・進行など深い gameplay 変更は enjoyment と結び付く傾向があった。ただし両方の95% 信頼区間はゼロをまたぐ。自由記述では、予期せぬ変化を探る exploratory editing、弾幕風など目標を持つ structural editing、極端値や小さな差を試す iterative tuning の3戦略が得られた。結論は、構造化設定に限定した単純な arcade game なら、音声による in-play 共創は成立し得る、という範囲である。

■ 内容分析
この仕組みの価値は、自然言語がそのままゲームコードになることではない。プレイヤーの「もっと刺激的に」という高水準の意図と、実行可能な限定スキーマの間に、説明付き plan と検証可能な atomic patch を置いた点にある。新規 mechanic や任意コード生成を許さず、変更可能な空間を先に人間が設計したから、不正な出力を状態非変更で落とせた。これは「LLM が安全にゲームを書き換えた」より、「人間が作った安全な制御面の意図解釈を LLM に担わせた」と読むべきだ。

97.1% も注意が必要である。これはプレイヤーの意図どおりの効果が得られた率ではなく、構文・schema 上の validation を通った command 率である。論文は intention–behavior alignment を主観評価に含むが、command 単位の semantic correctness、前後差が予測と合った率、予期外の副作用は独立に報告していない。plan に理由と予想効果があっても、実現したかを機械的に閉じる feedback oracle はない。reset は一度の変更前後を読みやすくする反面、プレイの流れを切り、複数の patch が一度に入れば個々の因果は依然分離できない。

評価設計は「編集量」と「編集の焦点」を分けた点がよい。各 trial の操作数が増えるほどログ語の生頻度も増えるため、second-level path の生 count ではなく TF-IDF を使い、参加者 random intercept を持つ mixed-effects model で反復試行を扱っている。一方、PCA の第1・第2成分の累積説明率は47.86%、「即時知覚対 core gameplay」という名前は高負荷語の目視解釈で、確立したカテゴリではない。usability は beta=0.442、p=0.095、enjoyment は beta=-0.475、p=0.053 でいずれも95% 信頼区間がゼロをまたぐ。「見た目は使いやすさ、コアは楽しさ」は有用な次の仮説だが、成果として固定してはいけない。

また、経験差がないとの結果も同等性の証明ではない。21人を6・8・7人に分けた探索的比較で、小さな差を検出する power が低い。比較条件もなく、voice と text、プレイ中編集と通常の inspector、plan/action 分離と直接 patch のどれが負荷や楽しさに寄与したかは分からない。レトロ筐体の物理的新鮮さ、熟知された単純なルール、各 trial の最低成功回数という実験文脈も評価に混ざる。複雑な状態機械、narrative dependency、新規 mechanic 生成への一般化はできない。

■ 自分達の環境への適用
自分達には、プレイヤー向けの音声編集機能そのものより、「遊んだ直後の感覚的指示を、追跡可能な安全な差分に落とす」調整系として移植する。prototype ごとに tuning schema を用意し、変更可能 path、type、上下限、相互制約、reset 可否、観測可能な効果を持たせる。入力は「敵弾が理不尽」のようなプレイ直後の言葉でよいが、適用前に、対象 path、before/after、意図解釈、予想効果、壊れるかもしれない条件、atomic patch を出す。未知 path、型不一致、範囲外、制約違反は state を変えず落とす。

その上で validation を三層に分ける。第一層は schema validity、第二層は headless 実行で、起動、例外、到達不能状態、難度急変、フレーム時間を固定 seed で前後比較する。第三層は人間の semantic check で、「意図どおりか」「楽しくなったか」「別の良さを壊したか」を短く遊んで判定する。論文の97.1% に相当するのは第一層だけで、三層を混ぜず、それぞれの success rate を残す。

一回の調整は原則一意図・少数 patch にし、baseline state、指示原文、plan、patch、validator 結果、before/after の metrics、replay、人間の判定、rollback 先を同じ edit record に保存する。変更後はただ reset するのではなく、同一 seed の A/B と複数 seed の分布を両方取る。予測が「待ち時間を減らす」なら実測値へ、「緊張感を上げる」なら敵接近時間・回避頻度・被弾分布など代理指標とプレイ感覚の両方へ落とす。予測と実測の不一致を残すことで、次回の意図解釈と schema 設計の教師データにできる。

編集の順序は、まず即時知覚できる小さな変更で loop の信頼性を確かめ、次に core mechanic の変更へ進む。ただし「即時知覚は usability、core は enjoyment」を rule にせず、自分達の build でタグ付き edit log とプレイ後の二問「差が読めたか」「もう一度遊びたいか」を取る。最初の小さな検証は、一つの既存 prototype、10個以下の tuning field、同一 seed 5本と複数 seed 10本、人間の前後プレイ2回程度で足りる。目的は大規模な自然言語 editor ではなく、「感覚的指示→安全な差分→機械検証→人間の面白さ判定→戻す/残す」が一本の追跡可能なループになるかの確認である。

記憶システムには、成功 patch だけでなく、拒否した指示、schema では表せなかった意図、予測外の効果、rollback 理由を残す。失敗は LLM の失敗だけでなく、制御面の表現力不足も示すからだ。個々の表現をそのまま恒久 rule にせず、同型の不一致が繰り返した時にだけ schema、validator、評価軸を更新する。

■ メリット・デメリット
メリットは、自然言語の低い入力障壁と、構造化 patch の検査可能性を両立したことだ。plan/action 分離は、意図解釈を適用前に読める。atomic patch、state 非変更の拒否、reset、構造化 log は、差分の再現、rollback、A/B、失敗の切り分けにそのまま使える。構文成功率とプレイ体験を分けて測れば、LLM 出力の見かけの安定性に止まらない。

デメリットは、安全性が事前定義した編集空間の狭さと引き換えなことだ。約100 field あっても、存在しない mechanic やルール間の新しい関係は作れない。validation 通過は意味的成功や面白さを保証せず、音声認識・LLM 呼び出しの latency、コスト、外部 API 依存も残る。reset は因果を読みやすくするが、flow を切断する。小標本・単一 game・比較条件なしの結果から、初心者一般への優位性や編集種類と体験の因果関係を採用するのは危険である。

■ 判定
部分採用。自然言語を構造化 plan と atomic patch へ落とし、schema、headless、人間の面白さ判定を分離した調整ループは採る。音声 UI や約100 field の大きさは移植せず、体験傾向は仮説として小さな prototype で再検証する。
