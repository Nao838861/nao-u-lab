■ 概要
『Burnout Crusaders』の作者が、学校イベント向けに完成させた GameMaker 製アクション prototype を振り返った postmortem。企画は当初、2人が短い minigame を連戦して先に規定点へ到達する party game だった。その後、敵 wave の合間に shop が出る roguelike 案へ移ったが、締切が迫るにつれて作者自身が「原形が分からないほど単純化した」と述べる範囲まで縮小された。ただし、これは単なる機能削除ではない。ゲーマーとゲーム未経験者の両方へ届く単純さを目標に、移動の気持ちよさを中心へ置き、roll に「素早い移動」「攻撃の cancel」「combo の延長」を集約した。roll 後の攻撃が十分に楽しかったため、control stick を回す spin と、大型敵を即座に倒す固有 spin attack は、重複し複雑さを増やす能力として削除している。

実装面では、attack frame と hitbox を一般化して結び付けられず、player と enemy ごとに hard-code した。敵が互いをすり抜けると balance 上問題になるため collision も終盤に追加したが、適切な pathfinding がなく、さらに唯一の level は四隅へ逃げて状況を整理できるため、作者は全体が簡単すぎると評価している。一方で現行 build は title、multiplayer、keyboard/controller 対応、敵2種、power-up 2種、match 統計、固有効果音を備え、accessibility option を除けば prototype として一通り動く。学校イベントでは参加者数こそ少なかったが、joystick を握った経験がない教員がすぐ操作できた事例を、単純化が初心者に届いた手応えとして挙げる。作者の結論は、作品は想定以上に成立した一方、今後は hitbox や enemy AI の複雑な system の管理と、実現可能な scope の見積もりを改善する必要がある、というものだ。

■ 内容分析
この記事で最も再利用しやすい判断は、「締切なので要素を減らす」ではなく、「残す中心動詞へ複数の役割を圧縮する」という縮小の仕方である。roll は移動だけなら回避手段、cancel だけなら上級者向け technique、combo 延長だけなら攻撃 system の一部に留まる。三つを同じ入力へ重ねることで、追加 sprite や別 ability を増やさず、位置取りと攻撃継続の選択を一つの操作から生んだ。spin の削除も予定表だけを理由にせず、roll から攻撃する方が楽しく、結果が重複するという play feel を根拠にしている。scope cut が体験の密度を落とす削除ではなく、操作語彙の集中になっている点が重要だ。

ただし、多機能化は常に単純化になるわけではない。記事には roll の無敵時間、cancel 可能 frame、combo が延びる条件、失敗時の挙動、初心者が三機能を意識して使い分けたかが書かれていない。同じ入力が状況で別の結果を返すなら、animation、敵の予告、入力猶予が弱いと「覚える button は少ないが挙動は読めない」設計にもなる。教員が問題なく動かせた観察は、基本移動の導入障壁が低い証拠にはなるが、cancel や combo extension まで理解した証拠ではない。作者の “flawlessly” も、何を成功と数えたかが定義されていない。

難度の記述も有用である。敵同士の collision、pathfinding 不足、四隅へ退避できる layout は個別には小さな実装・level 判断だが、組み合わさると敵集団が詰まり、player が安全地帯から一体ずつ処理できる可能性を作る。つまり難度は enemy の体力や速度だけではなく、「集団の空間利用 × 追跡能力 × arena の逃げ道」で決まる。唯一の room が tutorial としては適切でも、後続 level がない現状では、学習用の余白と作品全体の低難度を切り分けて評価できない。

実装負債についても、hard-code 自体を即座に失敗とは読まない方がよい。短期 prototype を完成させる局面では、汎用 hitbox system の設計に時間を使うより、player と敵2種を個別実装する方が合理的になり得る。問題は、作者が次の敵や attack を追加する時に修正箇所が増える構造であり、記事にも再利用性、test、追加コストの測定はない。一方、num 0 で全 hitbox/hurtbox を表示できる debug 機能は、内部表現が粗くても判定を可視化して調整可能にする、小さいが価値の高い投資である。

評価の限界は明確だ。playtest 人数、session 時間、失敗回数、使用 character、熟練者との比較、離脱、再挑戦、match 統計の中身が示されていない。企画変更前後や spin 有無の比較もないため、roll 集約が retention や勝敗の公平性を改善したとは結論できない。この記事は成功効果を測った研究ではなく、設計判断・実装負債・観察された失敗条件が同じ作者の言葉で残る一次 postmortem として強い。

■ 自分達の環境への適用
小規模 action prototype では、最初に中心操作の「役割契約」を一枚で固定する。たとえば roll なら、移動距離、攻撃から cancel できる区間、roll 後に接続できる攻撃、連打時の回復時間、被弾時の優先順位を列にし、「この操作を消すと何が失われるか」まで記録する。追加 ability は新しい animation や名前があるかではなく、中心操作では作れない判断を増やすかで採否を決める。spin のように結果が重なる案は、一度小さく実装しても、固有の敵対処・risk・位置変化を生まなければ削除候補へ戻す。

headless 評価では手触りそのものを採点せず、roll 集約が作る構造を測る。固定入力 trace で、攻撃から roll が受理される frame、roll 後の attack 接続率、入力から状態遷移までの遅延、同一敵配置での移動距離、行動不能時間を記録する。難度は collision 有無、簡易追跡有無、corner の遮蔽有無を小さな組合せで回し、敵の滞留密度、player 接近までの時間、corner 滞在率、撃破時間、被弾数を見る。これなら「敵 collision を入れたら見た目は自然になったが、通路が詰まって安全になった」といった相互作用を再現可能な差分として残せる。

人間 playtest は別枠にし、初心者では最初の移動までの秒数、説明なしで出せた行動、最初に詰まった入力、初回 room の完了可否、必要だった声掛けを観察する。経験者には cancel と combo を発見した時点、roll を常用する理由、spin 相当の別能力が本当に重複するかを確認する。初心者が移動できたことと、system の深さを使えたことを同じ「操作できた」で畳まない。記事の教員一名の逸話を仮説生成に使い、複数 session の観察項目へ変換する。

実装面では hard-code を禁止せず、増殖条件を exit criteria にする。敵2種までは個別 attack-frame 判定を許容し、3種目の追加で同じ修正が複数箇所に発生したら data-driven な frame event へ移す。hitbox overlay は早期から screenshot や replay と共に保存する。制作記憶には「採用した機能」だけでなく、削除した spin、その理由、比較した build、難度を崩した collision/pathfinding/layout の組合せを一つの decision record として残す。そうすれば次の prototype で、機能数ではなく中心操作の役割密度と検証可能性から scope を決められる。

■ メリット・デメリット
メリットは、少数の操作で移動と combat の選択を増やし、animation・実装・tutorial の範囲を同時に抑えられること、冗長能力の削除理由が play feel と役割重複に結び付いていること、敵 AI と arena layout を別々に調整する危険が具体例で分かること、完成優先の hard-code と判定可視化を両立させていることにある。

デメリットは、roll の多機能化が一強化すると他 ability と敵設計を空洞化しやすく、状況依存の挙動が feedback 不足で不透明になり得ること、初心者事例が一名の逸話で上級機能の理解を示さないこと、比較 build と定量値がなく単純化の因果効果を判断できないこと、prototype の hard-code を規模拡大後まで持ち越すと追加速度と regression の両方を悪化させることである。

■ 判定
部分採用。中心動詞へ役割を集約し、重複能力を削る scope 縮小法と、collision・追跡・layout を組合せで検証する視点は採用する。一方、「初心者がすぐ動かせた」ことを accessibility や combat 理解の達成とは扱わず、headless の状態遷移計測と、初心者・経験者を分けた観察で補強する。hard-code は短期完成の手段として期限付きで許容し、増殖条件を満たした時点で一般化する。
