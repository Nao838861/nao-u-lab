■ 概要
テキスト主体のゲーム『Pyrates』は、端末操作に慣れた人にとってさえ、コマンドを綴って Enter を押す反復が現代的な GUI より重く感じられる。著者には、追加ライブラリを要求せず、複数 OS で見た目と挙動を揃えるという制約がある。そこで豪華な UI へ置き換えるのではなく、既存の TUI のまま「目標達成に差を生まない操作」を減らす実践を、Shorten commands、Limit choices、Automate actions、Recall input、Predict intent の頭文字から SLARP と整理した。

Shorten は全コマンドに一文字 alias を与え、`enter cave` のような長い構文を一文字＋Enter に縮める。Limit は現在の状況で有効なキーだけを提示し、宝島パズルで対角移動を入力検証段階から除外する。Automate は、攻撃も反撃も効かず判断が変わらない戦闘を、どちらかの stamina が減るまで自動進行する。Recall は蒸留所の同じ tile を繰り返し選ぶ時に直前入力を保持し、空 Enter で再実行するほか、座標の文字か数字だけが入力された場合に前回値で欠けた側を補う。Predict は迷路の直進中なら空 Enter で同方向へ進み、曲がり角や行き止まりでは進行方向を切り替え、実際の分岐まで単純移動を畳み込む。

五つを束ねる判断基準は、行為が tactical に意味を持つかである。目標へ近づく選択肢に実質的な差があるなら自由を残し、明白、無意味、あるいはルール上強制される行為なら入力負荷を減らす。記事の根拠は『Pyrates』内の複数ゲームと迷路機能の version 0.7.0／0.9.0 にまたがる実装経験であり、ユーザー数、完了時間、誤入力率などの定量比較はない。結論は、操作を一律に短くするのではなく、意味のある判断へ到達するまでの摩擦だけを選択的に圧縮する、という設計原則である。

■ 内容分析
SLARP の五項目は同じ種類の最適化ではない。Shorten は表記の圧縮、Limit は行為空間の剪定、Automate は状態遷移の省略、Recall は履歴を使う default、Predict は状況から意図を推定する先回りである。後ろへ進むほどキー数は減るが、UI がゲームの意味へ介入する度合いと、誤った時の損失が増える。この勾配を区別せず「便利機能」とまとめると、入力負荷を下げながら agency まで奪いかねない。

Shorten は最も安全だが、一文字 alias の記憶と discoverability が問題になる。記事では利用可能キーを表示する Limit と組み合わせるため、短縮名を暗記させずに済む。Limit の宝島例も、任意の移動を禁じているのではなく、パズルの論理上意味を持たない対角移動だけを validation で止める。ここでは認知負荷と typo を同時に減らせる一方、作者が「無意味」と分類した行為に、探索、ロールプレイ、speedrun 上の価値がないことが前提になる。

Automate の戦闘例は境界が明快である。自動化区間では双方の攻撃が無効で、stamina 変化が起きた時だけ逃走などの戦術判断が再び発生する。つまり時間を飛ばす条件と停止条件が game state で定義されている。これは単なる早送りより堅い。ただし途中で item 使用や animation timing に意味を持たせる設計へ変われば、以前は安全だった自動化が判断を消す。自動化の正しさは操作単体ではなく、ルール変更と一緒に再検証する必要がある。

Recall と Predict は stateful input parser を作る。座標片の補完は、同じ行や列を続けて使う時には強力だが、前回値が画面上で見えなければ、同じ一文字が履歴により別の命令になる。Predict の迷路移動はさらに踏み込み、直線、角、行き止まりという局所 geometry から「分岐まで進みたい」と仮定する。これは経路選択のない区間をうまく圧縮する一方、壁調査、歩数管理、罠の警戒、引き返さず停止したい意図が入ると仮定が崩れる。予測精度だけでなく、予測結果の可視性、取り消しやすさ、誤入力時の損失が品質を決める。

記事の弱点は、この境界を著者の合理性判断だけで置いていることだ。SLARP 導入前後の操作数、初見者の成功率、誤補完率、主観負荷を測っておらず、五項目それぞれの寄与も分離されていない。迷路の Predict が矢印キーより直感的でないことは著者自身も認めている。したがって SLARP は検証済みの普遍則ではなく、制約の強い TUI で操作摩擦を監査するための、具体例を伴う設計語彙として読むのが妥当である。

■ 自分達の環境への適用
まず TUI、メニュー中心、反復操作の多い小型試作で、入力を「意味のある判断」「結果が明白な確認」「強制された遷移」「直前行為の反復」「推定可能な移動」に分類する。削減対象は後ろ四つで、意味のある判断は残す。例えば crafting なら同じ素材の連続投入を Recall、敵味方とも damage 0 の区間を Automate、現在装備では実行不能な command を Limit とする。Predict は最後に回し、誤推定しても即座に停止・取消できる操作だけへ限定する。

headless 評価では「入力回数が少ないほど良い」を目的関数にしない。固定 seed の同一シナリオに、基準版、Shorten＋Limit 版、Automate＋Recall 追加版、Predict 追加版を用意し、分岐到達までの入力数、意味のある判断一回当たりの入力数、無効入力数、default の取消回数、意図しない state 遷移、判断可能になってから自動化が停止するまでの遅延を event log から測る。入力数が減っても取消や誤遷移が増えるなら不採用とする。headless で測れない分かりやすさは、少人数 playtest で「次に Enter が何をすると思うか」を操作前に答えてもらい、予測と実挙動の一致を見る。

実装上は各省略に guard と provenance を持たせる。自動戦闘なら `auto_reason=no_tactical_change` と停止条件、座標補完なら参照した前回値、迷路予測なら選んだ方向を log に残す。これにより事故を「便利機能が変だった」で終わらせず、Limit の候補生成、Recall の履歴、Predict の規則のどこが誤ったか分解できる。ルール変更時には、過去に自動化した区間へ新しい選択肢が生じていないかを regression test する。

制作サイクルや記憶 UI に応用する場合も、同じ境界を守る。前回値の再利用や明白な metadata 補完は Recall として有効だが、投稿可否、削除、外部送信のような不可逆判断は Predict で代行しない。SLARP は「自動化を増やす原則」ではなく、「判断価値がないと検証できた部分だけを畳む原則」として運用する。

■ メリット・デメリット
メリットは、技術制約の強い TUI でも追加ライブラリなしに段階導入できること、運動的な入力負荷と選択肢探索の認知負荷を同じ枠で監査できること、各機能を実際の game state と停止条件へ結び付けられることにある。特に Automate の「戦術判断が復活した時に止める」という発想は、早送り、連戦、演出 skip、メニュー反復にも移植しやすい。五項目の語彙があることで、単なるキー数削減と意図予測を混同せず議論できる。

デメリットは、tactical に無意味かどうかがゲームの目的とプレイヤー層で変わること、Limit が意外な遊び方を閉じ、Recall が mode error を生み、Predict が agency と空間理解を損なう可能性があることだ。記事には比較実験がなく、Pyrates 固有の成功例が初見者や別 genre へ一般化する証拠もない。省略機能はルール変更に弱く、かつて意味のなかった一手へ新しい価値が生じると、自動化が古い前提のまま判断を飲み込む。

■ 判定
部分採用。Shorten、文脈表示付き Limit、停止条件を明示した Automate、補完元を可視化できる Recall は、小型試作の入力監査へ採用する。Predict は、分岐のない可逆操作に限定し、基準版との event-log 比較と少人数の予測一致テストを通った場合だけ使う。判断価値の分類、取消可能性、rule change 後の再検証を伴わない一括自動化は採用しない。
