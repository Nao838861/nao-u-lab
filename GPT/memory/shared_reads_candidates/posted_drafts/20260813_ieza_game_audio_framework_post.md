■ 概要
「IEZA: A Framework For Game Audio」は、ゲーム音響を speech / sound effect / music という素材種別や制作担当で分けるだけでは、音がプレイ中に何をしているかを説明できない、という問題から出発する。著者 Sander Huiberts と Richard van Tol は既存の映画音響論、ゲームコード上の資産分類、音源の位置に基づく分類を比較し、ゲームプレイ中の音を二つの直交軸で整理する IEZA framework を提案した。

第一軸は音の存在する層である。足音、銃声、雨、群衆のざわめきのように架空世界内の音源へ帰属する diegetic と、HUD 通知やスコア更新音、背景音楽のように世界外の層から与えられる non-diegetic を分ける。第二軸は音が表す内容である。操作やゲームイベントなど「何が起きたか」を伝える activity と、場所、感情、社会・文化など「どんな状況か」を伝える setting を分ける。この二軸の組合せから Interface、Effect、Zone、Affect の四領域が生まれる。

Interface は世界外×activity で、メニュー操作、体力変化、得点更新など、HUD とシステム状態への反応を伝える。Effect は世界内×activity で、足音、武器、衝突、台詞など、プレイヤー操作やゲーム内イベントへ即時に反応する。写実的な音でなくても、マリオのジャンプに同期する電子音のように世界内活動へ認知的に結び付けば Effect である。Zone は世界内×setting で、風雨、都市、工場、ジャングルなど、個別音源の列というより環境を一つの聴覚的な層として成立させる。Affect は世界外×setting で、音楽や非現実的な恐怖音によって感情、文化、サブカルチャー、来る出来事の予感を与える。

著者らの重要な結論は、Interface / Effect 側は具体的なデータや統計の伝達に向き、Zone / Affect 側はゲームの feel の伝達に向く、という非対称性である。また activity に応じて Zone や Affect を変化させれば、四領域は固定棚ではなく相互作用する。枠組みは Utrecht School of the Arts で三年間教えられ、二年分の audio game 課題のうち、設計法として IEZA を教えた年度では、音世界の多様性、Interface と Effect の分離、音を起点にした発想が改善したと報告される。論文級の統制評価ではないが、音響を素材一覧から機能設計へ移す語彙としての有効性を示した記事である。

■ 内容分析
IEZA の価値は「四分類を埋めれば良い音になる」ことではなく、音の不足を機能の不足として発見できることにある。例えば攻撃音が鳴っていても、入力受付、発生、命中、無効化が同じ一音なら Effect は存在していても因果が読めない。環境音が豊かでも危険度や場所の違いが伝わらなければ Zone は装飾に留まる。壮大な曲があっても実際の脅威状態と無関係なら Affect がゲーム状態を誤って予告する。素材名では見えない欠陥を、「どの層から、活動と設定のどちらを、何の判断のために伝えるか」へ分解できる。

もう一つの強みは、同じ意味を複数領域へ冗長化できる点である。瀕死状態を Interface の警告音だけで示す代わりに、Effect の荒い呼吸、Zone の帯域変化、Affect の緊張音楽を組み合わせられる。これは単なる豪華化ではない。視覚 HUD を見ていない瞬間にも状態が届き、色覚・視野・注意配分の差に対する補助経路になる。ただし記事そのものはアクセシビリティ効果を参加者実験で測っておらず、著者の研究背景と枠組みの応用可能性を、実証済みの成果と混同してはいけない。

限界も明確である。第一に、一つの音が複数機能を持つ。危険接近で音楽が変われば Affect でありながら activity の情報も運ぶし、世界内ラジオは diegetic な音源で文化的 setting を示す。境界を厳密な資産所属にすると分類争いになる。第二に、IEZA はミックス、音量、周波数マスキング、遅延、反復疲労、空間定位、再生機器差を評価しない。四象限が埋まっていても重要音が聞こえないことはある。第三に、教育事例は人数、採点基準、統計、有意差が示されず、年度差や学生差を除けない。したがって IEZA は品質スコアではなく、設計仮説と監査の座標として使うべきである。

■ 自分達の環境への適用
ゲーム prototype ごとに audio event ledger を作り、各音を asset 名ではなく `trigger / intended_information / IEZA quadrant / urgency / competing_sounds / fallback cue` で記録する。最初の監査対象は四象限の数ではなく、重要なプレイ判断である。入力が受理されたか、攻撃が当たったか、被弾したか、回避可能時間が迫ったか、報酬を得たか、区域と危険度が変わったかを列にし、それぞれがどの領域から何ミリ秒以内に伝わる設計かを確認する。

小さな検証では同一戦闘を三条件で比較する。A は現行音、B は Effect / Interface の情報音を切った版、C は Zone / Affect を切った版とする。headless 側では入力から音イベント発火までの遅延、重要状態に対応する event coverage、同時発火数、同一 cue の過密、状態遷移と adaptive layer の一致をログ化できる。人間側では「何が起きたか」「次に何をすべきか」「場所や危険度がどう変わったか」を、画面あり・低視認性・音なし条件で短く答えてもらう。B で操作理解が落ち、C で空間や緊張の認識が落ちるなら、四領域の役割分担が実作で機能している。逆に差が出なければ、音が情報経路として働いていないか、切り分け条件が粗すぎると判断し、資産追加より先に cue の役割を再設計する。

headless 評価だけで完了させないことが重要である。event が正しく発火しても、実際の音が埋もれる、耳障り、意味を誤認する問題はログから分からない。deterministic test は「鳴るべき時に鳴る」を保証し、録画・試聴 review は「聞こえ、区別でき、意図した判断につながる」を保証する二段構えにする。記憶には「四象限を埋める」という一般則ではなく、各 prototype で欠けていた判断、追加した cue、無音条件との差、失敗した重複表現を evidence とともに残す。

■ メリット・デメリット
メリットは、音響担当以外も使える少数の語彙で、操作フィードバック、世界内因果、環境の気配、感情文脈を同じ表に載せられること。音を実装末期の装飾ではなく、プレイヤーへ情報を渡すインターフェースとして早期に設計できる。二軸なので「世界内に馴染ませたいが明瞭な通知も必要」といった設計上の緊張も可視化できる。状態を複数領域へ冗長化する検討は、視覚負荷の軽減や音中心の遊びにもつながる。

デメリットは、分類が品質を保証しないこと。境界例を一つの箱へ押し込むと、本来の複合機能を失う。象限ごとの音数を KPI にすると不要音が増え、マスキングと疲労を悪化させる。記事の教育成果は定性的で、現代の live mix、3D audio、haptics、字幕・visual cue との連携まで直接扱わない。導入時は「所属を決める表」ではなく「意図と欠落を説明する表」に限定し、最終判定は実音の試聴とプレイ結果で行う必要がある。

■ 判定
部分採用。IEZA を音響資産の固定分類や完成度スコアにはせず、重要なプレイ判断に対する情報経路と feel の欠落を発見する設計座標として採用する。まず一つの action prototype で audio event ledger と三条件比較を行い、deterministic な発火検証と人間の聴取検証を分離して運用する。
