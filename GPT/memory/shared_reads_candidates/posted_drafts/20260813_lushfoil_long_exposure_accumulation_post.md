■ 概要
『Lushfoil Photography Sim』の開発者 Matt Newell が、Unreal Engine 上で長時間露光をどう擬似したかを、3 つの合成法の比較として解説した記事。目標は、写真経験者が納得でき、初心者がカメラ設定を学べる DSLR simulation である。被写界深度、焦点距離、露出、noise は Unreal Engine の既存機能で表現できたが、shutter を開けている間の動き全体を一枚に蓄積する長時間露光は欠けていた。そこで、実カメラの連続的な受光を、時間の異なる複数 frame を順に capture して合成する問題へ置き換えた。

第 1 案は、1 秒間に得た 30 枚をすべて加算し、最後に 30 で割る単純平均だった。blur は出たが、除算より前の大きな輝度値が clamp されたと開発者は推測しており、白と黒の関係が崩れた。第 2 案は、新しい frame を足すたびに結果を 2 で割った。露出の発散は抑えたが、新しい frame ほど重みが大きくなり、最後の像が強く浮き出た。第 3 案では、n 枚目の取り込みに応じて n を使う逐次的な正規化に変え、各 frame の寄与を均等にした。記事は「2 枚目は 2、12 枚目は 12 で割る」と説明するが、完全な式や material/node 構成は示していない。等重みにする数学的な読みは、累積平均 A(n-1) と新 frame F(n) から A(n)=A(n-1)+(F(n)-A(n-1))/n を更新する方法である。これなら過去の全 frame が最終結果で 1/n ずつを占め、全加算後の大値を保持する必要もない。

最終的に capture rate は、smear の連続感と性能負荷の折り合いとして 30 captures/s に設定された。player は shutter を開ける時間を変えられ、機能は manual mode や他のカメラ設定と連動する。開発者は、blur や motion の入った「不完全な写真」の方が生物的で現実感があると評価している。結論は、長時間露光を post effect として見せるだけでなく、時間、被写体の動き、カメラ設定を player が組み合わせ、意図的に一枚を作る操作へ統合できた、というものだ。

■ 内容分析
この事例の良さは、「現実と同じ物理を実装した」ことではなく、現実の現象を game engine が扱える離散 sample の蓄積へ翻訳し、失敗像から「輝度範囲」と「時間重み」という別の原因を切り分けた点にある。第 1 案は、算術平均の原理が間違いなのではない。十分な精度と範囲を持つ浮動小数点 render target で最後まで値を保てるなら、最後の除算で同じ平均へ到達できる。失敗は、演算順序と中間表現の範囲が実装の前提に入っていなかったことを示す。第 3 案は大きな中間和を作らず、平均の範囲内で accumulator を更新できるため、数値的にも実装上の都合が良い。

第 2 案は、ただの失敗ではなく、別の効果を持つ。A(n)=(A(n-1)+F(n))/2 と更新すれば、最新 frame の重みは 1/2、一つ前は 1/4、その前は 1/8 と急減する。これは露光時間全体を均等に残す写真には不適切だが、最近の動きを強調する trail、sensor の減衰、記憶の忘却のような表現にはむしろ使える。したがって「正しい合成法は一つ」ではなく、時間窓の中のどの時点をどれだけ残したいかに応じて kernel を選ぶ問題と読むべきだ。

一方、評価は開発者の視覚判断と掲載画像が中心である。30 captures/s がどの GPU、解像度、scene complexity でどれほどの frame time を使ったか、15/30/60 captures/s の視覚比較、高速で動く小物体の temporal aliasing、HDR・tone mapping・translucency・TAA との順序、実機写真との誤差は報告されない。manual mode と他の設定に「正しく影響」するとあるが、shutter time、ISO、aperture、最終露出の対応式も未掲載である。このため、本記事は再実装できる完全な technical recipe ではなく、問題の分解と探索の記録として強い。

■ 自分達の環境への適用
時間を蓄積する prototype に、この記事を「長時間露光 shader の複製」として入れるのではなく、時間表現を player-controlled mechanic にする最小の設計単位として使える。分ける変数は、蓄積時間 T、sample rate f、重み kernel w(t)、中間 buffer の表現範囲、player が作りたい結果の 5 つである。T と f を大きくすることを自動的に「高品質」とせず、軌跡が分離しすぎず読めるか、操作後に因果を説明できるか、負荷の上限内かを別々に測る。

最小 probe では、一定速度で動く光点と明暗が固定された scene を作り、算術平均と指数減衰の 2 kernel、15/30/60 captures/s、0.5/1/2 秒の時間窓を比較する。headless 側では、取り込み枚数、重みの合計、accumulator の min/max、定常 scene で出力が変化しないこと、一 frame だけの impulse が算術平均でどの位置でも同重みになることを検証する。これで clamp、重みの偏り、sample 漏れを image review 前に切り分けられる。次に、同じ動きをどの設定で撮れば望む軌跡になるかを説明なしで試し、設定変更から結果を予測できるかを人の操作評価にする。

ゲーム設計上は、蓄積した画像が美しいだけでは足りない。player が「水流を絹のようにする」「動く光で路径を描く」などの目的を持ち、時間窓と被写体の動きを予測し、結果を見て次の設定を修正できて初めて遊びになる。この「意図→設定→時間中の行動→結果→修正」の loop は、撮影に限らず、過去の軌跡を読む観測ゲーム、残像を足場にする action、一定期間の行動が地形へ残る simulation にも移植できる。

■ メリット・デメリット
メリットは、第一に、少数の変数と簡単な蓄積式で、時間の動きを一枚の結果へ変換できること。第二に、失敗像が clamp と temporal weighting の診断証拠になり、「見た目が変」を実装原因へ落とせること。第三に、shutter time を manual mode に組み込んだことで、表示効果が player の予測と工夫の対象になっていること。第四に、「不完全さが現実感を生む」という美学的な判断と、数理・性能・操作の制約が一つの機能に接続していることである。

デメリットは、実装詳細と定量評価が足りず、30 captures/s をそのまま性能基準にできないこと。等重み平均は露光中の動きを公平に残すが、それ自体が必ず遊びに適するわけではなく、過去が残りすぎて現在の操作が読みづらくなる場合もある。scene を複数回 render/capture する設計は、高解像度、複雑な lighting、透過、post-processing と組み合わせた時のコストが重い。また、物理的に厳密な sensor simulation と与えると誤解を生む。学習用を謳うなら、現実の shutter・ISO・aperture とどこが同じで、どこが game 向けの近似かを明示する必要がある。

■ 判定
部分採用。逐次平均で中間 clamp を避ける考え方、失敗した重みから時間 kernel の性質を読む方法、時間蓄積を player の操作 loop へ統合する設計は採用できる。ただし、記事の漸化式は説明が不完全で、30 captures/s と画質判断は作品固有である。移植時は等重みの数値 test、buffer 範囲、段階的な sample rate 比較、player が結果を予測できるかの 4 点を再検証する。
