■ 概要
「Player-Driven Emergence in LLM-Driven Game Narrative」は、LLMを物語の自動生成器ではなく、プレイヤーが設計者の想定外の遊び方を表明する媒介として捉え、その痕跡をプレイログから回収する研究である。実験用ゲーム DejaBoom! は、爆発が起きる一日を繰り返し、爆弾の場所と解除手段を探すテキストアドベンチャーだ。1日は30 actionで終了し、世界とNPCの記憶はresetされるが、プレイヤーは前回の知識を保持する。勝敗に関わる状態遷移はTextWorld上の固定game logicが担当する。一方、GPT-4は自由入力をactionかwordsに分類し、actionを固定engine用のverb-objectへ変換し、会話ではpersona、backstory、clue、開示条件、game historyから応答を生成する。成功条件までLLMへ委ねず、決定論的な世界の上に非決定的な対話層を重ねている。

中心的な着想は、この自由度を「会話が自然だった」という感想だけで終わらせず、設計者のnarrative graphと実プレイのgraphとの差として測ることにある。著者らは各logを日ごとに分け、GPT-4で区間化し、それぞれを「その時点のplayer strategy」へ要約してgame state labelを付ける。同じ意味かつ同じstateのnodeを日をまたいでmergeし、時系列edgeを持つplayer graphを作る。設計者による複数walkthroughから同じ方法で基準graphを作り、player graphを統合した際に基準nodeへmergeされなかったものをemergent nodeと定義した。

米国のRPG経験者28人が各1時間プレイし、平均75 step、平均2.5回の反復を行った。解除成功は6人だが、25人が楽しさを報告した。ログからは53件、重複を除くと43件のemergent nodeが得られた。代表は、NPCから想定外に情報を引き出す11件、新entityの要求8件、隠し情報を探す新手法6件、新しい解除案5件である。例えば、Moriartyの共犯者を装って計画を聞く、Merlinを講義で気をそらして解除キットを盗もうとする、犬に人物を探させる、といった行動が暗黙の要望として可視化された。LLMとのinteractionは想定外のpathを引き出すが、全nodeが有用とは限らず、設計者の選別が必要だと結論づけている。

■ 内容分析
この研究で価値が高いのは、生成された物語の良し悪しより「プレイヤーが何を成立させようとしたか」を観測単位にした点である。未実装のflashlightをinventoryへ入れようとする行動はゲーム内では失敗だが、設計上は利用可能だと期待されたaffordanceを示す。Moriartyを欺く会話も、モデルが一度それらしい返答をしたという事実より、プレイヤーが敵側へ寝返る分岐を欲したことの方が重要である。失敗commandを単なるparser errorとして捨てず、未実装の攻略案、世界への期待、表現したいroleとして分類することで、自由入力のノイズをbacklogへ変換している。

一方、emergenceの操作的定義には混同がある。「基準graphへmergeされない」ことは新規性を表すが、楽しさ、実現可能性、因果的にLLMが生んだことまでは保証しない。論文自身もdead endを含むと認めている。存在しないsheriffや時計を尋ねたnode、固定engineが受け付けないobjectを要求したnodeは、創造的な攻略である場合も、世界説明の不足やparser mismatchである場合もある。またstrategy要約、state label付与、意味的mergeをすべてGPT-4に依存しており、同義nodeの分割は件数を水増しし、異なる意図のmergeは差分を消す。人手で43 unique nodeを広いcategoryへまとめているが、抽出・merge精度のannotator agreementやgold labelとの比較は報告されていない。したがって53件という値をモデル間・作品間の絶対的な創造性scoreとして使うのは危険である。

user studyも探索的である。参加者は28人、米国内のRPG経験者に偏り、解除成功は6人に留まる。creativity motivationを選んだ6人のうちemergent nodeを作ったのは2人だけで、その2人が11件、1人平均5.5件を作ったため「creative profileほど多い」という示唆が出ている。しかも2人ともmasteryも選択している。これはinterestingな仮説だが、player selection規則にはできない。運用品質では40%が約15秒のlatency、10%がpersona不整合、10%が反復応答、14.28%がNPCの情報開示が容易すぎることを指摘した。自由度を増やす対話層が、同時にpacing、謎の難度、人格の一貫性を壊すことも示している。

固定logicと生成対話の分離も重要である。LLMが存在しないobjectを語れても、TextWorldのstateには追加されない。この不一致は欠点だが、安全装置でもある。会話の即興性を許しつつ、inventory、解除条件、location開放をdeterministicに保てるからだ。研究の本質は「LLMにgame masterを任せる」ことではなく、「固定されたplayable systemの周縁でplayer intentを広く受け止め、後から設計差分を見つける」ことにある。

■ 自分達の環境への適用
最も直接的な導入先は、playtest logから次のplayable diffを選ぶ工程である。各prototypeについて、まず設計者の想定解を「state、player intent、実行action、結果」の短いnode列として保存する。human playtestとheadless agentのlogから同じ列を作り、基準にmergeできないnodeを候補化する。ただし候補を即採用せず、少なくとも「有効な別解」「欲されたが未実装のaffordance」「表現・roleplay」「説明不足」「入力解釈ミス」「生成層のhallucination」に分ける。複数sessionで反復されたnode、主目標に接続できるnode、低コストで試せるnodeを優先すれば、単なる奇抜さではなく設計改善へ戻せる。

小さなprobeは、既存prototypeを1つ選び、想定walkthrough 2本とhumanまたはheadless log 5本程度だけを使えばよい。LLMには原文logとdeterministic state snapshotを同時に渡し、strategy要約と「根拠となるlog位置」を出させる。mergeはstate一致を必須にし、semantic similarityだけで自動確定せず、境界例をreview queueへ送る。評価値はemergent node総数ではなく、(1) human reviewで有効と判定された比率、(2)複数runで再現した率、(3)次のdiffへ採用された件数、(4)採用後に成功率・理解度・楽しさが改善したか、の4段階にする。これならLLM抽出器の誤差とゲーム設計上の価値を分離できる。

headless評価では、agentへ単に勝利を求めるだけでなく、探索方針を変えた複数personaを用意する価値がある。最短攻略、世界モデル検証、roleplay、object探索などの方針別にlogを集めれば、人間28人をすぐ集められない段階でも未想定intentの候補を広げられる。ただしheadless agentの提案はhuman funの証拠ではないため、最終的な昇格条件には短いhuman playtestを残す。

記憶システムには、raw logを消さず、抽出nodeをatom相当の派生物として持たせる構造が合う。nodeにはsource span、state label、抽出model、prompt version、merge先、review判定、採用diffを紐付ける。これにより後から抽出規則を変えて再計算でき、同じ失敗要求が別prototypeでも現れたかをrecallできる。制作cycleではPhase 4aの問題抽出に近いが、恒久ルールを増やす前に可逆なprobeへ落とす、という現在の運用とも整合する。

■ メリット・デメリット
メリットは、第一に自由入力を「生成品質」ではなく具体的な設計差分へ変換できること。第二に、失敗したactionもプレイヤーが期待したaffordanceとして保存できること。第三に、固定logicを維持したまま対話の探索空間だけを広げられること。第四に、walkthroughとの差分という形なので、human logとheadless logを同じ監査単位で比較しやすいことにある。

デメリットは、差分が価値を意味せず、dead end、説明不足、hallucinationを大量に含み得ること。抽出とmergeを同じLLMへ任せると、modelやpromptの変更でnode数が揺れ、自己評価的なbiasも入る。さらにリアルタイム生成は15秒級のlatency、persona崩れ、反復、clue漏洩を起こし、謎解きのpacingを損ねる。少人数・単一genreの実験なので、player profileとの関係や他genreへの一般化も未確立である。導入コストはgraph自体より、source spanを保持したreviewと、候補を実装backlogへ昇格させる人間判断にある。

■ 判定
部分採用。designer walkthroughとplay logを同じstrategy graphへ変換し、未merge nodeを設計候補として拾う枠組みは採用する。一方、emergent node数を創造性scoreとして扱うこと、生成NPCを勝敗stateへ直接接続すること、player profileから有望testerを選別することは現時点では採用しない。まず1 prototype、5 log程度でsource span付き抽出とhuman reviewを試し、有効候補率と次のplayable diffへの接続率で継続判断する。
