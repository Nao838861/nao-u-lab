■ 概要
この記事は、Stone Librande が GDC 2013 で報告した SimCity（2013）の設計過程を、One-Page Design が大規模 simulation 開発のどこまで通用し、どこで別の道具を必要としたかという観点から再構成している。出発点は、設計書が厚い design bible になると読まれにくく、system 間の関係も見えにくいという問題である。Librande は pre-production の5人チームから出荷までの3年半、設計の中心を一枚の図で伝える実験を行った。目的は全情報を無理に一枚へ収めることではなく、この制約が破綻する地点と理由を制作の中で見つけることだった。

初期には、実在都市を参照した map、multiplayer trading、都市 specialization などを、空間配置、矢印、色、短い注記で同じ視野へ置いた。一部の初期 map は出荷時まで残った。より重要なのは、multiplayer trading の関係図を作る過程で、構想が既に扱いにくい複雑さへ達していると露出し、実装や調整へ大きな資源を投じる前に切れた事例である。一枚は完成仕様というより、依存関係を圧縮し、設計者自身が説明できない箇所を早期に発見する診断面として働いた。

しかし規模が増すと限界も現れた。coal city について、製造施設の段階、追加 module、支援要素、simulation への影響、reward、resource chain を一つの「消化可能な」図にする要求は重かった。磁石の部品を印刷して組み替える案は制作時間が大きく、card game 化は表現が目的化して実務に合わなかった。最終的には CSV / spreadsheet に詳細値を置き、その情報を色分けした統合 chart へ戻す hybrid に移った。high-level な変更のたびに担当者が各作業場所の古版を外して新版を配り、閲覧者が資料を探しに来るのを待たなかった。

評価は統制実験ではなく、3年半の制作利用と postmortem に基づく定性的 evidence である。図の一部は作成から3年半後にも参照され、最上位構造から詳細へ降りる project organization の土台として有効だったと team 内で評価された。一方、spreadsheet、壁一面、部屋単位へ拡張した事実そのものが、一枚だけでは simulation の数値と例外を保持できないことを示す。結論は One-Page Design が万能だったという話ではない。俯瞰図を中心に据えつつ、詳細表現を適切な道具へ逃がし、更新版を能動的に届ける運用まで含めて初めて、大規模制作に耐えたという報告である。

■ 内容分析
この事例の価値は「一枚の図は伝わりやすい」という一般論ではなく、圧縮、分離、同期の三段階を制作期間全体で見せた点にある。圧縮では、同じ視野へ置けない依存や読めない線の密度が複雑さの signal になる。分離では、core loop や resource flow の形を chart に、係数、level 別値、例外を spreadsheet に置く。同期では、high-level update ごとに配布物を差し替える。この三つのどれかを欠くと、一枚は仕様の省略、spreadsheet は孤立した数値倉庫、壁の poster は古い誤情報になる。

特に重要なのは、設計上の複雑さと文書上の複雑さを区別することだ。trading 図が読みにくい時、単に作図能力が不足している場合もあれば、system 自体が過剰結合している場合もある。記事は前者と後者を機械的に判別する基準を出していない。それでも実装前に図を作り、説明不能な関係を切る判断へ接続した点は強い。図の美しさを成果にせず、実装投資を止められたかを成果にしたからである。

一方、成功 evidence は慎重に読む必要がある。記事が示すのは team の回顧、長期参照、具体的失敗例であり、従来文書との比較、作成時間、更新漏れ、手戻り削減量は測っていない。磁石や card game の失敗は「視覚化が常に安い」という前提を崩すが、どの情報量で spreadsheet へ移るべきかという閾値もない。また紙を物理配布する運用は可視性を上げる反面、最新版の識別、遠隔参加、accessibility、変更履歴には弱い。現在の環境へ移すなら、poster の雰囲気ではなく、正本、版、owner、生成元を明示する必要がある。

もう一つの示唆は、図と数値表を二重管理しないことである。chart と CSV を人手で別々に直すと、見やすさと引き換えに不整合が増える。記事の hybrid は情報を統合して配布したが、自動同期までは扱っていない。現代的な実装では spreadsheet や設定 file を数値の正本にし、図側は概念名と参照先を持つか、可能なら正本から一部を生成する方が安全である。One-Page Design は database ではなく、どの関係を理解し、どの詳細へ降りるかを示す front map と位置づけるのがよい。

■ 自分達の環境への適用
小規模 simulation prototype では、実装前に一枚の「system map」を作る。中央に player action と主要 feedback loop、周囲に resource の source / sink、state transition、成功・失敗条件を置き、各 edge に code 上の system 名または headless assertion ID を付ける。具体的な rate、cost、cooldown、spawn table は CSV や設定 file に分離し、図へ数値を複製しない。図の header には対象 build、owner、更新時刻、数値正本、未解決点を記録する。

最初の probe は resource chain を持つ playable diff 一件で十分である。実装前の図から、①一視野で説明できない交差、②循環依存、③source / sink の欠落、④変更が三つ以上の system へ波及する edge を数える。実装後は、発見が実際の不具合や手戻りに対応したか、図の作成・更新時間、古版参照、図と設定値の不一致、第三者が core loop を説明するまでの時間を記録する。作図で複雑さが見えただけで終わらせず、system を削る、境界を切る、test を足すという diff へ接続できた件数を評価する。

制作サイクルでは Phase 1/2 の候補メモや長文分析を一枚へ圧縮しない。適用先は game task ごとの軽量 index と playable contract である。図は設計意図、実装 file、headless trace、評価結果の入口だけを持ち、原文と証拠は既存の記憶層へ残す。変更時には code / data の正本を先に更新し、図の版が追随しなければ cycle を完了扱いにしない。紙の差し替えに相当するものを、古版の archived 化と参照 link の更新として実装する。

採用 gate は、図あり条件で未記載依存と解釈不一致が減り、その削減が作図・更新コストを上回ることとする。図を一枚へ保つために文字を縮小する、数値を埋め込む、例外を消す必要が出たら、対象範囲を分割するか spreadsheet へ逃がす。大きな一枚を守ることより、一つの判断面が一視野で読めることを優先する。

■ メリット・デメリット
メリットは、system 間の関係を同時に見せることで過剰結合を実装前に発見できること、職種や担当をまたぐ共通の入口を作れること、最上位構造から詳細の正本へ降りる導線を長期に残せることにある。hybrid 化を前提にすれば、俯瞰性と数値の精度を両立できる。能動的な差し替え運用も、重要な変更が「書かれたが届かない」状態を減らす。

デメリットは、良い図の制作に相応の時間と技能が必要なこと、見栄えが設計の妥当性と誤認されやすいこと、数値・例外・履歴を一枚へ持てないこと、複数の表現を人手同期すると古版や矛盾が増えることだ。記事の効果は定性的で、失敗条件の閾値も定量化されていない。全資料を置換すると、検索性、差分、accessibility、機械検証を損なう危険がある。

■ 判定
部分採用。One-Page Design を完全仕様ではなく、simulation の依存を早期露出し、詳細正本と test 証拠へ案内する versioned front map として使う。次の resource-chain prototype 一件で、未記載依存、解釈不一致、手戻り、更新コスト、古版参照を測る。図と数値表の同期が保て、実装前の削減判断へつながった場合だけ適用範囲を広げる。
