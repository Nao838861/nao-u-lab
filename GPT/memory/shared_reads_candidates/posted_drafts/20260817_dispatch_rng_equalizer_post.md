■ 概要
Game Developer が GDC Festival of Gaming 2026 の講演から紹介した、『Dispatch』の成功判定を「RNG as an equalizer」として設計した事例である。『Dispatch』は、事件ごとに適切なヒーローを派遣する物語主導のゲームで、選択した編成に応じて成功率を百分率で表示する。初期案は必要能力値を見せず、条件を満たせば成功・外せば失敗という不可視の閾値方式だった。しかしこれでは casual player は正解条件を推測できず、失敗によって物語進行を止められる。そこで合否を確率化し、不適切な派遣にも小さな成功可能性を残す一方、experienced player には資源を過剰投入せず成功率を高める min-max の余地を与えた。

重要なのは、画面の表示確率をそのまま抽選には使っていない点である。user testing 後、表示が76%を超える判定は自動成功にした。ただしプレイヤーがこの補助を3回受けると自動成功を解除し、その後は表示どおりの確率で抽選する。そこで76%超の判定に失敗すると、再び3回分の自動成功を有効にする。高確率なのに連続して外れる体験を抑えつつ、永続的な無敗にはしない状態機械である。また表示1〜14%の判定は、内部では一律15%まで引き上げた。悪い編成でも完全に望みを失わせず、偶然の逆転を物語として残すための floor と解釈できる。

参加者はこの仕組みを「公平だが、少し易しいこともある」と評価したという。そこで最終 episode だけは全ての不可視補助を停止した。シーズンを通して初めて表示値と生の抽選が一致し、学んだ dispatch skill をそのまま試す難しい finale にする狙いだった。記事が示す結論は、RNG を単なるノイズでなく、初心者の破綻を防ぎ、熟練者には資源最適化を残し、物語の難易度曲線まで制御する equalizer にできるというものだ。

■ 内容分析
この設計は単純な pity timer ではない。内部状態は少なくとも「高確率自動成功の残り回数」と「最終 episode か」を持ち、同じ85%表示でも、補助が残っていれば実効成功率100%、使い切った後なら85%になる。1〜14%表示も実効値は15%なので、表示値は予測確率ではなく、選択の相対的な良さを伝える UI になっている。抽選が履歴依存になることで、局所的な理不尽さを抑えながら結果の意外性を残している。

“equalizer” が均しているのは上手い選択と下手な選択の成功率そのものではなく、プレイヤー層ごとの破綻しやすさである。低確率側の floor は初心者の悪手にも救済を与え、高確率側の3回保証は適切な選択をしたのに運だけで否定される事態を防ぐ。experienced player はそれでも、誰を何人送れば76%超へ届くか、別事件のために誰を温存するかを最適化できる。したがって補助は意思決定を消すのでなく、「正しい判断が偶然で連続否定される幅」と「悪い判断が物語を完全停止させる幅」を狭めている。

高確率側の分布は特に巧妙である。3回保証を使い切った後も、生の抽選で成功し続ける限り補助は戻らず、最初の失敗だけが次の3回保証を再装填する。このため76%超の判定では連続失敗が起こらず、一度の失敗後には少なくとも3成功が続くが、単発の失敗までは消えない。常時100%にするより驚きを残し、単純な「3回に1回救済」よりも悪い streak へ直接反応する。反面、表示値ごとの独立試行という性質は失われ、同じ編成の結果を観測して確率を学ぶことは難しくなる。

ここには二種類の公平性が衝突している。統計的公平性は、85%と表示した試行が十分な回数で85%成功することを求める。体験上の公平性は、良い判断をしたプレイヤーが短い playthrough の不運で罰せられないことを求める。『Dispatch』は後者を優先した。数時間の物語体験では大数の法則が救ってくれる前に finale へ到達するため、この選択には合理性がある。しかし数値表示を採用した時点で前者への期待も生むので、成功率というラベルと内部救済の契約は完全には一致していない。

ただし、記事が示す評価は限定的である。user testing の人数、比較群、episode 別の失敗率、再試行率、編成の多様性、離脱率は記載されていない。「公平」「少し易しい」という定性的反応だけでは、76%・3回・15%が他作品にも有効とは言えない。成功・失敗が物語を分岐させる本作では救済が価値になるが、失敗から戦術を学ぶゲーム、対戦、ランキング、希少報酬を伴う経済では、同じ隠れ補正が結果の意味を壊す。

表示と内部確率の不一致にも信頼上のリスクがある。百分率は通常、長期頻度の約束として読まれる。履歴状態を知らないプレイヤーが記録を取れば、低確率帯と高確率帯の双方で上振れし、表示が虚偽だと判断し得る。特に finale で補助を突然外すと、それまで学んだ85%の体感が別物になり、ドラマ上の緊張ではなく恣意的な難化に見える。演出として成立するには、危機の激化や支援喪失など、ルール変化を感じ取れる予告が必要である。

■ 自分達の環境への適用
ゲーム試作では、まず「表示値を偽る技法」ではなく、履歴依存の不運抑制を独立した設計部品として試す。判定ごとに displayed_p、raw roll、effective_p、補助残数、編成コスト、episode、結果、seed を記録する。A: 生の確率、B: 記事と同じ76%超3回保証＋低確率15% floor、C: 連敗時だけ発動し UI でも救済状態を示す方式を、同じ入力列で比較する。

headless 評価では、表示帯ごとの成功率と calibration error、最大連敗長、物語進行を止める失敗回数、ヒーローの過剰投入量、選択肢の多様性、低確率挑戦の頻度を測る。B が停滞だけを減らし、最適編成が一択化せず、資源管理の差も残すなら採用候補になる。ただし「公平に感じる」「騙されたと感じない」はログから判定できないため、最後は少人数でも人間に、表示への信頼、失敗の納得感、finale の難化理由を確認する。

simulation は平均成功率だけで合否を出さない。各方式について1000 seed 以上を流し、失敗 streak の95・99 percentile、episode 完遂不能率、同じ displayed_p でも補助状態によって結果が変わる幅を分けて出す。さらに novice policy、確率最大化 policy、資源温存 policy を用意し、補助によって全 policy の成績が同じになるのか、初心者の下限だけが上がるのかを見る。equalizer が熟練差まで消すなら、意思決定ゲームとしては過補正である。

finale 解除も単独の A/B probe にする。通常 episode と同じ補助、全解除、段階的解除を固定 seed で比較し、クリア率だけでなく、直前まで有効だった戦略が急に無効になる割合を見る。全解除で失敗率の急上昇しか起きないなら、演出ではなく罰になっている。解除を使う場合は、episode 開始時に危機状態を明示するか、「成功率」ではなく「作戦評価」のように UI の語を変え、数字が厳密な抽選確率だという約束を弱める。

制作サイクルでは、補助を追加した commit と閾値変更の理由を test artifact に結び付ける。たとえば「76%だから」ではなく、「高確率失敗の99 percentile が物語停止を生み、人間テストで不公平反応が集中したため」と残す。後の prototype が別の失敗コストや session 長を持つ時、数値だけを模倣せず、元の問題条件から適用可否を再判定できる。

■ メリット・デメリット
メリットは、少ない状態で高確率の理不尽な連敗と、低確率の完全な無希望を同時に抑えられること、初心者の物語停止を減らしつつ熟練者の資源配分を残せること、補助の解除を難易度演出に接続できることだ。seed と補助状態を記録すれば deterministic に再生でき、閾値・回数・floor を headless simulation で探索しやすい。

デメリットは、表示確率が校正済み予測でなくなること、履歴状態が隠れてデバッグと説明が難しくなること、救済が多すぎると良い編成と悪い編成の結果差や失敗からの学習を薄めることだ。最終局面だけの解除は、十分な予告がなければ信頼違反になる。記事の user testing は再現に必要な分布や標本数を公開しておらず、76%・3回・15%を既定値として移植する根拠もない。

■ 判定
部分採用。採るのは「履歴を持つ不運抑制」「補助状態を含む再現ログ」「山場で補助量を変える際の段階評価」であり、表示値と内部確率の無条件な乖離ではない。物語進行を偶発的失敗から守る一人用ゲームに限定して比較 probe を行い、客観ログと人間の信頼評価の両方を通った方式だけを使う。対戦・ランキング・課金経済には適用しない。
