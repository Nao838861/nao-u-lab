■ 概要
『Academia: School Simulator』を Early Access 運営した Squeaky Wheel が、大量の player feedback から次に追加する mechanic を決めた手順の記録である。出発点は、Early Access で community にゲームを育ててもらおうとすると、要望の「firehose」が来る一方、全てに応えれば工数が破綻し、作品の核まで失われかねないという問題だ。そこで同チームは、要望をそのまま feature list にせず、段階的に roadmap へ変換する。

第一段階では、design director が feedback 確認と返信の責任者となり、共通する要望を spreadsheet に集約し、件数で重み付けする。ただし同じ欲求が異なる言葉で書かれるため、文面の機能名ではなく、player が実際に「何をしたいのか」という context を推定して同義要望を束ねる。第二段階では Trello 上で候補を Aesthetic、Quality of Life、Gameplay の三種に分け、チームの各人が一週間かけて定型 template で mechanic を pitch する。これは「欲しい」だけの投稿を避け、gameplay への影響まで言語化させるための制約である。

第三段階は、賛否だけの投票ではない。各 member は採用したい card に自分自身を担当者として割り当てる。つまり支持と実装責任を結び付け、「自分が作るとしても本当に必要か」を問う。無票の案は denied へ移し、複数票の案は賛成者への具体的な質問と反対意見を通して議論する。同時に実装期間の label を付け、schedule に収まるかを見る。一人だけが支持する案は、その人がゲームに必要な理由を強く説明し、それでも支持を作れない案を落とす。最後に残った mechanic を、例えば lawyer、goons、school monitor の変更を「law and order update」に束ねるように、相互に関係する theme で編成する。結論は、この編成が design task を管理可能な更新単位にし、player にも次回更新の意味を説明しやすくするというものだ。

■ 内容分析
この手法の中核は、要望数の多い順に作ることではなく、異質な signal を段階ごとに変換する funnel にある。原文の発言を潜在的な行動欲求へ、行動欲求を gameplay 上の仮説へ、仮説を担当意思と工数を持つ計画へ、そして計画を player に意味が伝わる update へ変える。要望頻度は最初の入力に過ぎず、最終判定では「作り手が責任を引き受けるほどの効果があるか」と「予定内に作れるか」が加わる。これにより、声の大きさと roadmap の優先度を切り離している。

特に良いのは、vote を無料の好みの表明にせず、ownership を伴う選択にした点だ。一方で、このフィルタは「良い mechanic」だけでなく、「チーム内で売り込みやすい mechanic」を選ぶ。記事自身も、内向的な人や説明の苦手な人の案が不利になることを認め、lead が意図を引き出す必要を指摘している。さらに分類も中立ではない。Aesthetic、QoL、Gameplay に分けると比較しやすい反面、操作感や可読性のように三種にまたがる改善は過小評価され得る。theme 化も説明と管理には強いが、個別 mechanic の成否を分離して観測しにくくし、一つの遅延が update 全体を止める危険もある。

評価の強さにも注意が必要だ。これは『Academia』で実際に用いた手順の回顧であり、導入前後の retention、review、開発速度、採用 mechanic の利用率は示されない。誰が feedback を送ったかという cohort の偏りや、発言しない player の行動データも扱わない。落とした案の一覧は保存されるが、どの段階で何を根拠に落とし、後日その判断が正しかったかを検証する閉ループも説明されない。したがって「この手順で良いゲームになる」という実証ではなく、会議を収束させ、roadmap に実装可能性を持たせるための運用例として読むべきである。

■ 自分達の環境への適用
自分達の小規模なゲーム制作では、team vote の人数を真似るのではなく、signal の変換順序を取り入れる。playtest 後、まず feedback 原文を保存し、似た表現を束ねながら「player がとれなかった行動」に書き換える。次に各候補を、根拠となる原文、推定した欲求、守る design pillar、期待する player behavior、実装見積り、最小 probe、中止条件の七項目で pitch する。「支持」の代わりは、次の iteration で実際に自分が作り、評価すると約束できるかで判定する。

headless 評価はこの funnel の「実装後」を補強できる。例えば新 mechanic が増やす選択肢数、到達可能状態、コスト、失敗率、進行時間は自動比較し、ルール違反や極端な支配戦略を先に落とせる。ただし、読みやすさ、気持ち良さ、作品らしさは headless で代用せず、人の playtest で確かめる。二段階評価にすれば、「作れるか」と「作る価値があるか」を混同しにくい。

最初の小さな検証は、直近の playtest から最大 10 件の要望を集め、意図ベースで同義統合し、上位 3 件だけを七項目で pitch する形でよい。各候補は一〜二日の prototype 上限を設け、headless の不変条件と人の観察の両方に通ったものだけ次の milestone 候補にする。theme 化はその後に行い、一つずつ無効化できる feature flag と個別評価を残す。これなら、更新の物語性と原因分離可能性を両立できる。

記憶システムにも同じ構造が使える。raw feedback を即座に永続ルールへ変えず、同義統合した candidate、検証可能な仮説、実装責任と廃棄条件を持つ probe、結果を伴う教訓の順に昇格させる。ここでの頻度は検討順を上げる signal であり、真実性や永続化の根拠ではない。記事の funnel をこのように読み替えると、player の声と自分達の記憶のどちらでも、「多く見かけた」から「実装すべき」への飛躍を防げる。

■ メリット・デメリット
メリットは、第一に、表現の違う要望を欲求単位へ束ね、単純な声量順の開発を避けられること。第二に、pitch、担当、工数を必須にし、意見を実行可能な commitment に変えられること。第三に、theme によって内部の task と対外的な更新説明を同じ単位で扱えることだ。

デメリットは、feedback する player の self-selection と loud-player bias を解消しないこと、説得力や組織内の立場が評価に混ざること、人気のない基盤改修や長期的な design debt が無票になり得ることだ。また、実装期間の label は工数の目安であり、効果量との比較ではない。themed update は結束を作る半面、個別検証の粒度を潰しやすい。導入時は行動データ、少数意見、design pillar、prototype 結果を別系統の根拠として残す必要がある。

■ 判定
部分採用。要望の同義統合、文面から行動欲求への変換、定型 pitch、実装責任と工数の確認までは、次 iteration の選定手順として採用価値が高い。一方、件数、チーム内投票、説得の上手さは効果の代理指標にせず、headless 検査と人の playtest で個別 mechanic を検証する。theme 化は採否を決める手段ではなく、検証を通った mechanic を説明可能な milestone に編成する最終段階に限定する。
