■ 概要
2005年に producer / lead programmer の Simon Hallam が書いた『Wik & The Fable Of Souls』のポストモーテム。13MBのダウンロード販売PCゲームを、11人規模の Reflexive Entertainment が約6か月、15MB上限という制約下で制作した記録である。出発点は、一日で作った「BugEater」という prototype だった。画面左右のヤモリ風キャラクターをクリックで直線ジャンプさせ、虫から幼虫を守る内容で、複数のマウスを一台のPCにつないで8人が競う MouseParty では混乱そのものが強い楽しさになった。約6本の候補から本制作へ選ばれたが、チームはこの multiplayer の盛り上がりを single-player の核の強さと取り違えた。

本制作の三か月目まで、直線ジャンプへ障害物、自動捕食、射程内の舌攻撃などを足しても、レベルを見た目以外で差別化できるほどの奥行きは生まれなかった。そこで重力を導入し、空中で舌を足場へ固定して振り子のように移動する案を試す。粗い初版でも従来案より明確に面白く、反復で上達できる技能が生まれたため、既存レベルを全廃して jump-and-swing を中心に再構築した。少数の基準レベルと挙動の調整だけで約6週間を使い、左右のマウス移動による加速、舌に触れた虫の回収、捕食物を散弾のように吐く連鎖まで発展させた。挙動は86個の editable property を持つ「Wik style sheet」へ分離し、再コンパイルせず調整できるようにした。

完成版の mouse-only control は座標を文字どおり実行しない。足場端付近へのジャンプでは落下しにくい軌道を選び、舌の接続ではクリック周辺から安全で有効な swing position を探す。4 pixel の外れを即死として処理するより、プレイヤーが達成しようとした行為を推定して成功側へ寄せる設計である。tutorial も、全員に同じ操作を順番どおり強制する初版では、初心者が後で旧習へ戻り、中級者以上は退屈した。複数目標を自由に解かせ、迷いが見えた時だけ助言する第二版に変えると focus group の結果は改善したが、偶然クリアして技能を身につけない人は残った。記事は release 後の案として、弱い技能を継続観測し、必要な時だけ助言する quiet watchdog まで提案している。

一方、pivot の代償で4体の boss は削除された。出荷後には社内25台と外部約20人の beta test を通過した OpenGL 問題が顕在化し、trial 利用者の推定8〜12%に描画異常や停止が発生したため、約2週間で AGG ベースの software rasterizer へ切り替えた。作品は高評価と IGF finalist という成果を得たが、商業的には期待を下回った。したがって結論は「大胆な再設計で作品品質を救った」だけではない。楽しさの仮説、入力の寛容さ、学習支援、互換性、売上は別々の成立条件であり、一つの成功指標を他へ代用してはいけないという記録である。

■ 内容分析
最も重要なのは、prototype の合否を「その場が盛り上がったか」ではなく、「製品版と同じ人数・目的・反復時間でも核が持続するか」で判定すべきだと示した点だ。MouseParty の楽しさには、8人の競争、同席者の反応、入力の混雑、短時間の騒がしさが混ざっていた。これらを除いた single-player で直線ジャンプだけを反復すると、意思決定や上達余地が薄い。初期三か月の追加要素は、弱い核を複雑な周辺機能で補強しようとしたため、レベル差を増やせなかった。対して重力と舌 swing は、入力、軌道予測、timing、release、失敗回復を一つの運動系へ結び、同じ部品から異なる状況を作れる。pivot が効いた理由は新奇さではなく、操作一回が次状態を変え、練習による改善が見える状態空間を作ったことにある。

86項目の style sheet も、単なる便利ツールではない。大きな方向転換後、残り時間内に「面白いが未調整」の運動系を製品へするには、仮説一つごとの変更費を下げる必要があった。少数の基準レベルを先に作り、コード変更と再コンパイルからパラメータ調整を切り離したことで、movement と level design の往復を速めている。ただし記事は86項目の名称、探索順、playtest 回数、採否閾値を示さない。数を模倣しても再現性はなく、重要なのは各 parameter を観測可能な挙動へ対応づけることだ。

入力補正は「簡単化」ではなく、観測できない意図を周辺文脈から推定する層と読める。クリック位置そのものは不完全な代理変数であり、足場端、到達可能距離、接続候補、失敗時の損失を使って意図を復元する。ここで危険なのは、補正が強すぎると自分の入力で成功した感覚、軌道の予測可能性、技能差を消すことだ。Wik では補正対象を「数 pixel 外した接続」など局所的な失敗へ寄せ、swing の加速や release timing は残している。この分業が、寛容さと習熟を両立させる要点である。

tutorial の評価も、説明を表示したか、区間を通過したかではなく、その後に技能が保持・転移したかを見ている。線形 tutorial は直後の task completion を改善しても、自由場面で旧習へ戻るため偽陽性になる。第二版も偶然通過を排除できず、記事自身が未解決を認めている。quiet watchdog は有望だが、実装・再評価された結果ではなく release 後の着想である点を区別する必要がある。また focus group の人数や定量値がなく、商業的不振の原因も marketing、顧客層、作品特性の仮説に留まる。これは強い因果証明ではなく、失敗と修正を具体的に追える単一事例である。

■ 自分達の環境への適用
ゲーム prototype では、最初の playable build に「成立条件表」を添える。人数、session 長、観客の有無、勝敗、操作デバイスを記録し、製品想定と違う条件が面白さを作っていないかを分離する。対戦 prototype を single-player 化する場合は、同じ資産を増やす前に、製品想定条件で10分反復し、状態遷移の種類、意味のある選択、失敗原因の説明可能性、試行ごとの上達を確認する。核が弱ければコンテンツ量で隠さず pivot 候補を一つ作り、旧版と同じ短い評価表で比較する。

調整値は「86個」を目標にせず、挙動名、値、変更理由、期待する観測、結果を一行で残す。headless 評価では、到達率だけでなく、入力から接続までの距離、補正発動率、補正後の生存率、同じ失敗の連続回数、軌道のばらつきを記録する。補正あり／なしを同一 seed で比較し、補正が小さな誤差だけを救っているか、意思決定そのものを代行していないかを見る。ただし「意図」は log だけで確定できないので、境界事例の replay を人が見て最終判断する。

tutorial には技能ごとの watchdog を小さく試す。たとえば swing なら、接続後の加速、適切な release、目的方向への速度という下位技能を定義し、tutorial 通過後の通常レベルでも再観測する。助言条件は「一度失敗」ではなく、同じ弱点が複数回続き、かつ進行が停滞した時に限定する。提示後は成功率だけでなく、助言なしで再現できたかを測る。この記録を制作サイクルへ返せば、「tutorial 完了」を学習済みと誤認するのを防げる。

記憶システムには、今回の教訓を抽象的な「早く pivot する」へ潰さず、適用条件と反証を組で残す。つまり、prototype と製品の条件差、三か月時点の level variation 不足、六週間の再調整、補正の局所性、tutorial の転移失敗、8〜12%の互換性問題、好評と商業的不振の分離までを検索可能にする。次回は「面白かった」という atom だけでなく、どの条件で、何を測り、何が未証明かを recall できる形が役立つ。

■ メリット・デメリット
メリットは、失敗した前提から pivot、tooling、入力補正、onboarding、出荷後障害までが一つの開発履歴としてつながっていること。特に、局所的な盛り上がりと持続する core loop を分ける視点、誤差は救うが技能は残す補正、tutorial 後の行動で習得を見る考え方は、現在の小規模 prototype と headless 計測へ移しやすい。失敗に三か月使った事実や、評価と売上が一致しなかった結末も、成功談への偏りを抑える。

デメリットは、2005年の単一作品で、focus group の規模、調整過程、retention、conversion、売上が開示されず、各施策の効果量を再計算できないこと。mouse-only、15MB、try-before-you-buy 市場という制約も現在の制作環境とは違う。さらに意図推定補正と watchdog は、誤判定すると操作主体性を奪い、助言過多を生む。定量的な自動評価だけで採用せず、replay 観察とプレイヤーの自己説明を併用する必要がある。

■ 判定
部分採用。prototype と製品条件の一致確認、調整値の観測可能化、局所的な入力補正、tutorial 後の技能監視は実装可能な評価軸として採る。一方、「大規模 pivot は正しい」「補正は多いほどよい」と一般化せず、同一条件での比較、補正発動ログ、人による replay 確認を通して小さく検証する。
