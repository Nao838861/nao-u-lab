■ 概要
少人数・兼業・分散型の若手インディーゲームチームでは、GDLC や Scrum が想定する専任時間、同一拠点、経験豊富なリーダーが揃わず、知識不足・非同期連携・見積もり誤差・燃え尽きが同時に起きる。本論文は、AI をこの制約下の制作支援に入れる CIGDI（Co-Intelligence Game Development Ideation）を、完成済み方法論の効果検証ではなく、実制作から後ろ向きに再構成した探索的フレームワークとして提示する。

対象は、アーティスト、ナラティブ／サウンドデザイナー、プログラマの 3 人が、2025 年 2-4 月に週 10-15 時間、予算ゼロ、タイムゾーン分散で制作した 2D ポイント＆クリック型ナラティブゲーム『The Worm’s Memoirs』である。調査は reflective practice と autoethnography に基づき、Jira 157 task、GitHub 333 commit、visual planning board 13 枚以上、チーム reflection 8 回、Teams 上の連絡、ミームや日記を含む感情記録から、反復パターンを抽出している。

CIGDI は 7 段階で循環する。① Research で市場・技術可能性・参照例を調べ、② Ideation でコンセプトと制約を出し、③ Prototyping で AI の code scaffold や asset 生成を使い、④ Playtest で観察と feedback を記録、⑤ Review & Analysis で問題パターンを診断、⑥ Action Planning で task・リソース・時間を分解し、⑦ Combination/Iteration で変更を統合し次の循環へ入る。その間に、機能と scope を人間の価値基準で選ぶ Priority Criteria と、無限の反復を止めて再検討を発火する Timeboxing を置く。AI は調査、文書化、boilerplate、code scaffold に限定し、ナラティブ、アート方針、核心 mechanic は人間が決める。

実践上は、AI が state machine や event system への知識アクセスを早め、定型処理の認知負荷を減らし、数日分の試作を数時間へ縮めた。その一方、チームが自力で作れる技量より複雑な system を所有し、動いていても内部を理解せず、修正や保守に再び AI を必要とする「comprehension debt」が生じた。論文の結論は、AI 支援は学習の足場にも依存の罠にもなり、本事例の 3 か月では長期的な技能形成まで判定できない、というものだ。

■ 内容分析
この論文の中核は、AI 開発の危険を「出力 code が汚い」という artifact 側だけではなく、「動く system とそれを変更する人の理解の差」として切り出した点にある。通常の technical debt は近道や品質低下が将来の保守費用を生む。一方、comprehension debt では code が見かけ上整っていても、作る速度が学ぶ速度を超えた construction-comprehension gap 自体が負債になる。そのため、lint、test coverage、動作確認だけでは検出できない。

原文にはこの差が具体的に出ている。数週間後に自分達の codebase へ戻ると、説明を AI に再依頼しないと理解できなかった。修正時は内部ロジックを理解せず system を壊し、似た問題で依頼を反復し、動く prototype が理解不足を隠した。加えて「Trust But Verify」を掲げても、検証する側の専門性が足りず、明白なエラーは捕まえられても微妙なアーキテクチャ問題を見逃した。検証を求める原則だけでは循環論法であり、「何を説明・変更できれば受け入れるか」の観測可能な基準が必要になる。

感情記録も補助的だが重要である。急速な進捗の高揚と、debug 失敗で技量差が露呈する不安が往復しており、「速く完成した」という即時 reward が将来の保守困難を見えにくくする。これは生産性評価を task 完了数や commit 数だけに縮退させない理由になる。

ただし、Jira や commit の件数は資料量を示すだけで、CIGDI による改善幅の測定値ではない。実践者と分析者が同一で、framework も開発 artifact から事後的に得られた。対照チーム、AI なし条件、debt の定量指標、長期保守の追跡はない。したがって、7 段階を採用すれば依存が減るとは言えず、観測項目と仮説を作るための記述的事例と読むべきである。

■ 自分達の環境への適用
ゲーム制作には、playable diff の受入条件を「起動する」「test が通る」の二つで終わらせず、機能的正しさと理解可能性を分けて記録する形で移植できる。重い新制度は不要で、AI が生成または大きく修正した subsystem だけに、次の 3 段階の comprehension receipt を付ける。

第 1 は即時の説明ゲートである。作業者は AI の説明文を保存するのではなく、入力、state 変化、主要依存、失敗時の退避箇所を自分の言葉で 5-10 行にする。「この条件を反転したらどの state が変わるか」という反実仮想を 1 件書けない場合は、試作には入れても保守可能な完成品とは扱わない。

第 2 は独立変更ゲートである。同じ seed と入力 trace で baseline を固定し、変数一つ、条件分岐一つ、依存一つのいずれかを AI なしで局所修正し、headless の state trace と目視の遊びを再確認する。これにより、「動作を再生できる」と「変更を所有できる」を別々に測れる。

第 3 は遅延再入ゲートである。7-14 日後に説明ログを開く前に、該当 subsystem の責務、変更入口、壊れやすい不変条件を再記述する。言えなければ debt を返済する task を起こすか、prototype-only と明示して保守前提から外す。少人数制作では debt ゼロを求めず、出荷を優先する意図的な負債と、気づかない依存を分ける。

制作サイクルの staging には、`system`、`owner_explanation`、`independent_change`、`delayed_recall`、`debt_decision`、`evidence`だけを残せばよい。これは記憶システムにも同型で適用できる。AI が作った ingest、recall、lifecycle 更新 script を「smoke test が通るか」だけでなく、どの source が正本か、状態遷移の不変条件は何か、壊れた時にどの index を再生成するかを独立に説明できるかで受け入れる。

■ メリット・デメリット
メリットは、第一に、生産性と code quality の間に隠れていた「保守主体の理解」を独立した評価対象にできること。第二に、資源制約下で AI 使用を禁止するのではなく、調査・定型化・試作と、創作的判断・検証・保守責任を分けられること。第三に、依存を抽象的な不安ではなく、数週間後の再説明、局所修正、依存箇所特定の失敗として観測できることである。

デメリットは、CIGDI 自体の有効性が比較評価されていないこと。Priority Criteria や Timeboxing が comprehension debt をどれだけ抑えたかは不明である。また、説明・変更・遅延再入を全生成物に要求すると、検証コストが試作速度を食い尽くす。さらに、AI に説明させた文を保存するだけでは理解の証拠にならず、生成文書が新たな理解負債になる。適用範囲は、保守期間が長い subsystem、失敗影響が大きい core mechanic、次回作で再利用する tooling に絞る必要がある。

■ 判定
部分採用。CIGDI の 7 段階を効果実証済みの標準プロセスとしては採用しない。一方、comprehension debt を機能的正しさと別の受入軸にし、高リスクな AI 生成 subsystem だけに即時説明・独立変更・遅延再入の小さな probe を付ける。試作を速めるために意図的に debt を持つ場合も、prototype-only と記録し、偶発的な依存と区別する。
