■ 概要
Human Head Studios が Amazon Game Studios と約18か月で制作したモバイル向けサバイバルホラー『Lost Within』の postmortem。中核チームは約20人、最大32人で、タッチ操作でも「状況は恐ろしいが、操作自体は信頼できる」体験を作ろうとした。記事の価値は成功談と失敗談が別々に並ぶことではなく、早期検証、仮実装の本番化、user test による局所修正という三段階が一つの因果として読める点にある。

制作初期、数分だけを完成品質まで磨く vertical slice は、見栄えのための近道や捨て作業を増やし、製品本体を進めないと判断した。代わりに採った proof of concept は、10分間に登場する全 system を揃えるのではなく、残りの制作判断を導ける「代表的な体験」だけを作るものだった。これはチームを勢いづけ、設計と実装の強み・弱みを早く露出させた。一方、移動、敵挙動、物体探索、扉操作など、承認後に書き直す前提だった prototype は、開発速度を優先して使われ続けた。扉の挙動を前提に level design と game design が積み上がると、置換は programmer 一人の局所作業ではなく他部門を巻き込む変更になる。残作業との比較で全面 rewrite を断念し、通常は動くが約5%で視点が扉を貫通する不具合を残した。

user test でも同じ「表面症状から依存の位置を探す」判断が現れる。追跡中の操作が苛立つという報告だけを読めば、tap 移動と virtual stick を作り直したくなる。しかし両方式は通常時の試験では高評価だった。追跡時の行動を掘ると、第一に焦った player は locker や door を正確に tap できず、近くへ移動するだけになる。第二に連打の後続入力が、すでに成功した避難行動を上書きしていた。そこで追跡中だけ対象の hit box を少し広げ、locker へ入る／door を通る入力が成立した直後だけ、短時間ほかの入力を受け付けないようにした。次の user test では操作 score が目立って上がり、苛立ちのコメントも減った。一般操作を作り直さず、stress 下で崩れる「意図から入力成立まで」の二箇所だけを補正したのである。

記事はほかにも、gameplay・物語・進行管理を三人の lead に分け、同室と定例会で整合させた体制、publisher の各専門 lead から直接 feedback を受ける構造、弱い内容を削って user test 時6〜8時間へ絞った scope 管理を成功として挙げる。反対に、物語変更が cinematic・level・game design の停止と手戻りを生み、安価なはずの静止3D cinematic が本数と演出調整を増やして最高 risk の部門になった。結論は「prototype を速く作ればよい」ではない。代表体験で早く学びつつ、仮物が他領域の前提へ変わる瞬間を管理し、feedback は全面改修の票ではなく、条件付きの故障を特定する証拠として扱う必要がある。

■ 内容分析
PoC の成功と prototype system の失敗は矛盾しない。前者は「何を学ぶために、どこまで作るか」という実験範囲の選択で、後者は実験後の asset をどう昇格・廃棄するかという lifecycle の失敗だからだ。prototype の負債はコードの汚さだけではない。level、演出、物語、save data、tool がその挙動を前提にした時点で、置換費用は依存先の数だけ増える。記事の扉は、95%の成功率でも頻繁に触る境界物なら残り5%が体験全体の信頼を傷つけること、しかも realism を守るため単純削除もできないことを示す。問題は rewrite の意思が弱かったことより、依存が増える前に本番昇格を判定する停止点がなかったことにある。

追跡時の修正は、難易度を下げる処理というより player の意図推定である。敵を弱くせず、成功入力の成立域と確定後の保護時間だけを文脈依存で変えた。スマートフォンの文字入力が候補文字の hit box を動的に変える比喩も適切で、物理座標をそのまま意図と見なさない設計になっている。重要なのは「焦ると連打する」という観察を、tap miss と成功 action の上書きという別々の故障へ分解した点だ。前者には空間的許容、後者には時間的許容を当てており、原因と介入が対応している。

ただし evidence は限定的である。記事には参加人数、端末差、hit box の拡大量、lockout 時間、score の実数、対照条件がない。次回 test の改善は有望でも、学習効果や参加者構成の差を除いた比較ではない。開発中だった usability lab では survival horror を嫌う参加者を除外できず、結果の採否に集団的な直感も使ったと明記される。発売後レビュー、4.5超の rating、恐怖を評価するコメントも製品全体の傍証であり、個別施策の因果証明ではない。

組織施策も移植条件が狭い。三 lead 制は長年一緒に働いた senior staff の信頼、同室、頻繁な連絡が前提で、責任境界だけを複製すれば決定の分裂を招く。「crunch は避けられない」として予定へ組み込む発想も、短期間に抑えたという記録以上には一般化しない。現代の制作規範として採用する根拠にはせず、scope を削って弱い内容を作らない判断だけを分離して読むべきである。

■ 自分達の環境への適用
第一の適用は、短期 playable diff を「捨てる spike」と「本番候補」に最初から分けること。コード品質で分類するのでなく、他要素が依存し始める境界を gate にする。level や敵配置が仮挙動を前提にした、調整値を複数 scene が参照した、headless replay がその API に固定された、のいずれかが起きる前に、①学習済み仮説、②残す interface、③既知の破綻条件、④置換費用、⑤rewrite／限定採用／廃棄、を短く決める。残すなら「後で直す」を続けず、production debt として owner と failure budget を明示する。

第二は stress 入力の headless probe 化である。通常 route だけでなく、追跡・弾幕・時間制限中に、目標中心から少し外す near-miss、短間隔の連打、成功直後の逆方向入力を発生させる policy を作る。補正なし／空間補正だけ／時間保護だけ／両方を同一 seed で比較し、target action 成功率、後続入力による取消率、安全状態までの時間、誤った対象への吸着率、操作を取り戻すまでの遅延を記録する。良い route の clear だけでなく、乱雑入力が万能になる bad-policy も落とす。これなら救済が意図回復なのか、単なる自動化なのかを分けられる。

第三は制作記憶への残し方である。「hit box を広げるとよい」という一般則にはせず、build、stress 条件、観測された失敗、介入、再テスト結果を一組で保存する。prototype の昇格判断にも build hash と依存先を付け、後の実装が前提を変えたら旧判断を失効させる。記事の教訓を恒久 rule に増やすより、次の入力問題で使う再現可能な probe と、依存が初めて増える時の review 項目に限定する。

最小検証は一 scene でよい。追跡状態だけ対象判定を段階的に拡張し、入力保護時間も複数値で sweep する。通常時の精密操作を変えず、stress policy の取消率が下がり、誤吸着と復帰遅延が許容範囲に留まる設定だけを採る。救済の発火回数も event log に残し、上手い player にはほぼ介入せず、破綻時だけ働いているかを確認する。

■ メリット・デメリット
メリットは、完成映像を早く作ることと代表体験を早く学ぶことを分離できる点、feedback を大改修へ直結させず条件・空間・時間の故障へ分解できる点にある。局所補正なら既に好評な操作を壊しにくく、A/B と headless replay にも落としやすい。prototype の依存 gate は、rewrite が不可能になる前に判断費用を払わせる。

デメリットは、gate と計測自体に制作時間が要ること、短期作品では負債を抱えて出す判断が合理的な場合もあることだ。動的 hit box は別対象への誤吸着、短時間 lockout は取消不能や「入力を無視された」感覚を生む。救済条件が不透明だと操作学習を乱し、強すぎれば緊張を失わせる。user test の平均改善だけでは熟練者、端末、アクセシビリティごとの悪化を隠すため、介入率と false positive を別に見る必要がある。

■ 判定
部分採用。代表体験を先に作る PoC、他領域が依存する直前の production 昇格 gate、stress 入力を空間誤差と時間的上書きに分ける診断を採る。三 lead 制と予定 crunch は前提依存が強いため採用しない。入力救済は固定 rule にせず、通常 route、stress policy、bad-policy の比較で誤吸着と操作復帰まで合格した scene にだけ限定導入する。
