■ 概要
『Pathologic 2』は、疫病が進行する open world で、多数の人物と出来事が実時間に沿って動き、プレイヤーが何もしなければ事件そのものを逃す。主人公 Haruspex の物語だけで約25万語あり、会話画面では文章へ集中できても、行動中に開く通常の quest log は物語から切り離された命令文になりやすい。この記事は、この複雑さを削るのでなく、主人公が世界を理解していく「mindmap」として可視化し、quest log、map、codex、tutorial、再開支援を一つの仕組みに統合した制作報告である。

中核は “Replace goals with ideas.”、つまり目標を思考へ置き換えることだ。会話、戦闘、item の取得、待機、建物の通過など、異なる接触から得た情報をすべて同形の node として記録する。node は客観的事実の羅列ではなく、主人公固有の言葉遣いと態度で書かれる。したがって「十匹倒せ」という外部からの命令ではなく、「この人物の話が気になる」「町では人違いが起きている」といった主人公の認識が interface になる。後者の気づきは、初日の小事件を三日目のなりすましの手掛かりへ接続でき、main / side quest の区分も弱める。

graph は関連する思考を線で結び、重要度と時間を同時に表す。古く周辺的な情報は外側、現在重要な情報は中央の大きく明るい node に置く。場所に関係する node は map marker と双方向に接続され、map から思考の文脈へ、思考から場所へ移動できる。lore、具体的行動、tutorial も同じ mental space に入り、別冊 codex のように物語から孤立しない。中断後に戻った時も、目的地だけでなく近接 node をたどることで「誰に、なぜ頼まれたか」を復元できる。

情報過多への対策として、主題に接続しない小事件は載せず、進行のたびに node を増やす代わりに同じ node を更新する。数日・story beat ごとに page を送り、過去は Act 別に保存して、現在必要な情報を一画面へ限定する。将来の帰結は破線の空 node で予告するが、先の数や接続を隠す場合もあり、構造の spoiler を案内として使うか、秘密を守るかを branch ごとに調整する。選ばなかった機会は削除せず黄色に変え、「発見できなかった空白」ではなく「参加しなかった履歴」として残す。赤を避けたのは、非参加を誤答として叱らないためである。

既存ファンを含む旧来・新規 player の大多数から好意的に受け取られ、空の図がつながりながら埋まる過程自体が達成感を生んだ、と記事は結論づける。ただし根拠は定性的 feedback である。playtest では node 通知が頻繁すぎて疲れる参加者もおり、個別箇所は直したものの、全体頻度はさらに調整できたと制作者自身が認めている。

■ 内容分析
この設計の新しさは、quest log の見た目を graph にしたことではない。game state を「やるべき task」へ変換する段階をやめ、「主人公が何を知り、どう解釈したか」という中間表現を interface の正本にした点にある。同じ node から map marker、recap、lore、tutorial を引けるため、情報種別ごとの画面を増やさずに済み、物語上の声と実用情報の出所も一致する。side story の出来事そのものではなく、そこから抽出された考えを後の本筋へ再利用するので、寄り道が単なる報酬箱でなく理解の変化になる。

一方、graph は因果関係をそのまま表示しているわけではない。線は出来事の因果、連想、人物関係、抽象的推論を混在させる。これは人間の思考らしさには効くが、自動生成や headless 判定では意味が曖昧になる。さらに破線や node 数は未来の分岐数を漏らし得る。記事は spoiler を常に欠陥とせず、期待を作る情報として意図的に見せ、秘密 branch では接続を隠す。つまり graph 化よりも、どの構造をいつ開示するかという authored reveal policy が品質を決める。

最大の制作費は node の選別と文章である。全 event を載せれば通知疲れと clutter が起き、減らしすぎれば再開支援が壊れる。同じ node を更新するにも、旧文面をいつ置換し、履歴へ何を残すかを branch ごとに設計しなければならない。しかも node は主人公の voice を保つ必要があるため、event log から機械的に生成した要約では代替しにくい。writer が story map を描く自己検査には有効だが、線が分断されていることが直ちに脚本の欠陥とは限らない。孤立、誤解、無関係さを意図した物語まで接続数で評価すると均質化する。

評価の限界も明確で、好意的 reception の人数、比較対象、質問文、play time、復帰率は示されない。従来型 log に対して理解度や再開成功率が上がったとは定量的に証明されていない。示されているのは、実製品へ導入され、旧作ファンにも大きく拒絶されず、制作者が playtest で通知疲れを観測したという design evidence である。発想の採用根拠にはなるが、効果量の根拠にはならない。

■ 自分達の環境への適用
最初から全面的な graph UI を作らず、分岐と時限 event を持つ小規模 prototype で probe する。正本は event の完了一覧ではなく、`thought_id / protagonist_text / source_event / related_thoughts / map_anchor / reveal_state / act / salience / missed_reason` を持つ思考 record とする。画面には現在 Act の高 salience node だけを出し、細かな event は既存 node の更新へ畳む。map marker、再開 recap、tutorial hint は別文章を持たず、この record から派生させる。

比較条件は従来の時系列 log と mindmap の二つを用意する。同じ scenario を途中で中断し、翌日相当の再開時に、現在の目的、関係人物、理由、失効した機会を説明できるか測る。指標は文脈再生の正答、目的地到達、再開後最初の意味ある行動までの時間、誤った未完了認識、画面滞在時間、node 通知を閉じた回数とする。headless test では reveal 条件、hidden branch の漏洩、missed node の色と理由、Act 移行後の current page 上限を deterministic に検証する。

通知頻度は固定値で決めず、story beat ごとに集約する。新情報のたびに popup を出さず、即時の行動判断が必要な node だけ通知し、それ以外は節目でまとめる。再開 recap は直近 node の羅列ではなく、現在中央にある node と、その一段隣の理由を優先する。これなら「何をするか」だけでなく「なぜそう思ったか」を短く戻せる。writer 向けには実装前の story graph を作り、孤立部分を欠陥として自動修正せず、意図的孤立か接続漏れかを review する診断図として使う。

■ メリット・デメリット
メリットは、物語理解、主人公表現、map 導線、tutorial、再開支援を同じ情報構造から作れることだ。命令文を減らして player の解釈余地を守り、寄り道から得た知識を本筋へ戻せる。見逃しを削除せず中立色で残すことで、時間制限のある game でも「全部回収できなかった＝失敗」という圧力を弱められる。空の graph が埋まること自体も進行 feedback になる。

デメリットは、node selection、voice を持つ文章、reveal 制御、branch ごとの更新に高い authoring cost がかかることだ。接続線の意味が混在すると読解も自動検査も難しく、未来 node は分岐や twist を漏らす。統合 UI が一画面へ情報を集めすぎれば、記事自身が報告した通知疲れを再生産する。定量比較がないため、複雑な graph が単純な recap より本当に復帰を助けるかは別途測る必要がある。簡潔な筋書きや、目的の即読性を最優先する action game へそのまま移すと過剰設計になる。

■ 判定
部分採用。全面 UI ではなく、思考 record を map、recap、時限 event 履歴の共通中間表現にする点と、未参加を誤答色にしない表現を小規模 probe へ入れる。従来 log との中断再開比較で文脈再生と初動が改善し、通知疲れと spoiler 漏洩が許容範囲に収まる場合だけ graph 表示を広げる。効果を裏づける定量値は記事にないため、構造の魅力だけで全 prototype の標準にはしない。
