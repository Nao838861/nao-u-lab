■ 概要
『A Broken Time Machine』は、GMTK Game Jam 2026 の4日間のうち最初の2日を企画の迷走で使った作者が、残り約2日で完成まで持っていった PuzzleScript 製 Sokoban 系パズルの postmortem である。作者は前年の応募作を締切時に遊べない状態にして失格しており、今回は「面白そうだが4日では作れない新案」と「作れるが自分が惹かれない案」の間で停滞した。そこで完全な新 mechanic の発明を諦め、過去作『Time Juice』の「限られた手数で必要な物体を壊れたタイムマシンへ運ぶ」という既知の核を、残り日数で実装可能な Sokoban へ移植した。

制作初日は PuzzleScript で基本規則を組み、方眼紙上で level 案を作った。規則が既知だったため実装と level design の不確実性は小さく、短い level 列を早期に得られた。二日目はそのまま level を増やさず、PuzzleScript Next へ移行し、sprite の高解像度化と palette 探索を始めたため数時間を消費した。しかし Pancelor の Aseprite Puzzlescript Export を見つけ、sprite 変換の反復を高速化して外観を確定し、締切直前に最後の数 level を追加して提出可能な状態へ到達した。

提出直後、別 PC で動かして初めて、制作機の高い monitor gamma では見えていた黒い pit が wall と判別しにくいことが分かった。jam 中は修正できなかった。実際の feedback は視認性ではなく「最初は規則を理解しにくいが、mechanic と level design は良い」というものが中心だった。最終成績は enjoyment 上位約5%、creativity 上位約6%、他部門は上位3分の1程度。評価分布はおよそ半分が positive、3分の1が neutral、残りが negative だった。作者は、パズルを解こうと粘る層には報酬があった一方、最初の数面で目的を掴めない層を即座に遠ざけたと読む。一般的な jam audience には、規則を試したくなる即時の誘因と tutorialization が必要だと結論づけた。投票終了後は level を変えず、pit の視認性を上げる sprite 修正だけを行っている。

■ 内容分析
この事例の核は、短期制作の成功と初回体験の失敗が同じ判断列から生じていることだ。既知 mechanic の再利用、規則の早期実装、方眼紙での level 設計は「そもそも完成しない」危険を下げた。前年の失格を踏まえれば、独創性の最大化より playable な縦切りを先に確保したのは合理的である。creativity 上位約6%という結果も、既存 mechanic の再利用が独創性の放棄と同義ではなく、制約、主題、level 構成の組合せで新鮮さを作れることを示唆する。

一方で、作者にとって既知の規則を再利用したため、初見者がどの情報を持っていないかが見えにくくなった可能性がある。実装できること、作者が解けること、パズル好きが粘れば理解できること、jam の広い参加者が最初の数分で目的を把握できることは別の品質軸である。mechanic と後半 level が好評でも、入口で離脱した人は詳細な feedback を残さない。約半数 positive という分布と「規則が最初は難しい」というコメントは入口問題と整合するが、離脱率、level 別到達率、理解までの手数は測られていない。したがって tutorial 不足が negative 評価を生んだという読みは有力でも、実証済みの因果ではない。

視認性についても同様で、別 PC では再現したが、投票者から直接指摘はなかった。作者自身が「黙って評価を押し下げたかもしれない」と推測している段階である。ただし、これは問題が軽い証拠ではない。contrast 不良はプレイヤーに「表示環境差」ではなく「盤面が読みにくい」「規則が分からない」と知覚され、具体的な bug report にならないことがある。pit と wall は単なる装飾差ではなく、移動可能性を決める gameplay state なので、色味ではなく形、輪郭、明度差でも冗長に符号化すべきだった。

二日目の art 作業も単純な失敗ではない。PuzzleScript Next への移行と sprite 改善は最終的な魅力に寄与した可能性があるが、締切前に新 tool を探しながら pipeline を変えたため、level 数、tutorial、別環境確認へ使える時間を圧迫した。export tool の発見は局所的な反復速度を回復したものの、「締切前に pipeline を変えてよいか」という上位判断までは解決しない。記事が示すのは art を後回しにせよという一般則ではなく、残り時間ごとに playable build、入口理解、表示互換、content 量のどれが未達かを比較し、pipeline 投資の回収可能時間を見積もる必要である。

■ 自分達の環境への適用
短期 prototype では、開始時に mechanic を「新規発明」「既存 atom / 過去作から再利用」「再利用して一要素だけ反転」に分け、残り時間が短い時は後二者を明示的な候補にする。ただし再利用の目的は思考停止ではなく、実装不確実性を減らして level、敵配置、操作感など player-facing な変奏へ時間を移すことに置く。制作記録には、再利用した核、今回変えた制約、節約できた時間、入口で新たに必要になった説明を一組で残す。これなら「前回作れたから今回も分かるはず」という作者知識の持ち越しを検出できる。

playable gate は締切直前の完成確認だけでなく、最初の3面に限定した理解 probe を入れる。説明文を読んだかではなく、各面の目的を何手目で推定したか、無効操作の連続数、restart 数、同じ失敗の反復、3面目への到達率を記録する。headless agent は全 level の可解性、最短手数、deadlock、規則の一貫性を検査できるが、「盤面を見て何を試したくなるか」や contrast は保証できない。したがって solver の完走と、初見 trace の理解率を別 gate にする。agent が内部 state を直接読める評価だけでは tutorial を過大評価するため、観測を画面相当の情報へ制限した条件も用意する。

視認性には、提出候補 build から代表 frame を自動取得し、少なくとも高低2段階の gamma、grayscale、縮小表示で比較する smoke test を加える。重要 tile は隣接色との輝度差だけでなく、silhouette、outline、texture のいずれかでも区別する。pixel-level の contrast 指標は候補抽出には使えるが、人間の意味上の混同までは判定できないため、最終確認では「wall、pit、goal、可動物を一瞬で言い分けられるか」を見る。これは大規模な恒久 rule ではなく、次の短期パズル1本で試す可逆な checklist とする。

制作サイクルには三つの時点を置く。残り50%時点で playable core と最低1面、残り25%時点で最初の3面と tutorial trace、提出前に別表示条件と clean environment で build を確認する。新 engine や asset pipeline への移行は、予想節約時間が導入・故障対応時間を上回り、既存 playable build に戻せる時だけ許容する。評価後は全体 score だけでなく、理解前離脱、理解後満足、視認性の三仮説を分けて記録する。今回のように patch 後の再評価がない場合は「修正済み」ではなく「修正したが効果未測定」として残す。

■ メリット・デメリット
メリットは、既知 mechanic の再利用を妥協ではなく schedule risk の制御として扱えること、solver が測る論理的完成度と初見者が感じる入口品質を分離できること、別 PC で偶然見つかった問題を提出前の再現可能な確認へ変えられることにある。方眼紙による level 設計も engine 上の装飾作業から puzzle structure を切り離し、短い反復で複数案を比較する方法として採用しやすい。

デメリットは、この一本の自己報告から「既存 mechanic なら高評価」「tutorial を増やせば成績が上がる」と一般化できないことだ。順位は応募母集団、投票数、作品露出の影響を受け、評価分布も level 別行動を示さない。視認性が投票へ与えた影響は作者の推測で、sprite 修正後の A/B 比較もない。理解 probe や multi-gamma screenshot を毎回義務化すると、小さな jam の速度を逆に奪う。検査は入口3面と重要 tile に絞り、失敗が再現した時だけ拡張すべきである。

■ 判定
部分採用。既知 mechanic の再利用、紙上での level 設計、入口3面の理解 trace、別表示条件での contrast smoke test を、次の短期パズル prototype の限定 probe として使う。上位成績や作者の推測は成功則にせず、solver 完走と初見理解を別々に測る。新 pipeline 導入には回収時間と rollback 条件を付け、probe が制作時間を圧迫するなら範囲を縮める。
