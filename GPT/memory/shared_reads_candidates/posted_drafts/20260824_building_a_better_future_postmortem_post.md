■ 概要
RPG Maker VX Ace 製の仕事シミュレーション『Building A Better Future』について、作者が最終更新に近い v1.2 で公開した短い postmortem。題材は、EcoCredits で市民を選別する制度の職員として囚人を判定する仕事である。作者は『The Sims』『Papers, Please』、現実の社会情勢に加え、『Spec Ops: The Line』を参照した。ただし着想の核は、道徳的に重い物語を見せること自体ではない。作者は『Spec Ops』を「残酷な現実を示す優れた作品だが、player が仕事を失敗したり、別のやり方で制度に関与したりする余地は乏しい」と捉え、自作では規則への服従だけを正解にしないことを狙った。模範職員として一日中働く、仕事を避ける、全員を裏切り者と判定する、誰も裏切り者にしない、ひどい仕事をしても制度から報酬を得る、といった互いに異なる態度を許し、行政組織の責任の曖昧さを mechanics にしようとした。

しかし公開後の実績は 14 downloads、comment なしで、友人 3 人から得た feedback と作者自身の振り返りでは、意図した自由度より入力負荷と単調さが前面に出た。囚人一人ごとに 3 個の単語・topic を text box へ入力させ、携帯電話や social district にも用途の薄い option を多数置いたため、player は意味のある方針を選ぶより、UI を埋める作業を強く要求された。文章も定型的で感情に乏しいまま長く、冷たい制度を表現するなら、長い無機質な会話ではなく文章量そのものを減らすべきだったと作者は認めている。さらに、仕事部分へ比重を置きすぎ、家の upgrade、自転車や車の購入といった生活側の進展を十分に育てられなかった。

作者が振り返って提示した代替案は具体的である。初日は「EcoCredits が基準未満の人を一定数選ぶ」という quota だけを置き、その後、一日ごとに mechanic を一つずつ追加し、最終的に全要素へ到達させる。これは単なる tutorial の追加ではなく、player が最初に制度の目的と一日の閉じ方を理解してから、判断材料と逸脱手段を段階的に増やす構成への変更である。結論は、player experimentation と規則を外れる余地には手応えがあったが、それを支える仕事 loop、文章、UI、生活報酬の設計をまとめ切れず、「自分には大きな学びだったが、他の人にはひどいゲームだった」という厳しい自己評価で終わる。後続の v1.3 では RPG Maker の入力環境を plug-in で改善した形跡はあるが、上記の構造変更を施した比較評価はまだ示されていない。

■ 内容分析
この記事で最も使えるのは、「選択肢が多いこと」と「agency があること」を分離できる点だ。3 語を自由入力できる仕組みは、入力空間だけを見れば広い。しかし、入力ごとの差が状態、報酬、他者の反応、後日の制度運用として返らなければ、player が感じるのは自由ではなく記入負担である。反対に、全員を告発する、誰も告発しない、quota だけ満たす、仕事を回避する、という少数の方針でも、それぞれが別の生活・評価・物語結果へつながれば agency は強い。自由度の単位を option 数や text box 数ではなく、「結果まで追跡可能な方針の数」として数えるべきだという示唆がある。

もう一つ重要なのは、progressive disclosure が操作説明だけでなく意味の学習順序を作ることだ。初日の単純な quota は、誰を選ぶか、選ぶと何が起きるか、一日を終えると何が返るか、という最小 loop を可視化する。二日目以降に属性、例外規則、監視、私生活上の報酬を一つずつ足せば、新 mechanic が既知の loop をどう歪めるかを player が比較できる。全要素を最初から並べた場合には「どれが効いたか」が読めないが、一日一要素なら、制度が複雑化する過程そのものを物語にもできる。

文章の失敗も題材固有である。官僚制の冷たさを出すための「定型的で感情のない文」が長文化すると、意図した不快さと単なる退屈を区別できない。冷たい文体を残すなら、短い様式文、判定結果の即時表示、後日の具体的な影響を組み合わせ、読む量ではなく結果の非情さで冷たさを作る必要がある。また、家や移動手段の upgrade が弱かったという反省は、仕事の判断を生活の欲望へ接続できなかったことを示す。制度に従う誘惑を描くには、給与という数値だけでなく、その金で得られる生活変化を見せる方が、服従・逸脱の cost を実感しやすい。

ただし評価の限界は大きい。14 downloads に対して公開 comment はなく、質的 feedback は友人 3 人だけで、play time、離脱地点、各 option の利用率、異なる方針の到達率は示されていない。「現代の player には入力が多すぎる」「popular な作品だけを遊ぶ人には嫌われる」という説明も測定結果ではなく作者の解釈である。さらに、提示された quota 方式は実装後に比較されたものではない。したがって本記事は、段階導入が有効だという実証ではなく、失敗した build から検証可能な次案を抽出した記録として読むのが妥当である。

■ 自分達の環境への適用
我々の prototype では、「自由度を入れた」という実装報告を option 数で済ませず、3 日分の縦切りで検証する。Day 1 は一日の quota、対象選択、確定、報酬だけにする。Day 2 で判断材料を一つ、Day 3 で規則から外れる手段を一つ追加する。各日について、初回判断までの秒数、必須入力回数、説明を開き直した回数、同じ状態から異なる結果へ出た branch 数、一日を完了できた割合を記録する。自由入力を採用する場合は最初から全員へ 3 項目を書かせず、一件だけ optional にし、定型選択と比べて結果差を生むかを見る。

headless 評価では面白さを代行させず、strict（規則通り）、maximal accusation（最大限告発）、avoidant（最低限しか働かない）という 3 policy を同じ seed で走らせる。最終 state、所持資産、NPC 状態、職場評価がほぼ同じなら、UI 上の選択肢が多くても実質的 agency は薄い。逆に差が出る場合も、一手だけの数値差ではなく、翌日以降に読める consequence が保持されるかを確認する。これなら「選べる」と「選んだ結果が残る」を機械的に切り分けられる。

人間の playtest では、終了後に「何を目指していたか」「別の方針を取れたと思うか」「どの入力が判断で、どれが事務作業に感じたか」を聞く。作者が想定した方針名を質問文で先に教えず、player 自身の言葉で区別できるかを見る。制作サイクルの記憶には、記事から直接「一日一 mechanic」を恒久ルール化せず、仮説、変更した build、計測値、観察された失敗、次の判断を一組の receipt として残す。改善版の結果がなければ成功 lesson に昇格させない。

■ メリット・デメリット
メリットは、独立開発の失敗を抽象的な反省で終わらせず、3 語入力、用途の薄い携帯電話 option、長い無機質な文章、仕事偏重、quota からの日次導入という実装粒度まで落としていることだ。agency、onboarding、文章量、生活報酬が同じ loop 上で干渉する様子も見える。小さな prototype で再現可能な検証案へ変換しやすい。

デメリットは、母数が極小で telemetry も改善前後比較もなく、問題の優先順位が確定していないことだ。入力 UI を直せば自由入力が機能する可能性も、仕事 loop を単純化すると作品固有の異様さが失われる可能性も残る。段階導入は理解を助けても、各 mechanic 自体が退屈なら救済しない。また、生活 upgrade を強化すると、制度批判が単なる効率最適化へ吸収される危険がある。

■ 判定
部分採用。採用するのは、agency を結果まで分岐する方針で測ること、core loop を先に成立させて mechanic を一日単位で足すこと、自由入力の負荷と結果差を別々に測ること。採用しないのは、3 人の反応から player 一般の嗜好を推定することと、未検証の quota 案を完成形として扱うこと。次の制度 simulation で 3 日縦切りと 3 policy replay を行い、差が持続した時だけ lesson 化する。
