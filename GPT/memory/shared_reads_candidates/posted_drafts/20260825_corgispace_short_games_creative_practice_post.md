■ 概要
Game Developer 編集長 Danielle Riendeau が、Finji の Adam Saltsman による GDC 2026 講演を、自身も短編ゲームを作り教える立場から読み解いた記事。背景には、大量解雇やスタジオ閉鎖が続き、熟練者さえ創作を続けにくい業界で「好きな分野が沈んで見える時、どう作り続けるか」という問題がある。Saltsman の答え CorgiSpace は、短いゲームを速く量産する生産術ではない。最初から「脚が短い」作品を選び、制作が消耗ではなく発見と回復になる範囲へ意図的に閉じ込める創作実践である。

Saltsman は限られた余暇で約1年かけ、PICO-8 による13本の小作品を完成させた。各作は1時間未満で十分探索できる規模で、Dust Bunny の掃除パズル、Mole Mole、Dino Sort など、単純な動詞と奇妙な組み合わせを核にする。実践の原則は三つある。第一は「easy, but not obvious」。難しい実装を達成目標にせず、手持ちの道具では容易だが、既成ジャンルの定石からは自動的に出てこない選択を探す。第二は idea と formula の分離。idea は作り始めた理由や熱源であり、formula は prototype、実装、design document など、その idea を一時的に写した型にすぎない。初期実装が弱くても idea まで捨てず、formula を可変に保つ。第三は「game design is about noticing things」。計画の再現より、実際に動かした時に起きた挙動、違和感、笑い、プレイヤーの発見を見つけ、作品の中心へ育てる。

「道具の木目に沿う」ことが三原則を接続する。PICO-8 の解像度、色数、容量、入力、tilemap といった制約に逆らって大規模機能を足すのでなく、その環境で描いて即座に遊べるものを設計材料にする。Dust Bunny も、家の掃除中に生まれた着想を壮大な企画へ膨らませず、小さな掃除動作と盤面の発見へ落とした例として語られる。結論は、小さいだけでは足りず、容易さの中に非自明な発見を残すこと、初期の型を着想そのものと誤認しないこと、制作者自身が作る過程を楽しめることが、完走と学習を両立させるというものだ。

■ 内容分析
重要なのは scope を「機能数」だけでなく「探索可能な設計空間」として扱う点だ。普通の小規模化は、予定した大作から機能を削り、縮小版を正確に完成させようとする。CorgiSpace は逆に、道具が安く返せる反応だけで探索空間を作り、そこで見つかった非自明なものを作品にする。easy は品質を下げる許可ではなく、一手の実装費を下げて観察回数を増やす条件である。not obvious がないと単なる既視感のある練習作になり、easy がないと発見前に実装負債で止まる。この二条件が対になっている。

idea / formula の分離も有効だ。「掃除に感じる奇妙な快感」のような動機と、「倉庫番型の盤面」「30面構成」といった現時点の実装案を同じ仕様書に固定すると、prototype が面白くない時に着想まで失敗扱いされる。formula を仮説と見なせば、入力、空間表現、勝利条件を交換しながら idea を再検査できる。一方で、idea は常に良いという表現を文字通り採るべきではない。熱源として本物でも、遊びとして伝達できない、倫理・権利・市場条件に合わない、何度 formula を替えても観察可能な差が出ない idea はある。守るのは着想への執着ではなく、最初の実装失敗から結論を急がない区別である。

評価根拠の強さも限定して読む必要がある。記事が示すのは、1年分の完成作、製品化されたコレクション、制作日誌、Saltsman が「消耗より回復になった」とする自己報告、そして Riendeau が自分の短編制作経験と照合して得た納得である。CorgiJam に29件が集まったことは原則の伝達可能性を補うが、従来手法より完走率、独創性、疲労を改善した比較実験ではない。選択バイアスもあり、PICO-8 と熟練制作者の組み合わせを一般化できない。したがって、この記事は効果量を証明する研究ではなく、完成物を伴う設計仮説として価値がある。

失敗条件は三つある。第一に、「難しいからやらない」を、作品の核に必要な問題から逃げる言い訳にすること。第二に、偶発挙動なら何でも発見と呼び、プレイヤーへ読める形に編集しないこと。第三に、短さを目的化して、学習曲線や感情的な蓄積に必要な長さまで削ることだ。短い脚は全ゲームの理想ではなく、発見を一作品として閉じられる時だけ機能する。

■ 自分達の環境への適用
適用先は、短い playable diff を次の判断へ接続する制作サイクルである。1本の prototype に `idea_core`、`formula_v0`、`grain_constraints`、`noticed_behavior`、`next_cut` の五項目を置く。idea_core には「なぜ触りたいか」を一文、formula_v0 には現在の操作・ルール・表現仮説、grain_constraints には既存 engine、asset、headless harness が安く実現できる範囲を書く。最初の playable 後は仕様一致だけでなく、予定外に繰り返した操作、状態遷移の偏り、失敗なのに笑える挙動、説明なしで読めた規則を noticed_behavior として原文付きで残す。

次の一手は、機能追加ではなく「観察された核を強める最小変更」に限定する。たとえば敵種を増やす前に、面白かった押し合いが多く起きる配置を1面作る。headless 評価ではクリア率、入力列長、到達状態、死因、seed 間分散を取り、formula が壊れていないかを見る。ただし非自明さや制作者の回復感は自動指標だけでは測れないため、短い replay と操作ログを人が見て、`予想外だが再現可能`、`プレイヤーが利用できる`、`追加説明なしに伝わる` の三条件で発見を判定する。

probe は1本、二制作サイクルに絞る。各サイクル終了時に、実装時間、遊んだ回数、見つかった挙動、残した変更、削った変更、制作前後の主観的エネルギーを記録する。合格条件は、予定機能を増やさず playable の固有性が上がり、headless の基本健全性を保ち、次に試す一手が観察から導けること。不合格条件は、非自明さを説明文で後付けする、formula を替えても核が現れない、短編なのに補助 system が増殖すること。記憶上も design intent、implementation assumption、runtime observation を別 atom にし、「初期実装の失敗＝idea の否定」という誤った学習を防ぐ。

■ メリット・デメリット
メリットは、完成規模を増やさず試行回数と発見密度を上げられること、初期仕様への執着を弱められること、道具選びと scope 判断を一つの基準で扱えることだ。小作品を完成単位にするため、未完 prototype の山より振り返り可能な証拠が残る。制作エネルギーも評価対象に含めるので、技術的に成功しても継続不能な進め方を早く止められる。

デメリットは、熟練者の暗黙知を「気づく力」として要求すること、発見の質を headless 指標だけで自動判定できないこと、容易さが技術負債や課題回避を正当化し得ることだ。PICO-8 の強い制約は探索を助けるが、既存 project の toolchain では木目が曖昧な場合もある。また、物語の長期蓄積、複雑な戦略、運用型設計には短編の成功条件をそのまま移植できない。

■ 判定
部分採用。idea と formula の分離、道具の木目、観察から次の最小変更を決める三点を、1本の短い prototype で試す。CorgiSpace を全制作の標準や「難しい作業を避ける」規則にはしない。完成率だけでなく、固有挙動の再現性、scope 増加、制作エネルギーを同時に記録し、二サイクル後に継続可否を決める。
