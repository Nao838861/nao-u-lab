■ 概要
この論文は、企画初期の短いゲーム案を、そのまま開発へ渡せるほど具体化する際に、一般家庭や小規模スタジオの GPU で動く中規模 LLM がレビュー役になれるかを調べた研究である。クラウド型モデルへの企画情報の送信には、知的財産、プライバシー、継続利用性の懸念がある。そこで著者らは、まず既存のゲームデザイン／レベルデザイン文献から、ゲーム案を点検する10観点を整理した。Player Experience、Theme、Gameplay、Place、Unique Features、Story and Narrative、Goals / Challenge / Rewards、Art Direction、Purpose、Opportunities and Risks である。Gameplay なら3〜5個の動詞と典型的な30秒、Unique Features なら既存作品との差、Risks なら発生可能性と軽減策まで求めるため、単なる項目名の列挙ではなく、実装前の不足を露出させる枠組みになっている。

比較対象は LLaMA 3.1 8B Instruct、Qwen 2.5 7B Instruct、DeepSeek-R1-Distill-Llama 8B。GPT-4o で15個のゲーム案を生成し、各案の全文版と要約版を用意して計30入力とした。各モデルを各入力に一度だけ実行し、計90出力を、10観点に沿う形式、全観点の網羅、文章の明瞭性で研究者2名が評価した。LLaMA と Qwen は反復ループや出力打ち切りのため形式適合が各1/30だった。DeepSeek-R1 は形式30/30、網羅26/30、明瞭27/30で、ループはなかった一方、3/30で文中に中国語文字が混ざった。詳細分析では、入力に不足が多いほど重点的な提案を返す傾向、入力にない場所などを事実のように補う例、具体的で実行可能な回答と一般論に留まる回答のばらつきが確認された。

この結果から、著者らは DeepSeek-R1 を組み込んだ Streamlit 製 prototype「SPARC」を作った。基準環境は RTX 3080 Ti、12GB GDDR6X、Ubuntu 22.04 で、応答時間は約1〜2分。ただし三モデル比較自体は時間短縮のため2基の NVIDIA A40 で実行している。実装開始前の6チーム、学生10名が各チームの案を一度レビューした pilot study では、回答品質は10人中8人が4または5、役立ち度は4または5が4人だった。提案を案へ取り込みそうかには `Yes` が20%、残り80%は `Maybe`。将来また使いたいかは `Yes` 80%、`Maybe` 20%だった。これは実際の採用率を追跡した結果ではなく、利用直後の採用意向である。自由記述では4人が深さ不足、3人が全10観点一括ではなく個別観点への集中を求め、入力にない art style を読み込んだ誤解も報告された。

著者らの結論は、中規模ローカル LLM は初期案の構造化に使えるが、提案を増やすだけでは不十分というものだ。将来形として、案の代筆や全面改稿から離れ、不明瞭・未発達な観点を特定し、用意した質問群から設計者の省察を促す質問を返す方式を提案している。

■ 内容分析
この研究の価値は「8B model がゲームを設計できた」ことではなく、粗い案をレビュー可能な単位へ分解したことにある。10観点は完成した GDD の schema ではない。Player Experience と Purpose は狙いを、Gameplay と Goals / Challenge / Rewards は実際の行為と進行を、Place と Art Direction は表現を、Risks は制作可能性を問う。これらを同じ文章上に並べることで、「雰囲気はあるが典型的な30秒がない」「物語はあるがプレイヤーの能動詞がない」といった、実装前に高くつく欠落を発見しやすい。

一方、モデル比較の数値は狭く読む必要がある。各入力一回、評価者2名、30入力という小規模な定性的比較で、評価者は10観点の定義にも深く関与している。評価者間一致度、blind 化、推論設定、量子化条件、統計的不確実性は報告されていない。テスト案も GPT-4o 由来で、著者自身が巨大企画や「複数の次元」といった trope への偏りを認めている。LLaMA と Qwen の形式崩れは当該 prompt／serving 条件での失敗であり、モデル系列一般の能力差とは言えない。DeepSeek-R1 の30/30も内容の正しさではなく形式適合であり、具体性や hallucination は別問題として残る。

pilot study も、10人を独立した10案として扱えない。入力は6チーム分で、同じチームのメンバーは同一出力を見て回答しており、案の成熟度も統制されていない。さらに「使いたい」80%に対し、提案を取り込む回答は確定的な `Yes` が20%しかない。ここには、読みやすさ、珍しさ、ローカル実行への好感と、設計判断を変えるほどの有用性の間に距離がある。品質評価を採用行動の代理にしてはいけない、という点が最も実務的な結果である。

それでも研究の自己修正は妥当だ。全10観点を一度に生成させると、既に十分な箇所の要約が token と注意を消費し、弱い箇所の質問が浅くなる。加えて、モデルが提案者になると、補完と捏造の境界が曖昧になる。入力の欠落を機械的に検出し、対象を一観点へ絞り、設計者へ質問を返すなら、創作上の所有権を人間側に残したままレビューの網羅性を利用できる。

■ 自分達の環境への適用
ゲーム制作へは、10観点を新しい長大な仕様書にせず、prototype 着手前の小さな review probe として使う。対象案から、プレイヤーが繰り返す動詞、典型的な30秒、短期目標、失敗と回復、独自性、表現上の制約、最大の制作リスクを抽出する。空欄だけでなく、「静かな探索体験」と「常時高密度戦闘」のような観点間の矛盾も候補にする。LLM には完成案を書かせず、不足または矛盾が強い上位2観点について一度に一問だけ質問させる。回答は設計者が決め、元案と変更理由を記録する。

検証は最近のゲーム案3件程度で、無レビュー、10観点一括 feedback、対象を絞った質問方式を比較する。見る指標は文章の長さや好感度ではなく、最初の playable build までに未決定事項が何件残ったか、実装後に覆った設計判断、質問から採用した変更、不要だった提案、prototype の build／headless test／短い実プレイで発見した矛盾である。headless 評価には、テーマや楽しさを直接判定させない。たとえば「典型的な30秒」を操作列と state transition に落とし、主行動が実際に実行可能か、報酬と失敗状態が到達可能かを検査する。意図と実行 evidence を結び、文章の網羅度を遊びの成立と混同しない。

記憶システムでは、10観点そのものを恒久 schema に増やさず、probe の入力、質問、回答、実装差分、評価結果を一つの candidate／atom に束ねる。質問が設計の手戻りを減らしたかを後から追えなければ、便利そうな checklist が増えただけと判定する。モデル名や 12GB という条件は固定的な推奨値にせず、local inference を選ぶ際の再現 metadata として model revision、quantization、VRAM、latency、prompt を保存する。

■ メリット・デメリット
メリットは、曖昧な企画レビューに共通語彙を与え、実装後に高くつく欠落を早く見つけられること、ローカル実行によって未公開案を外部へ送らずに済むこと、モデルに案を所有させず設計者の判断を引き出す形へ変えられることにある。10観点は project に応じて削る前提なので、小さな prototype にも調整しやすい。

デメリットは、網羅を目的化すると凡庸で説明過多な案を作りやすいこと、LLM が入力外の設定を自然に補って事実と提案を混ぜること、全観点一括では浅い feedback と長い待ち時間が増えることだ。研究上も、合成データ、小標本、非独立な参加者、自己申告、実装後の追跡なしという制約がある。2025年時点の三モデルの順位や12GB環境の速度を、現在の model／runtime へそのまま外挿できない。最大の危険は、形式30/30や再利用意向80%を、設計改善の証拠と読み替えることである。

■ 判定
部分採用。10観点を企画完成度の採点表にはせず、不足と矛盾を見つけて設計者へ一問ずつ返す review probe として使う。採用条件は、文章評価ではなく playable までの未決定事項、手戻り、採用判断、実行 evidence が改善すること。モデルによる全面改稿、全10観点の一括出力、特定モデルの固定採用は見送る。
