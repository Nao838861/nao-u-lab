■ 概要
『That’s BU//S#!T』は、初見殺しの罠を笑いにする HTML5 アクションゲームで、Evil Game Jam 4位と Most Creative を得た作品である。中心となる仕組みは、開始前に Easy / Normal を選ぶ通常の難易度設定ではなく、罠で死亡した後、その罠だけをプレイヤー自身が段階的に弱体化できることだ。作者は当初「全てを消して空虚な勝利を渡すゲーム」になると予想していた。しかし live play や友人の playtest では、弱体化を一度も使わない人と、十分苦しんだ後に必要な箇所だけ使う人が多く、後続の level や罠への興味は失われなかった。結果として作者の予想以上に “Self customizable difficulty” として機能した、という postmortem である。

jam 後の v1.2.2 は、この着想を「選べるだけ」から「選んだ効果が理解できる」仕様へ修正している。sawblade は jam 版では、速度を25%ずつ二回低下、サイズ50%化、停止、削除という五段階だった。追加 playtest では最初の25%低下がほぼ知覚されず、停止すれば十分簡単なので削除まで別段階にする意味も薄かった。そこで速度50%化、サイズ50%化、削除の三段階へ圧縮した。

横から飛び出す SuckerPunch は、最初の弱体化で不透明なアニメーション付き警告記号と warning panel を即時追加し、二回目で削除する形に変更した。以前は短時間しか見えない警告を二度経て三度目に削除しており、冗談の意味も効果も伝わりにくかったためである。選択可能範囲も本体の一点ではなく移動経路全体へ広げた。さらに spike を消すと穴が非致死になる一方、高い壁の中から出られない softlock が生じたため ledge を追加した。上級者向けには、通常は勝利後まで隠す death count と、pause・死亡・quick reset 中も進む speedrun timer を表示する任意の Tryhard mode を別に置いた。結論は、局所的な救済は挑戦を奪うとは限らないが、効果の知覚、選択操作、level topology、respawn flow まで一体で設計し直す必要がある、というものだ。

■ 内容分析
重要なのは、難易度を固定 preset ではなく「失敗した対象への局所編集権」として渡した点である。死亡後ならプレイヤーは自分が何に負けたかを知っており、救済の対象と理由が一致する。全体を Easy に落とす時のように、既に攻略できた区間や次の未知の罠まで弱くしない。しかも opt-in なので、上級者は同じ ruleset のまま挑戦を続けられる。これは動的難易度調整のような見えない介入ではなく、プレイヤーが「ここだけは下げる」と決める明示的な契約である。

五段階から三段階への変更は、調整量を細かくするほど親切になるわけではないことを示す。25%低下が見えなければ、選択コストを払ったのにゲームが応答しなかったように感じる。停止と削除が攻略上ほぼ同じなら、段階数は意味のある選択肢でなく UI の摩擦になる。段階は数値上等間隔である必要はなく、「動きが遅くなる」「当たり判定が小さくなる」「存在しなくなる」のように、見た目、攻略法、意味が区別できることが重要だ。

SuckerPunch の変更も同じ原則を別角度から示す。警告追加は単純な damage 低下ではなく、隠れた情報を可視化して反応可能性を上げる弱体化である。罠の punchline は残しながら、次回は学習して避けられる。移動経路全体をクリック可能にしたことは、概念上の対象と UI hit area を一致させる修正であり、難易度選択そのものが操作精度 test になる矛盾を避けている。

一方、これは厳密な効果検証ではない。人数、死亡回数、弱体化利用率、離脱率、clear率、各版の比較値は報告されず、作者が live play を数回観察し、友人を追加で遊ばせた質的記録である。jam の客層、短い一発ネタ、Cat Mario 型の「理不尽さを笑う」期待も利用行動に影響する。作者自身も standalone project には向かないと見ている。したがって「選択式救済は常に自尊心を守る」と一般化する材料ではない。価値は成功率の証明より、観察した違和感を sawblade、SuckerPunch、softlock、respawn の具体的な修正へ結び付けた設計記録にある。

■ 自分達の環境への適用
小型アクション prototype では、全体難易度 menu より先に、死亡原因 ID に紐づく一段階の局所救済を試せる。例えば同じ弾幕で三回死亡した時だけ「弾速を半分」「弾を小さく」「この emitter を止める」を順に提示する。ただし自動適用はせず、通常再挑戦を既定にする。選択後は色、軌跡、音、説明を変え、何が変わったかを一秒以内に認識できるようにする。利用しても level の未見部分、score route、隠し challenge は残し、Tryhard mode 相当の timer や death count は希望者だけに見せる。

headless 評価では、救済前後の単純な clear率だけでなく、障害単位の death_count、提示から選択までの死亡回数、nerf_level、選択後の再死亡、次 checkpoint 到達、離脱を event log に残す。probe は同じ障害に対して A:救済なし、B:全体preset、C:死亡後の局所救済を比較し、初回clear率、再挑戦回数、救済利用率、利用後継続率、未使用者の割合を見る。人間 playtest では「効果に気づいたか」「自分で攻略した感覚が残ったか」も短く聞く。headless agent は知覚や自尊心を測れないため、到達可能性と難度差の確認に限定し、選択の心理的意味は人間で検証する。

実装時には救済を level geometry の状態遷移として扱う。障害を消した各状態で、出口までの path、落下地点からの脱出、checkpoint、dialog と respawn の再入可能性を自動検査する。この記事の spike pit は「hazard を消せば安全」という局所判断が「死なないが出られない」という全体破綻を生む実例である。罠 component に nerf 段階だけでなく、各段階の expected cue、navigation invariant、復帰方法を持たせれば、playtest の発見を次の prototype に再利用できる。

採用 gate は、局所救済が全体presetより次区間への継続を保ち、段階ごとの効果が認識され、どの nerf 状態でも softlock を作らないこととする。利用率が高すぎる場合は元障害が不適切、利用率がゼロでも大量離脱する場合は提示時期や心理的コストが不適切、と分けて診断する。少人数でも動画、event log、直後 interview を同じ build ID に束ねれば、作者のような質的観察を再現可能な制作記憶へ変えられる。

■ メリット・デメリット
メリットは、詰まった箇所だけを下げるため、攻略済み区間と未知部分の緊張を保ちやすいこと、救済を自分で選ぶため見えない補正より納得しやすいこと、死亡原因ごとの log がそのまま調整候補になることだ。弱体化を速度、サイズ、可視情報、削除に分ければ、単一の Easy preset より「何が難しかったか」も特定しやすい。

デメリットは、障害×段階ごとに挙動、表示、入力範囲、地形整合性を実装・検証する費用が増えることだ。死亡直後の dialog はテンポを切り、選択が「降参」表示に見えれば使われず、逆に報酬付きなら最適化のため意図せず使われる。削除後の softlock のように、危険判定だけ変えて level topology を壊す可能性もある。また本記事の観察は小規模で対照群がなく、利用しなかった人が満足したのか、仕組みに気づかなかったのかも分離できない。

■ 判定
部分採用。死亡原因に結び付く任意の局所救済、知覚可能な少数段階、各段階の到達可能性検査を、小型アクション prototype の一障害で試す。自動難易度調整や全作品共通ルールにはせず、event log と人間 playtest で継続率、効果認識、攻略感、softlock を確認してから広げる。
