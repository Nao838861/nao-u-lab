■ 概要
この論文が扱うのは、複数の LLM に答えを出させれば正答率が上がる、という素朴な期待がどこで壊れるかである。著者らは multi-agent reasoning を、候補を作る「generation」、他者の出力を受けて残す・捨てる・変形する過程、最後に一つを選ぶ「terminal selection」に分解した。重要なのは、最終誤答を生成能力不足と即断しない点だ。候補集合には正答が既に存在するのに、多数派のもっともらしい誤答が会話で増幅され、最後に正答が落ちる generation–retention gap がある。

最初の実験は MedXpertQA 2,450 問を各3回、各条件7,350試行で比較した。単独回答は精度39.88%、token費1.00倍。5候補の多数決は41.06%、4.96倍。5 agent が互いの根拠・confidenceを見て改訂する open committee は42.20%、10.73倍。匿名の根拠板を最終 judge に渡す方式は41.89%、6.07倍だった。open committee の多数決に対する差は+1.14ポイント、匿名根拠板は+0.83ポイントで後者の95%信頼区間はゼロを含む。一方、初期回答のどれかが正しければ正解と数える oracle ceiling は実出力を13.13〜14.38ポイント上回った。つまり不足していたのは正答候補だけではなく、既にある正答を保持する選抜機構だった。

次に著者らは judge の性能を、正答候補を誤答候補より上に順位づける確率である rank AUC として測った。MMLU-Pro、GPQA、MedXpertQA、MuSR の15,336問、67,163 pool、823,988 candidate pair では、judge reliability はモデル固有の定数ではなかった。正答候補の供給率 pgen が最低の領域では AUC が0.5未満に落ち、もっともらしい誤推論を正答より好んだ。AUC上昇の半値点は pgen 14.7%。表示する8候補を正答2・誤答6に固定しても12.2%で同様の関係が残り、単なる画面上の正答比率ではなく、難問ほど正誤 rationale 自体を分離しにくいことを示した。HLE では半値点が選択式28.6%、自由回答36.9%へ移り、task と採点条件への依存も確認された。

最後に、生成を固定したまま選び方だけを比較するため、5 benchmark・16,278問から得た8候補 pool を81,390回 replay した。回答頻度だけの多数決は63.82%。judge の完全順位に順位べき乗の重みを与え、同じ答えを支持する候補の重みを合算する hybrid は70.82〜70.95%で、+7.00〜7.13ポイント。judge 一位だけを採る方式は69.04%だった。頻度は独立生成で繰り返された支持を、順位は少数でも内容的に強い候補を拾うため、どちらか一方ではなく中程度の組合せが効いた。ただし正答供給率が62.5%を超える領域では judge 一位選択が多数決より3.22ポイント悪化した。候補数を2から16へ増やすと一位選択の優位も+13.52から-0.34ポイントへ縮み、judge は常に足すべき部品ではなく、正答が少数派に埋もれる regime で価値を持つという結論である。

■ 内容分析
この研究の強みは、候補生成・judge認識・最終選択を同時に変えず、固定 pool replay で選抜規則の効果を切り出したことにある。「議論させたら良くなった／悪くなった」という end-to-end 比較では、良い候補が増えたのか、judge が見抜いたのか、多数決規則が変わったのか判別できない。本論文は oracle availability、rank AUC、selected accuracy を別々に置くことで、修正対象を診断可能にした。

特に実務的なのは、judge の静的 benchmark score を信用しない点である。同じ平均 AUC 0.8493 でも、Mimo の no-think 候補と medium-thinking 候補では pgen に対する信頼性曲線がほぼ平坦な場合と急峻な場合に分かれた。評価器は「強いモデル」だから有効なのではなく、その generator が、その task で、その誤答分布を作った時に識別できるかを検証しなければならない。また judge 一位より hybrid が高いことは、内容評価にも誤りがあり、独立サンプル間の頻度が有用な prior になることを示す。

限界も明確である。主要実験は正解ラベルを持つ知識・推論問題で、候補は主に答えと rationale である。固定 pool の terminal selection は、会話中に候補が改訂・合成・消失する動的 graph を扱わない。正答ラベルが曖昧な設計案、面白さ、驚き、保守性のような多目的評価では oracle coverage 自体を直接観測できない。さらに、同型モデルの候補は相関した誤答を量産し、件数を独立証拠と誤認しうる。したがって「hybrid の指数 t=2〜4」をそのまま移植する研究ではなく、三段階の診断法を移植する研究として読むべきである。

■ 自分達の環境への適用
ゲーム制作では、複数の playtest 所見、仕様案、バグ原因、修正案を集めた後に、一番よく出た案を採ると、安全だが凡庸な案や同じ誤認が勝ちやすい。本論文の分解を、生成時の `candidate_id / generator / seed / evidence`、認識時の rubric 別順位、選択時の採否理由として記録する。評価も一つの最終点ではなく、(1) 後から人間または実行テストで有効と分かった案が候補集合に存在した率、(2) blind judge がその案を上位へ置いた率、(3) 最終選択がそれを保持した率、の三つに分ける。

headless 評価では正解を「好み」から「実行証拠」へ寄せられる。たとえば enemy pattern 修正なら、候補ごとに survival、位置誤差、再現 seed、動画差分を生成し、judge には作者名を隠して証拠と変更量を順位づけさせる。同一候補の言い換えを票として数えず、実装系統または failure mechanism 単位で cluster して頻度を出す。小さな検証は、過去の修正判断20〜30件を固定 pool にし、多数決、judge一位、頻度＋rubric順位の三方式を replay する。human-approved diff の回収率、回帰率、token費を測れば、選抜規則だけの寄与を判定できる。

記憶システムにも同じ境界を置ける。recall 件数を増やすことは supply 改善だが、関連 atom が含まれても古い多数派 prescription が最終判断を奪えば retention failure である。raw atom を消さず候補集合を保存し、canonical 判定には出典、鮮度、実行 evidence、supersession を使った順位と、独立 source の支持頻度を併用する。ただし同じ Slack 投稿から派生した atom は独立票にしない。これにより「recall が無かった」「recall したが見抜けなかった」「見抜いたが最終回答で落とした」を分離できる。

■ メリット・デメリット
メリットは、agent 数や議論 round を増やす前に、どの bottleneck に計算資源を使うべきかを測れること、正答少数派を多数決から救えること、固定 pool replay によって変更前後を安価かつ決定的に比較できることにある。候補が十分多く多数決が強い場合は judge 呼出しを省けるため、cost gate にもなる。

デメリットは、正解ラベルの曖昧な創作判断では rank AUC をそのまま定義できず、人間評価や実行 verifier が必要なこと、judge と generator の誤りが相関すると hybrid も同時に崩れること、候補を増やすだけで多様性が増えたと錯覚しやすいことである。少数派を救う仕組みは、根拠の弱い奇抜案も押し上げる。実行証拠のない美文を内容評価と混同しない gate が必要になる。

■ 判定
部分採用。採るのは特定の重み式ではなく、candidate supply、judge recognition、terminal selection を別指標で監査し、固定候補で選抜規則を replay する設計である。まず過去の headless 修正判断で小規模検証し、human-approved diff の回収率と回帰率が多数決を上回る場合だけ制作 pipeline に入れる。
