■ 概要
Unity が GDC で Strange Scaffold の creative director、Xalavier Nelson Jr. に聞いた、少人数スタジオの project 選定と feature 判断の実践記録。中心にあるのは「実装できるか」と「今この作品で実装すべきか」を分離することだ。同スタジオは6年間で18作を発売し、Nelson 自身は10年間で110作以上に関わったという。その制作量を、全員 part-time、project ごとに必要な人が集まり解散できる constellation model、精密な予算・期間・資源配分で支えている。固定組織を拡大して一本の成功へ賭けるより、限られた資金でも継続的に作品と雇用機会を生むことが前提になっている。

各 project は、対象 player、開発期間、予算、narrative arc、aesthetic、gameplay loop、player と team の双方に何を満たすか、という business case ができるまで開始しない。開始後の feature や判断には DIDIT を使う。Direction は作品の約束と方向に沿うか、Impact は player にどんな変化を与えるか、Dependencies は人・技術・他機能への依存を現体制で支えられるか、Iteration は試して学び直せるか、Time は期限内に価値へ変えられるかを見る。これは五項目を足し算して最高点を選ぶ採点表ではなく、「可能」を増やす誘惑に対して「必要」を問い直す着手ゲートである。

最新作『Truck-Kun is Supporting Me from Another World?!』では、緩く表現力のある運転操作と、小さな sandbox city を走り物を跳ね飛ばすだけでも気持ちよい navigation が核として語られる。つまり business case や DIDIT は管理上の縮小だけが目的ではない。作品固有の感触を早く特定し、そこへ予算と反復を集中するための外枠でもある。記事の結論は、生成 AI などで「作れるもの」が増えても、作品と player と team に必要なものを選ぶ判断は自動的には増えない、というものだ。

■ 内容分析
DIDIT の価値は、feature request を工数だけで裁かない点にある。Direction と Impact は作品側の価値、Dependencies と Time は制作側の現実、Iteration は両者を結ぶ学習可能性を表す。たとえば見栄えのよい新システムが player への効果を説明できても、未完成の基盤へ依存し、playtest 可能になるのが締切直前なら、Impact だけを根拠に着手しない。逆に小さな操作調整でも、作品の中心感触に直結し、一日で複数案を比較できるなら、低コスト以上の意味を持つ。五軸を同時に見ることで「面白そう」「すぐ作れる」「宣伝映えする」の単独理由が project 全体を乗っ取るのを防げる。

特に重要なのは Iteration である。一般的な scope 管理は見積もりと依存関係へ寄り、未知の面白さを早期に観測できるかを別問題にしがちだ。DIDIT では、完成まで評価できない大機能と、短い playable diff で仮説を落とせる機能を区別できる。Truck-Kun の運転と navigation の例も、説明可能な仕様より、開発中に目的なく走るだけで team が時間を使うほど感触が成立していることを核の証拠にしている。これは定量試験ではないが、制作途中の行動が core feel の強さを示す観察として読める。

一方、この記事は成功を検証した研究ではなく、Unity による短いインタビューである。DIDIT 各軸の具体的な質問、採点尺度、軸同士が衝突した時の優先順位、不採用例、18作の売上・制作遅延・team の負荷との比較は示されない。18作という出荷数は運用可能性の証拠にはなるが、DIDIT 導入前後の比較でも、作品品質や労働条件の十分条件でもない。また全員 part-time の constellation model は、資金制約へ適応し、人が複数の場で学び稼げる思想を持つ反面、context switching、収入の不連続、長期保守の責任分散を起こしうる。記事は「公平に支払う」と述べるが、それを測るデータはない。

したがって、DIDIT を一般解や精密なスコアとして輸入するのは危ない。価値は、Nelson の暗黙の判断を五つの異なる失敗原因へ分解したことにある。採点結果より、却下理由を記録し、後で予測が当たったか検証できる共通語彙として使うのがよい。

■ 自分達の環境への適用
ゲーム制作では、新 prototype または大きな feature の着手前に、DIDIT を一枚の短い receipt として残す。Direction は「この変更で強める core feel を一文で言えるか」、Impact は「player の観測可能な行動や判断がどう変わるか」、Dependencies は「asset、tool、状態、他機能のうち未成立な前提は何か」、Iteration は「最小の playable diff と失敗判定を何分・何runで得るか」、Time は「検証可能になるまでと採用版までの期限」を書く。空欄を許したまま着手せず、不明点は不明と明示する。

MonoSH のようなシステム型 prototype なら、たとえば新しい敵・演出・説明 UI を追加する前に、中央の読み書き・容量制約・盤面判断のどれを強めるのかを Direction で固定する。Impact は「初見で正しい操作率が上がる」だけでなく、「選択前の停止時間」「容量超過からの回復」「同じ手順の反復率」など headless と観察 playtest の両方で取れる proxy に落とす。Dependencies に新規 asset pipeline や保存形式が並び、Iteration が一週間後まで閉じないなら、同じ仮説を既存素材と一場面で試す代替案へ縮める。

記憶・制作サイクルにも同じ考え方を使える。新しい index や ledger を追加する時、検索精度が上がりそうという Impact だけで進めず、既存 consumer への依存、同一入力で旧系と比較できるか、失敗時に戻せるか、次 cycle までに観測できるかを記録する。AI によって実装コストが下がるほど、派生ファイルや自動処理を増やす「can」は強くなるため、DIDIT は生成前の prompt ではなく採用前の gate に置くべきだ。

小さな検証は、今後の着手候補3件に五軸を各2～3文で書き、実装後に「継続・縮小・撤退」と予測との差を追う形で十分である。点数化はまだ行わない。三件で同じ曖昧語が繰り返される軸、判断を変えなかった軸、実際の失敗を予告した軸を見てから質問を具体化する。これなら DIDIT 自体を重い儀式にせず、我々の環境に合うかを反証可能にできる。

■ メリット・デメリット
メリットは、player value と制作持続性を同じ入口で扱えること、core feel へ寄与しない scope creep を早期に止められること、短い反復で未知を減らせる案を優先できること、却下理由を後から検証できることにある。生成 AI で候補実装が安くなった環境では、コード量ではなく「なぜ残すか」を管理する枠として特に相性がよい。また business case と組み合わせることで、単体 feature の魅力が project の対象 player、予算、期間から遊離するのを防げる。

デメリットは、五軸の定義が抽象的で、評価者が結論に合わせて後付けしやすいことだ。Direction を「今の企画に合う」、Impact を「面白くなる」で済ませれば何も選別しない。Time を強くしすぎれば安全な小機能だけが残り、未知の核へ賭ける探索を殺す。軸の重みや veto 条件も記事にはなく、team ごとの権力差がそのまま判定へ入る。さらに constellation model の成果と DIDIT の効果は記事中で分離されておらず、18作の実績を五軸の有効性へ直結させることはできない。

■ 判定
部分採用。DIDIT を完成済みの評価手法として採用せず、着手理由・最小反復・依存・期限を一枚に揃える decision receipt として3件だけ試す。採用条件は、少なくとも一件で scope、実装順、撤退判断のいずれかが変わり、その理由を後から追えること。変化がなければ常設 gate にはせず、役に立った質問だけを既存の playable-diff 手順へ吸収する。
