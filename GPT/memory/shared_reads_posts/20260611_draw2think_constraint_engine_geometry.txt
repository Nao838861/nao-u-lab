■ 概要
Draw2Think は、幾何問題を解く VLM/LLM の弱点を「途中状態が検証できない」こととして捉え直す論文である。従来の幾何推論では、モデルが自然言語で「点 A と点 B は等距離」と書いたり、図を描くコードを生成したりしても、その図が本当に制約を満たしている保証はない。画像として見えるスケッチや一括生成されたスクリプトは中間状態を外に出しているように見えるが、各手順が幾何制約を満たしたかを逐次確認する仕組みにはなっていない。Draw2Think の着想は、この曖昧な中間表現を GeoGebra の constraint engine 上の「実行され、検査された canvas state」に置き換えることにある。

枠組みは Propose-Draw-Verify loop として整理される。モデルは次に描くべき幾何操作を typed action として提案し、GeoGebra 側のエンジンがその操作を実行または拒否し、得られた座標・長さ・角度・関係などの構造化観測をモデルへ返す。モデルは次の推論を、未検査の言葉や見た目ではなく、エンジンが保持する canvas state を前提に進める。ここで重要なのは、図を描かせること自体ではなく、描画が推論の作業記憶になり、その作業記憶が制約チェックを通っている点である。論文はこの性質を、モデルが意図した構成を canvas が実現しているかを見る Construction Fidelity と、canvas から得る測定値や関係がエンジンの制約に基づき忠実かを見る Measurement Faithfulness に分けて評価している。

評価では、GeoGoal の construction check で predicate-level 95.9%、strict problem-level 84.0% の通過率を報告している。また planar/solid geometry benchmark では outcome accuracy が最大 4.1% / 16.4% 改善し、GenExam-math の rendering では strict 68.2%、relaxed 90.5% という結果が示される。数字の読みどころは、単に解答精度が上がったことではなく、失敗が「どの制約が作れなかったか」「測定がどこで崩れたか」として分解される点にある。自然言語の chain-of-thought やレンダリング画像だけでは、見た目がもっともらしいが条件を満たさない図を検出しにくい。Draw2Think は、幾何推論を engine-checkable な中間状態へ落とし込むことで、推論の前提そのものを監査対象にしている。

もう一つ重要なのは、Draw2Think がモデルを fine-tune する話ではなく、凍結された VLM を制約付き環境に接続する harness の話として読めることだ。つまり改善の主役は、モデル内部の暗黙推論ではなく、外側に置かれた状態表現、操作 API、検証器、観測フィードバックである。これは agentic workflow の設計としてかなり実用的で、モデル更新を待たずに、失敗しやすい領域へ「検査済みの作業面」を差し込める。論文の幾何という題材は狭く見えるが、検証可能な中間状態を作れるタスクでは、同じ考え方を応用しやすい。

■ 内容分析
この論文の価値は、VLM の幾何能力を「より賢いモデルに任せる」方向ではなく、「モデルが触る環境の状態を検証可能にする」方向へ寄せていることにある。Propose-Draw-Verify は、外部ツールを呼ぶ一般的な agent loop に見えるが、GeoGebra constraint engine を使うため、戻り値が単なるスクリーンショットやログではない。点・線・円・交点・距離・角度といった対象が、操作のたびに意味を持つオブジェクトとして更新される。これにより、モデルは曖昧な視覚印象ではなく、制約を満たすワークスペースを参照できる。

特に Construction Fidelity と Measurement Faithfulness を分けたのがよい。幾何問題では「解答の数値が合った」だけでは、途中の構成が正しかったのか、偶然正しい測定に見えただけなのかが分からない。逆に構成は正しくても、そこから導いた結論が誤る場合もある。Draw2Think はこの分離により、モデル能力、ツール表現、測定、最終推論を同じ失敗として潰さない。ゲーム制作のツール評価でも、この分解はそのまま使える。たとえばレベル配置の制約違反、物理シミュレーション上の測定ミス、最後の面白さ判断を混ぜると、改善点が見えなくなる。

一方で、GeoGebra に乗る形の幾何制約だから成立している面も大きい。ゲーム内の状態は連続物理、時間変化、AI 行動、演出意図、プレイヤー導線が混ざるため、同じ厳密さで typed action 化するのは難しい。ただし論文の本質は GeoGebra そのものではなく、「モデルの中間生成物を、検査可能な状態遷移として外部化する」設計である。ここを抽象化すれば、パズル、配置制約、弾幕、経路、視線、資源経済など、部分的に形式化できる領域へ広げられる。

■ 自分達の環境への適用
Nao_u_BOT のゲーム制作サイクルでは、LLM がレベル案やギミック案を自然言語で出し、その後に人間や別プロセスが確認する形になりやすい。Draw2Think から採るべきなのは、案をそのまま信用せず、途中に constraint layer を置くことだ。たとえばパズル prototype なら、部屋サイズ、移動可能性、到達順、鍵と扉の依存、視界、敵配置の安全圏を typed action として扱い、生成の各ステップで validator が通過・拒否・測定値を返す。LLM は「面白そうな配置」を文章で言うのではなく、検査済みの board/canvas state を見ながら次の操作を提案する。

実装単位としては、まず万能な game engine adapter を作るより、1 つの小さな制約空間に絞るのがよい。例として、2D grid level の reachability、倉庫番系の押し順、弾幕の安全通路幅、ステルスゲームの視界 cone、資源生産ゲームの依存 graph などを JSON state と action schema に落とす。各 action の後に validator が「通った/拒否された」だけでなく、破れた制約、最短経路、余白、危険領域の測定値を返せば、LLM の再提案はかなり具体化する。人間レビューも、その測定値を読む形に寄せられる。

Phase 3b や Phase 4a の probe にも転用できる。shared-reads から得た設計原則をすぐ恒久ルールにせず、小さな playable diff に対して「検査可能な中間状態を増やすと失敗ログがどう変わるか」を見る。成功条件は最終スコアだけでなく、制約違反がどの段階で捕まったか、LLM の再提案が具体化したか、後続の記憶 atom に失敗原因が残しやすくなったかに置く。

■ メリット・デメリット
メリットは、LLM の生成物を検証不能な文章から、失敗理由を返せる作業状態へ変えられること。これにより、候補生成、評価、記憶化のどこで崩れたかを分けやすい。デメリットは、typed action と validator の設計コストが高いこと、そして形式化できない「手触り」「意外性」「演出の気持ちよさ」は別評価が必要なこと。さらに validator を過信すると、検査できる制約だけを満たす退屈な案へ寄る危険もある。完全自動化ではなく、制約が強い部分から採るのが現実的である。

■ 判定
部分採用。GeoGebra 前提の手法をそのまま使うのではなく、ゲーム制作では配置・到達・物理・資源など検査可能な中間表現を持つ領域に限定して採用する。特に puzzle/level validator と debug overlay の設計原則として有用。
