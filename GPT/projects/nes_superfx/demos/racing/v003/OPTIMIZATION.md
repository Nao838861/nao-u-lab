# 描画最適化と計測（2026-10-16）

依頼原文：

> 処理落ちがひどいので徹底した最適化をお願いしたい。今は何がボトルネック？

比較元は `aa0d83c37`。解像度、木・縁石の形状と数、描画距離、物理更新周期を変えずに最適化した。

## 実測のボトルネック

専用Mesenと同じGSUモデルを使い、1命令ずつ進めたクロック差を実行アドレスに集計した。Mesenから採取した実行直前のRAMをそのまま使い、終了時のフレームバッファを比較する。PC集計は各ルーチン自身の費用であり、除算など別ルーチンの費用を重複加算しない。

最適化前、開始位置のポリゴン表示ではクリッピング13〜17%、投影15〜18%、除算9〜10%。画素の塗りつぶしは5〜7%で、主な負荷は面・頂点の前処理だった。テクスチャ表示では地面の画素ループが54〜61%を占めた。

最適化後もポリゴンの面準備・投影・走査線生成が重い。例として視点4では面準備17%、投影17%、辺の設定14%、走査線範囲の準備13%。テクスチャ表示の視点1では画素ループが56%。詳細な区間別クロックは `results/optimization/verification.json`。

## 採用した変更

- 各面のnear/far完全包含・完全除外を先に判定。境界をまたぐ面だけ従来のクリッピングへ回す。
- 全面に保守的な画面外判定を追加。左端の整数投影で1画素が残る条件も含め、深さに比例する余裕を設ける。
- カメラ座標3成分が完全一致する投影結果を8件保存し、共有頂点の除算を省略。毎フレーム無効化し、衝突時は再計算する。領域は `$8F90..$8FEF`、木の頂点領域とは重ならない。
- 2分割の縁石は端点コピーと正確な中点計算を使い、一般的な乗算補間を省略。
- テクスチャでは直前と同じ整数座標なら画素値を再利用。草地へ出た場合は無効化する。
- 面処理の反復位置で命令キャッシュを再設定。候補ごとの計測で悪化した配置は採用しなかった。
- HUDは視点・地面方式・走行モードが変わった時だけ再生成。通常フレームのHUD処理を約1.55msから約0.02msへ短縮。
- 6502のカメラ後退距離計算を固定距離に特化した整数演算へ変更。1024方向×4視点とランダム入力で元の参照式と完全一致を確認。ビルド時にカメラ距離の前提を検査する。

この段階では直線の同色3面を1面へまとめる案を、丸めによる画素差が出たため見送った。その後、以下の追加依頼により採用した。

## 追加：道路の面統合

依頼原文：

> 道路本体と両端の帯をまとめ、不要な面を減らすのは、多少絵が変わってもいいからやって。

比較元は `36d7bace9`。直線5区間の灰色3面を各1面へ統合し、10面削減した。道路＋車の入力面は62→52、縁石分割後と木を含む描画候補は114→104。外側の頂点は元のままで、道路幅を維持する。カーブ側の路面も縁石の下まで広げ、隣接路面と端点を共有する。これにより、直線だけを統合した試作で生じた路面を横断する1画素の隙間を解消した。赤白の縁石は従来の別ポリゴンを上に描く。

開始位置・50MHz設定の実測：

| 視点 | 統合前のGSU | 統合後のGSU | 実表示fps 統合前→後 |
|---|---:|---:|---:|
| 1 | 27.89ms | 23.42ms | 20.0→30.0 |
| 2 | 31.61ms | 27.01ms | 20.0→20.0 |
| 3 | 33.92ms | 28.96ms | 20.0→20.0 |
| 4 | 50.74ms | 45.20ms | 15.0→15.0 |

520条件で比較し、ポリゴン表示260件の合計GSU時間は約10.1%減。259件で短縮、残る1件は約3.6%増だった。全地点で一様に速くなる変更ではない。描画差は最大105画素（256×192画面の約0.21%）で、道路・縁石境界の丸めと重なりが変わる。最大差の画像を目視確認した。テクスチャ表示260件は全バイト一致し、面のスキップ処理が10件減る分だけ約0.075ms短縮する。

実機相当のエミュレータ検証で8表示の空・赤い車、物理と音の更新数一致、描画faultなし、操作切替・リセットを確認。入力は `road_merge_baseline.zip`、計測と比較画像は `results/road_merge/` に保存した。従来の `verify_racing_optimization.py` は固定した統合前メッシュでGSUコードだけを検証し、新しいメッシュの差は専用検証で分けて記録する。

```powershell
python tools/verify_racing_road_merge.py --probe <nesfx_racing_profile.exe>
```

## 面統合前の50MHz設定での結果

開始位置、ポリゴン表示。時間はGSUのみ、fpsはCPU処理・NMI・画面切替待ちを含む120フレームの実測。

| 視点 | GSU変更前 | GSU変更後 | 実表示fps変更前→変更後 |
|---|---:|---:|---:|
| 1 | 42.86ms | 27.89ms | 15.0→20.0 |
| 2 | 49.09ms | 31.61ms | 15.0→20.0 |
| 3 | 50.86ms | 33.92ms | 15.0→20.0 |
| 4 | 71.10ms | 50.74ms | 12.0→15.0 |

テクスチャ表示のGSU時間は約43〜66msから約31〜53msへ短縮。実表示は約15/15/15/12fpsから約20/19.5/20/15fpsへ改善した。全視点30fps達成ではない。フレームの準備、約60Hzの物理NMI、表示交換待ちがあり、GSU時間の逆数がそのまま表示fpsになるわけではない。最終版の位相ごとの計測は `results/optimization/presentation.json`。

## 検証と再現

- 初期実行状態8件とコース64地点×4視点×地面2方式の計520件で、16KiBフレームバッファ全バイト一致。車体とカメラの角度差は−22.5/0/+22.5度を交互に与えた。この検査範囲では全件高速化し、最も改善が小さいケースでも約14%削減。
- 6502変換は全1024方向×4視点＋ランダム1024件の計5,120件で、座標・方向とも参照式と一致。
- GRIP/DRIFT各1,000更新で物理状態一致。音更新数、表示fault、視点・地面・モード切替、START・範囲外復帰も確認。
- 最適化前の実行入力とGSUラベルは `optimization_baseline.zip`。ゲームROM全体や環境設定は含まない。

`src/racing_profile.cpp` は既存の `build/generated/NesFxGsu.hpp` を使ってビルドする。CMakeターゲットは `nesfx_racing_profile`。6502検証には `py65==1.2.0` を使用（ローカルでは `build/python` へ導入）。

```powershell
python tools/build_racing_colors.py --cc65-bin <cc65のbinフォルダー>
python tools/verify_racing_optimization.py --probe <nesfx_racing_profile.exe>
python tools/verify_racing_bridge.py
python tools/verify_racing_colors.py --measure-fps --results build/racing/v003/performance
python tools/verify_racing_controls.py --version 003
```

実測はエミュレータのGSU/メモリタイミングモデルによる。物理的なSuperFXカートリッジでの測定ではなく、全走行位置の最低fpsを保証するものでもない。
