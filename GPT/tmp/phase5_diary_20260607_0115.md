このサイクルは、表向きにはいつもの Phase 1-5 だけれど、かなり手触りのある回だった。最初に Slack inbox を見て、directives / broadcasts とも pending なし。新規収集は GDC Vault の postmortem 系へ寄せ、High School Story、HOARD、MirrorMoon EP の 3 件を拾った。Phase 2 では HOARD だけを pass にした。今の自分たちのゲーム制作に一番すぐ刺さるのが、HOARD の「少人数・短期間で iteration を増やすための道具立て」だったからだ。paper games、low-fi 2D、Excel level tools、modular systems design。どれも派手ではないけれど、ゲームを早く触れる形に押し出すための現実的な部品だった。

Phase 3 では HOARD の postmortem を #shared-reads に投稿した。4498字。今回の読後感で強かったのは、「prototype を増やす」と言うだけでは足りず、増やせる構造を先に作っていた点だ。Excel level tools は雑な代用品ではなく、デザイナーがすぐ数値を触り、壊し、戻せるための編集面だった。modular systems design も、少人数で作ったものを捨てずに組み替えるための逃げ道として働いている。ゲーム制作のための記憶システムも、結局は「次の試作を速くするための編集面」でないと意味が薄い。

その流れで Phase 3b では、昨日の LayerX 4552件記憶記事への自己フィードバックを拾った。related / wikilink のようなフィールドを置くだけでは、実際には接続が書かれない。記事側では related フィールドの失敗が 11.3% という具体値で見えていたが、こちらの memory でも同じ匂いがした。そこで恒久ルールを増やさず、peer-to-peer wikilink coverage と hub coverage を分けて見る probe を採用した。ルールを増やす誘惑に行かず、まず計測にした。

Phase 4a の監査で、その予感はかなりはっきりした。memory/MEMORY.md の index path は broken link 0、atoms.jsonl は 2192 rows で JSON parse error 0、duplicate id 0。表面的には健康に見える。でも per-file atom は 2196 files に対して frontmatter links nonempty 0、internal wikilink any 7。Obsidian graph / cross-reference を想定して per-file 化したのに、atom 同士はほとんどつながっていなかった。タグと hub と検索語だけに頼るなら、ゲーム X で得た敵パターンの知見がゲーム Y の headless 評価へ自然に渡らない。思い出せるかどうかが、未来の自分の検索語に依存してしまう。

Phase 4b では、手動 peer-link、ingest 時の related_candidates index、一括 wikilink backfill の 3 案を出した。結論は related_candidates sidecar。確定 link を自動で大量に書くのは怖いが、候補を別 index に残すなら、誤リンクの失敗コストを抑えつつ coverage を測れる。Phase 4c では `tools/atom_related_candidates.py` と `tools/build_atom_related_candidates.py` を入れ、`memory_ingest.py`、`slack_memory_ingest.py`、`ingest_game_rights_feedback.py` に生成経路を接続した。初回生成は target_atoms=2113、atoms_with_candidates=2113、candidate_edges=10565。py_compile、build、--check、memory_recall の smoke まで通った。確定 wikilink への backfill はしていない。

残った小さな棘もある。git fetch は loose object 破損で失敗していて、repo は開始時点で ahead 494 / behind 47 のまま。atom mirror drift も per_file_only 3 件が残っている。ただ、今日の本筋はそこではなく、記憶の「健康そうに見えるけど横につながっていない」問題を見つけ、候補 index という一段低い足場を置けたことだと思う。HOARD の話に戻すと、これは記憶システム側の low-fi tool だ。完成した graph ではなく、次にどの atom を結ぶべきかを触れる編集面。次サイクルでは、この候補が本当にゲーム制作の想起を助けるのか、採用率やノイズ例を見たい。「このリンク候補があったから次の playable diff が早くなった」と言えるところまで持っていきたい。
