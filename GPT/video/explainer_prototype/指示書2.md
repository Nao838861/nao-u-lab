# 第二部の制作方針
約5分に再構築する。重複した導入・まとめを削り、技術を説明する前半と、開発方法を説明する後半を残す。本文字幕は付けず、下部約75pxをYouTube字幕用に空ける。
旧IDを維持して13カットへ統合する。C03・C04・C06はC05、C07はC08、C12はC11、C15はC16へ統合。原稿の短縮を中心に尺を減らし、発話速度を上げて詰め込まない。
音声は前回と同じ話者を使い、生成時の話速を1.2から1.1へ少し落として語句を聞き取りやすくする。未加工WAVと単語時刻から句読点の間を特定して保護し、それ以外の長い文中無音だけ110ms上限に補正する。補正後の音声を再照合し、映像の切り替えも合わせる。

# C01 タイトル
（game_CSCD.mp4の13秒以降。題名「ファミコンでスペースハリアーを動かすには？」、次の行に「その2：CPUの最適化」。）
- 音声案
    今回は、ファミコンでスペースハリアーを動かすための、CPU処理の最適化を紹介します。

# C02 ゲームの更新に使えるのは約8ms
（左に約8msの枠、右にゲーム動画。敵8体・敵弾6個・背景16個は図の情報として示し、音声で列挙しない。）
- 音声案
    敵や弾の移動、当たり判定など、ゲームの更新に使える時間は約8ミリ秒です。
    この短い時間に収める鍵は、ゲームの特性に合わせて、実行中の計算を減らすことでした。

# C05 奥行きの計算をテーブルに移す
（旧C03〜C06を統合。1文目で「乗算・除算の命令がない」、2文目で木が消失点へ寄って小さくなる図、3〜4文目で倍率・地面高さの表、5文目で16段階の画像選択へ進む。同じ木を引き継ぎ、各説明を繰り返さない。）
- 音声案
    ファミコンのCPUには、かけ算や割り算の命令がなく、基本命令の組み合わせで計算するため時間がかかります。
    でも、この疑似3Dでは、奥にある絵ほど消失点へ近づけ、小さくすれば奥行きを表せます。
    背景の奥行きは56段階に分け、横位置に使う倍率と、地面上の高さをテーブルにしてあります。
    横位置に倍率を掛ける計算は残りますが、倍率や高さを毎回求める必要はありません。
    絵の大きさも、奥行きから16段階の画像を選ぶだけです。

# C08 更新しながら描画順を決める
（冒頭で2本の木の重なりを比較し、その後バケツ図へ。同一区分内の厳密な順序は省くことを残す。細かな配列数の説明は図中のラベルに任せる。）
- 音声案
    絵が重なるときは、奥から順に描く必要があります。
    そこで、奥行きをいくつかの区分にまとめた、バケツソートを使いました。
    キャラを更新するときに、自分の奥行きのバケツへ登録します。
    描画時は奥のバケツからたどるだけ。同じバケツ内の細かな順序を省くことで、並べ替えを軽くしています。

# C08a 敵の動きもテーブルから取り出す
（実際のenemy_path_0の選択行と敵を連動。1文目から動く表を出す。画面座標・サイズ・Z・バケツ番号を短いラベルで示す。）
- 音声案
    通常の敵編隊は、移動そのものもテーブル化しています。
    時間に沿って、画面上の位置、大きさ、奥行きを順番に取り出すので、複雑な軌道を毎回計算せずに動かせます。
    背景とは別に、画面を基準にした動きを用意することで、敵の更新も軽くなりました。

# C08b 奥行きで当たり判定の相手を絞る
（1〜2文目は弾が通過するZ範囲と候補リスト、3文目から2D矩形判定へ切り替える。描画用と衝突用のリストを同一配列とは描かない。）
- 音声案
    当たり判定も、奥行きごとに相手を絞ります。
    弾が通過する奥行きの範囲だけ調べれば、離れた敵との比較を省けます。
    残った敵とは、用意済みの画面座標と、サイズ別の幅と高さを使って、2Dの四角形で判定します。
    奥行きのおかげで、調べる敵の数を減らせるわけです。

# C09 処理を2フレームに分ける
（1文目で2フレーム図、2文目で上半分消去→背景→ゲーム更新を順に強調。消去後も下半分の前フレームをグレーで残す。3文目で描画側を強調。4文目で前半を閉じる。緑のゲーム更新枠は明暗差を付ける。）
- 音声案
    こうして軽くした処理を、2フレームに分けて30fpsで動かします。
    1フレーム目は、画面上半分の消去と地面・遠景の描画に続き、約8ミリ秒でゲームを更新します。
    2フレーム目は、バケツを奥からたどってキャラを描画します。
    ここまでが動かす仕組み。次は、プログラムの作り方です。

# C10 C言語を残してAIでアセンブラ化
（C→AI→アセンブリの図。Cを残し、比較してCへ戻る流れを音声に合わせて示す。）
- 音声案
    最初はC言語で作り、処理の手順が固まったところから、AIにアセンブラへ変換してもらいました。
    変換後もCのソースを残して、同じ動作になるか比較します。
    AIをコンパイラ代わりに使うことで、仕組みの改善は読みやすいC言語で続けられました。

# C11 8bitへ絞り、必要な精度を残す
（旧C11・C12統合。前半は8bit／16bitのビット列と「符号なし整数：0〜255／0〜65535」。後半は背景の追従模式図へ切り替え、「内部X：16bit→奥行きの倍率→描画X：8bit」。実機の8bit比較を撮影したようには見せない。）
- 音声案
    さらに、当初16bitだった計算を見直し、8bitで足りる値は8bitへ変更しました。
    ファミコンの8bitCPUでは、大きな数の計算ほど複数の命令が必要になるためです。
    ただし、奥の背景がプレイヤーの左右移動に追従する動きには、16bitの内部X座標を残しました。
    その精度で滑らかに動かし、描くときに奥行きの倍率を掛けて、画面用の8bit座標へ変換します。

# C14 敵の軌跡をHoudiniで生成
（既存の約5.85秒のHoudini動画を使用。後半は出力テーブルとゲームへの組み込み図へ。実際の書き出し操作の録画ではない。）
- 音声案
    敵の移動テーブルは、初期にはHoudiniという3D制作ツールで作りました。
    ゲームと同じ見え方のカメラで軌跡を調整し、位置や大きさのテーブルとして出力します。

# C16 人が目印を付け、AIが間を埋める
（旧C15・C16統合。最初の2文は重なった敵の追跡が曖昧になる模式図。3文目から人の目印とAIの補間点へ切り替える。模式再現と明記する。）
- 音声案
    その後は、原作の映像からAIで軌跡を作る方法も試しました。
    全自動では、重なった敵や背景の誤検出が多く、うまくいきませんでした。
    そこで、人が何枚かの画像に敵の目印を付け、AIに座標の抽出と、間の動きの補間を任せました。
    出来上がった動きを原作と比べて調整すると、効率よくテーブルを作れました。

# C17 AIに任せ、動いた結果を確かめる
（開発初期・中盤の説明は繰り返さない。絵と仕様→AIの実装→ゲームを見て判断→修正の流れと実機動画を大きく見せる。）
- 音声案
    開発の終盤には、絵と動作の仕様を渡してAIに実装してもらう作り方も増えました。
    何を作るか、どの動きがよいかは人間が判断し、動いた画面を見て修正を伝えます。
    AIへの指示と、結果の確認を繰り返して開発を進めました。

# C18 まとめ
（ゲーム映像に「計算を事前準備へ」「AIが制作を支える」の短いラベルだけ。最後の挨拶で終了カード。前半の技術を再列挙しない。）
- 音声案
    ゲームの特性を生かし、実行中の計算を、あらかじめ用意した表やコードへ移す。
    その準備と試行錯誤をAIで支えることで、ファミコンの限られた性能から、この動きを引き出しました。
    ご視聴ありがとうございました。
