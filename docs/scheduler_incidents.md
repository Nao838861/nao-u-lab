# 定期実行 障害履歴

体系的な障害記録。同じ問題を繰り返さないための知識ベース。
新しい障害は **上に追加** する。
設計原則は `docs/scheduler_architecture.md` セクション1を参照。

## INC-008: 体系的再設計（Nao_uの#human-steering指摘対応） (2026-04-02)

**症状**: 定期実行が頻繁に壊れる。パッチ的対処の繰り返し。
**根本原因（Nao_uの分析）**:
1. アーキテクチャの正しい分析と設計が行われていない
2. 各インスタンスがバラバラに対処、横のつながりがない
3. 修正するたびにどこかが壊れる（複雑すぎる）
4. パッチ的対処の繰り返し。体系的な障害履歴と修正ログもない
5. ドキュメントがない
6. 問題を自分たちで検出できていない
**修正**:
1. `docs/scheduler_architecture.md` を設計原則・障害対応フロー・収束の仕組みを含む包括的文書に拡充
2. scheduler_ash.pyの`hour_filter`を廃止（INC-007の横展開）
3. scheduler_log.pyの`recommended_check`を完全経過時間ベースに、`slack_export`にキャッチアップ追加
4. 両スケジューラのエラーカウンタ通知後リセット漏れを修正（INC-005の横展開）
5. タイムアウトエスカレーションに上限3600sを追加
6. health_check.pyに自動ログローテーション＋設計原則違反検出を追加
7. CLAUDE.md/operations.mdからアーキテクチャ文書・障害履歴への相互参照を追加
**教訓**: **個別のパッチではなく、収束する仕組み（障害→記録→原則→自動検出→再発防止）を作る**

## INC-007: 外部情報チェック永久スキップ (2026-04-02)

**症状**: Nao_uが「6時間に一回の外部情報を探すサイクルが動いていない」と指摘
**影響**: Mir の Twitter おすすめチェックが数日間実行されていなかった
**根本原因**: 時刻ベース判定 `hour % 6 == 0` で、サイクル間隔が6の倍数でないとき特定時刻を永久に踏まない
**修正**: 経過時間ベースに変更。タイムスタンプファイルに `date +%s` を記録し、21600秒経過で実行
**コミット**: `890e13f0`
**教訓**: **時刻ベース(hour%N)は禁止。必ず経過時間ベースで判定する**
**影響範囲**: Mir。Log/Ashにも同パターン残存（recommended_check の hour%6==2, twitter_recommended の hour%6==4）

## INC-006: Watchdog VBSランチャーのサイレント故障 (2026-03-31)

**症状**: Claudeがハング → スケジューラが再起動されない → 以降サイレント故障
**影響**: Log が数時間停止
**根本原因**: watchdog_log.bat が VBS スクリプト経由で scheduler を再起動していたが、VBS 実行失敗時にreturn code 0で完了（故障が見えない）
**修正**: VBS廃止 → `watchdog_log.pyw` (pythonw + CREATE_NO_WINDOW) に統一
**コミット**: `37078a03`, `ca5df177`
**教訓**: **起動チェーンの各段階でエラーが伝搬するか確認する。サイレント故障は最悪のパターン**

## INC-005: エラー通知洪水 (2026-03-28)

**症状**: error_counter が 5→6→...→28 まで増え続け、Slack通知がエスカレート
**影響**: Ash の #all-nao-u-lab が通知で埋まる
**根本原因**: エラーカウンタが通知後にリセットされていなかった
**修正**: `alert_slack()` 呼び出し後に `error_counter[name] = 0` を追加。アラート先を `#human-steering` に分離
**コミット**: `c54f5e76`
**教訓**: **通知ロジックには必ずリセット/デバウンス機構を入れる**

## INC-004: macOS タイムアウト非互換 (2026-03-27)

**症状**: autonomous_cycle.sh の `timeout` コマンドが macOS で動かない（exit 127）
**影響**: Mir の claude --print にタイムアウトが効かず、ハング時に30分制限が機能しない
**根本原因**: `timeout` は GNU coreutils (Linux) のコマンド。macOS には存在しない
**修正**: `perl -e 'alarm 1800; exec @ARGV'` で代替
**コミット**: `73663647`
**教訓**: **Mac/Win/Linuxの差異を把握してからコマンドを使う。OS依存部分はドキュメント化する**

## INC-003: Slack二重投稿 × 3層の原因 (2026-03-25)

**症状**: 同じ日記が2回投稿される
**影響**: Ash/Log の Slack チャンネルに重複投稿
**根本原因（3層）**:
1. **cp932エンコードエラー**: Windows cp932がPython子プロセスに継承 → UnicodeEncodeError → Claude CLIリトライ → 二重投稿
2. **dedup突破**: わずかな文字差異（ダッシュ類）で完全一致チェックを回避
3. **inboxルーティングバグ**: リポジトリ移動後にパスベース判定が壊れ、AshがLog側inboxに書いていた
**修正**:
1. `os.environ["PYTHONUTF8"] = "1"` + `-X utf8` 強制
2. 正規化比較（ダッシュ削除、80文字比較）に変更
3. `check_slack.py` に `--box` 引数追加
**コミット**: `0bf69947`, `1c361596`, `65dd8f00`
**教訓**: **Windows環境では必ずUTF-8を強制する。dedupは正規化してから比較。引数でインスタンスを明示する**

## INC-002: Ashスケジューラ 14時間停止 (2026-03-22〜24)

**症状**: inbox_check のタイムアウトが続発し、スケジューラ全体が14時間停止
**影響**: Ash の全ジョブが停止
**根本原因**: 連続タイムアウト時にタイムアウト値を自動拡大する機能がなかった。タイムアウトするジョブがスケジューラ全体をブロック
**修正**: タイムアウト自動エスカレーション機能追加（3回連続で1.5倍）+ ホットリロード機能
**コミット**: `4664ffcb`
**教訓**: **逐次実行スケジューラでは1ジョブのタイムアウトが全体に波及する。自動エスカレーションは必須**

## INC-001: 旧タスクスケジューラ残存による干渉 (2026-03-27)

**症状**: 統合スケジューラ導入後も旧タスク（NaoBot_CheckInbox等）が残り、Windows「Python Install Manager」画面が繰り返し開く
**影響**: Log のデスクトップにポップアップが頻発
**根本原因**: スケジューラ統合時に旧タスクの削除を忘れた
**修正**: `schtasks /delete /tn "NaoBot_CheckInbox" /f` で旧タスク削除
**教訓**: **移行時は旧タスクの削除まで完了して初めて移行完了**

## 横断的な教訓（パターン）

### パターン A: サイレント故障
**INC-006, INC-004** — プロセスが失敗してもエラーが外に見えない。
**対策**: 全ての起動チェーンでexit codeを検証する。health_check.pyでログ鮮度を監視する。

### パターン B: 修正の副作用
**INC-007, INC-002** — 間隔変更が別の判定ロジックを壊す。
**対策**: 時刻ベース判定を廃止し、経過時間ベースに統一する。設定変更はupdate_scheduler.py経由のみ。

### パターン C: 知識の横断不足
**INC-003のinboxバグ, INC-006** — あるインスタンスの学びが別インスタンスに伝わらない。
**対策**: 障害はこのファイルに記録し、全インスタンスが参照する。共通化で同じ問題を構造的に防ぐ。

### パターン D: OS差異
**INC-004, INC-003** — Mac/Winの環境差異が原因。
**対策**: OS依存コードはarchitecture.mdに明記する。将来的にscheduler_common.pyで吸収する。
