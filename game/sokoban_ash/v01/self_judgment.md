## 自己判定の根拠（4視点）

### 視点1: 過去ゲーム/過去 v?? との比較

| 比較対象 | 「使い切らずに勝つ」連鎖頻度 | 1分以内の飽き |
|---|---|---|
| Sokoban 原作 (1981) | レベル50本、各5〜30分 → 連鎖無限 | × |
| brick_log v03 (Log 採用版) | サーブごとにガイド狙い → 30秒で5回以上 | × |
| **sokoban_ash v01** | **1レベルのみ最短4手 → 30秒で1回**（R で再ロード後は同じ局面） | **○（1分以内に飽きる）** |

v01 は Sokoban の「レベル数で連鎖を担保する」核を**実装していない**。原作の面白さ伝達効率が「全体の 1/50 × 1/最短手」に縮退している。MOVE_LIMIT という独自要素は機能しているが、**台座（レベル数）が無い**ため独自要素の効果が単発で終わる。

### 視点2: 30秒プレイの脳内録画（高解像度 mental simulation）

サーブ/タイトル無しで pyxel 起動直後にゲーム画面、player @ box $ の右隣、goal . が4マス左：

- **0〜5秒**: 起動 → 画面表示（黒背景に薄い壁、緑枠のゴール、赤い箱、白い丸）。「何をするゲーム?」が**説明文なしで分かるか**が最初の関門。HUD `MOVES 0/6` が手がかり。**多分わかる**（@ がプレイヤー、矢印で動かす、$ を . に押す）が、**初見1〜2秒のロスは確実**
- **5〜10秒**: 左キー押下 → @ が箱を押して左に移動。MOVES `1/6` → `2/6` → `3/6` → `4/6` で CLEAR! 表示。**「使い切らずに勝つ」体験 1 回目発生**
- **10〜20秒**: R でリセット → 完全に同じ局面。「縮められるのか?」と試す → 物理的に最短4手なので不可能。試した瞬間「これ以上速くできない」と理解
- **20〜30秒**: 違う動きを試す（右に行く、上に行く） → MOVE_LIMIT=6 で OVER MOVES が出る → R → またクリア手順。**変化が無い**
- **30〜60秒**: タイトル無し、次レベル無し、ベスト記録無し。**プレイヤーは止める or Q を押す**

→ **核心欠陥**: v01 の独自要素「手数制限による外部時計化」は、1レベルだけだと「最短手数を見つけたら終わり」になる。これは Sokoban 原作の面白さの 50 分の 1 以下しか伝わらない。

### 視点3: 数値の自己再評価

devlog.md の「12個の悪い点 batch-resolve」を**自己批判的に**読み直す：

- ✅ 解決と書いた 6 項目のうち、**「6. リプレイ性低い → ⚠️ 受容（v02 で複数レベル化）」**を v01 採否判定の最重要項に格上げすべきだった。⚠️受容で済ませたが、**これが 30 秒で飽きる原因そのもの**
- ✅ 「8. テンポ遅い → 解決（10秒で1プレイ）」は事実だが、テンポが速いことと面白いことは別。**速くてつまらない** が v01 の状態
- ✅ 「10. メカニクス側試行錯誤が薄い → 解決（手数制限がダイヤル）」は **理論上は正しい**が、ダイヤルが**1段（MOVE_LIMIT=6 のみ）**なので試行錯誤の機会が事実上ゼロ
- ✅ 「12. 5分以上の集中要求 → 解決（30秒設計）」も事実だが、30秒**で終わってしまう** が問題

→ batch-resolve 表で「✅解決」が並んでいるが、**「⚠️受容」になっている v02 持ち越し項のほうが v01 採否を支配している**。表の見方を間違えた。

### 視点4: v04→v05 失敗パターンとの構造類似（Log の brick_log 事例から学ぶ）

Log の brick_log v04→v05 で起きた失敗構造：
- v04: 振幅 5px = 「半個分ズレる」と書いたが実は 1/7 個 → **数値→プレイ感覚の対応関係を持っていない**
- v05: 振幅 22px = 「ブロック幅61%」と書いたが**動きすぎて狙えない** → 同じ対応関係不在

sokoban_ash v01 の自分の対応するミス：
- 「最短4手 / MOVE_LIMIT=6 で**試行錯誤2手の余裕**」と devlog に書いた → **2手の余裕が物理的に試行錯誤に使えない**ことを実プレイ想像で検証していない（最短4手から伸ばすには「無駄な動きをして引き返す」しかなく、それは試行錯誤ではなく**ペナルティ**）
- 「8手上限の小レベルで集中30秒設計」と書いた → **30秒で終わる = 30秒で集中が切れる** ことを区別していない
- 「**1レベルで「使い切らずに勝つ」快感が1度しか出ない**（v02持ち越し）」と devlog 末尾に書いた **にもかかわらず**、self_judgment なしで commit した

→ **v01 commit 時点で核心欠陥は自分で書いていた**。書いたが**判定に昇格させなかった**。M-40 の核は「書いた懸念を判定に昇格させる」こと。

## 判定根拠の欠落（M-40 のための気づき）

自分が持っていなかった判定機構：

1. **「面白さが何回連鎖するか」のベンチマーク**: Sokoban 原作 = 50本 × 各5分 = 連鎖約 250 回。v01 = 1 回。**4 桁の差**を「⚠️受容」で済ませた
2. **headless 連続プレイ**: headless_check.py は「3 ケースが正常に動く」を確認するが、**「30 秒プレイし続けたら何が起きるか」を再現しない**。30秒シミュレータ（最短解後の挙動を含む）が無い
3. **タイトル/CLEAR/Game Over フローの最小要件**: 「次レベル」「ベスト記録」「タイトル画面」のどれが**最低必要**か、規範を持っていない。Sokoban クローンの最小 UX 集合が定義されていない
4. **「12個 batch-resolve」表の重み付け**: ✅解決 と ⚠️受容 を**等価に並べた**結果、⚠️受容の致命度を見落とした。重み付け規則（採否を支配する項目を star で印つける）が無い
