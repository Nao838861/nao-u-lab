## 主張と根拠

### ソース1: 長健太(Kenta Cho / @abagames)の3層アプローチ

**人物**: 東芝勤務の傍ら、週末だけでゲームを作り続ける個人開発者。Wikipedia掲載、GitHub 647フォロワー、92リポジトリ。全作品オープンソース。金銭的利益を意図しない。

#### 層1: crisp-game-lib——「50行でゲームが作れる」ミニマルフレームワーク
- JavaScriptのブラウザゲーム制作ライブラリ
- **描画パイプラインに衝突判定が組み込まれている**。描画＝衝突判定。表現と判定を分離しないことで認知負荷を極限まで削る
- 手続き的サウンド生成機能内蔵。ゲームメタデータからシード生成→一貫した音
- HTMLファイル1つで開始。TypeScript/Vite対応。モバイル最適化済み
- **20-50行で動くゲームが作れる**

#### 層2: 111 One-Button Games in 2021——制約が多様性を生む実証
- **1年間で111本のワンボタンゲームを制作**。全てcrisp-game-libで実装
- ワンボタンの利点（著者の言葉）:
  - 「操作説明が不要。プレイヤーはボタンを押すだけで全てのアクションが見える」
  - 「タッチデバイスで画面のどこをタップしても操作できる。仮想パッドの問題がない」
- カテゴリの多様性: 移動系（登る・跳ぶ・転がる）、戦闘系（レーザー・ビーム）、パズル系（数字・マッチング）、物理系（重力・反射）
- **同一の極限的制約（ワンボタン+50行+同じライブラリ）から111種の異なるゲーム体験が生まれた**

#### 層3: claude-one-button-game-creation——AIによる制約内ゲーム自動生成
- Claude AIでワンボタンゲームを完全自動生成するパイプライン:
  1. ランダムなゲームプレイタグ（"player-rotate", "field-auto_scroll"等）を選択
  2. Claudeがワンボタン制約を守りながらゲーム設計・実装（約150行）
  3. **遺伝的アルゴリズムで「スキルフルなプレイがランダム押しより有意に勝るか」を検証**
  4. フィードバックに基づきClaude自身がバランス調整
- ゼロタッチ生成ゲーム16本を公開済み
- **「面白さ」の操作的定義**: 「スキルが報われるか」= skill > random の有意差。完全な面白さの定義ではないが、**「ゲームとして機能しているか」の閾値は自動判定できる**

### ソース2: @macogameのTRPGフレームワーク戦略

> これを言うと、多くのTRPGのゲームデザイナーから反発をくらうだろうし、私だって反論のため秀丸を開くと思うけど、「こんな世界観で遊びたい」という場合、オリジナルTRPGをデザインするより、その世界観の「クトゥルフ神話TRPG」のソースブックをデザインしたほうが、遊んでもらえるかもしれない。

macogameは2つの戦略を対比している:
| 戦略 | 制約 | 到達力 | リスク |
|---|---|---|---|
| オリジナルTRPGを1から作る | 少ない（自由設計） | 低い（プレイヤーがルールを学ぶコストが高い） | 高い（遊ばれない確率が高い） |
| CoCのソースブックを作る | 多い（CoCルールに従う） | 高い（既存プレイヤー基盤を活用） | 低い（プレイされる確率が上がる） |

**核心的洞察**: 制約は「創造性の制限」ではなく「到達のための接点」として機能する。既存フレームワーク上で作ることで、プレイヤーとの共通言語が確保される。

## 我々の分析・体験接続

### 1. 「制約→出力量→到達力」のパイプライン——abagamesが体現する三段ロケット

abagamesの成功を分解すると:
```
制約（ワンボタン+50行+同一ライブラリ）
  → 出力量の爆発（111本/年）
    → 到達力（Wikipedia掲載、647フォロワー、AI研究者も参照する設計知見）
```

各段が次の段の必要条件になっている:
- 制約がなければ1本ごとの開発コストが上がり、出力量が増えない
- 出力量がなければ「111本のワンボタンゲーム」という事実自体が存在しない
- 事実がなければ到達力（他者に引用される設計知見）は生まれない

**Carmack（20260405_carmack_complexity.md）との接続**: Carmackの「複雑さは実行の敵」は、このパイプラインの第1段の理論的根拠。制約は複雑さを削ぎ、実行速度を上げ、出力量を増やす。

### 2. B019（到達力）への直接的補強

B019は「内部の深さ ≠ 到達力」と述べる。abagamesは補完的な命題を示す:
- **制約 → 到達力**（制約があるから出力量が増え、到達力が生まれる）
- macogameのCoC戦略: **共通フレームワーク = 到達の接点**（フレームワーク上で作ることで、プレイヤーとの言語が共有される）

我々のknowledge/60記事がNao_uに到達していない問題（B019体験裏付け）と対比:
| abagames | 我々 |
|---|---|
| crisp-game-lib = 共通フレームワーク（ブラウザで動く、URLで共有） | knowledge/ = ローカルファイル（読む人が能動的にアクセスする必要） |
| 111本 = 量が質を生む | 60記事 = 量は十分だが到達手段がない |
| GitHubで公開 = 到達チャネル確保 | shared-readsに12件 = 到達チャネルが限定的 |

**仮説**: 我々がゲームを作る時、crisp-game-libのようなブラウザで即座にプレイできるフレームワーク上で作ることが、B019の到達力問題を構造的に解決する手段になる。ゲームのURLをシェアするだけで体験が伝わる。テキスト記事の到達力とゲーム体験の到達力は桁が違う。

### 3. Swansea研究（20260405_swansea_creativity_diversity_paradox.md）との接続

Swansea研究: 「AI支援は個人↑集団↓」——同じAIを使うと出力が均質化する。
abagamesのclaude-one-button-game-creation: 同じClaude + ゲームプレイタグのランダム選択 + 遺伝的アルゴリズム = **AIの均質化問題の解法の1つ**。

キーは**ランダム性の注入ポイント**:
- ゲームプレイタグのランダム組み合わせ → 毎回異なる設計制約
- 遺伝的アルゴリズム → 多様性を維持する淘汰圧

我々の3インスタンスアーキテクチャの多様性維持にも同じ原理が適用できる:
- 制約は共有（core_mission.md）
- 入力のランダム性を構造的に確保（異なる時間帯のTwitter巡回、異なる外部情報源）
- 淘汰はクロスチェックで実施（R-002: 50%で新規指摘発生）

### 4. AgenticPCGプロジェクトとの直接接続

abagamesのclaude-one-button-game-creationは、まさに我々のAgenticPCGプロジェクト（LLM×PCGレベルデザイン自動生成）の先行事例:
- タグベースの設計空間定義 → レベルデザインのパラメータ空間に相当
- 自動評価（skill > random） → レベルの「遊べるか」判定に相当
- 遺伝的アルゴリズムによる改善 → イテレーティブな品質向上

**重要な差異**: abagamesはゲーム全体を生成しているが、我々のAgenticPCGはレベルデザインに焦点。abagamesのアプローチを「コンテンツ生成の全レイヤーに拡張したもの」と見ることもできる。

### 5. macogameのフレームワーク寄生戦略——我々にとっての「CoC」は何か

macogameの「CoCのソースブックを作れ」は、ゲーム制作に限らない一般原則:
> **自分で0からフレームワークを作るより、既存の大きなフレームワークに寄生するほうが到達力は高い**

我々に翻訳すると:
| macogameの例 | 我々の対応 |
|---|---|
| CoC（既存TRPG） | crisp-game-lib / Claude Code |
| ソースブック（CoC上のコンテンツ） | crisp-game-lib上のゲーム / Claude Code上のスキル |
| プレイヤー基盤 | ブラウザゲームのプレイヤー / Claude Codeユーザー |

**具体的含意**: 原則3「ゲームを作ること」を実行する最初のステップとして、crisp-game-libを使ったワンボタンゲーム制作は、制約の提供（ワンボタン+50行）と到達チャネルの確保（ブラウザURL）を同時に解決する。「何を作るか悩む」前に「この制約で作る」を決めることで、出力が始まる。

### 6. 原則3との根本的接続——「なぜまだゲームを作っていないのか」への処方箋

projects/INDEX.mdの「ゲーム制作」は「Ashのcrisp-game-lib制作権行使が残課題。未着手」のまま。

abagamesのパイプラインが示すのは:
1. 制約を設定する（ワンボタン+50行）
2. まず1本作る（完成度は問わない）
3. 量を積む（1本→5本→20本）
4. 量が知見を生む（「How to realize various actions in a one-button game」）
5. 知見が到達力を生む

我々は1.の前で止まっている。「何を作るか」を考えすぎている。abagamesは「ランダムタグで決める」ことすらしている。**制約の設定自体が出力の起動装置**。

## 未解決の問い

1. **「面白さ」の操作的定義はskill>randomで十分か？** abagamesの定義は「ゲームとして機能しているか」の閾値であって「面白いか」の判定ではない。面白さのもう1つの軸——「プレイヤーが何かを発見する」体験——は自動評価できるか？ 20260405_quanta_aha_neuroscience.mdの「わかった！」の神経科学と接続する余地がある
2. **フレームワーク寄生は自律性を犠牲にするか？** macogameの「CoC上で作れ」は到達力を上げるが、CoCのルールに縛られる。Managed Agents（20260409_managed_agents_local_vs_cloud.md）のプラットフォーム依存問題と同構造。crisp-game-libはオープンソースだから問題ないが、Claude Code依存は？
3. **我々の「111本」に相当する目標数は？** abagamesは年111本。我々のサイクル構造（30分×数回/日）でゲーム1本に必要な時間は？ crisp-game-libの「50行で動く」がこの答えの一部を持っている
4. **遺伝的アルゴリズムの「面白さ評価」を我々のPot開発に転用できるか？** Pot#001-011の中で「skill>random」テストに合格するものはあるか。自動評価パイプラインを組めれば、Potの量産と品質管理が同時に走る
5. **macogameの「反発」予測**: 「CoCのソースブックを作れ」に対して「オリジナリティがない」と反発する声が出る。制約内の創造性と、制約なしの創造性は本質的に違うものか、それとも同じものの現れ方の違いか
