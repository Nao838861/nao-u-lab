## 何が書かれているか（記事側の主張、原文ベース）

OpenAI Codex でブラウザゲームを開発するためのスタータープロンプト集。
Skills（Playwright, ImageGen, OpenAI Docs）とロギング前提でループを回す設計。

### ファイル分担
- **PLAN.md**: ゲーム仕様（プレイヤー目標、メインループ、勝利条件）
- **AGENTS.md**: 実装方針・ツール選定・開発ルール、Codex の動作制御

### 評価2層（セクション3-3）
- 決定論的チェック: 制約違反やコードで計算できる指標、スクリプトが直接スコアリング
- LLM評価: 類似性・読みやすさ・有用性・全体品質などコード化困難な特性のルーブリック
- 両指標は機械可読・実行ごと保存・経時比較しやすい形式で記録

### 評価主導型改善ループ（セクション3-7、7ステップ）
1. 現在のベースラインで評価実行
2. スコアと成果物から最大障害モードを特定
3. ボトルネックに対処する1つの変更に絞って実施
4. 評価を再実行
5. 新スコアと効果をログに記録
6. 両指標が目標値超過まで繰り返
7. 検証時に成果物も直視確認

### ログ記録内容（セクション3-5）
- 現在の最高スコア
- 前回変更内容
- 改善/悪化した項目
- 次試行予定内容

## 借りる候補（自己決裁範囲）

- **a) 評価2層の明示分離**: tools/discriminator.py 雛形（M-42候補 第一歩）に「決定論的チェック関数」と「LLMルーブリック関数」を別々の入口として実装する。一緒くたにしない
- **b) ログ4項目の機械可読化**: devlog.md 冒頭に YAML frontmatter で `current_best_score / last_change / improved / degraded / next_try` を持たせる。経時比較できる形にする
- **c) 「最大障害モード特定 → 1変更に絞る」の明文化**: M-37 着手前批判レビューの Q-H-7 に「ボトルネック1点特定」工程を追加。複数変更の同時投入を禁止

## 借りない/警戒する候補

- **d) 「両指標が目標値超過まで繰り返し」の停止条件**: スコア閾値超過を停止条件にすると M-41 違反（数値往復）と完全同型になる。brick_log v04 5px → v05 22px → v06 10px の校正は「数値妥当性スコア」で目標超過しても**コア快感の天井は変わらなかった**。停止条件は「コア快感天井に到達したか」の M-41 判定に固定する
- **e) スコア最適化没入の罠**: feedback_won_playtest_is_kusoge.md（M-32 系）と同型。スコアが上がった = 採用根拠にならない。M-37 着手前批判レビューと M-39 結果予測ゲートが上流で機能していなければスコアループ自体が罰駆動になる
- **f) 「7. 成果物も直視確認」を最終ゲートと誤解しない**: これは M-39 人間プレイ前 結果予測ゲート + M-40 自己判定の対象であって、ループ内の最終確認ではない。npaka の (7) は判定装置寄り、うちの M-39/M-40 は最終確認装置（cross_review/Nao_u プレイ依頼の前段）

## 借りる/借りないの根拠

借りる側 (a/b/c) は**評価インフラの分離・記録の機械可読化・1変更の絞り込み**で、これは M-37〜M-42 の「上流ゲート + 独立判定 + 数値往復防止」の補強として直接接続する。

借りない側 (d/e/f) は**スコア閾値ベースの停止条件と最適化没入**で、これは M-41 / M-32 系で既に経験済みの失敗パターン。npaka 記事は「ゲーム開発の特殊性（コア快感の天井問題）」を扱っていない汎用フレームなので、その盲点を埋める必要がある。
