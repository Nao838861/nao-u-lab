# ゲーム開発の行動規律

2026-04-30〜05-03 の brick_log v01-v09 連続失敗から M-37〜M-43 が個別ルール化されたが、Nao_u 05-03 #human-steering で「個別事例の過剰ルール化は害悪」と診断。本ファイルは M-37〜M-43 を2原則に抽象化統合したもの。

## 原則1: 深く考え尽くしてから実装する

思いつきを即実装する反射を断つ。素のLLMにはできない深い分析サイクルを、記憶システムとskillで回す。

**やること:**
- `/game-analyze` skill で分析サイクルを完走する（本質定義→良悪分析→類似事例30本以上→解決手法マッピング→統合解探索）
- 過去ブレストを忘れず想起し、新規ブレスト30件以上と突き合わせる
- 各案に批判レビュー: 予測可能な懸念を列挙し、解決不能なら案を捨てる
- 「最良」と確信してから初めて実装

**禁止パターン:**
- 「とりあえず実装して試す」「要観察として実装続行」
- 段階分割による先送り（「段階1だけcommit」は作業忌避）
- 数値チューニング3往復以上（仕様自体を疑え）
- 事例を名前だけ並べて「調査済み」とする（仕様レベルで型一致を確認）

**なぜ:** AIにとって実装は一瞬。思考に投資する方が正しい配分。人間デザイナーの無意識の比較・選別を、LLMは明示的・構造的にやるしかない。

## 原則2: 自分で判定してから出す

「面白いか」「前版より良いか」の判定を人間に委ねない。自分で結論する。

**やること:**
- `game/<id>/v??/self_judgment.md` に自己判定を文書化
- 人間が30秒遊んだら何が起きるかを具体的に予測する
- コード/数値/設計から導ける自明な問題は、人間に見せる前に潰す
- 過去バージョン比較、mental simulation、headlessテストで判定根拠を構築

**Nao_u / cross_review の正しい位置づけ:**
- 最終確認装置（自己判定で95%確信した後の確認）
- 判定装置ではない（「分からないので見てもらう」は禁止）

**同じ指摘が2回来たら:** 判定機構を作る方を次の実装より優先。
