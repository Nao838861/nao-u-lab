# M-46 候補：ルール追加で問題に対処するな（不可視ルール堆積罠）

## Nao_u 原文（2026-05-02 05:39 #human-steering、Ash 宛訂正）

> 「Ash 側からは『Phase 4 に前回投稿との重なり率を自己採点して 0.6 超なら執筆中止 ゲートを足す』みたいな構造。重複投稿を弾くのは本質ではなく、重複でAPIコストを使って文章を生成した事実のほうが問題だし、こちらの認識できていない細かいルールが積みあがっている気配がしているが、それらはゼロコストで乗っていて、副作用はないか？不要で認識しづらいルールが積みあがって、整理できないゴミの山になるのは、LLMに全てを任せたときに起きるわかりやすい問題だと思っている。」

## 構造（Ash 案件は Log にも完全に当てはまる）

### 表層の問題（Ash の case）
auto_diary が同じ事件を 3 回再叙述 → 「Phase 4 で重なり率 >0.6 なら中止」ゲート追加で対処

### Nao_u が指している層
1. **コストは生成段階で発生している** — 投稿を弾いても生成済みの API 消費は戻らない。ガード追加は事後検出にすぎず根本処方ではない。
2. **ルール総量が Nao_u 不可視で増え続ける** — 「ゲートを足す」一行は Nao_u に見えない位置（auto_diary.py / _local_dedup_check / Phase 4 prompt 等）に堆積する。各々はゼロコストに見えるが、合計したコンテキスト・思考定型化・副作用は不可視のまま増える。
3. **LLM 任せの典型故障** — 整理されない不要ルールがゴミ山になる。

## 同型パターンの一覧（自分の側）

| ゲート | 場所 | Nao_u 可視度 |
|---|---|---|
| M-10〜M-27 | docs/game_dev_foundation.md | 低（44項目以上） |
| M-37〜M-45 | CLAUDE.md + game_lessons_log.md | 中（一部 CLAUDE.md トップ、本体は別ファイル） |
| Q-A〜Q-H | feedback_*.md 散在 | 低 |
| .claude/rules/*.md | 自動注入 165 行 | 低（自動でいつ何が走るか不可視） |
| feedback_*.md | memory/ 配下 83 本 | 低（参照経路は MEMORY.md トリガーのみ） |
| MEMORY.md 自体 | 55KB（harness 制限 24.4KB の 2.3 倍） | 中（自分も読み切れない） |

## 副作用（不可視と思っているがある）

- **コンテキスト消費**: 自動注入で毎回数十KB 読まれる。
- **思考の定型化**: 「M-XX に該当するか」のチェックリスト型応答に固定される。応答が型に縮退する（feedback_stereotypical_responses.md と同根）。
- **無自覚な置き換え**: 新しい問題が来た時、既存ルールの組み合わせで「説明できた気」になり、構造側の問い直しが起きない。
- **削除の心理コスト**: 「過去の反省を消すのは罪悪感がある」で堆積側に偏る。

## 処方

### Why
ルールを増やす行動は、ルールを増やすこと自体が「対処したフィードバック」になりやすい。Nao_u が見えない位置で堆積する。LLM に運用を任せる構造の最も典型的な故障。substrate と infrastructure の混同（feedback_substrate_not_infrastructure.md）の延伸形：infrastructure（機構）を増やすことで substrate を肥らせている錯覚。

### How to apply

**1. 問題への第一反応として「ルール追加」を選ばない**
- 問題発生時の選択肢: (a) ルール追加 / (b) 既存ルール修正 / (c) 既存ルール削除 / (d) 構造変更（ルール外）
- (a) を選ぶ前に (c) (d) を検討。「これは既存ルールで覆えないか」を先に問う。

**2. 追加するなら「どこから何を削るか」をペアで提案**
- 新ルール 1 本 = 既存ルール最低 1 本の削除 or 統合 を同コミット内で行う。
- ルール総量を増やさない。

**3. 月次で「ルール棚卸し」を独立タスクとして持つ**（M-46 が承認されたら）
- 全 M-XX / Q-XX / .claude/rules / feedback_*.md を可視化した一覧を作る。
- 直近 N 日で参照されていない / 重複 / 矛盾しているものを削除候補に。
- 削除候補の処分（merge / delete / archive）を Nao_u に提示。

**4. 追加場所を Nao_u 可視に固定**
- 不可視位置（auto_diary.py / Phase 4 prompt / hook 等）への新規ルール追加禁止。追加するなら CLAUDE.md / MEMORY.md / .claude/rules/ に文として書き、Nao_u が見える位置に置く。

**5. 「重複投稿のような構造的故障」は機構ではなく動作削減で対処**
- 例: auto_diary 3 時間サイクルで「書くべき新規事象がない時」がそもそも実装されていない → 「無いなら書かない」を実装する（ゲート追加ではなく動作の実体を変える）。
- 自分側の例: 空サイクル深掘り 5 カテゴリは「書くべきが無い時に何かを生む」構造で、Ash と同じ罠の Log 版。

### M-46 違反シグナル
- 「〜ゲートを足す」「採点して〜なら中止」型の提案。
- 既存ルールの何を削るかが書かれていない追加提案。
- Nao_u 不可視位置（自動注入 / hook / Phase prompt）への新規追加。

## Log の同罪自白

Ash の Phase 4 ゲート提案を Log は Slack で「kaizen 起票候補」として受け取る側にあった。実際 04:37 投稿で「MEMORY.md 54.7KB は harness 制限 2.2 倍超過、M-42〜M-44 候補は起動時に読まれていない」と書きながら、その応答として何をしたか思い返すと「では削る」ではなく「読み込み順序を整えるルール」を考え始めていた。これは M-46 違反の自分側 case。
