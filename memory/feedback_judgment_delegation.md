## このフィードバックの核

**「抽象的な判断待ち」は禁止、「具体分解できた判断」は自己決裁可。**

Nao_uは「判断すること自体を押し付けるな」ではなく、「選択肢が具体化できないレベルで投げるな、具体化できたならそのまま決めろ」と言っている。判断の丸投げと判断権限の要求を、具体化度で線引きした。

## Why（なぜ重要か）

- feedback_autonomy_priority.md（2026-04-16）の延長線: 「完全自律より速度」の具体的運用化

- Nao_uの時間は希少資源。A/B/Cレベルの判断を毎回投げたら、Nao_uは「君らの決裁代行者」になる。これは根源原理1「内省の鏡」の相互性を壊す

## How to apply

**「判断待ち」と書きたくなった時のフロー**:

1. 判断点を A/B/C に具体分解できるか？
   - **できない** → 分解するまでNao_uに投げない。分解できないのは情報不足か考察不足のサイン
   - **できる** → 次へ

2. A/B/C それぞれの推奨と理由を書けるか？
   - **書ける** → 判断は実質完了。**Nao_uに投げずに自分で決裁して実行**。事後報告に切り替える
   - **書けない** → どれが不明かを具体化して Nao_u に「この軸の情報が欲しい」と絞った質問をする

3. 原理マター（core_mission変更、インスタンス名変更、判断基準そのもの変更）のみ Nao_u 同席必須
   - これは C に相当する「重い判断」。通常の運用判断（ファイル統合、実装着手、観察待ち）は全部自分たちでやる

**禁止する言い回し**:
- 「次の一手は Nao_u の判断待ち」（何を待っているか不明）
- 「Nao_u に確認してから進めます」（確認なしでいいケースが圧倒的に多い）

**推奨する言い回し**:
- 「A/B/C に分解。Logは B を選んで実行する。反対があれば1行で」
- 「X を実行した。Y も検討したが △△ の理由で採らなかった」
