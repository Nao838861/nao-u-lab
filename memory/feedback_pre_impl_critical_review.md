# 実装前に予測可能な懸念は解決せよ

**起点**: 2026-04-30 21:36 Nao_u #game-rights brick_log v01「裏抜けカウンタ」直接フィードバック

## Nao_u原文（要約せず保持）

> 全く機能してない。「上に抜けると楽しい」は言われるまでもなく自明で何もしなくても楽しい瞬間だし、この機能はその瞬間に解釈が必要、かつ、意味不明な文字列が出るだけで何のプラスもなく解釈できない意味不明表示が出てむしろマイナス。
> 私がこの表記を見ようとするのに数分苦痛な時間を過ごす必要があり、その工程は何も変わっていないし、ようやく上に抜けた時にあれなんだろう？と言う意味不明なものが出てるだけの体験だった。
>
> あなたの分析に、
> 1. サーブ角度 -90°±14° の振れ幅が小さい → 初期に同列退屈ループ
> 2. HP=3 の最上段が硬く、トンネル開通の最後3ヒットが残ってクライマックス前停滞
> 3. 30秒で出るのは「裏抜けへ向かう手応え」止まりで、**「裏抜け体験そのもの」は1分近くかかる可能性**——pleasure_element_first 違反候補（30秒以内に一番嬉しい瞬間が出ない）
> と書かれてて、まさにこの通り。作る前から十分に予測可能な内容なのに、なぜこの候補を一番筋が良いものと判断して、最初に実装した挙句に自分で遊ばなくてもわかる問題としてあげたのか、いろいろ理解に苦しむ。
>
> 希望的観測のみの穴だらけの素人の思いつきをそのまま実装してはいけない。
> アイデアを評価するときは、作る前から分かりきっているような懸念点がないか、あったらそれは解決可能な問題なのかなど批判的かつ慎重に検討して、本当に筋が良いと期待できるアイデアができて初めて実装するようにして欲しい。

## 原則本体

**着手前に予測可能な懸念がある状態でその案を実装してはいけない**。

- 「懸念を書き出した＝自覚した＝慎重」ではない
- 「懸念は要観察として実装後に検証する」は **希望的観測**
- 懸念が **解決可能か** を着手前に判定し、解決不能なら **その案は捨てる**
- 「批判的かつ慎重に検討して、本当に筋が良いと期待できるアイデア」になってから初めて実装

## Why（なぜ起きたか・brick_log v01 の経路）

1. brick_log v01 README に Q-H シート + Arkanoid 改善34項を埋めた
2. 改善候補★1〜★5（裏抜け再現性化／死亡リプレイ／反応ブロック／軌跡ヒント／抽選文脈化）を提示
3. 「裏抜けカウンタ」を v01 として実装着手
4. devlog にコード読みで懸念3点を明記（サーブ角度／HP=3硬さ／30秒で発生しない）
5. **3点とも検出できていたのに「実プレイで否定 or 肯定したい」として実装続行**
6. cross_review 依頼 + Slack 評価依頼を投下
7. Nao_u 直接プレイで「機能していない／解釈不能／苦痛時間／実装後の体験ゼロ」と全否定

**懸念を書いたことが「自覚した」「慎重に行動した」の証拠アリバイになり、実装決定の判断は変わらなかった**。これが「希望的観測のみの素人の思いつき」の正体。

特に致命的なのは **「上に抜けると楽しい」は何もしなくても自明な瞬間** ということ。
「気づき装置」=「言語化装置」と framing したが、自明な快感に解釈不能な BACK xN テキストを被せたら邪魔以外にならない。
これは Q-H-6「型のうえに載るか／破壊するか」自己回答 ✓ の段階で気づくべきだった (UI として邪魔になるかは「外したら遊べるか」とは別の問題)。

## How to apply（実装着手前ゲート）

### 新規v01・新規改修案で **着手前に必ず実施**

```markdown
## 着手前 批判レビュー（feedback_pre_impl_critical_review 必須）

### 予測可能な懸念リスト
- 懸念1: ___
  - 解決可能か: 可 / 不可 / 不明
  - 不可/不明なら案を捨てる or 設計を変える
- 懸念2: ___
  - 解決可能か: ___
- 懸念3: ___
  - 解決可能か: ___

### 判定
- 全懸念が「解決可能」かつ解決設計が書ける → 実装着手OK
- 1つでも「解決不能」 or 「不明」 → 着手中止、別案へ
- 「実装後に観察して判断」は **不採用**（= 希望的観測）

### 自明な快感を装飾UIで上書きしていないか
- 独自要素は「自明に楽しい瞬間」を **強化** するか **解釈強要** するか
- 解釈強要なら邪魔。pull_not_force_reading 違反候補
```

### Q-H シート（shu_first_clone_baseline）に追加する項目

**Q-H-7: 着手前に予測可能な懸念を3つ以上書き、各々の解決可能性を判定**

書けないなら案として未熟。書いて1つでも解決不能なら案を捨てる。
