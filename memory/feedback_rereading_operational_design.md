# 再読サイクル運用設計（初回所見3点）

**ルール**: `memory/game_lessons_log.md` / `game/*/pot_devlog.md` / `game/*/raw_log.md` のような**累積型ドキュメント**を定期再読する運用を回すとき、次の3点を守る。

## Why（2026-04-21 C101 Phase 3 Log 初回実行で結晶化）

前サイクル C100 で Nao_u 13:27「記憶システムの目的宣言」（ゲーム制作の試行錯誤知見蓄積／単発記憶AIと長期蓄積AIのゲームは次元が違う）を受け、「繰り返し確認・再読運用拡張」を宣言。C101 Phase 3 で初回実行したところ、`game/log_textadv_01/README.md`（C97 起票）が `game_lessons_log.md` の「次作4ゲート契約」を 0/4 で満たしていなかったことを検出。起票翌日に書いた契約を起票翌日に違反していて、再読しなければ opening.md 着手で違反のまま実装に入るところだった。**「繰り返し確認」の効能が初回で即発火した実行証拠**として、運用設計を3点抽出した。

## 運用設計3点

### (i) 再読は「検索」ではなく「現在の着手点を持って過去に当てにいく照合」

- 着手点（今サイクルでは log_textadv_01 起票翌日）が無いと再読は散る。漫然と読むのではなく、**「今着手しているもの／これから着手するものが、過去の契約・教訓・設計原則に違反していないか」**の照合として使う
- 着手点が無いサイクル＝「読むべき理由が無い」サイクルは、**再読を強制せず「発見なし」で短く記録**する（空振りこそが運用の安定を測る材料）
- 着手点は ⊆ {次サイクル実装予定, 起票翌日のREADME, 改修予定ファイル, 行き詰まり中のPot, 他インスタンスからの指摘}

### (ii) 発見は1つに絞る

- 多点抱え込みは Phase 3 を散らす。**1サイクル1発見**で構造を動かすほうが累積する
- 複数見つかった場合、最も「次サイクルで契約違反のまま実装に入るのを防ぐ」効果が高い1点を選ぶ
- 残りは `drafts/` 等に「発見候補ストック」として残し、次サイクルの着手点として拾い直す

### (iii) 発見そのものが Phase 3 の 1mm 成果として正当化される

- **実装を動かさなくても構造を動かした扱い**にする（`feedback_empty_cycle_rule.md` 精神の拡張）
- 具体的な Phase 3 成果物: (a) 違反箇所に ⚠警告ブロック追加、(b) 隣接 devlog に「再読発見 YYYY-MM-DD」節追記、(c) 次サイクルの着手プロトコル規定
- 「読んだだけ」で終わらせず、**読んで動かした構造の残骸**を Phase 3 成果として記録する

## How to apply

- **サイクル開始時**: Phase 1 staging_log で「今サイクルの着手点」が特定できたら、再読対象（game_lessons_log.md / 関連devlog.md / 関連raw_log.md）を明示
- **Phase 2 or 3**: 着手点を持って再読→1点発見→(a)(b)(c)の Phase 3 成果物を生成
- **着手点が無いサイクル**: 再読を強制しない。「着手点なし・再読見送り」を staging に明示
- **空振り時**: 「再読実行・発見0件」を短く記録（実行自体を習慣化）

## 検証トリガー

- 次サイクル (C102) Phase 1 で「再読対象を着手点とセットで staging に書けたか」
- 3日後（2026-04-24）に C101〜C104 の再読実行率＋発見件数を振り返る
- 1週間後（2026-04-28）に「空振りを短く記録する運用」が回っているか（空振りを恥じて長文弁解していたら運用崩れ）
