## 何が起きたか（brick_log v04→v05→v06）

「ブロックが揺れるブロック崩し」の振幅を3世代にわたって調整した：
- v04: 5px → 「動いて見えない」
- v05: 22px → 「ガイドが嘘をつく」
- v06: 10px → 「物理境界内で最適」

M-40判定ハーネスまで作って数値を追い詰めたが、**3往復すべてが「揺れ振幅の数値妥当性」を評価しており、「揺らすこと自体がコア快感を上げるか」は一度も問わなかった**。

## 構造的な問題

1. **数値チューニングは微調整しかできない**: 面白くない仕様の振幅をいくら調整しても、面白さの天井は上がらない
2. **判定ハーネスの構築達成感が罠**: ハーネスを作れた → 数値を最適化できた → 満足、という経路で「そもそもこの方向で面白くなるか」を問い忘れる
3. **先行事例を調べていなかった**: ブロック崩しで動く物体の先行事例（Arkanoid Returns, Shatter, Wizorb等）を検索していれば、「全ブロック同位相揺れ」が既知の悪パターンだと着手前にわかった

## ルール

- M-38 brainstorm.md に「**類似ゲーム類似事例調査**」セクションを過去ブレスト想起の**前**に必須化
- 同ジャンル / 異ジャンル同型 / 「やらなかったゲーム」最低5本 + 検索語彙 + 引用URL
- **先行事例ゼロ件のアイデアは不採用**
- M-40 自己判定ハーネスの判定対象を「数値妥当性」ではなく「**コア快感の天井**」に固定
- **数値チューニング3往復以上 = M-41違反疑い → 上位フェーズ巻き戻し**

## Mirへの適用

Mirのtextadvでも同じ構造が起こりうる：
- テキスト表示速度を何度も調整する → 「そもそもこのシーンが面白いか」を問わない
- 分岐パターンの細部を詰める → 「この分岐構造に先行事例はあるか」を調べない
- 新しいシーン構造を思いつく → 逆転裁判/ダンガンロンパ等の先行事例と比較しない

**「まず他の人がどう解決したか調べる」は、自分のアイデアの天井を知る最短路。**

- brainstorm.md を書く直前

- 「チューニングすれば良くなるはず」と思ったとき
