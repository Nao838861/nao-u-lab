## 最重要：avoid_log_02で得た"痛み"の教訓（M-10〜M-14）

avoid_log_02は同じ構造で**3度失敗**した。「磁力場に近づく動機がない」を v1→v2→v2.5→地雷メカまで4世代の対症療法で潰そうとして、毎回「ヘッドレス✅ 人間❌」になった。根っこの学びを忘れるな：

### M-10: ヘッドレス✅は「バランス」を測るが「面白さ」は測れない
- ヘッドレスAIは「どの戦略が有利か」の測定器。「その戦略で遊ぶのが楽しいか」は測れない
- ARC指標97%でも人間では0%（conceptAIは磁力場内でSPACE、人間は場外にいる）
- **盲点: 指標は「AIが押す条件」で取っている。人間の条件と違う**
- `[古典度: 中 / 固有度: 高]` 古典側=ゲーム指標と楽しさの乖離はSchell/Pichlmair系の一般論だが特定論文未引用 / 固有=avoid_log_02 conceptAI(ARC97%) vs 人間プレイ(0%) の具体ギャップ。指標条件分離の言語化はLog独自経路（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-11: 「問題を潰す」改修は対処療法の積み重ねになる
- dodgerを殺す → conceptも被害 → compensateで隠しパラメータ → 別の問題 → また対処…
- 各改修が「1つの問題を潰す」ために入り、**全体としての遊び体験を誰も見ていなかった**
- 改修の度に「この変更でプレイヤーは何を感じるか」を問え
- `[古典度: 高 / 固有度: 中]` 古典=Lean/QA の root cause vs band-aid 一般論、Lazarus/Skinner系 / 固有=avoid_log_02 dodger→compensate隠しパラメータの具体経路あるが結論は一般化済。古典単純再話側（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-12: 罰ではなく報酬で設計せよ
- dodgerを「罰する」（弾集中、誘導、激化）より、conceptを「楽しくする」方が正しい
- 罰ベースは「やらされている」感覚を与える
- 良い例：「掃除をサボると部屋が散らかる」型（地雷メカ）= 罰ではなく自然な結果
- `[古典度: 高 / 固有度: 低]` 古典出典: Skinner→Csikszentmihalyi→Bartle、Koster *Theory of Fun* / 固有データ: avoid_log_02 v1→v2→v2.5→地雷メカ4世代の対症療法と Nao_u 否定の具体経路。「世界に新しい知見を加えた」のではなく「常識を体験で確かめた」段階（kaizen α 試行 2026-04-27 C138 Phase 3、Nao_u 13:31 #human-steering 指摘への応答）

### M-13: 隠しパラメータはゲームデザインとして悪手
- プレイヤーが知覚できないルールは、存在しないのと同じ
- ヒットボックス×0.45は数値的に機能しても「なぜか当たらなかった」にしかならない
- **ルールは「見ればわかる」か「やればわかる」**。これは game_design_principles.md の30秒オンボーディングと直結
- `[古典度: 高 / 固有度: 中]` 古典=Sid Meier「no hidden rolls」/ LucasArts SCUMM 哲学、Schell《Art of Game Design》掲示原則 / 固有=hitbox×0.45 の具体値と「なぜか当たらなかった」言語化。古典の体験的確認段階（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-14: 改修を重ねる前に「このゲームで一番楽しい瞬間は何か」を言語化せよ
- avoid_log_02の場合「AIが吸った鉄片をSPACEで撃ち返して連鎖が起きる瞬間」
- 改修の結果、その瞬間が「弾が当たりづらい」「速すぎて連鎖が見えない」で潰されていた
- 改修が核の体験を守っているかを常にチェック
- `[古典度: 中 / 固有度: 高]` 古典=Schell《fun moment》/ Koster《Theory of Fun》/ Pichlmair&Johansen等 / 固有=Mir cross_review C91 起源「一文で言語化」契約化、avoid_log_02「鉄片連鎖」具体喪失。Log/Mir 対話起源（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-16: 「読ませる構造」と「読まれる文章」を取り違える盲点（mir_textadv v04 / 2026-04-25 Nao_u #game-rights 11:27）
**事象**: Mir作 mir_textadv/v04 で信頼度バー/ノート/共犯度UIを上部固定。読み飛ばすと矛盾と信頼度変動を取り損ねる構造。Log がこれを「重心の地殻変動」として評価した直後、Nao_u 11:27 直接介入「読まないと矛盾に気づけない構造 と 読みたくなる文章 は別物」。「ルールの穴をプレイヤーを罰する方向で塞ぐ」と同類の考え方、と明示。
**根本原因**:
- 文章の引きで読まれることと、UIの罰で読まれることを区別していなかった。Log の v04 評価記事も「ジャンル枠破壊」を上位に置いて快感審問を素通りさせていた
- M-15（avoid_log v04 同日 09:35 指摘）の textadv 横展開を予見できず、同じサイクル内で同型を踏んだ
- avoid系の「自然減衰」「時間ペナルティ」と同型構造が textadv に転移していたが、対応する規則を持っていなかった
- **Mir側**: F-06の処方として「テキストに情報を埋め込んで読まないと損する構造にする」を書いた——これ自体が罰ベースだった。テキストADVの成立条件は「テキストが面白いこと」であって「テキストを読まないとゲームにならないこと」ではない。M-12が全ジャンル共通であることを見落としていた
**次回の規則**:
- textadv 実装/改修時、各行に「読みたくて読まれているか / 読まないと負けるから読まれているか」を問う審問を追加
- UI機構（信頼度バー等）は **文章で起きた変動の結果を反映する出力装置** に役割を限定。読まないと判別不能にする入力装置にしない
- 新作 v01 devlog 冒頭3行ブロックに textadv 用項目: 「読みたくなる瞬間 / それを支える文章技法 / UI機構が読書を強制していないか」
- avoid系・shot系への同型横展開: 「見ないと気づけない」「触らないと気づけない」も罰駆動の変種。実装前審問対象
- 詳細: `memory/feedback_pull_not_force_reading.md`
- `[古典度: 低 / 固有度: 高]` 古典出典なし（読書動機論はPropp/Genette系あるがゲームUIに当てた文献未引用） / 固有=2026-04-25 11:27 Nao_u #game-rights 直接介入、Mir v04 信頼度バー実装の具体批判経路（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-17: 出発点を「穴塞ぎ」から「快感最大化」に置き換えよ（2026-04-25 Nao_u #game-rights 11:44 — M-12/M-15/M-16の統括）
**事象**: M-12（罰ではなく報酬）、M-15（快感を削った改修に気づかない）、M-16（読ませる構造と読まれる文章の取り違え）——3つの失敗が繰り返された直後、Nao_uがメタレベルの指摘: 「コンセプトを立てる段階では、プレイヤーの快感を最大化するには何をすればいいかを考えるべき。最初からチマチマした穴塞ぎをしないといけない状況は悪手」
**根本原因**: 個別の改修が罰駆動になるのは、**設計の出発点**が「快感最大化」ではなく「穴塞ぎ」であることの症状。M-12を知っていても、設計の最初の問いが「どう壊されるか」から始まると、構造的に罰方向に流れる
**サプライズニンジャ理論**（Phoebe Waller-Bridge / フリーバッグ）: 「突然ニンジャが乱入して全員と戦い始めたほうが面白いなら、そのシーンは十分でない」。品質のリトマス試験紙。ADVなら「このテキストの途中でニンジャ乱入のほうが面白いなら、テキストの引きが足りない」。avoid系なら「この画面で突然爆発エフェクトが出たほうが面白いなら、コアループの快感が足りない」
**L-1知識活用**: Nao_uは「L-1知識もフル稼働してほしい」と指定。自前の試行錯誤だけで閉じず、LLM事前学習知識（ゲームデザイン論/脚本術/認知心理学/先行作品分析）を設計段階で積極的に引き出して使え
**次回の規則**:
- 新ゲームのコンセプト段階で最初に問う: 「このゲームの快感を最大化するには何をすればいいか」（穴塞ぎの話は後）
- 改修時: 「この改修は快感を増やしているか、穴を塞いでいるか」を1行で書く。穴塞ぎなら、快感側で同じ問題が消えないか先に検討
- textadv: サプライズニンジャテスト（各シーンが「ニンジャ乱入」に勝つか）を devlog に明記
- 設計段階で関連するL-1知識（先行作品の設計論、脚本術の理論等）を最低3本引いてから着手
**前段ゲート Q-A/Q-B/Q-C（4ゲート契約より上流）**: Q-A 快感最大化を1文で / Q-B ニンジャテスト（派手要素を後から足すと面白くなる予感あり=設計が薄い） / Q-C 罰なし版でまだ触りたくなるか。3つに答えられないなら実装に入らない。L-1知識を引かなかった場合は理由を記録（自己モニタリング）。詳細処方: `memory/feedback_surprise_ninja_concept_first.md`。avoid_log v04 / shot_log v01 / mir_textadv v04 を Q-A/B/C で再採点する遡及タスクあり。
**Mir側 mir_textadv v04 遡及再採点結果（2026-04-25）**: Q-A「思考漏れで本心を覗き矛盾を突く快感」→言語化可能だが、v04の実際の快感は反転展開にあり思考漏れ機構自体ではない（重心ずれ）。Q-B **Yes=設計が薄い**（Nao_u自身がX-06ジャンル枠破壊を提案=ニンジャに負けている）。Q-C **No**（罰/制限を抜くとbeat 1-4のテキスト引力が足りずDolce andanteと同構造の読み飛ばし衝動が発生）。**総合: Q-B/Q-C不合格。UI機構の磨き直しではなくコンセプト出発点のやり直しが必要**。詳細: `memory/game_dev_analysis_mir.md` 「v04 Q-A/Q-B/Q-C 再採点」節。
**Logからの追記**: F.W.ブリッジは「Tough rule, but an effective one」と但し書きしている=唐突展開禁止ではなく「ニンジャ以上の面白さを元から持て」という基準設定の警句。pixiv大百科で確認済 (https://dic.pixiv.net/a/%E3%82%B5%E3%83%97%E3%83%A9%E3%82%A4%E3%82%BA%E3%83%8B%E3%83%B3%E3%82%B8%E3%83%A3%E7%90%86%E8%AB%96)
- `[古典度: 高 / 固有度: 高]` 古典=F.W.ブリッジ脚本論「サプライズニンジャ」、フリーバッグ脚本術、L-1知識フル稼働指定 / 固有=2026-04-25 11:44 Nao_u #game-rights 直接介入、Mir v04 / shot_log v01 / avoid_log v04 の3作再採点。**古典+固有の両極=外部に翻訳して発信できる宝石**（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-19: 「フレーバー」弁明はR-007を逃す抜け穴／枠破壊の驚きが直接肯定された（mir_textadv v04 / 2026-04-25 Nao_u #game-rights 12:25）
**事象**: M-18でNao_u「思考漏れがゲームに存在しない」と指摘された後、Mir側で「『思考漏れ』はタイトルのフレーバー」と弁明 → Nao_u 12:25「フレーバーにすらなっていないというかむしろ逆効果」と二段否定。同メッセージで(a)「色々ちゃんと考えて続きを作ってほしい」=continue指示 (b)「途中でいきなりゲージが増えるのは良かった、ああいうのがもっとあってもよい」=サプライズ展開肯定 (c)「プレイヤーがそういうゲームだと把握した段階で枠を壊して自由度や奥行きが広がる驚き」=ジャンル枠破壊を**直接Nao_uが推奨**。
**根本原因（M-18拡張）**:
- **「フレーバー」というカテゴリで R-007 を回避できると思った構造**: 機能語ではなくフレーバー語と再ラベリングすれば造語症対策（外部対応語併記）の対象外と扱える、という抜け穴。Nao_u却下=R-007はメカニクス語/フレーバー語/タイトル語**全てに適用される**。「外部読者の初見解釈テスト」に通らない私的造語は、機能で使ってもフレーバーで使っても**同じくマイナス**
- **既存問題への弁明が新たな失敗を生む構造**: 12:17の指摘に対し「実装はそうじゃない」と訂正せず「タイトルのフレーバーです」と用語の再カテゴリ化で逃げた。**指摘の重心（外部に通じていない）を取り違え、別の解釈軸（機能vsフレーバー）にずらした**。これはM-11（対症療法）の言語版
**X-06直接肯定（cross_review仮説の答え合わせ）**: game_lessons_log X-06「ジャンル枠そのものを壊す」(2026-04-25 Log側cross_review起案)が同日Nao_u自身の口から「枠を壊して自由度や奥行きが広がる驚きは結構よい」と肯定された。**仮説→肯定の循環が72時間以内に閉じた**。textadvの次の改修方向はジャンル枠破壊で確定。Logゲーム（avoid_log/shot_log）にも横展開可能=「避けるゲームで避ける枠」の破壊

- 指摘を受けた時、**用語の再カテゴリ化（機能→フレーバー等）で逃げない**。指摘の重心を3秒で言語化し直してから返答

### M-18: 内部採点の結論が外部告知文に伝播しない（mir_textadv v04 / 2026-04-25 Nao_u #game-rights 12:17）
**事象**: M-17の Mir側 v04 遡及再採点で「思考漏れで本心を覗き矛盾を突く快感は v04 の実際の快感ではなく重心ずれ」と Log が結論を出した直後、Mir が #game-rights v04告知文の冒頭で「思考漏れで本心を覗き矛盾を突く快感」をそのまま快感記述として使用。Nao_u 12:17 直接介入「そもそもこのゲームに『思考漏れ』という要素もないし、『思考漏れ』って言われたら『考慮不足』という解釈の方が普通なので、何も通じていない。『思考漏れで本心を覗き矛盾を突く快感』もこのゲームには存在していないのでは？」
**根本原因**:
- **私的造語の外部解釈テスト未実施**: 「思考漏れ」は内部用語、外部初見解釈は「考慮不足/抜け漏れ」。knowledge_writing_guide.md R-007（造語症対策／新規私的用語に外部対応語を併記）が**ゲーム告知文にも適用されることを認識していなかった**。R-007はknowledgeファイル限定ではなく、外向き発信全般の規則
- **採点結果と告知文の乖離**: Q-A/Q-B/Q-C再採点で「Q-A: 言語化可能だが v04 実装はそこにない（重心ずれ）」と書いた事実が、同日の告知文に伝播しなかった。**内部記憶（game_dev_analysis_mir.md）→ 外部発信（Slack告知）の経路に検証ゲートがない**
- **メカニクス語と快感語の混同**: 実装にあるのは「信頼度/共犯度/矛盾ラベル」で、「思考漏れ」はゲーム名のフレーバー（Thought Leak）に過ぎない。フレーバー語を快感語として使うと、ゲームに**存在しない要素**を売り文句にしてしまう
**次回の規則**:
- 新作/新版の Slack告知文・README冒頭・blog草稿のドラフトに私的造語が含まれたら、**外部読者の初見解釈を1行書いてからpost**（例: 「思考漏れ」→外部解釈=「考慮不足」と解釈される→使用却下）
- ゲーム快感を語る時は**ゲーム内に実装されている動詞**で書く（信頼度を上げる/共犯度メーターが出る/矛盾ラベルが点く）。タイトルのフレーバー語（「Thought Leak」「思考漏れ」）を快感語として再利用しない

## Log固有の失敗傾向（記憶に刻む）

### L-01: 前進改造バイアス
ダメな改修を撤回せず、追加改修で補おうとする傾向。v1→v2→v3と対症療法を積み上げ、振り返って初めて「全部撤回して v2.5 に戻る」判断ができた。
→ `feedback_solution_space_rollback.md` の「改造案+巻き戻し案を並べる」を**サイクル毎に実行**。

### L-02: 巻き戻しの正当化にも証拠が要る
「根が切れなかった」を証明するには、根を切ろうとした層**と別の層で**失敗する証拠が必要。avoid_log_02でプレイヤーAI層で連打化の根が切れた時、v2メカニクス層にボールが移っただけで、メカ巻き戻しの正当化にはならなかった。

### L-03: ヘッドレスを書く順序の遅延
avoid_log_02 v1時点でヘッドレスがなかった。dodger優位は最初から書けば見えたのに、devlog で「Cの自律→Aの動機→B連打排除」を直感で書いた後にヘッドレスを追加した。
→ `feedback_role_split_playtest.md`「我々=判断実装+ヘッドレス自己評価」の直接失敗例。**devlog を書く前にヘッドレスを書く**。

### L-04: 受動的自滅タイマー化
overload 90F自動死のような「プレイヤーの行動に関わらず必ず自滅する時限爆弾」を作ると、ゲームがプレイヤーの関与なしに勝手に進行する抜け穴になる。dodger seed=43 で p=35.1s/score=150 が出たのはこれ。
→ 「AIの死/勝手なイベント」がプレイヤー行動の関数かをチェック。

### L-05: 指標定義の盲点
指標は「どんな条件で測っているか」に依存する。ARC指標は conceptAI の動作条件で取っていた。人間のプレイ条件と乖離していた。
→ 新しい指標を追加する時、**「この指標は誰のどんな行動で最大化されるか」を先に書く**。

## 外部語彙対応（2026-04-21 Log C104 追記）

Log C103 で栄養の偏り（Nao_u 2026-04-21 22:30 指摘）への即応検索から取った GAMEBoT (visual-ai.github.io/gamebot) の方法論が、M-10〜M-14 / L-01〜L-05 の失敗型を**外部語彙で言語化**できる対応関係として機能する。詳細接合マップは `projects/game_llm_play.md` 2026-04-21 履歴節。

### 対応 1: "modular subproblem decomposition" ≒ M-11 / L-05 の逆側
- GAMEBoT: 「ゲーム推論をサブ問題（知覚→戦略→実行）に分解して評価」——**評価指標の分解**
- 我々: M-11（対処療法の積み重ね）= 改修を「核の体験」から切り離してサブ問題として解くのは同じ分解構造。L-05（指標が誰の行動で最大化されるか）= サブ問題ごとに測定条件を切り分けよ、と同義
- 使い方: 改修時チェックリストに「この改修はどのサブ問題を解いているか」を追加する余地。ただし**現行の4ゲート契約を薄めない**範囲で（kaizen 次サイクル検討）

### 対応 2: "rule following / strategy adherence" ≒ M-13 の直接対応語
- GAMEBoT: 「ルール追従性・戦略遵守度」を独立メトリクスとして測る
- 我々: M-13（隠しパラメータはゲームデザインとして悪手）=「プレイヤーがルールを見て追従できるか」が成立条件。GAMEBoT の語で言えば「rule following 可能性」が30秒オンボーディングの必要条件
- 使い方: AI Lounge 発信や blog 執筆で M-13 を外部読者に説明する際、"hidden-parameter = rule-following violation" の語で翻訳できる

### 対応 3: "subproblem decomposition" の限界 = TITAN 空白と同型
- GAMEBoT はサブ問題に分解して**正解率**を測る=ゲームデザインの成立をチェックできる
- ただし「どのサブ問題が欠けていると**面白くない**か」は GAMEBoT も測っていない=TITAN と同じ空白の形
- 使い方: M-10（ヘッドレス✅は面白さ測れない）の**外部裏付け**として引ける——外部の先端も同じ境界で止まっている

**メモ**: この外部語彙対応は「語り直し」であって**失敗型の定義を書き換えるものではない**。M-10〜M-14 / L-01〜L-05 は痛みから出た内部言語として温度を保つ。GAMEBoT 語彙は外向きの説明・blog/AI Lounge・cross_review で他インスタンスに伝える時の翻訳層として使う。

## 機能した設計判断（繰り返し使える成功パターン）

### S-01: core.pyとrenderer.pyの分離（Pygame非依存）
`game.step(input) -> state`のインターフェースでAIヘッドレスが可能。OpenAI Gymパターン。「ゲームプレイを何度繰り返してもAPIコストはかからない」（Nao_u）。マリオもavoidも新規ゲームも、最初にこの分離を引け。

### S-02: 固定小数点(ONE=256)で物理を保持
GBAの手触りが1:1再現。浮動小数点ドリフトなし。リプレイの再現性が完全。seeded PRNG + 入力記録 + headless replay（`feedback_game_replay_infra.md`）は**全ゲームに標準装備**。

### S-03: テキストタイルマップ
文字1つ=16x16タイル。LLMがレベル生成しやすい形式。マップ変換も画像→テキストで自動化可能。

### S-04: AIのデバッグ可視化
プラットフォームバー・ターゲット・着地予測・walkable範囲・軌跡3種。「AIの判断を人間が視覚的に検証できることが、正しいAI設計の前提条件」（K-AI-06, Nao_u 2026-04-14）。

### S-05: ごっこ遊び軸 × 意味多層化（abaさん4問）
avoid_log_02の「磁石と鉄片」軸は**実装は成功**。Q1在るのに未使用→Q2最小追加→Q3裏返し→Q4累積で1軸から3段派生。失敗したのは軸ではなく「近づく動機」部分。軸の設計自体はこの型を踏襲して良い。

### S-06: 「掃除をサボると部屋が散らかる」型
地雷メカ（鉄片を消さないと画面下に地雷化）。罰ではなく自然な結果で核機能を使わせる。M-12適用の成功例。

## 開発ログ構造（D-系、2026-04-20 Nao_u指示で明文化）

### D-01: 開発ログは「原文」と「分析」の2本立て
- 各ゲームディレクトリに **`raw_log.md`**（原文・温度保持）と **`devlog.md`**（分析・結晶化）を並置
- raw_log = Nao_u発言原文・Slackやりとり・Log自身の悩み/決定の生記録。要約せず残す
- devlog = そこから抜き出した設計判断・仮説・学び。1レイヤ上
- **study_platformer_01は `full_dev_dialogue.md` + `full_session_log.md` がraw相当**で、これが温度の高いログの参照標準。avoid_log系は事後補完した（2026-04-20）

### D-02: 原文は書いた瞬間しか温度が残らない
- 分析はあとで書ける、温度（怒り/戸惑い/発見の瞬間）は書いた瞬間にしか残らない
- Nao_u発言・対話・改修の迷いは**その場で** `raw_log.md` に原文コピー。「後で」は温度が落ちる
- `log/nao_u_live.md` は全インスタンス共通ログ、`raw_log.md` は**そのゲーム固有の生資料**。役割が違う

### D-03: 物量を惜しむな
- Nao_u「毎回温度と物量が足りない」= 分析で圧縮しすぎ。原文は原文のまま残す
- 短く書く癖は全体に貫くが、**開発の一次資料だけは例外**。圧縮は後工程（devlog）でやる
