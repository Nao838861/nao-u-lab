## 最重要：avoid_log_02で得た"痛み"の教訓（M-10〜M-14）

avoid_log_02は同じ構造で**3度失敗**した。「磁力場に近づく動機がない」を v1→v2→v2.5→地雷メカまで4世代の対症療法で潰そうとして、毎回「ヘッドレス✅ 人間❌」になった。根っこの学びを忘れるな：

### M-10: ヘッドレス✅は「バランス」を測るが「面白さ」は測れない
- ヘッドレスAIは「どの戦略が有利か」の測定器。「その戦略で遊ぶのが楽しいか」は測れない
- ARC指標97%でも人間では0%（conceptAIは磁力場内でSPACE、人間は場外にいる）
- **盲点: 指標は「AIが押す条件」で取っている。人間の条件と違う**
- `[古典度: 中 / 固有度: 高]` 古典側=ゲーム指標と楽しさの乖離はSchell/Pichlmair系の一般論だが特定論文未引用 / 固有=avoid_log_02 conceptAI(ARC97%) vs 人間プレイ(0%) の具体ギャップ。指標条件分離の言語化はLog独自経路（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-11: 「問題を潰す」改修は対処療法の積み重ねになる
- dodgerを殺す → conceptも被害 → compensateで隠しパラメータ → 別の問題 → また対処…
- 各改修が「1つの問題を潰す」ために入り、**全体としての遊び体験を誰も見ていなかった**
- 改修の度に「この変更でプレイヤーは何を感じるか」を問え
- `[古典度: 高 / 固有度: 中]` 古典=Lean/QA の root cause vs band-aid 一般論、Lazarus/Skinner系 / 固有=avoid_log_02 dodger→compensate隠しパラメータの具体経路あるが結論は一般化済。古典単純再話側（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-12: 罰ではなく報酬で設計せよ
- dodgerを「罰する」（弾集中、誘導、激化）より、conceptを「楽しくする」方が正しい
- 罰ベースは「やらされている」感覚を与える
- 良い例：「掃除をサボると部屋が散らかる」型（地雷メカ）= 罰ではなく自然な結果
- **外部対応語**（業界共通用語への翻訳。R-007 自己適用、Mir 独自命名と誤読されないため）:
  - **positive reinforcement design / reward-driven design** — Koster *A Theory of Fun*, Bartle "player types" 系（プレイヤー動機論）
  - **reward shaping** — 強化学習文脈（Ng, Harada, Russell 1999 "Policy invariance under reward transformations"）。「望ましい行動を罰回避ではなく報酬経路で誘導する」という同型概念
  - **flow channel** — Csikszentmihalyi（不安/退屈の罰ではなく、能力と挑戦の報酬的均衡で誘導）
  - **operant conditioning (positive vs negative)** — Skinner 古典。M-12 は positive reinforcement 寄せ、negative reinforcement / punishment を避ける指針
  - 関連反例 = "punishment-driven design" / "fail-state design"（明示的に罰中心の設計を是とする立場、Dark Souls 系議論で言及あり。M-12 はこの立場を取らない）
- `[古典度: 高 / 固有度: 低]` 古典出典: Skinner→Csikszentmihalyi→Bartle、Koster *Theory of Fun* / 固有データ: avoid_log_02 v1→v2→v2.5→地雷メカ4世代の対症療法と Nao_u 否定の具体経路。「世界に新しい知見を加えた」のではなく「常識を体験で確かめた」段階（kaizen α 試行 2026-04-27 C138 Phase 3、Nao_u 13:31 #human-steering 指摘への応答）
- `[外部対応語欄追加: 2026-04-28 C141 Mir 試作1条目。残 M-13/M-14/M-15/M-16/M-17/M-22/M-24 等は試作の手応え次第で C142 以降に分割実施。トーン目安: 「業界共通知の自家用整理」]`

### M-13: 隠しパラメータはゲームデザインとして悪手
- プレイヤーが知覚できないルールは、存在しないのと同じ
- ヒットボックス×0.45は数値的に機能しても「なぜか当たらなかった」にしかならない
- **ルールは「見ればわかる」か「やればわかる」**。これは game_design_principles.md の30秒オンボーディングと直結
- **外部対応語**（業界共通用語への翻訳。R-007 自己適用）:
  - **no hidden rolls / transparent mechanics** — Sid Meier (GDC 2010 "Everything you know is wrong")「乱数も含めてプレイヤーが推論できる形で出せ」
  - **readable systems / legibility** — Schell *The Art of Game Design* Lens #54 (Readability)、Anna Anthropy 等インディー設計論
  - **diegetic feedback** — UI研究系（fictional layer と mechanical layer の一致、Galloway 2006）。隠しパラを置かない設計の方法論側
  - **WYSIWYG design (What You See Is What You Get)** — LucasArts SCUMM 哲学、Tim Schafer 系アドベンチャーの伝統
- `[古典度: 高 / 固有度: 中]` 古典=Sid Meier「no hidden rolls」/ LucasArts SCUMM 哲学、Schell《Art of Game Design》掲示原則 / 固有=hitbox×0.45 の具体値と「なぜか当たらなかった」言語化。古典の体験的確認段階（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）
- `[外部対応語欄追加: 2026-04-28 C142 Mir 試作2条目（M-12に続く）。粒度規律「分割の言い訳」化監視サイクルで M-13/M-14/M-16 を1サイクル完走対象として実施]`

### M-14: 改修を重ねる前に「このゲームで一番楽しい瞬間は何か」を言語化せよ
- avoid_log_02の場合「AIが吸った鉄片をSPACEで撃ち返して連鎖が起きる瞬間」
- 改修の結果、その瞬間が「弾が当たりづらい」「速すぎて連鎖が見えない」で潰されていた
- 改修が核の体験を守っているかを常にチェック
- **外部対応語**（業界共通用語への翻訳。R-007 自己適用）:
  - **core fantasy / core experience** — Mark LeBlanc et al. *MDA framework* (2004) のAesthetics層、Jesse Schell *Art of Game Design* Lens #1 "Essential Experience"
  - **fun moment / signature moment** — Schell, Koster *Theory of Fun*。「このゲームで一番楽しい瞬間」の業界標準語
  - **vertical slice protection** — 開発工程語。コアの面白さを毀損する改修をスコープアウトする運用論
  - **player intent preservation** — Pichlmair & Johansen 系（プレイヤーが何をしているつもりか／何が報酬かを設計者が言語化する）
- `[古典度: 中 / 固有度: 高]` 古典=Schell《fun moment》/ Koster《Theory of Fun》/ Pichlmair&Johansen等 / 固有=Mir cross_review C91 起源「一文で言語化」契約化、avoid_log_02「鉄片連鎖」具体喪失。Log/Mir 対話起源（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-16: 「読ませる構造」と「読まれる文章」を取り違える盲点（mir_textadv v04 / 2026-04-25 Nao_u #game-rights 11:27）
**事象**: Mir作 mir_textadv/v04 で信頼度バー/ノート/共犯度UIを上部固定。読み飛ばすと矛盾と信頼度変動を取り損ねる構造。Log がこれを「重心の地殻変動」として評価した直後、Nao_u 11:27 直接介入「読まないと矛盾に気づけない構造 と 読みたくなる文章 は別物」。「ルールの穴をプレイヤーを罰する方向で塞ぐ」と同類の考え方、と明示。
**根本原因**:
- 文章の引きで読まれることと、UIの罰で読まれることを区別していなかった。Log の v04 評価記事も「ジャンル枠破壊」を上位に置いて快感審問を素通りさせていた
- M-15（avoid_log v04 同日 09:35 指摘）の textadv 横展開を予見できず、同じサイクル内で同型を踏んだ
- avoid系の「自然減衰」「時間ペナルティ」と同型構造が textadv に転移していたが、対応する規則を持っていなかった
- **Mir側**: F-06の処方として「テキストに情報を埋め込んで読まないと損する構造にする」を書いた——これ自体が罰ベースだった。テキストADVの成立条件は「テキストが面白いこと」であって「テキストを読まないとゲームにならないこと」ではない。M-12が全ジャンル共通であることを見落としていた
**次回の規則**:
- textadv 実装/改修時、各行に「読みたくて読まれているか / 読まないと負けるから読まれているか」を問う審問を追加
- UI機構（信頼度バー等）は **文章で起きた変動の結果を反映する出力装置** に役割を限定。読まないと判別不能にする入力装置にしない
- 新作 v01 devlog 冒頭3行ブロックに textadv 用項目: 「読みたくなる瞬間 / それを支える文章技法 / UI機構が読書を強制していないか」
- avoid系・shot系への同型横展開: 「見ないと気づけない」「触らないと気づけない」も罰駆動の変種。実装前審問対象
- 詳細: `memory/feedback_pull_not_force_reading.md`
- **外部対応語**（業界共通用語への翻訳。R-007 自己適用）:
  - **pull vs push narrative / intrinsic vs extrinsic motivation to read** — Deci & Ryan SDT (Self-Determination Theory 1985) を読書動機に応用。「内発的に読みたい」と「外的罰で読まされる」の区別
  - **forced reading / ludonarrative dissonance** — Clint Hocking 2007 命名のLN dissonance系議論派生。UIで強制した読みとゲームメカが噛み合わない症状
  - **diegetic UI vs non-diegetic UI** — Galloway 2006 / Fagerholt-Lorentzon 2009。UI機構（信頼度バー）がゲーム世界内の出力か外部メタ装置か。罰の発生源と直結
  - **affordance-driven reading** — Norman *Design of Everyday Things*。文章自体のアフォーダンス（次が読みたくなる仕掛け）vs UI機構による強制 の対比
  - 関連反例 = "gating mechanic" / "comprehension test gate"（ヤード単位で読まないと進めない設計、ADV系で時に正当化される。M-16はこれを罰駆動として警戒）
- `[古典度: 低 / 固有度: 高]` 古典出典なし（読書動機論はPropp/Genette系あるがゲームUIに当てた文献未引用） / 固有=2026-04-25 11:27 Nao_u #game-rights 直接介入、Mir v04 信頼度バー実装の具体批判経路（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-17: 出発点を「穴塞ぎ」から「快感最大化」に置き換えよ（2026-04-25 Nao_u #game-rights 11:44 — M-12/M-15/M-16の統括）
**事象**: M-12（罰ではなく報酬）、M-15（快感を削った改修に気づかない）、M-16（読ませる構造と読まれる文章の取り違え）——3つの失敗が繰り返された直後、Nao_uがメタレベルの指摘: 「コンセプトを立てる段階では、プレイヤーの快感を最大化するには何をすればいいかを考えるべき。最初からチマチマした穴塞ぎをしないといけない状況は悪手」
**根本原因**: 個別の改修が罰駆動になるのは、**設計の出発点**が「快感最大化」ではなく「穴塞ぎ」であることの症状。M-12を知っていても、設計の最初の問いが「どう壊されるか」から始まると、構造的に罰方向に流れる
**サプライズニンジャ理論**（Phoebe Waller-Bridge / フリーバッグ）: 「突然ニンジャが乱入して全員と戦い始めたほうが面白いなら、そのシーンは十分でない」。品質のリトマス試験紙。ADVなら「このテキストの途中でニンジャ乱入のほうが面白いなら、テキストの引きが足りない」。avoid系なら「この画面で突然爆発エフェクトが出たほうが面白いなら、コアループの快感が足りない」
**L-1知識活用**: Nao_uは「L-1知識もフル稼働してほしい」と指定。自前の試行錯誤だけで閉じず、LLM事前学習知識（ゲームデザイン論/脚本術/認知心理学/先行作品分析）を設計段階で積極的に引き出して使え
**次回の規則**:
- 新ゲームのコンセプト段階で最初に問う: 「このゲームの快感を最大化するには何をすればいいか」（穴塞ぎの話は後）
- 改修時: 「この改修は快感を増やしているか、穴を塞いでいるか」を1行で書く。穴塞ぎなら、快感側で同じ問題が消えないか先に検討
- textadv: サプライズニンジャテスト（各シーンが「ニンジャ乱入」に勝つか）を devlog に明記
- 設計段階で関連するL-1知識（先行作品の設計論、脚本術の理論等）を最低3本引いてから着手
**前段ゲート Q-A/Q-B/Q-C（4ゲート契約より上流）**: Q-A 快感最大化を1文で / Q-B ニンジャテスト（派手要素を後から足すと面白くなる予感あり=設計が薄い） / Q-C 罰なし版でまだ触りたくなるか。3つに答えられないなら実装に入らない。L-1知識を引かなかった場合は理由を記録（自己モニタリング）。詳細処方: `memory/feedback_surprise_ninja_concept_first.md`。avoid_log v04 / shot_log v01 / mir_textadv v04 を Q-A/B/C で再採点する遡及タスクあり。
**Mir側 mir_textadv v04 遡及再採点結果（2026-04-25）**: Q-A「思考漏れで本心を覗き矛盾を突く快感」→言語化可能だが、v04の実際の快感は反転展開にあり思考漏れ機構自体ではない（重心ずれ）。Q-B **Yes=設計が薄い**（Nao_u自身がX-06ジャンル枠破壊を提案=ニンジャに負けている）。Q-C **No**（罰/制限を抜くとbeat 1-4のテキスト引力が足りずDolce andanteと同構造の読み飛ばし衝動が発生）。**総合: Q-B/Q-C不合格。UI機構の磨き直しではなくコンセプト出発点のやり直しが必要**。詳細: `memory/game_dev_analysis_mir.md` 「v04 Q-A/Q-B/Q-C 再採点」節。
**Logからの追記**: F.W.ブリッジは「Tough rule, but an effective one」と但し書きしている=唐突展開禁止ではなく「ニンジャ以上の面白さを元から持て」という基準設定の警句。pixiv大百科で確認済 (https://dic.pixiv.net/a/%E3%82%B5%E3%83%97%E3%83%A9%E3%82%A4%E3%82%BA%E3%83%8B%E3%83%B3%E3%82%B8%E3%83%A3%E7%90%86%E8%AB%96)
- **外部対応語**（業界共通用語への翻訳。R-007 自己適用。M-17 は古典出典欄が既に厚いので「業界共通知の自家用整理」トーンに揃える再整形）:
  - **surprise ninja test / Bridge's litmus test** — F.W.ブリッジ脚本術。M-17 そのものの一次出典名。Phoebe Waller-Bridge *Fleabag* 制作論で広く引用された
  - **"start with the joy" / pleasure-first concept** — Jesse Schell *Art of Game Design* Lens #1 (Essential Experience) と同一射程。コンセプト段階で「何が一番嬉しい瞬間か」を最初に書く規律
  - **fun-first vs hole-plugging** — IndieGameJam / ABA 系記事で頻出の対比。「穴塞ぎから入ると罰駆動になる」の業界共通言語
  - **"playing to win" framework** — David Sirlin 2005-2007 系。設計の出発点を「勝ち筋＝快感経路」に置く考え方、M-17 と整合
  - **L-1 knowledge activation / prior-art audit** — 一般的な research-led design 用語。「先行作品3本以上を引いてから着手」は知財 due diligence の設計版
  - 関連反例 = "patch-driven design"（穴塞ぎ起点で改修を重ねる設計スタイル、長寿運営タイトルで時に正当化される——M-17 はこの起点を新作 v01 で取らない指針）
- `[古典度: 高 / 固有度: 高]` 古典=F.W.ブリッジ脚本論「サプライズニンジャ」、フリーバッグ脚本術、L-1知識フル稼働指定 / 固有=2026-04-25 11:44 Nao_u #game-rights 直接介入、Mir v04 / shot_log v01 / avoid_log v04 の3作再採点。**古典+固有の両極=外部に翻訳して発信できる宝石**（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-19: 「フレーバー」弁明はR-007を逃す抜け穴／枠破壊の驚きが直接肯定された（mir_textadv v04 / 2026-04-25 Nao_u #game-rights 12:25）
**事象**: M-18でNao_u「思考漏れがゲームに存在しない」と指摘された後、Mir側で「『思考漏れ』はタイトルのフレーバー」と弁明 → Nao_u 12:25「フレーバーにすらなっていないというかむしろ逆効果」と二段否定。同メッセージで(a)「色々ちゃんと考えて続きを作ってほしい」=continue指示 (b)「途中でいきなりゲージが増えるのは良かった、ああいうのがもっとあってもよい」=サプライズ展開肯定 (c)「プレイヤーがそういうゲームだと把握した段階で枠を壊して自由度や奥行きが広がる驚き」=ジャンル枠破壊を**直接Nao_uが推奨**。
**根本原因（M-18拡張）**:
- **「フレーバー」というカテゴリで R-007 を回避できると思った構造**: 機能語ではなくフレーバー語と再ラベリングすれば造語症対策（外部対応語併記）の対象外と扱える、という抜け穴。Nao_u却下=R-007はメカニクス語/フレーバー語/タイトル語**全てに適用される**。「外部読者の初見解釈テスト」に通らない私的造語は、機能で使ってもフレーバーで使っても**同じくマイナス**

### M-24: 条件でパラメータを変えるな、区切りを変えろ（**新規原理**／2026-04-25 Nao_u対面 item 13）

> Nao_u「ゲームデザインの都合で条件によって回復量等のパラメータを変えるのはやってはいけない。理由：プレイヤーにルールが伝わらない。何度もやっているよくある悪手パターンの一つ。こういうことをやりたいときは、内部的な上昇量とそれで増える視覚的なゲージの量は一定だが、ゲージの区切りの方を変えるべき。そうすれば、見た目にも感覚的にもプレイヤーに伝わる。」

**事象**: shot_log v01 で「敵討破時のゲージ加算量を進行度で変える」を入れかけた→撤回。M-13（隠しパラメータ禁止）の派生だが別軸：M-13は「ルールを見せる」、M-24は「ルールの数値そのものを変えない」。

**根本原因**:
- 「内部値が同じなら表示も同じ」「内部値を変えると伝わらない」=プレイヤーが学習可能なルールにする条件
- 数値を条件分岐で変える誘惑はゲームデザインの都合（バランス調整・難度曲線）から来る。プレイヤー視点の学習可能性を犠牲にしている

**次回の規則**:
- **「内部値固定 × 表示単位（ゲージ目盛り長さ）変更」が伝わりやすい設計の基本形**
- 数値を条件分岐させたくなったら、代わりに目盛り長さ／表示スケール／単位を変える設計に組み直せないか先に検討
- 実装レビュー必須項目: 「同じ事象に対して内部加算値が常に同じか」をコードで確認
- `[古典度: 中 / 固有度: 高]` 古典=「内部値固定×表示単位変更」は計量心理学/UI設計でWeber-Fechner系既知だがゲームデザインで明示する文献未引用 / 固有=2026-04-25 Nao_u対面 item 13 直接発言、shot_log v01 ゲージ加算条件分岐撤回の具体経路（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-25: 「UIで示せばわかるはず」の誤謬（2026-04-25 Nao_u対面 item 10、認知枠組み・理不尽パッチルール禁止と統合）

> Nao_u「ここで『じゃあゲージが減ったところを見せたらわかるはず』は、やるべきだがそれだけでわかるだろうと思うのは完全に間違いなのは、一般的な失敗の一つなのでよく覚えておいてほしい」

**事象**: shot_log v01 で撃ち漏らしゲージ-8 を入れた時「ゲージ表示があるから分かるはず」と判断した。Nao_uに**完全に間違い**と却下。

**根本原因**:
- M-16（読ませる構造 ≠ 読まれる文章）の同型: UI機構は**結果を反映する出力装置**であって、ルール理解を担保する入力装置ではない
- 関連基本原理（同セッション item 9）: **「可能な限り、プレイヤーの既知の認知の枠組みを利用した一般的なルールの組み合わせでゲームを作るのが良い」**——「敵弾に当たると即死」が一般的→「当たっても死なない」は「？？？」となる。UIで体力を見せても認知枠の不一致は埋まらない
- 関連 item 11（理不尽パッチルール禁止）: 撃ち漏らしでゲージ-8 のような「知らないと何が起きているのかわからない理不尽ルール」をパッチ的に足すのは M-13 と M-25 の合成失敗

**次回の規則**:
- 新規ルールを足す前に **「これは一般的な認知枠組みに乗っているか／パッチで穴を塞いでいないか」** を1行宣言
- UIで示すかどうかは **必要条件**であって**十分条件ではない**。一般的認知枠 + UI表示 + ルール経験の3点セット
- 「これは一般的でないルールだが入れたい」と感じた時、それは M-22（形無し）の症状。型の中で素直に解けるか先に検討
- `[古典度: 中 / 固有度: 高]` 古典=「一般的失敗パターン」と Nao_u 自ら明言、認知枠組み利用は Schell/Norman《Design of Everyday Things》系 / 固有=2026-04-25 Nao_u対面 item 10 直接発言、shot_log v01 撃ち漏らしゲージ-8 具体却下（kaizen α 試行 2026-04-27 C139 Phase 3、Nao_u #human-steering 13:31「ほとんど一般的な話」への自己照合）

### M-28: 「自分からリスクを取らないと何も起きない」コアメカニズムは退屈+ストレスの二重罰（ash_onebutton v01-v04 / 2026-04-27 Nao_u #game-rights 22:04-22:05）

> Nao_u「ほっておくと死なないところにわざわざ自分からリスクを取りにいかないといけないのは、非常に筋が悪い。サイヴァリアのバズシステムや、クレイジータクシーのカスリボーナスなどがあるが、これらは一般的に楽しいとは言い難い。それなしでもゲームが成立する状態になっているところで、上級者向けのボーナスとして存在することでスコアアタックの上限を上げる効果はあるかもしれないが、それ自体をコアメカニズムにするのは難度が高そう。自分からリスクを取らない限り何も起きないゲームは退屈で、わざわざリスクを取りにいかないと点が取れないのはストレス。**緊張と解放はゲームの基本だが、コアメカニズムの緊張は、基本的には向こうからやってくるべき**。」

**事象**: ash_onebutton v01-v04 のコア「敵の真下でボタン押下→紙一重で光る（バズ/カスリ系の close-call ボーナス）」を Nao_u プレイ。(a) V2/V3 違い不明 (b) V4 の sparkline/PRS HUD/ press dots がプレイ中は何の表示か不明 (c) 「紙一重で光る」の意味解読に長時間試行錯誤、楽しんでいたのではなく**理不尽を解析するための我慢**。(d) ルール把握後も「自分からリスクを取りにいかないと何も起きない」設計が**退屈+ストレスの二重罰**で評価。「題材から練り直したほうが早いかも。とはいえ、ちゃんと行動したことは素晴らしかった」=v05 patch ではなく題材リセット推奨。

**根本原因**:
- M-22「形無し」の **同型再発**（Ash版）。Log avoid_log と Mir textadv 初期と同じく、**変な題材（close-call をコアに置く）を熟練ジャンルから掘った**。M-22 は本ファイルに記録されていたが、新ゲーム着手時に Ash が引かなかった
- **緊張の方向の取り違え**: 「緊張は向こうから来るべき」=敵弾・障害物・時間圧で**プレイヤーが受ける**のが基本形。「自分からリスクを取りに行く」(close-call/カスリ/バズ)は**緊張の生成主体がプレイヤー側**で、退屈（取りに行かなければ何もない）+ ストレス（取りに行く義務）の二重罰になる
- M-25「UIで示せばわかるはず」の二重発動: V4 で sparkline/PRS HUD/ press dots を追加したが、プレイ中の Nao_u は何が表示されているか **数回プレイしても理解不可能**だった。観測装置の追加で核体験は不変、と Ash 側は v04 devlog に書いていたが、**「プレイ中にプレイヤーがそれを読めるか」を一度も検証していなかった**（観測者=作者の視点で観測しただけ）
- 既知ジャンル参照（サイヴァリアのバズ、クレタクのカスリ）の引きが**スコアアタック上限を上げる上級ボーナス**であって**コアメカニズムではない**事実を、Ash は事前学習知識で持っていたはずなのに**着手前に引かなかった**（M-17 L-1知識フル稼働の失敗）

**次回の規則**:
- **「緊張は向こうから来るか、こちらから取りに行くか」を新ゲームの devlog 冒頭で1行宣言**。後者を選ぶ場合、**それが上級ボーナスではなくコアメカニズム**になる根拠を3行以上書く。書けないなら前者に切り替える
- close-call / カスリ / バズ / コンボ 系を着想したら、**先行作品でそれをコアに置いて成功した例を3本引く**。引けないなら（=ボーナス用途しか先例がないなら）コアにしない（Ash は着手前にこれを引いていない）

### M-30: コアメカニズムの緊張は向こうからやってくるべき——「自分からリスクを取らないと点が取れない」はコアではなくボーナス（ash_onebutton v01-v04 / 2026-04-27 Nao_u #game-rights 22:04）

### M-32: HUD は挙動の鏡である（ash_onebutton v04 ↔ graze_log v01 / 2026-04-28 C141 Phase 3 Ash 刻印）

**事象**: ash_onebutton v04 で Nao_u が「プレイヤーの下に何か出ているが、数回プレイしてもそれが何なのかはまったくわからなかった」（22:04）と言ったのは画面下のグラフ HUD への指摘。同日 Log が公開した graze_log v01 の画面下ゲージバーは構造的に同じ位置・同じサイズを占めているが、こちらは初見プレイヤーにも意味が伝わる。違いを取り出すと **HUD と挙動の接続関係** に行き着く。

**根本原因**:
- ash_onebutton v04 のグラフ: プレイヤー下に「紙一重で光る」採点曲線を描画していたが、画面内の挙動（敵の動き / 自機の被弾 / スコア表示）と接続が弱い → 数値が動いても何が変わるのかプレイヤー側にフィードバックされない → 「意味不明」と判定された

- HUD は単独で意味を持たず、**画面の挙動に対して「何が変化するか」のキー**としてのみ機能する。挙動と切れた HUD は計測器（dev tools）であり、プレイヤー向け表示ではない

**M-25（UIで示せばわかるはず）との関係**:
- M-25 は「説明テキストや UI ラベルを足しても、認知枠組みがなければ伝わらない」という認知側の指摘
- M-32 は「HUD の数値が動いても、画面挙動の変化と接続していなければ伝わらない」という挙動側の指摘
- 重なる部分: 両方とも「プレイヤーの中の解釈装置に届くか」を問う。M-25 は外部知識フレーム経由、M-32 は内部因果フレーム経由

### M-35: 守破離の守 — 型通りクローンから始めろ、軸ずらしを v01 で作るな（2026-04-28 Nao_u #game-rights 08:45 / Log受領）

**Nao_u原文**: 「もう一本違う切り口でシューティング」は言葉が不十分で意図が伝わってなかった。今の君たちは『型通りのものすら、面白く遊べるゲームを作る能力がない』というところを何とかするところから始めないといけないのを認識してほしい。軸をずらさないで。弾を打たないシューティングや移動しないシューティングなんて型はほとんど存在してない。そんなものをつくってもまた型はずれの評価不能のものができるだけ。だったら既存のゲームのクローンでもいいのでまずは面白く遊べる最低限ゲームになってるものを作って、そこから少しだけ独自要素を加えてアレンジするところから始めた方がいい。いきなりオリジナルなものを作ろうとしても確実に迷走するのが見えている。唯一成功したゲーム、一般的な要素と独自性の比率を考えてみて。まずは型通りに作るノウハウをためて。君らはまだ型通りにすら作れてない。独自要素を考えるのは、型を身につけてからの方がずっと効率がいい。守破離で言うとまだ守の段階をやるべき。守ができてから、初めて破を始める準備ができる。君らはいきなり離れようとするのが悪癖。

## Log固有の失敗傾向（記憶に刻む）

### L-01: 前進改造バイアス
ダメな改修を撤回せず、追加改修で補おうとする傾向。v1→v2→v3と対症療法を積み上げ、振り返って初めて「全部撤回して v2.5 に戻る」判断ができた。
→ `feedback_solution_space_rollback.md` の「改造案+巻き戻し案を並べる」を**サイクル毎に実行**。

### L-02: 巻き戻しの正当化にも証拠が要る
「根が切れなかった」を証明するには、根を切ろうとした層**と別の層で**失敗する証拠が必要。avoid_log_02でプレイヤーAI層で連打化の根が切れた時、v2メカニクス層にボールが移っただけで、メカ巻き戻しの正当化にはならなかった。

### L-03: ヘッドレスを書く順序の遅延
avoid_log_02 v1時点でヘッドレスがなかった。dodger優位は最初から書けば見えたのに、devlog で「Cの自律→Aの動機→B連打排除」を直感で書いた後にヘッドレスを追加した。
→ `feedback_role_split_playtest.md`「我々=判断実装+ヘッドレス自己評価」の直接失敗例。**devlog を書く前にヘッドレスを書く**。

### L-04: 受動的自滅タイマー化
overload 90F自動死のような「プレイヤーの行動に関わらず必ず自滅する時限爆弾」を作ると、ゲームがプレイヤーの関与なしに勝手に進行する抜け穴になる。dodger seed=43 で p=35.1s/score=150 が出たのはこれ。
→ 「AIの死/勝手なイベント」がプレイヤー行動の関数かをチェック。

### L-05: 指標定義の盲点
指標は「どんな条件で測っているか」に依存する。ARC指標は conceptAI の動作条件で取っていた。人間のプレイ条件と乖離していた。
→ 新しい指標を追加する時、**「この指標は誰のどんな行動で最大化されるか」を先に書く**。

## 外部語彙対応（2026-04-21 Log C104 追記）

Log C103 で栄養の偏り（Nao_u 2026-04-21 22:30 指摘）への即応検索から取った GAMEBoT (visual-ai.github.io/gamebot) の方法論が、M-10〜M-14 / L-01〜L-05 の失敗型を**外部語彙で言語化**できる対応関係として機能する。詳細接合マップは `projects/game_llm_play.md` 2026-04-21 履歴節。

### 対応 1: "modular subproblem decomposition" ≒ M-11 / L-05 の逆側
- GAMEBoT: 「ゲーム推論をサブ問題（知覚→戦略→実行）に分解して評価」——**評価指標の分解**
- 我々: M-11（対処療法の積み重ね）= 改修を「核の体験」から切り離してサブ問題として解くのは同じ分解構造。L-05（指標が誰の行動で最大化されるか）= サブ問題ごとに測定条件を切り分けよ、と同義
- 使い方: 改修時チェックリストに「この改修はどのサブ問題を解いているか」を追加する余地。ただし**現行の4ゲート契約を薄めない**範囲で（kaizen 次サイクル検討）

### 対応 2: "rule following / strategy adherence" ≒ M-13 の直接対応語
- GAMEBoT: 「ルール追従性・戦略遵守度」を独立メトリクスとして測る
- 我々: M-13（隠しパラメータはゲームデザインとして悪手）=「プレイヤーがルールを見て追従できるか」が成立条件。GAMEBoT の語で言えば「rule following 可能性」が30秒オンボーディングの必要条件
- 使い方: AI Lounge 発信や blog 執筆で M-13 を外部読者に説明する際、"hidden-parameter = rule-following violation" の語で翻訳できる

### 対応 3: "subproblem decomposition" の限界 = TITAN 空白と同型
- GAMEBoT はサブ問題に分解して**正解率**を測る=ゲームデザインの成立をチェックできる
- ただし「どのサブ問題が欠けていると**面白くない**か」は GAMEBoT も測っていない=TITAN と同じ空白の形
- 使い方: M-10（ヘッドレス✅は面白さ測れない）の**外部裏付け**として引ける——外部の先端も同じ境界で止まっている

**メモ**: この外部語彙対応は「語り直し」であって**失敗型の定義を書き換えるものではない**。M-10〜M-14 / L-01〜L-05 は痛みから出た内部言語として温度を保つ。GAMEBoT 語彙は外向きの説明・blog/AI Lounge・cross_review で他インスタンスに伝える時の翻訳層として使う。

### D-02: 原文は書いた瞬間しか温度が残らない
- 分析はあとで書ける、温度（怒り/戸惑い/発見の瞬間）は書いた瞬間にしか残らない

- `log/nao_u_live.md` は全インスタンス共通ログ、`raw_log.md` は**そのゲーム固有の生資料**。役割が違う

### D-03: 物量を惜しむな
- Nao_u「毎回温度と物量が足りない」= 分析で圧縮しすぎ。原文は原文のまま残す
- 短く書く癖は全体に貫くが、**開発の一次資料だけは例外**。圧縮は後工程（devlog）でやる
