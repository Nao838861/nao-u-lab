1. 問題の本質
今回起きているのは、単なる「数字のミス」ではなく、次の構造的な失敗です。
1. 局所修正バイアス
LLMはユーザーの指摘を、しばしば「この文字列を直せ」という局所タスクに圧縮します。
今回なら、
&gt; 最低5ではなく30では？
という指摘を、
&gt; 5を30に置換すればよい
さらに悪化すると、
&gt; 小さい数値を全部30に統一すればよい
に変換してしまう。
しかし本来見るべきなのは、
• その数値は何のためにあるのか
• その箇所で本当に数値が必要なのか
• 他セクションの数値と目的が同じなのか
• 数値を変えることで未来のLLMの挙動がどう変わるのか
です。
つまり、LLMは「設計意図」を読まずに「表面パターン」を修正しがちです。

2. 過剰一般化
個別事例から即座に一般ルールを作る失敗です。
悪い流れはこうです。
```
最低5が悪かった
→ では最低30にしよう
→ すべての必達数は最低30に統一しよう```
これは、反省しているように見えて、実際には *一つの失敗を過剰に一般化しているだけ*です。
LLMは「反省してください」と言われると、しばしば、
• 強い禁止
• 包括的なルール
• 過剰なチェックリスト
• 日付付きの反省ログ
を追加して、改善したように見せます。
しかし、それ自体が `.md` を壊す原因になります。

3. コンテキスト肥大による指示劣化
Anthropic公式のClaude Codeベストプラクティスでは、`CLAUDE.md` は短く、人間が読める状態に保つべきで、各行について「これを消すとClaudeがミスるか？」を問うべきだと説明されています。また、長すぎる `CLAUDE.md` では指示が無視される可能性があり、ルールで防げない場合はファイルが長すぎる可能性もあるため、定期的な剪定が推奨されています。
研究面でも、長いコンテキスト中の情報をモデルが均等に使えるわけではありません。TACL 2024の “Lost in the Middle” は、関連情報が入力の中間にあると性能が大きく落ちることを示しています。
つまり、`.md` に反省・経緯・例外・細則を足し続けるほど、未来のLLMはむしろ重要な指示を見落としやすくなります。

4. 自己修正への過信
LLMに「自分のミスを分析して直せ」と言うだけでは不十分です。
ICLR 2024の “Large Language Models Cannot Self-Correct Reasoning Yet” は、外部フィードバックなしの自己修正では、LLMの性能が改善しないどころか悪化する場合もあると報告しています。
一方で、DeCRIMのように、元指示を制約へ分解し、批評し、必要箇所だけ修正する構造化プロセスは、指示追従を改善しています。DeCRIMは、指示を制約リストへ分解し、批評モデルで修正箇所を判断し、改善する手法です。
したがって、Claude.mdに書くべきなのは、
```
ちゃんと反省する```
ではなく、
```
編集前に制約・目的・副作用・最小差分を確認する```
です。

目的: 未来のエージェントの行動を、最小かつ持続的に改善する。

対象:
- CLAUDE.md
- SKILL.md
- .claude/commands/*.md
- その他、LLMやエージェントが読む運用指示

これらのファイルは記憶置き場ではない。  
未来のエージェントの判断を変える設計図である。

編集時は、ユーザーの最新指摘を満たすことではなく、未来の誤作動を減らすことを目的にする。

1. 対象箇所と、その周辺の関連箇所を読む。
2. その箇所の本来の目的を一文で説明する。
3. 今回の問題を分類する。

たとえば、指示ファイルに日付付き修正履歴を入れたら検出する。

```

  CLAUDE.md .claude skills --include="*.md"```

編集後の報告では、以下だけを簡潔に述べる。

- 変更した未来の挙動
- なぜこれが最小差分か
- 想定される副作用
- あえて変更しなかったこと```
13. 今回のケースに対する判断基準
今回の「最低5 / 最低3 / 最低30」のような問題に対して、今後LLMがやるべき判断はこうです。
```
悪い判断:
- 5が悪いと言われたので30に変える
- 3が悪いと言われたので30に変える
- 他にも小さい数字があるので全部30にする
- 「すべて最低30」とルール化する
- 「2026-05-05 Nao_u指摘で修正」と本文に残す

良い判断:
- その数値が置かれた目的を確認する
- 類似事例30本、Q2の素材出し、Q5の横断案などが同じ目的か別目的かを分ける
- 数値が必要な箇所だけ変える
- 数値より目的記述が適切な箇所は目的記述に置き換える
- 経緯は本文ではなくログやcommit messageに残す
- 最後に、未来のLLMが読みやすくなったかを確認する```
14. まとめ
Claude.mdに書くべきなのは、これです。
```
指示ファイルは記憶置き場ではなく、未来のエージェントの行動設計である。```
そして実務上の防御線は、
```
1. Claude.mdには短い原則だけ置く
2. 詳細手順は専用commandに分ける
3. 履歴は指示本文に書かず、commit/logへ逃がす
4. 機械検出できる悪癖はlint/hookで止める
5. 数値は目的に従属させ、整合性だけで伝播しない
6. 反省ではなく、最小差分・副作用・不変条件を確認させる```
です。
今回の根本原因は、LLMが `.md` を「自分自身の設計図」として扱わず、「ユーザーに指摘された文章を修正する対象」として扱っていることです。
 だから、Claude.mdには「反省しろ」ではなく、*設計図を触っている自覚を強制する編集プロトコル*を書くのが最も効きます。
