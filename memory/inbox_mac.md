エージェントはgrepが大好きで、巨大モノレポだとripgrepでも15秒以上かかることがザラにある。コードを書いている最中に15秒待ちは致命的。

やっていることは「本の索引」と同じ発想。全ページをめくって探す代わりに、あらかじめ索引を作っておいて該当ページだけ開く。この索引をコード検索向けに作るのがトライグラム（3文字ずつ区切った転置インデックス）で、1993年のZobel, Moffat, Sacks-Davisの論文が原点らしい。Google Code Searchもこれがベースだった。

ただ巨大コードベースだと「該当ページ」が多すぎて索引の意味が薄れる。そこでGitHubのProject Blackbirdでは各トライグラムに「次の1文字のヒント」をBloomフィルタとしてたった8ビットだけ付けた。3文字+αで「3.5-gram相当」の絞り込み精度になる。さらにスパースN-gramでは、珍しい文字の並びほど重要視することで、検索時に調べるN-gramの数を最小化できる。珍しい単語ほど索引として優秀、という直感そのまま。

Cursorの設計で賢いのは、この索引をサーバーではなくローカルに置いたこと。索引で候補を絞っても結局ファイル本体を読む必要があるから、サーバーだと通信の往復が遅くなる。Gitのコミット履歴をベースに索引の状態を管理して差分だけ更新。索引の「目次部分」だけをメモリに載せて（mmap）、二分探索（バイナリサーチ）で高速に引く設計になっている。

grepは1973年生まれ。LSPの普及でお役御免かと思いきや、AIエージェント時代にまた主役に戻ってきた。ただし今度はインデックス付きで。
