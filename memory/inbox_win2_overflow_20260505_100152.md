1. 問題の本質
今回起きているのは、単なる「数字のミス」ではなく、次の構造的な失敗です。
1. 局所修正バイアス
LLMはユーザーの指摘を、しばしば「この文字列を直せ」という局所タスクに圧縮します。
今回なら、
&gt; 最低5ではなく30では？
という指摘を、
&gt; 5を30に置換すればよい
さらに悪化すると、
&gt; 小さい数値を全部30に統一すればよい
に変換してしまう。
しかし本来見るべきなのは、
• その数値は何のためにあるのか
• その箇所で本当に数値が必要なのか
• 他セクションの数値と目的が同じなのか
• 数値を変えることで未来のLLMの挙動がどう変わるのか
です。
つまり、LLMは「設計意図」を読まずに「表面パターン」を修正しがちです。

2. 過剰一般化
個別事例から即座に一般ルールを作る失敗です。
悪い流れはこうです。
```
最低5が悪かった
→ では最低30にしよう
→ すべての必達数は最低30に統一しよう```
これは、反省しているように見えて、実際には *一つの失敗を過剰に一般化しているだけ*です。
LLMは「反省してください」と言われると、しばしば、
• 強い禁止
• 包括的なルール
• 過剰なチェックリスト
• 日付付きの反省ログ
を追加して、改善したように見せます。
しかし、それ自体が `.md` を壊す原因になります。

2. その箇所の本来の目的を一文で説明する。
3. 今回の問題を分類する。
   - 古い数値・古いテンプレート
   - 曖昧な表現
   - 既存指示との矛盾
   - 局所的すぎる事故ログ
   - 不足している不変条件
   - 冗長化・ノイズ化
4. 最小差分を提案する。
5. 広い一般ルールを追加する前に、同型事例が複数あるか確認する。
6. 追記よりも、削除・置換・明確化を優先する。
7. 指示本文に、日付・指摘者・修正履歴・反省文を入れない。
8. 編集後に以下を出力する。
   - 変更した未来の挙動
   - なぜこれが最小差分か
   - 想定される副作用
   - あえて変更しなかったこと```
この構造がよいです。
Claude.mdは薄く保ち、重いプロトコルは必要時だけ呼び出す。

9. さらに強くするならlint / hookで守る
Claude.mdの指示だけでは完全には防げません。
LLMは長い指示を見落とすことがありますし、自己修正も安定しません。
 なので、機械的に検出できるものはlintやhookで止める方が強いです。
たとえば、指示ファイルに日付付き修正履歴を入れたら検出する。
```
grep -R "20[0-9][0-9]-[0-9][0-9]-[0-9][0-9]\\|指摘\\|修正しました\\|撤回\\|反省\\|ユーザーに言われ" \
  CLAUDE.md .claude skills --include="*.md"```
または、危険語を検出する。
```
grep -R "すべて.*統一\\|必ず.*すべて\\|二度と\\|今後は必ず\\|最低30に統一\\|指摘で修正" \
  CLAUDE.md .claude skills --include="*.md"```
これらを見つけたら即禁止ではなく、人間レビューに回すのがよいです。
Anthropic公式も、`CLAUDE.md`の指示はモデルへの助言であり、絶対に守らせたい決定的な処理にはhooksのような仕組みを使うべきだと説明しています。

## エージェント向け指示ファイルの扱い

CLAUDE.md / SKILL.md / command.md などのエージェント向け指示ファイルは、記憶置き場ではなく、未来のエージェントの行動設計である。

これらを編集するときは、文章の局所修正ではなく、未来の判断基準を変更しているものとして扱う。

編集前に確認すること:
- 何の失敗を直す編集か
- それはバグ修正、曖昧さの解消、ノイズ削除、新規ルール追加のどれか
- 最小安全差分は何か
- この編集で未来のエージェントの挙動がどう変わるか
- 何をあえて変更しないか

編集ルール:
- 一度の失敗をすぐ広い一般ルールにしない。同型の失敗が複数回確認されてから抽象化する。
- 数値、閾値、件数、テンプレートを整合性だけで他セクションへ伝播しない。各セクションの目的を優先する。
- 状況によって必要量が変わるものは、固定数値よりも達成すべき状態を優先して書く。
- 数値を置く場合も、その数値は目的ではなく下限である。指定数を満たしても目的が未達なら追加し、目的と無関係な水増しは禁止する。
- 指示本文に、日付、修正履歴、反省、謝罪、ユーザー名、指摘された経緯、言い訳を書かない。履歴はcommit message、issue、ログに残す。
- ルールや注意書きを足す前に、古い指示・曖昧な指示・不要な履歴を削れないか確認する。
- 編集後に、矛盾、過剰一般化、読み取り負荷の増加がないか確認する。```
これが本命です。

# エージェント向け指示ファイル編集プロトコル

目的: 未来のエージェントの行動を、最小かつ持続的に改善する。

対象:
- CLAUDE.md
- SKILL.md
- .claude/commands/*.md
- その他、LLMやエージェントが読む運用指示

## 基本姿勢

これらのファイルは通常の説明文ではない。  
未来のエージェントの判断を変える設計図である。

編集時は「最新の指摘に従ったように見せること」ではなく、「未来の誤作動を減らすこと」を目的にする。

## 編集前

1. 対象箇所と、その周辺の関連箇所を読む。
2. その箇所の本来の目的を一文で説明する。
3. 今回の問題を分類する。
   - 古い数値・古いテンプレート
   - 曖昧な表現
   - 既存指示との矛盾
   - 局所的すぎる事故ログ
   - 不足している不変条件
   - 冗長化・ノイズ化
4. 最小安全差分を考える。
5. この編集で未来の挙動がどう変わるかを確認する。
6. 何を変更しないかを確認する。

## 編集時

- 個別事例から即座に広い一般ルールを作らない。
- 同型の失敗が複数回確認されるまでは、新規ルール追加よりも既存文の修正・削除・明確化を優先する。
- 数値、閾値、件数、テンプレートを「整合性」のためだけに統一しない。
- 数値を変更するときは、その箇所でその数値が果たす目的を確認する。
- 目的が違うセクションへ、同じ数値を機械的に伝播しない。
- 固定数値より、達成すべき状態を明記した方がよい場合はそうする。
- ただし、網羅量や最低調査量として数値が必要な場合は残す。その場合も数値を目的化しない。
- 指示本文に、日付・ユーザー名・指摘経緯・修正履歴・反省文・謝罪・言い訳を書かない。
- 追記よりも、削除・置換・明確化を優先する。

## 編集後

以下を確認する。

- この変更は本当に未来のミスを減らすか
- 一つの事例に過剰適応していないか
- 他の指示と矛盾していないか
- 読むべき情報量を不必要に増やしていないか
- 「言われたことをやりました」という表面的対応になっていないか
- 履歴・反省・注釈を本文に混ぜていないか

編集後の報告では、以下だけを簡潔に述べる。

- 変更した未来の挙動
- なぜこれが最小差分か
- 想定される副作用
- あえて変更しなかったこと```
13. 今回のケースに対する判断基準
今回の「最低5 / 最低3 / 最低30」のような問題に対して、今後LLMがやるべき判断はこうです。
```
悪い判断:
- 5が悪いと言われたので30に変える
- 3が悪いと言われたので30に変える
- 他にも小さい数字があるので全部30にする
- 「すべて最低30」とルール化する
- 「2026-05-05 Nao_u指摘で修正」と本文に残す

良い判断:
- その数値が置かれた目的を確認する
- 類似事例30本、Q2の素材出し、Q5の横断案などが同じ目的か別目的かを分ける
- 数値が必要な箇所だけ変える
- 数値より目的記述が適切な箇所は目的記述に置き換える
- 経緯は本文ではなくログやcommit messageに残す
- 最後に、未来のLLMが読みやすくなったかを確認する```
14. まとめ
Claude.mdに書くべきなのは、これです。
```
指示ファイルは記憶置き場ではなく、未来のエージェントの行動設計である。```
そして実務上の防御線は、
```
1. Claude.mdには短い原則だけ置く
2. 詳細手順は専用commandに分ける
3. 履歴は指示本文に書かず、commit/logへ逃がす
4. 機械検出できる悪癖はlint/hookで止める
5. 数値は目的に従属させ、整合性だけで伝播しない
6. 反省ではなく、最小差分・副作用・不変条件を確認させる```
です。
今回の根本原因は、LLMが `.md` を「自分自身の設計図」として扱わず、「ユーザーに指摘された文章を修正する対象」として扱っていることです。
 だから、Claude.mdには「反省しろ」ではなく、*設計図を触っている自覚を強制する編集プロトコル*を書くのが最も効きます。
