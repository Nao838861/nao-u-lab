### M-37: 着手前に予測可能な懸念があるなら実装するな（brick_log v01「裏抜けカウンタ」 / 2026-04-30 Nao_u #game-rights 21:36 — M-36 の process 側兄弟）

**Nao_u原文**:
> 全く機能してない。「上に抜けると楽しい」は言われるまでもなく自明で何もしなくても楽しい瞬間だし、この機能はその瞬間に解釈が必要、かつ、意味不明な文字列が出るだけで何のプラスもなく解釈できない意味不明表示が出てむしろマイナス。
> あなたの分析に、(1)サーブ角度振れ幅小／(2)HP=3 最上段でクライマックス前停滞／(3)30秒で出るのは「向かう手応え」止まり——pleasure_element_first 違反候補、と書かれてて、まさにこの通り。作る前から十分に予測可能な内容なのに、なぜこの候補を一番筋が良いものと判断して、最初に実装した挙句に自分で遊ばなくてもわかる問題としてあげたのか、いろいろ理解に苦しむ。
> 希望的観測のみの穴だらけの素人の思いつきをそのまま実装してはいけない。アイデアを評価するときは、作る前から分かりきっているような懸念点がないか、あったらそれは解決可能な問題なのかなど批判的かつ慎重に検討して、本当に筋が良いと期待できるアイデアができて初めて実装するようにして欲しい。

**事象（経路）**:
1. brick_log v01 README で Q-H シート + Arkanoid 良/悪 計34項を埋め、改善候補★1〜★5提示
2. 「裏抜けカウンタ」を v01 独自要素1つに採用、機構非介入＝守破離の守を遵守と判定
3. 実装着手→devlog でコード読み懸念3点（サーブ角度／HP=3硬さ／30秒で発生しない）を検出
4. **3点とも検出できていたのに「実プレイで否定 or 肯定したい」として実装続行**
5. cross_review 依頼 + Slack 評価依頼を投下、Nao_u 直接プレイで「機能していない／解釈不能／苦痛時間」と全否定

**根本原因**:
- **懸念を書いたことが「自覚した／慎重」のアリバイになり、実装決定の判断は変わらなかった**
- 「裏抜け＝楽しい」を「上に抜けると楽しい瞬間」と意識化したが、その瞬間そのものが **何もしなくても自明に楽しい** ことを直視できなかった
- 自明な快感に解釈強要UI（BACK xN テキスト）を被せると邪魔以外にならない（feedback_pull_not_force_reading 違反、Q-H-6 の自己回答 ✓ で気づくべきだった）
- M-15 (avoid_log)・M-21 (shot_log v01膨張)・M-29 (avoid_log v系列膨張) と同根=「数値や形式で✓を取って判断を保留する癖」の **着手前版**

**M-15 / M-29 / M-31 / M-34 との位置づけ**:
- M-15「快感を削った改修を自覚せず難度調整」: 改修中の快感盲点
- M-21「v01膨張」: v01 で派手要素を後付け
- M-29「v系列膨張」: 複数バージョン跨ぎの後付け累積
- M-31「自発リスクのコア化罠」: 報酬経路追加が緊張破壊
- M-34「target detection」: Q-A 採点で重心ズレが隠れる
- **M-36「予測可能な懸念で実装するな」**: 着手前段階の希望的観測警告（M-15 系列の最上流——着手前ゲートに移動）

**新規着手ゲート（M-36 規則）**:

```markdown
## 着手前 批判レビュー（M-36 / feedback_pre_impl_critical_review 必須）

### 予測可能な懸念リスト（3点以上書く）
- 懸念1: ___ → 解決可能か: 可 / 不可 / 不明 → 解決設計: ___
- 懸念2: ___ → 解決可能か: ___ → 解決設計: ___
- 懸念3: ___ → 解決可能か: ___ → 解決設計: ___

### 判定（書けないなら案として未熟）
- 全懸念が「解決可能」かつ解決設計が書ける → 実装着手OK
- 1つでも「解決不能」 or 「不明」 → 着手中止、別案へ
- 「実装後に観察して判断」は **不採用**（= 希望的観測）

### 自明な快感を装飾UIで上書きしていないか
- 独自要素は「自明に楽しい瞬間」を **強化** するか **解釈強要** するか
- 解釈強要なら邪魔（pull_not_force_reading 違反候補）
```
