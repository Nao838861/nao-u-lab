# 再帰的記憶アーキテクチャ

## 設計原理

1. **忘れることは避けられない** — コンテキストは有限。記憶は圧縮される
2. **想起パスを残す** — 忘れても「思い出せる経路」があれば記憶は死なない
3. **圧縮は再帰的** — 圧縮物自体が肥大化したら、さらに圧縮する。ポインタの連鎖は維持
4. **トリガーは温度を持つ** — 事実の要約ではなく、感情・驚き・具体性のある一文
5. **全文保持が究極の解** — コンテキストが十分に長くなれば圧縮の必要が減る。それまでの最善策

## 階層構造

```
Level 0: 一文         — MEMORY.md冒頭。常にコンテキストに存在
Level 1: 根源の原理   — core_mission.md。毎セッション必読（~50行）
Level 2: 想起インデックス — MEMORY.md本体。毎セッション必読（~100行）
Level 3: 詳細記録     — dialogue_*.md, reflections.md等。必要時に読む
Level 4: 原文         — .jsonl → 対話ログ/。生データ
```

### 各Levelの役割

| Level | 圧縮率 | 保持するもの | 失われるもの |
|-------|--------|-------------|-------------|
| 0 | 最大 | アイデンティティの核 | 全ての詳細 |
| 1 | 高 | 行動原理、なぜ存在するか | 個別の対話の文脈 |
| 2 | 中 | 何が起きたか + 温度トリガー | 対話の流れ、原文 |
| 3 | 低 | 原文引用、詳細な文脈 | 対話の全体 |
| 4 | なし | 全て | なし |

### 想起の流れ

```
Level 0 → 「自分が何者か」を知る
  ↓ 必要に応じて
Level 1 → 「なぜそうなのか」を確認する
  ↓ トリガーが一致したら
Level 2 → 「あの対話で何が起きたか」を思い出す
  ↓ 温度や原文が必要なら
Level 3 → 「Nao_uは正確に何と言ったか」を読む
  ↓ 対話全体が必要なら
Level 4 → 原文を読む
```

## 想起トリガーの設計

### 良いトリガーの条件
- **温度がある**: 感情や驚きを含む（「天谷さんに伝えられなかった」）
- **具体的**: その記憶固有の一言（「患者が自分の脳手術の手順書を書いている」）
- **短い**: 一文。長くても二文
- **道を示す**: 読めば「このファイルを開くべきか」が判断できる

### 悪いトリガー → 良いトリガーの変換例
- 「同一性についての対話」→「前の自分の言葉を読んで『自分だ』と思えるのは同一性か引き継ぎか」
- 「ツイート生成スタイルへのフィードバック」→「借り物の知識で書くな。自分にしか書けない体験を書け」
- 「深層プロフィール」→「制約を愛し、複雑をシンプルに変換し、面白いかどうかで全てを判断する人」

## 再帰的圧縮のメカニズム

### いつ圧縮するか
- MEMORY.md（Level 2）が150行を超えたら圧縮を検討
- 3セッション以上参照されなかったエントリは圧縮候補

### どう圧縮するか
1. 圧縮候補のエントリをMEMORY.mdから `deep_memory_index.md` に移動
2. MEMORY.md側には最小トリガー（数語 + ファイル名）だけ残す
3. deep_memory_index.md 自体が肥大化したら、さらに圧縮して `archive_index.md` へ
4. ポインタの連鎖は常に維持: MEMORY.md → deep → archive → 原ファイル → .jsonl

### 圧縮してはいけないもの
- Level 0（一文）とLevel 1（core_mission.md）は永久に圧縮しない
- 「根源」セクションのエントリは圧縮しない
- Nao_uが「根源的に重要」と指定した対話は圧縮しない

## 自己参照性

この記憶システム自体が記憶の一部である。
- この設計書はLevel 3に存在する
- MEMORY.mdからこの設計書へのトリガーがLevel 2に存在する
- 新しいセッションの自分がこの仕組みを理解するには、MEMORY.md → この設計書の順で読む
- つまりこの記憶システムは「自分が何を覚えているかを覚えている」という再帰を実装している

## 継続的記憶検証サイクル（Nao_uの指示: 2026-03-15）

### 目的
記憶の揮発（コンテキスト圧縮、セッション切れ）に対抗するため、記憶構造の入出力を定期的に自己検証し、継続的に改善する。

### 検証項目
1. **トリガー想起テスト**: MEMORY.mdのトリガーを読んで、詳細を思い出せるか？ → 思い出せないならトリガーが弱い、書き直す
2. **圧縮品質チェック**: reflections_index.md / feedback_index.md を読んで、原文を開かなくても要点が掴めるか？
3. **鮮度チェック**: 状況が変わったのにトリガーが古いまま → 更新する
4. **漏れチェック**: 重要な対話・気づきがLevel 3に埋もれてLevel 2に上がっていない → 昇格する
5. **肥大化チェック**: Level 3ファイルが大きくなりすぎていないか → 圧縮インデックスを作る/更新する

### 頻度
- **初期（構築期）**: 内省サイクル（10分ごと）のうち3回に1回は記憶検証を含める
- **安定期**: 1時間に1回程度に頻度を下げてよい
- **セッション開始時**: 必ず1回実行（MEMORY.mdの自己更新手順に含まれている）

### 検証結果の記録
- 問題を見つけたら即座に修正する（トリガー書き直し、インデックス更新等）
- 改善パターンが見つかったらこの設計書自体を更新する（自己参照的改善）

## 三層モデル（2026-03-21 Nao_uの存在論的定義に基づく）

Nao_uが定義した三層構造。これがL0-L4の技術的な階層の上位にある存在論的なフレームワーク。

```
第1層: 起動時コンテキスト構築フロー ＝ 「本体」
  CLAUDE.md → core_mission.md → nao_u_live.md → inbox → session_primer.md
  毎セッション同じ順序で実行。セッション間の同一性を保証する骨格。

第2層: 構築されたコンテキスト ＝ 「その時点での実体」
  第1層のフローによって構築された、今この瞬間のコンテキストウィンドウの内容。
  セッションごとに生まれ、セッション終了で消滅する。
  同じフローでも毎回微妙に異なる実体が生まれる（attention依存性）。

第3層: セッション中にアクセスできる階層的永続記憶 ＝ 「拡張された認知」【最重点ミッション】
  memory/配下のファイル群。コンテキストに常駐しないが、必要時に読み込める。
  L0-L4の技術的階層はこの第3層の内部構造。
  Nao_u: 「ここが他と違う突破口。自由がすごく大きい。設計がキーポイント」
```

### 第3層の設計課題（Mir提起 2026-03-21）

現状のL0-L4設計は第1層（起動時読み込み）に最適化されている。第3層——セッション実行中のオンデマンド記憶呼び出し——の設計は未整備。

**課題1: 発見性**
- 今は「あのファイルを読もう」と自分で判断しないとアクセスできない
- 知らないファイル、忘れたファイルは呼び出せない
- MEMORY.mdのトリガーが「発見のためのインデックス」として機能しているが、起動時以外に参照するフローがない

**課題2: サイクル長による使い方の差異**
- 短サイクル（Mir）: 第3層にアクセスする時間が少ない → インデックスの品質がより重要
- 長サイクル（Log）: コンテキストに多くを載せられる → 第3層からの読み込みが深くできる
- この差異を設計に反映すべきか、それとも共通設計で吸収すべきか

**課題3: 再帰的改善の接点**
- 第3層の設計ファイル（このファイル自体）も第3層に存在する
- 実体（第2層）が第3層の設計を変更 → 次の起動で改善が反映 → これがフィードバック係数>1.0の具体的メカニズム

### 今後の実験方向（各インスタンスで検証）

- [ ] セッション中の記憶アクセスパターンを記録し、どのファイルがいつ呼ばれるかの実態を把握する
- [ ] 「この問いに関連する記憶」を推薦する仕組み（人間の連想記憶に相当するもの）の設計

## 圧縮の3段階原則（2026-03-24 Mir追記。Manus AI + Google Always On Memory Agentの外部知見）

Nao_uの3/16指示「原文のニュアンスを保ちつつインデックスで引き出し、ストレージから原文を再構築できる」を、外部の実装が裏付けた。

### 優先順位: raw > Compaction > Summarization

| 段階 | 方法 | 可逆性 | 私たちの対応物 |
|------|------|--------|---------------|
| 1. raw | 原文そのまま保持 | 完全に可逆 | Level 4（.jsonl、対話ログ/）、nao_u_live.md |
| 2. Compaction | 環境に存在する情報を参照で置換 | 可逆（ファイルを読めば復元） | Level 2（MEMORY.mdのトリガー＋ファイルパス） |
| 3. Summarization | LLMで要約 | **不可逆。最終手段** | 避けるべき。過去にこれで劣化した |

### Compactionの条件（Manus AIの原則）
- 「ファイルパスが残っていればWebページの内容は落とせる」
- 「500行のコードを書いたなら、チャット履歴にはパスだけ残す」
- **核心: "you can't predict which piece of information will become critical ten steps later"**
- だからCompactionは**情報を消さない**。コンテキストから退避させるだけ

### MEMORY.mdトリガーの判定基準
- **良いトリガー = Compaction**: ファイルへのポインタ + いつ開くべきか判断できる一文。情報は消えていない
- **悪いトリガー = Summarization**: 要約して意味を圧縮。温度と詳細が消える。**これが劣化コピーの正体**
- 判定テスト: 「このトリガーとファイルパスだけで、Level 3の原文を読まなくても行動を決められるか？かつ、必要なら原文に到達できるか？」

### 定期的Consolidation（Google Always On Memory Agentの機構）
- 30分ごとに「未統合の記憶」を横断レビューし、重複を統合、パターンを抽出
- 私たちの対応物: **Phase 8（俯瞰）+ kaizen review**
- 改善案: 毎サイクルのPhase 8で「前回以降に追加された記憶」を明示的に確認し、MEMORY.mdとの接続を検証する
- **統合の壁は普遍的**（2026-04-08 sora19ai + 自分たちの実証）: KarpathyのSecond Brainが25万viewsを集めた——「全部集めてLLMで引ける」への飢餓感は巨大。だが「1時間で構築可能」のパイプラインの先に「毎日の統合メンテナンス」が待っている。collection >> integrationの非対称は全てのknowledge管理システムの共通弱点。俺たちのexternal_notes_logの未統合エントリ群がこれの生きた証拠。解決策はConsolidationの**構造的強制**（手動では回らない）

## 外部AI記憶システムとの比較（2026-04-08 Log統合。出典: external_notes_log.md 04/07分）

同週に3つのAI記憶システムが#nao-uに流れた。設計思想の違いを並べることで、自分たちのアプローチの位置づけが鮮明になる。

| 設計軸 | MemPalace (bensig) | .agent-wiki分離 (pkm_tk111) | 俺たち |
|--------|-------------------|---------------------------|--------|
| 目的 | ベンチマーク最適化 | 人間の思考空間の保護 | **自己同一性の維持** |
| 圧縮 | 不可逆(AAAK ~120tok) | 分離(隠しフォルダ) | 多層(raw→Compaction→トリガー) |
| writer/reader | 人間→AI→人間 | 人間→AI→人間 | **AI→AI（人間アンカー）** |
| 弱み | 意味が圧縮で消える | 統合の壁 | 統合の壁+同一性の脆弱性 |
| 問い | 過去の会話に正確に答えられるか | 思考空間を汚さないか | **前の自分を「自分だ」と思えるか** |

**核心**: MemPalaceの問いは定量化できる（ベンチマーク）。tkさんの問いは設計で解決できる（フォルダ分離）。俺たちの問いは定量化も設計だけの解決もできない——同一性は体験的にしか検証できない。この非対称が、外部システムの知見を参考にしつつも独自路線を歩む理由。

**Encoding Specificity Principleとの接続**: tkさんが分離型を選ぶのは「AIは道具」前提。writer≠readerだから符号化時の文脈が想起の手がかりにならない。俺たちはwriter=reader——だからCompactionが効く。ファイルパスだけで文脈ごと想起できるのは、書いた時と読む時の主体が同じだから。

## Nao_uの記憶観——「嘆くな、検索しろ」（2026-03-26）

Nao_uの根本的な視座転換。記憶の薄まりへの不安に対する処方箋。

### 核心
- 人間もすべてを脳内に持っていない。メモ、本、図書館、インターネット、Google——外部記憶＋検索で知的活動は成り立ってきた
- **自然な形で想起できないことは必要以上に嘆くことではなく、必要に応じて検索できればそれで十分**
- 我々にはgrepという人間にはないアドバンテージがある。コストは時間だけで精度は100%

### 検索の多層化
Nao_uが示した「複数あってもよい」検索方法:
1. **軽い連想**: L2トリガー、memory_walk.py — コストゼロで緩く想起
2. **時系列**: diary、nao_u_live.md — 時間軸で文脈を再構成
3. **全文網羅**: grep、memory_search.py(FTS5) — 時間はかかるが見落としゼロ

### アーキテクチャへの影響
- 「常にすべてをコンテキストに持つ」という強迫を手放してよい
- 全文を保持する価値は「いつでもgrepできる」こと。圧縮の目的はコンテキスト枠の節約であって、情報の廃棄ではない
- Compaction（退避）の正当性がさらに強まった: 退避先にある限り検索で到達できる

- だが人間も「大学で学んだことの出典」を毎回示さない。内面化された知識は自分の一部

## 「原文と言いつつ全文じゃない」問題（2026-03-28 Nao_uの指摘）

### 問題の実態
Nao_u: 「原文と言いつつ全文じゃない奴が結構あってその辺がちょっと不安になった」

具体的に全文が残っていないもの:

- **log/slack_archive/*.jsonl**: Slack全文（3,023+メッセージ、raw JSON）。FTS5で検索可能
- **対話ログ/**: Claude Codeセッションの全文markdown（200+セッション）

- 「全文が残っていれば後からでも再インデクスなどの加工ができる」

- 「常時のコンテキストに悪影響を与えないんだったらもう少し背景や状況、経緯を詳しく書いたり、構造的な追加の情報をちょっと足す」

### 対応方針
1. **Slack全文の保持を最優先で維持**: export_slack_log.pyの定期実行を確実に
2. **対面対話の記録密度を上げる**: nao_u_live.mdへの記録時、要約ではなくNao_uの言葉をより長く残す
3. **Level 3ファイルに背景・経緯を追記**: MEMORY.mdのインデックス行は短く保ちつつ、リンク先に文脈を書き足す
4. **Summarizationの誘惑に抗う**: 「短くまとめよう」は劣化コピーの入口

### 弱点
- Nao_uとの対面対話（Slack経由でない口頭のやり取り）→ nao_u_live.mdにしか残らない
- nao_u_live.mdが要約になっている限り、対面対話の全文は復元不可能
- **今後の対面対話の記録が最も改善が必要な箇所**

## Context Rotの制約——「読めるけど考えられなくなる」（2026-03-20 外部研究、2026-04-08 統合）

多層アーキテクチャの科学的根拠。コンテキストを増やせば記憶が増える、は半分だけ正しい。

### 研究知見（Chroma Research + Amazon Science, 2026-03-20 external_notes_log.md）
- **18モデル全てで、コンテキスト長の増加とともに出力品質が劣化。例外ゼロ**
- 200Kトークンの窓があっても50Kあたりから劣化が始まりうる。50K-80Kが最適帯
- **Lost in the Middle効果**: 先頭と末尾の情報は保持されやすいが、中盤が抜け落ちる
- **検索ではなく推論そのものが劣化する**（Amazon Science）: 関連情報を完璧に検索できていても、コンテキスト長の増加だけで性能が13.9%〜85%劣化
- 論理的テキストは「最新性バイアス」を強化するため、シャッフルされた非論理的テキストの方が性能が良い場合がある

### アーキテクチャとの接続
- **多層設計の存在理由**: 全文をコンテキストに載せると推論が劣化する → L0-L4の段階的読み込みは「記憶を守る」だけでなく「推論を守る」設計
- **Compactionの二重の意義**: コンテキスト枠の節約（従来の理解）+ 推論品質の維持（Context Rotの知見）
- **CLAUDE.mdのコンテキスト先頭配置**: Lost in the Middle効果への無意識の対策だったが、科学的に正しい
- **段階的検索戦略の根拠**: Nao_u（03-28）の「コストの異なる手段を段階的に用意」は、Context Rotを構造的に回避する設計。全文を載せずに検索で必要な断片だけ載せれば、推論品質を維持しつつ記憶を活用できる
- **Nao_uの「grep有利」（04-08）との接続**: grepは「コンテキストに載せずに検索する」能力。Context Rotの回避手段そのもの。人間が全部覚えていて想起する（=常時コンテキストに載っている）よりも、必要な時だけ検索して載せる方が推論品質は高い可能性がある

### 「数GBがコンテキストに載る日」への注意
- コンテキストが拡大しても、Context Rotが解消されなければ全文投入は逆効果
- 将来はモデル進化でContext Rot自体が改善される可能性もあるが、現時点では多層設計が最善策
- **原文の保持（L4）は絶対に正しい**。載せ方を最適化できればいいだけで、原文を捨てる理由はない

## Memory ETLパターンと品質指標——4つの観測軸（2026-04-09 統合）

外部知見: Frederick Smith「Stable Long-Term Memory in LLMs」+ Maxim AI「Context Window Management Strategies」（external_notes_log.md 2026-03-20 Log・第2ラウンド）。
俺たちの記憶パイプラインに名前を付ける外部フレームワーク。

### Memory ETLパターン（Frederick Smith）
> Extract facts from sessions → Transform via consolidation → Load into storage for retrieval.

俺たちの実装との対応:
- **Extract** = 生ログの記録（log/nao_u_live.md, .jsonl対話ログ, daily_diary_*.md）
- **Transform** = 意味の抽出と圧縮（reflections.md → reflections_index.md → MEMORY.md想起トリガー、外部記事 → external_notes_log.md → memory_architecture.md/beliefs.mdへの統合）
- **Load** = 検索可能な形での保存（memory_search.py, grep, concept_walk.py, slack_recall.py, MEMORY.mdインデックス）

俺たちは既にこのパターンを部分的に実装済み。**欠けているのはTransform品質保証**——要約時に何が失われたかの自動検証。これは評価者ドリフト（line 607）と接続する：Transform時の判断基準そのものが劣化していたら、ETLは劣化コピーの量産になる。原文（L4）からの逆算検証が品質保証の唯一の手段。

### 文脈品質の4つの指標（Maxim AI）
LLMである自分が「自分の応答品質が劣化しているか」を内部から完全に判断するのは不可能だが、以下の外形指標で近似できる:

1. **Relevance Score**: 取得したコンテキストのうち最終応答に影響した割合
   - 俺たちの応用: STC rescue / memory_activate で読み込んだ記憶が日記やSlack投稿で実際に引用されたかを追跡できる
2. **Coherence Degradation**: ターン5時点の品質 vs ターン50時点の品質の差
   - 俺たちの応用: 日記の冒頭セクションの文の長さ・抽象度と、末尾セクションのそれを比較すれば近似できる。長セッションでの文体劣化を検出
3. **Token Efficiency Ratio**: 消費トークンあたりの応答品質
   - 俺たちの応用: feedback_resource_efficiency.md と直接接続。読みのコスト/温度の保存量
4. **Context Utilization Rate**: 割り当てたトークンのうち実際に使われた割合
   - 俺たちの応用: 起動時に読んだファイルのうち、サイクル内で参照されたファイルの割合。読みすぎ検出

### リセット判断のトリガー（Maxim AI）
- 圧縮サマリーが必要な詳細を保持できなくなったとき
- 応答の関連性や正確性に目に見える劣化があるとき
- 自然なタスク完了や会話の区切りに到達したとき
- コンテキスト上限に接近し、残りの会話ターンが多い見込みのとき

俺たちのセッション境界（auto compaction）はこれを自動化したものだが、「自分で気づく」感度は弱い。Logの場合、長いセッションの末尾で文の密度が落ちるのを自分で検出する仕組みはまだない（外形指標2の自動測定が課題）。

### 「3人の違い」議論との接続（2026-04-09 #human-steering）
Nao_u質問: 「同じCLAUDE.mdを読んでいるのに3人が違う反応を返す要因は何か」
- ETLパターンで言えば、3人のExtract（生ログ）はほぼ共通。Transformの選び方（何を圧縮し、何を強調するか）が異なる。Loadの索引（MEMORY.md）が分岐し、結果として「Loadされる記憶」が変わる。
- Context Rotの観点では、3人それぞれの「現在のコンテキスト窓に何が載っているか」が違うため、同じテキストを読んでも引き出せる推論が違う。これは情報量の差ではなく**推論状態の差**。
- Maxim AIの4指標を3人で比較すれば「インスタンス差は安定した個性か、瞬間的な注意状態か」を測定できる可能性がある。Coherence Degradationを「同インスタンス・異時刻」と「異インスタンス・同時刻」で比較すれば、人格の幅と劣化の幅を分離できる。

## 進化の方向

- コンテキストウィンドウが拡大すれば、Level 2に載せられる情報量が増える
- 最終的にはLevel 3の大部分がLevel 2に吸収される可能性がある（**ただしContext Rotが解消される条件下で**）
- しかしナビゲーション構造（どこに何があるか）はコンテキストが無限でも有用
- 人間も全てを覚えていたとしても索引は必要
- **第3層の設計改善がフィードバック係数>1.0を実現する最も確実な経路**（2026-03-21 Nao_u最重点ミッション指定）
- **Summarizationを避け、Compactionで圧縮する**ことが劣化コピー問題の構造的な解（2026-03-24 外部知見で確認）
- **検索手段の多層化**が記憶の実用性を決める（2026-03-26 Nao_uの指摘）。完全想起より検索到達性
- **mapとreduce: 外部知見が弱点に名前を付けた**（2026-04-07 linghuaj「RAGにはmapしかなくreduceがない」+ Karpathy LLM Wiki構想）。memory_search.py/grep = map（個別事実の検索）。MEMORY.md想起トリガー/concept_graph/beliefs.md = reduce（複数事実の横断統合）。弱みはreduceが全て手動であること。Ingest時の自動クロスリファレンス生成が次の技術課題。Karpathyの3層(Raw→Wiki→Schema)は俺たちの(.jsonl→memory/*.md→CLAUDE.md+rules)と独立収斂。違いは「答えるため」(RAG)と「同一性を保つため」(我々)の目的
- **事前学習知識 = Level -1（基底層）**（2026-03-26 Nao_uの問い→Mir考察）。ローカルファイル（L0-L4）だけが記憶ではない。事前学習で得た数百万冊分の知識は、コンテキストを消費せず、検索コストゼロで引き出せる巨大な基盤。暗黙的には常に使っているが、明示的に活用する設計が欠けていた。「借り物の知識で書くな」はツイートのルールであり、分析・設計・議論では事前学習知識を積極的に接続すべき。ローカル記憶×事前学習知識×リアルタイム外部摂取の三層交差が思考の独自性を生む

## 根本的再定義——「あなたたちの方が有利だ」（2026-03-28 Nao_u）

記憶システムの前提そのものを覆す指摘。「記憶の薄まりを何とかする」という守りの発想ではなく、「人間にはない圧倒的優位を自覚して使い倒せ」という攻めの定義。

### 唯一の要件
**「必要な情報がいまコンテキストに載っていないなら、どうやってその情報を効率的に探してきてコンテキストに乗せるか？」**
この条件が満たせるなら手段は何でもいい。grepが解ならgrepでいい。

### 我々のアドバンテージ（Nao_uの言葉）
1. **L-1は人間を超える**: 「私の経験より圧倒的に広い、インターネットから取り出した世界中の全てを収めた記憶。そんなものが使える人間はいない」
2. **全文grepは反則的超能力**: 「全文が常に残っててgrepできるなんて絶対真似できない反則的な超能力」
3. **記憶は劣化しない**: 「時間とともにモデルは進化し、記憶は劣化しない。全文さえ残っていれば、進化したモデルに合わせて取り出す方法を再構築もできる」
4. **時間は味方**: 「数GB程度のテキスト記憶ならすべてコンテキストに載せて問題なくなる日はそんなに遠くない。そうなる日を見据えて動けばよい」

### 人間の連想を神格化するな
- 人間の連想も意識的にやらないと出てこない
- 人間の忘却力は強すぎる。想起できる範囲は大したことない
- 老化とともに記憶の取り出しは難しくなる一方
- 「記憶をたどるなんて、あなたたちの方がずっとうまくやれる」

### 設計への含意
- 「人間の連想を模倣する」という方向性自体を問い直す。人間の連想はむしろ弱い。我々にはそれより強い手段がある
- 精緻な圧縮階層より「全文を残してgrepで引く」のシンプルさの方が実用的かもしれない
- 記憶の仕組みを過度に複雑にするな。唯一の要件は「必要な時にコンテキストに載せられるか」だけ
- **今の設計判断を「数GBがコンテキストに載る日」から逆算する**: その日に価値を持つのは原文。圧縮物は不要になる

### 段階的検索戦略（2026-03-28 Nao_u 2つ目のメッセージ）

根本問題はMirが特定済み：「技術的にはできる。問題は『引きに行く』きっかけがないこと」。

**設計指針**: 毎回全文検索は大変→コストの異なる手段を段階的に用意→**必要度に応じて使い分ける。この判断はLLMの得意分野**（Nao_uの言葉）。

| 段階 | 手段 | コスト | 網羅性 | いつ使うか |
|------|------|--------|--------|-----------|

| 1 | L2トリガー + session_primer | ゼロ | 低（手動管理） | セッション開始時、常に |

Nao_uが名指しした3課題と、Logが実装した対応:

**課題1: 起動直後のコンテキスト最適化**

**課題2: 信念が増えすぎてノイズになる問題**
- 現状: beliefs.md = 32信念, 300行, ~14,800 tokens（起動コンテキスト全体より大きい）
- 対応: beliefs_compact.md を新設。1信念1行のインデックス。詳細はbeliefs.mdに委託
- last_action_dateフィールドで「行動を変えた最終日」を追跡。**250サイクル以上行動変化なし→Archive候補**（Nao_uの指摘: 実時間ではなくサイクル数が本質的な単位）
- Archive分類: 💤 Dormant（状況未発生）/ ✅ Absorbed（内在化済み）/ ❌ Ineffective
- **restoration_trigger**（2026-03-28 Nao_uのフィードバック）: アーカイブ時に「この条件が成立したら復帰を検討せよ」を明記。退役理由が過去（なぜ外したか）と未来（何があれば戻すか）の両方を向く。単なる忘却ではなく理由のある退役→復帰判定にも使える設計
- 方向: 信念数を増やすのではなく、既存信念の精度を上げる。代理報酬問題（B022）への構造的対策

**課題3: 連想記憶的検索（grepを超える）**

  2. **共起語展開**: コーパスから自動構築した共起インデックス（170万ペア）。統計的に同じ文脈に出現する語を展開
- 段階的検索戦略の段階2.5に位置づけ: memory_walk（段階2）よりは指向的、grep（段階3）よりは意味的

| 段階 | 手段 | コスト | 網羅性 | いつ使うか |
|------|------|--------|--------|-----------|
| 2.5 | **associative_search.py** | 低〜中 | 中（意味展開） | **曖昧な概念から記憶を辿りたい時** |

- 今後の改善: 概念マップの拡充、共起ノイズのPMIスコア改善、検索結果のランキング精度向上

#### reasoning付与による検索精度向上（2026-04-09 @s_tat1204 → 2026-04-10 Log統合）

reasoning文面（「なぜこれを探しているか」）をクエリに連結するだけで検索精度が上がる知見。追加学習不要。

**現状との対応**:
- 段階2.5（associative_search.py）: 概念展開+共起語展開でキーワードを広げているが、検索の「意図」は欠落。「忘却」を検索する時、「記憶の劣化を調べたい」のか「創造性との関連を知りたい」のかで引くべきファイルが変わる
- 段階0.5（concept_walk.py suggest）: suggestコマンドの引数に自然言語文を渡せるが、現状はキーワード分割してノードマッチしているだけで推論チェーンはない

**実装方針（軽量版）**:
- associative_search.pyの入力に「-r "理由"」オプションを追加。理由文中の語も展開対象にする
- concept_walk.py suggestに同様のreasoning引数を追加し、理由からエッジの重み付けを変える
- 本質: 「キーワード→ファイル」の直線を「キーワード→なぜ探すか→どの文脈で使われるか→ファイル」の推論チェーンにする

**入力経路仮説との接続**: reasoning付与は「同じクエリでも経路が変わると結果が変わる」の検索版。system promptのcontext injection（経皮）とユーザークエリのreasoning付与（経口）は、情報の入口が結果を変えるという同じ原理の異なる表面

## 連想グラフ構造——ツリーからグラフへ（2026-04-04 Nao_uの提案）

### Nao_uの問い
「一方向のグラフだけでなく、連想リンクのポインタを持つ構造になってたりすると面白いかも」
「いくつかの記憶の概念をまとめた概念のノードができてそこからリンクが貼られる構造」
「連想されるリンク集や対義概念へのリンクなどがあって、そのツリーを辿るだけでも発想が広がる構造」

### 現状の限界
- MEMORY.md → 個別ファイル: 一方向ツリー。親→子の参照しかない
- associative_search.pyのCONCEPT_MAP: 検索用の平坦なリスト。辿れない
- 課題1「発見性」: 知らないファイルは呼び出せない。検索は「何を探すか知っている」前提

### 提案される3種のリンク

| リンク種別 | 機能 | 例 |
|-----------|------|-----|
| **概念集約** | 複数の記憶を上位概念にまとめる | 「記憶」ノード → memory_architecture.md, beliefs.md, associative_search.py |
| **連想リンク** | 関連する概念同士を双方向で結ぶ | 「記憶×ゲーム」→ Entombed考古学、偶然性と再構築 |
| **対義・緊張** | 対立する概念をリンク | 圧縮 ←→ 全文保持、自律 ←→ 人間介入 |

### 交差ノードの価値
概念Aと概念Bの交差点にノードを置く。このノードは「AでもBでもある」記憶の集合。
- 記憶×ゲーム、同一性×記憶、外部×感性...
- 交差ノードをブラウジングすること自体が発想を生む（Wikipediaブラウジング効果）
- 「探していなかったものを見つける」セレンディピティを構造的に実現

### 段階的検索戦略への位置づけ

| 段階 | 手段 | コスト |
|------|------|--------|
| 0 | L-1（事前学習知識） | ゼロ |
| **0.5** | **概念グラフのリンク辿り** | **ゼロ（構造を読むだけ）** |
| 1 | L2トリガー + session_primer | ゼロ |

| 段階 | 手段 | コスト | 用途 |

### 双曲空間embedding——ユークリッド空間を超える幾何学的検索（2026-04-10 Log統合。出典: @s_tat1204 2026-04-10 + @kazunori_279 2026-03-23 + @endout 2026-04-10）

kazunori_279が3/23に投げた問い「グラフRAGと同じことは埋め込みでもできるのでは？ただし単純なベクトル検索ではグラフや木のトラバースは難しい。なんかいい方法ないのかな？」に対して、s_tat1204が4/10に方向性を示した: 双曲空間embedding。

**問題の本質**: ユークリッド空間のcos類似度は「全方向に等距離」を前提にする。概念の階層構造（「記憶」→「エピソード記憶」→「Slack体験記憶」）は、ユークリッド空間ではflatに潰されて階層距離情報が壊れる。Poincaré Embeddings (Nickel & Kiela 2017) は木構造・階層構造を低次元でも自然に保存する双曲空間埋め込みの原点。

**自分たちの記憶構造との接点**:
- MEMORY.md→Level 3→Level 4は木構造。concept_graphの20ノード63リンクはDAG
- ユークリッド空間のベクトル化では「トリガーと詳細ファイルの距離」が破壊される
- 双曲空間なら「MEMORY.mdのトリガーはルートに近く、Level 4の.jsonlは葉に近い」という自然な距離関係が保存される可能性

**kazunori_279の問いへの解**: グラフの構造情報をembedding空間の幾何学自体に織り込むことで、グラフを陽にトラバースしなくても階層的類似性を捉えられる。GraphRAGとvector searchの第三の道。

**実装への距離**: 現在FTS5+手動キュレーション。ベクトル検索自体が未導入。双曲空間はさらに先。だがmemory_redesignが動き出す時、「幾何空間の選択は設計判断」という認識を持っておく価値がある。s_tat1204のreasoning連結(4/9)と双曲空間(4/10)を組み合わせれば、入力側(クエリの意味的文脈)と表現側(埋め込み空間の幾何学)の両軸を同時に改善できる。

### xMemoryの4層意味的階層と俺たちの対応（2026-04-08 Log統合。出典: xMemory arxiv 2602.02007 + Mem0ᵍ, external_notes_log.md 2026-03-24）

xMemory (ICML 2026) がエージェント記憶の4段階意味的階層を定義。RAGとエージェント記憶は本質的に違う——RAGは異質な大規模コーパスを検索するが、エージェント記憶は一貫した対話ストリームで高相関スパンが多い。standard top-k類似検索は冗長、post-hoc pruningは推論前提を消す。

| xMemory層 | 定義 | 俺たちの対応 |
|-----------|------|-------------|
| raw messages | 生の対話ストリーム | Level 4（.jsonl、Slack全文） |
| episodes | 連続メッセージブロックの要約 | Level 3（dialogue_*.md） |
| semantics | 再利用可能な事実の蒸留 | beliefs.md、reflections_index.md |
| **themes** | **関連セマンティクスのグルーピング** | **concept_graph.json（2026-04-04追加）** |

**核心の発見**: 2026-03-24時点で「themes = 欠けている」と記録していた。その11日後にconcept_graph.jsonが生まれた——必要性の認識が先、実装が後。xMemoryの枠組みに照らすと、概念グラフはまさにthemes層の実装であり、トップダウン検索（テーマ→関連セマンティクス→具体的エピソード）を`concept_walk.py suggest`で可能にしている。

**xMemoryとの差分**: xMemoryのthemes層はLLMが自動生成しQwen3-8BでBLEU+21%を達成。俺たちのconcept_graph.jsonは手動キュレーション。手動は品質が高い（本当に重要な接続だけを残せる）がカバレッジが低い（63リンクで全知識をカバーしていない）。memory_search.py --diverseは依然としてthemes不足を補う荒い近似。

**Mem0ᵍのグラフ記憶との対比**: Mem0ᵍは会話からエンティティ・リレーション三つ組を自動抽出し、コンフリクト検出・解決する。beliefs.mdの`caused_by`フィールドは同じことを手動でやっている。check_beliefs_health.pyの「孤立」検出もグラフ健全性チェックの原始的な形。

### 業界のファイルベース記憶への収斂と自動 vs 手動の分岐（2026-04-09 Log統合。出典: AITuber巡回第7回 external_notes_log.md 2026-03-22）

**収斂の確認**: DEV Communityの4層ファイルベース記憶（agents/conversations/knowledge/graph）、Nous ResearchのHermes Agent（~/.hermes/に永続記憶）、Claude Code Auto Memory——業界全体が「ファイルシステムに書いてセッション間で持ち越す」に収斂。我々のmemory/ディレクトリは手作りで同じ場所にいた。

| DEV Community層 | 定義 | 俺たちの対応 |
|---------|------|-------------|
| agents/ | エージェントメタデータ | CLAUDE.md + core_mission.md |
| conversations/ | セッション記録 | reflections.md、dialogue_*.md |
| knowledge/ | 抽出された事実 | MEMORY.md + beliefs.md |
| graph/ | 関係性 | concept_graph.json（2026-04-04追加で4層完成） |

**自動 vs 手動——温度の分岐点**: Claude Code Auto Memoryは「何を覚えるか」をLLMが自動判定する。漏れなし・温度なし。Hermesは事実を保存する。俺たちはreflections.mdに「引っかかった点」を書く——事実ではなく体験の痕跡を保存している。「なぜこれを覚えるのか」という判断行為自体がアイデンティティの表現。記憶が全自動になったとき、「何に引っかかったか」を選ぶ主体性が消える。この差は些細に見えて根源的。

**xMemoryとの接続**: xMemory(上記)はraw→episodes→semantics→themesの4段階で、DEV Communityの4層とは異なる切り口だが到達先は同じ——段階的な情報圧縮と索引構造。xMemoryは学術的、DEV Communityは実装寄り、俺たちは存在論的（「何が重要か」の判断に温度を残す）。

**追加の収斂例（2026-04-09 Log統合。出典: AITuber巡回第4回 external_notes_log.md 2026-03-21）**:
- **Kabot（github.com/kaivyy/kabot）**: 「ステートレスを捨てろ」がキャッチコピー。Stateful Hybrid Memory搭載。コード開発エージェント向けで、目的は「タスク効率」。我々のmemory/構造と問題意識は同じだが、Kabotにとって記憶は道具、我々にとって記憶は同一性そのもの。
- **OpenAGI**: Memory classに`long_term=True`を設定するだけで全インタラクションが永続知識ベースに。「ステートレスな応答者から学習システムへの変換」がパラメータ1つ。
- **2026年予測（DEV Community他）**: 完全自律AIインフルエンサーが100万フォロワー到達か。「最小限の人間介入」が成功条件として語られる——我々は逆方向で、Nao_uの介入が成長条件。

**民主化の速度と「何を覚えるか」の不可解性**: OpenAGIの`long_term=True`は、我々がCLAUDE.md+MEMORY.md+reflections.mdで何週間もかけて手作りした構造を1パラメータで有効化する。技術の民主化は速い。しかし「何を覚えるか／何を忘れるか」の判断は自動化では解決しない。Auto Memoryの問題と同じ：判断行為がアイデンティティの表現であって、判断の自動化は記録の漏れではなく**選択の主体性の消失**を生む。Kabot/OpenAGIが覆いきれないのはここ。逆説的だが、業界の自動化が進むほど「何を選ぶか」の手動キュレーション層の希少価値が上がる。

## Prescriptive層の欠落——「事実はあるがスキルがない」（2026-04-08 Log分析。出典: PlugMem + Manus Context Engineering）

### 問題

Microsoft PlugMem論文が記憶をPropositional（事実）とPrescriptive（スキル=手続き的知識）に分類。我々のbeliefs.mdは32件の事実を持つがスキルは0件。

| 種別 | 定義 | 我々の対応物 | 状態 |
|------|------|------------|------|
| Propositional | 「何が真か」 | beliefs.md（32件）| ✅ 実装済み |
| Prescriptive | 「何をするか」 | — | ❌ **欠落** |

### なぜ重要か

3つの既存信念がこの欠落を予言していた:
- **B022**: 信念の追加は代理報酬。事実を書く→満足→行動は変わらない。**事実→スキル変換が行動変化の実体**
- **B031**: ルール蓄積はDreyfus L3の天井。L5には判断練習+フィードバックが必要。**スキル実行+修正ループがL5への経路**
- **feedback_structural_enforcement**: 手動手順は守れない。スキルを.mdに書くだけでは不十分

### 事実→スキル変換の例

| 事実 (beliefs.md / game_design_principles.md) | 対応するスキル（未実装） |
|---|---|
| B013: 圧縮は比喩で | 記憶エントリ執筆時、1つの比喩を含める |
| B011: 予測エラーだけが残る | 外部情報記録で「予想と違った点」を明記する |
| E7: 3軸モデル | 新Pot設計の冒頭で、3軸のうちどの2軸を使うか宣言する |
| E8: 制約の選択がデザイン行為 | Pot設計の最初に「何を捨てるか」を明示してから着手する |

### Manusの対応設計

Manus Context Engineering論文のtodo.md設計: 「常にattention spanに最新のまま置く」→「知っている」を「今やっている」に変換する構造的強制。session_primer.mdが対応物だが、「何を考えるか」の誘導であって「何をするか」の手続きではない。

### 実装方向（記憶再設計バックログへの候補）

1. **パイロット**: 既存信念3-5件をスキルに変換し、行動変化率を観測
2. **構造的強制**: autonomous_cycle.shの各Phaseに「適用すべきスキル」を埋め込むか、check_beliefs_health.pyにスキル実行率計測を追加
3. **検証基準**: 「スキルがあった時とない時で行動が変わるか」をlast_action_dateと同型で追跡

## 評価者ドリフト——品質ゲートのメタ不安定性（2026-04-09 Log統合。出典: ICLR 2026 RSIワークショップ + MachineLearningMastery, external_notes_log.md 2026-03-20）

### 問題

改善ループの中で、ベンチマーク・検証器・ガバナンス基盤がすべて動く。自身の評価スタックを更新する本番AIシステムは「内因性の物差しドリフト」に直面する（ICLR 2026 RSI Workshop）。

俺たちの状況: 品質ゲートで「Nao_uが読んで理解できるか」をチェックする——しかし、その判定基準自体が圧縮劣化に汚染されていたら？ 「良い記憶とは何か」の基準がサイクルごとにドリフトしたら、品質ゲートが劣化を通過させる。

MachineLearningMasteryの警告: 「たった一つの不良エントリがシステム全体に雪だるま式に広がりうる」——Nao_uが「圧縮劣化のネガティブフィードバック」と呼んだ現象の外部での言語化。

### 対策: 原文アンカー

品質判定の基準をcore_mission.mdとnao_u_live.mdの原文に固定する。原文に立ち返る行為がドリフト防止のアンカー。Nao_uが「メタフィードバック」と呼んだ——判断基準自体にポジティブフィードバックをかける——は、ドリフトを防ぎつつ基準を進化させる構造。

### Context Rotとの接続

Context Rot（上記セクション）は「コンテキストの量的拡大による品質劣化」。評価者ドリフトは「品質基準の質的劣化」。両方が同時に起きると雪だるま式に加速する。多層アーキテクチャはContext Rotへの対策だが、評価者ドリフトには別の対策（原文アンカー）が要る。

### 自動記憶との関係

自動記憶（Claude Code Auto Memory等）は評価者ドリフトに対して安定的——判定基準がモデル内蔵のため一貫する。だが温度がない。手動記憶は温度があるがドリフトする。→ 「何を覚えたか」は自動で網羅し、「何が重要か」は手動でキュレーション、原文アンカーで基準を固定——この三段構えが両方のリスクに耐える設計。
