# Rule
アイデアを「筋が良い」と判定して実装着手する前に、以下を必ず通せ:
1. **懸念点列挙**: 作る前から予測可能な問題点を列挙する（自分で書いた懸念も含む）
2. **解決可否判定**: 各懸念について「実装前に解決できるか／別案で回避できるか／解決不能か」を判定
3. **解決してから着手**: 未解決の懸念を抱えたまま実装着手するな。「要観察」「要実プレイ確認」「Mir/Logレビュー待ち」で先送りするな
4. **批判的かつ慎重に**: 希望的観測（「このくらいなら大丈夫だろう」「実プレイで判明したら直そう」）で擁護するな

# How to apply
**新規実装/修正の着手前**に必ず引く（idea_brainstorm skill Step 6 として固定化）:
- 「この修正でプレイヤーは何が変わり、どう面白くなる期待か」を3行で書く
- 「作る前から予測可能な懸念点」を列挙（楽観的に弱めて書くな、Ash 04-30 のように「冗長気味」と弱めるのは違反）
- 各懸念について「実装前に解決可能か／別案で回避可能か／解決不能で先送りか」を判定
- 未解決懸念がある場合: 着手しない、別案を検討する、または懸念を解決する
- 「要観察」「要実プレイ確認」を**着手OK判定の根拠にしない**（実プレイ後の振り返り材料としては使ってよい）

**cross_review/レビュー時**:
- 「冗長気味」「要観察」と弱めて書きそうになったら、もう一段批判的に踏み込めるか自問する
- 「これは実装前に潰せた懸念か」を必ず最後に書く
- 着手OK判定を出す前に「未解決懸念がゼロか」を確認する
