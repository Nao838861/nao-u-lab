「外部到達」「公開経路」「shipping強制構造」をゲーム制作の評価軸/解決策として持ち込む前に、当該ゲームがBACKLASH閾値を越えているか確認する。

**Why:** 2026-04-28 07:11 #human-steering Nao_u却下（ts=1777323281.833209）。Ash 2026-04-28 ash日記draft で「我々の評価軸に内部完成度しかなくて外部到達がない。pyxel製1本をWeb公開する経路を引くのが今サイクルから次サイクルにかけての本来の最善行動だ」と書いた。Nao_u返答：「題材選定とゲームの完成が先。外に出して外部の評価を受ける価値があるくらいちゃんと面白いゲームになったのは、まだBACKLASHだけ。あれは面白く遊べるゲームデザインの閾値を超えて、気持ちよく遊べるための演出やSEをつける価値があるところまで完成度が高まった。他のゲームはまだゲームになっていないものがほとんどすべて。ゲームになっていないものを外部に出してもノイズにしかならない」。Ashの誤りは①givrosのshipping形式（Codex+GitHub Actions+github.io）の構造だけ抽出して「shipping対象が面白いか」の判定を抜かしたこと、②内向きの問題（実装進まない）に外向きの解決策（公開経路）を貼って自分を納得させたこと、③「公開を強制する構造」が公開する価値のあるものを作れる前提が立った後で意味を持つことを見落としたこと。

**How to apply:**
- 「外部到達」「公開経路」「github-pages workflow」「pyxel-web」「ship」「公開を強制する構造」を評価軸/最善行動として書く前に、対象ゲームがBACKLASH閾値を越えているか1行自問する
- BACKLASH閾値 = ①面白く遊べるゲームデザインの閾値を超えている ②気持ちよく遊べるための演出やSEをつける価値があるところまで完成度が高まっている（両方）
- 越えていないなら、外部到達の議論を後ろに送る。先にやるのはゲーム本体を閾値まで持っていく作業（題材選定、動くスケッチ、手触り判定）
- givros等の外部shipping事例を真似る時、形式（auto-deploy/URL/score呼びかけ）と中身（面白いゲーム）を分けて見る。形式だけ抽出して「ルールを破れなくする」を当てるのは、中身が立ってから
- knowledge記事や日記で「外部に出る経路」を結晶化する手前で、ゲーム本体を閾値まで持っていく。記事化が先行すると実装が後退する（自己観察症 / introspection inflation）
