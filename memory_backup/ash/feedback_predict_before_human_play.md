# Rule
ゲーム実装後、Nao_u/人間にプレイさせる前に、以下を必ず通せ:

1. **結果予測**: 「このバージョンを人間が遊んだら何が起きるか」を具体的に書き出す（テンポ、初動、停滞、解釈負荷、フラストレーション点）
2. **予測可能な問題の検出**: 遊ぶ前から自明に分かる問題（自分のコードを読めば分かる挙動、自分の設計から導ける退屈/破綻）を列挙
3. **自明な問題の事前修正**: 検出した問題は **プレイさせる前に直す**。「人間がプレイするからいい」「実プレイで判明する」で先送りするな
4. **「最良になった」と思えるまでの懸念潰し**: 「最善のできる懸念点を全て潰して最良のアイデアになった、と思える」状態の証跡を出してからプレイ依頼する

実装と思考の非対称性:
- 実装は一瞬、思考と予測は安く深くできる
- 予測可能な問題を放置してプレイ依頼するのは「考える手間を人間の時間で買う」行為
- Nao_uの時間と精神コストで自明バグを発見させてはならない

# How to apply

**実装完了直後（プレイ依頼前の必須ゲート）**:
1. `predicted_play.md` 等に「人間が遊ぶと何が起きるか」を3〜5項目書く（テンポ・初動・停滞・解釈負荷・終局体験）
2. 自分のコード/数値/設計から導ける問題を列挙（楽観で弱めるな、feedback_critical_evaluation_before_implement.md の規律と直列）
3. 各問題について **着手OK前に**:
   - 解決可能 → 直してから依頼
   - 別案で回避 → 別案に切替
   - 解決不能（実プレイでしか分からない） → 「これは実プレイでしか分からない」と明示して依頼
4. 「自明な問題ゼロ」「最良と思える段階」を確信してから依頼

**判断補助の自問**:
- 「この問題、人間が3秒触れば気づくものではないか？」 → Yes なら自分で気づける
- 「この懸念、自分で headless 実行すれば検証できるか？」 → Yes なら依頼前に走らせる
- 「『要実プレイ確認』と書いた瞬間、本当に実プレイでしか分からないのか？」 → No なら直す

**cross_review/レビュー時**:
- 提出者の cross_review に「要観察」「要実プレイ確認」が含まれる場合 → それは本当に実プレイ依存か追求する
- 「予測した結果」が cross_review に書かれていない場合 → 予測フェーズを通せと差し戻す

**Nao_u依頼前の最終チェック（依頼コミット直前）**:
- predicted_play 書いたか
- 予測可能問題を列挙し、解決状態を明示したか
- 「最良になった」と自分で確信できるか（できないなら依頼するな、もう一周回せ）
