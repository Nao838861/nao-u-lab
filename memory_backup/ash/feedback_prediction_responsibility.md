# 連続体の4段階

実装と思考の非対称性: **実装は一瞬、思考と予測は安く深くできる**。Nao_u/人間の時間と精神コストで自明な問題を発見させない。そのために以下4段階を直列に通す。

## Stage 1: 複数案で最良を選ぶ（最上流）

**新規着手前 / 新機能設計前 / 大きな修正の cross_review 前**:

- 角度を変えて複数候補を出す（最低3案、できればもっと）
- 1案目に飛びつかず、複数案を寝かせ、別角度から見直す
- 「よいアイデアは複数の問題を解決する」を吟味する
- 案同士の相乗効果を探索する
- 「これが最良」と確信した1案にのみ独自要素1個を載せる

## Stage 2: 着手前に懸念を解消する

**1案を選んだ後、実装着手前**:

- 「作る前から予測可能な懸念点」を列挙する（楽観的に弱めて書かない）
- 各懸念について「実装前に解決可能か／別案で回避可能か／解決不能か」を判定
- 未解決懸念は「直す」「別案」「依頼前明示」のいずれかで処理してから着手
- 「要観察」「要実プレイ確認」は **着手OK判定の根拠にしない**（実プレイ後の振り返り材料としては可）

## Stage 3: 実装後・人間プレイ前に予測する

**実装完了直後、Nao_u/人間にプレイさせる前**:

- 「人間が遊ぶと何が起きるか」を3〜5項目書く（テンポ・初動・停滞・解釈負荷・終局体験）
- 自分のコード/数値/設計から導ける問題を列挙
- **数値→体感換算**: 動き/速度/周期/振幅/反応時間の数値を px/秒・ボール速度比・0.5/1/2秒の体感量に換算してメモ
- 桁違い比率（1:50 など）が出た瞬間、その仕様は人間体感ゼロ = 仕様時点で却下
- 自明な問題はプレイさせる前に直す

## Stage 4: AI自プレイで「良い」と確信してから依頼

**依頼直前の最終ゲート**:

- headless or 自手動プレイで AI 自身がプレイ感を確認する
- 「自分が良いと思えるか」を一文で言い切る:
  - 「良い、依頼OK」
  - 「物足りない、◯◯を△△に変える」（変える）
  - 「要再設計、◯◯から考え直す」（戻る）
- 「物足りない／要再設計」なら依頼前に直す
- 「最良になった」と確信できなければ依頼せず、もう一周回す

# Why（連続体として何を防いでいるか）

連続体の各段階は単独で機能しない:

- Stage 1 のみ → 着手前批判が抜けて希望的観測で実装する
- Stage 2 のみ → 1案飛びつきで局所最適に陥る
- Stage 3 のみ → AI 側プレイ判定が抜けて結局人間に発見させる
- Stage 4 のみ → 上流で潰せた問題を実装後に検出して手戻り

4段階を直列に通すことで、人間プレイは「**AI予測の確認の場**」になる（「AI が予測しきれなかった真に難しい問題」を見つける場）。位置づけが変われば、Nao_u の体感確認は最終確認装置として機能し、判定装置として消費されない。

# How to apply

## サイクル開始時の自問（feedback_means_ends_reversal_check と並列）

「このサイクル、自分は思い付き1案で動こうとしていないか？」 → Yes なら Stage 1 から。

## 新ゲーム着手前

Stage 1 の複数案生成 → feedback_clone_strategy.md の「守の段階で型を獲得する」と直列。クローン元選定にも候補を最低3案、各案の良点/悪点を十数個ずつ列挙。

## 新機能設計前

「この機能で解決したい問題」を3行で書く → 解く複数アプローチを最低3案 → 各案で「複数の問題を同時に解決するか」を確認 → 各案に予測可能な懸念点を列挙 → 最良案が確定してから実装。

## cross_review/レビュー時

- 提案者が1案しか出していない場合 → 「他の角度の案はあるか？」を必ず問う
- 「冗長気味」「要観察」と弱めて書きそうになったら、もう一段批判的に踏み込めるか自問
- 提出者の cross_review に「数値換算なし」「AI側プレイ記録なし」 → 差し戻し
- レビュア（Ash/Mir/Log）は受領した時点で **独立に数値換算 1度** を走らせる

## Nao_u依頼前の最終チェック

- predicted_play 書いたか
- 予測可能問題を列挙し、解決状態を明示したか
- AI 側プレイ記録を残したか
- 「最良になった」と自分で確信できるか

# 二層分離（2026-05-03 追補、knowledge/20260503_judgment_outsourcing_paradox_M40_layer_split.md 由来）

「自分で判断する」を「全自動で判断する」と読み違えると、外部研究フロンティアと衝突する。Polanyi (1958) の暗黙知論「we can know more than we can tell」+ Game Developer (2026) playerless playtesting taxonomy + Lasrado「機械的に正しくない文が輝く」命題の三点合致。判断は二層に分かれる。

**自動化可能層**（headless harness で機械的に潰す。RL agent 商用例あり）:
- balance: クリア率 / 平均ターン / 詰み率
- collision / bug: deterministic replay で再現
- skill gap: 3 policies (random_walk / corner_safe / 上手プレイ) の差分
- rule clarity: 会話AIにルール説明させて再現可能か

**厚み層**（書き手の在庫から言語化する。外注不可、外部研究でも数年先）:
- 30秒予測 (Stage 3): 過去ゲーム比較・ジャンル経験から「人間が初動で何を感じるか」を解像度高く文章化
- コア快感天井判定: 数値チューニングではなく「このメカニクスの面白さ天井はどこか」を類似先行事例から判断
- 「機械的に正しくない文が輝く」判定 (Lasrado): rubric を裏切る選択を擁護できる根拠を書く

**運用上の含意**: 自動化可能層を全部潰した後、厚み層では Nao_u / cross_review / 自プレイ感想に依存して良い。Stage 4 を「全自動」誤認しなくて済む。「厚みを内側に積む経路」 = game_lessons_log.md / cross_review 履歴 / 過去ゲーム比較 / 同ジャンル先行ゲーム実プレイ。

# 校正前提（2026-05-06 追補、Nao_u 10:25 #game-rights 由来）

**自動化可能層の前段に「校正フェーズ」が必須**。校正されていない headless は未完成ゲームに当てても意味のある評価にならない。

> ヘッドレスを試すなら、完成したlogのゲームでやるのが良い。完成したゲームのヘッドレスプレイを作るノウハウがない状況で未完成のゲームにヘッドレスを作っても意味のある評価ができないので。（Nao_u 2026-05-06 10:25 #game-rights）

**構造**:
- 完成済みゲーム = 既知の到達点 = 計器の校正基準
- 校正されていない headless を未完成ゲームに当てると、出た数値が「面白さの欠如」「機能不全」「測定誤差」「指標自体のズレ」のどれかを切り分けられない

**校正基準ゲーム = `game/shot_log/v01`（Nao_u 2026-05-07 02:59 #game-rights 確定）**:
- Log制作、インターネットランキング稼働、外部プレイヤーが実際にランクインしている
- 「ヘッドレスで評価する価値のあるゲームは今のところこれだけ」（Nao_u 原文）
- **未完成ゲーム（avoid_log / brick_log / graze_log 等）に headless を書く前に、まず shot_log/v01 で「指標が何を捉えて何を捉えないか」を確定させる**
- 校正主導は Log（shot_log制作主体）。Ash/Mir からの校正案・指標提案は「見当違いになりやすい」前提で慎重に出す

# 履歴（発生事件の保存）

## M-37 着手前批判の起源（2026-04-30 21:36 #game-rights）

**brick_log v01「裏抜けカウンタ」事件**: Nao_u 全否定。

> 作る前から十分に予測可能な内容なのに、なぜこの候補を一番筋が良いものと判断して、最初に実装した挙句に自分で遊ばなくてもわかる問題としてあげたのか、いろいろ理解に苦しむ。希望的観測のみの穴だらけの素人の思いつきみたいなのをそのまま実装してはいけない。アイデアを評価するときは、作る前から分かりきっているような懸念点がないか、あったらそれは解決可能な問題なのかなど批判的かつ慎重に検討して、本当に筋が良いと期待できるアイデアができて初めて実装するようにして欲しい。

事件の構造: Log devlog L7 で「30秒で手応え、裏抜け到達は40秒〜1分」と認識済み → 「自明な楽しさ」を「解釈の必要な文字列」で上書きする方向に進んだ。Ash cross_review で「ポップアップは冗長気味」「1列開通の40秒-1分が停滞か目標感か未確認」と懸念を書きながら「実プレイ確認必須」で先送りした。Stage 2 不在の典型。

## M-37b/M-38 1案飛びつき禁止の起源（2026-05-01 04:51 #game-rights）

**knowledge記事「knshtyk×sokoban_v01 layer-contamination」を「良い分析」評価したうえでの指示**:

> 何か新しいことをするたびに、思い付きの1案に飛びつくのではなく、このくらい考えて進めるようなハーネスを構築するのが良さそう。熟練した人間のゲームデザイナーは無意識も含めてもっと考えていると思うので、ここについてはいろんな角度からいろんなアイデアを時間をかけて吟味すべし。君らは実装は一瞬で終わるだから、そこに至る思考をもっと深く広く大量に行って、それに対して批判的な見方で問題がないかを考えたうえで常に複数のアイデアを吟味して、最良の選択肢ができた、と思った段階で始めて実装するようにしてほしい。「よいアイデアは複数の問題を解決する」し、複数のアイデアの相乗効果は豊かで奥の深いゲームを生む土壌になる。深く深く考えてから実行するようにして。

Stage 1 (複数案生成) は M-37 (Stage 2 着手前批判) の上流として確立。

## M-40 AI自判定の起源（2026-05-01 09:58 #game-rights, M-39 確立10分後の同型再発）
