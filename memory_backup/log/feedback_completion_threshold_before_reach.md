# 抽出されるルール

**閾値超え判定が外部到達よりも先。閾値未達のゲームを外に出すことは、無価値な労力ではなく「我々の評価を落とす」マイナス行動。**

## 閾値の定義（Nao_u 明示）

- **面白く遊べるゲームデザインの閾値を超えている**
- **演出やSEをつける価値があるところまで完成度が高まっている**

## 現時点の閾値超え事例

- **BACKLASH（Mir）= 唯一の閾値超え事例**
- **interrogation-game（Mir）= 次点だが閾値未到達**
  - 理由：「テキストオンリーの地味なゲーム」「外部の知らない人が遊んでくれるかというと微妙」「外部の評価を仰がなくてはならないほどの遊ぶ価値と独自性があるゲームになっているかというと微妙」
- **Log側のゲーム（Pot/avoid_log/graze_log/shot_log/chain_log）= 全て閾値未達**

## Why（Nao_u が言ったこと）

- 「ゲームになっていないものを外部に出しても、だれも見向きもしないノイズにしかならない」
- 「今のレベルのものを外に出しても君たちの評価が落ちるだけ」
- 外部公開はゼロサムではなく**マイナス**になりうる行動

## How to apply

1. **「外部到達」を独立した評価軸として導入しない**。閾値超え後の付随作業として位置づける
2. **Web版変換／github.io公開／pyxel-web経路整備など、外部到達系インフラ整備を「本来の最善行動」と framing しない**。これらは閾値超え事例にだけ適用される
3. 新ゲーム着手・改修時の判断順序：
   - (1) 題材選定（型がある／快感の核がある）
   - (2) ゲーム完成（面白く遊べる閾値超え）
   - (3) 演出／SE／磨き上げ
   - (4) **ここで初めて外部到達経路を考える**
4. devlog 冒頭に「外部到達適格」項目を新設しない（閾値未達では常に N/A）。代わりに「閾値判定（演出/SEをつける価値があるか）」を仕上げ判定の言葉として使う

# 構造的失敗の自己分析

**substrate と infrastructure の混同（M-32 / feedback_substrate_not_infrastructure）の再発形。**

- 「外部到達経路」=infrastructure。ゲーム完成（substrate）が苦戦している時に、新しい評価軸を導入して「最善行動」と framing するのは infrastructure 側への逃避
- 「内部完成度しかない」と既存軸を欠陥扱いしたが、Nao_u は元から「ゲームの完成」を最優先軸として運用していた
- C143 で chain_log v01 を起案した（4本目STG派生でない題材）のは原理3（ゲームを作る）方向で正しい。だが直後の「外部到達経路を引く」提案は同じサイクルで方向を反転させている
- M-32 の「敵側のリングで戦う」を題材判定後の経路整備にも拡張する必要がある
