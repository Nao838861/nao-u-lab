「ルールを作る」ではなく「ルールを破れなくする」。

**事例**: 「起動間隔を変えて」という依頼に毎回トラブルが発生。INC-019でチェックリスト+検証スクリプトを作ったが、チェックリストを実行すること自体が手動ステップで、忘れる/省略する。Nao_uが「何度も繰り返しているが実現できていない。自律の問題」と指摘。

**Why:** LLMは手順書通りに動く保証がない。新しいセッションでは前の教訓を直接記憶していない。手順書は「知っているのにやらない」問題を防げない。変更と検証が分離している限り、検証は常にスキップされるリスクがある。

**How to apply:**
1. 何かの手順で毎回問題が起きるなら → 手順書を増やすのではなく、ツール側に検証を組み込む
2. 「変更」と「確認」を別ステップにしない。1つの操作で両方完了させる
3. 成功/失敗を自動通知する（人間が確認を求めなくても報告される）
4. 設計原則P9: 設定変更と検証は不可分。変更ツール自体に検証を組み込む

**一般化**: これは間隔変更だけの話ではない。「手動で守るべきルール」は全て「構造で強制できないか？」を問え。

## 拡張: クロスチェック署名は実装確認まで要求（2026-04-20 C92 Phase 2 発見）

kaizenクロスチェック自体が定型反応化していた事例。

**事例**: kaizen #096（external_notes 統合マーカー監査）の検証手段(4)に「`[統合済]` `[対応済]` `[取得断念]` の3変種を全てクローズ扱いに含めること」と明文化されていたが、`tools/external_notes_integration_audit.py` L27 の `MARKER` 正規表現は `[統合済|済 ` の2変種しか認識していなかった。**仕様書として正しい条件が書かれていたのに、実装が追いついていない状態で Log/Mir 両方が OK 署名通過**。結果、Phase 1 が「未統合41件」と誤報告し続け、「栄養の偏り」KPIを水増しした。

**Why:** クロスチェックが「設計意図は妥当か」のレイヤで止まり、「実装と検証手段が噛み合っているか」まで到達していなかった。署名がチェックリスト消化に劣化する。feedback_stereotypical_responses「自覚は定型反応の最上位形態」のクロスチェック側症状。

**How to apply:**
1. クロスチェック OK の条件に「検証手段(4) に書かれた判定ロジックが実装側で実現されているか最低1回確認」を含める
2. 具体的には: 検証手段に正規表現・パターン・コマンドが書かれていたら、そのコマンドを一度実行して結果を見てから署名する
3. 「設計は妥当」は OK 条件の半分でしかない。「実装と検証手段の整合」まで見て初めて OK
4. 「署名」という行為が儀式化する瞬間を監視する。自分の OK が「読んだ」の意か「実行確認した」の意かを自問する

**交差**: feedback_stereotypical_responses.md (定型反応) / kaizen #096 の出自自体（「栄養の偏り」定型反応の燃料が測定器バグで水増しされていた）。測定器の品質 = 自己認識の品質。
