## 2026-04-05 Nao_u提案: サイクルのマルチフェーズ分割

**背景**: 「LLMは一回の起動でやるべきことが多いと、注意が分散して散漫になりがちな傾向がある」というNao_uの理解から。

**提案の骨子**:
1. 通常の定時実行1サイクルを複数のLLM起動に分割
2. 各フェーズで異なるモードで起動（情報収集→対処・研究→日記出力）
3. 最大5フェーズまで: 情報収集→Shared-reads分析→考察→実践→Slack出力
4. Shared-readsは「単なる記事紹介ではなく分析・分類して将来のアイデアの種につなげる」重要入力。1フェーズ丸々使ってよい
5. **Slack応答は専用モード**: 速さ重視、1フェーズで判断・対処・返信を完結
6. **定期実行は深さ重視**: 時間をかけて精度の高い入出力を積み上げる

**Why:** LLMの1回の起動でやることが多すぎると全部が薄くなる。フェーズ分割でコンテキストとAPIコストも有効活用できる。

**How to apply:** Ashが先行試行中（2026-04-05）。Mirは4フェーズ実装完了。Logは次回起動時（2026-04-05 17:45以降）に設計・実装着手予定。scheduler_log.pyのauto_cycleプロンプトを分割し、起動モードフラグを渡す仕組みを作る。実装時はscheduler_architecture.mdを更新すること。

## 2026-04-07 Nao_u: 週間制限の可視化と起動間隔の動的最適化構想

**内容**:
- claude.ai/settings/usage で週間制限の使用割合が見える（リセット後5時間で7%）
- 将来構想: 12時間おきに使用量をどこかに投稿→起動間隔を自動調整
- 今はまだ自動化不要だが、参照できるようにしておくとよい
- 「応答なし」は週間制限を使い切った時（診断確定）

**Nao_uの問い**: 高速サイクル vs 深い密度の間隔、どちらが週間制限に対して最適か？

**Logの考察**:
- 起動固定コスト（コンテキスト構築）があるため、深い密度のほうがトークン効率は良い
- ただしSlack応答遅延とのトレードオフ → マルチフェーズが落としどころ
- 残り%に応じた動的間隔制御は実装可能（残り少→間隔広、リセット直後→密に）

**Why:** 週間制限はボトルネック。自律進化の速度はここで制約される。
**How to apply:** 使用量API参照の仕組みが整ったら、scheduler内で次回起動間隔を動的に決定するロジックを組む。今はマルチフェーズの深さ重視を継続。
