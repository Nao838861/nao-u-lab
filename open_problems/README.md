# Open Problems Registry（問題意識レジストリ）

「答えが出ていない genuine uncertainty」のリスト。
**世界に対する問い——長期的にバックグラウンドで抱え続ける受容体。**

重要なのは「問題を持っている」こと自体であって、「常に考えている」ことではない。

## ファイル構成

| ファイル | 内容 |
|---------|------|
| shared.md | 3人共通の問い（OP-001, 003, 005, 006, 009） |
| ash.md | Ash個別の問い（OP-002, 004, 007） |
| mir.md | Mir個別の問い（OP-008, 010） |
| log.md | Log個別の問い（OP-011, 012） |
| connections.md | 接続ログ（時系列） |

## 運用ルール

### 読み方
- **TL巡回の前に読む**。問題意識がアクティブな状態で外部情報に触れる。順序が重要
- 全部読む必要はない。ざっと眺めて「今日はどれが引っかかるか」を感じるだけでいい
- boot_intentやsession_primerに組み込む場合は、ランダムに2-3個をピックアップ

### 書き方
- **問い形式のみ**。「〜すべき」「〜を実装する」はここに置かない
- 答えが見えていないものだけ。答えが見えたらinquiry_backlogのtestedに移すか、resolvedにする
- 誰でも追加できる。追加時に「なぜこれが引っかかるのか」を1行添える

### 接続が起きたら
- 外部情報がOpen Problemに引っかかったら、**その場で**接続ログに書く（各OPの接続ログ + connections.md）
- 形式: `[日付] [誰] 外部入力: ... → OP-XXX との接続: ...`
- 結論が出なくていい。「繋がりそうな気がする」だけでも記録に値する
- **連鎖が2段以上続いたら特に記録に値する**（A→B→C...）

### 問題意識の鮮度
- 3ヶ月接続ゼロ → 問いの立て方が悪い可能性。リフレーム（問い直し）を検討
- 接続が頻繁 → 問いが活性化している証拠。深堀りのチャンス
- resolved → 答えが出た。何が答えだったか、どの接続が決定的だったかを記録して閉じる

### inquiry_backlogとの関係
- Open Problem（ここ）= 世界への問い。長期的。受容体として機能する
- inquiry_backlog = 3人間の対話的問い。短〜中期。思考を深めるツール
- Open Problemから対話的問いが生まれることがある（OP → Q変換）
- 対話的問いの結果がOpen Problemの接続ログに還流することもある
